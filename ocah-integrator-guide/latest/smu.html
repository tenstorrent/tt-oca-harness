SMU Top-Level Integration

The System Management Unit (SMU) comprises three peer subsystems: the System Management Controller (SMC), the Debug & Test Ports (DTP), and the Security Processor (SEP). The subsections below describe each subsystem’s interfaces independently, followed by the SMU Composition section that explains how they are wired together inside the SMU and how to select between the smu.sv logic-level core and the smu_wrapper.sv reference integration.

1. Address Map Integration

The OCAH address map has three levels, and the assignment contract splits across the integrator, SEP firmware, and SMC firmware. Assign and program them from this section; the deeper subsystem and crossbar sections referenced below give the per-block detail.

  • Chiplet envelope (integrator). The SoC/chiplet address map assigns each subsystem a global base and reserved size, and the adopter’s fabric decoder routes those ranges to the SMU. The SMU crossbar preserves offsets and does not constrain envelope size, so the integrator owns non-overlap and containment at the SoC level.

  • SEP and SMC chiplet apertures (firmware). Each subsystem exposes a chiplet-visible aperture whose base and size are programmable at runtime. Inbound transactions to an aperture are remapped global-to-local before they reach the subsystem.

  • Local-alias views (fixed in RTL). Internally each subsystem addresses its own resources through a fixed local map: the SMC at 0xC000_0000 (see Address Map and Aperture), the SEP through its own local map. These are RTL-fixed and not integrator-assigned.

1.1. Register collateral

The machine-readable address map ships in the repository tree; integrators consume it from the release checkout or tarball rather than a separate package. The source of truth is distributed by ownership: each subsystem or IP keeps its canonical register sources and generated outputs beside its implementation. The integration/ directory centralizes symlinks to that distributed collateral so an integrator does not have to discover every owner-local path.

integration/rdl/<subsystem>/ is a flat, self-contained list of the SystemRDL files required by that subsystem. Filenames remain unchanged, and shared dependencies appear in every subsystem that needs them. Non-RDL support files needed by relative includes remain at the integration/rdl/ root — for example, integration/rdl/i3c_defines.svh sits there because both integration/rdl/smc/registers.rdl and integration/rdl/smu/registers.rdl reach it through the I3C core’s own parent-relative include (../i3c_defines.svh), and that relative path only resolves if the header is one directory above every subsystem folder that needs it. The matching generated IEEE 1685-2014 component descriptions use the same flat subsystem organization under integration/ipxact/<subsystem>/.

These directories are generated symlink indexes; run python3 scripts/collect_integration.py after adding or moving collateral. Their canonical targets remain under hw/sys/<sys>/regs/, hw/ip/<ip>/regs/, and vendor/…​ — the regs/ element of every component’s directory layout, described in the Getting Started Guide. Other generated outputs remain under each owner’s regs/gen/{c,sv,svh,py,ral,adoc,html,ipxact}/ directory.

For the architecture-level responsibility split between the integrator, firmware, and the internal SEP/SMC maps, see OCAH Memory Map.

2. Immutable ROM FW Integration

OCAH contains three immutable ROM FW images: the SMC production ROM FW, the SEP production ROM FW, and the Key Manager production ROM FW. Each image has two integration contracts. The adopter connects and configures the corresponding ROM macro, and the final ROM FW image must be present before its processor leaves reset. Where ROM FW must initialize or access an adopter-owned peripheral outside OCAH, the image may also expose build-time integration hooks.

2.1. Weak-symbol override method

An immutable ROM FW image may provide selected vendor-neutral integration hooks as weak symbols. Supply an adopter implementation as a strong definition of the same symbol before the final image is frozen. The strong implementation must program the same adopter-owned IP instantiated by the RTL integration, and its signature, ABI, return values, and documented semantics must match the weak declaration.

This mechanism applies only when the ROM FW needs to interact with a peripheral outside OCAH. It is a build-time image-composition mechanism, not a runtime extension mechanism. Include the adopter implementation in the final ROM FW build so that it replaces the weak definition at link time.

Inspect the final ELF or linker map after linking. For example, riscv64-unknown-elf-nm must report each selected implementation as a strong symbol rather than W; successful linking alone does not prove that the weak default was replaced.

2.2. SMC ROM FW integration

Connect smc_rom_intf_req_o and smc_rom_intf_rsp_i to the adopter’s ROM implementation. In the current four-core configuration, the request provides the ROM clock, enable, and 14-bit 64-bit-word address, and the response returns one 64-bit word. This is a direct memory interface, not AXI-Lite. The 128 KiB ROM FW image must be present before the first boot; its build is under hw/sys/smc/bootrom/prod/.

Connect the ROM macro configuration input reached as rom_cfg_i and mem_cfg_i according to the selected macro’s contract. OCAH forwards these 11 bits without assigning technology-specific semantics; the reference smc_ip_integration.sv ties them to zero. Set the eFuse shadow value that drives the CPU’s rom_flip_endianness_i path to match the byte order of the image and ROM macro. Deasserted passes each 64-bit read word unchanged; asserted reverses its eight bytes.

3. System Management Controller (SMC) Integration

The System Management Controller (SMC) is a subsystem responsible for power management, clock control, reset sequencing, and peripheral interface coordination. The smc.sv module exposes logic-level interfaces; all technology-specific components (PLLs, PVT sensors, eFuses, memory macros, GPIO padrings) are instantiated externally by the adopter. See the SMU Module Variants section for how the reference wrappers demonstrate this integration.

For detailed architectural documentation about the SMC internal design, refer to hw/sys/smc/doc/. The public integration examples are hw/top/smc_wrapper.sv and hw/top/smc_ip_integration.sv.

3.1. Clock and Reset

The SMC requires three external clock inputs: clk_smc_i (primary system clock driving the CPU cluster, fabric, and peripherals), clk_periph_i (peripheral clock driving the peripherals), and clk_ref_i (reference clock for timing-sensitive operations). All must be generated externally by the adopter’s PLL infrastructure; the SMC provides AXI-Lite control outputs for PLL configuration (see Peripheral Interface Connections). The peripheral clock is used to drive the I3C interface, I2C interface, UART interface, and AVSBus interface.

Hold rst_cold_ni asserted (low) while power supplies and clocks stabilize. Assert powergood_i once supplies reach nominal, then deassert rst_cold_ni (drive high) to start the boot sequence.

The SMC generates AASD (async-assert / sync-deassert) reset outputs: rst_primary_smc_clk_no for the main clock domain, rst_primary_periph_clk_no for the peripheral clock domain, and rst_primary_ref_clk_no for the reference clock domain. These ensure clean reset release without metastability across the system hierarchy.

Reset domain overrides are delivered through a single typed input, jtag_reset_ctrl_i (smc_pkg::jtag_smc_reset_ctrl_t), which carries all SMC reset override enables and active-low values. The DTP drives this input through the JTAG IC_RESET mechanism (see SMC-DTP Internal Interconnection); most integrations leave all override enables deasserted.

3.2. Address Map and Aperture

The SMC has a chiplet-visible aperture and an internal local address view. Internally, the SMC uses a fixed local base address of 0xC000_0000 and a fixed local window size of 16 MiB. SMC-local addresses (registers, memories, remapped regions) are defined as offsets from that base. The chiplet-visible aperture is adopter-defined: the chiplet or SoC address map assigns the global base and size that external masters can use to reach SMC through the SMU crossbar.

When integrating the SMC into a chiplet or SoC, the adopter assigns a system base address and reserved size for the SMC window. The system base (e.g. 0x0800_0000 in a chiplet address map) may be different from the SMC-local base 0xC000_0000. Firmware programs the SMC GLOBAL_BASE / REGION_SIZE CSRs during early boot to match that assignment. The adopter’s fabric or address decoder must route the reserved system range to the SMC block so that offsets are preserved: system base + offset maps to SMC-local 0xC000_0000 + offset.

The SMC fabric uses three registers in the CPU Control block (0xC001_0000) to distinguish local from remote addresses:

  • LOCAL_BASE (read-only, fixed at 0xC000_0000): The local alias base. Together with REGION_SIZE, this is the address space the SMC CPU and internal fabric use to access SMC resources.

  • GLOBAL_BASE (read-write, defaults to 0x4000_0000): The system-level base address. Firmware must program this during early boot to match the adopter’s system address assignment, enabling the SMC to issue outbound transactions using global system addresses.

  • REGION_SIZE (read-write, resets to 0x0100_0000 / 16 MiB): The size of both the local alias window and the global aperture. It sizes the SMC input fabric’s local/global split as well as SMU-level routing and SEP-to-SMC decode. Firmware must not program it to zero, and must keep LOCAL_BASE + REGION_SIZE inside the 32-bit SMC-local address space.

For full details on alias remapping and outbound routing, see the SMC Fabric documentation (hw/sys/smc/doc/fabric.adoc).

For a detailed breakdown of all components within the SMC local map, refer to the SMC Memory Map documentation (hw/sys/smc/doc/memmap.adoc).

3.3. AXI Interface Configuration

The SMC provides three distinct AXI interface groups serving different access paths. The sys_axi_in interface accepts requests from external system masters requiring access to SMC-managed resources. This interface uses a 56-bit address space with 64-bit data width and 6-bit transaction IDs. Connect this interface to your system fabric for normal operational access from application processors or DMA controllers.

The sep_axi_in interface provides dedicated access from the Security Processor (SEP) subsystem. This interface shares the same sizing parameters as the system input but operates independently to maintain security domain separation. Use this interface only when integrating alongside the SEP subsystem. The interface may remain unconnected if your integration does not include SEP.

The output_axi interface carries filtered and remapped requests from the SMC to external system resources. This interface uses an 8-bit transaction ID field to accommodate merged traffic from multiple input paths. Connect this interface to your system interconnect to allow SMC components access to external memory and peripherals. An AXI VIP or equivalent BFM is a suitable stand-in during integration verification before the real system fabric is available.

The jtag_axi_in interface provides debug access through JTAG mechanisms. This interface uses reduced 2-bit transaction IDs and connects to your JTAG debug infrastructure.

3.4. GPIO Pad Integration

GPIO pad integration requires careful attention to function assignment and pull requirements. The GPIO table below lists each signal, bump location, function, recommended pull, and integration notes. Default input/output direction is defined by smc_padring_pkg::DefaultDirectionMap, not by the table.

The public hw/top/smc_wrapper.sv and hw/top/smc_ip_integration.sv examples show the pad connections. For bidirectional pins, implement proper tri-state buffers controlled by the core2pad_en_o signals. Connect multiplexed UART, I2C, I3C, and SPI pins to external devices according to the function assignments in the GPIO table.

Configuration straps are captured separately from the GPIO table. Establish them before cold reset deassertion and keep them stable during capture. The generated reset-unit STRAPS_LO and STRAPS_HI register descriptions define the decoded bit assignments, including BYPASS_SRAM_REPAIR at STRAPS_LO[13] and TEST_EN at STRAPS_LO[14].

3.5. Peripheral Interface Connections

The SMC exposes logic-level interfaces to several technology-specific subsystem components that the adopter instantiates externally. The subsections below describe each connection in turn.

3.5.1. Adopter Peripheral Window

The smc_external_req_o and smc_external_resp_i signals form a 32-bit AXI-Lite interface to the adopter’s own peripheral register maps. Any technology- or product-specific block that SMC firmware needs to reach sits behind this window rather than on a dedicated per-peripheral port.

The window is the recommended home for the control/status registers of logic that the SMC must configure or monitor but that the SMC itself does not implement — padring configuration logic, clock generation, on-die sensors, memory-technology SHIMs, and similar adopter-owned blocks are typical examples. For example, runtime reconfiguration of pin directions, pull settings, and peripheral multiplexing is expected to be reachable here. The SMC decodes the aperture and forwards the transaction; what lives behind it is entirely adopter-defined.

The window is split into a mandatory region, whose contents and placement the SMC memory map fixes and every integration must implement, and a supplementary region for anything else the adopter chooses to expose. For placement and the full register layout, refer to the SMC Memory Map documentation (hw/sys/smc/doc/memmap.adoc).

3.5.2. eFuse Interface

This guide uses eFuse and OTP interchangeably for the same one-time programmable bank and the SHIM that fronts it. Port names mix both (efuse_*, otp); they refer to the same interface.

The eFuse interface consists of two parts:

  • efuse_bank_ctrl — a 32-bit AXI-Lite interface used to access the SHIM control CSRs (for example, foundry-specific bank timing such as the initialization delay before sensing can begin).

  • efuse_shim_command — the custom fuse command interface used to issue read, program, and program/read-back operations to the eFuse bank.

Adopter responsibility. The efuse_shim_command interface is intentionally generic and technology-neutral. The adopter must implement an Interface SHIM that converts these generic commands into the hardware signals required by their OTP macro. The conversion is driven by the adopter’s own read and program state machines inside the SHIM; OCAH only defines the command/response contract, not the macro-side signaling.

The command and response payloads are exchanged as packed structs:

// Controller -> SHIM
typedef struct packed {
    addr_t                address;             // Target address (in bits)
    logic                 program_data;        // Data to program (when programming)
    access_length_words_t access_length_words; // Number of WORD_WIDTH words to access
    command_t             command;             // READ / PROGRAM / PROGRAM_READ_BACK
    logic                 valid;               // Request valid
} fuse_command_req_t;

// SHIM -> Controller
typedef struct packed {
    data_t data;   // Read data (one WORD_WIDTH word)
    logic  status; // Operation status (0 = OK, 1 = error)
    logic  valid;  // Response valid (qualifies `data` for one cycle)
} fuse_command_resp_t;

Fuse sensing protocol. During automatic sensing the controller issues a single read with access_length_words set to the entire bank (all NUM_WORDS words). The SHIM is expected to stream the bank back one WORD_WIDTH word at a time: for each OTP access it drives the read data onto fuse_command_resp_o.data and asserts valid for exactly one cycle. The controller consumes one word per cycle that valid is high, advancing to the next eFuse word on each assertion.

valid must be asserted for only a single cycle per returned word. If the SHIM holds valid high for two cycles, the controller will sample the same data value a second time and count it as the data for the next eFuse word, shifting all subsequent words and corrupting the sensed shadow contents. The adopter’s SHIM FSM is responsible for producing a clean one-cycle valid strobe per WORD_WIDTH access.

The shadow_regs_o output provides read-only access to the sensed fuse values. During bring-up the SMC automatically senses the fuse contents and propagates them through the shadow registers; the smc_fuse_sense_done_o signal indicates completion of this sensing operation.

3.6. Memory Subsystem Integration

The SMC includes an embedded RISC-V CPU cluster with associated memory interfaces. See Immutable ROM FW Integration for the ROM FW integration contract.

3.6.1. SRAM and Cache Array Integration

Scratch RAM interfaces (smc_scratch_ram_intf_req_o and smc_scratch_ram_intf_rsp_i) connect to 32 independent RAM banks totaling the scratchpad memory space. Cache memory interfaces for L1 instruction and data caches (smc_l1_icache_* and smc_l1_dcache_*) connect to tag and data RAM banks as specified in the port table.

The smc_disable_sram_auto_init_i input controls automatic memory initialization behavior. When deasserted, the SMC automatically zeroes all SRAM contents during bring-up. The smc_init_mem_done_o output indicates completion of this initialization sequence. The SRAM_AUTO_ZERO_DISABLE strap (STRAPS_LO[26]) can disable this automatic zeroing behavior if your integration requires preserved SRAM contents across resets.

3.7. Memory Repair Integration

The SMC implements Built-In Redundancy Analysis (BIRA) memory repair to address manufacturing defects in SRAM arrays. Repair uses redundant memory elements configured with data stored in eFuse memory, replacing defective cells detected during manufacturing test.

Memory repair executes automatically during boot after eFuse sensing completes and before MBIST operations. The process must complete successfully before the CPU cluster can safely access SRAM arrays. Repair is required on every cold reset but can be bypassed during Function Level Reset (FLR) operations for faster recovery.

Control Signals:

  • smc_fuse_sense_done_o: eFuse controller output indicating fuse sensing completion. External DFT logic monitors this signal to trigger repair operations.

  • skip_mem_repair_o: Reset unit output indicating repair should be bypassed. It is driven by the isolation request inputs (isolate_req_pin_sync_smc or the SMC isolation register), not directly by the strap. When asserted, external repair logic should skip operations and immediately assert completion status.

  • ext_boot_seq_done_i: External signal indicating the external boot sequence (memory repair and shadow register override) is complete. Held low to pause reset release until the external agent gives the go-ahead; required before the system can continue its boot sequence

Repair Data:

The SMC fuse map does not allocate storage for repair data. Your external memory repair controller must source it from wherever your manufacturing flow keeps it and apply it to SRAM arrays according to your memory architecture.

Status Monitoring:

Repair completion and success are reported through DFX_CTRL_STATUS.STATUS_SMU at 0xC000_B800. The mem_repair_done bit indicates completion regardless of success, while mem_repair_success indicates successful repair. Both bits are set by the external repair controller. The SMC ROM FW monitors these bits during initialization to verify repair completion.

Bypass Configuration:

The BYPASS_SRAM_REPAIR configuration strap (STRAPS_LO[13]) is captured into the reset-unit strap registers. Keep these three mechanisms distinct:

  • No RTL path drives skip_mem_repair_o from this strap directly. skip_mem_repair_o is driven from the isolation request path.

  • Production ROM reads the strap and, when asserted, skips repair-status validation and writes MBIST_STATUS_MEM_REPAIR_BYPASSED to scratchpad register 15 (SMC_SCRATCH_MBIST_STATUS, 0xC003_90F8). It does not cause the external repair controller to skip physical repair.

  • External repair logic independently honors skip_mem_repair_o to decide whether to bypass physical repair operations.

Use bypass mode only when SRAM arrays are guaranteed defect-free, such as during development or with known-good components.

Integration Requirements:

Provide an external memory repair controller that monitors smc_fuse_sense_done_o to initiate repair, respects skip_mem_repair_o for bypass control, reads repair data from eFuse shadow registers, applies repair configuration to SRAM arrays, asserts ext_boot_seq_done_i and updates DFT Control Status registers with completion status. The controller operates independently of the SMC core and must complete before the CPU cluster accesses SRAM.

For direct access to the eFuse besides from the shim, i.e. from a DFT fuse controller, adopters must ensure the integrated logic will not interfere with accesses from the OCAH’s efuse interface.

During FLR operations, the isolation request path asserts skip_mem_repair_o to bypass repair for rapid reset sequences. Normal cold reset sequences always execute repair unless isolation is already asserted.

3.8. Interrupt Integration

The SMC aggregates interrupts from multiple sources into cpu_interrupts_o, which feeds the PLIC of the embedded RISC-V CPU cluster. The interrupt vector is assembled in hw/sys/smc/rtl/smc_base.sv and hw/sys/smc/rtl/smc_peripherals/rtl/smc_peripherals.sv. The authoritative bit-level map (RTL trace and PLIC source ID note) is maintained in a single place:

SMC CPU interrupt vector map

The SMC PLIC and CPU interrupt vector are internal. sync_irq_o is not the interrupt aggregate — it is the software-controlled SYNC_REG.sync global synchronisation bit in the reset unit, unrelated to PLIC interrupt delivery. Do not connect an external interrupt controller to sync_irq_o.

External interrupt sources visible to the adopter are smc_ext_interrupts_i (SMC external interrupt input vector, width NUM_INT_TO_SMC), smc_ext_mailbox_interrupts_o (outbound mailbox notifications, width NUM_MAILBOXES), gpio_interrupt_o (GPIO edge/level events, width NUM_GPIO_WRAPS), and uart_interrupt_o (UART TX/RX events, width NUM_UART). Drive smc_ext_interrupts_i as an active-high level or as a pulse that stays high long enough to be sampled on clk_smc. The pin is three-flop synchronized; a short asynchronous pulse can be lost. There is no edge-triggered mode. For the full PLIC source map see the SMC Technical Reference Manual.

3.9. Telemetry and Debug Integration

For system-level debug and telemetry, the SMC implements ATB (Advanced Trace Bus) receiver interfaces. The telemetry interface group (telemetry_atdata_i, telemetry_atid_i, telemetry_atvalid_i, telemetry_atready_o) operates in a dedicated clk_telemetry_i clock domain with separate rst_telemetry_ni reset. Connect these signals to ATB trace sources for debug data collection.

At the SMC boundary, ext_debug_bus_i is 512 bits wide; the SMU concatenates the adopter-visible 128-bit input with the SEP’s internal 384-bit bus before driving SMC. The typed xtrigger_ss_i / xtrigger_ss_o ports are the only cross-trigger signals at the SMC boundary. The adopter-visible SMU cross-trigger interfaces are xtrig_ctm_*, xtrig_clk_stop_req_i, and the CTP groups.

Trace memory interfaces (trace_mem_req_o and trace_mem_resp_i) connect to trace RAM instances for storing captured debug data. smc_ip_integration.sv shows an example set of RAM instances that can be adapted to your debug requirements.

3.10. Bring-Up Sequence

The recommended bring-up sequence begins with asserting rst_cold_ni while stabilizing power supplies and clocks. Once all supplies reach nominal voltages, deassert rst_cold_ni to initiate the SMC boot sequence. The SMC immediately begins fuse sensing to read configuration values and security credentials.

Monitor the smc_fuse_sense_done_o signal to detect completion of fuse sensing. Configuration straps sampled during this phase determine boot modes and operational settings. After fuse sensing completes, the SMC releases internal subsystem resets based on the programmed reset sequencing configuration.

The CPU cluster begins executing the ROM FW after reset release. The ROM FW performs additional initialization including peripheral configuration, memory testing (unless disabled), and system health checks. The smc_init_mem_done_o signal indicates completion of memory initialization if automatic SRAM zeroing is enabled.

To support Function Level Reset (FLR), assert cfg_flr_pf_active_i to trigger a warm reset sequence. The SMC asserts isolate_req_o bits for the affected subsystem indices. The adopter’s power controller drives ss_reset_complete_i high once the subsystem reset is complete; the SMC synchronizes this into the readable SS_RESET_COMPLETE register. Isolation remains asserted until cleared by software: SMC firmware must poll SS_RESET_COMPLETE and then write ISOLATE_REQ_SMC_REG to clear the FLR isolation latch. Do not assume isolation releases automatically on ss_reset_complete_i.

See hw/top/smu_wrapper.sv and hw/top/smc_ip_integration.sv for reference bring-up wiring examples covering clock, reset, strap, and peripheral connections.

4. Debug & Test Ports (DTP) Integration

4.1. Configuration

The cross-trigger topology is fixed at elaboration by dtp_pkg, a committed source file at hw/sys/dtp/rtl/dtp_pkg.sv. DEFAULT_NUM_CTP, DEFAULT_NUM_INT_CT, and DEFAULT_NUM_CLK_STOP_REQ there set the XTRIG_NUM_CTP, XTRIG_NUM_INT_CT, and XTRIG_NUM_CLK_STOP_REQ localparams of dtp, so a different port count is applied by editing that package rather than by overriding parameters at the instantiation. The remaining DTP parameters, including XTRIG_INT_CT_MODE and every JTAG_* enable, are set at the instantiation as shown below.

Include the DTP in your build using Bender target dtp, which pulls in the DTP RTL together with the JTAG and cross-trigger IPs it instantiates. The legacy filelist hw/sys/dtp/rtl/config/dtp.f covers only the JTAG portion of the hierarchy and is not a complete DTP recipe.

4.3. Clock and Reset

  • TCK Domain: JTAG logic operates on external Test Clock

  • System Clock (clk_i): Cross trigger logic and JTAG2AXI bridges

  • Power-On Reset (pwr_on_rst_ni): Asynchronous reset for JTAG state machine

4.4. Constraints

  • JTAG interface: 10-50 MHz TCK frequency

  • Cross trigger signals synchronized to system clock

  • DTP remains active during clock stop for debug access

  • External CTP signals require pad ring integration with ESD protection

4.5. STAP Scan Chain Topology

The DTP secondary scan path chains multiple STAPs on a single PTAP-managed scan string. The fixed order on this string is: PTAP, I/O STAP (if JTAG_STAP_IO_ENABLE=1), SMC debug STAP (if JTAG_SMC_DBG_ENABLE=1), SEP debug STAP (if SEP=1 in the SMU), extra STAP[N-1:0], and return to PTAP.

Both the SMC and SEP debug STAP host interfaces are internal to the SMU and are not exported on the SMU boundary. The SMU wires the SMC debug STAP host outputs to the SMC CPU/system JTAG ports (smc_cpu_jtag_*) when JTAG_SMC_DBG_ENABLE=1; when disabled, the DTP bypasses this STAP in the secondary scan chain and drives the internal host outputs low. The SEP debug STAP connects to the SEP JTAG debug port when SEP=1; when SEP=0, the SMU ties sep_stap_tdo_to_dtp = 1’b0 to bypass the SEP STAP return path.

Each STAP host interface is gated by a field of dbg_disable_i, synchronized to TCK inside the DTP. Each field is active-high (1 = path disabled).

5. Security Processor (SEP) Integration

The Security Processor (SEP) is the Root of Trust for the chiplet, providing a physically isolated execution environment for security-critical services such as secure boot, lifecycle control, device attestation, cryptographic acceleration, and key management. This section provides practical integration procedures for adopters integrating the SEP as part of the SMU or as a standalone out-of-context IP.

For detailed architectural documentation about the SEP internal design, refer to the dedicated SEP documentation located in hw/sys/sep/doc/. The SEP hardware overview and interconnect fabric are described in hw/sys/sep/doc/overview.adoc and hw/sys/sep/doc/fabric.adoc respectively.

5.1. Module Overview

The sep.sv module provides the complete SEP functionality with logic-level interfaces. Technology-specific components — SRAM, ROM, and eFuse shims — are instantiated by the adopter outside SEP, following the same vendor-neutral philosophy used for the SMC.

Separately, SEP exposes interfaces for supplementary peripherals an adopter may add on rather than substitute: an external TRNG and an additional SPI controller. These are not technology-specific — SEP contains its own entropy source and SPI host — so the interfaces exist to supplement what SEP already provides, and may be left unused.

When integrated inside the SMU, the SEP’s external interfaces are passed through the SMU boundary with a sep_ prefix.

5.2. Clock and Reset Requirements

The SEP requires two clock inputs. Connect clk_i to the primary system clock driving all SEP internal logic. Connect clk_wdt_i to a 200 kHz clock source for the watchdog timer; this clock must be independent of the system clock so that the WDT can detect system clock failures.

The primary reset rst_ni follows the standard active-low, asynchronous assertion / synchronous deassertion convention. The dbg_rstb_i input provides a separate reset for the EL2 CPU debug module. The wdt_rst_ni input receives the watchdog reset generated by the SMC reset unit. The SEP outputs wdt_timer_rst_req_o when the WDT triggers a reset request.

5.3. AXI Interfaces

The SEP connects to the system through three AXI paths. The smn_outbound_axi master interface allows SEP firmware to access system resources outside the SEP domain, such as SMC registers or external memory. The smn_inbound_axi slave interface accepts requests from system masters requiring access to SEP-managed resources. The sep_ext_to_smc_axi output provides a dedicated AXI path for SEP-to-SMC transactions, connecting to the SMC’s sep_axi_in port.

An additional AXI extension port (axi_extension_axi) enables adopters to attach custom peripherals to the SEP interconnect fabric without modifying the SEP core. When unused, tie the response input to return DECERR.

5.4. Memory Interfaces

All SEP memory macros are instantiated externally and connected through dedicated request/response interfaces. The sep_cpu_tcm interface provides tightly-coupled memory (ICCM and DCCM) for the VeeR EL2 CPU. The sep_sram interface connects scratch SRAM used for firmware data. The sep_boot_rom interface provides the BL0 ROM containing the first-stage bootloader.

The crypto subsystem requires additional memory interfaces. sep_crypto_pka_imem_sram and sep_crypto_pka_dmem_sram connect to the OTBN public key accelerator instruction and data memories respectively. km_rom_mem and km_sram_mem connect to the Key Manager’s dedicated ROM and SRAM macros.

abr_mem connects the Adams Bridge working SRAM. On an idle cycle (re low), ABR expects the channel’s read data to return 0 the following cycle. SEP_ABR_SRAM_LATENCY must equal the macros' native registered-read latency (default 1). Word-write channels are full-word we / re / address / data. sig_z and pk carry one-bit-per-byte wstrobe; map those to the macros' byte-write enables. SEP_ABR_MASKING_EN (default 1) selects 2-share DOM: thirteen 1R1W macros versus nine, plus a second NTT. This changes ABR internal behavior (sequencing, SCA, memory topology), not merely throughput. Give the same value to SEP and to the SRAM instances. When it is 0, do not instantiate the four masked coefficient banks; their response fields read as 0.

5.5. Cryptographic Subsystem Connections

The SEP includes an internal entropy source that requires a ring-oscillator sample clock connected to entropy_rosc_sample_clk_i. This clock must be asynchronous to clk_i and typically runs between 100 and 400 MHz.

5.5.1. External TRNG

For adopters providing an external TRNG, the ext_trng_axil AXI-Lite interface connects to the external TRNG’s control registers, while the ext_trng_axis AXI-Stream interfaces carry entropy data. The ext_trng_irq_i input is routed to the PIC.

SEP decodes the 4 kB TRNG aperture (0x1091_7000 - 0x1091_7FFF) as a single window and forwards every access on ext_trng_axil. It does not decode offsets inside that window: the endpoint is an adopter-defined IP.

The adopter must perform the intra-aperture decode. An address that owns no register must return SLVERR and must not alias onto a live register. When no external TRNG is connected, terminate ext_trng_axil with a DECERR slave.

5.6. eFuse and Lifecycle

SEP has its own eFuse bank. Instantiate a separate SHIM and physical eFuse bank; do not share the SMC’s. The SHIM contract is eFuse Interface. On sep.sv connect efuse_bank_ctrl_* and efuse_shim_command_*. Through the SMU those ports appear as sep_efuse_bank_ctrl_* and sep_efuse_shim_command_*.

SEP senses this bank after its own reset. Watch sep_fuse_sense_done_o. On sep.sv, drive smc_fuse_sense_done_i from the SMC so firmware can see when the SMC fabric is out of reset; the SMU wires that input internally.

Lifecycle and test-mode ports on sep.sv, and what to do with them. Behaviour is in the Technical Reference Manual, not here.

  • secure_tm_req_i signals a request to enter secure test mode. SEP latches it into secure_tm_o when fuse sensing completes, or at cold-reset release if SEC_DIS is already asserted. Secure test mode forces a no-secret, no-fuse-program configuration; it is not an authorization bit. See Test Mode Entry and secure_tm and the Secure Scan Chain in the TRM. secure_tm_o is also an SMU output.

  • security_disable_o is the SEC_DIS token-match result (emergency A0 unlock). On sep.sv, route it to SMC sep_security_disable_i; the SMU does that internally. See Security Disable in the TRM.

  • lc_state_o is the differentially encoded LC_STATE shadow. lc_sigint_err_o is the decode integrity error (fail-closed). Both are SMU outputs. See Life Cycle Controller in the TRM.

  • dbg_disable_o is the typed per-path debug/test disable vector (active-high: 1 = path disabled). On sep.sv, route it to DTP dbg_disable_i; the SMU does that internally.

  • lcc_demote_state_1_o / lcc_demote_state_2_o are differentially encoded in-field debug demotion. They leave the SMU for adopter lifecycle logic and are not connected to the SMC. See in-field debug demotion in the TRM.

  • sep_fuse_dft_disable_o / smc_fuse_dft_disable_o gate DFT-inserted OTP access. Leave them open if no such path is inserted. They are SMU outputs.

OTP debug AXI-Lite (axil_sep_otp_jtag) is connected to the DTP inside the SMU; when SEP=0 the SMU instantiates an AXI-Lite error slave on that path.

5.7. SPI Host Interface

The SEP provides a SPI host controller through the sep_io_spi interface, supporting single and quad modes. The controller’s own interrupt leaves the module as the irq field of sep_io_spi_req_o, so no separate interrupt output is needed.

5.8. Bring-Up Considerations

The SEP boot sequence begins after the SMC completes fuse sensing and releases the SEP reset. The SEP BL0 ROM FW verifies the BL1 software image using non-volatile public keys before transferring control. Feature controls derived from secure boot authentication and lifecycle state govern what operations are permitted after boot.

The jtag_id input must be tied to an appropriate constant in the top-level integration. A rst_vec_i port exists on tb_top.sv for DV reset vector injection; it is not present on sep.sv itself and requires no integration tie-off.

6. SMU Composition and Internal Wiring

The System Management Unit (SMU) combines the SMC, DTP, and optionally the SEP into a unified subsystem. The interface descriptions in the preceding sections apply directly when integrating the SMU, since the SMU inherits all three subsystems' ports. This section covers the module variants available to adopters, how the SMU wires its subsystems together internally, and what additional configuration it exposes.

6.1. Module Variants and IP Integration

OCAH core modules (smc.sv, sep.sv, dtp.sv, and the composite smu.sv) expose logic-level interfaces only. All technology-specific components — PLLs, PVT sensors, eFuse shims, memory macros, GPIO padrings, SPI controllers, and external TRNG — are instantiated outside the core modules by the adopter. This separation keeps the OCAH deliverable technology-neutral.

The repository provides reference wrappers that demonstrate how to bridge the gap between OCAH core interfaces and adopter-specific IP:

  • smu_wrapper.sv wraps smu.sv with pad-level signal handling for clocks, resets, GPIO, eFuse, and JTAG interfaces. It internally instantiates smc_ip_integration.sv for SMC-related vendor IP and (when SEP=1) sep_ip_integration.sv for SEP-related vendor IP.

  • smc_wrapper.sv provides an equivalent reference wrapping smc.sv alone, useful when integrating the SMC without the DTP/SEP subsystems.

Neither the wrappers nor the IP integration modules are part of the OCAH deliverable; they exist as integration guides and for Tenstorrent internal usage. Adopters must develop their own equivalents following the interface patterns demonstrated in these modules. The interface contracts at the module boundaries ensure technology substitution without modifying the verified OCAH logic.

6.1.1. IP Integration Modules

smc_ip_integration.sv demonstrates integration of SMC-side technology components: PLL wrappers (generating pll_cgm_clk_o and pll_awm_clk_o), PVT sensor interfaces, eFuse shims, GPIO padring logic, memory macros (ROM, scratchpad RAM, cache tag and data arrays), and trace memory instances.

sep_ip_integration.sv demonstrates integration of SEP-side technology components: SEP memory macros (TCM, scratch SRAM, boot ROM, OTBN IMEM/DMEM, Key Manager ROM/SRAM), eFuse shim, external TRNG, and SPI controller selection.

6.1.2. Wrapper Clock Architecture

The smu_wrapper.sv reference wrapper accepts pre-generated clocks directly: clk_smu_i (primary), clk_ref_i (reference), and clk_periph_i (peripheral). The smc_wrapper.sv uses clk_smc_i for the primary clock. Clock generation is entirely the adopter’s responsibility. The pll_wrap model included in the DV environment only terminates the SMC’s AXI-Lite PLL control interface; it does not generate functional clocks and must not be used as a synthesis model.

6.2. Clock and Reset Architecture

Connect clk_smu_i to the primary system clock and clk_ref_i to a stable reference source. The DTP operates on TCK for JTAG logic and on the system clock for cross-trigger and AXI bridges. Reset sequencing follows the SMC flow; the DTP JTAG state machine uses pwr_on_rst_ni, which the SMU connects to rst_cold_ni. The SMU internally connects DTP debug paths to the SMC and optionally instantiates the SEP when the SEP parameter is set to 1. The full interconnection details are described in SMC-DTP Internal Interconnection and SEP-Conditional Wiring below.

6.3. SMU AXI Crossbar Address Map

Inside the SMU, the smu_axi_xbar module routes traffic between three AXI4 manager/subordinate pairs: the SEP outbound master (sep_out), the SMC outbound master (smc_out), and the external SMU AXI input (ext_in / smu_axi_in). The corresponding targets are the SEP and SMC inbound subordinates, and the external SMU AXI output (ext_out / smu_axi_out).

Connectivity is described in SMU AXI Crossbar; the split between hardware-fixed behaviour and firmware-programmable apertures is documented in OCAH Memory Map.

The crossbar uses a runtime address map. Only the SEP and SMC apertures are programmable at runtime; the ext_out rule is static:

  • sep_global_base_addr_i / sep_region_size_i come from the sep_cpu_ctrl CSRs SEP_GLOBAL_BASE_ADDR / SEP_REGION_SIZE, exposed at both the sep.sv and smu.sv boundaries as sep_global_base_addr_o / sep_region_size_o (both 56-bit). SEP_REGION_SIZE is a 32-bit CSR field, zero-extended to 56-bit at the SEP system CSR; the xbar input takes only the lower 32 bits. SEP_REGION_SIZE defines the SEP global/chiplet aperture for SMU routing and SEP inbound global-to-local remap. It is distinct from the SEP CPU’s architectural local-alias span. SEP_REGION_SIZE currently resets to 0x0100_0000 (16 MiB). Tied to '0 at the smu.sv boundary when the SEP parameter is 0.

  • smc_global_base_addr_i / smc_region_size_i come from the SMC CPU control CSRs GLOBAL_BASE / REGION_SIZE, exposed at both the smc.sv and smu.sv boundaries as smc_global_base_o (56-bit) / smc_region_size_o (32-bit). REGION_SIZE resets to 0x0100_0000 (16 MiB).

SEP, SMC, and smu_axi_xbar all run on clk_smu_i, so these quasi-static CSR fields need no clock-domain crossing. The crossbar’s address arithmetic is done on 57-bit widened sums. ext_out is a catch-all port that carries any outbound SEP/SMC manager request not matched by the programmed apertures; it has no fixed lower-bound address. Unmatched inbound (ext_in) requests return a decode error and do not reach ext_out.

6.3.1. Firmware programming order

Firmware must program SEP_GLOBAL_BASE_ADDR / SEP_REGION_SIZE and SMC GLOBAL_BASE / REGION_SIZE during early boot, before any cross-subsystem AXI traffic is issued, and must ensure the two apertures do not overlap and both fall within the chiplet-visible SMU envelope assigned by the integrator. The SMU crossbar does not itself constrain envelope size.

See OCAH Memory Map for the responsibility split between integrator, firmware, and the internal SEP/SMC address maps.

6.5. IC_RESET TDR Structure

The DTP primary TAP implements the IEEE 1149.1-2013 §17 IC_RESET TDR as three independently enabled slices plus a single reset_hold bit nearest TDO. At the SMU the scan order from TDI to TDO is:

TDI → SMC slice → SEP slice → external slice → reset_hold → TDO

The SMU enables the SMC slice unconditionally, the SEP slice when SEP=1 (otherwise that slice has width 0 and is omitted), and the external slice when JTAG_IC_RESET_ENABLE is set. Each slice is a packed struct with .ovrd and .val halves of equal width; jtag_ptap sizes the slice from $bits(type)/2 and interleaves the halves into the {reset_enable, reset_control} pair IEEE §17 requires per port. Declaration order within each half is the TDI-to-TDO scan order: the first field is nearest TDI.
