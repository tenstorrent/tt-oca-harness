Open Chiplet Atlas Harness (OCAH): Integrator Guide

This guide provides instructions and best practices for integrating OCAH subsystems into your chiplet design. Each section covers integration considerations, interfaces, and configuration requirements for the respective subsystem.

2. SMU Top-Level Integration

The System Management Unit (SMU) comprises three peer subsystems: the System Management Controller (SMC), the Debug & Test Ports (DTP), and the Security Processor (SEP). The subsections below describe each subsystem’s interfaces independently, followed by the SMU Composition section that explains how they are wired together inside the SMU and how to select between the smu.sv logic-level core and the smu_wrapper.sv reference integration.

2.1. System Management Controller (SMC) Integration

The System Management Controller (SMC) is a subsystem responsible for power management, clock control, reset sequencing, and peripheral interface coordination. The smc.sv module exposes logic-level interfaces; all technology-specific components (PLLs, PVT sensors, eFuses, memory macros, GPIO padrings) are instantiated externally by the adopter. See the SMU Module Variants section for how the reference wrappers demonstrate this integration.

For detailed architectural documentation about the SMC internal design, refer to hw/smc/doc/. The testbench dv/smc/tb/tb_uvm/sv/smc_chiplet_wrap_uvm_top.sv provides a complete integration example.

2.1.1. Clock and Reset

The SMC requires three external clock inputs: clk_smc_i (primary system clock driving the CPU cluster, fabric, and peripherals), clk_periph_i (peripheral clock driving the peripherals), and clk_ref_i (reference clock for timing-sensitive operations). All must be generated externally by the adopter’s PLL infrastructure; the SMC provides AXI-Lite control outputs for PLL configuration (see Peripheral Interface Connections). The peripheral clock is used to drive the I3C interface, I2C interface, UART interface, and AVSBus interface.

Assert powergood_i after power-up sequence completion. Deassert rst_cold_ni after the power-up sequence completion.

The SMC generates AASD (async-assert / sync-deassert) reset outputs: rst_primary_smc_clk_no for the main clock domain, rst_primary_periph_clk_no for the peripheral clock domain, and rst_primary_ref_clk_no for the reference clock domain. These ensure clean reset release without metastability across the system hierarchy.

Optional reset override inputs (rst_cold_override_ni, rst_cool_override_ni, rst_core_override_ni) allow external control of specific reset domains for test and debug scenarios. Most integrations leave these override enables deasserted; the DTP drives them through JTAG IC_RESET controls when enabled (see SMC-DTP Internal Interconnection).

2.1.2. Address Map and Aperture

The SMC has a chiplet-visible aperture and an internal local address view. Internally, the SMC uses a fixed local base address of 0xC000_0000 and a fixed local window size of 16 MiB. SMC-local addresses (registers, memories, remapped regions) are defined as offsets from that base. The chiplet-visible aperture is adopter-defined: the chiplet or SoC address map assigns the global base and size that external masters can use to reach SMC through the SMU crossbar.

When integrating the SMC into a chiplet or SoC, the adopter assigns a system base address and reserved size for the SMC window. The system base (e.g. 0x0800_0000 in a chiplet address map) may be different from the SMC-local base 0xC000_0000. Firmware programs the SMC GLOBAL_BASE / REGION_SIZE CSRs during early boot to match that assignment. The adopter’s fabric or address decoder must route the reserved system range to the SMC block so that offsets are preserved: system base + offset maps to SMC-local 0xC000_0000 + offset.

The SMC fabric uses three registers in the CPU Control block (0xC001_0000) to distinguish local from remote addresses:

  • LOCAL_BASE (read-only, fixed at 0xC000_0000): The local alias base. Together with the fixed 16 MiB LOCAL_ALIAS_REGION_SIZE, this is the address space the SMC CPU and internal fabric use to access SMC resources.

  • GLOBAL_BASE (read-write, defaults to 0x4000_0000): The system-level base address. Firmware must program this during early boot to match the adopter’s system address assignment, enabling the SMC to issue outbound transactions using global system addresses.

  • REGION_SIZE (read-write, currently resets to 0x0100_0000 / 16 MiB): The size of the SMC global aperture used by SMU-level routing and SEP-to-SMC decode. The SMC input fabric’s local/global split uses the fixed LOCAL_ALIAS_REGION_SIZE parameter in RTL.

For full details on alias remapping and outbound routing, see the SMC Fabric documentation (hw/smc/doc/fabric.adoc).

For a detailed breakdown of all components within the SMC local map, refer to the SMC Memory Map documentation (hw/smc/doc/memmap.adoc).

2.1.3. AXI Interface Configuration

The SMC provides three distinct AXI interface groups serving different access paths. The sys_axi_in interface accepts requests from external system masters requiring access to SMC-managed resources. This interface uses a 56-bit address space with 64-bit data width and 6-bit transaction IDs. Connect this interface to your system fabric for normal operational access from application processors or DMA controllers.

The sep_axi_in interface provides dedicated access from the Security Processor (SEP) subsystem. This interface shares the same sizing parameters as the system input but operates independently to maintain security domain separation. Use this interface only when integrating alongside the SEP subsystem. The interface may remain unconnected if your integration does not include SEP.

The output_axi interface carries filtered and remapped requests from the SMC to external system resources. This interface uses an 8-bit transaction ID field to accommodate merged traffic from multiple input paths. Connect this interface to your system interconnect to allow SMC components access to external memory and peripherals. The testbench shows example connections using AXI VIP components that can be replaced with your system fabric.

The jtag_axi_in interface provides debug access through JTAG mechanisms. This interface uses reduced 2-bit transaction IDs and connects to your JTAG debug infrastructure. The testbench demonstrates typical debug access patterns through this interface.

2.1.4. GPIO Pad Integration

GPIO pad integration requires careful attention to pull-up/pull-down requirements and strap configurations. The GPIO table below specifies default directions and pull settings for each pin. During power-up, certain GPIO pins function as configuration straps that determine boot behavior and operational modes.

The testbench provides reference implementations for pad connections starting at line 732. For input-only pins such as the JTAG interface (pins 68-77), connect directly to external pads without output drivers. For bidirectional pins, implement proper tri-state buffers controlled by the gpio_out_en_o signals. The testbench demonstrates pull-up resistor integration using pullup primitives on specific signals like I2C and I3C interfaces.

Configuration straps such as BYPASS_SRAM_REPAIR (pin 13), TEST_EN (pin 14), and others listed in the GPIO table must be set before the cold reset deassertion. These strap values determine fundamental operational modes and cannot be changed after the SMC completes fuse sensing. The testbench shows examples of strap forcing through GPIO pad connections.

For peripheral interfaces like UART, I2C, I3C, and SPI that multiplex through GPIO pins, the testbench demonstrates loopback configurations between transmit and receive pairs. In actual integration, connect these pins to external devices according to the pin function assignments shown in the GPIO table. The lsio_interface_select_o signals control peripheral multiplexing and are driven by SMC configuration registers.

2.1.5. Peripheral Interface Connections

The SMC exposes logic-level interfaces to several technology-specific subsystem components that the adopter instantiates externally. The subsections below describe each connection in turn.

PLL Interface

The axil_pll_req_o and axil_pll_resp_i signals form a 32-bit AXI-Lite interface to the adopter’s PLL control logic. The SMC uses this interface to configure output frequencies and manage clock generation; connect it to the control/status registers of the external PLL block(s).

PVT Interface

The axil_pvt_req_o and axil_pvt_resp_i signals form a 32-bit AXI-Lite interface to the adopter’s Process-Voltage-Temperature (PVT) monitoring blocks. Connect it to the external PVT sensor control registers to enable runtime monitoring and reporting.

eFuse Interface

The eFuse interface consists of two parts:

  • efuse_bank_ctrl — a 32-bit AXI-Lite interface used to access the SHIM control CSRs (for example, foundry-specific bank timing such as the initialization delay before sensing can begin).

  • efuse_shim_command — the custom fuse command interface used to issue read, program, and program/read-back operations to the eFuse bank.

Adopter responsibility. The efuse_shim_command interface is intentionally generic and technology-neutral. The adopter must implement an Interface SHIM that converts these generic commands into the hardware signals required by their OTP macro. The conversion is driven by the adopter’s own read and program state machines inside the SHIM; OCAH only defines the command/response contract, not the macro-side signaling.

The command and response payloads are exchanged as packed structs:

// Controller -> SHIM
typedef struct packed {
    addr_t                address;             // Target address (in bits)
    logic                 program_data;        // Data to program (when programming)
    access_length_words_t access_length_words; // Number of WORD_WIDTH words to access
    command_t             command;             // READ / PROGRAM / PROGRAM_READ_BACK
    logic                 valid;               // Request valid
} fuse_command_req_t;

// SHIM -> Controller
typedef struct packed {
    data_t data;   // Read data (one WORD_WIDTH word)
    logic  status; // Operation status (0 = OK, 1 = error)
    logic  valid;  // Response valid (qualifies `data` for one cycle)
} fuse_command_resp_t;

Fuse sensing protocol. During automatic sensing the controller issues a single read with access_length_words set to the entire bank (all NUM_WORDS words). The SHIM is expected to stream the bank back one WORD_WIDTH word at a time: for each OTP access it drives the read data onto fuse_command_resp_o.data and asserts valid for exactly one cycle. The controller consumes one word per cycle that valid is high, advancing to the next eFuse word on each assertion.

valid must be asserted for only a single cycle per returned word. If the SHIM holds valid high for two cycles, the controller will sample the same data value a second time and count it as the data for the next eFuse word, shifting all subsequent words and corrupting the sensed shadow contents. The adopter’s SHIM FSM is responsible for producing a clean one-cycle valid strobe per WORD_WIDTH access.

The shadow_regs_o output provides read-only access to the sensed fuse values. During bring-up the SMC automatically senses the fuse contents and propagates them through the shadow registers; the fuse_sense_done_o signal indicates completion of this sensing operation.

GPIO Interface

For GPIO controller access, connect the axil_req_gpio_ctrl_o and axil_resp_gpio_ctrl_i signals to the GPIO padring configuration logic. This interface allows runtime reconfiguration of pin directions, pull settings, and peripheral multiplexing options.

2.1.6. Memory Subsystem Integration

The SMC includes an embedded RISC-V CPU cluster with associated memory interfaces. The rom_intf_req_o and rom_intf_rsp_i signals connect to boot ROM containing the SMC firmware. The ROM must be populated with valid firmware images before initiating the boot sequence.

Scratch RAM interfaces (scratch_ram_intf_req_o and scratch_ram_intf_rsp_i) connect to 32 independent RAM banks totaling the scratchpad memory space. Cache memory interfaces for L1 instruction and data caches (l1_icache_* and l1_dcache_*) connect to tag and data RAM banks as specified in the port table.

The disable_sram_auto_init_i input controls automatic memory initialization behavior. When deasserted, the SMC automatically zeroes all SRAM contents during bring-up. The init_mem_done_o output indicates completion of this initialization sequence. The strap SRAM_AUTO_ZERO_DISABLE (GPIO pin 26) can disable this automatic zeroing behavior if your integration requires preserved SRAM contents across resets.

2.1.7. Memory Repair Integration

The SMC implements Built-In Redundancy Analysis (BIRA) memory repair to address manufacturing defects in SRAM arrays. Repair uses redundant memory elements configured with data stored in eFuse memory, replacing defective cells detected during manufacturing test.

Memory repair executes automatically during boot after eFuse sensing completes and before MBIST operations. The process must complete successfully before the CPU cluster can safely access SRAM arrays. Repair is required on every cold reset but can be bypassed during Function Level Reset (FLR) operations for faster recovery.

Control Signals:

  • fuse_sense_done_o: eFuse controller output indicating fuse sensing completion. External DFT logic monitors this signal to trigger repair operations.

  • skip_mem_repair_o: Reset unit output indicating repair should be bypassed. Asserts during FLR operations or when the BYPASS_SRAM_REPAIR strap is set. When asserted, external repair logic should skip operations and immediately assert completion status.

  • ext_boot_seq_done_i: External signal indicating the external boot sequence (memory repair and shadow register override) is complete. Held low to pause reset release until the external agent gives the go-ahead; required before the system can continue its boot sequence

Repair Data:

Repair data is stored in the eFuse BIRA shadow register as a 16-kilobit repair_data field. The eFuse controller reads this data during fuse sensing and makes it available through shadow registers. The external memory repair controller must read repair data from shadow_regs_o and apply it to SRAM arrays according to your memory architecture.

Status Monitoring:

Repair completion and success are reported through DFT Control Status registers at 0xC000F800 (SOC) and 0xC000F80C (SEP/SMC). The mem_repair_done bit indicates completion regardless of success, while mem_repair_success indicates successful repair. Both bits are set by the external repair controller. The SMC ROM firmware monitors these bits during initialization to verify repair completion.

Bypass Configuration:

The BYPASS_SRAM_REPAIR configuration strap (GPIO pin 13) bypasses repair logic when asserted high, causing skip_mem_repair_o to assert. Use bypass mode only when SRAM arrays are guaranteed defect-free, such as during development or with known-good components.

Integration Requirements:

Provide an external memory repair controller that monitors fuse_sense_done_o to initiate repair, respects skip_mem_repair_o for bypass control, reads repair data from eFuse shadow registers, applies repair configuration to SRAM arrays, asserts ext_boot_seq_done_i and updates DFT Control Status registers with completion status. The controller operates independently of the SMC core and must complete before the CPU cluster accesses SRAM. The testbench demonstrates example integration patterns adaptable to your DFT infrastructure.

For direct access to the eFuse besides from the shim, i.e. from a DFT fuse controller, adopters must ensure the integrated logic will not interfere with accesses from the OCAH’s efuse interface.

During FLR operations, repair is automatically bypassed via skip_mem_repair_o to enable rapid reset sequences. Normal cold reset sequences always execute repair unless explicitly bypassed via strap configuration.

2.1.9. Telemetry and Debug Integration

For system-level debug and telemetry, the SMC implements ATB (Advanced Trace Bus) receiver interfaces. The telemetry interface group (telemetry_atdata_i, telemetry_atid_i, telemetry_atvalid_i, telemetry_atready_o) operates in a dedicated clk_telemetry_i clock domain with separate rst_telemetry_ni reset. Connect these signals to ATB trace sources for debug data collection.

The ext_debug_bus_i provides a 512-bit wide debug observation bus for internal signal monitoring. The cross-trigger interface (xtrigger_pads_i, xtrigger_pads_o, xtrigger_ss_i, xtrigger_ss_o) enables coordinated debug triggering across multiple subsystems. The halt_clock_global_i input array accepts clock halt requests from external debug agents.

Trace memory interfaces (trace_mem_req_o and trace_mem_resp_i) connect to trace RAM instances for storing captured debug data. The testbench shows example debug infrastructure connections that can be adapted to your debug requirements.

2.1.10. Bring-Up Sequence

The recommended bring-up sequence begins with asserting rst_cold_ni while stabilizing power supplies and clocks. Once all supplies reach nominal voltages, deassert rst_cold_ni to initiate the SMC boot sequence. The SMC immediately begins fuse sensing to read configuration values and security credentials.

Monitor the fuse_sense_done_o signal to detect completion of fuse sensing. Configuration straps sampled during this phase determine boot modes and operational settings. After fuse sensing completes, the SMC releases internal subsystem resets based on the programmed reset sequencing configuration.

The CPU cluster begins firmware execution from the boot ROM after reset release. The firmware performs additional initialization including peripheral configuration, memory testing (unless disabled), and system health checks. The init_mem_done_o signal indicates completion of memory initialization if automatic SRAM zeroing is enabled.

For Function Level Reset (FLR) support, assert cfg_flr_pf_active_i to trigger a warm reset sequence. This isolates subsystems through isolate_req_o signals and performs controlled reset propagation. Monitor ss_reset_complete_i signals to verify subsystem reset completion before releasing isolation.

The testbench file demonstrates the complete power-on sequence including clock initialization, reset timing, strap configuration, and peripheral bring-up. Reference this testbench when implementing your integration-specific bring-up procedures.

2.2. Debug & Test Ports (DTP) Integration

2.2.1. Configuration

Before integrating the DTP, run the configuration script to generate required files:

cd hw/dtp
python3 generate_dtp.py --num-ctp <N> --num-int-ct <M>

Include the DTP in your build using hw/dtp/config/dtp.f or Bender target dtp_rtl.

2.2.2. Instantiation

dtp #(
    // JTAG Configuration
    .JTAG_BSR_ENABLE          (1'b1),
    .JTAG_TMP_ENABLE          (1'b1),
    .JTAG_SMC_DBG_ENABLE      (1'b1),
    .JTAG_SEP_DBG_ENABLE      (1'b1),
    .JTAG_IDCODE_MFR_ID       (11'h15A),
    .JTAG_IDCODE_PART_NUM     (16'h1234),
    .JTAG_IDCODE_SI_REV       (4'h1),
    // Cross Trigger Configuration
    .XTRIG_INT_CT_MODE        (10'b0000000000)
) u_dtp (
    .clk_i                    (clk),
    .rst_n_i                  (rst_n),
    .pwr_on_rst_ni            (pwr_on_rst_n),
    // JTAG, Boundary Scan, Cross Trigger interfaces...
);

2.2.3. Clock and Reset

  • TCK Domain: JTAG logic operates on external Test Clock

  • System Clock (clk_i): Cross trigger logic and JTAG2AXI bridges

  • System Reset (rst_n_i): Resets cross trigger and AXI; does not affect TAP controller

  • Power-On Reset (pwr_on_rst_ni): Asynchronous reset for JTAG state machine

2.2.4. Constraints

  • JTAG interface: 10-50 MHz TCK frequency

  • Cross trigger signals synchronized to system clock

  • DTP remains active during clock stop for debug access

  • External CTP signals require pad ring integration with ESD protection

2.2.5. STAP Scan Chain Topology

The DTP secondary scan path chains multiple STAPs on a single PTAP-managed scan string. The fixed order on this string is: PTAP, I/O STAP (if JTAG_STAP_IO_ENABLE=1), SMC debug STAP (if JTAG_SMC_DBG_ENABLE=1), SEP debug STAP (if SEP=1 in the SMU), extra STAP[N-1:0], and return to PTAP.

Both the SMC and SEP debug STAP host interfaces are internal to the SMU and are not exported on the SMU boundary. The SMU wires the SMC debug STAP host outputs to the SMC CPU/system JTAG ports (smc_cpu_jtag_*) when JTAG_SMC_DBG_ENABLE=1; when disabled, the DTP bypasses this STAP in the secondary scan chain and drives the internal host outputs low. The SEP debug STAP connects to the SEP JTAG debug port when SEP=1; when SEP=0, the SMU ties sep_stap_tdo_to_dtp = 1’b0 to bypass the SEP STAP return path.

2.3. Security Processor (SEP) Integration

The Security Processor (SEP) is the Root of Trust for the chiplet, providing a physically isolated execution environment for security-critical services such as secure boot, lifecycle control, device attestation, cryptographic acceleration, and key management. This section provides practical integration procedures for adopters integrating the SEP as part of the SMU or as a standalone out-of-context IP.

For detailed architectural documentation about the SEP internal design, refer to the dedicated SEP documentation located in hw/sep/doc/. The SEP hardware overview and interconnect fabric are described in hw/sep/doc/overview.adoc and hw/sep/doc/fabric.adoc respectively.

2.3.1. Module Overview

The sep.sv module provides the complete SEP functionality with logic-level interfaces. Technology-specific components (SRAM, ROM, eFuse shims, external TRNG, SPI controller selection) are instantiated outside SEP in a sep_ip_integration block, following the same vendor-neutral philosophy used for the SMC. When integrated inside the SMU, the SEP’s external interfaces are passed through the SMU boundary with a sep_ prefix.

2.3.2. Clock and Reset Requirements

The SEP requires two clock inputs. Connect clk_i to the primary system clock driving all SEP internal logic. Connect clk_wdt_i to a 200 kHz clock source for the watchdog timer; this clock must be independent of the system clock so that the WDT can detect system clock failures.

The primary reset rst_ni follows the standard active-low, asynchronous assertion / synchronous deassertion convention. The dbg_rstb_i input provides a separate reset for the EL2 CPU debug module. The wdt_rst_ni input receives the watchdog reset generated by the SMC reset unit. The SEP outputs sep_reset_n_o for its IP integration block and wdt_timer_rst_req_o when the WDT triggers a reset request.

2.3.3. AXI Interfaces

The SEP connects to the system through three AXI paths. The smn_outbound_axi master interface allows SEP firmware to access system resources outside the SEP domain, such as SMC registers or external memory. The smn_inbound_axi slave interface accepts requests from system masters requiring access to SEP-managed resources. The sep_ext_to_smc_axi output provides a dedicated AXI path for SEP-to-SMC transactions, connecting to the SMC’s sep_axi_in port.

An additional AXI extension port (axi_extension_axi) enables adopters to attach custom peripherals to the SEP interconnect fabric without modifying the SEP core. When unused, tie the response input to return DECERR.

2.3.4. Memory Interfaces

All SEP memory macros are instantiated externally and connected through dedicated request/response interfaces. The sep_cpu_tcm interface provides tightly-coupled memory (ICCM and DCCM) for the VeeR EL2 CPU. The sep_sram interface connects scratch SRAM used for firmware data. The sep_boot_rom interface provides the BL0 ROM containing the first-stage bootloader.

The crypto subsystem requires additional memory interfaces. sep_crypto_pka_imem_sram and sep_crypto_pka_dmem_sram connect to the OTBN public key accelerator instruction and data memories respectively. km_rom_mem and km_sram_mem connect to the Key Manager’s dedicated ROM and SRAM macros.

2.3.5. Cryptographic Subsystem Connections

The SEP includes an internal entropy source that requires a ring-oscillator sample clock connected to entropy_rosc_sample_clk_i. This clock must be asynchronous to clk_i and typically runs between 100 and 400 MHz.

For adopters providing an external TRNG, the ext_trng_axil AXI-Lite interface connects to the external TRNG control registers (in sep_ip_integration), while the ext_trng_axis AXI-Stream interfaces carry entropy data. The ext_trng_irq_i input is routed to the PIC; ext_trng_alarm_i is reserved for RAS.

2.3.6. eFuse and Lifecycle

The SEP accesses its own eFuse bank through the efuse_bank_ctrl AXI-Lite interface and the efuse_shim_command custom interface, mirroring the pattern used by the SMC. The SEP must wait for the SMC fuse sense to complete (smc_fuse_sense_done_i) before initiating its own fuse operations, and it signals completion through sep_fuse_sense_done_o.

The lifecycle controller outputs lc_state_o (differentially encoded), feat_ctrl_o (feature control vector), lc_sigint_err_o (signal integrity error), and security_disable_o. These outputs gate debug access through the DTP and control feature availability across the chiplet. The lcc_demote_state outputs report lifecycle demotion events to the SMC.

An OTP debug AXI-Lite port (axil_sep_otp_jtag) connects to the DTP for JTAG access to SEP fuses. When SEP is disabled (SEP=0 at the SMU level), the SMU instantiates an AXI-Lite error slave on this path.

2.3.7. SPI Host Interface

The SEP provides a SPI host controller through the sep_io_spi interface, supporting single, quad, and octal modes. The spi_irq_i input receives the muxed SPI interrupt from sep_ip_integration, which selects between the internal OpenTitan SPI controller and an external SPI controller. The ot_spi_irq_o output (at the SMU level) carries the OpenTitan SPI interrupt for external muxing.

2.3.8. Bring-Up Considerations

The SEP boot sequence begins after the SMC completes fuse sensing and releases the SEP reset. The SEP BL0 ROM firmware verifies the BL1 software image using non-volatile public keys before transferring control. Feature controls derived from secure boot authentication and lifecycle state govern what operations are permitted after boot.

The sep_straps_i input provides configuration straps for SEP-specific settings. The rst_vec, jtag_id, and core_id inputs must be tied to appropriate constants in the top-level integration.

2.4. SMU Composition and Internal Wiring

The System Management Unit (SMU) combines the SMC, DTP, and optionally the SEP into a unified subsystem. The interface descriptions in the preceding sections apply directly when integrating the SMU, since the SMU inherits all three subsystems' ports. This section covers the module variants available to adopters, how the SMU wires its subsystems together internally, and what additional configuration it exposes.

2.4.1. Module Variants and IP Integration

OCAH core modules (smc.sv, sep.sv, dtp.sv, and the composite smu.sv) expose logic-level interfaces only. All technology-specific components — PLLs, PVT sensors, eFuse shims, memory macros, GPIO padrings, SPI controllers, and external TRNG — are instantiated outside the core modules by the adopter. This separation keeps the OCAH deliverable technology-neutral.

The repository provides reference wrappers that demonstrate how to bridge the gap between OCAH core interfaces and adopter-specific IP:

  • smu_wrapper.sv wraps smu.sv with pad-level signal handling for clocks, resets, GPIO, eFuse, and JTAG interfaces. It internally instantiates smc_ip_integration.sv for SMC-related vendor IP and (when SEP=1) sep_ip_integration.sv for SEP-related vendor IP.

  • smc_wrapper.sv provides an equivalent reference wrapping smc.sv alone, useful when integrating the SMC without the DTP/SEP subsystems.

Neither the wrappers nor the IP integration modules are part of the OCAH deliverable; they exist as integration guides and for Tenstorrent internal usage. Adopters must develop their own equivalents following the interface patterns demonstrated in these modules. The interface contracts at the module boundaries ensure technology substitution without modifying the verified OCAH logic.

Wrapper Clock and PLL Architecture

The smu_wrapper.sv (and smc_wrapper.sv) reference accepts BP_REFCLK at the pad level and processes it through the integrated padring to produce internal reference timing. A pll_wrapper module generates system clocks pll_cgm_clk_o and pll_awm_clk_o from the padring-processed reference. The SMC controls this PLL through the same AXI-Lite interface exposed by the core module. However, the core receives its clocks through DFX inputs pll_cgm_clk_dfx_i and ref_clk_vdd_sys_dfx_i, so the adopter must route PLL outputs through the clock distribution network and feed them back through these DFX inputs.

2.4.2. Clock and Reset Architecture

Connect clk_smu_i to the primary system clock and clk_ref_i to a stable reference source. The DTP operates on TCK for JTAG logic and on the system clock for cross-trigger and AXI bridges. Reset sequencing follows the SMC flow; the DTP JTAG state machine uses pwr_on_rst_ni, which the SMU connects to rst_cold_ni. The SMU internally connects DTP debug paths to the SMC and optionally instantiates the SEP when the SEP parameter is set to 1. The full interconnection details are described in SMC-DTP Internal Interconnection and SEP-Conditional Wiring below.

2.4.3. SMU AXI Crossbar Address Map

Inside the SMU, the smu_axi_xbar module routes traffic between three AXI4 manager/subordinate pairs: the SEP outbound master (sep_out), the SMC outbound master (smc_out), and the external SMU AXI input (ext_in / smu_axi_in). The corresponding targets are the SEP and SMC inbound subordinates, and the external SMU AXI output (ext_out / smu_axi_out). Connectivity is described in SMU AXI Crossbar; the split between hardware-fixed behaviour and firmware-programmable apertures is documented in OCAH Memory Map.

The crossbar uses a runtime address map. Only the SEP and SMC apertures are programmable at runtime; the ext_out rule is static:

  • sep_global_base_addr_i / sep_region_size_i come from the sep_cpu_ctrl CSRs SEP_GLOBAL_BASE_ADDR / SEP_REGION_SIZE, exposed at both the sep.sv and smu.sv boundaries as sep_global_base_addr_o / sep_region_size_o (both 56-bit). SEP_REGION_SIZE is a 32-bit CSR field, zero-extended to 56-bit at the SEP system CSR; the xbar input takes only the lower 32 bits. SEP_REGION_SIZE defines the SEP global/chiplet aperture for SMU routing and SEP inbound global-to-local remap. It is distinct from the SEP CPU’s architectural local-alias span. SEP_REGION_SIZE currently resets to 0x0100_0000 (16 MiB). Tied to '0 at the smu.sv boundary when the SEP parameter is 0.

  • smc_global_base_addr_i / smc_region_size_i come from the SMC CPU control CSRs GLOBAL_BASE / REGION_SIZE, exposed at both the smc.sv and smu.sv boundaries as smc_global_base_o (56-bit) / smc_region_size_o (32-bit). REGION_SIZE resets to 0x0100_0000 (16 MiB).

SEP, SMC, and smu_axi_xbar all run on clk_smu_i, so these quasi-static CSR fields need no clock-domain crossing. The crossbar’s address arithmetic is done on 57-bit widened sums; ext_out covers 0x0000_8000_0000 up to the top of the 56-bit address space.

Firmware programming order

Firmware must program SEP_GLOBAL_BASE_ADDR / SEP_REGION_SIZE and SMC GLOBAL_BASE / REGION_SIZE during early boot, before any cross-subsystem AXI traffic is issued, and must ensure the two apertures do not overlap and both fall within the chiplet-visible SMU envelope assigned by the integrator. The SMU crossbar does not itself constrain envelope size; see OCAH Memory Map for the responsibility split between integrator, firmware, and the internal SEP/SMC address maps.
