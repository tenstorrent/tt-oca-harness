Direct Memory Access (DMA) Engine

The SMC DMA copies data through an AXI master using register-programmed linear or two-dimensional transfers. Software supplies one shared configuration and submits it by reading NEXT_ID_0. The engine does not fetch descriptor lists. SMC instantiates one control interface, one stream and one DMA master.

Table 1. SMC DMA integration
Item SMC configuration

Control aperture

0xC003_8000–0xC003_81FF (512 bytes, SMC-local view).

Control path

AXI, 9-bit local address and 64-bit data, 8-bit ID, converted internally to 32-bit register accesses. This is not an AXI4-Lite-only wrapper.

Data path

56-bit addresses, 64-bit data; 3-bit ID at the DMA wrapper and 4-bit ID after the shared DMA/zeroer mux. Backend internal IDs are 2 bits.

Access policy

Transfers pass through SMC fabric remapping/filtering; program addresses permitted by that integration.

1. Architecture and Configuration

The frontend captures register state into a request FIFO. The 2D midend expands each command into linear transfers, and the backend performs the AXI reads and writes. The DMA and zeroer share the outgoing fabric path shown below.

Figure 1. SMC DMA frontend, backend and shared fabric path

The DMA and the zeroer share smc_data_accelerator_wrap. Its control demux sends the zeroer register window to the zeroer and every other address to the DMA, and each control path narrows the address to its own register window. Its master mux merges the two master ports onto the port to the input fabric and adds one ID bit to tell their responses apart. In the figure, thick lines are AXI4, thin dark lines are the register bus, and grey lines are iDMA requests and responses, gated clocks and status outputs. The dashed box is the manager-to-backend FIFO, which is absent because SMC sets M2B_FIFO_DEPTH to 0. With one control interface and one master interface, the request manager is a passthrough, so the arbitration described under [smc-dma-request-arbitration] is not instantiated.

The generic request manager can arbitrate multiple control/master interfaces with round-robin selection, per-master origin tracking and buffered response routing. In the instantiated one-control/one-master SMC configuration it is a passthrough; these generic arbitration features add no extra SMC streams.

The frontend has a bus-aware clock gate; the request manager and backend use a separate activity/hysteresis gate. cg_enable_i=0 keeps them awake, and test mode overrides gating. Clock gating does not abort transfers or isolate the bus.

2. Transfer Configuration

2.1. Stream and Register Ownership

The generated map contains NEXT_ID, STATUS and DONE banks for 16 streams, but only bank 0 is functional in SMC. Reads of NEXT_ID_1..15 complete with zero and launch nothing; their STATUS and DONE registers also read zero. A read of NEXT_ID_0 is a command, not a status read: any read whose bytes include NEXT_ID_0, such as a 64-bit read at 0x48, launches a transfer; a 32-bit read of the unused word at 0x4C does not.

Source, destination, length, strides, repetitions and CONFIG are registers shared by all software contexts, with no configuration-lock register. The 64-bit fields use low/high 32-bit register halves, which the register path does not update atomically.

The frontend casts register values to these effective widths: upper bits are discarded, not validated as an out-of-range access. Program unused upper bits as zero and ensure all row addresses and lengths fit the permitted address range. Address stepping uses the effective address width.

2.2. Linear and Two-Dimensional Copies

A linear copy is one repetition with CONFIG.ENABLED_ND set; a 2D copy adds source/destination strides and a repetition count. Strides can gather or scatter evenly spaced rows; there is no linked-list walker.

Clearing CONFIG.ENABLED_ND forces the midend repetition count to zero. A zero-repetition command produces an internal midend error response without data movement; that response still retires a transfer ID. The control aperture does not expose the error payload, so a retired ID alone is not proof that valid data was copied.

The names above follow the published register map. The RTL frontend calls the configuration conf, the ND-enable field enable_nd, and the repetition pair reps_2_low/high; these refer to the same fields.

The frontend requests incrementing AXI bursts and sets the cache attribute to modifiable. CONFIG supplies decoupling, maximum burst-length and length-reduction options; the CONFIG register description gives each field’s effect. The backend handles alignment and burst splitting; these mechanisms do not grant permission to access a filtered or otherwise invalid address.

3. Submission and Completion

The DMA Engine section of the Programmer’s Guide gives the submission and completion sequence.

Table 4. DMA status and notification
Indication Meaning

STATUS_0[7:0]

Eight copies of frontend request readiness: 0xFF means room to accept a command. These are not per-channel backend busy bits.

STATUS_0[8] / [9]

Bit 8 is the midend activity indication; bit 9 is zero.

DONE_0

Most recently retired transfer ID. No byte-progress or classified software error-status register is provided.

DMA interrupt

One-cycle pulse on a falling edge of combined frontend/backend busy, routed to raw CPU vector bit 322 (PLIC ID 323). No local enable, mask or pending register; this is not one interrupt per submitted descriptor.

Frontend readiness and a zero STATUS value do not indicate completion. The transfer-ID generator resets NEXT_ID to 2 and DONE to 1 and skips zero on wrap. PLIC gateway behavior does not turn successive busy-falling pulses into a counted queue.
