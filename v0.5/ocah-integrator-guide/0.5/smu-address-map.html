Address Map Integration

The OCAH address map is configured in three layers, which are described in detail in the TRM at OCAH Memory Map.

  • Chiplet envelope (integrator). The SoC/chiplet address map assigns each subsystem a global base address and reserved size. The decoder in the adopter’s fabric routes accesses to these ranges to the SMU. The SMU crossbar preserves offsets and does not constrain envelope size, so the integrator is responsible for non-overlap and containment at the SoC level.

  • SEP and SMC chiplet apertures (firmware). Each subsystem exposes a chiplet-visible aperture whose base and size are programmable at runtime. Inbound transactions to an aperture are remapped global-to-local before they reach the subsystem.

  • Local-alias views (fixed in RTL). Internally each subsystem addresses its own resources through a fixed local map. The SMC is at 0xC000_0000: see Address Map and Aperture. in the SMC’s section of this integrator guide. The SEP accesses its registers through its own local map. The SMC and SEP internal base addresses are RTL-fixed, not integrator-assigned.

Programming order and constraints: firmware programs the SEP and SMC aperture CSRs during early boot, before any cross-subsystem AXI traffic is issued, and must keep the two apertures non-overlapping and inside the chiplet envelope the integrator assigned. The full runtime crossbar behavior and the exact CSR plumbing are in the Firmware programming order section of the integrator’s guide.

1. Register collateral

The machine-readable address map ships in the repository tree; integrators consume it from the release checkout or tarball rather than a separate package. The source of truth is distributed by ownership: each subsystem or IP keeps its canonical register sources and generated outputs beside its implementation. The integration/ directory centralizes symlinks to that distributed collateral so an integrator does not have to discover every owner-local path.

Each subsystem lists the SystemRDL files that it requires in a flat self-contained list at integration/rdl/<subsystem>/. Filenames remain unchanged, and shared dependencies appear in every subsystem that needs them. Non-RDL support files needed by relative includes remain at the integration/rdl/ root. For example, integration/rdl/i3c_defines.svh sits there because both integration/rdl/smc/registers.rdl and integration/rdl/smu/registers.rdl reach it through the I3C core’s own parent-relative include (../i3c_defines.svh). That relative path only resolves if the header is one directory above every subsystem folder that needs it. The matching generated IEEE 1685-2014 component descriptions use the same flat subsystem organization under integration/ipxact/<subsystem>/.

These directories are generated symlink indexes; run python3 scripts/update_integration_symlinks.py after adding or moving collateral. The targets of these symlinks are RDL files, one per subsystem, which remain at their canonical locations in hw/sys/<sys>/regs/, hw/ip/<ip>/regs/, and vendor/…​. These directories are the regs/ element of every component’s directory layout, described in the Getting Started Guide. Other generated outputs remain under each owner’s regs/gen/{c,sv,svh,py,ral,adoc,html,ipxact}/ directory.

For the architecture-level responsibility split between the integrator, firmware, and the internal SEP/SMC maps, see OCAH Memory Map.
