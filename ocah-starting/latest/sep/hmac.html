HMAC-SHA2

The HMAC component is based on the OpenTitan HMAC design.

1. OCAH Modifications

  • AXI4-lite key bus slave interface replaces side loading interface

  • AXI4-lite control/status bus slave interface

The crypto interconnect narrows HMAC’s host path from 64-bit AXI to 32-bit AXI, converts and isolates it as AXI-Lite, then hmac_wrapper bridges it to TL-UL for the tt_hmac core. The address path subtracts the HMAC base address and masks to a 13-bit window (8 KB), accommodating both the register space and the message FIFO window at offset 0x1000. HMAC exposes a single fatal alert channel (index [0] in OpenTitan Alert Termination), three interrupts (done, fifo_empty, err), and an idle_o status output. Unlike the other crypto wrappers, HMAC has no EDN connection.

The Key Manager delivers a 256-bit HMAC key as eight words per share, in the format given in Key Manager Key Delivery. HMAC has no select bit: the delivered key is used in preference to the engine’s software key registers whenever KEY_CTRL.KEY_VALID is set.

The delivered key is most-significant-bit justified in the engine’s 1024-bit key field, and the engine takes its key length from CFG.key_length, which the delivery path does not write. Software shall program CFG.key_length to the 256-bit encoding to match the delivered key. An unset or unsupported length raises a configuration error when hashing starts. A supported length that disagrees with the delivered key does not raise an error: the engine takes key material from the top of the 1024-bit field, so the padding below the delivered key is mixed into the key and the resulting digest is wrong but repeatable.

Consult the OpenTitan HMAC documentation for the authoritative core functionality of the IP. The register map is reported in the Detailed Register Map.
