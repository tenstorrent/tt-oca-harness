Environment Setup

This document is currently under development.

1. Repository

To clone the repository, ensure that you have git installed (sudo apt install git), and then run the following commands:

git clone https://github.com/tenstorrent/tt-oca-harness.git

cd tt-oca-harness

The repository contains a Python environment used for scripting workflows. Some of these workflows are contained within submodules, meaning the Python environment requires the submodules to be initialised. The container image tag needs them too: once you modify any file, docker-run.sh fails with Failed to fetch git repository if they are missing. To initialise them, run the following command:

git submodule update --init --recursive

2. Toolchain access

Most OCAH workflows require a RISC-V cross-compiler, EDA tools (Yosys, Verilator, Slang, Verible), and documentation tools (Antora, Asciidoctor). There are three ways to get these:

Method Summary

Container (recommended)

A Nix-built container image bundles all EDA and firmware tools. No individual tool installs needed beyond a container engine (Podman or Docker). This is the primary supported method for the initial release.

Native

Install each tool individually on the host. Gives the most control but requires the most setup. See this section for the (Ubuntu) native path and refer to Dependencies for version requirements.

Nix Development Shell

nix develop provides the same tool set as the container, directly on the host, via the Nix package manager. Available but not first-class supported — useful on NixOS or hosts that already have Nix installed.

3. Container (recommended)

The container is the primary toolchain access method for the initial release. It is built from the Nix flake in this repository, and CI publishes that image to the GitHub Container Registry. You can pull the exact image CI verified rather than build it yourself (see Pulling the prebuilt image); docker-run.sh builds it locally on first use when no registry is configured.

The container bundles:

  • RISC-V cross-compiler (riscv64-unknown-elf-gcc + picolibc) — making a native RISC-V toolchain install optional for firmware workflows

  • yosys + yosys-slang for synthesis

  • slang, verilator, verible for lint

  • antora for documentation

Tools that must be installed natively even when using the container: Python / uv (for register generation and DV Python tooling), bender (IP dependency management), and git.

3.1. Container engine setup

Install a container engine (Podman or Docker):

  • Podman (recommended)

  • Docker

If you installed Podman, also install fuse-overlayfs and register the Docker Hub registry:

sudo apt install -y fuse-overlayfs

sudo mkdir -p /etc/containers/registries.conf.d
cat <<'EOF' | sudo tee /etc/containers/registries.conf.d/docker.conf
unqualified-search-registries = ["docker.io"]
EOF

3.2. Pulling the prebuilt image

CI builds the OCAH container and publishes it to the GitHub Container Registry, so you normally do not need to build it yourself. Point docker-run.sh at the registry and it pulls the exact image CI verified:

export OCAH_CONTAINER_REGISTRY_IMAGE=ghcr.io/tenstorrent/ocah-container
export OCAH_IMAGE_WITH_UV=true            # the variant CI publishes
./scripts/docker-run.sh verify           # pulls once; run/shell then reuse it

The image is tagged with a hash of the Nix flake, which docker-run.sh evaluates before every command. Without Nix on the host it evaluates the hash in a throwaway nixos/nix container, which takes several minutes each time even when the image is already loaded; installing Nix keeps it fast.

Published images are listed on the ocah-container package page. Build the image locally only when you are changing its definition. See scripts/docker.md for the full set of container commands and environment variables.

3.3. Using the container

All container interaction goes through scripts/docker-run.sh. The image is pulled (or, with no registry configured, built) automatically on first use:

# Open an interactive shell (builds the image if needed)
./scripts/docker-run.sh shell # use shell-here for 1:1 paths

# Run a command inside the container
./scripts/docker-run.sh run make dv-fw-tests TARGET=smc

# Run with 1:1 host paths (needed for workflows using absolute paths)
./scripts/docker-run.sh run-here make ocah-synth-yosys-all

To pre-build the image explicitly (e.g. before going offline):

./scripts/docker-run.sh build

To bundle UV dependencies in with the container, for a fully offline system, set OCAH_IMAGE_WITH_UV=true before building

4. Native Installation

4.1. Python

We recommend the use of pyenv to ensure the correct version of python is in use. To install pyenv, visit their GitHub page, or run curl https://pyenv.run | bash.

The piping of a script from the internet as above, without checking it, is never safe. You should always check the contents of the script first to guarantee safety. This may be done using curl https://pyenv.run, which will print the script, instead of running it.

To install Python 3.11 with pyenv, first install the python build dependencies, and then Python 3.11 itself:

# Check Pyenv GitHub for up-to-date build environment
sudo apt update
sudo apt install make build-essential libssl-dev zlib1g-dev \
libbz2-dev libreadline-dev libsqlite3-dev curl git \
libncursesw5-dev xz-utils tk-dev libxml2-dev \
libxmlsec1-dev libffi-dev liblzma-dev libzstd-dev

pyenv install 3.11

From here, enter a pyenv shell, and install uv using the following commands:

pyenv shell 3.11

# In the shell
pip install uv

4.2. Package Dependencies

Once the repository is cloned, install the required open source tools:

sudo apt install asciidoctor asciidoctor-pdf verilator gcc \
ccache picolibc-riscv64-unknown-elf cmake default-jre-headless

default-jre-headless provides the Java runtime that renders PlantUML diagrams in the PDF builds. The asciidoctor-diagram extension those builds require is not packaged for Ubuntu; install it as a gem:

gem install asciidoctor-diagram

Follow the instructions on the following pages for tools not packaged within Ubuntu:

  • Antora

  • Bender

  • Verible

  • Slang

  • Yosys (Also packaged via apt, but newer version recommend)

    • SV-Elab (Formerly Yosys-Slang) Required to allow Yosys to synthesise SystemVerilog

  • Surfer (optional, alternatives available, used for wave trace debugging)

  • Drawio (optional, used for creating new diagrams for documentation)

  • Wavedrom (optional, used for creating new diagrams for documentation)

Enter the repository and use the following command to set up the Python environment:

uv sync # or `make uv-sync`

5. Nix Development Shell (available, not first-class supported)

If you have Nix installed, the dev shell provides the same tool set as the container directly on the host — no container engine needed:

nix develop    # activates the dev shell; tools are then available on PATH

With direnv configured, the shell activates automatically on cd into the repo.

See the OCA Harness Nix Readme for more information on Nix integration.

The Nix dev shell is not first-class supported for the initial release. It has been deployed on NixOS and Linux hosts with Nix installed, but is not actively tested. MacOS builds have not been attempted. The container is the recommended path.
