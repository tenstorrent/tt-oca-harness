1. Life Cycle Controller (LCC)

The Life Cycle Controller (LCC) supports multiple security domains for chiplet-based systems and generates the feature-control policy for the current lifecycle state.

The LCC handles life cycle management and includes decoding life cycle states and the generation of the debug/test/feature control vector corresponding to each state.

The LCC performs the following actions to support life cycle management:

  • Receive inputs from SEP OTP (Fuse) Shadow Registers (populated by OTP sense FSM on power-on)

    • LC_STATE[3:0]

    • Debug/test/feature control vectors: SIP_DIS and SYS_DIS

  • Generate the per-LC-state debug/test/feature control vector (feat_ctrl_o) and send it to its downstream destinations (TAP, DFT, peripherals, downstream chiplets, Key Manager).

  • Maintain volatile in-field debug demotion state via the DEMOTE_1, DEMOTE_2, DEMOTE_LOCK_1, and DEMOTE_LOCK_2 CSRs, and apply the resulting PROD_DBG access profile to the feature control vector. See DEMOTE_1 and DEMOTE_2 — In-Field Debug Demotion.

  • Detect signal-integrity errors on the differentially encoded LC_STATE input arriving from the OTP shadow register; fail closed (force feat_ctrl_o = 0) on detection.

DEMOTE_1 and DEMOTE_2 — In-Field Debug Demotion

In addition to the LC state stored in OTP, SEP implements two volatile demotion CSRs (DEMOTE_1, DEMOTE_2) and two companion lock CSRs (DEMOTE_LOCK_1, DEMOTE_LOCK_2). When asserted, these grant additional in-field debug access without changing the LC state stored in OTP. SEP cold reset clears all four registers, returning the device to its OTP-stored LC state.

The feature control profiles produced in PROD_DBG mirror those of the corresponding RMA state exactly across all three groups (debug, DFT, and function). See Per-LC-state feature-control profile for the exact formulas.

Invariant: DEMOTE_1 Implies DEMOTE_2

DEMOTE_1 = 1 always implies DEMOTE_2 = 1 as a manifest-construction convention. The combination (DEMOTE_1 = 1, DEMOTE_2 = 0) is not a legal configuration in the specification.

This invariant mirrors the LC state RMA hierarchy: just as RMA_CHIPLET can only be reached after first transiting RMA_SIP (two successive token matches required), chiplet-owner-level demote (DEMOTE_1) is intended to denote a strictly higher access level than SiP-owner-level demote (DEMOTE_2). Asserting DEMOTE_1 without also asserting DEMOTE_2 mis-encodes the access level and is therefore disallowed by specification.

The invariant is not enforced by hardware. In a two-owner deployment (see Signing-Model Enforcement) SiP-owner approval is already on the path for every loadable image by virtue of universal co-signing, so the manifest author is responsible for setting D1 and D2 consistently with the intended access level. In a single-owner deployment the chiplet-vs-SiP distinction is degenerate; the single owner is nevertheless expected to honor the convention.

Signing-Model Enforcement

Enforcement of the DEMOTE authorization model — including the DEMOTE_1 implies DEMOTE_2 invariant — is delegated entirely to the firmware signing model. The LCC hardware does not check signing authority, does not check DEMOTE_1/DEMOTE_2 consistency, and does not inspect manifest contents; it simply applies the feature-control profile that corresponds to the bit pattern in the DEMOTE registers.

The signing requirement is set by the deployment-time provisioning state of the SiP-owner public key in eFuse, not by which DEMOTE bit an image asserts:

  • If SIP_PUBK_DIGEST is provisioned (two-owner deployment — chiplet creator plus SiP integrator), every signed image loadable by SEP ROM must be co-signed by both the chiplet creator and the SiP owner. This requirement is uniform: it applies whether the image touches DEMOTE bits or not, and irrespective of which DEMOTE bits it asserts. SiP-owner approval is therefore present on the path for every loadable image by construction, so the manifest author can assert any legal demote configuration (D2 alone, or D1+D2) knowing the SiP owner has already approved.

  • If SIP_PUBK_DIGEST is not provisioned (single-owner deployment — only the chiplet creator owns the part), only the chiplet creator’s signature is required. The chiplet-vs-SiP distinction is degenerate at the owner level, although the two DEMOTE registers still exist in hardware; the single owner is expected to honor the Invariant: DEMOTE_1 Implies DEMOTE_2 by manifest convention.

SIP_PUBK_DIGEST is the hash digest of the SiP owner’s root public key, programmed into eFuse during integration. Public keys themselves are never stored in eFuse — only their hash digests are — and the chiplet creator’s root public-key digests are embedded in SEP ROM, not in eFuse. Do not confuse SIP_PUBK_DIGEST with PUBK_HASH0 / PUBK_HASH1: those are additional chiplet-owner authentication key hashes that supplement the chiplet-creator digests embedded in the SEP ROM (see the Fuse Controller (OTP) fuse-field table in this chapter for PUBK_HASH0/PUBK_HASH1 and CHIPLET_PUBK_REVOKE). They are unrelated to the SiP-owner co-sign rule above.

In a typical OCAH deployment, the demote decision is carried in the BL1 image, and BL1 is signed according to the rule above. Either bootloader stage may in principle carry the demote assertion — the controlling factor is the set of signing authorities on the image, not the boot stage.

Lock Behavior

  • When DEMOTE_LOCK_x = 0, firmware can assert DEMOTE_x = 1.

  • Once DEMOTE_LOCK_x = 1, DEMOTE_x can no longer be changed until SEP cold reset clears both registers.

  • A signed boot image whose manifest takes ownership of the demote decision for this boot programs DEMOTE_LOCK_x = 1 as part of committing the decision. The locked value may be DEMOTE_x = 0 (commit non-demoted state) or DEMOTE_x = 1 (commit demoted state) — in either case, locking commits the decision and prevents any later boot stage from modifying it until cold reset.

  • If the manifest instead defers the demote decision to a later boot stage, it leaves DEMOTE_LOCK_x = 0 so the next stage can complete the programming. The detailed boot-stage decision protocol (e.g., manifest selector / value / deferral hint) is out of scope for the LCC chapter and is described in the OCAH SEP boot specification.

Reset Behavior

SEP cold reset clears all four demote registers (DEMOTE_1, DEMOTE_2, DEMOTE_LOCK_1, DEMOTE_LOCK_2), returning the device to plain PROD (or to its OTP-stored LC state, whichever applies).

Multiple Security Domains

The diagram below depicts three chiplets, one primary and two secondaries with two security domains. Chiplets may or may not have a local SEP along with its Life Cycle State.

There are two security domains as illustrated above. Each chiplet which has a SEP has the ability to support two domains:

  • Domain 1 — Chiplet-owner controlled. Governs debug access to the chiplet’s own internal assets. Asserted via DEMOTE_1 (in PROD_DBG_1) or by transition to RMA_CHIPLET. Entering Domain 1 requires both chiplet-owner and SiP-owner authorization (co-signed image for DEMOTE_1; both RMA tokens for RMA_CHIPLET).

  • Domain 2 — SiP-owner controlled. Governs debug access to SiP-owned assets and to downstream secondary chiplets. Asserted via DEMOTE_2 (in PROD_DBG_2) or by transition to RMA_SIP. Entering Domain 2 requires the SiP-owner signature (or the RMA_SIP_TOKEN) only.

Feature control vectors are tied to both security domains, and Domain 1 access implicitly includes Domain 2 access — the chiplet owner cannot reach Domain 1 without SiP-owner authorization, so any asset readable in Domain 1 is also readable in Domain 2 from the SiP owner’s perspective (see Invariant: DEMOTE_1 Implies DEMOTE_2).

In the diagram above, the intermediate secondary chiplet is depicted without a SEP and dedicated debug control. Debug access in this case is governed by the primary chiplet’s Domain 2 configuration. See Non-Primary Chiplets.

LC State Machine

The LC controller is a stateless decoder of the LC_STATE shadow register provided by the OTP/Fuse controller. The OTP controller initializes the shadow-register output to the INVALID encoding (4’b1111) and only drives it to the OTP-stored LC state value once fuse sense is complete (see Fuse Controller (OTP) in this chapter). The LCC’s output therefore tracks fuse sense automatically: INVALID feature-control profile before fuse sense, the per-LC-state profile (TEST_DEV / PROD / PROD_END / RMA_SIP / RMA_CHIPLET) after.

The PROD and PROD_DBG states are distinguished by the value of the DEMOTE_1/2 configuration register (CSR) bits; field debugging of production packages is supported via the PROD_DBG_1/2 states. For feature control the DEMOTE bits act only in PROD — selecting the PROD_DBG_1 (chiplet-owner, all features) or PROD_DBG_2 (SiP-owner, honours SIP_DIS/SYS_DIS) profile — and do not change the profiles of TEST_DEV, RMA_SIP, or RMA_CHIPLET, which are fixed by the LC state (see Per-LC-state feature-control profile; e.g. TEST_DEV honours SIP_DIS/SYS_DIS and RMA_CHIPLET already enables all features). A chiplet cold reset resets the DEMOTE_1/2 bits.

There are two flavours of PROD debug — PROD_DBG_1 and PROD_DBG_2 — distinguished by the volatile DEMOTE register state rather than by a separate LC encoding (see DEMOTE_1 and DEMOTE_2 — In-Field Debug Demotion). The two flavours map onto the RMA access hierarchy:

  • PROD_DBG_2 (DEMOTE_2 = 1, DEMOTE_1 = 0) provides SiP-owner-level debug access, equivalent in access privilege to RMA_SIP.

  • PROD_DBG_1 (DEMOTE_1 = 1, DEMOTE_2 = 1) provides chiplet-owner-level debug access, equivalent in access privilege to RMA_CHIPLET.

The combination (DEMOTE_1 = 1, DEMOTE_2 = 0) is not a legal configuration; enforcement is via the firmware signing model (see Signing-Model Enforcement).

Second, we will require two successive token matches to enter RMA_CHIPLET state. First we must enter RMA_SIP state via the RMA_SIP_TOKEN and then we can move to RMA_CHIPLET state via the RMA_CHIPLET_TOKEN. This RMA token sequence is the LC-state analogue of the DEMOTE_1 implies DEMOTE_2 invariant described above.

The Key Managers key derivation function (KDF) uses the DEMOTE_1/2 bits in addition to CHIPLET_UID, SIP_UID, SYS_UID and LC_STATE as inputs. Mixing the DEMOTE_1/2 bits into the KDF ensures that the derived keys in PROD_DBG_1/2 states are distinct from the ‘live’ keys in PROD state.

During normal chiplet operation, the current LC states are retrieved from OTP, stored in differential shadow registers and propagated to the rest of the chiplet and potentially propagated from a primary chiplet to secondary chiplets.

In the next generation of SEP, the LC state registers will be redundantly encoded in order to guard against attacker modification via laser fault injection or FIB modification. The first-generation SEP uses the LC state encoding shown in this table.

Debug, Test and Functional Feature Control Vectors

Debug, test, and functional features are gated at runtime by the feature control vector feat_ctrl_o. This vector is not stored directly: it is derived from two 64-bit disable vectors held in OTP — SIP_DIS and SYS_DIS — as the inverted OR of the two, gated per LC state, then overridden by SEC_DIS and finally gated by SECURE_TM:

`feat_ctrl_o = ~(SIP_DIS | SYS_DIS)`   (per-LC-state gating; then SEC_DIS / SECURE_TM, see below)

In other words, each feature’s enable is the inverse of its disable bits. This section is organized bottom-up: the disable vector format first, then ownership, the OR/invert combining rule, applicability, overrides/gates, and finally the per-LC-state feature-control result.

DIS Vector Ownership: Predecessor-Programs-Disables

OCAH uses a predecessor-programs-disables convention. Each X_DIS vector specifies restrictions imposed by an earlier owner that should apply for the rest of the part’s life (until the chiplet creator themselves regains full access via RMA_CHIPLET):

  • SIP_DIS — programmed by the chiplet creator before the part is transferred to the SiP integrator. A bit value of 1 disables the corresponding feature for any access level below RMA_CHIPLET.

  • SYS_DIS — programmed by the SiP owner before the part is transferred to the system integrator. A bit value of 1 disables the corresponding feature for any access level below RMA_CHIPLET.

The system owner has no successor in the OCAH ownership chain, so there is no third DIS vector restricting them. The system owner’s own fuse fields (SYS_PUBK_DIGEST, SYS_UID) are provisioned by the system owner directly before transitioning the part from TEST_DEV to PROD. See the Fuse Controller (OTP) section in this chapter for the full multi-owner provisioning sequence.

Combining Rule: OR then Invert

The per-LC-state formulas combine SIP_DIS and SYS_DIS with bitwise OR, then invert (~(SIP_DIS | SYS_DIS)) to produce the positive-logic feat_ctrl_o output ("1 = feature enabled"). The OR is the natural fuse-level combiner:

  • DIS bits live in OTP fuses, which are write-once: a fuse bit can only transition from 0 to 1, never from 1 to 0.

  • The DIS convention is "1 = disabled," so each owner’s restriction is expressed as a 1 fused into their vector.

  • Combining multiple owners' restrictions therefore uses OR: a feature is disabled if any owner has fused a 1 in that bit position. There is no way for a later owner to "undo" an earlier owner’s restriction once fused.

  • The output feat_ctrl_o uses positive logic ("1 = feature enabled"), so the combined disable is inverted: ~(SIP_DIS | SYS_DIS).

When Each DIS Vector Applies

Both SIP_DIS and SYS_DIS apply at every LC state except chiplet-level access (PROD_DBG_1 / RMA_CHIPLET), where the chiplet creator has full access and no predecessor has authority to restrict them. Two further controls — the SEC_DIS override and the SECURE_TM final gate — sit on top of this; see Overrides and Final Gates (SEC_DIS, SECURE_TM).

Overrides and Final Gates (SEC_DIS, SECURE_TM)

Two controls sit on top of the per-LC-state / DIS-vector computation, applied in this order (a later step overrides an earlier one):

  1. Signal-integrity fail-closed (base): if the differentially encoded LC_STATE fails its integrity check (lc_sigint_err), the base feat_ctrl is forced to all-0s (all features disabled).

  2. SEC_DIS override: when SEC_DIS = 1, feat_ctrl is forced to all-1s — every feature enabled, regardless of LC state, the DIS vectors, or the sigint result. (A0 emergency bypass; see the Security Disable section.)

  3. SECURE_TM final gate (applied last): when SECURE_TM = 0 (normal operation — not in secure test mode), the entire test group feat_ctrl_o[47:32] (SEP_FUSE_TEST, SMC_FUSE_TEST, FUSE_VENDOR_TEST, and the reserved test bits) is forced to 0. Because this gate is applied after the SEC_DIS override, the test features are disabled even when SEC_DIS = 1 — test features are available only when SECURE_TM = 1. The debug group [31:0] and function group [63:48] are not affected by SECURE_TM.

Net effect on the test group: a test feature is enabled only if the LC-state/DIS computation (or SEC_DIS) enables it and SECURE_TM = 1. See also secure_tm and Scan Dump for how secure_tm relates to the per-LC-state scandump gating.

Asset and Scan-Chain Protection

Two distinct DFT operations use the scan chains, and the protection model treats them differently:

  • Scan test — shift in a test pattern, run the functional clock for one or two cycles, then shift the result out. Used for manufacturing / DFT coverage.

  • Scan dump — shift the live internal state out directly. Used for debug.

The design goal is to maximize DFT coverage (keep as many flops on the scan chain as possible) while ensuring secrets can never be dumped. This section maps SEP asset classes to scan chains and to the gates that control each.

Asset Classes

SEP assets are partitioned into three classes. Class 1 (non-scannable) is split by protection rationale — 1a (confidentiality) and 1b (integrity). Class 2 (crypto / Key Manager secret-bearing) is scannable for test coverage but is never scan-dumpable. Class 5 is everything else.

secure_tm and Scan Dump

secure_tm is the secure-test-mode indicator: the TEST_EN strap latched into the internal SECURE_TM signal. It is latched when SEP fuse sensing completes if SEC_DIS is not asserted, or on chiplet cold-reset release if SEC_DIS is asserted (see the Test Mode section). Tests can be enabled only when SECURE_TM = 1.

secure_tm protects secrets at two points, which together let the crypto and Key Manager logic stay on the scan chain (maximizing DFT coverage) while never exposing secrets:

  • During scan test (secure_tm = 1): the secret-bearing shadow-register outputs (CHIPLET_UID / SIP_UID / SYS_UID, CLASS_KEY) are disconnected from downstream logic, OTP fuse-write enables are tied inactive, and LOCKS / LC_STATE / SIP_DIS / SYS_DIS are locked against updates (see Fuse Controller (OTP)). So Class 2 consumers can be shifted and tested without any real secret being present in them.

  • During scan dump (secure_tm = 0): the dedicated Class 2 secret-bearing scan chain is tied off, so its contents can never be extracted via debug — independent of the *_DBG feature-control bits and of the LC state.

The Class 1 vs Class 2 split follows from where each asset sits:

  • Class 2 can be scannable because its registers are consumers of secrets reached over functional paths; secure_tm = 1 cuts those paths during test.

  • Class 1 cannot be scannable because its registers are the secrets (Class 1a) or the integrity-critical control fields (Class 1b) — the data lives in the registers themselves, so they are excluded from every scan chain.

The _DBG feature-control bits are a separate, coarser control: they gate *general (Class 5) debug / scan-dump access per scope (SEP_DBG, SIP_DBG, CHIPLET_DBG). They do not affect the Class 2 secret-bearing chain, which is governed solely by secure_tm.

Feature-Bit to Scan-Chain Mapping

Each general (Class 5) scan chain is gated by a per-scope _DBG feature-control bit in feat_ctrl_o; the bit’s owner — which predecessor DIS vector sets its default (see DIS Vector Ownership: Predecessor-Programs-Disables) — sets the multi-owner default policy. The Class 2 secret-bearing chain is *not gated by a feature-control bit; it is governed by secure_tm and is never dumpable.

Non-Primary Chiplets

Primary chiplets always include a local SEP and LCC; the asset partitioning described in Asset and Scan-Chain Protection applies directly. Non-primary chiplets may not include a local SEP, in which case lifecycle and debug enablement is governed by the primary chiplet’s Domain 2 (see Multiple Security Domains).

For non-primary chiplets, the adopter is responsible for:

  • Identifying which non-primary chiplet assets require protection.

  • Partitioning those assets across scan chains analogous to the class scheme in Asset Classes (1a/1b, 2, 5).

  • Wiring the non-primary chiplet’s scan / DFT enables to the appropriate feature-control bits forwarded from the primary chiplet (typically driven by the primary chiplet’s SIP_DBG bit and other downstream-debug signals in feat_ctrl_o).

  • Applying the same scan-protection treatment to any non-primary chiplet logic that handles secrets: Class 1 excluded from scan chains, Class 2 scandump-gated by the forwarded feature-control bits.

The cross-chiplet propagation of feature-control bits (via the SIP_DBG mechanism documented in Disable Vector Format (SIP_DIS / SYS_DIS)) is the contract by which the primary chiplet’s LCC reaches the non-primary chiplet.

Adopter Extension (Design Open)

If an adopter integrates SEP into a chiplet with assets that require their own scan-chain protection — assets not covered by the chiplet-scope SEP scan chain or the general-logic scan chain in Asset and Scan-Chain Protection — the LCC architecture accommodates this via the reserved bits in feat_ctrl_o (and the matching positions in SIP_DIS / SYS_DIS):

  • Debug group: bits 6-31 (26 reserved bits)

  • Test group: bits 39-47 (9 reserved bits)

  • Function group: bits 48-63 (16 reserved bits)

Each new scan chain is gated by exactly one reserved bit. The corresponding bit position in SIP_DIS or SYS_DIS (chosen by which predecessor owner sets the default policy — see DIS Vector Ownership: Predecessor-Programs-Disables) determines the default OTP-programmed restriction.

Constraints any adopter extension must satisfy:

  • One feature-control bit per scan chain.

  • Asset-class compliance. Secret-bearing fields used by the new chain must follow the asset-class scheme (see Asset and Scan-Chain Protection): actual secrets and integrity-critical state are excluded from scan chains (Class 1), and any scannable secret-consuming logic (Class 2) has its scandump gated by the chain’s feature-control bit — the same treatment that makes Class 2 safely scannable.

  • Per-LC-state policy. The new bit follows the standard per-LC-state formulas (see Per-LC-state feature-control profile): disabled in PROD and PROD_END, bypassed by SEC_DIS, enabled at chiplet-level access (PROD_DBG_1 / RMA_CHIPLET), and subject to the predecessor-programs-disables convention for TEST_DEV and SiP-level access.

The specific bit-allocation convention — which reserved bits are reserved for which adopters, how bit assignments are advertised in the RDL / package outputs, and whether a partials-style register interface is provided to extend feat_ctrl_o — is currently open and will be defined in a future revision of this specification.
