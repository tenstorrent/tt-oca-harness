[[uart-16550-interface]]
== Interface

=== Configuration Parameters

The UART 16550 module provides configurable parameters to customize FIFO
sizes according to system requirements.

<<uart-module-parameters-table>> lists the configurable transmit and receive FIFO
depths.

[[uart-module-parameters-table]]
.UART Module Parameters
[width="100%",cols="20%,15%,15%,50%",options="header",]
|=======================================================================
|Parameter |Type |Default |Description
|`TX_FIFO_DEPTH` |`int unsigned` |`16` |Transmitter FIFO depth. Must be
a power of 2 between 4 and 4096 (inclusive). Determines the number of
characters that can be buffered for transmission.

|`RX_FIFO_DEPTH` |`int unsigned` |`16` |Receiver FIFO depth. Must be a
power of 2 between 4 and 4096 (inclusive). Determines the number of
characters that can be buffered for reception.
|=======================================================================

=== Modem Control Interface

The modem control interface provides full RS-232 modem signaling
compatibility. All modem signals are active low at the pins, matching the
RS-232 convention.

The modem inputs are *status only*. Each one is synchronized and then
reported in the `MSR` register in the opposite polarity (a bit reads `1`
while its pin is asserted low), and a change on any of them raises the
Modem Status Interrupt. None of them gates the datapath: this component
implements no automatic flow control, so software must act on the
interrupt to throttle traffic. See the Programming section.

<<uart-modem-control-input-signals-table>> defines the modem inputs and their status
reporting.

[[uart-modem-control-input-signals-table]]
.UART Modem Control Input Signals
[width="100%",cols="15%,10%,15%,10%,50%",options="header",]
|=======================================================================
|Signal Name |Width |Direction |Active Level |Description
|`cts_ni` |1 |Input |Low |Clear To Send. Asynchronous modem input. When
asserted (low), indicates remote device is ready to receive data.
Reported in `MSR.CTS`; a change sets `MSR.DCTS` and raises the Modem
Status Interrupt. Does not stall the transmitter - flow control is
performed by software.

|`dsr_ni` |1 |Input |Low |Data Set Ready. Asynchronous modem input.
Indicates remote modem is connected and ready. Reported in `MSR.DSR`; a
change sets `MSR.DDSR`.

|`ri_ni` |1 |Input |Low |Ring Indicator. Asynchronous modem input.
Indicates incoming call on modem connection. Reported in `MSR.RI`; a
trailing edge sets `MSR.TERI`.

|`dcd_ni` |1 |Input |Low |Data Carrier Detect. Asynchronous modem input.
Indicates carrier signal detected on modem connection. Reported in
`MSR.DCD`; a change sets `MSR.DDCD`.
|=======================================================================

<<uart-modem-control-output-signals-table>> defines the software-controlled modem
outputs.

[[uart-modem-control-output-signals-table]]
.UART Modem Control Output Signals
[width="100%",cols="15%,10%,15%,10%,50%",options="header",]
|=======================================================================
|Signal Name |Width |Direction |Active Level |Description
|`rts_no` |1 |Output |Low |Request To Send. Modem control output driven
from `MCR.RTS` in the opposite polarity. When asserted (low), indicates
this device is ready to receive data. Driven by software; the receiver
does not deassert it automatically when the RX FIFO fills.

|`dtr_no` |1 |Output |Low |Data Terminal Ready. Modem control output.
Indicates this device is connected and ready for communication.

|`out1_no` |1 |Output |Low |General-purpose output 1. User-defined modem
control output controlled by MCR register.

|`out2_no` |1 |Output |Low |General-purpose output 2. User-defined modem
control output controlled by MCR register. Often used for interrupt
enable in some systems.
|=======================================================================

=== DMA Interface

The DMA interface provides signals for Direct Memory Access controllers
to manage data transfers automatically.

<<uart-dma-interface-signals-table>> defines the receive-ready and transmit-ready
handshake outputs.

[[uart-dma-interface-signals-table]]
.UART DMA Interface Signals
[width="100%",cols="15%,10%,15%,10%,50%",options="header",]
|=======================================================================
|Signal Name |Width |Direction |Active Level |Description
|`rxrdy_o` |1 |Output |High |Receiver ready. Indicates received data is
available for reading. Behavior depends on DMA mode (immediate or
hysteresis).

|`txrdy_o` |1 |Output |High |Transmitter ready. Indicates transmitter is
ready to accept new data. Behavior depends on DMA mode (immediate or
hysteresis).
|=======================================================================

=== Interface Timing Considerations

=== Clock Domain

All interface signals operate in a single clock domain referenced to
`clk_i`. The following timing considerations apply:

* *AXI4-Lite Protocol*: All AXI4-Lite signals must meet setup and hold
time requirements relative to `clk_i`
* *Asynchronous Inputs*: `rx_i` and modem control inputs (`cts_ni`,
`dsr_ni`, `ri_ni`, `dcd_ni`) are asynchronous and are synchronized
internally
* *Reset Requirements*: `rst_ni` should be asserted asynchronously and
deasserted synchronously relative to `clk_i`

=== Serial Interface Timing

* *Baud Rate*: Serial data rate is determined by the divisor latch
registers (DLL/DLM) and uses 16x oversampling
* *Maximum Baud Rate*: Limited to `system_clock_frequency / 32` - a
divisor of `0` disables the transmitter and receiver, so the smallest
usable divisor is `1`
* *Data Frame*: Configurable start bit (always 1), 5-8 data bits,
optional parity bit, 1-2 stop bits

=== Protocol Support

The interface supports standard UART communication protocols:

* *RS-232*: Full modem control and serial data signaling
* *RS-485*: Can be used with external transceivers (using RTS for
direction control)
* *Industrial Protocols*: Compatible with Modbus RTU and other
industrial serial protocols
* *Debug Interfaces*: Suitable for system debug and console applications

The comprehensive interface design ensures compatibility with a wide
range of serial communication requirements while maintaining the
flexibility needed for diverse embedded system applications.
