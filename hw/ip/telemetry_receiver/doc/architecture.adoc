[[telemetry-receiver-architecture]]
== Architecture

The receiver has two stores: a byte assembly buffer for the incoming message
and a queue of decoded messages for software. Neither is a second independently
configurable telemetry channel.

=== Assembly and Decode

An accepted beat (`atvalid_i && atready_o`) writes one assembly byte. Eight
beats form a packet, least-significant byte first. Bit 63 marks the last packet;
the first packet carries the probe ID at bits `[60:56]`. Counter decoding starts
at block 1 of the first packet, continues across packet boundaries, and assembles
each counter most-significant byte first. All four block-valid bits must be set
for a counter to be valid; otherwise its decoded value is zero.

The assembly capacity is derived from `MAX_NUM_COUNTERS_PER_MESSAGE`. Reaching
that capacity without a last-packet marker raises `MISSING_LAST` and resets the
write pointer. A last-packet marker also resets the pointer and queues the
decoded message. The core accepts beats except during a receiver-flush pulse;
message-queue fullness does not apply backpressure.

IMPORTANT: Every configured counter position is decoded, including positions
beyond the last packet received. A short message following a longer one can
therefore inherit trailing values and validity bits. Producers must overwrite
the complete configured message footprint and mark unused counter blocks
invalid. Receiver flush resets the pointer but leaves assembly bytes intact;
only reset clears that storage.

=== Message Queue and Readout

The queue exposes its oldest message in `TELEMETRY_PROBE_ID`,
`TELEMETRY_COUNTER_VLDS` and `TELEMETRY_COUNTER[0..31]`. Reads do not consume data;
`CTRL.BUFFER_POP` advances the queue only when it is nonempty. Empty-queue reads
return zero. Counter registers beyond the configured counter count also return
zero and have cleared validity bits.

On arrival while full, hardware drops the oldest message and advances the read
pointer. There is no snapshot across the separate software reads: overflow can
change the visible message mid-read. Arrange sufficient buffering/service rate,
or quiesce the producer, when a coherent software snapshot is required. `STATUS`
reports empty/full, not a numeric occupancy count or an overflow interrupt.

=== Interrupts

`irq_o` is the OR of the two status sources masked by their corresponding
`INTR_ENABLE` bits. Masking an interrupt does not acknowledge its source.

[cols="1,3",options="header"]
.Telemetry interrupt conditions
|===
|Source |Condition and clearing
|`MISSING_LAST` |Sticky status when assembly capacity is reached without the
last-packet marker. It latches even while disabled. Write one to the status bit
to clear it; `INTR_TEST.MISSING_LAST` supplies a test pulse.
|`BUFFER_THRESHOLD` |Read-only live status while occupancy is strictly greater
than the effective threshold, or `INTR_TEST.BUFFER_THRESHOLD` is set. Drain to
at most the threshold, raise the threshold, or clear the test bit as appropriate.
Writing the status bit does not clear this source.
|===

=== Reset and Flush

++++
endif::backend-html5[]

Reset clears assembly bytes, queue pointers and control/interrupt registers.
Queue payload storage is not reset, but empty-queue reads return zero. Supply
`rst_ni` with asynchronous assertion and deassertion synchronized to `clk_i`.

`CTRL.TELEMETRY_RX_FLUSH` is a pulse that discards queued messages and resets
the assembly pointer. It does not erase either payload store or purge the
wrapper's upstream ATB crossing FIFO. Quiesce traffic when an empty receiver
must remain empty after the pulse.

`CTRL.TELEMETRY_TX_FLUSH` requests a flush from the upstream transmitter through
`afvalid_o`. Hardware clears the request after `afvalid_o && afready_i`.
Completion depends on the producer's acknowledgement; this is separate from a
local receiver flush.
