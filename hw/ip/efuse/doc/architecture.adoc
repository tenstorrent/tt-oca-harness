===== Architecture

The eFuse IP provides secure One-Time Programmable (OTP) memory
management with foundry-agnostic design. The layered architecture
separates security control logic from foundry-specific implementation
details, enabling deployment across different OTP technologies while
maintaining consistent security characteristics and software interfaces.

====== Interface Controller

The eFuse Interface Controller (efuse_interface_controller.sv) provides
dual-path access control with security policy enforcement.

====== Access Paths

* *SMC AXI4-Lite Interface*: Functional access for normal system
operations
* *JTAG AXI4-Lite Interface*: Debug access for manufacturing test and
development

====== Shadow Register Subsystem

The shadow register subsystem optimizes OTP performance through
boot-time caching.

====== State Machine Architecture

The read interface FSM (efuse_read_interface.sv) operates in a simple
two-state sequence, transitioning from idle to waiting for a response as
it handles on-demand eFuse reads that fall outside the shadow register
cache. This mechanism works alongside the shadow subsystem, providing
direct access only when necessary, and actively reports status to
support robust error handling and retry logic.

The write interface FSM (efuse_program_interface.sv) enforces the
write-once nature of OTP hardware, ensuring that programmed data cannot
be altered once set. It supports write-and-verify procedures for
reliability, integrating verification steps that check programmed values
against intended data, and fully blocks any unauthorized overwrites to
maintain data integrity.

====== Interface SHIM Layer

The Interface SHIM (`efuse_interface_shim.sv`) provides foundry-specific
abstraction by converting generic commands to hardware signals.

====== Efuse Bank Model

The reference implementation of the eFuse bank model
(efuse_bank_model.sv) is built around a 3KB (768 x 32-bit words) memory
with a standard APB4 interface. It accurately reproduces the One-Time
Programmable (OTP) timing and set-once behavior of real hardware, and
supports individual bit locking to guard against unwanted programming.

Command handling is straightforward: the system distinguishes between
read commands, write operations to program new bits, and a
write/read-back mode that verifies programming success. All command
processing occurs within a single clock domain (clk_i), with registers
protected by an active-low asynchronous reset (rst_ni). During idle
periods, clock gating conserves power, and all registers release from
reset in a synchronized manner.

For read operations, address decoding intelligently selects the
appropriate destination—whether it be shadow registers for highest
performance, control and status registers, memory-mapped registers, or
the hardware abstraction (SHIM) layer—while live eFuse access routes
through SHIM and the bank model, maintaining strict security at every
step. Write operations leverage the dedicated FSM for validation,
enforce lock checks to prevent unauthorized programming, and use the
SHIM for foundry-specific command translation. Timing control and
verification are tightly coordinated within the bank model.

Security is layered throughout the architecture. Field-level permissions
are managed via efuse_field_map_i, hardware and software lock mechanisms
are enforced, security disable tokens are validated, and protection is
ensured across all architectural levels for defense in depth.

====== Access Permissions and Security

The eFuse IP implements multiple layers of access control. Access
permissions are controlled by the `efuse_field_map_i` input, which
defines rules for each eFuse field:

[source,sourceCode,systemverilog]
----
typedef struct packed {
    logic [EFUSE_FIELD_MAP_IDX_WIDTH-1:0] idx;    // Field index
    logic [3:0]                          lock;   // Lock bits
    logic [31:0]                         start_addr; // Start address
    logic [31:0]                         end_addr;   // End address
} rule_t;
----

The eFuse IP employs several lock mechanisms to manage access and
security. Hardware locks, once set through eFuse programming, are
permanent and cannot be undone. In contrast, software locks provide
temporary restrictions and can be cleared with a system reset.
Additionally, access can be gated based on the current chip life cycle
state, enforcing further control depending on operational mode.

For sensitive functions, such as those governed by the MMR registers,
the system enforces token-based security. Only by providing the correct
256-bit tokens—the RMA SOP Token for state transitions, the RMA Chiplet
Token for chiplet-specific operations, or the Security Disable Token to
override protections—can access to these resources be granted.
