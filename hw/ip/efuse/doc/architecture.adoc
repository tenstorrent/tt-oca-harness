[[efuse-architecture]]
== Architecture

The eFuse IP provides secure One-Time Programmable (OTP) memory
management with foundry-agnostic design. The layered architecture
separates security control logic from foundry-specific implementation
details, enabling deployment across different OTP technologies while
maintaining consistent security characteristics and software interfaces.

=== Interface Controller

The eFuse Interface Controller (efuse_interface_controller.sv) provides
dual-path access control with security policy enforcement.

=== Access Paths

* *SMC AXI4-Lite Interface*: Functional access for normal system
operations
* *JTAG AXI4-Lite Interface*: Debug access for manufacturing test and
development

=== Command-path ownership

After fuse sense completes, software program and read requests share one
command path to the OTP bank. `EFUSE_PROGRAM_CTRL.program_enable` takes
that path in preference to `EFUSE_READ_CTRL.read_enable`, so the two
enables must be asserted exclusively. `program_enable` is a mode-ownership
bit: after `PROGRAM_DONE`, software deasserts `program_enable`
before any later read. The programming sequence is in
<<smc-dv-efuse-programming>>.

=== Shadow Register Subsystem

The shadow register subsystem accelerates OTP access by caching eFuse contents at boot time. On power-up, a dedicated FSM automatically issues a bulk read command (with `access_length_words` set to cover the full eFuse bank), copying all OTP data into the shadow registers. This ensures the shadow registers are fully populated and always synchronized with the OTP state at each boot.

=== State Machine Architecture

The read interface FSM (efuse_read_interface.sv) operates in a simple
two-state sequence, transitioning from idle to waiting for a response as
it handles on-demand eFuse reads that fall outside the shadow register
cache. This mechanism works alongside the shadow subsystem, providing
direct access only when necessary, and actively reports status to
support robust error handling and retry logic.

The program interface FSM (efuse_program_interface.sv) enforces the
write-once nature of OTP hardware, ensuring that programmed data cannot
be altered once set. It supports write-and-verify procedures for
reliability, integrating verification steps that check programmed values
against intended data, and fully blocks any unauthorized overwrites to
maintain data integrity.

*Readback Capture Behavior:*

When a read command completes successfully, the read interface captures data from
the SHIM response into the read-data CSR during the ST_WAIT_RESP state. This data
is retained and continues to be available after the FSM returns to idle, allowing
software to retrieve the result without a re-read.

=== Parameterized Command Typedefs

The fuse command request/response structs exchanged between the
controller and the SHIM are not declared with fixed types. Instead, they
are generated from parameterized preprocessor macros defined in
`efuse_typedef.svh`. This keeps the command interface technology-agnostic:
each integration supplies its own address, data, access-length, and
command types, while the macros guarantee a consistent struct layout and
field ordering across all OTP variants.

<<efuse-command-type-macros-table>> relates each command macro to its generated type and
purpose.

[[efuse-command-type-macros-table]]
[width="100%",cols="35%,30%,35%",options="header",]
.eFuse command type macros
|=====================================================================================
|Macro |Generated Type |Purpose
|`EFUSE_COMMAND_REQ_T` |`fuse_command_req_t` |Controller-to-SHIM command request
|`EFUSE_COMMAND_RESP_T` |`fuse_command_resp_t` |SHIM-to-controller command response
|=====================================================================================

The request macro is parameterized over the struct name plus four payload
types (`addr_t`, `data_t`, `access_length_words_t`, `command_t`), allowing
the controller to size the address space, transfer length, and command
encoding to match the target OTP technology:

[source,sourceCode,systemverilog]
----
`define EFUSE_COMMAND_REQ_T(fuse_command_req_t, addr_t, data_t, access_length_words_t, command_t)  \
  typedef struct packed {                                       \
    addr_t                    address;             // Target address       \
    logic                     program_data;        // Data to program (1'b1) \
    access_length_words_t     access_length_words; // Transfer size        \
    command_t                 command;             // Command type         \
    logic                     valid;               // Request valid        \
  } fuse_command_req_t;
----

The response macro is parameterized over the struct name and the
`data_t` read-data type:

[source,sourceCode,systemverilog]
----
`define EFUSE_COMMAND_RESP_T(fuse_command_resp_t, data_t)       \
  typedef struct packed {                                       \
    data_t              data;       // Read data                \
    logic               status;     // Operation status         \
    logic               valid;      // Response valid            \
  } fuse_command_resp_t;
----

A typical instantiation expands both macros with the integration's local
types:

[source,sourceCode,systemverilog]
----
`EFUSE_COMMAND_REQ_T(fuse_command_req_t, addr_t, data_t, access_length_words_t, command_t)
`EFUSE_COMMAND_RESP_T(fuse_command_resp_t, data_t)
----

=== Interface SHIM Layer

The Interface SHIM (`efuse_interface_shim.sv`) is an example, foundry-specific
implementation of the custom fuse command interface. Its role is to translate
the controller's generic commands into the signaling expected by a particular
OTP macro; in this reference version the macro-side interface is APB, but a
real integration would replace this with the foundry's native signals.

The SHIM decodes three command types from the controller:

* *Read* — fetch one or more words from the bank.
* *Program* — burn new bits into the bank.
* *Program/read-back* — program, then read back to verify success.

It implements these with dedicated read and program FSMs that sequence the
macro-side transactions and return a `fuse_command_resp_t` to the controller.
Foundry-specific timing and configuration (for example, program pulse widths)
are exposed through the SHIM Control CSRs, accessed over the
`fuse_bank_ctrl` AXI4-Lite interface.

=== eFuse Bank Model

The eFuse bank model (`efuse_bank_model.sv`) is a reference, simulation-only
stand-in for the real foundry OTP macro. It is a 3KB (768 x 32-bit word) store
fronted by a standard APB interface, and it emulates the set-once behavior of
real OTP so the controller and SHIM can be exercised end-to-end without
silicon. In a production integration it is replaced by the actual foundry
macro driven by the SHIM.

=== Access Permissions and Security

Access control is layered for defense in depth: per-field permissions
are described by `efuse_field_map_i`, lock state is enforced by the eFuse
guard (`efuse_guard.sv`), security-disable tokens are validated, and
access can additionally be gated by the chip lifecycle state.

Each eFuse field is described by a `rule_t` entry that pairs an address
range with a 4-bit `lock` permission field:

[source,sourceCode,systemverilog]
----
typedef struct packed {
    logic [EfuseFieldMapIdxWidth-1:0] idx;        // Field index
    logic [3:0]                           lock;       // Permission bits
    logic [31:0]                          start_addr; // Field start address
    logic [31:0]                          end_addr;   // Field end address
} rule_t;
----

The `lock` field encodes read, write, and secure-test-mode permissions
for the field (<<efuse-lock-field-encoding-table>>).

[[efuse-lock-field-encoding-table]]
[width="100%",cols="18%,22%,60%",options="header",]
.eFuse lock-field encoding
|=====================================================================================
|Bits |Function |Encoding
|`lock[0]` |Read |`0` = readable, `1` = read-locked
|`lock[2:1]` |Write |`00` = unlocked, `10` = set-only (1's may be added, never cleared), `11` = write-locked
|`lock[3]` |Secure-test write lock |`1` adds a shadow write lock while secure test mode is active; `0` adds no such lock. Other locks still apply.
|=====================================================================================

=== Hardware vs. Software Locks

The same permission semantics are reached through two independent
mechanisms, and the guard enforces whichever is more restrictive (<<efuse-hardware-and-software-locks-table>>).

[[efuse-hardware-and-software-locks-table]]
[width="100%",cols="20%,40%,40%",options="header",]
.eFuse hardware and software locks
|=====================================================================================
|Property |Hardware Lock |Software Lock
|Source |Permission bits fused into the eFuse array (the field map reflects
the programmed values) |Runtime writes to the `LOCKS` CSR (write-1-to-set)
|Persistence |Permanent — backed by one-time-programmable bits and cannot
be cleared once set |Volatile — retained only until the next system reset
|Reversibility |Irreversible by any means |Cleared by reset, allowing the
field to be re-opened
|Typical use |Final production lockdown of provisioned secrets |Temporary
protection during boot, debug, or staged provisioning
|=====================================================================================

Because software locks are write-1-to-set, firmware can tighten access at
runtime but can never loosen a restriction without a reset; hardware locks
cannot be loosened at all. On top of these per-field locks, sensitive
fields can be further gated by the chip lifecycle state and by secure test
mode (`lock[3]`), so a field may be accessible in one operational mode and
fully blocked in another even when its read/write bits are clear.

For sensitive functions, such as those governed by the MMR registers,
the system enforces token-based security. Only by providing the correct
256-bit tokens, such as the RMA SOP Token for state transitions, the RMA Chiplet
Token for chiplet-specific operations, or the Security Disable Token to
override protections, can access to these resources be granted.

=== Security Disable Bypass Mechanism

The eFuse interface controller supports a security disable bypass mechanism
via the `security_disable_i` input signal. This mechanism is primarily used
for test and debug scenarios where the automatic fuse sensing sequence needs
to be bypassed.

*Behavior when `security_disable_i` is asserted:*

<<efuse-security-disable-behavior-table>> describes the sensing behavior when
security_disable_i is asserted.

[[efuse-security-disable-behavior-table]]
[width="100%",cols="30%,70%",options="header",]
.eFuse security-disable behavior
|=====================================================================================
|Behavior |Description
|FSM Bypass |The automatic fuse sensing state machine is bypassed and does not
issue read commands to the physical eFuse bank.

|Shadow Register Output |Shadow register values are output directly to
downstream logic via `shadow_regs_o`, regardless of `fuse_sense_done` status.

|Shadow Register Loading |Shadow registers are not loaded from fuse command
responses; they retain their reset values (all zeros for SMC).

|APB Access |APB access to shadow registers is permitted without waiting for
`fuse_sense_done` completion.

|Reset Values |When the system is in reset state with `security_disable_i`
asserted, shadow registers are initialized to zero (default reset value for SMC).
|=====================================================================================

For SMC, the internal security disable signal is directly driven by the
`security_disable_i` input port.

=== Lifecycle State (LC_STATE) Effects

The eFuse interface controller enforces access restrictions based on the
chip's lifecycle state.

*Lifecycle State Encoding:*

<<efuse-lifecycle-encodings-table>> lists the lifecycle encodings used by the eFuse
controller.

[[efuse-lifecycle-encodings-table]]
[width="100%",cols="25%,25%,50%",options="header",]
.eFuse lifecycle encodings
|=====================================================================================
|State |Encoding |Description
|TEST_DEV |0x0 |Test/Development state (default)
|PROD |0x1 |Production state
|PROD_DBG |0x1 + DEMOTE=1 |Production Debug (volatile, clears on reset)
|RMA_SOP |0x2, 0x3 |RMA System-in-Package
|RMA_CHIPLET |0x6-0x7 |RMA Chiplet level
|PROD_END |0x8 |Production End (terminal state)
|INVALID |All others |Invalid state (error fallback)
|=====================================================================================

*JTAG Access Control Based on LC_STATE:*

JTAG access policies differ between SMC and SEP variants. The table below describes
the SMC variant policy, which restricts JTAG access in production and RMA states.
SEP applies a different policy: in restricted states (PROD or RMA_SIP), JTAG
accesses to the MMR (token register) space remain allowed for token programming;
accesses outside the MMR space are blocked with an error response.

*SMC JTAG Policy:*

When lifecycle state is PROD (0x1) or RMA_SOP (0x2, 0x3), JTAG access
to eFuse registers is restricted (<<efuse-lifecycle-based-jtag-permissions-table>>).

[[efuse-lifecycle-based-jtag-permissions-table]]
[width="100%",cols="32%,43%,25%",options="header",]
.eFuse JTAG permissions (SMC)
|=====================================================================================
|Access Type |PROD/RMA_SOP State |Other States
|JTAG Write |*Blocked* (error response) |Allowed
|JTAG Read |*Blocked* except JTAG_PUBLIC_IDENTITY |Allowed
|JTAG Read JTAG_PUBLIC_IDENTITY |Allowed |Allowed
|=====================================================================================

The access control mechanism uses an AXI-Lite demux that routes blocked
requests to an error slave. When a request is blocked, the error slave
returns an error response with data value `0xbadcab1e`.

*SMC exception for JTAG_PUBLIC_IDENTITY:*

Even in PROD or RMA_SOP states, JTAG read access to the JTAG_PUBLIC_IDENTITY
register is permitted. This allows identification of the chip for manufacturing
and field returns without exposing sensitive eFuse contents.

=== Secure Test Mode (secure_tm_i)

The eFuse interface controller supports a Secure Test Mode via the `secure_tm_i`
input signal. This mode provides additional protection for sensitive security
assets during secure manufacturing test operations.

*Behavior when `secure_tm_i` is asserted:*

<<efuse-secure-test-behavior-table>> describes the restrictions applied when secure_tm_i
is asserted.

[[efuse-secure-test-behavior-table]]
[width="100%",cols="30%,70%",options="header",]
.eFuse secure-test behavior
|=====================================================================================
|Behavior |Description
|Fuse Command Blocking |All fuse commands to the physical eFuse bank are blocked.
The guard logic filters incoming requests and returns default responses.

|RMA Token Protection |RMA SOP and RMA Chiplet tokens are disconnected from
shadow register outputs (set to zero), preventing token exposure during test.

|Write Lock Contribution |Secure test mode contributes to write lock status,
preventing shadow register modifications.

|Response Behavior |When fuse commands are blocked, default response values
(all zeros) are returned to requesters.
|=====================================================================================

*SMC Configuration:*

For SMC, `secure_tm_i` is tied to logic `0`, meaning Secure Test Mode is not
active during normal SMC operation. This signal is primarily relevant for SEP
where sensitive RMA tokens must be protected during manufacturing test flows.
