# Memory Interface

This directory contains the `memory_interface` module - a reusable AXI-to-memory bridge component that can be integrated into any memory-based design.

## Overview

The `memory_interface` module provides a standardized bridge between AXI4/AXI4-Lite bus interfaces and a generic memory interface protocol. This allows designers to easily integrate memory controllers into their systems without dealing with AXI protocol details. It is to be used along with an "Interface Shim" module that contains the CSRs and the memory interface to the memory macro, and a memory macro module. Examples of the Interface Shim and memory macro are provided in the `rtl/examples` directory. See the image below for a diagram of the components for a complete implementation of memory (note the separation between OCAH and adopter implemented components).

## Core Component: `memory_interface`

The `memory_interface` module is the key reusable component that provides a bridge between system bus interfaces and memory controllers. It handles protocol conversion from AXI4/AXI4-Lite to a simple memory interface, while also providing address translation and routing between CSR (register) and memory access paths. It can be used for any type of memory, not just the SRAM/ROM examples provided. It only supports word-aligned memory addresses (e.g. 0x0000, 0x0004, 0x0008, etc.).

### Generating the Interface

The `memory_interface` module supports separate interface types for CSR (register) and memory access, with both struct and flattened signal options. You can use the `generate_ip.py` script to generate the module with the appropriate interface types.

```bash
python3 generate_ip.py --name <name> --mem-port <mem-port-type> --csr-port <csr-port-type>
```

### Name Options (`--name`):

* `memory_interface` - Default name if `--name` is not specified
* `name` - Custom name for the generated module

If you specify the same name twice (or default twice), the script will add a number to the end of the name to make it unique (i.e. `memory_interface_1`).

### Memory Interface Options (`--mem-port`):

* `axi4` - Struct AXI4 interface for memory access
* `axi4-lite` - Struct AXI4-Lite interface for memory access
* `axi4-flattened` - Flattened AXI4 signals for memory access
* `axi4-lite-flattened` - Flattened AXI4-Lite signals for memory access


### CSR Interface Options (`--csr-port`):

* `axi4-lite` - Struct AXI4-Lite interface for register access
* `apb4` - Struct APB4 interface for register access
* `axi4-lite-flattened` - Flattened AXI4-Lite signals for register access
* `apb4-flattened` - Flattened APB4 signals for register access

### Example Usage:
```bash
# AXI4-Lite CSR with AXI4 memory
python3 generate_ip.py --csr-port axi4-lite --mem-port axi4

# APB4 CSR with AXI4-Lite memory
python3 generate_ip.py --csr-port apb4 --mem-port axi4-lite

# Flattened interfaces
python3 generate_ip.py --csr-port axi4-lite-flattened --mem-port axi4-flattened
```

### Implementation Requirements

To use this interface, you must define all parameters in the `memory_interface.sv` module. Here are all of the possible parameters, some are not needed depending on the interface type you generate:

**NOTE**: All of these parameters are defined in `example_sram_pkg.sv`/`example_rom_pkg.sv` and can be overridden as needed.

```systemverilog
// User Specified Parameters
parameter int unsigned MEM_ADDR_WIDTH           // Memory address width
parameter int unsigned MEM_DATA_WIDTH           // Memory data width
parameter int unsigned MEM_ID_WIDTH             // Memory ID width
parameter int unsigned AXI_USER_WIDTH           // AXI user width
parameter int unsigned CSR_ADDR_WIDTH           // CSR address width
parameter int unsigned CSR_DATA_WIDTH           // CSR data width

// Address Decode
parameter logic [31:0] CSR_BASE_ADDR            // CSR base address
parameter logic [31:0] MEM_BASE_ADDR            // Memory base address

// Type Definitions
// Memory Interface Types (flattened interfaces)
parameter type mem_addr_t;                      // Memory address type
parameter type mem_data_t;                      // Memory data type
parameter type mem_strb_t;                      // Memory strobe type
parameter type mem_id_t;                        // Memory ID type
parameter type mem_user_t;                      // Memory user type

// Memory Interface Types (struct interfaces)
parameter type mem_req_t;                       // Memory request struct
parameter type mem_rsp_t;                       // Memory response struct
parameter type mem_axi_req_t;                   // AXI memory request struct
parameter type mem_axi_resp_t;                  // AXI memory response struct
parameter type mem_axil_req_t;                  // AXI4-Lite memory request struct
parameter type mem_axil_resp_t;                 // AXI4-Lite memory response struct

// CSR Interface Types (flattened interfaces)
parameter type csr_addr_t;                      // CSR address type
parameter type csr_data_t;                      // CSR data type
parameter type csr_strb_t;                      // CSR strobe type

// CSR Interface Types (struct interfaces)
parameter type csr_axil_req_t;                  // AXI4-Lite CSR request struct
parameter type csr_axil_resp_t;                 // AXI4-Lite CSR response struct
parameter type csr_apb_req_t;                   // APB4 CSR request struct
parameter type csr_apb_resp_t;                  // APB4 CSR response struct
```

### Key Features

* **Dual Interface Support**: Separate configurable interfaces for CSR (registers) and memory access
* **Address Translation**: Automatic address parsing and translation using configurable base addresses
  - CSR transactions: Translates from system addresses to local CSR addresses using `CSR_BASE_ADDR`
  - Memory transactions: Translates from system addresses to local memory addresses using `MEM_BASE_ADDR`
* **Word Aligned Addresses**: The memory interface only supports word-aligned addresses (e.g. 0x0000, 0x0004, 0x0008, etc.).
* **Interface Validation**: Built-in assertions validate interface parameters and struct compatibility
* **Flexible Interface Options**: Support for both struct-based and flattened signal interfaces

### Built-in Parameter Validation

The `memory_interface` module includes comprehensive assertions to validate configuration parameters and ensure interface compatibility:

* **Memory Interface Validation**: Validates `MEM_ADDR_WIDTH`, `MEM_DATA_WIDTH`, and `MEM_ID_WIDTH` parameters
* **CSR Interface Validation**: Validates `CSR_ADDR_WIDTH` and `CSR_DATA_WIDTH` parameters
* **Type Width Checking**: Ensures typedef widths match parameter values when using flattened interfaces
* **Protocol Constraints**: Enforces protocol-specific constraints (e.g., AXI4-Lite data width limitations)

**Warning**: There is no validation if using struct interfaces due to SystemVerilog limitations, proceed with caution if using these. This will not be an issue for flattened interfaces.

These assertions help catch configuration errors early in the design flow and ensure proper interface integration.

## Memory Interface Protocol

The `memory_interface` module outputs a simple memory interface that you connect to your SRAM controller. The interface can be provided as either structured types or flattened signals, depending on your configuration.

### Structured Interface Mode

#### Memory Request (`mem_req_t`)
```systemverilog
typedef struct packed {
    logic                           req;        // Request valid
    logic [MEM_ADDR_WIDTH-1:0]      addr;       // Memory address
    logic [MEM_DATA_WIDTH-1:0]      wdata;      // Write data
    logic [MEM_DATA_WIDTH/8-1:0]    strb;       // Byte strobe
    axi_pkg::atop_t                 atop;       // Atomic operation type
    logic                           wenable;    // Write enable
} mem_req_t;
```

#### Memory Response (`mem_rsp_t`)
```systemverilog
typedef struct packed {
    logic                           gnt;        // Grant (memory isready to accept)
    logic                           rvalid;     // Response data valid (read or write)
    logic [MEM_DATA_WIDTH-1:0]      rdata;      // Read data
} mem_rsp_t;
```

### Flattened Interface Mode

When using flattened interfaces, the memory signals are provided as individual ports to the memory interface shim:

```systemverilog
// Memory Request Signals
input   logic                    mem_req_i;      // Request valid
input   mem_addr_t               mem_addr_i;     // Memory address
input   mem_data_t               mem_wdata_i;    // Write data
input   mem_strb_t               mem_strb_i;     // Byte strobe
input   axi_pkg::atop_t          mem_atop_i;     // Atomic operation type
input   logic                    mem_wenable_i;  // Write enable

// Memory Response Signals
output  logic                    mem_gnt_o;      // Grant (memory is ready to accept)
output  logic                    mem_rvalid_o;   // Response data valid (read or write)
output  mem_data_t               mem_rdata_o;    // Read data
```

## Example Implementation

There are two examples provided in the `rtl/examples` directory:
- `rtl/examples/sram` - Shows integration with SRAM macro and CSRs
- `rtl/examples/rom` - Shows integration with ROM macro and CSRs

These directories include example templates and register definitions that show how to use `memory_interface`. Both of these examples use memory macros that support word-aligned addresses (e.g. 0x0000, 0x0001, 0x0002, etc.), so the interface shim translates the word-aligned addresses from the memory interface to the byte-aligned addresses for the memory macro. This is vital for the memory interface to work correctly.

**Note**: The RDL (Register Description Language) files are provided as examples for register generation, but you don't have to use RDL - you can define your registers using any method that suits your design flow.

**These are templates and examples only** - customize them for your specific implementation. The SRAM macro, interface shim, and register definitions should be adapted to match your actual hardware requirements.

### SRAM Example

#### SystemVerilog Templates
- `rtl/examples/sram/templates/example_sram_wrapper.sv.tpl` - Shows integration with SRAM macro and CSRs
- `rtl/examples/sram/templates/example_sram_interface_shim.sv.tpl` - Shows CSR integration and memory interface handling, translates word-aligned addresses to byte-aligned addresses for the SRAM macro
- `rtl/examples/sram/example_sram_pkg.sv` - Shows package definitions needed for AXI, AXI4-Lite, and APB4 interfaces

#### Register Definitions (Optional)
- `regs/sram_example/example_sram_macro_csr.rdl` - CSR register descriptions
- `regs/sram_example/example_sram_wrap.rdl` - Wrapper register descriptions
- `regs/sram_example/example_sram.rdl` - SRAM register descriptions

#### Testbench
- `tb_sram/templates/tb_sram.sv.tpl` - SystemVerilog testbench template
- `tb_sram/templates/tb_sram.py.tpl` - Python test suite template (basic read/write operations and CSR read/write operations)

### ROM Example

The ROM example demonstrates how to integrate read-only memory with the memory interface. Unlike SRAM, ROM only supports read operations and requires its contents to be initialized at simulation time.

#### SystemVerilog Templates
- `rtl/examples/rom/templates/example_rom_wrapper.sv.tpl` - Shows integration with ROM macro and CSRs
- `rtl/examples/rom/templates/example_rom_interface_shim.sv.tpl` - Shows CSR integration and memory interface handling, translates word-aligned addresses to byte-aligned addresses for the ROM macro
- `rtl/examples/rom/example_rom_pkg.sv` - Shows package definitions needed for AXI, AXI4-Lite, and APB4 interfaces
- `rtl/examples/rom/generate_rom_init.py` - ROM initialization script for generating ROM content (Only works with VCS, not Verilator, this limitation is built into the python testbench)

#### Register Definitions (Optional)
- `regs/rom_example/example_rom_macro_csr.rdl` - CSR register descriptions
- `regs/rom_example/example_rom_wrap.rdl` - Wrapper register descriptions
- `regs/rom_example/example_rom.rdl` - ROM register descriptions

#### Testbench
- `tb_rom/templates/tb_rom.sv.tpl` - SystemVerilog testbench template
- `tb_rom/templates/tb_rom.py.tpl` - Python test suite template (basic read operations and CSR read/write operations)

## Quick Setup Guide

### Prerequisites Setup
```bash
# Load the environment setup
source bin/setup_env.sh  # from OCAH repository root

# Navigate to SRAM peripheral directory
cd hw/ip/memory_interface
```

### Generating and Testing

```bash
# Generate the IP first (required before testing)
python3 generate_ip.py --csr-port axi4-lite --mem-port axi4

# Navigate to testbench directory
cd tb_sram
# or
cd tb_rom

# Clean build
make clean

# Run all tests
make

# Run with specific simulator
make SIM=vcs

# Run a specific test
make TESTCASE=reset_and_init_test

# Run with waveform generation
make SIM=vcs WAVES=1
```
