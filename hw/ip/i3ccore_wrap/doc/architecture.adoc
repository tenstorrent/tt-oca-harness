[[i3ccore-wrap-architecture]]
===== Architecture

The I3C Core Controller is a MIPI I3C v1.0/v1.1.1 and HCI v1.2 compliant
communication controller supporting both active controller (master) and target
(slave) operations with I2C backward compatibility. The architecture provides
high reliability with hardware-managed queue operations, threshold-based
interrupts, and AXI4-Lite integration.

====== System Overview

The I3C controller is organized as a three-level wrapper hierarchy:

* *i3ccore_wrapper*: Top-level multi-instance demultiplexer supporting up to
6 independent I3C instances with AXI4-Lite address decoding
* *i3c_wrapper*: Per-instance wrapper handling CSR interfacing and signal
routing for a single I3C controller
* *i3c*: Main I3C module containing HCI queues, control/status registers,
controller/target FSMs, and physical layer interface

Each I3C instance occupies 0x1000 bytes of address space (12-bit addressing),
allowing software to access multiple controllers through a unified AXI4-Lite
interface.

This document goes over the i3c controller on a high level. For detailed
i3c controller fsm overview, look at the i3c-core-fork repo, under:
doc/i3c_controller_fsm_specification.adoc

====== Functional Blocks

====== Control and Status Registers (I3CCSR)

The I3CCSR module provides a comprehensive register interface organized into
hierarchical sections:

* *I3CBase* (0x00-0x68): Core controller configuration including HC_CONTROL,
PRESENT_STATE, INTR_STATUS, RESET_CONTROL, and section offset pointers
* *PIOControl* (0x80-0xB0): Programmable I/O interface with command/response/data
ports and threshold configuration registers
* *I3C_EC* (Extended Capabilities, 0x100-0x3A0): Secure Firmware Recovery
Interface (0x100-0x168), Standby Controller Mode (0x180-0x1C0), Target
Transaction Interface (0x200-0x290), SoC Management Interface (0x300-0x390),
Controller Config (0x398-0x39C), and Termination (0x3A0)
* *DAT* (0x400-0x7FF): Device Address Table, 128-entry address window
(2 DWORDs per entry) mapping device indexes to dynamic addresses
* *DCT* (0x800-0xFFF): Device Characteristic Table, 128-entry address window
(4 DWORDs per entry) holding device-specific characteristics

All registers are 32-bit aligned and accessed via a 12-bit address interface
from the AXI4-Lite slave.

====== HCI Queue Management

The Host Controller Interface implements five independent FIFO structures
for descriptor-based transaction management:

*Command Queue (64-bit entries)*: Software writes command descriptors
specifying transaction type (private transfer, CCC, I2C), target address,
data length, and control flags (TOC, WROC, RnW). The queue depth is
configurable via RDL parameters.

*Response Queue (32-bit entries)*: Hardware generates response descriptors
upon transaction completion containing transaction ID, error code, and actual
bytes transferred. Response ready triggers RESP_READY interrupt.

*TX Data Queue (32-bit entries)*: Stores outgoing data for controller write
transactions. Software fills the queue triggered by TX_THLD_STAT interrupt
when free space exceeds threshold. Hardware fetches data in 4-byte increments
during write operations.

*RX Data Queue (32-bit entries)*: Stores incoming data from controller read
transactions and target mode receives. Hardware accumulates received bytes
in 4-byte chunks and pushes to queue. RX_THLD_STAT interrupt triggered when
data available exceeds threshold.

*IBI Queue (32-bit entries)*: Stores In-Band Interrupt descriptors containing
IBI source address, optional payload data, and timestamp. IBI_STATUS_THLD
interrupt triggered when IBI entries exceed threshold.

*Unified Queue Design*: When both CONTROLLER_SUPPORT and TARGET_SUPPORT are
enabled, TX and RX queues are shared between controller and target modes to
reduce area. The OPERATION_MODE register selects which mode can access the
queues at runtime.

====== I3C Controller Processing Engine

The controller processing engine manages all I3C protocol operations through
integrated state machines coordinating byte-level (flow_active.sv) and
bit-level (i3c_controller_fsm.sv) operations.

*flow_active.sv (Transaction Flow FSM)*: Orchestrates high-level transaction
flow including command descriptor parsing, FIFO fetching/pushing, byte-by-byte
transfer sequencing, DAT/DCT lookup, and response descriptor generation.
Handles private transfers, CCC commands, and IBI reception.

*i3c_controller_fsm.sv (Physical Layer FSM)*: Manages bit-level SCL/SDA timing
control for START/STOP generation, byte transmission with T-bit parity,
ACK/NACK detection, and mode switching between Open-Drain and Push-Pull. Uses
software-configured timing parameters for precise bus timing across all
clock frequencies.

The controller FSM supports two timing modes:

[cols="30%,35%,35%",options="header"]
|===
|Timing Parameter |Open-Drain Mode |Push-Pull Mode

|Rise Time (t_r) |Programmable (typ. 1000ns I2C) |0-50ns
|Fall Time (t_f) |Programmable (typ. 300ns I2C) |0-50ns
|SCL High (thigh) |Programmable (≥4000ns I2C-SM) |Programmable
|SCL Low (tlow) |Programmable (≥4700ns I2C-SM) |Programmable
|Data Setup (tsu_dat) |Programmable (≥250ns I2C) |Programmable
|Data Hold (thd_dat) |Programmable (≥0ns I2C) |Programmable
|START Hold (thd_sta) |Programmable (≥4000ns I2C) |N/A
|START Setup (tsu_sta) |Programmable (≥4700ns I2C) |N/A
|STOP Setup (tsu_sto) |Programmable (≥4000ns I2C) |N/A
|Bus Free (t_buf) |Programmable (≥4700ns I2C) |N/A
|===

Open-Drain mode uses slower timing compatible with I2C and multi-controller
arbitration. Push-Pull mode achieves 12.5 MHz operation with near-zero
rise/fall times for maximum I3C performance.

All I3C transactions follow a common initialization sequence before diverging
into transaction-specific operations. The flows below trace data movement
from software commands through HCI queues, flow control FSM, physical layer
FSM, and finally to the I3C bus.

====== Transaction Initialization Flow

Every controller-initiated transaction begins with a common initialization
sequence:

....
   [START]
      |
      v
  +--------+
  |  IDLE  |<----------------------+
  +--------+                       |
      |                           |
      | Command Available         |
      v                           |
 +--------------+                 |
 | WaitStartTrig|                 |
 +--------------+                 |
      |                           |
      | TX/RX Threshold Met       |
      v                           |
 +-----------+                    |
 | FetchDAT  |                    |
 +-----------+                    |
      |                           |
      | DAT Entry Captured        |
      v                           |
 +---------------+                |
 | BroadcastAddr |                |
 |  Send 0x7E+W  |                |
 +---------------+                |
      |                           |
      +---> [Transaction Phase] --+
            (Write/Read/CCC/IBI)
....

1. *IDLE*: flow_active.sv waits for command descriptor availability in Command
Queue (signaled by hardware queue depth tracking)

2. *WaitStartTrig*: Check TX/RX FIFO threshold conditions to ensure sufficient
data/space before starting transaction (prevents underflow/overflow)

3. *FetchDAT*: Look up target device dynamic address from Device Address Table
using dev_idx field from command descriptor. DAT provides the dynamic address,
IBI accept/reject configuration, and auto-command settings.

4. *BroadcastAddr*: Transmit I3C broadcast address (0x7E) + Write bit + T-bit
in Open-Drain mode. Purpose: Alert all targets that a transaction is starting
and allow multi-controller arbitration. This phase is mandatory for all
controller-initiated I3C transactions.

5. Transition to transaction-specific phase based on command type (private
write/read, CCC, or IBI detection during broadcast).

====== Controller Write Transaction Flow

....
  From BroadcastAddr
         |
         v
  +---------------+
  |  TargetAddr   |
  | Send Addr+W+Sr|
  +---------------+
         |
         +--> NACK --> WriteResp --> IDLE
         |             (Error)
         v ACK
  +--------------+
  | FetchTxData  |
  | Read TX FIFO |
  +--------------+
         |
         +--> TX Empty --> WriteResp --> IDLE
         |                 (Error)
         v Data Available
  +---------------+
  | I3CDataWrite  |
  | Send byte+Tbit|<--+
  +---------------+   |
         |            |
         | Every 4B   |
         +------------+
         |
         v Transfer Complete
  +-------------+
  |  WriteResp  |
  | Gen Response|
  +-------------+
         |
         v
      IDLE
....

*Detailed Step-by-Step Flow*:

1. *TargetAddr*: Transmit target device 7-bit dynamic address + R/W=0 (write)
+ Sr (repeated START). If target supports Push-Pull mode (indicated in DCT),
switch from Open-Drain to Push-Pull for improved speed. Wait for ACK (I2C)
or T-bit (I3C) acknowledgment from target.

2. *FetchTxData*: Read 32-bit DWORD (4 bytes) from TX Data FIFO. Software
must have previously filled TX FIFO in response to TX_THLD_STAT interrupt,
which fires when free FIFO space ≥ TX_BUF_THLD bytes.

3. *I3CDataWrite*: Transmit data bytes sequentially:
   * Send byte MSB-first (bit 7 → bit 0) on SDA
   * Generate T-bit (odd parity for I3C: T = byte XOR parity)
   * Fetch new DWORD from TX FIFO every 4 bytes
   * Repeat until data_length bytes transferred from command descriptor

4. *WriteResp*: Generate response descriptor containing:
   * Transaction ID (TID from command descriptor)
   * Error code (SUCCESS, NACK, UNDERFLOW, etc.)
   * Actual bytes transferred
   * Push descriptor to Response Queue

5. Trigger INTR_STATUS.RESP_READY interrupt to notify software

6. Return to IDLE state for next transaction

*Error Handling*:
* NACK on TargetAddr → Abort, generate error response (ERROR_NACK)
* TX FIFO Empty during FetchTxData → Abort, generate error response
(ERROR_UNDERFLOW)

*Producer-Consumer Pattern*: Software (producer) fills TX FIFO triggered by
threshold interrupts, hardware (consumer) fetches data during transmission.
Threshold-based operation prevents FIFO underflow while minimizing interrupt
overhead.

====== Controller Read Transaction Flow

....
  From BroadcastAddr
         |
         v
  +---------------+
  |  TargetAddr   |
  | Send Addr+R+Sr|
  +---------------+
         |
         +--> NACK --> WriteResp --> IDLE
         |             (Error)
         v ACK
  +---------------+
  | I3CDataRead   |<-------+
  | Recv byte     |        |
  +---------------+        |
         |                 |
         v                 |
  +---------------+        |
  |  PushRxData   |        |
  | Write RX FIFO |        |
  +---------------+        |
         |                 |
         +--> Full --> WriteResp --> IDLE
         |             (Error)
         |                 |
         +-- More Data ----+
         |   (loop every 4B)
         v Transfer Complete
  +-------------+
  |  WriteResp  |
  | Gen Response|
  +-------------+
         |
         v
      IDLE
....

*Detailed Step-by-Step Flow*:

1. *TargetAddr*: Transmit target device 7-bit dynamic address + R/W=1 (read)
+ Sr. Switch to Push-Pull if target supports it. Wait for ACK/T-bit from
target confirming readiness to send data.

2. *I3CDataRead*: Receive data bytes from target:
   * Sample SDA bit-by-bit (MSB first) on SCL rising edge
   * Send ACK after each byte to request more data
   * Send NACK after final byte to terminate read
   * Accumulate received bytes into 32-bit DWORD

3. *PushRxData*: Write accumulated DWORD (4 bytes) to RX Data FIFO. Controller
waits if RX FIFO full. Software must drain RX FIFO in response to RX_THLD_STAT
interrupt, which fires when available data ≥ RX_BUF_THLD bytes.

4. Loop I3CDataRead ↔ PushRxData until data_length bytes received from
command descriptor

5. *WriteResp*: Generate response descriptor with transfer status and push to
Response Queue

6. Trigger INTR_STATUS.RESP_READY interrupt

7. Return to IDLE

*Error Handling*:
* NACK on TargetAddr → Abort with ERROR_NACK
* RX FIFO Full during PushRxData → Abort with ERROR_OVERFLOW

*Consumer-Producer Pattern*: Target (producer) transmits data, controller
accumulates and pushes to RX FIFO, software (consumer) drains FIFO triggered
by threshold interrupts.

====== In-Band Interrupt (IBI) Flow

I3C In-Band Interrupts enable targets to asynchronously notify the controller
without requiring a separate interrupt pin. The OCA implementation supports
two IBI entry mechanisms:

....
    Entry 1: From IDLE      Entry 2: From BroadcastAddr
    (Timer Expiry)          (During Transaction - OCA Enhancement)
           |                            |
           +----------+-----------------+
                      |
                      v
              +----------------+
              | ReadTargetAddr |
              | Identify IBI   |
              | Source         |
              +----------------+
                      |
                      +--> Address Invalid --> WriteResp --> Resume/IDLE
                      |    or IBI Disabled     (Error)
                      v Address OK
              +----------------+
              |  I3CDataRead   |<-------+
              | Recv IBI Data  |        |
              +----------------+        |
                      |                 |
                      v                 |
              +----------------+        |
              |  PushRxData    |        |
              | Write IBI FIFO |        |
              +----------------+        |
                      |                 |
                      +--> Full --> WriteResp --> Resume/IDLE
                      |             (Error)
                      |                 |
                      +-- More Data ----+
                      |   (<255 bytes)
                      v Data Complete
              +----------------+
              |   WriteResp    |
              | IBI Status Desc|
              +----------------+
                      |
                      v
         +------------+------------+
         |                         |
    Transaction              Return to
    Interrupted?                IDLE
         |
    Resume at
    saved state
....

*IBI Entry Mechanism 1: Bus Available Timer (Standard)*

1. Bus goes idle (no controller activity)
2. Target's bus available timer (configured via CSR) begins counting
3. Timer expires and target checks if bus still idle
4. Target initiates IBI by driving SDA low (START condition)
5. Controller detects START on idle bus → IBI detected

*IBI Entry Mechanism 2: Interrupt During Transaction (OCA Enhancement)*

This mechanism is unique to the OCA implementation and significantly reduces
IBI response latency:

1. Controller transmits broadcast address (0x7E) in Open-Drain mode at start
of transaction
2. Target with pending IBI drives its own address onto SDA simultaneously
during broadcast transmission
3. Controller detects address mismatch on SDA (wired-OR conflict) → IBI detected
4. Controller aborts current transaction, saves state, and immediately services
IBI
5. After IBI completion, controller resumes interrupted transaction from saved
state

*Benefit*: OCA's implementation allows targets to interrupt ongoing
transactions rather than waiting for bus
idle, reducing IBI response latency by up to milliseconds in active systems.

*IBI Processing Flow*:

1. *ReadTargetAddr*: Read 7-bit IBI source address from SDA
   * Verify address exists in DAT (valid target)
   * Check DAT.IBI_REJECT flag (IBIs from this device are NACKed when set)

2. *Decision - Accept or Reject IBI*:
   * *Accept (ACK)*: DAT.IBI_REJECT=0 AND DAT.IBI_PAYLOAD=1 AND IBI Queue not full
   * *Reject (NACK)*: DAT.IBI_REJECT=1 OR DAT.IBI_PAYLOAD=0 OR IBI Queue full

3. *I3CDataRead* (if accepted): Receive optional IBI payload
   * DAT.IBI_PAYLOAD indicates the device sends a mandatory data byte
     (e.g., sensor threshold value)
   * Maximum 255 bytes per I3C spec

4. *PushRxData*: Write IBI data to IBI FIFO in 4-byte chunks

5. *WriteResp*: Create IBI status descriptor containing:
   * IBI source address (7-bit)
   * Payload length (0-255 bytes)
   * Timestamp
   * Push to IBI_PORT (0x8C)

6. Trigger INTR_STATUS.IBI_STATUS_THLD interrupt when IBI entries ≥ threshold

7. *Resume or Return*:
   * If IBI interrupted transaction (Mechanism 2): Resume at saved state
   * Otherwise: Return to IDLE

8. Software reads IBI descriptor from IBI_PORT and determines appropriate
response (query target, send CCC, etc.)

====== Common Command Codes (CCC) Flow

Common Command Codes enable the controller to configure targets, query device
information, and manage bus topology. CCCs are classified as broadcast
(affecting all targets) or direct (targeting specific device).

....
    From BroadcastAddr
           |
           v
    +----------------+
    | CCC_SendCCCCode|
    | Send CCC byte  |
    +----------------+
           |
           v
    [Has Defining Byte?]
           |
    +------+------+
    |             |
  Yes            No
    |             |
    v             v
 +-------+    [Continue]
 | DefByte|       |
 +-------+       |
    |             |
    +------+------+
           |
           v
    [CCC Type Decision]
           |
    +------+------+------+------+
    |      |      |      |      |
 Bcast  Bcast  Direct Direct  Addr
 Write  Write  Write   Read  Assign
 (NoDef)(Def)                (SETDASA)
    |      |      |      |      |
    |      v      v      v      v
    |   Fetch  Target Target  Special
    |   TxData  Addr   Addr   Sequence
    |      |      |      |      |
    |      v      v      v      |
    |   I3C    I3C    I3C      |
    |   Write  Write  Read     |
    |      |      |      |      |
    +------+------+------+------+
           |
           v
      WriteResp
           |
           v
        IDLE
....

*Broadcast CCC (e.g., ENEC, DISEC)*:

1. *CCC_SendCCCCode*: Transmit CCC command byte (e.g., 0x00 for ENEC - Enable
Events Command) + T-bit

2. *CCC_DefiningByte* (optional, rare): Transmit defining byte for CCCs requiring
sub-command selection (e.g., ENEC with specific event enables). Most CCCs
skip this step.

3. *WriteResp*: No target response expected for broadcast CCCs. All targets
process command in parallel via their ccc.sv module. Generate success response.

4. Return to IDLE

*Direct Write CCC (e.g., SETMWL, SETMRL)*:

1. *CCC_SendCCCCode*: Transmit CCC command byte

2. *TargetAddr*: Transmit target device address + Sr

3. *FetchTxData*: Retrieve CCC-specific data from TX FIFO
   * SETMWL: 2 bytes (max write length in bytes)
   * SETMRL: 2 bytes (max read length in bytes)
   * Data prepared by software and written to TX_DATA_PORT

4. *I3CDataWrite*: Transmit CCC data bytes to target

5. *WriteResp*: Generate response descriptor

6. Return to IDLE

*Direct Read CCC (e.g., GETPID, GETMWL, GETSTATUS)*:

1. *CCC_SendCCCCode*: Transmit CCC command byte with read bit set (e.g., 0x8D
for GETPID)

2. *TargetAddr*: Transmit target address + Sr + Read bit

3. *I3CDataRead*: Receive CCC response data from target
   * GETPID: 6 bytes (48-bit Provisioned ID)
   * GETMWL: 2 bytes (max write length)
   * GETSTATUS: 2 bytes (device status flags)

4. *PushRxData*: Write response data to RX FIFO

5. *WriteResp*: Generate response descriptor with data length

6. Software reads CCC response from RX_DATA_PORT

7. Return to IDLE

*Address Assignment CCC (SETDASA)*:

1. *CCC_SendCCCCode*: Transmit SETDASA command (0x87) or SETNEWDA (0x88)

2. *I3CAddressAssignment*: Special two-address sequence:
   * Transmit Repeated START (Sr)
   * Transmit static address (7-bit, from device datasheet) + T-bit
   * Transmit dynamic address to assign (7-bit, chosen by controller) + T-bit
   * Transmit STOP

3. Target with matching static address accepts assigned dynamic address and
stores internally

4. *WriteResp*: Confirm address assignment success

5. Controller updates DAT memory with new dynamic address mapping

6. Return to IDLE

*CCC Data Sourcing*: CCC-specific data originates from two sources:
* Internal HCI settings: Hardware-provided values (e.g., max write length
from HC_CAPABILITIES register)
* TX FIFO: Software-provided values (e.g., custom configuration data)

*Defining Byte Usage*: Rarely used - only for CCCs requiring sub-command
selection (e.g., ENEC/DISEC with event type mask). Most CCCs proceed directly
to target addressing or broadcast without defining byte.

====== Target Mode Operation

When TARGET_SUPPORT=1, the I3C controller can operate as a target device
responding to controller commands. Target functionality includes:

*i3c_target_fsm.sv*: Target mode state machine monitoring bus for address
matches, processing received commands, and generating responses.

*CCC Processing*: The ccc.sv module (44 KB) implements comprehensive CCC
command processing including:
* SETDASA/SETNEWDA: Accept dynamic address assignment
* GETPID/GETBCR/GETDCR: Respond with device identification
* SETMWL/SETMRL: Configure max transfer lengths
* ENEC/DISEC: Enable/disable event generation (IBI, hot-join)

*Target Transaction Interface (TTI)*: When enabled via I3C_EC.TTI registers,
provides descriptor-based RX/TX queues for target mode data transfers, mirroring
controller mode queue architecture.

*IBI Generation*: Target can initiate IBI when enabled via ENEC CCC, subject
to bus available timer or immediate transmission capability during controller
broadcast.

====== Device Address Table (DAT) and Device Characteristic Table (DCT)

*DAT (Device Address Table)*: 64-bit entries mapping device indexes to dynamic
addresses. Each entry contains:
* DYNAMIC_ADDRESS[23:16]: dynamic address; only the low 7 bits are driven onto
the bus, hardware appends RnW and computes the ENTDAA parity bit
* STATIC_ADDRESS[6:0]: static address (for SETDASA correlation)
* IBI_REJECT[13]: NACK IBIs from this device (active high - clear to accept)
* IBI_PAYLOAD[12]: device sends a mandatory data byte with its IBI
* CRR_REJECT[14], TS[15], RING_ID[28:26], DEV_NACK_RETRY_CNT[30:29], DEVICE[31]
* AUTOCMD_MASK/VALUE/MODE/HDR_CODE[58:32]: auto-command configuration

Software populates DAT during device enumeration. Hardware reads DAT during
command processing to translate dev_idx to target address.

*DCT (Device Characteristic Table)*: 128-bit entries with device-specific
characteristics:
* PID_HI[31:0] / PID_LO[47:32]: 48-bit Provisioned ID
* DCR[71:64]: Device Characteristics Register - device type classification
* BCR[79:72]: Bus Characteristics Register - device role, limitations
* DYNAMIC_ADDRESS[103:96]: address assigned during ENTDAA

Hardware populates DCT during ENTDAA from the PID/BCR/DCR each target emits.

*Depth*: both tables expose a 128-entry address window, and DAT_SECTION_OFFSET /
DCT_SECTION_OFFSET advertise TABLE_SIZE=127, but the physical memories are
`DAT_DEPTH`/`DCT_DEPTH` = 16 entries deep (i3c_defines.svh). Only indexes 0-15
are backed by storage.

====== PHY Layer and Clock Domain Crossing

*i3c_phy.sv*: Provides dual flip-flop CDC synchronization for SCL/SDA inputs
crossing from I3C bus clock domain to controller system clock domain. Implements
sel_od_pp control for Open-Drain vs Push-Pull pad mode selection.

*Timing Flexibility*: All bus timing parameters (t_r, t_f, thigh, tlow, tsu_*,
thd_*, t_buf) are software-programmable via CSR registers, enabling operation
across arbitrary system clock frequencies. Controller FSM generates precise
SCL/SDA edges by counting system clock cycles derived from configured timing
values.

====== Transfer Command Response Interface (TCRI)

The MIPI TCRI v1.0 recovery subsystem enables secure firmware download
and device recovery:

*recovery_handler.sv*: Coordinates recovery flow state machine
*recovery_executor.sv*: Executes recovery commands
*recovery_transmitter.sv / recovery_receiver.sv*: Handle recovery data transfers
*recovery_pec.sv*: Packet Error Code calculation for data integrity

Recovery interface signals (recovery_payload_available_o, recovery_image_activated_o,
peripheral_reset_o, escalate_reset_o) connect to system-level reset and
firmware management infrastructure.

====== Error Handling

The controller detects and reports multiple error conditions via response
descriptors and interrupt flags:

* *Protocol Errors*: NACK on address, CRC failure (HDR modes), frame errors
* *FIFO Errors*: TX underflow, RX overflow, IBI queue overflow
* *Timeout Errors*: Bus timeout, clock stretching timeout
* *Abort Conditions*: Software abort via HC_CONTROL.ABORT, bus arbitration loss

Error codes in response descriptors enable software to implement retry logic,
device blacklisting, or system-level error escalation.

====== Interrupt System

The controller generates interrupts from multiple sources:

* *Queue Thresholds*: CMD_QUEUE_READY, RESP_READY, TX_THLD_STAT, RX_THLD_STAT,
IBI_STATUS_THLD
* *Transfer Events*: TRANSFER_COMPLETE, TRANSFER_ABORT, TRANSFER_ERROR
* *IBI Events*: IBI_UPDATED, IBI_THLD_STAT

Software configures interrupt enables via INTR_STATUS_ENABLE (mask) and
INTR_SIGNAL_ENABLE (routing to interrupt output pin). Reading INTR_STATUS
provides current interrupt state; writing 1 to status bits clears interrupts.

Threshold-based interrupts implement producer-consumer flow control, triggering
software action only when queue fill/empty levels cross configured thresholds,
minimizing interrupt overhead compared to per-byte polling.
