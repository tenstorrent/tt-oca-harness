[[interfaces]]
== Communication interfaces

The ROM enables the same target-interface set for every strap role:

* I3C controllers 0, 1, and 3; and
* I2C controllers 0 and 1.

I3C2 remains disabled in the software interface map.
The `BOOT_I2C`, `BOOT_RECOVERY`, and `PRIMARY_CHIPLET` straps are observable state but do not change this map.

[[interface-addressing]]
=== Address selection

I3C controllers 0, 1, and 3 use eFuse identifier slots 0, 1, and 3.
The eFuse driver reads and caches each slot as a 64-bit value and passes the
whole value to the I3C driver.
The open HCI driver uses bits 6:0 as the static address.
I2C controllers 0 and 1 take the low seven bits of slots 6 and 7.
An I2C value outside `0x08` through `0x77` is replaced with `0x55`.

A non-zero eFuse slot takes precedence over the fallback below.
If a selected eFuse slot is zero, the ROM forms a fallback address from two values:

* `CHIP_CONFIG.CHIPLET_TYPE`, the kind of chiplet the SMU is built as, its `CFG.SMC_CHIPLET_TYPE`: 0 memory, 1 CPU, 2 AI compute, 3 Ethernet, other values reserved; and
* the four `ADDR_SEL` straps, which select the address of one die among identical dies, as the A0-An pins of an I2C device do.

The seven-bit fallback address is `{CHIPLET_TYPE[1:0], 1'b0, ADDR_SEL[3:0]}`.
The same fallback function is used for I2C and I3C slots.
Each chiplet on a shared I2C or I3C bus that relies on the fallback needs a distinct `{CHIPLET_TYPE, ADDR_SEL}` pair.

Chiplet type 0 with `ADDR_SEL` 0 through 7 gives addresses `0x00` through `0x07`.
I2C reserves those addresses, MIPI I3C Basic v1.1.1 restricts `0x03` through `0x07`, and I3C itself uses `0x00` through `0x02`.
An I2C channel given one of them takes `0x55` instead, as above.
A memory chiplet whose I2C or I3C address relies on the fallback uses `ADDR_SEL` 8 through 15, or programs its eFuse identifier slots.

I3C channels are started in subordinate mode.
I2C channels are initialized in target mode.

=== Driver selection

The default I3C target symbols are weak.
Their initialization functions succeed so the ROM remains linkable without an active I3C implementation, while their data methods report a hardware error and their receive-availability method reports no data.
An adopter ROM FW build can replace those symbols with a strong driver.

Setting `I3C_CORE=chipsalliance` at build time enables the open MIPI HCI/I3CCSR implementation in `i3c_hci_driver.c`.
That implementation configures the target transaction interface, static address, dynamic-address-assignment acceptance, queue thresholds, and open-drain timing.

The HCI path reaches the pads through the LSIO selection and therefore leaves the GPIO hardware-function override clear.
Every non-HCI build enables the GPIO hardware-function override for the I3C
pad set before driver initialization, whether it uses the weak default or a
strong platform driver.
The ROM does not program GPIO drive strength from eFuses.

=== I3C response flow control

The HCI target implementation advertises a response only after response data is available.
For responses that fit in the transmit queue, it writes all data and then writes the transmit descriptor.
For larger responses, it fills the queue, writes the descriptor when the queue first becomes full, and continues filling as hardware drains data.
The target hardware does not accept a private read until its response-start threshold is met.

[[i3c-flow-control]]
.HCI target response flow
[plantuml]
....
@startuml
participant Controller
participant "I3C target hardware" as HW
participant "SMC ROM" as ROM

Controller -> HW: Private write containing OCCP request
HW -> ROM: RX descriptor and data
ROM -> ROM: Validate and execute request
Controller -> HW: Private read before response is armed
HW --> Controller: Read not accepted
ROM -> HW: Queue response data
ROM -> HW: Write TX descriptor with response length
Controller -> HW: Retry private read
HW --> Controller: OCCP response data
@enduml
....

The HCI receive implementation separately tracks each inbound frame's descriptor length and unconsumed bytes.
That accounting persists across the OCCP layer's header and body reads and supports exact incomplete/oversized-frame reporting.
See <<occp-protocol>> for the packet binding and controller-visible errors.

=== GPIO side effects

During OCCP initialization, the ROM enables the hardware-function override for CAT_THERM on GPIO 52.
After transport initialization, GPIO 58 is configured as an output and driven high when all requested channel initializations succeeded or low when any failed.
No status-sequence protocol is implemented on that GPIO.
