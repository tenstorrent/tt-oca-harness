== SMC Boot ROM Firmware Verification Plan

=== Overview

[cols=",",options="header"]
|===
|Field |Value
|Design Under Test |The production SMC Boot ROM (BL0), `hw/sys/smc/bootrom/prod`, executing on the target instance of the dual-SMC model
|Platform |The `dual` RTL target in `smc_sim_cfg.toml`: two SMC instances on a shared I3C bus. The target runs the production ROM and the controller runs DV firmware
|Repository |`tt-oca-harness`
|Project |OCAH
|Framework |cocotb, with the OCCP checks in the controller firmware
|Primary simulator |Verilator
|Design specification |The SMC Boot ROM chapters that `hw/sys/smc/bootrom/prod/doc/index.adoc` includes, and `hw/sys/smc/doc/rom.adoc` for the ROM region and reset vector
|Error and status codes |`hw/sys/smc/bootrom/prod/include/smc_occp_error_codes.h` and the ring-buffer status values in `status-coordination.adoc`
|Register sources |`hw/sys/smc/regs/` (SystemRDL) and the generated export `hw/sys/smc/regs/gen/`
|Testbench architecture |<<smc-dv-testbench-architecture,SMC_TB_ARCH>>
|How to run |`README.md` in this DV tree (`tools/dv/run_dv.py --dut smc --items occp_rom`)
|Tests |Every entry of `testlists/smc_rom.toml`: 36 tests
|===

This plan is the technical contract for the SMC Boot ROM firmware tests. It
states what each test drives, what it observes, which checkers can fail it, and
which sections of the ROM specification it claims. <<smc-vplan>> grades only
its `all` group, which holds none of these tests.

The DUT is firmware. The RTL is the platform that executes it. A test proves a
ROM behaviour only through state that the ROM makes visible: the OCCP responses
on the bus, the scratch registers, the POST word, the status ring buffers and
the target memory.

=== Verification Strategy

[[smc-rom-vplan-stimulus]]
==== Stimulus

The ROM image is the production build. A test changes the inputs of the ROM,
never the ROM itself.

* *ROM image.* Every build stage of these tests builds `hw/sys/smc/bootrom/prod` with `I3C_CORE=chipsalliance` and `ENABLE_RELEASE_PRINTS=1` (virtual console only) into `prod_rom.bin64`, and `+rom_bin64` loads it into both instances.
* *Controller.* `+bfm_rom_hex` replaces the controller ROM with a DV image from `hw/sys/smc/dv/fw/tests/<name>/`, linked with the OCCP controller library in `hw/sys/smc/dv/fw/common/occp/`. The image sends the OCCP sequence of the test.
* *Straps and lifecycle.* `smc_dual_base_test` forces the per-instance straps before strap capture. `+BOOT_I3C` selects I3C, `+FORCE_STATUS_REPORTING` clears `STATUS_RPT_DISABLE`, and `+lc_state` sets the target lifecycle.
* *eFuse.* The harness regenerates the eFuse image for the run seed before cold reset. `+fuse_transport_timeout` pins the OCCP transport timeout, and `+fuse_i2c_ids` programs I2C ID slots 6 and 7 with two distinct seeded addresses.
* *DFT status.* `+dft_scenario` drives the target memory-repair and MBIST status lines to a failure pattern. Without it, the lines are tied to passing.
* *Payload.* `+occp_payload_bin` and `+occp_payload_sym` supply the image that the hand-off tests transfer or stage.
* *SEP ring buffer.* The dual bench has no SEP. `env/smc_sep_ring_buffer_driver.py` takes its place and writes SEP status entries into the target SEP ring buffer over the target AXI port, plus a mirror copy in controller SRAM that the firmware compares against. `+sep_rb_entries` sets the entry count (drawn 1..512 from the seed when absent), and `+sep_rb_case` only labels the case.

[[smc-rom-vplan-checking]]
==== Checking

* *Controller firmware.* The rom-only tests check each OCCP response in the controller firmware: header, error code, CRC and body. The firmware reports the result through `TEST_PASS` or `TEST_FAIL` in scratch 0.
* *Driver verdict.* `smc_occp_rom_only_test` polls scratch 0 of both instances. `TEST_FAIL` in either instance, or the end of the poll budget, fails the test.
* *POST word.* Target scratch 1 carries the boot phase and error fields. The lifecycle and hand-off tests judge it.
* *Scratch contract.* Scratch 8, 9 and 15 carry the manifest address, the ready flags and the DFT result.
* *Evidence.* `dual_test` fails a test that does not log every `CHK-<ID>` in its `REQUIRED_EVIDENCE`. Each procedure group names those IDs.
* *Halt.* A terminal test samples the target hart 0 retired PC and requires a span of a few PCs for a fixed window.
* *Memory.* The hand-off tests read the target SRAM over AXI or through the backdoor peek and compare it with the payload.

[[smc-rom-vplan-bringup]]
==== Bring-up

. Regenerate the eFuse image for the run seed.
. Force the straps, the lifecycle and the DFT status lines of both instances before strap capture.
. Release cold reset and wait for strap capture on both instances.
. Hold `boot_stall`, program the reset vectors over AXI, write the firmware seed to scratch 3 (and the controller I2C target IDs to scratch 4), then release the target and the controller at the ROM base.
. Poll the verdict words up to the budget of the test, and judge the observables.

[[smc-rom-vplan-expansion]]
==== Scenario Expansion

Each rom-only test is one controller image. The image draws its command mix,
addresses and transfer sizes from the run seed, which the harness writes into
scratch 3. Every test runs on `seed = 1`, so a randomized test covers one draw
per regression.

=== BFM Policy

[cols="1,1,2",options="header"]
|===
|Interface / Protocol |VIP / Model |Purpose
|OCCP over I2C and I3C |Controller instance with DV firmware |Sends OCCP requests to the target ROM and checks every response

|eFuse |Seeded eFuse image generator |Supplies the sensed configuration for each run
|SEP ring buffer |`env/smc_sep_ring_buffer_driver.py` |Writes SEP entries into the target buffer
|DFT status |`env/smc_dft_status_driver.py` |Drives the memory-repair and MBIST status lines
|Virtual console |`env/smc_virt_console.py` |Decodes the firmware trace on scratch 2 of both instances
|===

A model generates stimulus or observes passively. A test judges the ROM through
a checker that can fail. Activity on an interface is not proof.

[[smc-rom-vplan-credit-rules]]
==== Credit rules

* Section credit needs a test that maps to the section, a passing `results.xml`,
  and the verdict that the test's procedure group names. This plan records no
  run. Each matrix row is a planned vehicle until a run supplies that evidence.
* A refusal test expects the error code that its member row names.
* A test that forces a signal or stages memory through a backdoor declares it in
  its member row. The forced value is stimulus, never a ROM-generated result.
* This plan maps each test to specification sections from the behaviour that
  the test judges.

[[smc-rom-vplan-known-limitations]]
=== Known Limitations

[cols="2,3",options="header"]
|===
|Limitation |Impact
|No CI tier runs `occp_rom` or `sanity` |Boot ROM evidence comes only from a local run with the firmware toolchain
|The rom-only verdict accepts `TEST_PASS` from either instance |The checks of those tests live in the controller firmware. The driver judges only scratch 0, so the strength of each test is the strength of its controller image
|Status-ring checks depend on the `STATUS_RPT_DISABLE` strap |The strap is drawn from the seed unless `+FORCE_STATUS_REPORTING` is set. The controller firmware runs its status-ring checks when status reporting is on
|DFT status is forced |`+dft_scenario` drives the target memory-repair and MBIST status lines. The tests judge the ROM reaction to those lines
|Specification and ROM disagree on the DFT continue control |`hardware-initialization.adoc` names eFuse `RESERVED_2[0]` as the control that lets boot continue after a memory-repair or MBIST failure. The ROM reads `SMC_CONFIG` bit 15 (`boot/memory_repair_check_override.S`). The ROM owner decides which one is correct
|===
