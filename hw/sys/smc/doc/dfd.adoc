= Design-for-Debug (DFD) and Core Logic Analyzer (CLA)
:description: SMC debug observation, event triggering, actions, and trace capture.

[[smc-dfd-cla]]

The SMC integrates a Design-for-Debug (DFD) subsystem that observes
internal activity, triggers on programmable conditions, and captures
trace, all on-chip and without external instrumentation. Its core is a
Core Logic Analyzer (CLA) that watches a configurable debug bus,
evaluates programmable events, and fires actions — an interrupt, a clock
stop, a cross-trigger, or a trace capture — when those events occur.
Trace storage uses the connected external sink-memory interface. Several
capabilities of the generic DFD block are not connected in SMC, as detailed below.

[[smc-dfd-diagram]]
.SMC DFD block diagram
image::smc-dfd.svg[alt="SMC DFD block diagram: the debug-bus mux tree, clock gate and time-tick generator in smc_dfd_wrap, and the CLA, debug signal trace, trace network and registers of the DFD IP, with the parts SMC does not build or connect drawn dashed",width=100%,pdfwidth=100%]

<<smc-dfd-diagram>> shows the DFD block as SMC instantiates it. `smc_dfd_wrap`
contains the DFD IP `dfd_top_cla_dst_apb` (`u_dfd_top`), configured with one
CLA and one debug signal trace (DST) instance. Parts of the generic block
that SMC does not build are drawn as dashed grey boxes. Inputs and outputs
that SMC ties off or leaves unconnected are drawn as dashed lines. The
instruction trace (N-Trace) is not built. The trace AXI master and the JTAG
register port are tied off, and the timestamp inputs are tied to zero.
The CLA and DST paths provide the observation functions described here.

The debug bus from `smc_base` has 64 lanes of 16 bits. Eight level-3 and
four level-2 debug-bus muxes reduce it to the 16 lanes that enter the CLA,
under the select register in the DFX CSRs. The CLA's own mux stage then
selects the 64-bit debug bus that the CLA evaluates and passes to the DST.
The wrapper gates `clk_smc_i` for the muxes and the IP under `dfd_cg_en`,
and it counts `clk_ref_i` edges into the CLA time tick. The trace sink
writes eight external trace RAMs of 256 × 64 bits, 16 KiB in total.

Software programs the mux tree one mux at a time through the single
`DEBUG_BUS_MUX` register. The level-3 muxes have IDs 7 to 14 and each takes
eight consecutive debug-bus lanes; the level-2 muxes have IDs 3 to 6 and each
drives four consecutive CLA input lanes. A mux takes `Dbmmode` while `Dbmid`
equals its ID, and its lane selects while `Dbmid` equals its ID and its mode
is 1. Each lane select is a binary index: 0 passes input lane _n_ to output
lane _n_, and 1 to 4 select input lanes 4 to 7. The CLA's own stage,
programmed through `CDbgMuxSelLo` with `DbmId` 0, decodes its selects the
same way, so 1 to 12 select CLA input lanes 4 to 15. The
ifdef::backend-html5[]
xref:ocah-programmer-guide::index.adoc#smc-dfd-capture[capture set-up sequence]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-programmer-guide/latest/index.html#smc-dfd-capture[capture set-up sequence]
endif::backend-pdf[]
is in the Programmer's Guide.

Bit 0 of `xtrig_clk_halt_mask` in the DFX CSRs masks the CLA cross-trigger
and halt-clock outputs, with every cross-trigger lane masked together; bits
15:1 have no effect. The clocks-stopped output also requires
`tdr_dbg_ctrl_clock_stop_en_i`; it drives a DTP clock-stop request, and its
rising edge pulses a CPU interrupt. A halt-clock action sets a request that
is held until the SMC primary reset: `CDbgEapStatus`, `EnableEap`,
`EnableCla` and `DisableGlobalClockHalt` do not release it, and the mask and
`tdr_dbg_ctrl_clock_stop_en_i` gate the output without clearing it. The debug interrupt drives a CPU
interrupt. The sixteen custom actions leave the SMC, and the SMU wires five of them to the SEP CPU
debug controls. The CLA debug marker returns to the SMC debug bus. The
`debug_marker`, `chiplet_enable`, `gpio_en`, `dtb_ns_en` and `dtb_ew_en`
fields of `DEBUG_CTRL` have no effect in SMC.

Key features include:

* A programmable debug bus that routes internal signals of interest to
  the analyzer under software control
* An event engine supporting signal-match, edge, transition, ones-count,
  any-change, and counter events
* Event-action pairing that binds detected events to system actions
* Per-trigger snapshot of the debug bus and status flags identifying
  which pair fired
* Cross-trigger exchange with the rest of the debug infrastructure
* Trace capture through the external sink-memory interface

== Debug Bus

The analyzer operates on a debug bus: a fixed-width vector of internal
signals sampled every cycle. A selection fabric chooses which internal
signals are driven onto the bus, so a single analyzer can be pointed at
different parts of the design without RTL changes. Software selects the
observed signal set, then programs the event engine against the resulting
bus value.

=== External and SEP Lanes

Lanes 32 to 63 carry the 512-bit `ext_debug_bus_i`: lane 32+__k__ is bits
[16__k__+15:16__k__]. A three-stage synchronizer to `clk_smc_i` delays them three
cycles behind lanes 0 to 31, and it synchronizes each bit on its own, so a
multi-bit value from another clock domain can be sampled while it changes.

_k_ on lane 32+__k__ (<<smc-debug-bus-sep-lanes-table>>), and lanes 56 to 63

=== Mux Programming

From reset every debug-bus mux is in mode 0 with its lane selects at 0 and
drives 0, so the CLA sees 0 on every input lane until each mux on the path is
in mode 1. A mux updates its mode only while `DEBUG_BUS_MUX.Dbmid` equals its
ID, and its lane selects only while `Dbmid` equals its ID and its mode is 1. A
`DEBUG_BUS_MUX` write addressed to another mux, or with a `Dbmid` that no mux
has (0 to 2, or 15 to 63), leaves every other mux's mode and selects as they
were, so the muxes can be programmed in any order.

The level-3 mux with ID 7+__m__ takes lanes 8__m__ to 8__m__+7. The level-2 mux
with ID 3+__m__ takes the outputs of the level-3 muxes with IDs 7+2__m__ and
8+2__m__ and drives CLA input lanes 4__m__ to 4__m__+3. In mode 2 a mux drives its
ID on its first output lane and 0 on the others, and in mode 3 its outputs
alternate every cycle between that pattern and its bitwise inverse; both
modes check the path from a mux to the CLA without a live signal.

== Core Logic Analyzer

The CLA is organized as a set of nodes, each holding several event-action
pairs (EAPs). An EAP binds one or more events, computed from the debug
bus, to one or more actions taken when those events occur. The event
engine evaluates several event types in parallel (<<smc-cla-event-types-table>>).

[[smc-cla-event-types-table]]
[cols="30%,70%",options="header",]
.SMC CLA event types
|=======================================================================
|Event |Description
|Signal match |Fires when the masked debug bus equals a programmed value
(`debug_bus & mask == match`). Several independent match events are
available.
|Edge |Fires on a rising or falling edge of selected debug-bus signals.
|Transition |Fires when a masked subset of the bus moves from a
programmed value A to a programmed value B.
|Ones count |Fires when the population count of a masked subset equals a
programmed value.
|Any change |Fires when any signal within a masked subset changes.
|Time match |Unavailable in this integration. Its timestamp input is tied to
zero. The comparator requires a nonzero match value, so the event cannot fire;
it does not use the local CLA timestamp register.
|Counter |Counts cycles following an event match and fires when the
count is reached; a small pool of counters is available for measuring
intervals or deferring an action.
|=======================================================================

When an EAP fires, a status flag records which pair triggered — for
example, so an interrupt handler can identify the source — and a snapshot
register latches the debug-bus value at the moment of the trigger for
post-mortem inspection. EAPs are enabled together once programming is
complete, so a partially programmed pairing never triggers.

== Actions and Cross-Triggering

An EAP can drive one or more actions:

* *Debug interrupt* — raise the CLA interrupt, a level PLIC source held
  until software releases it: clear `EnableEap`, then write the EAP's
  `CDbgEapStatus` W2C bit. A W2C write while `EnableEap` is set clears the
  status bit but not the interrupt (see Interrupts below).
* *Clock stop* — halt clocks to freeze the design for inspection.
* *GPIO toggle* — the generic block provides this action, but SMC terminates
  it on an unused local signal; it does not drive a pad.
* *Cross-trigger out* — signal other debug blocks that a local event
  occurred.
* *Trace capture* — hand the event to the trace subsystem.
* *Custom actions* — reserved outputs for design-specific use.

Cross-trigger inputs let events elsewhere in the system arm or fire local
actions, and cross-trigger outputs propagate local events outward, so
debug conditions can be correlated across blocks rather than observed in
isolation.

=== Action Codes

Each EAP has four 6-bit action fields, `Action0` to `Action3`, and the codes
of <<smc-cla-action-codes-table>>. The actions of every EAP of the current node
are combined and registered, so an action starts one cycle after its EAP
relation holds and, unless the table says otherwise, lasts while the relation
holds, the node stays current and `EnableEap` is set.

== Trace

The configured trace sink uses external memory request/response ports. The
optional trace AXI master has unconnected request outputs and tied-low response
inputs, so it cannot stream trace over the SMC fabric.

SMC selects local CLA timestamp scheme 0, advanced by the wrapper's reference
clock-derived `time_tick`. This local counter is distinct from the generic
`i_timestamp`, reference timestamp, and OCTS timestamp inputs, all tied to zero.
The integration does not provide the advertised global timestamp alignment
through those inputs. In particular, the time-match event consumes the tied-off
timestamp rather than the running CLA timestamp register.

Because of timestamp scheme 0 and the 64-bit CLA debug bus, several CLA
registers have no effect in SMC. `TsCapture`, `CDbgTimestampCapture` and
`CDbgClaTimestampOffset` serve only the reference-timestamp scheme. The Hi
halves of the match, compare, transition, ones-count, change and snapshot
registers serve only a 128-bit debug bus. `CDbgMuxSelHi`, and `Muxselseg4`
to `Muxselseg7` of `CDbgMuxSelLo`, select lanes beyond the four that the CLA
mux drives.

[[smc-dst-trace-format]]
=== Trace RAM Format

The DST writes a stream of packets of 1 to 10 bytes into the sink RAM, packed
back to back in frames. Successive `trDstRamData` reads return successive
4-byte words of the stream, the earliest byte in bits [7:0]. Read the RAM after
clearing `trDstControl.Trdstenable`, which completes the last frame (see Frames
below).

Bit 7 of the first byte of a packet gives its type: 0 for a data packet, 1
for a support packet. Bits [6:3] of that byte are the source ID, the low four
bits of `trDstInstFeatures.Trdstsrcid`, which resets to 0. Bit 2, packet
lost, is 1 when an earlier packet did not reach the RAM when the DST offered
it: the RAM could not take it, a timestamp packet took the place of a data
packet in the same cycle, or a trace stop discarded the last sample (see
Frames below).

[[smc-dst-data-packet-table]]
[cols="20%,80%",options="header"]
.DST data packet
|=======================================================================
|Byte, bits |Field
|0, [0] |Trace start: the first packet of a trace
|0, [1] |Trace stop: the last packet of a trace
|0, [2] |Packet lost
|0, [6:3] |Source ID
|0, [7] |0
|1 |Byte enables: bit _i_ is 1 when the packet carries byte _i_ of the
64-bit CLA debug bus, bits [8__i__+7:8__i__]
|2 onward |The enabled debug-bus bytes, lowest byte first, as sampled
|=======================================================================

A data packet is two bytes plus one per enabled byte.
`trDstControl.Trdstformat` selects which bytes it carries:

* 0: every byte of every sampled cycle.
* 1: every byte, in a cycle in which any bit of the bus changed.
* 3, the reset value: only the bytes that changed.
* 2 and 4 to 7: only the packets that carry every byte regardless of format.

A data packet carries every byte, whatever the format, when it carries the
start or stop flag. It also carries every byte when the data packet of the
previous cycle was lost, because the RAM could not take it or a timestamp
packet took its place, and, with `Trdstsyncmode` at 1, when the data packet of
the previous cycle was the first after a stream-count boundary. A timestamp
packet in a cycle without a data packet does not force every byte. Nothing
records how many cycles pass between data packets; only timestamp packets give
elapsed time.

[[smc-dst-support-packet-table]]
[cols="20%,80%",options="header"]
.DST support packet
|=======================================================================
|Byte, bits |Field
|0, [0] |Null: the packet is this one byte
|0, [1] |Extended: byte 1 follows
|0, [2] |Packet lost
|0, [6:3] |Source ID
|0, [7] |1
|1, [0] |Trace start
|1, [1] |Trace stop
|1, [7:4] |Form: 0 timestamp, 1 trace information
|2 to 9 |Timestamp form only: the 64-bit timestamp, lowest byte first
|=======================================================================

A timestamp packet is 10 bytes. A trace-information packet is 2 bytes and
carries a start or stop flag that could not travel in a data packet, such as
the stop flag when `Trdstenable` is cleared. The DST sends a timestamp packet
only while `Trdstsyncmode` is 2, once every 2^(`Trdstsyncmax`+4)^ DST clock
cycles of a running trace, and none at trace start. With
`trDstImpl.Trdsttimestampconfig` at 0, its reset value, the timestamp is the
external input, which SMC ties to 0; at 1 it is the CLA timestamp,
`CDbgClaTimestamp`, which counts `time_tick`.

==== Frames

A frame is 64 × `trDstImpl.Trdstvendorframelength` bytes, with the field at 1, 2,
4 or 8, and `trDstRamImpl.Trdstramvendorframelength` must hold the same value.
Frames fill the RAM in order from `trDstRamStartLow`, and `trDstRamWPLow`
advances by a whole frame. With `CDbgDebugTraceCfg.FrameModeEnable` at 1, its
reset value, every frame starts with a packet and no packet crosses into the
next frame. The bytes after a frame's last packet hold
`TraceFrameFillByte`. Its reset value, 0x81, reads as a null support packet with
source ID 0, so a decoder can skip fill as null packets; keep the fill byte at a
value with bit 7 and bit 0 at 1 and bit 1 at 0 to preserve that. With
`FrameModeEnable` at 0, packets can cross frame boundaries and the stream
cannot be aligned to frames, so keep frame mode on.

`FrameClosureMode` decides what happens to a packet that does not fit in the
rest of a frame. At 0 the frame is filled and the packet moves to the next
frame; if a newer sample is ready first, the packet is dropped and the next
packet has packet lost set. At 1 the DST closes each frame while it still has
room for one maximum-size packet of 10 bytes, so no packet has to move.

Clearing `trDstControl.Trdstenable` stops the trace and completes the frame.
The DST discards the last sample, the one that would carry the stop flag, and
sends null packets in its place. The stop flag follows in a trace-information
packet with packet lost set, then null packets and fill up to the end of the
frame. A trace stop from CLA action code 5 instead sends the last sample as a
data packet with every byte and the stop flag set, and leaves the frame open;
clearing `Trdstenable` afterwards adds only null packets and fill.

The CLA counter values and timestamp fields are software-writable. Software
writes take priority over simultaneous hardware updates; later hardware updates

read/write state, not read-only status.
