= Design-for-Debug (DFD) and Core Logic Analyzer (CLA)
:description: SMC debug observation, event triggering, actions, and trace capture.

[[smc-dfd-cla]]

The SMC integrates a Design-for-Debug (DFD) subsystem that observes
internal activity, triggers on programmable conditions, and captures
trace, all on-chip and without external instrumentation. Its core is a
Core Logic Analyzer (CLA) that watches a configurable debug bus,
evaluates programmable events, and fires actions — an interrupt, a clock
stop, a cross-trigger, or a trace capture — when those events occur.
Trace storage uses the connected external sink-memory interface. Several
capabilities of the generic DFD block are not connected in SMC, as detailed below.

<<smc-dfd-diagram>> shows the DFD block as SMC instantiates it. `smc_dfd_wrap`
contains the DFD IP `dfd_top_cla_dst_apb` (`u_dfd_top`), configured with one
CLA and one debug signal trace (DST) instance. Parts of the generic block
that SMC does not build are drawn as dashed grey boxes. Inputs and outputs
that SMC ties off or leaves unconnected are drawn as dashed lines. The
instruction trace (N-Trace) is not built. The trace AXI master and the JTAG
register port are tied off, and the timestamp inputs are tied to zero.
The CLA and DST paths provide the observation functions described here.

The debug bus from `smc_base` has 64 lanes of 16 bits. Eight level-3 and
four level-2 debug-bus muxes reduce it to the 16 lanes that enter the CLA,
under the select register in the DFX CSRs. The CLA's own mux stage then
selects the 64-bit debug bus that the CLA evaluates and passes to the DST.
The wrapper gates `clk_smc_i` for the muxes and the IP under `dfd_cg_en`,
and it counts `clk_ref_i` edges into the CLA time tick. The trace sink
writes eight external trace RAMs of 256 × 64 bits, 16 KiB in total.

Software programs the mux tree one mux at a time through the single
`DEBUG_BUS_MUX` register. The level-3 muxes have IDs 7 to 14 and each takes
eight consecutive debug-bus lanes; the level-2 muxes have IDs 3 to 6 and each
drives four consecutive CLA input lanes. A mux takes `Dbmmode` while `Dbmid`
equals its ID, and its lane selects while `Dbmid` equals its ID and its mode
is 1. Each lane select is a binary index: 0 passes input lane _n_ to output
lane _n_, and 1 to 4 select input lanes 4 to 7. The CLA's own stage,
programmed through `CDbgMuxSelLo` with `DbmId` 0, decodes its selects the
same way, so 1 to 12 select CLA input lanes 4 to 15. The

Bit 0 of `xtrig_clk_halt_mask` in the DFX CSRs masks the CLA cross-trigger
and halt-clock outputs, with every cross-trigger lane masked together; bits
15:1 have no effect. The clocks-stopped output also requires
`tdr_dbg_ctrl_clock_stop_en_i`, and it drives a CPU interrupt and a DTP
clock-stop request. The debug interrupt drives a CPU interrupt. The sixteen
custom actions leave the SMC, and the SMU wires five of them to the SEP CPU
debug controls. The CLA debug marker returns to the SMC debug bus. The
`debug_marker`, `chiplet_enable`, `gpio_en`, `dtb_ns_en` and `dtb_ew_en`
fields of `DEBUG_CTRL` have no effect in SMC.

Key features include:

* A programmable debug bus that routes internal signals of interest to
  the analyzer under software control
* An event engine supporting signal-match, edge, transition, ones-count,
  any-change, and counter events
* Event-action pairing that binds detected events to system actions
* Per-trigger snapshot of the debug bus and status flags identifying
  which pair fired
* Cross-trigger exchange with the rest of the debug infrastructure
* Trace capture through the external sink-memory interface

== Debug Bus

The analyzer operates on a debug bus: a fixed-width vector of internal
signals sampled every cycle. A selection fabric chooses which internal
signals are driven onto the bus, so a single analyzer can be pointed at
different parts of the design without RTL changes. Software selects the
observed signal set, then programs the event engine against the resulting
bus value.

== Core Logic Analyzer

The CLA is organized as a set of nodes, each holding several event-action
pairs (EAPs). An EAP binds one or more events, computed from the debug
bus, to one or more actions taken when those events occur. The event
engine evaluates several event types in parallel (<<smc-cla-event-types-table>>).

[[smc-cla-event-types-table]]
[cols="30%,70%",options="header",]
.SMC CLA event types
|=======================================================================
|Event |Description
|Signal match |Fires when the masked debug bus equals a programmed value
(`debug_bus & mask == match`). Several independent match events are
available.
|Edge |Fires on a rising or falling edge of selected debug-bus signals.
|Transition |Fires when a masked subset of the bus moves from a
programmed value A to a programmed value B.
|Ones count |Fires when the population count of a masked subset equals a
programmed value.
|Any change |Fires when any signal within a masked subset changes.
|Time match |Unavailable in this integration. Its timestamp input is tied to
zero. The comparator requires a nonzero match value, so the event cannot fire;
it does not use the local CLA timestamp register.
|Counter |Counts cycles following an event match and fires when the
count is reached; a small pool of counters is available for measuring
intervals or deferring an action.
|=======================================================================

When an EAP fires, a status flag records which pair triggered — for
example, so an interrupt handler can identify the source — and a snapshot
register latches the debug-bus value at the moment of the trigger for
post-mortem inspection. EAPs are enabled together once programming is
complete, so a partially programmed pairing never triggers.

== Actions and Cross-Triggering

An EAP can drive one or more actions:

* *Debug interrupt* — raise a non-maskable interrupt to the CPU.
* *Clock stop* — halt clocks to freeze the design for inspection.
* *GPIO toggle* — the generic block provides this action, but SMC terminates
  it on an unused local signal; it does not drive a pad.
* *Cross-trigger out* — signal other debug blocks that a local event
  occurred.
* *Trace capture* — hand the event to the trace subsystem.
* *Custom actions* — reserved outputs for design-specific use.

Cross-trigger inputs let events elsewhere in the system arm or fire local
actions, and cross-trigger outputs propagate local events outward, so
debug conditions can be correlated across blocks rather than observed in
isolation.

== Trace

The configured trace sink uses external memory request/response ports. The
optional trace AXI master has unconnected request outputs and tied-low response
inputs, so it cannot stream trace over the SMC fabric.

SMC selects local CLA timestamp scheme 0, advanced by the wrapper's reference
clock-derived `time_tick`. This local counter is distinct from the generic
`i_timestamp`, reference timestamp, and OCTS timestamp inputs, all tied to zero.
The integration does not provide the advertised global timestamp alignment
through those inputs. In particular, the time-match event consumes the tied-off
timestamp rather than the running CLA timestamp register.

Because of timestamp scheme 0 and the 64-bit CLA debug bus, several CLA
registers have no effect in SMC. `TsCapture`, `CDbgTimestampCapture` and
`CDbgClaTimestampOffset` serve only the reference-timestamp scheme. The Hi
halves of the match, compare, transition, ones-count, change and snapshot
registers serve only a 128-bit debug bus. `CDbgMuxSelHi`, and `Muxselseg4`
to `Muxselseg7` of `CDbgMuxSelLo`, select lanes beyond the four that the CLA
mux drives.

=== Memory Map

The CLA counter values and timestamp fields are software-writable. Software
writes take priority over simultaneous hardware updates; later hardware updates
can advance or clear them according to their configured controls. The sink's
`trDstRamWPHigh` register likewise accepts software writes. These are live
read/write state, not read-only status.
