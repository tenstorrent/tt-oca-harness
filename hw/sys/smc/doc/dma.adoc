= Direct Memory Access (DMA) Engine
:description: SMC DMA configuration, submission, completion and register reference.

[[direct-memory-access-dma-engine]]

The SMC DMA copies data through an AXI master using register-programmed linear
or two-dimensional transfers. Software supplies one shared configuration and
submits it by reading `NEXT_ID_0`. The engine does not fetch descriptor lists.
SMC instantiates one control interface, one stream and one DMA master.

[[smc-dma-controller-integration-table]]
[cols="1,3",options="header"]
.SMC DMA integration
|===
|Item |SMC configuration
|Control aperture |`0xC003_8000–0xC003_81FF` (512 bytes, SMC-local view).
|Control path |AXI, 9-bit local address and 64-bit data, converted internally
to 32-bit register accesses. This is not an AXI4-Lite-only wrapper.
|Data path |56-bit addresses, 64-bit data; 3-bit ID at the DMA wrapper and
4-bit ID after the shared DMA/zeroer mux. Backend internal IDs are 2 bits.
|Access policy |Transfers pass through SMC fabric remapping/filtering;
program addresses permitted by that integration.
|===

The frontend captures register state into a request FIFO. The 2D midend expands
each command into linear transfers, and the backend performs the AXI reads and
writes. The DMA and zeroer share the outgoing fabric path shown below.

[[smc-dma-zeroer-diagram]]
.SMC DMA and memory-zeroer architecture and shared fabric path
image::SMC_DMA_ZEROER_FIG013_FIG014.png[alt="SMC DMA and memory-zeroer architecture and shared fabric path",width=100%,pdfwidth=100%]

The generic request manager can arbitrate multiple control/master interfaces
with round-robin selection, per-master origin tracking and buffered response
routing. In the instantiated one-control/one-master SMC configuration it is a
passthrough; these generic arbitration features add no extra SMC streams.

[[smc-dma-configuration-parameters-table]]
[cols="2,1,3",options="header"]
.SMC DMA elaboration settings
|===
|Parameter |SMC value |Meaning
|`NUM_CTRL_INTERFACES`, `NUM_CTRL_STREAMS`, `NUM_MST_INTERFACES` |1 each
|One shared configuration, one functional stream and one DMA master.
|`DMA_MST_MAX_TXNS` |32 |Backend in-flight AXI limit, from `FABRIC_MAX_TRANS`.
The generic DMA wrapper default is 16.
|`F2M_FIFO_DEPTH` |4 |Request FIFO between frontend and 2D midend.
|`M2B_FIFO_DEPTH` |0 |Midend-to-backend FIFO bypassed.
|`BUFFER_DEPTH` |16 |Backend realignment buffer depth in beats; the generic
wrapper default is 3. It is not a reorder-buffer entry count.
|`EN_R_AW_COUPLING` |1 |Backend read/write address coupling enabled.
|`BYPASS_DMA_CTRL_FLOPS`, `BYPASS_DMA_MST_FLOPS` |0 each |Interface cuts retained.
|`CG_HYSTERESIS_W` |6 |Width of the runtime clock-gating hysteresis input.
|===

The frontend has a bus-aware clock gate; the request manager and backend use a
separate activity/hysteresis gate. `cg_enable_i=0` keeps them awake, and test
mode overrides gating. Clock gating does not abort transfers or isolate the bus.

=== Stream and Register Ownership

ifdef::backend-html5[]
// Stable links to consolidated material.
++++
<span id="control-interface"></span>
<span id="dma-frontend"></span>
<span id="smc-dma-frontend-control-interface-table"></span>

The generated map contains `NEXT_ID`, `STATUS` and `DONE` banks for 16 streams,
but only bank 0 is functional in SMC. Reads of `NEXT_ID_1..15` complete with zero
and launch nothing; their `STATUS` and `DONE` registers also read zero. Treat
these banks as reserved. A read of `NEXT_ID_0` is a command, not a harmless
status read; exclude it from diagnostic register dumps.

Source, destination, length, strides, repetitions and `CONFIG` are shared registers.
Serialize their writes and the submission read between software contexts. There
is no configuration-lock register. The 64-bit fields use low/high 32-bit register
halves; do not assume the two halves are updated atomically by the register path.

[[smc-dma-transfer-parameters-table]]
[cols="2,1,1,3",options="header"]
.DMA register storage and effective field widths
|===
|Field |CSR storage |Effective width |Use
|`SRC_ADDRESS_LO/HI`, `DST_ADDRESS_LO/HI` |64 bits each |56 bits each |Byte addresses.
|`LENGTH_LO/HI` |64 bits |56 bits |Bytes per linear copy or per 2D row.
|`SRC_STRIDE_LO/HI`, `DST_STRIDE_LO/HI` |64 bits each |56 bits each |Address increment
between consecutive row starts; source and destination increments are independent.
|`NUM_REPETITIONS_LO/HI` |64 bits |32 bits |Number of rows, including the first.
|===

The frontend casts register values to these effective widths: upper bits are
discarded, not validated as an out-of-range access. Program unused upper bits
as zero and ensure all row addresses and lengths fit the permitted address
range. Address stepping uses the effective address width.

=== Linear and Two-Dimensional Copies

For a linear copy, set `CONFIG.ENABLED_ND=1` and `NUM_REPETITIONS_LO=1` and `NUM_REPETITIONS_HI=0`. For a 2D copy, also
program source/destination strides and the required repetition count. Strides
can gather or scatter evenly spaced rows; there is no linked-list walker.

Set the combined length nonzero and `NUM_REPETITIONS_LO/HI` at least one. Clearing `CONFIG.ENABLED_ND` forces the
midend repetition count to zero. A zero-repetition command produces an internal
midend error response without data movement; that response still retires a
transfer ID. The control aperture does not expose the error payload, so a
retired ID alone is not proof that valid data was copied.

The names above follow the published register map. The RTL frontend calls the
configuration `conf`, the ND-enable field `enable_nd`, and the repetition pair
`reps_2_low/high`; these refer to the same fields. Some generated CONFIG field
descriptions say "Not used", but the frontend forwards the options described here.

The frontend requests incrementing AXI bursts and sets the cache attribute to
modifiable. `CONFIG` supplies decoupling, maximum burst-length and length-reduction
options. The backend handles alignment and burst splitting; these mechanisms
do not grant permission to access a filtered or otherwise invalid address.

== Submission and Completion

ifdef::backend-html5[]
// Stable links to consolidated material.
++++
<span id="command-processing"></span>
<span id="response-path"></span>
<span id="status-and-control"></span>
++++
endif::backend-html5[]

. Establish exclusive ownership of the shared configuration. Prepare the source
  data and destination ownership according to the platform's memory-ordering
  and cache-maintenance requirements.
. Program `CONFIG`, both address halves, length, strides and repetition count.
  Check effective widths and address bounds before submission.
. Ensure configuration writes are visible, then read `NEXT_ID_0` exactly once
  to submit and record its returned transfer ID. This read can be backpressured
  until the frontend accepts the request.
. Use `DONE_0` to track retirement. For a single outstanding command, wait for
  its ID; with multiple outstanding commands, maintain an ordered software
  record so a later retirement does not make an earlier equality test wait forever.
. Apply the platform's completion-ordering/cache rules before consuming the
  destination. Handle a firmware timeout as a recovery decision; there is no
  software abort register or state-preserving abort guarantee.

[[smc-dma-status-monitoring-and-control-table]]
[cols="1,3",options="header"]
.DMA status and notification
|===
|Indication |Meaning
|`STATUS_0[7:0]` |Eight copies of frontend request readiness: `0xFF` means
room to accept a command. These are not per-channel backend busy bits.
|`STATUS_0[8]` / `[9]` |Bit 8 is zero; bit 9 is the midend activity indication.
|`DONE_0` |Most recently retired transfer ID. No byte-progress or classified
software error-status register is provided.
|DMA interrupt |One-cycle pulse on a falling edge of combined frontend/backend
busy, routed to raw CPU vector bit 322 (PLIC ID 323). No local enable, mask or
pending register; this is not one interrupt per submitted descriptor.
|===

Do not infer completion from frontend readiness or from a zero `STATUS` value.
The transfer-ID generator resets `NEXT_ID` to 2 and `DONE` to 1 and skips zero
on wrap. Use wrap-aware tracking for long-running queues; ordinary unsigned
comparison is insufficient across rollover.

The busy-falling pulse is a service hint. Use `DONE_0` to establish retirement
and provide polling/timeout handling: PLIC gateway behavior does not turn
successive completion pulses into a counted queue.
