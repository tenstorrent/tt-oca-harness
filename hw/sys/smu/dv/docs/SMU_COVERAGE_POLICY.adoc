== SMU v0.5.0 coverage targets and closure policy

This chapter records the #484 decision. It approves *what* the SMU
release group is graded on and *how* a hole is waived. It does not
install a CI fail-on-hole gate; that is #492, after the first measured
database exists. Project-wide collection mechanics stay on #528.

Do not treat a merged copy as design-owner or DV-lead sign-off.

ahsiao confirmed SMU grades toggle. The DUT is an integration shell:
`smu.sv` is wiring, and Verilator emits no line / branch / expression
sites under `hw/sys/smu/rtl/`. A Python `smu_fcov.py` sampler is not
the release metric and is not a gate.

There is no checked-in 98%-after-waiver figure. Do not invent one.

[[smu-cov-out]]
=== Structural OUT versus a waiver hole

Two mechanisms. Do not mix them.

[cols="2,3,3",options="header",]
|===
|Kind |Effect |Carrier once #492 lands
|Structural OUT |the point never enters the database |`coverage_off`
file patterns (SMC, DTP, SEP, `hw/ip`, `hw/common`, CPU cluster, TB,
vendor trees the file pattern can reach)
|Waiver hole |the point exists and is not hit |`[[holes]]` with the
fields below
|===

A vendor site that `coverage_off` cannot name (hierarchy under `.u_smc`
/ `.u_dtp`) is a hole with `category = "out_of_scope"` and
`disposition = "exclude_scope"`. Write it only from a real database:
`expected_matches` is a hard count, and a guessed count is a
ConfigError on the first run.

[[smu-cov-waiver]]
=== Waiver fields

Every `[[holes]]` row that #492 writes must carry:

* `tool`, `metric_family` (`toggle`), `hierarchy` or file selector
* `category` (`out_of_scope` / `excluded` / `waived` / `open`)
* `disposition`
* `owner`
* `review_date`
* `issue` when the disposition is actionable

`max_unclassified_points = 0` is the fail-on-new-hole knob. It is not
set here. #492 sets it after the first weekly `--cov` database exists
and the owner signs the threshold.
