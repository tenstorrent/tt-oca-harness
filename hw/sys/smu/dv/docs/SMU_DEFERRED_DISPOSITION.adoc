[[smu-deferred-disposition]]
= SMU deferred and OUT disposition

This chapter has two parts. The table below is the catalog of every SMU test
name classified deferred or OUT, and none of those names is in the hosted
credit set `hosted`; <<smu-bench-standins>> is the record of every
stand-in, force, skip and waiver on a proof path of an enrolled test. The
table first. Three kinds of name are in it. Fifteen have a test body and are
enrolled in `testlists/all.toml`; their bucket says which group holds them
and why that group is not credit. Fifteen are enrolled in no testlist,
because this bench cannot run them or they cannot pass on it; their bucket
says what each needs. A deferred body, and
its sequence where it had one, is kept in git history rather than on disk and
is restored when the blocker named in its row clears. The rest never had a
test body here. None of the last two kinds is reportable as PASS. Enrolled names outside `hosted`
that carry neither classification — the lifecycle, debug-gating, chain and
elaboration leaves — are not in this table: each is carded in
`SMU_VPLAN.adoc` and enrolled in a named group of `testlists/all.toml`.

Buckets:

* `SEP1-enrolled` — has a body and runs in the wrapper `all` group with real SEP instruction retirement (`sep_real_fw`, `sep_entropy`, or `fw_boot` for the SEP smoke). Not `hosted` credit, and no CI workflow schedules those groups.
* `SEP1-blocked` — written against the wrapper bench, enrolled in no testlist: the SEP-driven SMC bring-up polls SMC SRAM that no sys-inbound master can reach, so the leaf cannot pass by construction. Re-enrols in `all` the day the SMC SRAM path exists.
* `not-runnable` — has a body in git history, enrolled in no testlist: the claim it checks is not met by the RTL as built, the bench cannot produce the condition it needs, or it needs the `smu #(.CFG(smu_pkg::NoSepCfg))` elaboration, which this package does not build. The row names the condition.
* `OUT-until-SEP1` — no body; a scenario driven by SEP firmware. The bench elaborates the real SEP and `smu_sep_smoke_test` retires its instructions, so a leaf written for one of these names runs SEP firmware, needs the RISC-V toolchain for its `c_build` stage, and joins the groups outside `hosted` (`fw_boot`, `sep_real_fw`) that no workflow schedules.
* `child-TB-owned` — protocol or CPU depth belongs to the SMC, SEP, or DTP TB.
* `waived` — superseded, toggle-as-pass, stimulus-pin gap, or leftover catalog name.

Enrolled names outside this catalog:

* The JTAG2AXI / OTP / filter set in `hosted` is recorded in the Component Signoff section of `hw/sys/smu/dv/docs/SMU_VPLAN.adoc`, which also records ATOP reject as OUT.
* `smu_ext_boot_seq_gate_test` and `smu_smc_mailbox_int_test` are enrolled in `hosted` (`testlists/all.toml`).
* `smu_ext_axi_global_addr_smoke_test` is in the table below under `not-runnable`.

[[smu-bench-standins]]
== Bench stand-ins and exceptions

A stand-in is anything that answers in place of the mechanism a claim is
about: a testbench force, a simulation-only path selected by a plusarg, a
configuration waiver, a loopback where a chain would be, a compiled-in
substitute for a product cell, or a model inside the product composition.
Nine sit on proof paths of enrolled SMU tests. Each has one entry of three
fields, filled from the tree: the claim that is accepted with the stand-in in
place, why the real path cannot be used, and the exact scope. Who approved an
entry, against which revision, and when it is next reviewed are recorded in
the pull request that adds or changes it and in the tracker, not here; an
entry whose approval is not recorded there is a declaration and clears
nothing, and every test on its scope is graded as if the stand-in were
undeclared. Each entry describes the tree that carries it, not an older
revision: the stand-ins and the entries that declare them move in the same
commits, so a hash written into this file is stale the moment the file is
edited. What makes an entry checkable is the command in
<<smu-standin-recheck>> -- one per entry, each naming a string a reader can
see for themselves; the approval records the revision checked and the command
run.

=== `+esrc_noise_force`

[cols="1,4"]
|===
|Claim accepted

=== SEP assertion-ignore patterns

[cols="1,4"]
|===
|Claim accepted

=== `+define+ASSERTS_OFF`

[cols="1,4"]
|===
|Claim accepted
|No SystemVerilog assertion inside the DUT, the vendored common cells or the testbench is a checker on any run this package records. Every enrolled verdict is a Python compare in a sequence or scoreboard, or the firmware's own terminal loop, and every card in `SMU_VPLAN.adoc` offers such a compare as its evidence; no card offers an SVA. |Scope
