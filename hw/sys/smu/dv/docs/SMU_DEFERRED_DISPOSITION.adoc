[[smu-deferred-disposition]]
= SMU deferred and OUT disposition

This chapter has two parts. The table below is the catalog of every SMU test
name classified deferred or OUT, and none of those names is in the hosted
credit set `hosted`; <<smu-bench-standins>> is the record of every
stand-in, force, skip and waiver on a proof path of an enrolled test. The
table first. Three kinds of name are in it. Fifteen have a test body and are
enrolled in `testlists/all.toml`; their bucket says which group holds them
and why that group is not credit. Fifteen are enrolled in no testlist,
because this bench cannot run them or they cannot pass on it; their bucket
says what each needs. A deferred body, and
its sequence where it had one, is kept in git history rather than on disk and
is restored when the blocker named in its row clears. The rest never had a
test body here. None of the last two kinds is reportable as PASS. Enrolled names outside `hosted`
that carry neither classification — the lifecycle, debug-gating, chain and
elaboration leaves — are not in this table: each is carded in
`SMU_VPLAN.adoc` and enrolled in a named group of `testlists/all.toml`.

Buckets:

* `SEP1-enrolled` — has a body and runs in the wrapper `all` group with real SEP instruction retirement (`sep_real_fw`, `sep_entropy`, or `fw_boot` for the SEP smoke). Not `hosted` credit, and no CI workflow schedules those groups.
* `SEP1-blocked` — written against the wrapper bench, enrolled in no testlist: the SEP-driven SMC bring-up polls SMC SRAM that no sys-inbound master can reach, so the leaf cannot pass by construction. Re-enrols in `all` the day the SMC SRAM path exists.
* `not-runnable` — has a body in git history, enrolled in no testlist: the claim it checks is not met by the RTL as built, the bench cannot produce the condition it needs, or it needs the `smu #(.CFG(smu_pkg::NoSepCfg))` elaboration, which this package does not build. The row names the condition.
* `OUT-until-SEP1` — no body; a scenario driven by SEP firmware. The bench elaborates the real SEP and `smu_sep_smoke_test` retires its instructions, so a leaf written for one of these names runs SEP firmware, needs the RISC-V toolchain for its `c_build` stage, and joins the groups outside `hosted` (`fw_boot`, `sep_real_fw`) that no workflow schedules.
* `child-TB-owned` — protocol or CPU depth belongs to the SMC, SEP, or DTP TB.
* `waived` — superseded, toggle-as-pass, stimulus-pin gap, or leftover catalog name.

Enrolled names outside this catalog:

* The JTAG2AXI / OTP / filter set in `hosted` is recorded in the Component Signoff section of `hw/sys/smu/dv/docs/SMU_VPLAN.adoc`, which also records ATOP reject as OUT.
* `smu_ext_boot_seq_gate_test` and `smu_smc_mailbox_int_test` are enrolled in `hosted` (`testlists/all.toml`).
* `smu_ext_axi_global_addr_smoke_test` is in the table below under `not-runnable`.

[[smu-bench-standins]]
== Bench stand-ins and exceptions

A stand-in is anything that answers in place of the mechanism a claim is
about: a testbench force, a simulation-only path selected by a plusarg, a
configuration waiver, a loopback where a chain would be, a compiled-in
substitute for a product cell, or a model inside the product composition.
Twelve sit on proof paths of enrolled SMU tests. Each has one entry of three
fields, filled from the tree: the claim that is accepted with the stand-in in
place, why the real path cannot be used, and the exact scope. Who approved an
entry, against which revision, and when it is next reviewed are recorded in
the pull request that adds or changes it and in the tracker, not here; an
entry whose approval is not recorded there is a declaration and clears
nothing, and every test on its scope is graded as if the stand-in were
undeclared. Each entry describes the tree that carries it, not an older
revision: the stand-ins and the entries that declare them move in the same
commits, so a hash written into this file is stale the moment the file is
edited. What makes an entry checkable is the command in
<<smu-standin-recheck>> -- one per entry, each naming a string a reader can
see for themselves; the approval records the revision checked and the command
run.

=== SEP assertion-ignore patterns

|Scope

=== `noXOnCsI` hold-off window

[cols="1,4"]
|===
|Claim accepted
|An X on the request of the SMC ROM, the SEP boot ROM or the Key Manager ROM before the SMC primary reset has released is not a verdict on any enrolled SMU claim. |Why the real path cannot be used

|Scope

=== Crypto EDN request-hold window

[cols="1,4"]
|===
|Claim accepted
|The six request-hold checks of the crypto EDN adapter `u_dut.u_smu.gen_sep.u_sep.u_sep_crypto.u_axis_edn_crypto_s3c_scan` -- the arbiter pair `u_arbiter.ReqStaysHighUntilGranted0_M` and `u_arbiter.LockArbDecision_A`, and the four `gen_ep[0..3].AxisEdnReqStableUnlessEndpointCancelled_A` -- hold at every instant outside one window. The window opens when the SMU-side JTAG IC_RESET override holds `sep_reset_n`, `aes_jtag_rst_n`, `kmac_jtag_rst_n` or `otbn_jtag_rst_n` low (`ovrd` set with `val` low) and closes eight SEP clocks after the last of those holds clears. Inside it the arbiter pair is off on any one of the four causes, and an endpoint check is off only while the reset of its own engine is held (endpoint 0 AES, 1 KMAC, 2 and 3 OTBN; all four under `sep_reset_n`) and for eight SEP clocks after that hold clears, whatever the other causes do; a check no cause has named for that long is armed. A firing at any other instant fails the run through the `u_axis_edn_(crypto\|pool)_s3c_scan` entry of `smu_sim_cfg.toml` `extra_hard_fail_patterns`, a run that ends inside the window fails through the `window still open at end` entry of the same list, and the pool instance keeps its checks throughout. What is not proven is the request hold from the JTAG reset edge to eight SEP clocks after its release: an ungranted request of an engine the override resets drops with no endpoint cancel, and the window covers that drop. The window does not cover a drop caused by clearing a release-type override (`ovrd` set with `val` high) while the sequenced reset is low: the engine reset then re-asserts from the sequenced reset two `clk_i` later with no endpoint cancel, the window keys only on `ovrd` set with `val` low, and a firing there fails the run.
|Why the real path cannot be used
|The JTAG IC_RESET override asserts the crypto engine resets without the isolation sequence: the `sep_reset_n` override reaches every engine reset asynchronously, a per-engine override reaches its engine two `clk_i` edges after the TCK-domain bit changes, and the EDN adapter and arbiter stay on the SEP power-on reset. The endpoint cancel the adapter needs before a client reset comes only from the isolation sequence, which the debug path skips by design, so the checks cannot hold across that edge.
|Scope
|`tb/tb_wrapper_top.sv`, inside `ifndef VERILATOR` and `ifndef UVM`: the window keys on `u_dut.u_smu.jtag_sep_reset_ctrl`, an `ovrd` bit set with its `val` bit low for `sep_reset_n`, `aes_jtag_rst_n`, `kmac_jtag_rst_n` or `otbn_jtag_rst_n`. While a cause holds, the arbiter pair is killed (`$assertkill`) on any cause and an endpoint check only for the engine the cause names (endpoint 0 AES, 1 KMAC, 2 and 3 OTBN; all four under `sep_reset_n`); an endpoint check re-arms eight SEP clocks after its own causes clear and the arbiter pair eight SEP clocks after the last cause clears, which closes the window; a margin during which the SEP clock has not risen for eight `clk_smu_i` edges ends after eight `clk_smu_i` edges instead, so a stopped SEP clock cannot hold the window open. The window prints `[tb] crypto EDN request-hold window open at <time>: JTAG override holds engine reset low: sep/otbn/kmac/aes=<bits>` on open, `[tb] crypto EDN request-hold window closed at <time>` on close, and `[tb] crypto EDN request-hold window still open at end: sep/otbn/kmac/aes=<bits>, SEP clock <running\|stopped>, last rose at <time>` from a `final` block if a run ends inside it; the `crypto EDN request-hold window still open at end` entry of `smu_sim_cfg.toml` `extra_hard_fail_patterns` fails the run on that last line. No plusarg selects it: every cocotb leaf of the wrapper on a four-state simulator compiles it in, and it opens only on a leaf whose override holds one of those resets low (the stand-in table names the one leaf that does). On `smu_jtag_reset_override_test` one open/close pair spans the SEP-port walk, from about 73.9 us to 88.0 us on seed 703853225. On Verilator `+define+ASSERTS_OFF` (its own entry) compiles the assertions out, and the SV-UVM shape holds the whole `u_axis_edn_crypto_s3c_scan` scope off by name (SEP assertion-ignore patterns entry; `SMU_TB_ARCH.adoc`), so the window is excluded there by `ifndef UVM`.
|===
