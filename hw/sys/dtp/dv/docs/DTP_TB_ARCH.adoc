[[dtp-dv-testbench-architecture]]
== DTP Testbench Architecture

=== Overview

[cols=",",options="header",]
|===
|Field |Value
|DUT |`dtp` (`hw/sys/dtp/rtl/dtp.sv`)
|Repository |`tt-oca-harness`
|Project |OCAH
|Framework |One UVM environment, realized in PyUVM on cocotb (`cocotb/`) and in SystemVerilog UVM (`uvm/`, `--framework uvm`)
|Primary simulator |Verilator (cocotb realization; the PR gate and the scheduled regressions)
|Supported simulator matrix |cocotb on `verilator` (default), `vcs`, and `xcelium`; SV-UVM on `vcs` only, because Verilator has no SV-UVM support and the runner's SV-UVM flow is VCS-only (`run_dv.py --list --json` reports the pairs for `dtp`)
|Commercial simulator use |SV covergroup, assertion, and code coverage collection; the SV-UVM realization
|===

The DTP testbench follows the canonical `hw/sys/<system>/dv/` layout under
`hw/sys/dtp/dv/`. One testbench top (`tb/tb_top.sv`) serves both realizations,
and both compose the shared OCAH VIPs (`hw/common/dv/vip/`) for the standard
interfaces; both extend the shared framework library
`hw/common/dv/vip/ocah_lib/`. Scenario names, testlist bindings, knob names,
the evidence grammar, and the functional-coverage modules are common to both.
The Layout table of the DV `README.md` says what each directory holds and its
Getting Started section gives the runner commands; the Regression Groups
section of `DTP_VPLAN.adoc` defines the testlist groups.

=== VIP Selection Policy

[arabic]
. Import unified OCAH BFM wrappers from `hw/common/dv/vip` for standard
protocol access.
. Wrap those BFMs in PyUVM agents so tests remain sequence-based and reusable.
. Use OCAH-local BFMs/models for custom OCAH protocols and for standards that
have no shared wrapper.
. Keep every BFM behind the same transaction-level agent boundary so backend
changes do not affect sequences or scoreboards.

[cols=",,,",options="header",]
|===
|DTP Interface |Preferred VIP |Modeling Approach |Notes
|Primary JTAG TAP |`ocah_jtag_vip` `OcahJtagMasterDriver` |Unified OCAH BFM |Active JTAG transaction driver and TAP helper
|SMC fabric AXI4 manager |`ocah_axi_vip` `OcahAxiSlaveAgent` |Unified OCAH BFM |AXI memory responder with scoreboard backdoor access
|SMC/SEP OTP AXI-Lite managers |`ocah_axi_vip` AXI-Lite wrapper |Unified OCAH BFM |AXI-Lite responder model for OTP bridge scenarios
|XTRIG AXI-Lite CSR subordinate |`ocah_axi_vip` AXI-Lite master |Unified OCAH BFM |Shared AXI-Lite master on `u_xtrig_master_if`; channel-skew, RREADY-hold, and partial-strobe operations come from its sequence API
|BSR scan loopback |Minimal OCAH-local scan model |OCAH-local simple model |Compact scan loopback and observable model
|STAP host ports / 3DCR |`ocah_jtag_vip` slave devices (`OcahJtagSlaveAgent`, cocotb / `ocah_jtag_slave_agent`, SV-UVM) behind an OCAH-local chain model |Unified OCAH BFM + OCAH-local model |Wire loopback by default; the STAP-selection scenarios splice one reactive downstream TAP per port and judge it through `ocah_jtag_slave_sequence`, and the zero-length-bypass scenario splices the same devices into its STAP chain
|iJTAG SIB networks |OCAH-local IEEE 1687 model |OCAH-local model |IEEE 1687 scan-network transaction model
|CTP/CTM cross-trigger protocols |OCAH-local BFM (cocotb); DUT-local `dtp_xtrig_if` (SV-UVM) |OCAH-local BFM (cocotb); TB interface (SV-UVM) |`DtpXtrigBfm` drives and samples the CTP/CTM pins in cocotb; the SV-UVM cross-trigger sequences drive and sample them through `dtp_xtrig_if` (see Realization differences); debug TDR clock-stop requests may be driven directly in the TB
|===

=== DUT-Local Model Ownership

The shared promotion checklist is defined in `hw/common/dv/README.md`. The DTP
models below are DUT-local because they encode this DUT's topology, lifecycle
rules, signal binding, or testbench fixtures:

[cols=",,,",options="header",]
|===
|Model / Helper |Scope |Why It Is DUT-Local |Shared-VIP criterion
|`DtpScanModel` |8-bit BSR identity-loopback stimulus and checking |Models the compact DTP TB fixture, not generic IEEE 1149.1 boundary cells |A parameterized boundary-cell model with an independent DUT consumer
|`DtpIjtagSibModel` |Three DTP SIBs with stored-open retention under a gate, per-SIB debug-disable gates, the bench's instrument stubs (chain layout, composed scans, capture prediction, latched instrument values) |Hard-coded DTP scan topology, stub widths, and security policy |Topology/instrument-neutral IEEE 1687 transactions plus a second consumer
|`DtpStap3dcrModel` |Composed TAP_3DCR chain state (PTAP 3DCR, per-STAP SIB and 3DCR), network-wide IR-scan composition, the chain of a DR scan under ZERO_LENGTH_BYPASS or BYPASS, capture prediction, chain updates only while the PTAP 3DCR select is set, per-STAP debug-disable update blocking, the downstream TAP segments (IR, IDCODE, BYPASS, or a latched register) of the `ocah_jtag_vip` devices attached behind the STAP host ports, and the host segment behind the extended STAP host scan interface |The chain hierarchy, the splice flops, and the downstream parking rules are DTP-specific |A parameterized IEEE 1838/STAP model with an independent DUT consumer
|`DtpXtrigBfm` / `DtpXtrigCtmModel` |DTP CTP wire-OR/P2P pins, CTM masks, CSR layout from the generated cross-trigger register headers |Assumes DTP port counts, flattened signal names, and OCAH routing policy |Parameterized binding and port counts with an independent consumer
|`DtpBypassSuiteCfg` / `DtpJtagBypassModel` |BYPASS opcode, pattern, capture, and one-bit-delay prediction |Encodes the DTP BYPASS scenario and evidence context |An independent JTAG consumer of the same model
|DTP TDR maps/packers |DTP instruction/register semantics layered over `ocah_jtag_vip` |Register layout and polling policy are DUT semantics, not JTAG protocol |A domain consumer of the same DTP register contract
|===

The shared `ocah_jtag_vip` and `ocah_axi_vip` packages own protocol-neutral
driving, monitoring, result, and error behavior. DTP agents own
hierarchy binding, address/TDR maps, expected values, debug-disable
policy, and scoreboarding.

=== BYPASS Reference-Model Contract

The DTP BYPASS scenario is the concrete reference-model/scoreboard example:

[source,text]
----
DtpBypassSuiteCfg
  -> load_ir / shift_dr JTAG stimulus
  -> DtpJtagBypassModel.predict(case) -> expected TDO
completed DtpJtagItem.result         -> observed TDO
expected + observed
  -> OcahJtagChecker
  -> CHK-BYPASS-* / CHK-NONVAC / CHECKER_SUMMARY
----

The frozen suite config is the single source for opcode, width, pattern,
capture bit, seed, and evidence context. The pure model has no simulator
handles or DUT reads. Aggregate checker mode lets every configured case run;
finalization then reports total checks/errors/missing IDs before failing.
Passing `results.xml` and native `result.json` are the run authority.

=== Testbench Hierarchy

One component tree from the test down to the pins; the two realizations
differ only where the language forces it (table below).

[source,text]
----
dtp_<scenario>_test          thin: create_scenario_seq(), loop-knob names,
  -> dtp_base_test            configure_test_cfg() (required features, evidence IDs)
       build:  dtp_test_cfg   seed and knobs -> randomize(): clock and TCK periods
               dtp_env_cfg    derived -> config_db -> dtp_env
       run:    bring_up()     reset ladder through the TB interface
               run_looped_scenario()  dtp_<scenario>_test_seq on dtp_env.m_vseqr,
                                      one pass per loop, scenario_seed = seed + pass

dtp_<scenario>_test_seq       virtual sequence on dtp_virtual_sequencer; one flow
  -> dtp_<family>_base_test_seq  (jtag, jtag2axi, debug_tdr, scan, xtrig)
  -> dtp_base_test_seq           TAP-state tracking, DTP checks, system-domain waits
       starts reusable operations on the virtual sequencer's typed handles:
         dtp_jtag_<op>_seq          -> m_jtag_seqr   (ocah_jtag_master_sequence)
         dtp_jtag2axi_<op>_seq      -> m_jtag_seqr
         dtp_axi_csr_<op>_seq       -> m_xtrig_seqr  (ocah_axi_master_sequence)
         responder backdoor/inject  -> m_<target>_slave_seq, m_stap_ds_seq[i]
       per-scenario evidence checker (required IDs) -> finalize() at end of body()

dtp_env                       composes; drives nothing; checks no protocol
  -> dtp_virtual_sequencer    m_jtag_seqr, m_xtrig_seqr, three AXI responder
                              sequences, four downstream STAP device sequences
  -> ocah_jtag_master_env     primary TAP: sequencer, driver, monitor (event_ap)
  -> ocah_axi_master_env      XTRIG CSR AXI-Lite initiator
  -> ocah_axi_slave_agent x3  SMC OTP / SEP OTP AXI-Lite, SMC fabric (AXI4) responders
  -> ocah_axi_env x4          passive per port: monitor -> ref model -> scoreboard -> checker
                              (monitor only on the XTRIG CSR port)
  -> ocah_jtag_slave_agent x4 downstream STAP TAPs, attached per test
  -> dtp_<feature>_ref_model  one per scoreboard feature: subscriber on the monitor
                              stream the feature is judged on (event_ap, scan_ap, the
                              XTRIG or bridge item_ap) and dtp_tb_if; holds a plain
                              dtp_<x>_model; publishes expected items on expected_ap
  -> dtp_scoreboard ALWAYS ON pairs each feature's expected_ap with its observed stream:
                              ir_decode, idcode, bypass, xtrig_csr, xtrig_decode,
                              jtag2axi_req, jtag2axi_status; predicts nothing; a required
                              feature with zero comparisons or an unpaired item fails
  -> dtp_axi_port_history x3  subscriber on each bridge port's item_ap; counts its
                              completed writes and reads and keeps the newest of each
  -> dtp_tap_fsm_checker      subscriber on event_ap; VIP TAP reference model
  -> dtp_scan_window_monitor  subscriber on event_ap; temporal scan-control windows
  -> dtp_jtag_scan_builder    IR/DR scan reconstruction (scan_ap) and the DUT's
                              Shift-IR/Shift-DR episodes from dtp_tb_if
  -> ocah_jtag_checker        env-owned aggregate evidence, finalized once

tb/tb_top.sv                  one framework-neutral core: interface instances, DUT,
                              adapters, counters, coverage, protocol SVA; the UVM
                              block adds the clock generator, config_db publication,
                              run_test()
  dtp_tb_if                   control domain: clock and period, resets and counters,
                              named debug disables, TAP-state and debug-TDR observables,
                              request-activity and READY-stall counters, CSR port
                              spill-register and crossbar demux counters, JTAG2AXI bridge
                              state flags, pending and CDC-clear observables, SVA enables
  dtp_scan_if                 scan domain: scan-chain controls, iJTAG and STAP host scan
                              outputs, forwarded STAP pins, downstream-TAP attach enables
  dtp_xtrig_if                cross-trigger domain: CTM req/ack pairs, CTP pad quartets,
                              the CT_Req_out shared wires (pulls, chiplet drivers, group)
                              and every port's receive pulse
  ocah_jtag_if x5             primary TAP and four downstream STAP TAPs
  ocah_axi_if x8              one active and one passive instance per DTP bus
----

|===
|Element |cocotb (PyUVM), `cocotb/` |SV-UVM, `uvm/`

|Clock |`Clock(...)` on `dtp_tb_if.clk` in the base test bring-up, period from the env cfg |A loop in the harness block toggling `dtp_tb_if.clk`, period from `dtp_tb_if.clk_period_ns` set by `dtp_env`, started once it is set
|Knob transport |environment variables |plusargs through `ocah_knobs`
|Seed source |`RANDOM_SEED` |`+ntb_random_seed`
|Run verdict |phase assertions, `results.xml` |`UVM_ERROR`/`UVM_FATAL` counts plus `UVM TEST PASSED` from `report_phase`
|Tests |one module per scenario, `@pyuvm.test()` |one class per scenario, `include`d by `dtp_tests.sv` in module scope
|===

=== HDL Top

`tb_top` (`tb/tb_top.sv`) is one framework-neutral core with no ports: it
instantiates the TB interfaces, the `dtp` DUT elaborated from the bench
configuration table (`tb/dtp_dv_cfg_pkg.sv`, whose cocotb copy
`cocotb/env/dtp_dv_cfg.py` is checked against it at bring-up), the adapters
between the DUT's packed structs and the interface members, the reset, request-activity, and
READY-stall counters, the CSR port spill-register and crossbar demux counters, the
functional-coverage modules, and the protocol SVA checkers. Both
realizations consume the same interface instances: SV-UVM through
`uvm_config_db`, cocotb through the hierarchical handles `DtpTbIf`
(`cocotb/env/dtp_tb_if.py`) holds. The `UVM` define adds the harness block:
the clock generator on `dtp_tb_if.clk`, the test classes, the `uvm_config_db`
publication of every instance, and `run_test()`. The `ocah_axi_if` instances carry the interface's
default geometry so the SV-UVM layer sees one virtual type; cocotb binds them
through `OcahAxiConfig.bus()` at each bus's real geometry.

The three JTAG2AXI bridge geometries (bus type, address width, data width, and
the read and write pipeline depths) come from the bench configuration table,
which also elaborates the DUT: `tb_top` passes the bridge AXI types it declares
and the six pipeline-depth parameters to `dtp`. The SMC fabric bridge's widths
are those of SMC `jtag_axi_in_req_i` in the SMC port table; the OTP widths and
the depths are the bench's choice, with a different read and write depth on
every bridge. `JTAG2AXI_TARGETS` in `cocotb/env/dtp_types.py` and the
`dtp_j2a_target_*` functions in `uvm/env/dtp_types.svh` read that table; every
other TDR field width derives from the widths by the `*_AXI_SINGLE_OP` and
`*_AXI_SERIES_CTRL` tables of the PTAP document. Every JTAG2AXI scenario opens
each pass with the geometry gate in the JTAG2AXI base sequence's `pre_body`: it
reads the three `*_JTAG2AXI_CAPS` TDRs and records `CHK-J2A-GEOMETRY` against
the table, so a DUT that publishes a different geometry fails before any bridge
request is packed.

=== Environment Components

==== Configuration: `dtp_test_cfg` and `dtp_env_cfg`

`dtp_test_cfg` is the highest configuration level and the only object the
seed touches: the runner seed and random volume, the randomized system-clock
period (10..100 ns) and TCK period (100..1000 ns), the knob-derived controls
(IDCODE reads per pass, random walks, matrix rows), the negative-validation
switches, the downstream STAP attach mask and the host segment attach, the
scoreboard features a test requires, and the required evidence IDs of each
shared-VIP recorder. The base test fills and randomizes it once; a thin test
adds its requirements in `configure_test_cfg()`. `dtp_env_cfg` is derived
from it (clock and TCK timing, responder memory size and response USER seed,
attach mask, evidence policy) and is what the environment reads. The cocotb
`DtpEnvCfg` carries the same timing randomization.

==== `dtp_virtual_sequencer`

The handle set every scenario coordinates through: `m_jtag_seqr`
(`ocah_jtag_master_sequencer`, the primary TAP), `m_xtrig_seqr`
(`ocah_axi_master_sequencer`, the XTRIG CSR AXI-Lite initiator), the three
JTAG2AXI responder sequences (`m_smc_otp_slave_seq`, `m_sep_otp_slave_seq`,
`m_smc_axi_slave_seq`, `ocah_axi_slave_sequence`), and the four downstream
STAP device sequences (`m_stap_ds_seq[i]`, `ocah_jtag_slave_sequence`, in
io, smc, sep, extra0 order), and the XTRIG CTP shadow
(`m_xtrig_ctp_shadow`: the programmed CTP mode and polarity) that the
cross-trigger sequences share across passes. The cocotb realization keeps
that shadow on `DtpEnvCfg`.

==== Shared VIP environments and agents

`dtp_env` fills one VIP config per port from `dtp_env_cfg` (interface,
geometry, `name_tag`, evidence policy) and builds: the active
`ocah_jtag_master_env` on the primary TAP (the commercial-overridable unit;
its `event_ap` feeds every JTAG checker); the active `ocah_axi_master_env`
driving the XTRIG CSR AXI-Lite port; one memory-backed, fault-capable
`ocah_axi_slave_agent` per JTAG2AXI bridge (SMC OTP and SEP OTP AXI-Lite,
SMC fabric AXI4), reached only through their responder sequences; one
passive `ocah_axi_env` per observed port (monitor, reference model,
scoreboard, evidence; monitor-only on the XTRIG CSR port, whose volatile
status reads and reset-cleared selects the memory-shadow model cannot
describe); and one `ocah_jtag_slave_agent` per STAP host port as the
downstream TAP a test may splice behind it (`dtp_scan_if.stap_<x>_ds_en`;
default keeps the wire loopback). The cocotb realization wraps the same
shared engines in `DtpJtagAgent`, `DtpAxiAgent`, `DtpXtrigAgent`, and
`DtpStapDsAgent`.

==== `dtp_scoreboard` and the reference models

Always on, in every test, and comparing only. Every feature is judged on two
streams: the observed VIP monitor stream, and the expected items published on
`expected_ap` by that feature's `dtp_<feature>_ref_model`, a subscriber
(`ocah_ref_model`) on the same monitor stream and `dtp_tb_if` that holds any
plain `dtp_<x>_model` it needs and neither compares nor reports. The
scoreboard pairs the two streams in order per feature and lane
(`ocah_scoreboard`), extracts the observed value from the monitor item,
records the verdict, and counts; it holds no expected-value state. Expected
values come from the DUT collateral and the stimulus the monitors saw, never
from the observation under check.

Composed scans (a wider instruction scan spanning the STAP chain, or a DR
scan after one) make the primary-TAP instruction unrecoverable at this level,
so the JTAG reference models stand down until the next plain instruction load
or TAP reset. `dtp_jtag_ir_model` also tracks the PTAP 3DCR from TAP_3DCR
data scans, decided from the instruction register's shifted value, which
composed scans do not hide. The select survives a Test-Logic-Reset by TMS
while config_hold is set, and only TRST or power-on reset clears it then.
While the select is set the STAP chain follows every data register on the
TDO side, so the models that predict TDO (idcode, bypass and the
jtag2axi_status capture) stand down as well. An instruction scan that reaches Update-IR without a Shift-IR
cycle latches the Capture-IR pattern, 01 in the two LSBs and zeros above
(IEEE 1149.1 7.1.1, `jtag_inst_reg`), which is the IDCODE opcode; the models
track it as an IDCODE load. STATUS reads carry no data contract. A reference
model on a one-to-one stream publishes one expected item per observed item,
marking the ones outside its contract as carrying none, so the two streams
stay in lockstep; the bridge request model publishes one item per launched
transaction on the lane of its port. The bridge model follows the jtag2axi
update, capture, and completion rules (single-operation rejection while
pending, the series address and read budget per CTRL programming, the
byte-lane placement of series transfers, the queued requests a completion
drops while the bridge is disabled, reset on Test-Logic-Reset, where the
requests already on the fabric complete as orphans the AXI side consumes)
and applies completions at the capture or update that follows them, so a
capture during a shift sees the state of its own Capture-DR; a capture
inside the CDC settle window after a completion carries no contract; the
series read-data FIFO is not predicted. Each feature ends the run as one `CHK-SB-<FEATURE>`
record through the shared evidence recorder; a required feature with zero
comparisons fails, and so does any item left unpaired.

The cocotb `DtpScoreboard` judges the same seven features on the same
contracts, through reference models of the same basenames:
`DtpJtagScanBuilder` runs the shared passive monitor on the primary TAP and
publishes its reconstructed scans and per-TCK events, `DtpXtrigAgent` runs a
passive monitor on the XTRIG AXI-Lite port, and `DtpAxiAgent` runs one on each
bridge port in every test. A cocotb test names the features it must exercise
in `required_features`: ir_decode by default, xtrig_csr in the cross-trigger
tests (`dtp_xtrig_base_test`), idcode, bypass or xtrig_decode where the SV-UVM
twin requires them, and both JTAG2AXI features in every test that enables the
shared `ocah_axi_vip` scoreboard. Each monitor's swallowed subscriber
exceptions are recorded as `CHK-JTAG-MON-CALLBACKS`, `CHK-XTRIG-MON-CALLBACKS`
and `CHK-J2A-MON-CALLBACKS` and must be zero. Every cocotb JTAG2AXI test also
enables the shared `ocah_axi_vip` scoreboard with required evidence IDs and
per-stream minimum counts; a test that drives the three bridges in one pass
requires its scenario IDs on each bridge.

==== `dtp_tap_fsm_checker` and `dtp_scan_window_monitor`

`dtp_tap_fsm_checker` is the always-on invariant subscriber on the JTAG
event stream: on every completed TCK cycle the DUT one-hot TAP state must
match the VIP IEEE 1149.1 next-state model, and the run ends as one
aggregate `CHK-TAP-STATE` record; the sanity scenario additionally records
per-pass state and transition closure (`CHK-TAP-VISIT-ALL`). It also holds
the TRST_N level of the last TRST edge, which the SV-UVM `pulse_por` samples
under the power-on reset; the cocotb `pulse_por` reads the TRST pin.
`dtp_scan_window_monitor` counts high samples of named scan-control
observables once per TCK cycle while a scenario holds a window open, and
each observable's high count among the cycles the DUT's exported TAP state
spends in Capture-DR through Update-DR and in Run-Test/Idle, so a gated
resource proves zero control pulses across a whole composed scan, an enabled
resource proves the expected pulses, and a selected chain proves its select
held across the whole DR scan. In both realizations a window holds the TCK
cycles that rise while it is open, so a window opened with `shift_dr_windowed`
holds that DR scan's own TCK cycles, from Select-DR to the return to
Run-Test/Idle; the cocotb twin is `DtpScanControlWindowMonitor`.

==== Plain models

Plain model classes without simulator handles or reporting, held by a
reference model or by a scenario sequence: `dtp_jtag_ir_model` (TAP state,
the active primary-TAP instruction and the PTAP 3DCR select, held by every
JTAG reference model),
`dtp_xtrig_csr_model` (the CSR readback shadow), `dtp_jtag2axi_model` (the

Stimulus is directed and deterministic except for seeded randomization in
the debug TDR and Basic JTAG pattern sweeps, the JTAG2AXI random operations,
and the cross-trigger route selections. Randomization happens at the
test-cfg level (timing) and in
each scenario pass from its per-pass seed.

[cols=",",options="header",]

|Area |Strategy
|Smoke |Verify one basic scenario per feature area: TAP FSM traversal and IDCODE readout, TMP_STATUS readback, an iJTAG scan with every SIB open, an SMC fabric JTAG2AXI write and read-back, and CTP wire-OR routing

=== Checking Strategy

Five checking places, each owned once, in this order of authority. The four
class-level places emit the `CHK-<ID> PASS|FAIL expected= observed= context=`
grammar and finalize exactly once with a `CHECKER_SUMMARY`; the protocol SVA
report through their assertion action blocks.

[cols=",,,",options="header",]
|===
|Place |Owns |Feed |Fails when
|`dtp_scoreboard` (mandatory, always on) with one `dtp_<feature>_ref_model` per feature |`ir_decode`, `idcode`, `bypass`, `xtrig_csr`, `xtrig_decode`, `jtag2axi_req`, `jtag2axi_status` |JTAG monitor event and scan streams, XTRIG monitor stream, the three bridge port monitor streams, `dtp_tb_if` observables and reset counters; the reference model publishes the expected item, the scoreboard pairs it with the observed one |Any pair mismatches, an item is left unpaired, or a required feature ends with zero comparisons

|===

The scoreboard features cover instruction decode, IDCODE, BYPASS, the
JTAG2AXI request and status pairings, and the cross-trigger CSR readback and
decode. No feature in either realization judges the debug TDRs (TMP_STATUS,
DEBUG_CONTROL, IC_RESET, the CAPS registers), the boundary-scan controls and
the RUNBIST and DFT chains, the iJTAG and STAP scan network, or cross-trigger
routing, stretch, handshake, and reset quiescence. The per-scenario checker
is the only judge of those intents: it compares the DUT with bench models the
scenario builds from its own stimulus and the design collateral
(`CHK-TMP-*`, `CHK-DBG-*`, `CHK-CAPS*`, `CHK-BSR-*`, `CHK-DFT-*`,
`CHK-RUNBIST-*`, `CHK-SCAN-*`, `CHK-DS-*`, `CHK-XTRIG-*`).

The JTAG2AXI write and read scenarios of VPLAN sections 2 and 3, security
gating excepted, and the error single-operation and series scenarios of
section 4 judge every bridge operation from the scenario sequence as
`CHK-J2A-BUS-REQ`, the same way in both realizations: once the operation
completes, the port monitor has completed exactly one single-beat transaction of
its direction, at the address the request carried over the full bridge address
width, at its size on AXI4, and for a write with the strobes and strobed data
the request drives; no other transaction reaches the port between operations or
between passes, and none reaches the other two bridge ports. Each responder
stores an access at its address modulo a 64 KiB window, and the backdoor
accesses, preloads, and byte images index the same window, so the series and
random-operation scenarios and the seeded single-write cases of sections 2 and 3
draw seeded address bits above it, and the plain incrementing series streams
cross its top in a seeded half of the passes, carrying the series address into
those bits: the bits reach the bus, where this check judges them.

Negative validation proves each checking path can fail:
`DTP_JTAG_FAMILY_CHECKER_NEGATIVE` corrupts every family expectation,
`DTP_JTAG_TAP_CHECKER_NEGATIVE` desyncs the cocotb TAP reference model and
arms a wrong expected IDCODE in SV-UVM, `DTP_AXI_SCOREBOARD_NEGATIVE`
arms the wrong expected response, `DTP_XTRIG_CHECKER_NEGATIVE` inverts the
CTM model selects, `+DTP_XTRIG_NEGATIVE_CHECK=<n>+` corrupts the observed
value of one cross-trigger evidence ID wherever the scenario records it (1
`CHK-XTRIG-CSR`, 2 `CHK-XTRIG-SIGNAL`, 3 `CHK-XTRIG-ROUTE-MODEL`, 4
`CHK-XTRIG-ISOLATION`, 5 `CHK-XTRIG-QUIET`, 6 `CHK-XTRIG-STRETCH`, 7
`CHK-XTRIG-AXIL`, 8 `CHK-XTRIG-AW-LOCK`, 9 `CHK-XTRIG-AR-STALL`, 10
`CHK-XTRIG-WIRE`, 11 `CHK-RESET-COUNT`),
`DTP_J2A_REF_MODEL_NEGATIVE` makes the bridge request reference model predict
corrupted addresses so the scoreboard pairing fails against the observed bus,
`DTP_XTRIG_CSR_REF_MODEL_NEGATIVE` and `DTP_XTRIG_DECODE_REF_MODEL_NEGATIVE`
flip one bit of every compared `xtrig_csr` and `xtrig_decode` prediction,
`DTP_J2A_GEOMETRY_NEGATIVE` corrupts the expected address size of the per-pass
CAPS comparison,
`DTP_J2A_BUS_REQ_NEGATIVE` corrupts the address each `CHK-J2A-BUS-REQ` record
expects,
`DTP_J2A_ORPHAN_NEGATIVE` flips bit 0 of the value each `CHK-J2A-ORPHAN-*`
record expects, and
`DTP_J2A_STATUS_BIT_NEGATIVE` leaves the with-status fault beat unarmed while
its expectation stands; a run with any of them set must fail. The same
knob names are environment variables in cocotb and plusargs in SV-UVM.

=== Coverage Strategy

The `cov/sv/` coverage modules, instantiated once in the shared `tb_top`,
carry two layers. Their covergroups are the functional coverage model and
compile only on the commercial simulators, behind `ifndef VERILATOR`. Their
labeled `cover property` points compile in every flow:
Verilator records them as user coverage, and VCS grades them with the
assertions. Crosses, `illegal_bins`, and `ignore_bins` exist only in the
covergroups, so the two layers do not carry the same bins. The debug-disable
22-cell contract keeps its checker-gated Python ledger; `cg_dbg_disable_scan`
and `cg_dbg_disable_jtag2axi` record the same cells in both realizations.
Assertion coverage and full code coverage come from the commercial
simulators. See `DTP_FCOV.adoc`.

=== Canonical RTL Selection

Bender supplies the OpenTitan `prim_flop_2sync` and generated
`cross_trigger_port_reg` and `cross_trigger_matrix_reg` implementations to the
DTP simulator flows. Verilator and VCS therefore compile the same synchronizer

=== SystemVerilog UVM Realization (`--framework uvm`)

The SV-UVM realization runs through the same native runner: `dtp_sim_cfg.toml`
declares it as the `[frameworks.uvm]` overlay (shared DV root, sim config, and
testlist; `build/uvm/` build tree), and `--dut dtp --framework uvm` selects
it on VCS (the `native` profile's `uvm` framework, `-ntb_opts uvm-1.2`). Every
scenario carries both implementations in its testlist `module` binding map,
so any group runs unchanged under either framework.

There is exactly ONE testbench top module: `tb_top` in `tb/tb_top.sv`,
a framework-neutral core with no ports (interface instances, DUT, adapters,
counters, coverage, protocol SVA) shared between both realizations. The bare
`+define+UVM` (set by the native profile's `[frameworks.uvm]` overlay) adds
the harness block: the clock generator (period from `dtp_tb_if`), the
`uvm_config_db` publication of every interface instance, the test classes,
and `run_test()`.
The Integrator Guide's Project Defines chapter
(`doc/integrator/src/defines.adoc`) lists the preprocessor defines DTP
compiles use, including `UVM`. `UVM` is the only source of the harness block:
the simulator's `-ntb_opts` option selects which UVM library is compiled but
does not set the name. The runner compiles `uvm-1.2` unless the sim config
selects another library with `[build.vcs]` `uvm_lib`. `uvm-1.2` is the floor,
because the vendored OpenTitan assertion macros do not compile against older
libraries.

  from the generated address maps), `dtp_test_cfg`, `dtp_env_cfg`,
  `dtp_virtual_sequencer`, the expected items, the plain models, one
  `dtp_<feature>_ref_model` per scoreboard feature, `dtp_tap_fsm_checker`,
  `dtp_scan_window_monitor`, `dtp_scoreboard`, and `dtp_env`.
. `uvm/seq_lib/dtp_seq_lib_pkg.sv` — the reusable operation sequences and
  the scenario virtual sequences on `dtp_base_test_seq`.
. `uvm/tests/` — thin test classes named exactly like the scenario;
  `uvm/tests/dtp_tests.sv` is the include manifest `include`d by `tb_top.sv`
  under `ifdef UVM` (`+UVM_TESTNAME` selects the class). Two group bases sit
  between `dtp_base_test` and the thin tests: `dtp_xtrig_base_test` for the
  cross-trigger scenarios, which drive no JTAG traffic (it requires the
  `xtrig_csr` scoreboard feature and lifts the TAP checker's activity demand),
  and `dtp_jtag2axi_robustness_base_test` for the cross-bridge scenarios,
  which arms the evidence contract of all three bridge recorders.

Compile order is explicit and load-bearing: the library and VIP layers come
from their manifests (`ocah_lib/uvm/sources.toml`,
`ocah_jtag_vip/uvm/sources.toml`, `ocah_axi_vip/uvm/sources.toml`, listed in
`[frameworks.uvm.build].source_lists` and expanded ahead of the bench's own
`sources`), then the bench configuration package `dtp_dv_cfg_pkg`, which sizes
the TB interfaces' signals, the bridge state-flag module, the bench SVA modules,
the `cov/sv/` coverage modules, and the open-drain wire shim, then the three
DTP TB interfaces, the generated cross-trigger port address map,
`dtp_env_pkg`, `dtp_seq_lib_pkg`, and `tb_top.sv` last.

Logical item names stay framework-neutral and match the VPLAN scenarios, and
the UVM class name equals the scenario name (testlist
`name = "dtp_sanity_test"`,
`module = { cocotb = "dtp_sanity_test", uvm = "dtp_sanity_test" }`), so
`--items dtp_sanity_test` selects the same scenario in either realization.
`UVM TEST PASSED` is emitted only in the base test's `report_phase` when the
global UVM_ERROR/UVM_FATAL counts are zero, matching the `uvm-log` parser
policy.

=== Realization differences

Both realizations run the same scenarios, knobs, evidence grammar, and
coverage modules, and in both the expected value of every check comes from
the design collateral, the configuration, or the responder memory, never
from the observation under check. The two realizations differ in the rows
below; each row states what each realization does.

[cols="1,3,3",options="header",]
|===
|Element |cocotb realization |SV-UVM realization
|Primary TAP agent |DUT-local `DtpJtagAgent`: a sequencer and `DtpJtagDriver` over the shared `OcahJtagMasterDriver` engine, with `DtpJtagItem` carrying the TAP, TDR, and JTAG2AXI operations |Shared `ocah_jtag_master_env`; the operations are `dtp_jtag_<op>_seq` and `dtp_jtag2axi_<op>_seq` on its sequencer
|Scenario coordination |Every scenario runs on the JTAG agent's sequencer; the XTRIG CSR master and the CTP/CTM pin BFM are reached through `DtpEnvCfg` handles |`dtp_virtual_sequencer` with typed handles; every scenario is a virtual sequence
|Configuration |One `DtpEnvCfg` with `randomize_timing(seed)` |`dtp_test_cfg` randomized from the seed and the derived `dtp_env_cfg`
|Cross-trigger pins |`DtpXtrigBfm` (`env/dtp_xtrig_agent.py`), reached through `DtpEnvCfg`, drives the CTP and CTM pins and samples them for the scenario |No CTP/CTM BFM or pin monitor: the cross-trigger sequences drive and sample the pins through the DUT-local `dtp_xtrig_if` (`xtrig_vif`)
|Scoreboard |`DtpScoreboard` pairing seven `Dtp<Feature>RefModel` streams, always on; a required feature with zero comparisons fails, and a test that sets `use_axi_scoreboard` requires `jtag2axi_req` and `jtag2axi_status`. `DtpAxiScoreboard` builds the shared `ocah_axi_vip` reference models and scoreboard when a test opts in (`use_axi_scoreboard`, required IDs, stream minimums); every JTAG2AXI test does. A record from any bridge stream meets a required ID of the shared scoreboard, and the stream minimums hold each bridge to compared transactions; a test that drives the three bridges in one pass names its scenario IDs per bridge (`axi_checker_target_required_ids`), and `DtpAxiScoreboard` gives each bridge a checker that must record every one of them |`dtp_scoreboard` pairing seven `dtp_<feature>_ref_model` streams, always on; a required feature with zero comparisons fails. Each bridge's passive recorder requires the IDs the test names for that bridge
|Debug-disable ledger |The two matrix tests fill the 22-cell `DtpDbgDisableFcov` ledger (`env/dtp_fcov.py`), and `require_cells` fails a run with a missing cell |No ledger: every matrix pass runs each field's one-hot row and both boundary rows; `cg_dbg_disable_scan` and `cg_dbg_disable_jtag2axi` record the cells in both realizations
|JTAG2AXI responder write order |The responder accepts a write's W beat independently of its AW, so `arm_w_before_aw()` changes nothing on the wires |The responder accepts AW first; `arm_w_before_aw()` makes it accept the next write's W beat while that write's AW waits (the AW-only leg of `dtp_jtag2axi_backpressure_long_stall_test`)
|TAP reference model |The VIP next-state and TMS-path helpers (`next_jtag_state`, `jtag_tms_path`) in the scenario layer; the `OcahJtagChecker` is attached per scenario. `CHK-TAP-STATE` covers only the TMS steps and parked states a scenario judges (`tms_expect`, the reset scenarios' state samples, a SINGLE_OP held in Update-DR): the TCK cycles inside driver-executed scans are not checked, and the cross-trigger scenarios and the JTAG2AXI scenarios outside those held operations have no TAP-state check |`dtp_tap_fsm_checker`, an env subscriber on the VIP next-state model, records each illegal transition as a `CHK-TAP-STATE` failure with the expected and observed states
|Reset-count evidence |`CHK-RESET-COUNT` on the scenario's evidence checker: the attached `OcahJtagChecker` in the basic JTAG, debug-TDR, and scan scenarios, the cross-trigger checker in the cross-trigger scenarios, and the shared AXI scoreboard in the JTAG2AXI scenarios; an inline assertion where the scenario attaches none |`CHK-RESET-COUNT` on the cross-trigger checker in the cross-trigger scenarios, and elsewhere on the env `ocah_jtag_checker`, which judges its required IDs once per run
|Per-scan length evidence |`CHK-SCAN-COUNT`, `CHK-SCAN-IR-LEN`, and `CHK-SCAN-DR-LEN` on the family checker, from the DUT's Shift-x episodes against the scans the sequence issued, in the basic JTAG, debug-TDR, and scan scenarios; `dtp_sanity_test` judges each issued scan's length as it returns; `dtp_jtag_idcode_test` and `dtp_jtag_tlr_reset_test` record none, since their random TMS walks visit Shift-x outside an issued scan |`CHK-SCAN-IR-LEN` and `CHK-SCAN-DR-LEN` for each issued scan on the env `ocah_jtag_checker` in every scenario that keeps the env scan builder; the scan scenarios' family checker also requires `CHK-SCAN-COUNT`, `CHK-SCAN-IR-LEN`, and `CHK-SCAN-DR-LEN`
|One-sided env modules |`env/dtp_axi_agent.py` and `env/dtp_xtrig_agent.py` (the bridge responders and port monitors, the XTRIG CSR master and pin BFM), `env/dtp_xtrig_types.py` (cross-trigger register constants), `env/dtp_dbg_disable.py` (debug-disable names), `env/dtp_tap_device.py` (the primary-TAP TDR map the JTAG driver and the sequences share), `env/dtp_jtag_bypass_model.py` and `env/dtp_scan_model.py` (BYPASS and BSR loopback prediction), `env/dtp_stap_ds_agent.py` (the downstream STAP devices), and `env/dtp_tb_if.py` and `env/dtp_dv_cfg.py` (the Python views of `tb/dtp_tb_if.sv` and `tb/dtp_dv_cfg_pkg.sv`) |`dtp_env` composes the shared VIP agents and builds the downstream STAP devices itself; `dtp_types.svh` holds the instruction encodings, the cross-trigger constants, and the debug-disable paths; `dtp_jtag_base_test_seq` predicts the BYPASS delay and the BSR loopback; the TB interfaces and `dtp_dv_cfg_pkg` are used directly
|===

=== Adding a Scenario to the SV-UVM Realization

One VPLAN scenario, two implementations: the testlist entry's `module`
binding map carries both, and the same `--items` name selects either
realization. To add the SV-UVM twin of a cocotb scenario:

[arabic]
. *Sequence* — mirror the cocotb scenario sequence under the same basename:
  `uvm/seq_lib/<name>_seq.svh` for a scenario with a sequence of its own, or a
  branch of the family sequence's `scenario` dispatch for a family scenario.
  The sequence is a virtual sequence on the family layer that matches the
  scenario: `dtp_jtag_base_test_seq` for instruction-family scenarios
  (per-pass family evidence and scan-builder cross-checks),
  `dtp_jtag2axi_base_test_seq` for bridge scenarios (single and series
  operations, responder backdoor, error arming),
  `dtp_debug_tdr_base_test_seq`, `dtp_scan_base_test_seq`, or
  `dtp_xtrig_base_test_seq`. The scenario starts the reusable operations
  (`dtp_jtag_<op>_seq`, `dtp_jtag2axi_<op>_seq`, `dtp_axi_csr_<op>_seq`)
  through the base wrappers and never a VIP driver or interface; a missing
  operation becomes a new `_seq` on the VIP sequence API first. Start
  `body()` with `seed_scenario_rng()` so every pass replays from `--seed`,
  and read knobs from `test_cfg`. Add the include line to
  `uvm/seq_lib/dtp_seq_lib_pkg.sv`.
. *Test* — add `uvm/tests/<name>.svh` (file, class, and scenario share the
  name) extending `dtp_base_test`: override `create_scenario_seq()` and the
  loop-count knob hooks (`specific_loops_knob`, `group_loops_knob`), or
  `run_phase()` with the library's `run_single_scenario()` for a scenario
  whose rows are its seeded iterations, declare the scoreboard features and
  the required `CHK-*` IDs the scenario owns in `configure_test_cfg()`
  (`cfg.require_feature`, `cfg.require_jtag_ids`, `cfg.require_axi_ids`),
  and plumb scenario evidence handles in `plumb_scenario_seq()` after
  `super`. Add the include line to
  `uvm/tests/dtp_tests.sv`.
. *Testlist* — change the scenario's entry to
  `module = { cocotb = "<name>", uvm = "<name>" }`; the `uvm` value drives
  `+UVM_TESTNAME`.
. *Qualify* — the group's VCS run is green at the 16-pass floor, and each
  checker the scenario arms fails the run under its negative knob (the
  Checking Strategy above lists them).

=== Overlaying a Commercial VIP (`DTP_OVERLAY_TESTS`)

An optional protocol backend follows the Template Contract in the
`ocah_jtag_vip` README and reaches the SV-UVM build through the runner's
adopter overlay layer (`run_dv.py --overlay`, described in
`tools/dv/doc/run-dv.adoc`), which carries the backend sources, include
directories, gate defines, simulator flags, factory overrides, and runtime
environment. The bench runs unchanged without the overlay. The DTP specifics
are where each hook sits:

[cols=",,",options="header",]
|===
|Port |Interface instance carrying the vendor nest |`dtp_env` member the override replaces
|Primary TAP |`u_jtag_if` (`ocah_jtag_if`) |`m_jtag_env` (`ocah_jtag_master_env`)
|XTRIG CSR AXI-Lite initiator |`u_xtrig_master_if` |`m_xtrig_master_env` (`ocah_axi_master_env`)
|Observed SMC fabric AXI4 manager port |`u_m_axi_if` |`m_smc_axi_env` (`ocah_axi_env`)
|Observed SMC OTP and SEP OTP AXI-Lite ports |`u_smc_otp_axil_if`, `u_sep_otp_axil_if` |`m_smc_otp_axi_env`, `m_sep_otp_axi_env` (`ocah_axi_env`)
|Observed XTRIG CSR AXI-Lite port |`u_xtrig_axil_if` |`m_xtrig_axi_env` (`ocah_axi_env`)
|===

The observed ports share one class, so a type override of `ocah_axi_env`
replaces every one of them and an instance override names one member.
An adopter test class compiles in through `DTP_OVERLAY_TESTS` at the end of
`uvm/tests/dtp_tests.sv`: the overlay defines it to the quoted name of an
include file on one of its include directories. Select such a class on a
stock `--items` name with `--plusarg +UVM_TESTNAME=<class>`; the runner
emits the testlist-mapped test name only when none is supplied.
