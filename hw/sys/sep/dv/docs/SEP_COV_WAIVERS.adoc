[[sep-coverage-waiver-evidence]]
== SEP coverage waiver evidence

The RTL evidence behind every entry in `cov/config/vcs/sep_cov_scope.hier`,
`sep_unreachable_exclusions.el` and `sep_otbn_isa_scope_exclusions.el`.

The bar: a waiver needs the RTL to DECLARE the arm unreachable -- a tie, a
parameter, a constant, an unconnected port, or a generate arm that does not
elaborate. A testbench-side tie is not a waiver. An assertion guarding the arm
is the strongest evidence there is.

Each section below also carries a REJECTED list. Those are holes that looked
waivable and are not: they stay in the denominator, and closing them is
stimulus work. The rejected lists matter as much as the waivers -- they are
what stops the next pass from re-litigating the same candidates.

=== Note on `csrng_cmd_stage`

`modinfo.txt` reports line and toggle coverage merged across a module's instances.
`csrng_cmd_stage` has three instances; `gen_cmd_stage[1]` is structurally dead, but
`gen_cmd_stage[2]` (the software command port) is live and leaves the same lines
uncovered. Waiving the dead instance therefore raises the per-instance score
(32.58 % -> waived) without removing any merged module line. It is listed because it
is a genuine structural tie that a hierarchical waiver file should carry; it is
scored at zero so the totals stay honest.

== Rejected — stimulus gaps, not waivers

`otbn_decoder` (254 lines), `otbn_predecode` (167), `otbn_alu_bignum` (97),
`otbn_controller` (47)::
The uncovered lines are instruction-decode and ALU arms — `slli`/`srai` shift
decode, branch and jump forms, the BN vector element-length cases, the load/store
post-increment forms, the CSR/WSR address decode. The test firmware never executes
those instructions. No parameter or tie removes them: `otbn` is instantiated with
`Stub(1'b0)` and `RegFile(RegFileFF)` at

(`vendor/lowRISC/opentitan/upstream/hw/ip/otbn/rtl/otbn_core.sv:1039`,

it contributes no uncovered lines. The MAI ISPR/WSR decode in `otbn_decoder` and
`otbn_controller` (`:1317-1318`, `:1472`) is still reachable — the stub returns a
software error rather than blocking the decode. This is a stimulus gap.

`aes_ghash` (114 lines), `aes_control_fsm` (47), `aes_cipher_control_fsm` (47),
`aes_key_expand` (58)::
The uncovered lines are the GCM phases (`GCM_INIT`, `GCM_RESTORE`, `GCM_AAD`,
`GCM_SAVE`, `GCM_TAG`), the PRNG-reseed and key/data clear states, and the AES-192

`otbn_scramble_ctrl` (27 lines)::

The constant `seed_valid = 1'b1` does make the `seed_valid == 0` branch unreachable,
but that branch is a single assignment already covered by the `1` case. Stimulus gap.

= Pass 3 coverage waivers -- pulp-platform AXI fabric

== W-FAB-1: `u_axi_dw_upsizer_dma` read slots `t = 1..7` are structurally unreachable

*Scope*: `vendor/pulp-platform/axi/upstream/src/axi_dw_upsizer.sv`, the
`AxiMaxReads` generate replicates of the read transaction slot, for the single
SEP instance `u_axi_dw_upsizer_dma` (`hw/sys/sep/rtl/sep_dma_wrap.sv:272`,
`AxiMaxReads(8)` at `:273`). This is the remainder that was left open after the
constant-header waiver on the same instance.

*Claim*: no stimulus can put more than one read in flight on that upsizer's
slave port, so slots `t = 1..7` -- and the read-side arbitration between slots
-- can never be occupied.

*Evidence*: the upsizer's slave port is `axi32_mst_req`
(`sep_dma_wrap.sv:292`), driven by `u_axi_lite_to_axi_dma`
(`sep_dma_wrap.sv:263`), whose slave port `axi_lite_mst_req` is driven by
`u_tlul_to_axi_lite_dma` (`sep_dma_wrap.sv:245`). `axi_lite_to_axi` is
combinational, so the outstanding count at the upsizer equals the outstanding
count at `tlul_to_axi_lite`.

`hw/common/axi/tlul_to_axi_lite.sv` is a single-transaction FSM. From `IDLE`
(`:172`) a TL-UL `Get` moves it to `AXI_AR_REQ` (`:187`); `AXI_AR_REQ`
(`:197`) asserts exactly one `ar_valid` and moves to `AXI_R_ACK` on
`ar_ready`; `AXI_R_ACK` (`:206`) waits for `r_valid` and moves to
`TL_D_RESP`; `TL_D_RESP` (`:256`) returns to `IDLE` only on `tl_i.d_ready`
(`:270`). `tl_o.a_ready` is asserted in `IDLE` alone, so a second TL-UL
request cannot even be accepted until the first read has fully retired. The
FSM therefore holds at most one AR outstanding for the life of the design.

*Consequence*: the read-slot replicates above `t = 0` in
`u_axi_dw_upsizer_dma` are dead by construction of the converter chain in
front of them, not by stimulus gaps. Driving the DMA harder cannot reach them.

*Not waived*: the `t = 0` read slot, and the write path, stay in scope and are
driven by `sep_cov_axi_dw_upsizer_dma_test`. Waiving this does not touch the
other `axi_dw_upsizer`-typed converters in SEP, which have real AXI masters in
front of them.

== Converter FSM: the two ties that make most of it unreachable

`axi_dw_downsizer` carries 316 uncovered FSM transitions in run
`20260922_172031__vcs__all`, 29% of every uncovered FSM transition in the
design and the largest single block of it. Most of that is unreachable by
construction, for two separate reasons, and the rest is a stimulus gap that
stays in the score. Nine instances carry the metric: eight inside `sep_crypto`
and `u_sep_dma_wrap.u_axi_dw_downsizer_reg` outside it.

=== SEP-CRYPTO-SINGLE-BEAT: no burst reaches a crypto aperture

*Tie.* `hw/sys/sep/rtl/sep_crypto_axi_interconnect.sv:111-112` computes
`aw_is_burst = |aw.len` and `ar_is_burst = |ar.len`, and `:175` / `:205` route
any such request to `SepCryptoAxiErrSlv` BEFORE the address decode runs. No
beat of a burst reaches any accelerator, whatever its address. This is the
architecture, not an accident: `hw/sys/sep/doc/crypto.adoc:117-123` ("Single-Beat
Access Only") states it as a software contract, and
`hw/sys/sep/doc/fabric.adoc:29` states the general rule that AXI4-Lite slave
bridges convert bursts to single transactions.

*Measured, not assumed.* A probe drove the AES aperture from the SMN inbound
master with the inbound filter opened and `allow_burst=1`: single 4-byte and
8-byte beats returned OKAY with real data, while 2-beat and 4-beat reads at
both sizes returned DECERR on every beat with error-slave fill. The same shapes
were refused identically from the CPU-LSU master.

*What this waives.* The `R_SPLIT_INCR_DOWNSIZE` arm only builds a request when
the converted length `(len+1) * conv_ratio - align_adj - 1` exceeds 255
(`vendor/pulp-platform/axi/upstream/src/axi_dw_downsizer.sv:426`, taking the
split branch at `:430`), which on this bus needs `ARLEN >= 128`. `len` is
pinned to zero at all eight crypto instances, so that arm and its return to
`R_IDLE` cannot be entered.

*NOT waived, deliberately.* Three things stay in the denominator:

* `u_sep_dma_wrap.u_axi_dw_downsizer_reg`. It sits outside `sep_crypto`, so
  `:205` does not reach it. Its own argument would be the 336-byte extent of
  `SECURE_DMA_REG_MAP`, which cannot hold the 1032 bytes a split needs -- a
  weaker and different claim, and not made here.
* `R_IDLE -> R_INCR_DOWNSIZE` and `R_IDLE -> R_PASSTHROUGH`, with their returns.
  A SINGLE beat enters both: at `ARSIZE=3` the ratio is 2 and the converted
  length is `1*2-0-1 = 1`, well inside the limit, so the converting arm runs on
  an ordinary 64-bit access. These are dark because the suite drives 32-bit
  single beats everywhere, which is a stimulus gap and a test's job.
* The `BURST_WRAP` / `BURST_FIXED` arcs. The burst TYPE is independent of
  `len`, and the crypto demux filters on `len` alone, so a single-beat WRAP or
  FIXED reaches the converter. Reachability confirmed by reading, not driven
  yet.

=== SEP-ATOP-UPSTREAM-TIED: no atomic reaches SEP

*Tie, and it is one level up.* SEP is delivered inside SMU rather than
standalone, so its inbound port is only ever driven by `smu_axi_xbar`,
instantiated with `.ATOPs (1'b0)` at `hw/sys/smu/rtl/smu_axi_xbar.sv:131`.
`aw.atop` is therefore zero by construction in every real integration. That is
exactly what SEP's own `NoAtopAllowed` assumption states
(`axi_demux_simple.sv:570`, passed from `axi_filter_wrap.sv:242`), and the
assumption is satisfied upstream rather than merely assumed. SEP's own
`ATOPs(1'b0)` sites -- `sep_local_axi_xbar.sv:266`,
`sep_crypto_axi_interconnect.sv:275`, `sep_crypto.sv:560`, `sep_cpu.sv:596` --
are the places where the filter does not elaborate at all; the instances that
DO elaborate sit inside `axi_to_axi_lite` and inside `axi_err_slv` within the
width converters, and those are what this chain covers.

Citing an SMU file is deliberate: the waiver describes the system being
measured, not this repository in isolation.

*Provenance.* This supersedes the earlier reading recorded under F-FAB-2 below,
which treated the absorb path as reachable because nothing in SEP ties
`aw.atop`. That was correct about SEP alone and wrong about the delivered
system. The disposition was settled when the specification question was closed
with "SEP ships as part of SMU, not standalone", and the same branch resolved
the corresponding SMU question as an explicit out-of-scope waiver.

*What this waives.* The `R_INJECT_AW` arm of every `axi_dw_downsizer`, entered
only by `aw.atop[ATOP_R_RESP]` (`axi_dw_downsizer.sv:852`), and the FSM of the
31 `axi_atop_filter` instances that elaborate.

*NOT waived.* Nothing else changes: the filter instances that never elaborate
carry no coverage objects, and the absorb path's line coverage is a separate
claim from its FSM arcs.

== F-FAB-1: `sep_cov_xbar_wrap_burst_test` drives a shape its target declares unsupported (finding, not a waiver)

*Symptom*: the leaf reports PASS but the simulator prints four vendor
`$error`s per run, at
`vendor/pulp-platform/axi/upstream/src/axi_to_detailed_mem.sv:587` and `:590`,
"Non-incrementing bursts are not supported!"
(run `20260919_225443__vcs__all`, leaf log
`sep_cov_xbar_wrap_burst_test/seed_1797011571/attempt_0/logs/sep_cov_xbar_wrap_burst_test.log`,
times 613 ns, 626 ns, 782 ns, 938 ns, 951 ns, 1159 ns).

*Diagnosis*: the leaf sends WRAP to the SEP SRAM aperture. That aperture is
served by `u_sram_memory_interface.u_axi_to_mem.i_axi_to_detailed_mem`, whose
two assertions require `burst == BURST_INCR` for any `len > 0` on both AR and
AW. WRAP at this endpoint is not a legal-consume shape: the endpoint states it
does not support it, and it answers OKAY with wrong data rather than an error,
so the leaf is also driving an unspecified response.

*No SEP endpoint consumes WRAP.* The other two endpoint families refuse it as
well, but by design and without an assertion:

* the data-width converters (`axi_dw_downsizer.sv:462`, `:548`, `:924`) take
  `BURST_WRAP` to `*_PASSTHROUGH` with `throw_error`, which routes the
  transaction to their internal `axi_err_slv` (`axi_dw_downsizer.sv:190`,
  `Resp(RESP_SLVERR)`);
* `axi_to_axi_lite` contains `axi_burst_splitter`, which documents at
  `axi_burst_splitter.sv:22` that it does not support wrapping bursts.

*Recommended fix* (one tracked file, `sep_cov_xbar_wrap_burst_test`):
retarget the WRAP accesses from `SEP_SRAM_MEM_BASE_ADDR` to the crypto
aperture behind `u_otbn_axi_dw_converter`
(`hw/sys/sep/rtl/sep_crypto_axi_interconnect.sv:331`), and tolerate the
by-design SLVERR. The crossbar `aw.burst[1]` / `ar.burst[1]` toggle the leaf
exists for is reached identically on that route, and no assertion fires.

*Duplication note*: the converter-side WRAP and multi-beat FIXED arms are
already driven by `sep_cov_axi_dw_read_burst_shape_test` and
`sep_cov_axi_dw_write_burst_shape_test`, so if the retarget is not wanted the
leaf can be dropped without losing converter coverage; only the crossbar
`burst[1]` toggle on the SRAM route would go dark.

== F-FAB-2: a non-zero `AxATOP` cannot be presented from the testbench today (finding, not a waiver)

*Scope*: the 31 `axi_atop_filter` instances that do elaborate -- unconditional
inside `axi_to_axi_lite`, and inside each `axi_err_slv` that takes the default
`ATOPs` (`axi_err_slv.sv:45`, `if (ATOPs)`), including the one inside every
`axi_dw_downsizer` (`axi_dw_downsizer.sv:190`). Roughly 57 lines per instance
are dark for want of a non-zero `aw.atop`.

*Reachability*: the path is real. `smn_inbound_axi_req_i` (`hw/sys/sep/rtl/sep.sv:98`)
is a full AXI4 port with no ATOP tie -- only `sep_cpu.sv:467-469` ties ATOP --
so an inbound ATOP write would reach the filters through the ordinary fabric.

*What blocks it*: two testbench-side gaps, both outside the RTL.

. `hw/sys/sep/dv/tb/tb_top.sv:950` builds the inbound request with
  `smn_inbound_req_drive = '{default: '0}` and then assigns each field from a
  flat `m_axi_*` pin. There is no `m_axi_awatop` pin, so `aw.atop` keeps the
  `'{default: '0}` value. (`:879` does the same for the CPU-LSU splice.)
. The cocotb VIP has no ATOP either: `ocah_axi_struct_bridge.sv:13-14` states
  that the pulp AW `atop` field "has no interface member and is not carried",
  and `cocotbext.axi`'s master drives no such signal.

*Exactly what to change* (testbench only; no RTL change, and this is not a
backdoor -- it adds a master-side stimulus pin, it does not poke DUT state):

* in `hw/sys/sep/dv/tb/tb_top.sv`, declare a module-scope
  `logic [5:0] m_axi_awatop_drive = 6'b0;`
* inside the SMN-inbound `always_comb` (the block starting at `:949`), after
  the `'{default: '0}` line, add
  `smn_inbound_req_drive.aw.atop = m_axi_awatop_drive;`

A leaf then sets `cocotb.top.m_axi_awatop_drive.value` to an AXI atomic
encoding (for example `6'h30`, AtomicLoad-ADD, or `6'h20`, AtomicStore), issues
one single-beat write through the VIP master, waits for B, and clears the pin
to 0. AXI requires an atomic burst to carry an ID no other in-flight burst
uses, so the leaf must be the only traffic in flight while the pin is set, and
must use an otherwise unused AxID. The response is SLVERR by design
(`axi_atop_filter.sv:24`), so the leaf tolerates the error response and the
`m_axi` monitor already runs with `fail_decerr=False`.

This is filed rather than implemented because it needs a tracked file changed,
which this pass is not allowed to do.

== Question 1 -- AXI atomic transactions (ATOP) on the SEP fabric

=== Verdict: (c) SPEC IS SILENT

No specification text in the tree mentions AXI atomics in any form.

.Searches run, all over `.adoc`/`.md` outside `dv/` trees
* `atop`, `AXI atomic`, `atomic transaction|operation|access`
* `exclusive access`, `exclusive monitor`, `AWLOCK`, `ARLOCK`, `awatop`

Only two hits exist in the whole `hw/` documentation set, and neither is
about SEP's fabric:

* `hw/sys/smc/doc/dma.adoc:100` -- "Atomic Operations | Atomic command
  submission and status reading". This is about DMA command submission,
  not AXI5 atomic transactions.
* `hw/ip/memory_interface/README.adoc:167` -- a code listing of an AXI
  request struct that happens to contain `axi_pkg::atop_t atop;`. A field
  declaration in a quoted struct, not a statement of behaviour.

One near-miss that is not about atomics at all:
`hw/sys/sep/doc/crypto.adoc:528` -- "There is no atomic reset boundary

=== Answering the four sub-questions

Does SEP claim AXI4 atomic support on its inbound/SMN port?::
Neither claimed nor denied. `hw/sys/sep/doc/overview.adoc:21-22` lists
"Outbound AXI4 system bus master" and "Inbound AXI4 system bus slave"
with no attribute qualification. `hw/sys/sep/doc/fabric.adoc:19-33`
describes the fabric as "a hierarchical AXI4 crossbar fabric" and
enumerates exactly three things an AXI4-Lite bridge must handle -- bursts,
WSTRB, and AxID. Atomics are not in that list, and the list is about
Lite bridges, not about the top-level port.

Is there an interface contract with the SoC/SMU side about atomics?::
No. `hw/sys/sep/doc/port_table.adoc:76-77` is the only normative
statement about the inbound port:
+
----
|`smn_inbound_axi_req_i` | ... | SMN inbound AXI request (system bus
slave). | SMN fabric | Tie to '0 if unused
----
+
The "Integration note" column carries a tie-off rule for the unused case
and nothing about permitted transaction attributes. No document tells the
requester not to issue atomics, and none says SEP will refuse them.

If atomics are out of scope, what does SEP do on receiving one?::
Undefined by the documents. `hw/ip/axi_filter/doc/index.adoc` (section
"Blocked Transactions") specifies the filter's only documented error
behaviour, and it is address/attribute based, not atomic based:
+
"A blocked transaction is not dropped. It is steered to an AXI error
subordinate that terminates it with a `DECERR` response on `BRESP` or
`RRESP`, so the initiator always receives a response and the fabric never
stalls on a filter denial."
+
The match conditions the same section lists are `entry_enabled`, address
range, `prot[1]` vs `allow_ns`, source ID, and `allow_burst`. `atop` is
not a match input. So the spec does not say SLVERR, does not say DECERR,
and does not say undefined -- it never raises the case.

Does any spec text imply the atop filters SHOULD be exercised?::
No. No document names `axi_atop_filter` or any atomic-filtering function.
There is no documented feature whose verification would require driving a
non-zero `atop`.

== Question 2 -- out-of-bounds eFuse addresses

=== Verdict: (a) for the register spec vs the datapath RTL; (d) for the register spec vs the assertions

The specification *does* define behaviour for an out-of-range address, and
it defines it in the register documentation rather than the prose chapters.
The datapath RTL implements exactly that behaviour. The two assertions
forbid the stimulus that the specified behaviour exists to handle, so the
assertions contradict the spec.

=== The spec text

`hw/ip/efuse/regs/efuse_interface_ctrl.rdl` is the canonical register
source, and `hw/ip/efuse/doc/memmap.adoc` (section "eFuse Control
Registers") includes its generated output into the shipped IP
documentation. The generated copy is
`hw/ip/efuse/regs/gen/adoc/efuse_interface_ctrl.adoc`.

`EFUSE_INTERFACE_CTRL_STATUS`, register description
(`efuse_interface_ctrl.rdl:9`):

----
eFuse interface status and error-clear register. Reports the sense-done
flag and request/address error conditions, and provides write-1 strobes
to clear those errors.
----

Bit 5, `efuse_program_addr_error` (`efuse_interface_ctrl.rdl:28-29`,
generated at `efuse_interface_ctrl.adoc:27`):

----
Indicates that an invalid eFuse program address was used (address exceeds
the implemented eFuse size). The error must be cleared by writing 1 to
efuse_program_addr_error_clear.
----

Bit 6, `efuse_read_addr_error` (`efuse_interface_ctrl.rdl:34-35`,
generated at `efuse_interface_ctrl.adoc:26`):

----
Indicates that an invalid eFuse read address was used (address exceeds
the implemented eFuse size). The error must be cleared by writing 1 to
efuse_read_addr_error_clear.
----

Their clear strobes, bits 9 and 10 (`efuse_interface_ctrl.rdl:48` and
`:55`), name the condition again: "Clears the program out of bounds error
bit" and "Clears the read out of bounds error bit".

And `EFUSE_READ_CTRL.read_status`, bit 26
(`efuse_interface_ctrl.rdl:147`, generated at
`efuse_interface_ctrl.adoc:56`):

----
0: No Error.  1: Error. Set when read_go is asserted while read is not
enabled, the address is out of bounds, or the read request times out.
----

This is decisive on the three sub-questions:

Does the spec define behaviour for an out-of-range address?::
Yes. Three status bits and two clear strobes, with "address exceeds the
implemented eFuse size" stated as the setting condition. The behaviour is
a sticky, software-cleared error flag, not a refusal that goes unreported.

Or is the range a software contract the hardware need not police?::
No. The opposite. The hardware is specified to police it and to report
the violation. There is no text anywhere declaring a legal range that
software must respect on its own.

Is there a register description of the address-error status bit?::
Yes -- quoted above -- and it is fed. `efuse_interface_controller.sv:531-533`
computes `reg_interface_program_addr_oob` from the untruncated 16-bit CSR
field against `SHADOW_REG_BITS`, and passes it as `program_addr_oob_i`
into `efuse_program_interface.sv:39-41`, which returns
`program_addr_error_o` and takes `program_addr_error_clear_i`. The read
side mirrors it exactly at `efuse_interface_controller.sv:612-614` and
`efuse_read_interface.sv:34-36`. So this is not the "documented bit with
no reachable producer" case: the producer exists and is reachable. The
gap is that it is never *driven* in simulation, because of the assertions.

=== The contradiction

`efuse_interface_controller.sv:835` and `:839`:

----
`OCAH_OT_ASSERT(ProgramAddrValid_A, reg_interface_program_go |->
                !reg_interface_program_addr_oob, clk_i, !rst_ni)
`OCAH_OT_ASSERT(ReadAddrValid_A, reg_interface_read_go |->
                !reg_interface_read_addr_oob, clk_i, !rst_ni)
----

These are `assert property`, not `assume property`. An assert declares
that the condition cannot occur; the register spec declares that it can,
and specifies what the hardware reports when it does. Both cannot be
right. Since the register spec is the contract and the datapath
implements it, the assertions are the wrong artefact -- they should be
assumes at most, or deleted, so that the specified error path can be
covered without a `$assertoff`.

The RTL comment at `:829-833` says the same thing in the code's own
voice, but per the method note that comment is evidence about the code,
not about the specification. The specification evidence is the RDL field
descriptions quoted above, and they stand on their own.

The consequence for SMC is the visible symptom: SMC must `$assertoff`
both assertions behind a plusarg to run its boundary test, which means a
behaviour the shipped register documentation promises to software can
only be demonstrated with a piece of the RTL's own checking switched off.

=== A secondary documentation defect found along the way

`hw/ip/efuse/doc/programming.adoc` never mentions the address-error bits.
Its "Program Operation Sequence" step 3 enumerates `program_status` as a
four-value code:

----
* Read `program_status` field:
** 0: Success
** 1: Bad data (data was not 1)
** 2: Bad enables (program_enable not set or lock active)
** 3: Programming failure (verification failed)
----

`program_status` is a *one-bit* field in the RDL
(`efuse_interface_ctrl.rdl:105`, `program_status [26:26]`, "0: No Error.
1: Error"), and the example code at the top of the same file reads it as
`(EFUSE_PROGRAM_CTRL >> 26) & 0x3`, which straddles bit 27
(`program_enable`). The prose chapter is stale against the register
source. Neither the read nor the program sequence tells firmware to check
`EFUSE_INTERFACE_CTRL_STATUS` bits 5 and 6 after an operation, so a
documented error report has no documented consumer procedure.

This is a real gap but a different one from the question asked: the
register spec answers the question, the prose chapter has not been
updated to match it.

=== What to ask the designer

. Confirm that `ProgramAddrValid_A` and `ReadAddrValid_A` are wrong as
  asserts, given that `efuse_program_addr_error` and
  `efuse_read_addr_error` are documented, implemented and exist only to
  report the condition the asserts forbid. Should they be removed, or
  demoted to assumes for formal only?
. With the asserts gone or demoted, both address-error arms become
  ordinary coverable RTL and the negative test needs no plusarg. Confirm
  that is the intended end state before the coverage item is closed.
. Separately: should `programming.adoc` be corrected -- the stale
  four-value `program_status` enumeration and the `& 0x3` mask -- and
  should both operation sequences gain a step that reads
  `EFUSE_INTERFACE_CTRL_STATUS` bits 5 and 6?

= Metric scope: assertion coverage is not graded

`sep_sim_cfg.toml` compiles with `-cm line+cond+tgl+fsm+branch`. The `assert`
metric is absent by decision, not by oversight.

== Reason

SEP assertions are predominantly negative controls: the implication antecedent
is an illegal condition -- a protocol violation, an out-of-range field, a
forbidden state transition. VCS scores an assertion as covered only when it
records a successful attempt, which requires the antecedent to match. This
environment drives legal stimulus only, by policy, so a negative-control
assertion cannot record an attempt from any test the policy permits.

That makes the hole uncoverable by construction rather than by a stimulus gap,
which is the same standard the structural waivers in this document meet: the
design, not the testbench, decides the arm cannot be taken. Grading the metric
reports the absence of traffic the stimulus policy forbids.

Measured on the `sep-code-cov-v2a` database, assertion coverage was 52.64%
(10403 assertions, 4927 uncovered, 79 without attempts). Removing the metric
moves the headline to 60.38 and leaves every code metric unchanged. The gain of
about one point is a consequence of the decision, not its purpose.

== Where the metric is dropped, and why it is not the `-cm` list

The drop is a `-metric` argument on the report command, set by
`[coverage.vcs].report_cmd` in `sep_sim_cfg.toml`.

Removing `assert` from the compile-time `-cm` list does NOT work, and must not
be attempted: in this VCS version `-cm assert` does not gate assertion-coverage
collection. The report still carries an ASSERT column without it.

Worse, the `-lca -cm_common_hier` pair is what confines assertion coverage to
the `-cm_hier` scope. Dropping that pair alongside `assert` admits assertions
from the excluded library hierarchy, which pass trivially: ASSERT rose from
52.67 to 88.89 and the headline to a meaningless 64.46. Both flags stay in
`compile_args` for that reason, even though the metric is not reported.

== What this does NOT do

`-cm assert` governs coverage accounting only. Every assertion stays compiled,
evaluating, and able to fail a test. An assertion that fires still stops the
run and still reports. Nothing about the checking surface changes.

== Consequences

* `-cm_common_hier` and its `-lca` opt-in are dropped from both the compile and
  the report. Their only purpose was extending `-cm_hier` from the code metrics
  to assertion coverage; with no assertion metric there is nothing to scope.
* The report no longer renders assertion pages, so `asserts.txt` -- which also
  carried the Failure and Incomplete tallies -- is gone. Assertion failures
  still surface per test in the simulation log and in `results.xml`.

== When to restore it

Add `+assert` back if SEP gains an illegal-stimulus or error-injection
environment. At that point the negative controls become reachable and the
metric measures a real gap again.
