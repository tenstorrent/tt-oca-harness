== Verdict

*The Phase 1 + Phase 2 target has not arrived* under the definition in
`oss_dv_plan.adoc`.

That definition is: Phase 1 + Phase 2 together cover *> 60% of SEP*, where
"covered" means a spec-visible *iconic* behaviour has a `PROVEN` evidence-item,
and Phase 2 randomizes whenever the feature has a legal matrix or knob space
(`oss_dv_plan.adoc` lines 37–39).

What *has* arrived is the other, weaker reading: a strong *integration spine*.
The wires between blocks are mostly proven. Several IPs still do not have the
feature that makes that IP itself. Grade tables hide that distinction: a suite
can be 147 + 101 `PROVEN` with two hard `FAILED` spec-gaps and still miss
iconic-per-IP.

[cols="2,3",options="header"]
|===
| Reading of "60% of SEP" | After Phase 1 + 2 land?

| Integration / datapath spine (sideload, LC stitch, inbound-filter gate,
  DMA copy, entropy consume, CPU boot, SPI handshake)
| *Yes.* This is what Phase 1 was built to be, and it matches the internal
  environment's small cross-IP interconnect suite.

| Iconic feature per in-scope IP, randomized if possible, `PROVEN` in a kept
  Verilator log (`oss_dv_plan.adoc`)
| *No.* AES / HMAC / KMAC / SPI / SRAM / WDT / EDN-arbiter / DRBG
  segmentation are in that shape. Key Manager as a command device, eFuse
  program/lock, lifecycle demote product, OTBN as a compute engine,
  inbound-filter as a *matrix*, and live outbound remap are not.
|===

Do not mix the two. Closing Phase 2 while the 69-name backlog is still listed
as Phase 2 would report a pass on the spine and a fail on the plan.

== How this was judged

Three independent reads, then this synthesis.

. The architecture spec (`hw/sys/sep/doc/`) is the denominator. Iconic =
  the behaviour that makes the block itself. Corner = error, security
  permutation, negative matrix. Deferred / not-in-bare-SEP (AGP, local UART
  and GPIO, licensed SPI PHY, ROM patch, next-gen DMA-AES) are *out* of the
  60% count. ROM-*firmware* contracts (SPI boot path, integrity reject,
  forced-EDN RSA) are out of *this* VPLAN — ROM-FW owner — and are not a
  Phase 2 GAP this suite should execute.
. Phase 1 and Phase 2 plans were scored by evidence-item grade, not by test
  count. A `PARTIAL` or `GUARD` row is not a 60% credit. A backlog *name* is
  not coverage. After the cleanup, running checkers are `PROVEN` or `FAILED`
  only; a `FAILED` spec-gap is honest and is not a 60% credit either.
. The internal UVM environment is a per-IP matrix (hundreds of directed
  tests, coverage-bin close-out in the *same* bench). OSS is supposed to
  *compress* that matrix into iconic + random representatives, not re-port
  it. Where OSS already randomized a matrix (AES mode × key-size, HMAC
  variants, KMAC modes), that is the concept working. Where OSS kept a
  69-name breadth ledger, that is the internal concept leaking back in.

=== Conflict with `3693829a` (the plan was right)

This plan's own rule:

> strengthen the checker so it can fail, or move the unproven slice to
> Phase 3 with an explicit name.

`3693829a` broke that rule on the five KM alive-mode CHK5 rows: they moved
`PARTIAL` (bit-exact) → `PROVEN` (alive-only) with a longer note, and named
no owner for the excluded slice. The out-of-range and segmentation rows in
the same commit are fine — those took the second branch (`sep_drbg_gen_segmentation_test`
owns segmentation).

Resolution, which current Phase 1 text now states and this plan will keep:

* Bit-exact CHK5 under `rom_main` is infeasible (firmware pull order). That
  is not "strengthen."
* The excluded slice's *named owner* is the small KM ROM tests:
  `sep_esrc_e2e_smoke_test` and `sep_drbg_gen_segmentation_test` (and
  `km_rom_entropy` where loaded). Alive-mode on the sideload KATs is a
  different checker (live beats).
* Same-class leftovers that still need a name, not a description caveat:
  AES CTR round-trip re-runs ENCRYPT (keystream-determinism, not a DECRYPT
  opcode) — Phase 3 or an explicit accepted-identity, not a silent 9-cell

Do not execute §7 by writing more notes. Name the owner or strengthen.

== What not to do

These would move the suite *away* from `oss_dv_plan.adoc`.

* Do not implement the 69 Phase 2 backlog names as 69 tests. Most are
  overlap with a graded entry, or error/security matrices that belong in
  Phase 3 UVM.
* Do not start Phase 3 UVM coverage-closure until the Phase 2 *iconic*
  set below is `PROVEN`. A new bench that re-hits AES-ECB-256 or DMA
  SHA-256 is the overlap the plan already forbids.
* Do not treat a `PARTIAL` as done by writing a longer note. Either
  strengthen the checker so it can fail, or move the unproven slice to
  Phase 3 *with an explicit name* (or a named existing test). `3693829a`'s
  KM alive-mode re-scope is the worked example of the forbidden move;
  naming the small KM ROM tests as CHK5 bit-exact owner is the repair.
* Do not add GPIO, licensed SPI PHY, or vendor TRNG tests. The spec places
  UART/GPIO in SMC; OSS hygiene drops licensed leaves.

== Improvements

Each item is Why (the spec or plan gap) then How (the change) then Done-when
(the evidence-item that must appear in a kept Verilator log).
None of §1–§8 is work this PR still owes.

=== 1. Make Phase 2's document match Phase 2's job

Why::
`oss_dv_plan.adoc` says one iconic feature per IP, randomized if possible.
`verification_plan_phase2.adoc` still presents a 22 + 69 breadth ledger.
Reviewers will score the ledger, not the plan. The 69 names are not
evidence, but they *are* a worklist people will execute.

How::
Rewrite the Phase 2 front matter to an iconic checklist (the scorecard
above). Split the 69 names into three lists in that document. The split is
not a judgment call — each name maps through the scorecard:

* *compress* — the name's coverage intent is already a `PROVEN` or `FAILED`
  checker on a graded entry (`COVERED_BY` / `MERGED_INTO`). Delete from
  Phase 2.
* *iconic remaining* — the name *is* a scorecard row that is `GAP` or
  `PARTIAL` (the items in §2–§8 below). Keep the name only as that row's
  remaining work.
* *Phase 3* — error, security permutation, coverage-bin walk, or a corner
  of an already-`PROVEN` iconic row (AES CTR DECRYPT opcode, KM wipe,
  health tests, inbound negative product).

Stop calling Phase 2 "basic functional breadth."

Done-when::
Phase 2 names only tests that are implemented-and-graded or on the iconic
remaining list. Every former backlog name has a one-line map to compress /
iconic remaining / Phase 3. The 69-row table is gone. `oss_dv_plan.adoc` and
Phase 2 use the same words.

=== 2. Key Manager as a command device

Why::
The spec's KM identity is an isolated CPU behind a mailbox, with a command
set (generate, revoke, transfer, shred, …) and a KPV. Phase 1 proved
*consume*: a known key appears in an engine. That is the interconnect
seam. It is not KM. Internal coverage of KM is the largest IP folder for
exactly this reason.

How::
One RAND-REP, not a command-per-test matrix. Walk the discrete legal
commands that are frontdoor-stimulable on this DUT in one invocation
(generate, transfer to one engine already covered by a KAT, revoke or
shred, a documented illegal command → error). Seed legal continuous knobs
(slot, owner, length). Same config object for DUT and checkers. Mailbox
protocol (separator, depth, flush, IRQ RW1C) can be the same test or a
sibling RANDCFG — do not split it into five directed ports.

Done-when::
A kept log shows every required command cell, a value check that is not
the sideload KAT repeated, and mailbox IRQ RW1C to 0. Wipe stays Phase 3
(destructive security edge, already parked).

=== 3. eFuse program × lock

Why::
After sense-and-image, eFuse's iconic remaining behaviour is "a field can
be programmed, a lock sticks, a locked program is refused." Phase 1 proved
the controller can sense and that one program persists across resense. It
did not prove the lock contract. That is what makes OTP different from a
shadow RAM.

How::
One RAND-REP over a *legal* spare/test field (never `LC_STATE`, which the
spec says must not be R/W locked). Discrete cells: program while unlocked
→ resense sees it; set write-lock → further program refused; read-lock
behaviour as spec'd for that field. Seed which legal field and which bit.
Clear `EFUSE_PROGRAM_CTRL` after program (liveness: both enables starve
the read). Independent expected value from the generated fuse map, not
from the DUT shadow.

Done-when::
Log names the field, shows W1S persist, shows lock refusal, shows
post-clear read completing. Permission-neg × `secure_tm` permutations
are Phase 3.

=== 4. Lifecycle demote product

Why::
The spec's demote rule is the thing people get wrong: TEST_DEV forces
debug on, PROD *relaxes to honour DIS*, RMA/PROD_END ignore demote,
DEMOTE_1 and DEMOTE_2 are independent. Phase 1 used `DEMOTE_1` as a switch
to open the inbound filter and now also proves `DEMOTE_2` independence.
That still does not walk the product. The golden already exists
(`sep_lcc_golden.py`, spec Table 50).

How::
One RAND-REP: walk the discrete LC × demote × a small legal DIS subset in
one invocation. Check `feat_ctrl` against the spec golden, then one
*live* consequence (inbound filter skip vs force) so it is not
CSR-storage-only. Seed the DIS vector bits that the spec defines
(SEP_DBG, CHIPLET_DBG, SIP_DBG), not reserved bits.

Done-when::
Every required cell logs `feat_ctrl` vs golden *and* a live filter or
debug-gate observation. A PROD vector with a DBG_1 bit disabled must
*not* open that bit under demote (the #242 distinction).

=== 5. Finish randomization on tests that already exist

Why::
The plan says: pin directed, then upgrade; do not ship a one-point
stand-in for a matrix. Several Phase 2 entries already have the datapath
and a config object. Upgrading them is cheaper than new tests and is the
fastest 60% move.

How::
In place, same test names:

* `sep_fabric_inbound_filter_rule_matrix_test` — walk entry index ×
  read/write-allow × at least two windows. Keep live PROD sense. Keep the
  ownership-window assert hard (issue 1050); do not XFAIL it.
* `sep_dma_basic_test` — keep the mode/width walk; un-pin the seed;
  randomize legal addr/len/chunk under the alignment the RTL requires.
* `sep_crypto_per_ip_reset_isolation_test` — walk the remaining
  `SW_RESET_N` bits that this DUT actually isolates (do not claim KM if
  KM reset is a different mechanism).
* `sep_spi_ot_flash_cmd_rand_test` — neighbour-sector erase is in (10
  BFM opcodes). Either walk the remaining opcode cells the BFM can
  show, or drop the RAND-REP label. Dual/quad stay deferred if the BFM
  cannot show lanes; that is infra, not a silent pass.

Done-when::
Each upgraded test logs `CHK-RAND-REP` (or equivalent) with the cell
count, and the previous "one point" iconic hole is gone or explicitly
infra-gated.

=== 6. OTBN compute, not only key-dump

Why::
OTBN's iconic feature is "a program in IMEM runs and writes DMEM." Phase 1
proved a sideloaded key is visible to OTBN. Secure-boot RSA is real math
but ROM-FW, with EDN responses forced, so it does not prove the entropy
seam and is not this VPLAN's job. Without one honest compute cell, OTBN is
a memory window plus a key sink.

How::
One directed-then-RANDCFG test: load a tiny known program over 32-bit AXI
beats, wait `STATUS==IDLE` after wipe, run, compare DMEM against an
independent expected value. Release OTBN from SW reset before any KM
transfer if sideload is in the same test. If EDN is required, bring up
real entropy (do not add another `edn_force` on the proof path).

Done-when::
Log shows `ERR_BITS==0`, DMEM == golden, and EDN was either unused or a
real CHK5 consume. Forced-EDN RSA boot stays with the ROM-FW owner.

=== 7. Close the honesty gaps on tests we already run

Why::
DV bugs first. A `PROVEN` row whose checker cannot see the failure it
names is worse than a named GAP. Execute this section by strengthening or
naming an owner — not by lengthening the note (`3693829a` KM CHK5).

How::
No new IPs. Fix the checker or the stimulus:

* Entropy Generate segmentation: **closed** by
  `sep_drbg_gen_segmentation_test`. Do not triplicate onto the Phase 1
  entropy tests.
* Crypto EDN arbiter: **closed** by
  `sep_crypto_edn_round_robin_grant_test` (kept log `20260820_210207`).
* CHK5 bit-exact vs `rom_main`: **named owner** — small KM ROM tests.
  Do not re-open as a PARTIAL on the sideload KATs.
* AES CTR DECRYPT opcode: **name it** (Phase 3 corner, or an accepted
  CTR-identity note with that name). Do not leave it as a sentence inside
  CHK-CELL `PROVEN`.
* CHK1..CHK4 + CHK5 on every DRBG cross — still the standing rule. Known
  holes: `sep_crypto_edn_round_robin_grant_test`,
  `sep_aes_mode_keysize_rand_test`,
  `sep_kmac_mode_strength_rand_test`. Dual-sink bit-exact routing still
  needs the unported arbiter-assignment trace.
* `sep_cpu_dbg_reset_independence_test`: keep the dropped isolation claim
  dropped.
* Boot ROM firmware stays out of this VPLAN. Sources and enrollment
  live in `testlists/rom_fw.toml`; ROM-FW owner.

Done-when::
Each open item is either a new `PROVEN` line or an explicit Phase 3 name
in the Phase 2 document. No `PROVEN` row whose log cannot fail the slice
the test's name implies.

=== 8. Live outbound remap — only if it is still iconic after §5

Why::
The spec's fabric identity includes "programmed regions translate, and
the outbound filter can forbid a path." CSR R/W of those banks is
decode, not `[LIVE]`. If §5's inbound-filter upgrade plus Phase 1 alias
remap already carry fabric for the 60% bar, this can wait. If review
still counts fabric as a hole, it is one test, not a gap-matrix port.

How::
One RANDCFG: program one legal remap region, issue a beat that must land
at the translated address (observed on a real DUT port or a location the
frontdoor can read), then a forbidden outbound beat that must complete
with DECERR. No backdoor peek of the remapper.

Done-when::
A translated hit and a filtered miss, both attributed in the log. The
fabric gap-matrix and tail-closure names stay Phase 3.

=== 9. Phase 3 starts with a UVM smoke, not the leftover names

Why::
`oss_dv_plan.adoc` already assigns Phase 3 a different job from Phase 2.
Phase 1 + 2 are the cocotb baseline (*> 60%* feature coverage). Phase 3 is
a *new* UVM bench whose coverage job is combined code coverage *> 95%*
on the *union* of all three phases, plus corners those phases deferred.
Stimulus is coverage-driven against holes in a combined Phase 1+2 run.
A Phase 3 test whose bins Phase 1+2 already hit is rejected.

Starting Phase 3 from the 69 leftover *names* would do the opposite: it
would re-implement the spine (KM sideload, AES-ECB, DMA SHA-256) under a
new harness — the overlap rule — and it would treat a worklist as a
coverage map. The spec's measurement is bins, not names.

A UVM smoke first is the same evidence-item bar the cocotb suite already
uses: clock, reset, a register read, a kept Verilator log. Until that
exists, Phase 3 cannot prove it can produce a `PROVEN` row at all.

How::
After §1–§7: new UVM environment, same DUT, same quality bar
(evidence-items, force-free, Verilator close-out). First test is UVM
smoke (clock/reset/a register read). Then coverage-driven stimulus aimed
at bins Phase 1+2 never hit, plus the parked corners: KM wipe, token-error
matrix, health-test stress, inbound negative permutations, AES CTR
DECRYPT opcode, DMA abort/opcode-error. Secure-boot reject stays with the
ROM-FW owner unless that owner asks Phase 3 to carry it.

Done-when::
A UVM smoke `PROVEN` on Verilator. A written list of coverage holes taken
from a combined Phase 1+2 run — not from the 69-name list.
