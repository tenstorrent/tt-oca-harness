= SEP Open-Source DV Plan
:toc: left
:toclevels: 2
:icons: font
:source-highlighter: rouge

== Purpose

This is the high-level plan for verifying the SEP subsystem in the open-source
tree. It says *what each phase is for*, *how coverage is counted*, and *what
every test must satisfy*. Phase 1 is signed off. Phase 2 baseline (25 of
40) is closed. Phase 2+ is the active cocotb close-out (34 of 40 iconic
rows). Phase 2++ then activates the last unactivated blocks (38 of 40)
before UVM. Phase 3 is a future UVM environment, not an execute
list.

It is not a test-by-test contract. Those live in the per-phase verification
plans (see <<documents>>). A passing run is never a substitute for those
contracts.

== Phases

One DUT (`sep_wrapper`). Two environments. Phase 1, Phase 2, and Phase 2+
share the cocotb bench. Phase 3 is a new UVM bench. The jobs do not
repeat each other.

The architecture spec (`hw/sys/sep/doc/`) is the feature-scorecard
denominator. Iconic = the mode, command, or contract that makes that IP
itself. Excluded for OSS hygiene: peripherals outside bare SEP, and
proprietary IPs in nonfree. Also out of the count as deferred: AGP,
local UART and GPIO, ROM patch, next-gen DMA-AES, DCLS-in-SEP, and the
PCR vault. ROM-*firmware* contracts are out of this VPLAN — ROM-FW
owner. A backlog *name* is not a credit. A `FAILED` spec-gap is honest
and is not a feature credit either.

The scorecard is <<iconic-scorecard>> — feature coverage, not checker
count and not line coverage. The directed environment has no
SystemVerilog covergroups, and RTL SVA is compiled out under Verilator,
so this scorecard carries no *functional*-coverage number. RTL
*code* coverage is a separate number, collected by the nightly
Verilator run and thresholded nowhere yet. A graded test
with `PROVEN` checkers is evidence *behind* a feature row; it does not
by itself make the feature `PROVEN`. `PARTIAL` is a feature grade only
(a test exists, the iconic claim is not fully proven). Checker tables
stay binary (`PROVEN` / `FAILED`). A `FAILED` checker is not a feature
credit. Phase 2
link:verification_plan_phase2.adoc#iconic-remaining[iconic remaining]
holds the `GAP` rows. A Phase 1 leftover claim is listed in the Phase 2
handoff table and stays outside the signed-off Phase 1 contract. Phase 2
covers it: extend a Phase 2 test that already owns that IP/claim, or add
the named new Phase 2 test. Do not stretch the Phase 1 e2e / smoke entry
into a matrix.

Phase 1 and Phase 2 stay on the existing cocotb environment and finish
there. Phase 3 does not extend that environment — it starts a new UVM
bench when that work is scheduled.

=== Phase 1 — smoke + representatives

Bring the open-source bench up, then prove the widest datapaths with a short
list of representatives: fabric and memories, entropy and crypto sideload, DMA,
eFuse / lifecycle, CPU boot, the inbound filter.

The selection rule is *coverage per test*, not completeness per IP. A Phase 1
test that only walks CSRs is a smoke test. A Phase 1 representative must move
real data on a real path. Phase 1 is 10 smoke tests plus 21 representatives.

Detail: `verification_plan_phase1.adoc`.

=== Phase 2 — iconic features, by IP

Fill the IP-shaped holes Phase 1 left. Each IP gets its *iconic* feature —
the mode, command, or contract that makes that IP itself — not the full
internal matrix.

Randomize when there is something legal to randomize. A mode × key-size
product, a command set, a legal address or length range: walk every required
discrete cell in one invocation, and draw the legal continuous knobs from a
seeded PRNG. The same config object programs the DUT and the golden. Pin the
datapath directed first, then upgrade that test — do not ship a one-point
stand-in for a matrix. Skip randomization only when the feature has no legal
knob space (a strap, a single named handshake).

Cross-IP seams (arbitration, isolation, status-clear that spans two blocks)
belong here when they are basic; they are the work a per-IP bench
structurally cannot do.

A Phase 1 representative whose budget never hits an event the checker names
is closed here with a dedicated run, not by stretching that representative.
Generate-command segmentation is the standing example: ``EDN.BOOT_GEN_CMD``
resets to ``glen=4095`` and ``BOOT_REQ`` uses that register, so CHK4 never
sees ``gen_last``. Phase 2's `sep_drbg_gen_segmentation_test` programs
``glen=4`` into both the boot generate and the auto generate from the same
`SepEntropyCfg` that feeds the golden. The kept run completes the boot
Generate at that length, so `gen_last` fires and the trailing CTR_DRBG
Update is actually scored.

Phase 1 + Phase 2 is the cocotb baseline. Together they must reach at
least 18 of 40 in-scope iconic-feature rows, and they aim at 25 of 40
(`PROVEN` rows on <<iconic-scorecard>>). Completeness of that baseline
beats compression: merge, extend, and randomize to *reach* the target,
do not drop a real gap to keep the test count pretty.

Iconic representatives that are not yet coded stay *named* in
`verification_plan_phase2.adoc` until they are. That plan is the execute
list for new Phase 2 tests. Existing Phase 2 tests that shipped a
one-point stand-in for a matrix are strengthened in place. A leftover
from the Phase 1 handoff table is covered by that Phase 2 extend or by
the named new Phase 2 row — not by turning the Phase 1 representative
into the matrix. Former leftover names are mapped there to `COVERED_BY` /
`MERGED_INTO` or held for Phase 3. Do not port them as 69 directed
tests. There is no separate improvement worklist.

The active Phase 2+ attention set is entropy (ESRC / DRBG / EDN),
lifecycle, eFuse, Key Manager, and fabric.

Detail: `verification_plan_phase2.adoc`.

=== Phase 2+ — 34 of 40

Same cocotb environment. Eleven close-out rows are `PROVEN`
(program × lock, demote including lock, standalone RMA, live outbound
remap, ESRC watermark arming, eFuse set-only, ESRC lock and alert,
local-master alias, KM key/policy vault, SEC_DIS override, CSR bit-bash).
The scorecard is 33 of 40. Dead-space decode is a landed hard `FAILED`
( the filed RTL defect), not a
feature credit. Remaining: KM command set (parked) and two RTL closes
(inbound ownership; dead-space refuse). Phase 3 does not start until
this close-out finishes, and its first deliverable is UVM bring-up
plus smoke, not these rows.

Implementation order and the reachability / spec-vs-RTL traps live in
link:verification_plan_phase2.adoc#phase2-plus[Phase 2+]. Do not XFAIL
a spec-vs-RTL checker.

Detail: link:verification_plan_phase2.adoc#phase2-plus[Phase 2+].

=== Phase 2++ — block activation, 38 of 40

Same cocotb environment again. Phase 2+ closes the feature rows the plan
scoped; Phase 2++ closes a different kind of hole — blocks the DUT
instantiates and the suite never reaches at all. A block with no row
cannot appear as a `GAP`, so these were invisible rather than deferred,
which is why they are called out as their own phase.

Four blocks, four vehicles: the Adams Bridge post-quantum engine, the
entropy-pool aperture, the Key Manager CRC engine, and the KPV
scrambler. A fifth item, `sep_crypto_axi_isolate`, is an extension of the
existing per-IP reset test rather than a new vehicle.

Two of the four are reachable only from Key Manager firmware, so they
need dedicated KM ROM images in the pattern `km_rom_vault` already
established. That is the cost of activating them honestly; a SEP-side
poke at KM-private state would not be a proof.

Detail: link:verification_plan_phase2.adoc#phase2-plus-plus[Phase 2++].

=== Phase 3 — a new UVM environment

Phase 3 is a new UVM testbench. Its first deliverable is bring-up plus a
UVM smoke test, not a corner-case list. After smoke, stimulus is
coverage-driven: constrained-random traffic aimed at holes the cocotb
phases leave, plus the corner, error, and security cases those phases
defer.

Phase 3 is deliberately *low overlap* with the cocotb phases. It does
not re-implement those tests. A Phase 3 test whose bins are already hit
by the cocotb suite is rejected. Code-coverage close-out lives here.

Detail: `verification_plan_phase3.adoc`. Not an execute list.

== How coverage is counted

Two different numbers. Do not mix them.

Feature coverage (the cocotb phases)::
The iconic claim for each in-scope IP, graded on <<iconic-scorecard>>.
These are scorecard goals, not measurements: floor 18 of 40 in-scope
rows `PROVEN`, Phase 2 goal 25 of 40, Phase 2+ goal 34 of 40, Phase 2++
goal 38 of 40 before UVM.
There is no SystemVerilog covergroup number for this — the directed
environment has none, and RTL SVA is compiled out under the Verilator
acceptance flow. A `PARTIAL` feature (a test exists, the iconic claim is
incomplete) and a `GAP` (no test yet) are not credits. Per-test checker
tables are the evidence behind a row, not a substitute for it.

Code coverage::
A separate number. `[coverage.verilator]` in `sep_sim_cfg.toml`
instruments line, expression, and user coverage (toggle stays off), and
the nightly `no_cpu` regression collects it. No threshold is set:
`cov/config/<tool>/` holds no coverage policy, so no run gates on a
coverage percentage. Close-out is Phase 3 work. This number is not
feature coverage; do not mix them.

A feature Phase 1 already proves is a Phase 1 credit, even if a later
test could hit it too. Credit once, at the earliest phase that proved
it.

== Quality bar

These rules apply to every test in every phase, cocotb or UVM. They outrank
coverage count.

=== Evidence-items

Every testcase is audited against the verification plan as a list of
*evidence-items*. Each item is two parts, both required:

* *Check* — the condition that must hold, or the test means nothing.
* *Proof* — the exact evidence in a kept log that the check held. Verbatim
  where practical. A checker whose proof cannot be pointed at is not a checker.

A green `PASS` line is the entry condition for reading the evidence-items,
never a substitute for them. Grades, and the rules that reject a checker
outright, are in `verification_plan_phase1.adoc` (Evidence rules) and apply
unchanged to later phases.

=== DV bugs first

A broken DUT that still passes is a DV bug, and DV bugs are first priority —
ahead of new tests, ahead of coverage percentage.

These are DV bugs. They are not tolerated, documented around, or left for
later:

* *Fake pass* — the test prints `PASS` for a check that did not run, could
  not fail, or compared a value to itself.
* *Silent pass* — a missing handshake, a skipped step, or a vacuous loop
  does not fail the test; the log just never mentions it.
* *Said nothing* — a checker that only prints on failure. Absence of a
  `FAIL` line is not evidence. Success must emit a named proof line.
* *Weakened to pass* — expected value edited to match the DUT, a failing
  leg skipped, a check disabled by plusarg.
* *Hang instead of fail* — an unbounded wait that expires the sim budget
  with no attributed error.

A checker that cannot fail is deleted. It is never counted as proof about the
DUT. `GUARD` is not a legal verdict in Phase 1 or Phase 2.

=== Force-free

Drive and observe the DUT through its real buses and ports: the CPU-LSU AXI
master, the external SMN-inbound master, and the DUT's register and memory
apertures.

No `force`, deposit, or hierarchical peek on the proof path, except the
signed-off testbench hacks listed in `tb/tb_top.sv` (the CPU-LSU splice, memory
image init, observation-only probes). Adding to that list needs an explicit
sign-off and a recorded reason that no frontdoor exists.

A backdoor on the proof path, when a frontdoor exists, is a DV bug.

=== What else does not move

Acceptance engine::
Verilator is the close-out engine. Commercial simulators may be used to
iterate; they never close an evidence-item.

Independent expected values::
Goldens come from the specification, generated maps, or a model that does not
share source with the RTL under test. An expected value taken from a passing
DUT is not a check.

Liveness::
Every accepted request finishes in bounded time, including the illegal and
concurrent corners. A deadlock is a test failure with a named handshake, not a
timeout.

Open-source hygiene::
No licensed or proprietary IP in the build. No vendor or foundry paths in any
SEP filelist. TT-authored firmware that ships with its RTL is in scope; a
wrapper that depends on a licensed leaf is not.

== Environment in one page

DUT::
`sep_wrapper` — the `sep` core plus its IP integration (real memory macros,
generic eFuse model). The OpenTitan SPI host is inside the `sep` core; there
is no SPI pad mux in this build. A mux between the OCAH SPI host and a
proprietary SPI, when it exists only in a companion wrapper, is driven from
that repo.

Stimulus::
Two run modes, not two DUTs. `no_cpu` holds the CPU off and drives the LSU bus
from the testbench. `cpu` boots VeeR EL2 firmware from ICCM. The external
SMN-inbound master is a third *port*, used when the test must traverse the
inbound filter.

Phase 1 / 2 bench::
cocotb / PyUVM, already in this tree.

Phase 3 bench::
A new UVM environment. Same DUT, same quality bar, different stimulus
engine. It does not exist in this tree.
