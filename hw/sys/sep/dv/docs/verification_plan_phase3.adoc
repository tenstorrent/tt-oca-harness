*Nothing in this document is committed scope.* Phase 3 is a candidate list, not a

====

== Where Phase 3 sits

Phase 1 (smoke plus subsystem representatives) is closed, and its record is
`verification_plan_phase1.adoc`. Phase 2 (iconic features, by IP) is active, in
`verification_plan_phase2.adoc`. Phase 3 collects what both earlier phases explicitly
*deferred*: advanced corner cases, error and security permutations, and the deeper
cross-IP integration edges that are not the iconic feature.

[[direction]]
== Direction: Phase 3 moves to a new UVM testbench

Phase 1 and Phase 2 stay on the existing cocotb/PyUVM environment and are being finished
there. Phase 3 will not extend it. It will be built on a new UVM environment, and the
first deliverable is a *UVM environment bring-up plus smoke test*, not any candidate
below.

The reason is fit, not preference. Phase 3 work is error injection, stress, and security
permutation — which wants constrained-random UVM infrastructure rather than the directed
cocotb flow this environment is built around. The candidate list below is therefore left
as-is and unscheduled; it will be revisited once the UVM environment exists.

== What qualifies as Phase 3

A candidate belongs in Phase 3 rather than Phase 2 when it is *not the iconic
feature of an IP* — that is, when it is one of:

* an advanced corner case;
* an error or security permutation;
* a negative-path matrix;
* a cross-IP integration edge whose *basic* behaviour is already covered elsewhere, so
  only the advanced or integration slice is new.

It must also trace to at least one test in the reference suite, and be frontdoor-stimulable
on the bare `sep` build — or record the DV-infrastructure gate that stops it being so.

[NOTE]
====
Every candidate needs a full detail card — owner, testlist entry, reference trace, mapping
outcome, checker list, run and fuse mode, DV-infrastructure needs, and deltas from the
reference — *before* any code is written. Neither candidate below has one yet.
====

== Candidates

Both arrived from reference-suite updates that landed after this environment last synced.
Neither is an iconic-feature gap, so both are Phase 3 rather than Phase 2. No tracking issues
exist yet; owners should file them rather than inventing numbers here.

=== `sep_km_sw_emergency_wipe_test`

Key Manager and key distribution.

Reference provenance:: A Key Manager RTL feature adding software-controlled emergency
wipe, covered force-free in the reference suite by a frontdoor register write to
`sep_cpu_ctrl.KM_WIPE_CTRL.wipe_state`.

What is new:: A genuinely new SEP-to-KM integration edge. `sep_system_csr` drives
`KM_WIPE_CTRL.wipe_state` (offset `0x1A0`) into `sep_crypto` and on to
`key_manager.wipe_state_i`. A 0-to-1 edge zeroes every
KPV entry and raises the `WIPE_STATE` interrupt. There is no coverage of this today.

Qualification:: *Yes.* Key Manager Phase 2 planning explicitly deferred wipe. The feature
makes it frontdoor-stimulable, but it is a destructive security and lifecycle action across
an IP boundary — a security/integration representative, not the KM iconic
command-set row.

Proposed run mode:: `no_cpu` with the external or CPU-LSU frontdoor. Fuse mode depends on
whether the KPV pre-state needs real sense; a pure register-edge proof likely wants
`+skip_fuse_sense`.

Checker sketch:: Provision KPV state, drive `KM_WIPE_CTRL.wipe_state` 0-to-1 through the
frontdoor, then prove the KPV entries are zeroed and the `WIPE_STATE` interrupt asserts,
clears on write-one-to-clear, and reads back zero. Frontdoor only — no backdoor KPV read
without a recorded exception.

Effort:: Moderate. Needs new firmware or sequence plus a KPV-state observation path.

=== `sep_cpu_sram_aes_sram_test`

Crypto and entropy, CPU integration.

Reference provenance:: A reference-suite test in which real EL2 CPU firmware provisions an
AES-128 key through the production KM mailbox firmware (key load, then transfer/sideload to
AES), copies a payload SRAM-to-AES-to-SRAM through the AES data registers in both
directions against NIST vectors, then shreds the engine; a negative leg rejects the
non-sideload case; a passive monitor watches the KM-to-AES private bus.

What is new:: The crypto correctness is already covered *more strongly* by Phase 1's
`sep_km_aes_sideload_kat_test` (a KM-to-AES sideload consume-proof with an ECB round trip
and isolation) and by Phase 2's `sep_aes_mode_keysize_rand_test`. The only genuinely new
intent is the `cpu` run mode — real EL2 firmware orchestrating a KM-mailbox sideload and an
AES computation in one boot — and the SRAM-to-AES-to-SRAM CPU data-movement path, with
sentinel checks and a negative disable leg in CPU firmware.

Qualification:: *Yes, lower priority.* Not an iconic-feature gap, since the crypto is covered
more strongly already. It is a CPU-firmware integration representative, deferred by
construction.

Proposed run mode:: `cpu` (real EL2 firmware boot) with the KM ROM image;
`+skip_fuse_sense` unless the KM path needs real sense.

Required delta from the reference:: Replace the reference suite's backdoor key-bus monitor
with the frontdoor isolation proof `sep_km_aes_sideload_kat_test` already uses — the
`SW_RESET_N` read-back plus the public `KEY_SHARE` reading zero. No new backdoor without
sign-off. The infrastructure exists: KM ROM boot, `env/sep_aes_golden.py`, and the CPU-boot
harness are all in place, and AES-128 is a small extension to the existing golden.

Effort:: Large. Needs new CPU firmware, the SRAM-AES orchestration, the negative leg, and
the isolation proof.

== Audited and not carried forward

From the same reference-suite sync, these changes were checked and need no work here:

* a SHA-384 addition that was reverted upstream — net zero;
* a Key Manager firmware HMAC-SHA256 split — the committed firmware image is unaffected and
  the ROM image is rebuilt automatically;
* a boot-ROM startup-flow change — this environment's responder is self-contained;
* hardening of a TRNG, SPI-reset and lifecycle-to-KM vacuous pass — the ports here already
  fail closed, or the test is not ported;
* a token rename and the retirement of a SHA error leg — nothing here references either.

One forward guard worth recording: a future Key Manager mailbox-interrupt representative
must model the aggregated interrupt as *masked* — `IRQ_STATUS & IRQ_ENABLE` — per the
specification back-port that introduced it.
