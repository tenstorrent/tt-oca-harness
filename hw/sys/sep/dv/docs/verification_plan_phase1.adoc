:toc: left

:icons: font

== Purpose and scope

This document is the verification contract for *Phase 1* of the SEP open-source DV
environment: the bring-up smoke suite plus the twenty-one representative subsystem tests
selected to carry the widest coverage per test.

Phase 1 is *closed*. Every testcase listed here is implemented, runs in the
cocotb/PyUVM + Verilator flow, and is expected to pass in regression — with one
exception, recorded in <<open-items>>: `sep_rom_non_secure_boot_test` needs a boot-ROM
image this repository does not build, so a clean checkout cannot run it. This document
records what each test *proves*, and the exact evidence in its log that proves it.

What this document is *not*: it is not a status tracker and not a coverage percentage.
There is no functional-coverage number for this environment: it has no SystemVerilog
covergroups at all (`cov/config` and `cov/sv` are empty placeholders), and RTL and
vendor-IP SVA are compiled out under the Verilator acceptance flow. Coverage here means "this
behaviour has a test whose log demonstrably proves it", nothing more.

Each testcase in this plan traces to a reference test in Tenstorrent's internal SEP
verification suite. Those references are recorded internally and are deliberately not
reproduced here.

=== Acceptance flow

Verilator is the acceptance engine. A testcase is credited only when a kept Verilator
log shows the evidence named in its checker table. Faster commercial simulators may be
used during development, but a result from one of them never closes a checker.

One property of that flow shapes how every result in this document should be read: RTL
assertions are compiled out. The shared native build profile — used by both the
cocotb and UVM flows — defines `DISABLE_ASSERT`
and `COMMON_CELLS_ASSERTS_OFF`, so no SVA in the design or in the vendored IP
participates in any run recorded here. Nothing is watching except the checks these
tests make explicitly. Where an entry says a property is proven, that is the whole of
the proof — there is no assertion layer underneath catching what the checkers miss.

== How to read a testcase entry

Every entry has the same three parts.

Description::
What the test proves, in one paragraph — the behaviour under test and the path it
exercises. Not a restatement of the steps.

Steps::
The ordered stimulus the test applies, as a table. Every step carries its own
*Proof* — the log evidence that this step actually happened — and a status of
`LOGGED` or `NOT-LOGGED`.
+
--
A step marked `NOT-LOGGED` is not a defect in the design; it means the run leaves no
trace that the step executed. That matters because a step that silently stops
happening — a configuration write dropped by a refactor, a loop that exits
immediately — would not change the result. Closing these is a logging change to the
test, not a change to what it verifies.
--

Checkers::
A table of *evidence-items*. Each row is one checker and has three parts:
+
--
* *Check* — the condition that must hold for the test to mean anything.
* *Proof* — the exact evidence the kept log must contain. Verbatim log text where
  practical. A checker whose proof cannot be pointed at in a log is not a checker.
* *Status* — the grade from the most recent audit (see <<evidence-rules>>).
--

A test PASS is the entry condition for reading the checkers, never a substitute for
them. A green run whose checkers cannot be located in the log is an unproven test.

[[evidence-rules]]
== Evidence rules

Checker status uses these grades:

[cols="1,4",options="header"]
|===
| Status | Meaning

| `PROVEN`
| The named proof is present in a kept Verilator log for the current test source.

| `PARTIAL`
| The checker holds, but a named sub-condition was not exercised in the graded run.
  The unexercised part is stated in the row.

| `GUARD`
| The checker cannot fail on any DUT, because it guards a *build* precondition rather
  than a hardware property — a linker-script alignment, a generated-register tie-off.
  Kept because it does catch a regression in the thing it covers, graded separately so
  it is never read as evidence about the design, and excluded from the proof count.

| `INSUFFICIENT-EVIDENCE`
| The check is implemented but the log does not carry enough to confirm it.

| `NOT-RUN`
| The checker exists in the plan but no run has graded it.

| `STALE`
| The proof is present in a kept log, but the artefact that produced it cannot be
  rebuilt from this repository, so the grade describes something a reader cannot
  reproduce.

| `FAILED`
| The proof contradicts the check.
|===

A checker is rejected outright, regardless of run result, if it:

* cannot fail — it asserts something true by construction, or compares a value to itself.
  The single exception is a checker that guards a *build* precondition rather than a DUT
  property — a linker-script alignment, a generated-register tie-off. Those are kept
  because they catch a real regression in the thing they do cover, but they are graded
  `GUARD`, never `PROVEN`, and they are excluded from the proof count. A checker that
  cannot fail and has no such role is deleted, not reclassified;
* is vacuous — its loop or conditional body never executed in the graded run, and the
  test does not prove that it did;
* was weakened to pass — an expected value edited to match observed hardware, an exact
  comparison relaxed, a failing leg skipped, or a check disabled by plusarg;
* proves through a backdoor where a frontdoor path exists, without a recorded exception;
* depends on a forced or deposited value on the proof path itself.

Every test therefore carries a *non-vacuity* obligation: the log must show the checking
actually ran, typically as a non-zero comparison count.

A proof string must also be *reproducible*. Quote text that any correct run produces,
never a value that belongs to one particular run — a seed, anything derived from a seed
such as the clock period, or a count that depends on how much traffic happened to flow.
Where the interesting thing is a number that varies, quote the invariant instead and say
that the number varies. Reproduce spacing and column padding exactly, since a proof that
does not match under a literal search is not a proof anybody can check. After editing
this file, check every string it quotes against the corresponding kept log — mechanically,
not by eye. A whole class of the proofs in an earlier revision of this document could never
have matched any run, and nobody noticed because nobody grepped them.

The same obligation applies to stimulus. Every step must be traceable to a line in the
kept log, so the plan can be checked against what the test actually did rather than
against what it was written to do. Steps that cannot be traced are listed as
`NOT-LOGGED` and collected in <<open-items>>.

== Testcase entries — bring-up and smoke

Eleven short tests that prove each memory, peripheral and register block is
reachable and responds. They are the first thing to run after any build change:
if one of these fails, no result from the representative tests below is meaningful.

[[sep_axi_smoke_test]]
=== sep_axi_smoke_test

[horizontal]
Tier:: Smoke
Run mode:: `no_cpu`
Testlist:: `system.toml`

==== Description

Proves the SEP register fabric decodes and responds on the CPU LSU bus with no CPU
booted. A driver on the LSU splice reads a register with a known non-zero reset value —
so a correct result cannot be produced by an unmapped address returning zeros — then
writes and reads back four read/write registers chosen to have no hardware side effects
and no external-memory dependency. This is the shortest path that exercises the whole
chain from filelist through elaboration to a responding register block, which is why it
is also the CI gate.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode; the cocotb AXI driver owns the CPU LSU splice.
| `SEP timing: sys_clk_period=` then `Skipping fuse sense`
| LOGGED

| 2
| Read `SEP_LOCAL_BASE_ADDR` and require its reset value.
| `AXI read  0x10a300c8 -> 0xd0000000 (ok=True resp=0)`
| LOGGED

| 3
| For each of four read/write registers, write a distinct pattern and read it back, masking the comparison to the implemented field bits.
| Four write/read pairs, e.g. `AXI write 0x10a30178 <- 0xdeadbeef (ok=True resp=0)` and `AXI write 0x10a30180 <- 0xbadc0de (ok=True resp=0)`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-DECODE
| The reset-value read returns the specified non-zero reset value, proving real decode
  rather than an unmapped-address zero.
| `read check OK @ 0x10a300c8 = 0xd0000000`
| PROVEN

| CHK-WR-RB
| Each read/write register returns exactly the pattern written, masked to its
  implemented bits. Note the `SEP_NMI_VEC` pattern already has bit 0 clear, so the
  reserved-bit mask is a no-op here and reserved-bit behaviour is not exercised by this
  or any other test.
| `read check OK @ 0x10a30180 = 0x0badc0de` +
  `read check OK @ 0x10a30170 = 0x000000a5` +
  `read check OK @ 0x10a30020 = 0x00000007`
| PROVEN

| CHK-RESP
| Every read beat returns `OKAY` and no transaction decode-errors. The cited tally
  covers read beats; write responses are enforced by the scoreboard line under
  CHK-NONVAC, which fails any non-OKAY item.
| `SEP AXI monitor [s_axi]: 5 R beats, 4 B resps; R-resp tally OKAY=5; 0 expected DECERR; 0 errors`
| PROVEN

| CHK-NONVAC
| The scoreboard performed a non-zero number of value comparisons.
| `SEP scoreboard: 9 checks (5 value-verified, 0 expected-error), 0 errors`
| PROVEN
|===


[[sep_address_map_test]]
=== sep_address_map_test

[horizontal]
Tier:: Smoke
Run mode:: `no_cpu`
Testlist:: `system.toml`

==== Description

Sweeps the SEP control register map over the CPU LSU bus. 31 of the block's 32
registers are visited — `KM_WIPE_CTRL` is not, because a write to it wipes key
material — and 21 registers are read and required to equal the reset value the generated
map exports before anything is written to them; four of those are written and restored
later in the same sweep. The three registers the sweep classifies as hardware-driven
(`REFERENCE_COUNTER`, `SEP_TEST_CTRL`, `SEP_FUSE_SENSE_STATUS`) get a response check;
the reference counter additionally gets a value check, since this testbench does not
drive its reference clock and it therefore cannot advance. Pure
read/write registers store and return what was written, and the base/size address
registers survive a write, readback and restore without disturbing decode. This is
the broadest register-level check in the suite and the reason the other tests can
assume the map is correct.

Three of the read/write registers are storage-only reserved placeholders with no
software-visible behaviour. They are still swept, because proving they store is the
only claim that can honestly be made about them.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode.
| `SEP timing: sys_clk_period=` then `Skipping fuse sense`
| LOGGED

| 2
| Read both halves of the reference counter and require the reset value. The counter's
  reference clock is not driven by this testbench, so it cannot advance here — if that
  clock is ever connected this expectation has to become a two-read increment check.
| `CHK-REFCNT-READ PASS: REFERENCE_COUNTER readable as 0x00000000_00000000`
| LOGGED

| 3
| For each pure read/write register: write a pattern, read back masked to the implemented bits, restore the original value.
| Write/readback/restore pairs, e.g. `AXI write 0x10a30028 <- 0xbadc0df (ok=True resp=0)` followed by `AXI write 0x10a30028 <- 0x0 (ok=True resp=0)`
| LOGGED

| 4
| For each base/size register: write, read back, restore.
| `AXI write 0x10a300c0 <- 0x12340000 (ok=True resp=0)` then restore `<- 0x0`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-REFCNT-READ
| Both halves of the reference counter read back the reset value exported by the
  generated map. This was previously read with no expected value at all, so the row
  reported whatever the DUT returned.
| `CHK-REFCNT-READ PASS: REFERENCE_COUNTER readable as 0x00000000_00000000`
| PROVEN

| CHK-RW-READBACK
| Every pure read/write register returns exactly what was written, masked to its
  implemented bits, and is restored afterwards.
| `CHK-RW-READBACK PASS: 5 pure-RW CSR(s) write->masked readback->restore`
| PROVEN

| CHK-BASEADDR-RW
| The base and size registers accept a write, read back, and restore cleanly.
| `CHK-BASEADDR-RW PASS: 3 SEP base/size CSR(s) write->readback->restore`
| PROVEN

| CHK-NONVAC
| The sweep performed a large, non-zero number of value comparisons.
| `SEP scoreboard: 77 checks (41 value-verified, 0 expected-error), 0 errors`
| PROVEN
|===

[[sep_rom_non_secure_boot_test]]
=== sep_rom_non_secure_boot_test

[horizontal]
Tier:: Smoke
Run mode:: `cpu`
Testlist:: `cpu.toml`

==== Description

Boots the real boot ROM image rather than a test firmware and lets it run its
non-secure startup flow. The ROM announces each stage it reaches, so the console
trace is the evidence that the ROM executed its memory-check stage on the real core and
that the copied payload ran afterwards. The markers are required as a set, not in a
sequence — nothing checks their order — and the fuse-check marker comes from the payload
after handoff, not from the ROM.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Stage the boot ROM image and release the CPU with the ROM as the reset vector.
| `SEP fuse sense done at cycle 804` (real sense, no skip)
| LOGGED

| 2
| Let the ROM run its non-secure boot path.
| `ROM> BOOT_SECONDARY` then `ROM> WAIT_SMC_MANIFEST` on the ROM's virtual console
| LOGGED

| 3
| Collect the stage markers it prints.
| `CHK-ROM-STAGES PASS: all 5 required ROM/BL1 stage markers observed`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-ROM-STAGES
| The ROM announces its memory-check and hash-validation stages, and the copied payload
  announces its own stages after handoff — so the set evidences both that the real ROM
  ran and that control transferred. These markers are now required, not merely printed:
  the whole virtual console could previously go dark and the run would stay green.
  Note the hash markers show the ROM *reports* validating the manifest and payload;
  nothing here corrupts either, so rejection is untested. What the set does prove is
  that the real ROM image executed on the core rather than a stub.
| `CHK-ROM-STAGES PASS: all 5 required ROM/BL1 stage markers observed` — the run
  additionally logs each marker as a `ROM> ...` line
| PROVEN
|===

[[sep_sram_smoke_test]]
=== sep_sram_smoke_test

[horizontal]
Tier:: Smoke
Run mode:: `no_cpu`
Testlist:: `memory.toml`

==== Description

Proves the SEP local fabric routes to the SRAM and that the SRAM stores. A read of
an untouched location returns zero, a 64-bit write stores and reads back exactly,
and a narrow 4-byte second write to the upper half changes only that half — which shows
byte-lane handling rather than a whole-word overwrite.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode.
| `SEP timing: sys_clk_period=` then `Skipping fuse sense`
| LOGGED

| 2
| Read the target location and require zero.
| `read check OK @ 0x10000100 = 0x0000000000000000`
| LOGGED

| 3
| Write a 64-bit pattern; read it back.
| `AXI write 0x10000100 <- 0x123456789abcdef (ok=True resp=0)` then `read check OK @ 0x10000100 = 0x0123456789abcdef`
| LOGGED

| 4
| Write a 32-bit pattern to the upper half; read the full 64 bits back.
| `AXI write 0x10000104 <- 0xfeedface (ok=True resp=0)` then `read check OK @ 0x10000100 = 0xfeedface89abcdef`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-RESET-READ
| A read of the target location before any write returns zero with an `OKAY` response —
  the decode and liveness anchor for the write/readback that follows. This is not an SRAM
  reset property: the macro has no array reset, and the zero comes from simulator memory
  initialisation, so this leg would not reproduce on silicon.
| `read check OK @ 0x10000100 = 0x0000000000000000`
| PROVEN

| CHK-STORE
| A 64-bit write stores and reads back exactly.
| `read check OK @ 0x10000100 = 0x0123456789abcdef`
| PROVEN

| CHK-LANE
| A genuine 4-byte beat (`AxSIZE=2`) to the upper half changes only those lanes; the
  lower four survive. This is the only narrow-`AxSIZE` access in the suite — every other
  test on this bus drives full-width beats.
| `read check OK @ 0x10000100 = 0xfeedface89abcdef`
| PROVEN

| CHK-RESP
| Every read beat returns `OKAY` and no access decodes to `DECERR`. The cited tally
  covers read beats only — write responses are counted but their code is inspected for
  `DECERR` alone, so an `SLVERR` on a write would leave that line unchanged. Write
  responses are enforced separately, by the scoreboard line quoted under CHK-NONVAC.
| `3 R beats, 2 B resps; R-resp tally OKAY=3; 0 expected DECERR; 0 errors`
| PROVEN
|===

[[sep_otbn_mem_smoke_test]]
=== sep_otbn_mem_smoke_test

[horizontal]
Tier:: Smoke
Run mode:: `no_cpu` (`target = "lsu_stub_all_live"`, `+skip_fuse_sense`)
Testlist:: `crypto.toml`

==== Description

Proves the OTBN instruction and data memories are writable and readable over the CPU
LSU frontdoor at the 32-bit access width OTBN's own program-load driver uses. The test
establishes from the DUT that OTBN is not locked and is not wiping these memories,
writes a word to each, reads it back, requires both write responses to be `OKAY`, and
separately confirms through the memory request counters that exactly the issued
accesses arrived — so a read that happened to match a preloaded value cannot pass on
its own, and neither can an access pattern other than the one the plan describes.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode.
| `SEP timing: sys_clk_period=` then `Skipping fuse sense`
| LOGGED

| 2
| Read OTBN `STATUS` and require it to be neither `LOCKED` nor a memory-wipe state.
| `OTBN memory-access precondition OK: STATUS=0x00000004 (not LOCKED, not executing)`
| LOGGED

| 3
| Write a known word to the OTBN instruction memory base; read it back.
| `AXI write 0x10904000 <- 0x13 (ok=True resp=0)` then `read check OK @ 0x10904000 = 0x00000013`
| LOGGED

| 4
| Write a known word to the OTBN data memory base; read it back.
| `AXI write 0x10908000 <- 0xa5a55a5a (ok=True resp=0)` then `read check OK @ 0x10908000 = 0xa5a55a5a`
| LOGGED

| 5
| Read the instruction and data memory request and write counters.
| `OTBN memory counters: imem=2/1 dmem=2/1`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-IMEM
| The instruction-memory word reads back exactly as written.
| `read check OK @ 0x10904000 = 0x00000013`
| PROVEN

| CHK-DMEM
| The data-memory word reads back exactly as written.
| `read check OK @ 0x10908000 = 0xa5a55a5a`
| PROVEN

| CHK-ARRIVED
| Both memories saw exactly the issued accesses — 2 SRAM requests each, of which 1 is
  a write — proven by the counters rather than by the readback alone.
| `OTBN memory counters: imem=2/1 dmem=2/1`
| PROVEN

| CHK-WRESP
| Both write responses are `OKAY`.
| `AXI write 0x10904000 <- 0x13 (ok=True resp=0)` and `AXI write 0x10908000 <- 0xa5a55a5a (ok=True resp=0)`. A non-OKAY response would instead produce a `SCOREBOARD FAIL:` record and fail the run, so that string is deliberately absent from a passing log
| PROVEN

| CHK-PRECOND
| OTBN is neither `LOCKED` nor executing when the memories are accessed, so a bus access
  to them is legal. This is an exclusion, not an exact-state check: any other `STATUS`
  value is acceptable. (An earlier revision excluded the two scramble-key-request states
  instead and permitted execute, which was backwards — bus access is diverted and
  flagged illegal only while OTBN executes.)
| `OTBN memory-access precondition OK: STATUS=0x00000004 (not LOCKED, not executing)`
| PROVEN
|===

[NOTE]
====
OTBN sits in `StatusBusySecWipeInt` (`0x04`) for the whole of this test: leaving that
state needs EDN entropy to reseed URND, and the `no_cpu` smoke configuration never
brings EDN up. That is harmless here — the internal wipe does not touch IMEM/DMEM —
which is why every access completes `OKAY`. Reaching `IDLE` would require bringing up
the entropy complex, which belongs to the sideload tests, not to a memory smoke test.

Step 2 deliberately excludes only the states that would invalidate the access —
`LOCKED`, and `BusyExecute`, the state in which the core owns these memories and a bus
request is diverted to a dummy response and flagged as an illegal bus access. It does
not pin `STATUS` to `0x04`: if OTBN later reaches `IDLE`, that is a better
state for this access, not a regression, and the test should not fail on it. So the
step catches OTBN coming up locked or wiping these memories; it does not detect a
change from `BusySecWipeInt` to `IDLE` or `BusyExecute`, and is not intended to.

Accesses drive `AxSIZE=2` (4-byte beats). These memories are 32-bit SECDED words and
reject the 64-bit default beat with `SLVERR`; the 32-bit width is what OTBN's own
program-load driver issues. No enrolled test covers that rejection — it is stated here
as design context, not as a verified claim.
====

[[sep_efuse_image_test]]
=== sep_efuse_image_test

[horizontal]
Tier:: Smoke
Run mode:: `no_cpu`, real fuse sense
Testlist:: `efuse_lcc.toml`

==== Description

Proves the write-one-to-set programming path into one-time-programmable memory: bits
that are burned read back as one directly from the array before any re-sense,
programming two bits in the same word does not clobber the earlier one, and after a
cold re-sense the shadow equals the original image plus exactly the bits that were
burned. Together these establish that programming is real, additive, and persistent —
the three properties every later lifecycle test assumes.

[NOTE]
====
The OTP array behind the fuse-command interface is a simulation-only behavioural bank,
not an OTP macro. Two of the properties this entry reads as proven are properties of
that model rather than of hardware: write-one-to-set additivity is OR-only by
construction in the generated model, so the "bank that overwrites instead of ORs" that
CHK-W1S-NOCLOBBER names cannot be represented; and persistence across cold reset comes
from the model having no reset on its storage. What the checkers do prove against real
logic is that each program reached its addressed bit through the real programming path,
and that the sense FSM re-reads the array after reset and the shadow tracks it.

[[sep_efuse_km_axil_cpu_mux_coexist_test]]
=== sep_efuse_km_axil_cpu_mux_coexist_test

[horizontal]
Tier:: Tier 1
Run mode:: `cpu`, real fuse sense
Testlist:: `km.toml`

==== Description

The widest single test in the suite: two independent processors contend for the eFuse
block at the same time. The main CPU reads the chiplet identifier from the eFuse map
in a loop while the Key Manager's own processor concurrently writes eFuse
manufacturer registers, both arriving through the shared register-bus multiplexer.

never changes, the Key Manager's ownership tags stay intact, and its register payload
never moves backwards.

processors, and the reset controller path that releases the Key Manager.

| `STEP Key Manager released from software reset`
| LOGGED

| 3
| Handshake over the mailbox — receive the ready token, send the go token.
| `KM READY received; EL2 GO sent`
| LOGGED

| 4
| Loop exactly 512 times: read the chiplet identifier, sample the Key Manager's register payload and ownership tags, publish a counter to cold scratch.
| `coexist observer: ready=0xe9050001 count=512` with `bad_uid=0 backward=0 bad_tag=0` on the same line — the host asserts the count equals 512. The `changes=` value on that line varies with arbitration and is required only to clear a floor, so it is not quoted here

[cols="1,3,4,1",options="header"]

  the key bus directly. Observing it would require a backdoor on the proof path, which
  the evidence rules forbid. The construction evidence is the reset-control register
  reading back the parked value, not the engines' reset pins themselves.
* The raw noise on the entropy path is injected by the testbench under

  entropy IP's own default verification mode, not an open-source substitute — see

  datapath and is golden-compared bit-exactly.
* The Key Manager ROM image is built with the production boot wipe and the
  unrecoverable-fault wipe compiled out, so `CHK0`'s boot is not the silicon boot
  sequence. The key-shred legs of `rom_boot_init()` are not exercised here.

[[lcc-golden-follows-rtl]]
[NOTE]
====
*Lifecycle decode: resolved. The golden is now derived from the specification, not
transcribed from the RTL.*

This entry used to carry a warning that `cocotb/env/sep_lcc_golden.py` transcribed the
combinational decode in `hw/sys/sep/rtl/sep_lifecycle_ctrl.sv` rather than deriving it
from `hw/sys/sep/doc/lifecycle_controller.adoc`, and that the two disagreed for PROD
with `DEMOTE_1`. A transcription cannot catch the decode being wrong in the same way
the RTL is wrong, so the disagreement was recorded rather than papered over.

PR #242 landed and resolved it in favour of the chapter. Under the current decode a PROD
demotion *relaxes* its debug group to `~(SIP_DIS | SYS_DIS)` instead of forcing every
debug bit to 1, Function always takes both vectors, and `DEMOTE_1` / `DEMOTE_2` act
independently on `[15:0]` and `[31:16]` rather than being mutually exclusive.

All three consequences this note predicted then occurred, and all three are now fixed:

* The golden is re-derived from Table 50 ("Per-LC-state feature control profile") of the
  lifecycle-controller chapter — from the specification, deliberately not from the new
  RTL, because transcribing again would reproduce the same blind spot in a new form. Its
  import-time KAT set gained the three demote branches the old formula got wrong: a
  `DEMOTE_2`-only vector, a both-demoted vector, and a PROD vector with a `DBG_1` bit
  disabled, which pins the difference from the old decode by requiring that the
  demotion *not* open it.
* `sep_lcc_uvm_inbound_filter_gating_test` failed exactly as predicted
  (`PROD_DBG_1 sep_debug must be 1, got 0`). Its `SIP_DIS`/`SYS_DIS` both disabled
  `SEP_DBG`, which the old decode overrode and the new one honours. The vectors now
  leave `DBG_1` bits 0 and 1 enabled so the demotion scenario is reachable, with the
  staged t=0 image in `dv_sim_prestage.py` split to match. That test's "distinctive
  value" argument moved from the hi word to the lo word, since demotion no longer
  touches Function and the hi word is now identical in both phases.
* `LC_STATE` moved from `0x008` to `0x00C` behind a new `LOCKS_SPARE`. Rather than
  re-stating the new offsets, `sep_efuse_image.py` now *derives* its whole field table
  from the generated map, with a self-check that the result tiles all 256 words. The
  hardcoded copies in the stitch sequence and test, the image test, the address-map
  probe and `fw/drivers/sep_efuse.h` are derived too. This is the lesson worth keeping:
  a hand-written copy of a generated map is a latent failure that reports success, and
  the firmware side had already been migrated to derivation for exactly this reason.

[[sep_dma_cpu_contention_test]]
=== sep_dma_cpu_contention_test

[horizontal]
Tier:: Tier 2
Run mode:: `cpu`
Testlist:: `system.toml`

==== Description

The only test where the CPU and the DMA engine are genuinely competing masters on the
SRAM at the same instant. Firmware starts a large DMA copy without waiting for it,
then immediately runs its own store loop into a different SRAM region. The proof of
real overlap is a status sample taken at the exit of that store loop, showing the DMA
busy and not yet done. Busy is set once on leaving idle and cleared once at
completion, so busy-and-not-done at loop exit means the DMA was in flight for the
loop's entire duration. Both masters' data is then checked intact.

Without that sample this would be a sequential test wearing a concurrency label,
which is why that checker is the one that matters.

[cols="1,4,4,1",options="header"]

| LOGGED

| 2
| Seed the source pattern; clear the destination and the CPU's own region.
| `STEP source seeded; DMA destination and CPU region cleared`
| LOGGED

| 3
| Start the DMA copy and do not wait.
| `STEP DMA copy started (non-blocking)`
| LOGGED

| 4
| Immediately run the CPU store loop.
| `STEP CPU store loop entered`
| LOGGED

| 5
| Sample DMA status at store-loop exit, then poll to completion.
| `overlap STATUS=0x00000001` inside the pass line
| LOGGED

| 6
| Check both regions and clear the status bits.
| `PASS: DMA(2KiB) + CPU(256B) SRAM contention; overlap STATUS=0x00000001, ERROR_CODE=0, DONE+RW1C clear, dst==src`
| LOGGED

[[sep_mailbox_plic_test]]
=== sep_mailbox_plic_test

[horizontal]
Tier:: Tier 2
Run mode:: `cpu`
Testlist:: `cpu.toml`

==== Description

Completes the interrupt path all the way to the CPU. A single word written into the
outbound mailbox raises an interrupt that must traverse the aggregator, the CPU's
platform interrupt controller, and the machine external interrupt bit, and finally
trap into a service routine. A wrong source cannot pass — though not by the
claimed-identifier compare. With fast interrupt redirect the hardware vectors on the
claim identifier itself, so only the mailbox source has a registered handler and any
other source lands in the dummy handler, leaving the routine unrun and the test
failing on that.

This reaches CPU-internal interrupt state that no bus-level test can observe, which
is why it is a firmware test rather than a host-driven one.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Initialise the fabric filter. The firmware also writes the clock-gate control
  register, but the only field the generated map defines there is the PKA gate, so
  that write ungates nothing in this design and is not on the proof path.
| `STEP filter init done; mailbox CSR clock ungate written`
| LOGGED

| 2
| Register a service routine on the mailbox interrupt source and enable it.
| `STEP ISR registered on the mailbox PIC source and enabled`
| LOGGED

| 3
| Arm the mailbox: clear pending status, set the watermark to fire on one word, enable the interrupt.
| `STEP mailbox armed: status cleared, watermark 0, IRQs enabled`
| LOGGED

| 4
| Write one word into the mailbox queue.
| `STEP one word pushed into the mailbox queue`
| LOGGED

| 5
| Wait for interrupt; the routine claims it, raises the watermark, clears the status
  bits, confirms they read back clear while the enable is still set, then masks the enable.
| `PASS: mailbox[0] IRQ -> PIC claim id 0x00000001 -> CPU ISR; IRQS/IRQP W1C->0, no storm (count=0x00000001)`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-DELIVERY
| The service routine actually runs — the interrupt reached the CPU rather than

| `PASS: mailbox[0] IRQ -> PIC claim id 0x00000001 -> CPU ISR`
| PROVEN

| CHK-CLAIM-ID
| Only the mailbox source has a registered handler, so any other source reaches the
  dummy handler and fails the test with the routine never having run. Under fast

| `PIC claim id 0x00000001`
| GUARD — build precondition, cannot fail on any DUT

| PROVEN

==== Description

| LOGGED

| Enable the interrupt and write the real test bit.

[[sep_drbg_real_sink_multi_km_aes_test]]

==== Description

driven concurrently — genuinely concurrent, as two forked tasks, not one after the

partitioned between them rather than duplicated or invented.

its own feed, in order, which is a per-consumer routing proof. The Key Manager's order
is firmware-driven and so is checked for membership rather than order.

run — the log records `0 completed commands` with the blocks still in an open command.
The test intends to stay inside one command by budget, but nothing enforces that
budget: this run reached 38 blocks against a declared legal length of 32, and the
segmentation legality check inspects only completed segments, so an over-long open
segment is not bounds-checked. See <<esrc-noise-exception>> for what the raw-noise
injection on this path does and does not cover.

[[sep_cpu_ifu_lsu_alias_remap_matrix_test]]
=== sep_cpu_ifu_lsu_alias_remap_matrix_test

[horizontal]
Tier:: Tier 3
Run mode:: `cpu`
Testlist:: `cpu.toml`

==== Description

Proves the CPU-side address alias window remaps both data and instruction accesses to
physical SRAM. Firmware programs the window, then checks it in three directions: a
write through the alias appears at the physical address, a write to the physical
address is visible through the alias, and — the strong one — a function is written
into SRAM and called through its alias address, so the instruction fetch unit itself
must remap for the call to return.

This must run with a booted CPU. In the host-driven mode the bus splice sits after the
remap, so the window would be bypassed entirely and the test would prove nothing.

==== Steps

[cols="1,4,4,1",options="header"]
|===

| 1
| Probe the alias base CSR with a value distinct from its reset value, restore the operating base, and read back. The region size is a fixed localparam and is not programmed.
| `CHK-CSR PASS: SEP_LOCAL_BASE writable (probed 0xe0000000), restored to 0xd0000000 (fixed 768MiB window -> 0x10000000)`
| LOGGED

| 2
| Write through the alias; read the physical address.
| `CHK-LSU-WR PASS: write@0xd0000308 -> phys 0x10000308 == marker`
| LOGGED

| 3
| Write the physical address; read through the alias.
| `CHK-LSU-RD PASS: read@0xd0000310 -> phys 0x10000310 == marker`
| LOGGED

| 4
| Write a small function into SRAM, fence, and call it through its alias address.
| `CHK-IFU PASS: call@0xd0000000 -> IFU fetch remapped to phys 0x10000000 -> returned 42`
| LOGGED

|===

==== Checkers

[cols="1,3,4,1",options="header"]
|===
| ID | Check | Proof | Status

=== sep_nmi_sanity_test

[horizontal]

Run mode:: `cpu`
Testlist:: `cpu.toml`

==== Description

Covers the non-maskable interrupt mechanism end to end: the handler trampoline is
correctly aligned, the vector register has the right default, accepts a new value,
and refuses further writes once locked — and then a real watchdog bark delivers an
actual non-maskable interrupt to that handler, which clears the condition and returns.

vector must still hold its previous value.

[cols="1,4,4,1",options="header"]

| 1

| LOGGED

| 2
| Check the vector register default; write a new vector; read it back.
| `CHK-VEC-DEFAULT PASS: SEP_NMI_VEC=0xc0000100` then `CHK-VEC-WRITE PASS: SEP_NMI_VEC readback=0xc0000500`
| LOGGED

| 3
| Set the lock; attempt another write; confirm the vector is unchanged.
| `CHK-LOCK PASS: lock=1 and locked write ignored (vec still 0xc0000500)`
| LOGGED

| 4
| Configure the watchdog with a small bark threshold and enable it; wait.

[[sep_lcc_uvm_inbound_filter_gating_test]]
=== sep_lcc_uvm_inbound_filter_gating_test

[horizontal]
Tier:: Tier 3
Run mode:: `no_cpu`, real fuse sense
Testlist:: `system.toml`

==== Description

Proves that the lifecycle security state actually gates the external inbound port —
the security-boundary property, not just the register that describes it. In the
production state the debug bit is clear and an external read is refused with a decode
error. Writing the demote register flips the state, the debug bit sets, and the same
external read now succeeds and returns the expected value.

The value the external read returns is deliberately distinctive, which is what makes
the allow case meaningful: it shows the read genuinely reached the lifecycle
controller rather than being answered by something else on the path.

Both halves of the feature-control register are compared exactly, in full, against the
golden decode — not just the single debug bit. The gating property above is proven on
live RTL and stands on its own. The *value* comparison does not: the golden follows the
RTL rather than the lifecycle-controller chapter, and the two disagree precisely on the
demoted-PROD case this test exercises. Read <<lcc-golden-follows-rtl>> before citing
`CHK-DBG-FEAT` or `CHK-DBG-ALLOW` as evidence that the policy is correct.

| `CHK-PROD-FEAT PASS: FEAT_CTRL=0xf000000000000000 == golden, sep_debug=0`
| LOGGED

| 3
| Attempt the same read from the external port; require a decode error.
| `CHK-PROD-BLOCK PASS: external AXI @0x10918000 blocked with DECERR (resp=3)`
| LOGGED

| 4
| Write and read back the demote register over the control bus.
| `CHK-DEMOTE PASS: DEMOTE_1.demote write -> read-back == 1`
| LOGGED

| 5
| Re-read feature-control; compare against golden; confirm the debug bit is now set.

| 6

[NOTE]

[[esrc-noise-exception]]
Forcing raw noise at the source is a recorded exception, not a backdoor on the proof
path. A ring oscillator is a free-running combinational loop — `entropy_ring_oscillator`
is a NAND-plus-buffer delay chain closed on itself — and no event-driven simulator
produces physical randomness from it. Injection is therefore the only way to exercise
the stack, and it is applied at the decorrelator noise input, upstream of every stage
this plan checks.

This matches the entropy IP's own testbench, which injects a behavioural ring-oscillator
model at the same node and does so *by default*; using the real oscillators is the
non-default mode there. So the open-source flow is not a weaker substitute for the IP's
verification — it is the same mode, at the same node.

What this does mean is worth stating at its true width. The injection point is the
decorrelator noise input, which sits downstream of the entire noise source — the ring
oscillator, the metastable sampling flop, and the sample-clock-to-core-clock
synchroniser — and the oscillator tune/detune path drives that same stage. All of that
is real silicon logic, and none of it is exercised by any test in this plan: no
testlist entry runs this stack with the injection off. Entropy quality, oscillator
tuning, and the health tests over real noise belong to the entropy IP's own testbench,
not here. Every stage after the injection point is real logic and is golden-checked.
====

== Document history

This plan supersedes the earlier Phase 1 plan and its separate detail file. Checker
evidence was re-derived from a full Verilator regression rather than carried over.

Every entry was then audited individually against its kept log, its test source and,
for the firmware tests, its C. That pass found eleven checkers that could not fail —
among them a suppressed write-response check that let two erroring writes pass, a SPI
data check that accepted the exact value a broken receive path produces, a lifecycle
transition check applied to a compile-time constant instead of to the DUT, three
key-register reads whose read data is tied to zero in the generated register block, and
a set of boot-ROM stage markers that were printed but never required. Each is fixed or,
where fixing it needs a decision this document cannot make, recorded in
<<open-items>>.

The audit also found that a large share of the evidence strings this document quotes
could never have matched any log — some pinned to a seed, some to counts that vary per
