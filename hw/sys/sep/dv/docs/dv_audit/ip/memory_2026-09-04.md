## Join findings — what no single test could see

### J1 — the `cpu` group is scheduled by nothing · GOOD-TO-HAVE
`testlists/all.toml:151` defines a `cpu` group holding the three firmware tests of this
bucket. `.github/workflows/sim.yml:264-278` runs `items=smoke` on the pull-request tier
and `items=${{ matrix.nightly_items }}` nightly, and SEP's `nightly_items` is `no_cpu`
(`:125`, with the reason stated in the comment above it). So no automatic run covers
these three.

Judged deliberately, and **not** as policy 1.7: the tests do execute — the logs this
audit consumed come from a real run of them on 2026-09-04 — so no claim rests on a run
that did not happen. What is weak is durability: a regression nobody schedules drifts
without anyone learning, and combined with the missing revision stamp there is no
mechanism that would notice.

*Escalation trigger, not evaluated:* whether anything outside CI (a cron on the compute
host, a release checklist) schedules the `cpu` group. One look at whatever holds that
schedule settles it. If nothing does, and the plan offers these three as closed evidence,
that is policy 1.7 and it becomes MUST-FIX.

**Policy gap, recorded rather than invented around:** `dv_policy.md` §1.7 covers "in no
testlist, or only in a group nobody schedules", and §2 has no entry for "enrolled in a
group that runs by hand but not on a schedule". The tier for J1 was therefore chosen by
the toss-up rule (lower tier, trigger named). That distinction belongs in the policy.

### J2 — every log binds to exactly one invocation, by path · OBSERVATION
No shared or overwritten log in this bucket: each result lives at
`build/runs/<run>/<test>/seed_<n>/attempt_<k>/logs/<test>.log`, and each `result.json`
names its own log, `results.xml` and script. So the "a shared `sim.log` is not a log"
failure does not apply here. What is absent is *content* identity (J-nothing binds the
log to a revision — the D6 gap above), not path identity.

### J3 — no shared helper carries a finding · OBSERVATION
The shared infrastructure on these five proof paths was audited once, in full, and none
of it produced a finding. Dispositions, cited by all five test reports and not re-opened:

| Helper | `file:line` | Disposition |
|---|---|---|
| assertion propagation | `cocotb/tests/sep_base_test.py:1029-1031` | `run_phase` awaits `run_scenario()` with no `try`/`except`; any `AssertionError` fails the run. No finding. |
| AXI register access | `cocotb/seq_lib/sep_axi_reg_driver.py:41-63` | `_wr`/`_rd` raise on any non-OKAY response, so each access is also a live-bus assertion. Caveat: `allow_unverified_write_resp=True` tolerates the response code, and there the read-back must carry the proof. No finding. |
| boot scoreboard | `cocotb/env/sep_boot_scoreboard.py:61-94` | `check_phase` accumulates errors and asserts the list is empty; a missing trace monitor is an error, not a skip; requires ≥16 distinct fetch PCs, `fw_done` and `fw_pass`. Proves the core booted and the firmware self-reported PASS, and nothing about any behaviour the firmware claims to have checked. No finding. |
| boot poll loop | `cocotb/tests/sep_base_test.py:581-590` | Bounded loop breaking on `fw_done_o`; falling out sets nothing and `check_phase` then errors "firmware never signaled completion". Not a timeout-as-pass. No finding. |
| X/Z resolution | `cocotb/tests/sep_base_test.py:98-115` | `rd()` resolves X/Z to 0 per bit. On the boot observables this fails safe (X `fw_done_o` reads not-done, X `fw_pass_o` reads FAIL). It is what `sep_sram_smoke_test`'s open 2.6 trigger is about. No finding. |

**This is the load-bearing result of the height.** The bucket's two firmware verdicts rest
on the scoreboard, so a defect in it would have been one finding and two lying passes.
Because it is sound, each firmware test's honesty turned on its own C source — which is
where both per-test agents went, and both found the firmware's checks real, with goldens
traceable to the committed ROM image rather than to the design.

### J4 — no repeated shape, and no unpaired deny leg · OBSERVATION
- **Repeated shape:** the two firmware tests share one pattern — firmware self-reports a
  verdict magic, the host asserts on DUT-produced console content. In both the count of
  firmware checks is pinned (host-side `assert seen == 7` in one; a compile-time array
  plus the scoreboard gate in the other), so the shape is not carrying a defect. Nothing
  in the bucket looks generator-made.
- **Positive controls:** one deny-shaped leg exists in the bucket — the ROM
  write-ignored check — and its control is inside the same test, on the same port. No
  deny in this bucket depends on an allow leg living somewhere else, so there is no
  unpaired deny to escalate to 1.4.

  `cpu` group. One file, not read, because I do not know which file it would be.

- **The two per-test GOOD-TO-HAVE findings were not re-derived.** They are taken from the
  test-height reports as written; this height does not re-read a test.
- **Independence is partial.** The same session performed IP-prep, read the shared
  infrastructure, and wrote this join. The five test-height grades were produced by
  separate agents with no conversation context, and every join above rests on those
  reports plus fresh reads of the testlists and the CI workflow — but a reader who wants
  §7 independence end to end should have this height redone in a clean context.
- **Budget actually spent at this height:** the five test reports as input, plus
  `testlists/all.toml`, `testlists/memory.toml` and `.github/workflows/sim.yml`. No test
  source and no log was re-opened.
- **Not this height's business, and not looked at:** whether five tests are enough for
  the behaviours the plan claims of SRAM, ROM and boot. That is the plan's review.
