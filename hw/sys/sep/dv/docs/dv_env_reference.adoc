[[sep-dv-env-reference]]
== SEP OSS DV Environment Reference

Deep-dive companion to link:SEP_TB_ARCH.adoc[SEP_TB_ARCH]: how eFuse contents
are selected, what backs the memory / eFuse / SPI ports, how CPU trace is
reconstructed, and how Boot ROM images are built.

For the testbench hierarchy, VIP policy, and bring-up flow, start with
link:SEP_TB_ARCH.adoc[SEP_TB_ARCH]. For getting a run going, see the
link:../README.md[README]. For what each test proves, see
link:SEP_VPLAN.adoc[SEP_VPLAN]. This chapter is collected into
link:index.adoc[index.adoc] after the TB architecture and VPLAN.

=== eFuse content selection

All eFuse tests select their contents through
`sep_base_test.select_efuse_image()`. The shared helper uses
`+sep_efuse_preload` as the selector for fixed contents; without that plusarg, it
generates constrained-random eFuse contents from the test seed.

`+sep_efuse_preload=<path>`:: Loads a specific fixed `.hex` / `.preload` image.
`+sep_efuse_preload` (no path):: Loads the committed default preload image.
(none):: Generates a random image from the test seed.
`+sep_efuse_hex=<path>`:: A special model-file override; normal eFuse tests use
  the generated `out/sep_efuse.hex` path.

The selected `SepEfuseImage` is the single source of truth. Because the generic
eFuse model deposits its image once at t=0 (not on every reset), the per-seed
image is staged BEFORE the simulator launches by the pre-sim hook
(`cocotb/dv_sim_prestage.py`, driven from `run_dv.py`), which writes
`out/sep_efuse.hex`; the model `$readmemh`s it at t=0 and its persistent W1S
storage retains programmed bits across resets. The same `SepEfuseImage` object
computes the expected shadow-register data for comparison.

End to end, one eFuse test runs:

. Test starts; calls `select_efuse_image()`, which reads the cocotb plusargs.
. Per the selector table above, a fixed, default, or seed-random image is built
  into one `SepEfuseImage` golden object.
. The pre-sim hook writes that image to `out/sep_efuse.hex`.
. The simulator launches; the model deposits the image at t=0.
. Reset is applied and released; the model's W1S storage persists.
. The RTL fuse-sense FSM reads the OTP words and fills the eFuse shadow
  registers; the test waits on `sep_fuse_sense_done_o`.
. The test reads the actual shadow data and compares it against the expected
  data computed from the same `SepEfuseImage`. Mismatch fails the test.

==== Readout method vs image source

The generic eFuse model sense flow (OTP image → sense FSM → shadow) is used
by more than the two shadow-compare tests. *Readout method and image source
are independent axes* for those two — backdoor is the default readout, exactly
one test uses the AXI front door, and either readout can run any source:

`sep_efuse_sense_test`:: *Backdoor* shadow compare (the default), reading the
  sensed array directly from the top-level `efuse_shadow_probe_o` port. Enrolled
  with `+sep_efuse_preload` (committed default preload).
`sep_efuse_image_test`:: The *one* test that reads the shadow over the *AXI front
  door* (exercising the real software read datapath), plus a resense cycle with a
  fresh image. Runs the default (random) source.

Other enrolled tests also run *real* fuse sense (no `+skip_fuse_sense`) for a
different contract — lifecycle decode, inbound-filter `SEP_DBG` gating — and
do not replace the shadow-compare pair: `sep_efuse_lcc_lc_state_stitch_test`,
`sep_lcc_uvm_inbound_filter_gating_test`,
`sep_fabric_inbound_filter_rule_matrix_test`.

=== Memory / eFuse / SPI models

The memory and eFuse integration is RTL inside `sep_wrapper`
(`hw/top/sep_ip_integration.sv`). The OpenTitan SPI host is RTL inside the
`sep` core. The TB does not back those ports with responders.

==== Memory macros

Real `prim_ram_1p` / `prim_rom` / EL2 TCM (`ram_16384x39`) macros. They have no
runtime init, so `tb_backdoor_mem` (in `tb/tb_top.sv`) pre-fills correct
power-up patterns (KM ROM NOP+parity, KM SRAM zero+valid parity, OTBN
SECDED-valid zero) and backdoor-loads images:

* boot-ROM / SEP-SRAM / KM-ROM via the `+sep_boot_rom_hex` / `+sep_sram_hex` /
  `+km_rom_hex` plusargs, with a CWD-default fallback to `sep_boot_rom.hex` /
  `sep_sram.hex` / `km_rom.parhex`.
* the ICCM/DCCM firmware on `tcm_load_i`, de-interleaved with per-word Hsiao ECC.

These backdoor writes require the target arrays to be public under Verilator
(`sep_public_scope.vlt`: `prim_ram_1p.mem`, `prim_rom.mem`,
`ram_16384x39.ram_core`).

==== Generic eFuse model

`hw/ip/efuse/dv/models/efuse_bank_model.sv`, shared with SMC via a plusarg
prefix. It backs the eFuse bank-control and fuse-command datapath so fuse sense
runs without foundry OTP macros. It self-preloads its OTP image at t=0 via
`+sep_efuse_hex` (default `out/sep_efuse.hex`, staged by the pre-sim hook) and
persists W1S programs across reset. It can inject opt-in OTP program failures
with `+sep_efuse_prog_fail_count`, `+sep_efuse_prog_fail_percent`, and
`+sep_efuse_prog_fail_seed`.

==== OpenTitan SPI host

Internal to the wrapper; its pads come out as scalar cocotb ports in `tb_top.sv`
so tests can attach the Apache-2.0 `OcahSpiFlash` Python BFM.

The SPI pad mux is absent from a pure-open build — the pads are driven
straight off the wrapper's struct port, and flash tests need no mux step.
If a mux that selects between the OCAH SPI host and a proprietary SPI exists
only in a companion wrapper, the driver for it lives in that repo and that
repo's `fw.mk` compiles and links against it. Open firmware does not program
it.

==== Kept TB shims

`shims/` holds the `sep_cpu` stub (no_cpu build), `prim_sync2`, the ABR key-CSR
Verilator stub, and the entropy ring-oscillator. `tb/sep_outbound_mbx.sv` (the fw
console / PASS monitor) is also kept — it services a real wrapper output port,
not a memory model.

=== Processor-state monitoring and firmware stack tracing

Firmware execution visibility has three layers: the virtual console
(`tb/sep_outbound_mbx.sv`, byte stores to `0x8000_0000` plus the PASS/FAIL
magic), the processor-state monitor, and firmware stack tracing. The last two
live in `cocotb/env/sep_cpu_trace_monitor.py`, a passive `uvm_component` built
by `sep_base_test` for every test and self-idling unless the `+cpu_boot` run
mode is active.

==== Trace source

`tb_top.sv` exports the complete VeeR EL2 retirement-trace struct
(`el2_trace_pkt_t`) as ports: `cpu_trace_valid_o`, `cpu_trace_addr_o`,
`cpu_trace_insn_o`, `dbg_cpu_trace_exc_o`, `cpu_trace_ecause_o`,
`cpu_trace_interrupt_o`, and `cpu_trace_tval_o`. The no-CPU shim ties the
struct to zero, so no_cpu targets elaborate unchanged. Sampling gates on
`sep_cpu_reset_n_o`; a warm CPU reset (e.g. the WDT bite path) flushes the
shadow call stack while history and tallies survive.

==== What the monitor reconstructs

PC history:: every retirement feeds a count, a distinct-PC set (the boot
  scoreboard's PC-advance evidence), and a 512-entry ring of the most recent
  retirements.
Shadow call stack:: retired RV32IMC encodings are decoded for linking calls
  (`jal`/`jalr`/`c.jal`/`c.jalr` through ra/t0), returns (`jalr`/`c.jr`
  through ra/t0), and `mret`. Exception-flagged retirements push a synthetic
  trap frame carrying ecause/interrupt/tval; `mret` unwinds it.
Trap records:: every exception retirement is kept with its cycle, PC, decoded
  mcause name, and tval.
Hang watch:: after the first retirement, a 20k-cycle retirement-free gap out
  of reset logs a one-shot warning with a full dump. Diagnostic only — a core
  idling in a wait loop or halt is legitimate.

Reconstruction hiccups (pop of an empty stack, depth overflow) are tallied as
resync notes and logged, never failed; pass/fail judgement stays in
`sep_boot_scoreboard.py`.

==== Symbolization

`cocotb/env/sep_fw_symbols.py` parses the `nm -B -n` listing the firmware
build emits next to every ELF (`<test>.tcm.sym`; `boot_rom.sym` for ROM
profiles — both staged into the run directory via the `[c_build.*].outputs`
manifests) and resolves PCs to `name+0xoff`. `boot_firmware` attaches the
listing automatically from the ITCM hex path; a missing listing degrades to
numeric PCs and never fails a test. Trace PCs are link addresses — the
`-0xC0000000` bias in `fw.mk` only rebases the TCM hex images.

==== Output

On any failing boot exit (no boot, hang, cycle exhaustion, firmware FAIL) the
monitor dumps the symbolized call stack, trap records, and the tail of the
retirement ring at error level before the scoreboard assertion ends the run; a
passing run logs the same summary at info level in `report_phase`. Passing
`+cpu_trace_log` additionally streams every retirement (cycle, PC, encoding,
symbol) to `cpu_trace.log` in the run directory.

`sep_cpu_trace_diag_test` (`testlists/cpu.toml`, firmware
`fw/tests/cpu_trace_diag_test`) audits the reconstruction against
architectural ground truth: a known noinline call chain, one breakpoint trap
with the CSR-true `mcause`/`mepc` reported on the console, cross-checked
against the monitor's trap record, shadow-stack depth, and symbolization.

=== Boot ROM firmware builds

Production Boot ROM firmware tests (`sep_rom_non_secure_boot_test`,
`sep_rom_ot_{dma,pio,secure}_boot_test`) live in `testlists/rom_fw.toml` and run
in the `all` and `rom_fw` groups. They belong to the ROM-FW owner; the OSS suite
grades ROM *hardware* access only (`sep_boot_rom_smoke_test`,
`sep_rom_sanity_test`, `sep_boot_rom_lsu_read_test`).

A named ROM run needs the Boot ROM + manifest + BL1 image. Each test declares
both keys of a `firmware = { name = ..., mode = ... }` pair (`mode` alone does not
select a `[c_build.*]` block), and the three profiles select three different
blocks in `sep_sim_cfg.toml`, all driving
`hw/sys/sep/bootrom/prod/Makefile`:

`boot_rom`:: `sep_rom_non_secure_boot_test` — `[c_build.boot_rom]`, the SMC-SRAM
  manifest path.
`boot_rom_ot`:: `sep_rom_ot_dma_boot_test` and `sep_rom_ot_secure_boot_test` —
  `[c_build.boot_rom_ot]`, the OpenTitan SPI host with the SECURE_DMA drain.
`boot_rom_ot_pio`:: `sep_rom_ot_pio_boot_test` — `[c_build.boot_rom_ot_pio]`, the
  same transport with the CPU-PIO drain.
 The one prerequisite a build step must not
mutate git for is the manifest packer submodule; without it the pack half dies
with `No module named tt_boot_manifest`:

[source,bash]
----
git submodule update --init hw/sys/sep/bootrom/prod/tools/tt-boot-manifest
----

Build the ROM by hand only when iterating on the ROM sources themselves. The two
halves are split by tool dependency, so each runs where its tools are:

`toolchain-images`:: Needs the RISC-V toolchain *with* picolibc — the generated
  register headers close their packing checks with `static_assert`, i.e.
  `<assert.h>`, which is not a freestanding header. Use the toolchain container.
`pack-images`:: Pure Python; its deps come from the submodule's own
  `pyproject.toml`, installed on demand by `uv` (no `pip3 install` needed).

`[c_build.boot_rom]` performs exactly these two steps. It probes the host
toolchain for picolibc first and builds natively when the probe succeeds; the
container is the *fallback* for a host whose toolchain has no picolibc:

[source,bash]
----
# host toolchain has picolibc:
make -C hw/sys/sep/bootrom/prod toolchain-images \
  GCC_PREFIX=... RISCV_TOOLCHAIN=... RISCV_PREFIX=...
# otherwise, in the OCAH toolchain container:
./scripts/docker-run.sh run-here make -C hw/sys/sep/bootrom/prod toolchain-images

# pack-images is pure Python and always runs on the host:
make -C hw/sys/sep/bootrom/prod pack-images
----
