[[sep-dv-functional-coverage]]
== SEP OCAH Open-Source Functional Coverage Plan

=== Overview

This plan covers **basic legal operating modes** of every SEP IP the OSS suite
already walks. It is the functional-coverage contract for the PyUVM/Verilator
flow.

Verilator does not compile SystemVerilog `covergroup`. Phase 1 bins are VCS
covergroups in `hw/sys/sep/dv/cov/sv/sep_fcov.sv` (`ifndef VERILATOR`),
sampled by the single passive `u_sep_fcov` instance in `tb/tb_top.sv`. There
is no Verilator cover-property layer.

Feature checkers stay on the VPLAN scorecard. The FCOV number is the URG
Group report on `sep_uvm_top.u_sep_fcov`, not the DUT line/cond/toggle/FSM
SCORE.

|===
|Field |Value
|DUT |`sep_wrapper`
|Reference specification |`hw/sys/sep/doc/`
|Reference VPLAN |`SEP_VPLAN.adoc`
|Open-source framework |PyUVM on cocotb
|Open-source simulator |Verilator
|===

=== Owning tests

A hole is not gradable without knowing which test was supposed to fill it, so
the owner is named here rather than left to the VPLAN. `owner` is the `all`
member that MUST fill the group; a group its owner leaves empty is a dead bin
or a stimulus that does not do what the test says, and either way it needs a
human. Other members may fill a group in passing.

Thirty-three Phase 1 covergroups, compiled and sampled for VCS only
(`ifndef VERILATOR`). Several IPs carry more than one group, because their
Phase 1 contract has independent halves that different tests reach: the Key
Manager splits generate from consume; lifecycle splits the sensed state, the
transition taken, the `FEAT_CTRL` profile, demotion, and the SEC_DIS window
while sensing is still open; eFuse splits sense from
the program/lock matrix; and the DMA splits the transfer from which completion
route reported it. Phase 2 names are listed at the end of this document.

=== Evidence

A collection or elaboration claim names the tool and the `run_dv.py` run ID
and quotes the launcher `result status=` line. Verilator does not compile
these groups, so a Verilator class regress is not Phase 1 fill evidence.
Local paths under `build/runs/` are not durable.

=== Collection

`sep_fcov` is a passive TB-side sampler. It drives nothing.

Its CSR side reads the post-remap CPU-LSU AXI bus, wired from the same node
`tb_top` already mirrors to its flat `s_axi_*` ports and force-splices on the
no-CPU builds -- not a new probe, and not a Python path into the fabric
(`sep_public_scope.vlt` keeps public marks off it). The flat `s_axi_*` request
ports carry TB stimulus only, so under `+cpu_boot` the EL2 owns the bus and a
port-side sampler would score nothing on any firmware test. Everything else is
the real `m_axi_*` DUT port or a `tb_top` probe port.

Register data bins are gated on exactly ONE outstanding AXI transaction in
that direction, so the address that labels a bin is unambiguously the address
that carried the data. A pipelined burst of firmware traffic is therefore
sampled only where it is serial: a missed sample is a missed hit, never a
false one.

A covergroup bin is an interface event. It is not a substitute for a VPLAN
checker that compares a golden (digest, banner text, shadow image).

Collect with `--tool vcs --cov --target default` and read the URG Group pages
for `u_sep_fcov`. The DUT SCORE (line/cond/toggle/FSM/branch/assert) is a
different number, and the sampler's own line weight is part of it -- it is a
testbench cone, not a DUT cone.

`OCAH_FCOV_COVER` cover-property points are unused.

=== Phase 1 coverage definitions

Each row is one coverpoint of the named covergroup in
`cov/sv/sep_fcov.sv`. A row states what the sampler must SEE, which is not
always the whole feature contract: where the contract needs a golden, the row
says which checker keeps it. Do not read a hit as the checker's claim.

==== `sep_axi_decode_cg`

*Description*: The LSU bus decodes a live CSR and returns OKAY.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_reset_value` |An OKAY read of `SEP_LOCAL_BASE_ADDR` returns its generated reset value
|`cp_wr_rdback` |A whole-word CSR write, then an OKAY read of that address returning the written word
|`cp_resp_wr` / `cp_resp_rd` |An OKAY write response; an OKAY read response (separate coverpoints, so a write-only or read-only run cannot fill both)
|===

==== `sep_sram_access_cg`

*Description*: The 64-bit SRAM port accepts a write and returns the same data.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_write` |An OKAY write inside the SRAM aperture
|`cp_match` |An OKAY read of that address returning the full 64-bit word written
|===

==== `sep_boot_rom_cg`

*Description*: The CPU fetches from the Boot ROM, and the ROM answers a data read.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_ifu` |A retired PC inside the Boot ROM aperture
|`cp_lsu` |An OKAY data read of the Boot ROM aperture
|===

The word-matches-the-loaded-image claim stays on the VPLAN checker
(`sep_boot_rom_lsu_read_test`); the sampler sees the access, not the image.

==== `sep_cpu_boot_cg`

*Description*: VeeR EL2 boots firmware and reports PASS.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_console` |A firmware console-byte strobe
|`cp_pass` |Firmware completion with PASS
|`cp_pc` |A retired PC that is non-zero
|===

The expected banner text and the distinct-PC count stay on the boot
scoreboard. A covergroup counts hits, not distinct values.

==== `sep_aes_mode_cg`

*Description*: AES legal mode x key-size x operation. The suite walks 15 cells.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_mode` |ECB, CBC, CTR
|`cp_key` |128, 192, 256
|`cp_op` |ENC, DEC
|`cp_sideload` |SW key (`KEY_SHARE` CSRs) and KM sideload key (`CTRL_SHADOWED.sideload`)
|`x_mode_key_op` |15 cells: the 9 ENC cells plus the ECB/CBC decrypt legs of the round-trip. CTR x DECRYPT is excluded, see below. A cell is sampled when that configuration reached `STATUS.output_valid` and its `DATA_OUT_0` word was read
|===

CTR x DECRYPT is an `ignore_bins` in the cross because the cell has nothing
to score, not because the suite happens not to drive it. CTR is a stream
mode: the engine runs the forward cipher whichever way `OPERATION` is
programmed, so a test that programmed DECRYPT there would pass with the
field disconnected. It is not a deferral -- there is no cipher contract
behind that cell for a later phase to claim. The scoreable neighbour is
`OPERATION`'s shadowed-register behaviour, which is mode-independent and
belongs on a CSR vehicle. `cp_op` and the decrypt cells are owned by
`sep_aes_mode_keysize_rand_test` CHK-RT (the engine round-trip);
`cp_sideload.km_key` by `sep_km_aes_sideload_kat_test` and
`sep_km_command_set_rand_test`. The ciphertext-equals-golden and
round-trip-equals-plaintext claims stay on those tests. The GCM phases are
Phase 2.

==== `sep_hmac_mode_cg`

*Description*: HMAC SHA-2 variants the suite walks. A cell is sampled when
`INTR_STATE.hmac_done` is observed after a `CMD.hash_process` on that CFG.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_digest` |SHA2-256, SHA2-384, SHA2-512
|`cp_key_length` |Keyed only: 128, 256, 384, 512, 1024
|`cp_plain` |Plain SHA (`hmac_en` = 0): the three digest sizes
|`x_digest_key` |The 14 legal keyed cells. SHA-256 with a 1024-bit key is illegal in `hmac.sv` and is an `ignore_bins`, not an empty cell
|===

The digest-equals-golden claim stays on `sep_hmac_sha_variant_rand_test`.

==== `sep_kmac_mode_cg`

*Description*: KMAC-family modes the suite walks. A cell is sampled when
`INTR_STATE.kmac_done` is observed after a `CMD` process on that CFG.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_sha3` |L224, L256, L384, L512
|`cp_shake` |L128, L256
|`cp_cshake` |L128, L256
|`cp_kmac` |L128, L256. Samples `CFG_SHADOWED.mode` = cSHAKE with `kmac_en` = 1 after a completed process. That is the programmed configuration, not an SP800-185 digest proof. `SepKmacCfg.cfg_word()` and `keyed_mac` both write that word. `sep_kmac_mode_strength_rand_test` walks five keyed cells (L128 / L256 × key 128 / 192 / 256 / 384 / 512) against `kmac_family_words`, an SP800-185 golden that self-tests at import. The KM sideload KAT is an engine cross-check and has no digest golden.
|`cp_sideload` |Keyed KMAC only: SW key (`KEY_SHARE` CSRs) and KM sideload key (`CFG_SHADOWED.sideload`)
|`cp_kmac_key_length` |Key 128, 192, 256, 384, 512 from the `KEY_LEN` register. Both drivers write `KEY_LEN` before `CFG_SHADOWED` (`CFG_REGWEN` locks at Start) and the register holds its value across a CFG write, so the sampler does not invalidate it there
|===

The digest-equals-golden claim stays on `sep_kmac_mode_strength_rand_test`.
A `keyed_mac` hit fills `cp_kmac` as configuration only.

==== `sep_otbn_execute_cg`

*Description*: OTBN runs a compute program to IDLE.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_cmd` |An `EXECUTE` write to `CMD`
|`cp_done` |ONE bin: the same post-`EXECUTE` window saw `STATUS` back at IDLE and then `ERR_BITS` == 0
|===

`cp_done` is one bin. Two independent strobes would let a stale
`ERR_BITS` zero score alongside a program that never ran. Secure wipe and
`LOCKED` are Phase 2.

==== `sep_abr_keygen_cg`

*Description*: Adams Bridge ML-DSA keygen completes.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_op` |`MLDSA_CTRL` = KEYGEN
|`cp_done` |`MLDSA_STATUS.VALID` after that KEYGEN -- the bit the KAT polls, not "STATUS non-zero"
|===

The public-key-equals-KAT claim stays on `sep_abr_mldsa_keygen_kat_test`.

==== `sep_abr_sign_cg`

*Description*: Adams Bridge ML-DSA signing and verification complete.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_op` |`MLDSA_CTRL` = SIGNING, and `MLDSA_CTRL` = VERIFYING
|`cp_sign_done` / `cp_verify_done` |`MLDSA_STATUS.VALID` after that command.
Separate coverpoints, not one concatenated cell: the pending flags are
independent, so a command that never completes would otherwise drop a later
command's genuine completion into no bin. Each arms only on an observed
`VALID == 0` read after its `MLDSA_CTRL` write, so the sticky VALID of a
previous operation cannot be credited to a command the engine dropped
|===

Split from `sep_abr_keygen_cg` rather than added to it: KEYGEN, SIGNING and
VERIFYING are separate `MLDSA_CTRL.CTRL` encodings with separate owning leaves,
and folding them would let the keygen leaf report a sign cell. The
signature-equals-ACVP and verify-accept-vs-reject claims stay on
`sep_abr_mldsa_sign_verify_kat_test`. KEYGEN_SIGN (0x4) is not covered.

==== `sep_abr_mlkem_cg`

*Description*: Adams Bridge ML-KEM-1024 commands complete.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_op` |`MLKEM_CTRL` = KEYGEN, ENCAPS, and DECAPS
|`cp_keygen_done` / `cp_encaps_done` / `cp_decaps_done` |`MLKEM_STATUS.VALID`
after that command, one coverpoint each for the same reason as the ML-DSA pair,
and each armed on an observed `VALID == 0` read after its `MLKEM_CTRL` write.
`MLKEM_CTRL` is writable only while `STATUS.READY` is set, so a command issued to
a busy engine is dropped silently and the arm is what stops the stale VALID being
read as its completion
|===

ML-KEM is a separate register block from ML-DSA in the same aperture, with its
own `MLKEM_CTRL` and `MLKEM_STATUS`, so this is a separate group rather than
more bins on `sep_abr_sign_cg`: no ML-DSA command can reach an ML-KEM cell and
the owning leaves stay distinct. The value claims -- ek/dk, ciphertext and
shared key against the ACVP vectors, and the implicit-rejection key for a
modified ciphertext -- stay on `sep_abr_mlkem_kat_test`. `KEYGEN+DECAPS` (0x4)
is not covered.

==== `sep_esrc_edn_flow_cg`

*Description*: Entropy leaves ESRC, passes DRBG, and a sink consumes it.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_seed` |Seed presented to CSRNG
|`cp_gen` |A CTR_DRBG genbits-valid beat
|`cp_crypto` |A crypto-leg sink handshake (`tvalid && tready`)
|`cp_km` |A KM sink handshake
|`cp_edn_aes` / `cp_edn_kmac` / `cp_edn_otbn_rnd` / `cp_edn_otbn_urnd` |Which `drbg_axis_edn_adapter` client took the post-adapter grant: `aes`, `kmac`, `otbn_rnd`, `otbn_urnd`. `cp_crypto` above samples the shared AXIS stream ahead of the fan-out, so it is hit by any sink and cannot show that a given client was served.
|===

Health-test watermarks, FIPS lock, and alerts are Phase 2.

==== `sep_km_generate_cg`

*Description*: The mailbox generates a key.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_generate` |A decoded `RESP_CMD` frame echoing `CMD_KEY_GENERATE` with rc 0 and a non-null handle
|===

The frame is decoded from the mailbox `SEP_READ_DATA` word sequence, so the
bin needs the KM's own answer. Silence cannot score it.

==== `sep_km_command_sideload_cg`

*Description*: A generated key is transferred to each consumer.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_dest` |HMAC, KMAC, AES, OTBN, ABR ML-DSA seed, ABR ML-KEM seed D, ABR ML-KEM seed Z, ABR ML-KEM message -- one cell each for all eight destinations the KM firmware decodes, taken from `RETURN_ARG` dest_engine of a successful `CMD_KEY_TRANSFER`
|===

The consumer's use of the sideloaded key (the KAT digest) stays on the four
`sep_km_*_sideload_kat_test` checkers for HMAC/KMAC/AES/OTBN, and on
`sep_km_abr_seed_sideload_test` for the ABR ML-DSA seed and
`sep_km_abr_mlkem_sideload_test` for the three ML-KEM cells. Those leaves are
the MUST-fill owners for consume. `sep_km_command_set_rand_test` also writes one
seed-selected classic dest and a directed ABR dest every seed. The sampler
scores `RETURN_ARG` dest_engine when `RESP_CMD` echoes `CMD_KEY_TRANSFER`
with rc 0. A refused dest cannot fill a cell. A raw `WRITE_DATA` fill
cannot. One seed of that leaf does not fill all four classic cells; daily
reseed accumulates.

==== `sep_km_host_cmd_cg`

*Description*: SEP-visible mailbox command IDs that are not generate or transfer.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_cmd` |`CMD_HW_VER`, `CMD_ROM_VER`, `CMD_SRAM_VER`, `CMD_RECOV_ACK`, `CMD_EXEC_ROM`, `CMD_SRAM_LOAD_EXEC`, `CMD_SRAM_EXEC`, `CMD_OTP_READ_LOCK_COLD`
|===

Sampled on the `RESP_CMD` echoed command ID when the latched return code is 0.
`CMD_SRAM_VER` scores its defined failure code. A refused command cannot fill
a success bin. A raw inbound `WRITE_DATA` fill cannot score.

==== `sep_km_wipe_cg`

*Description*: A write of `KM_WIPE_CTRL.wipe_state` with the byte strobe that
carries bit 0.

==== `sep_km_sw_reset_cg`

*Description*: A write of `SW_RESET_N` that releases the KM bit, with the byte
strobe that carries bit 0.

==== `sep_crypto_isolate_cg`

*Description*: The per-IP isolate-then-reset sequencing for the HMAC and Adams Bridge domains.
An accelerator reset waits on both the SEP host path and the Key Manager path,
so the ordering bin reads both completion bits.

Every bin is an EDGE, not a state. Both isolate bits stay high for the whole
reset window, so a state bin would fill on any run that parks HMAC at all --
including one where the reset preceded the drain, which is the thing the
ordering bin exists to catch.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_km_iso` |The cycle the `km_hmac` path reports isolated. The host-side isolation entries never present a transaction on this path; that a KM master path reaches isolation at all is what this bin records.
|`cp_rst_ordered` |The cycle the HMAC gated reset falls, with both the host and Key Manager isolate bits already high. A reset that fell before either bit does not fill this bin.
|`cp_abr_rst_ordered` |The same for the Adams Bridge domain, whose host path is a full-AXI isolate rather than AXI-Lite. The Key Manager bit carries an ABR term; without it the sequencer never releases and this bin cannot fill.
|`cp_reopen` |The cycle `km_hmac` reports un-isolated again, so the path was released rather than left isolated for the rest of the run.

==== `sep_dma_copy_hash_cg`

*Description*: DMA copies memory and computes a hash.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_copy` |`CONTROL.GO` with opcode COPY
|`cp_hash` |`CONTROL.GO` with opcode SHA256
|`cp_hash_opcode` |Which inline-hash opcode was commanded on a `CONTROL.GO`: `sha256`, `sha384`. `cp_hash` above is SHA-256 only, so it does not distinguish a SHA-384 transfer. SHA-512 is a legal opcode (`OpcSha512`) that no leaf commands, so it has no bin rather than a permanent hole.
|`cp_copy_done` |Completion after a COPY GO
|`cp_hash_done` |Completion after a SHA256 GO
|`cp_chunk` |`STATUS.chunk_done` observed while a GO'd transfer is outstanding
|`cp_rego` |A GO with `INITIAL_TRANSFER` = 0, i.e. a continuation chunk
|===

`cp_chunk` and `cp_rego` record the DMA's normal one-chunk-per-GO protocol:
the engine raises `CHUNK_DONE` and drops BUSY, and firmware W1Cs it and re-GOes
until the final chunk reports DONE (`fw/drivers/sep_dma.h`,
`dma_basic_test.c`). That loop is why one transfer produces many GO writes, and
without these two bins it hides inside `cp_copy`. They do not claim the Phase 2
`sep_dma_transfer_cg` enumeration -- chunk sizes, endpoints and range configs
stay there.

Completion is `STATUS.done` OR the DMA-done interrupt
(`sep_internal_interrupts[8]`, `sep.sv:535`), because the suite's firmware uses
both routes: `dma_basic_test` polls `STATUS`, while `dma_hash_test` enables
`INTR_ENABLE.DMA_DONE`, WFIs, and its handler clears `STATUS.done` before
software reads it -- so on that path no `STATUS` read with the DONE bit ever
reaches the bus. A `STATUS`-only bin therefore cannot fill `cp_hash_done`.
The GO'd opcode still labels the cell, so an interrupt cannot score the
wrong one.

The destination-matches-source and digest-matches-golden claims stay in the
DMA firmware. These cells are driven only by the firmware tests
(`sep_dma_basic_test`, `sep_dma_hash_test`, `sep_dma_cpu_contention_test`),
which is why the sampler reads the internal LSU bus: on the flat TB ports they
could not fire at all. Opcode and range errors are Phase 2.

==== `sep_inbound_filter_allow_cg`

*Description*: One legal inbound transaction is allowed.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_allow_wr` |An `m_axi` write OKAY whose address is inside the programmed enabled window
|`cp_allow_rd` |An `m_axi` read OKAY inside that window
|===

The window is decoded from the `FILTER_CONFIG` / `START_ADDR` / `END_ADDR`
writes on the CSR bus. The compare is against the PROGRAMMED range, not its
4 KB page:
`traffic_filter.sv` compares `addr[.:12]` only in its allow_burst arm, and
`addr[.:DataBusWidthLog2]` otherwise, so a page compare is a superset of the
real grant. Comparing the range can only miss a page-widened grant, never
invent one. Both bins are also gated on exactly one outstanding inbound
transaction, like the CSR-side bins -- `sep_axi_order_sweep_m_axi_test` runs
several at once, and a last-write latch would pair one access's response with
another's address.

The window is committed as ONE entry: START and END are latched with their
entry index and are accepted only at the enabling `FILTER_CONFIG` write of that
same entry. Three independent last-writes would otherwise assemble a window out
of one entry's START, another's END and a third's ENABLE -- a window the DUT
never held. The entry count comes from
`sep_pkg::INBOUND_FILTER_NUM_FILTERS`, not a literal.

The full rule matrix, the deny path, and the winner walk over all 48 entries
(inbound `INBOUND_FILTER_NUM_FILTERS` = 16 plus outbound
`OUTBOUND_FILTER_NUM_FILTERS` = 32) are Phase 2.

==== `sep_efuse_sense_cg`

*Description*: Real fuse sense completes.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_done` |A RISING edge of `sep_fuse_sense_done_o`, on a run that did NOT pass `+skip_fuse_sense`
|`cp_episode` |First sense after cold-reset release, and a later re-sense
|===

The episode split follows the FCOV specification's sense-episode coverpoint:
programming a fuse and re-sensing is a distinct event from the bring-up sense.

==== `sep_efuse_program_lock_cg`

*Description*: A spare eFuse field is programmed while unlocked, and refused
once its write-lock is set.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_field` |SPARE0..SPARE8
|`cp_lock` |The target's write-lock state when the program was issued: unlocked, locked
|`x_field_lock` |18 cells
|`cp_outcome` |`PROGRAM_DONE` (programmed) and `PROGRAM_STATUS` (refused)
|===

Programming a write-locked field is a legal software action with a specified
outcome, not a fault injection -- the same class as writing a read-only
register -- so it is Phase 1 and not one of the Phase 2 error groups.

All 18 cross cells are filled by a SINGLE seed:
`sep_efuse_program_lock_matrix_test` walks unlocked-program, then lock, then
reject on each of SPARE0..SPARE8 in order, and only the bit offset inside a
spare is seed-selected. Walking every spare is what makes the slot numbering
falsifiable -- a lock bit wired to the wrong slot would otherwise be caught only
on the seed that happened to draw that spare.

The outcome is a separate coverpoint rather than a third cross dimension: a
`field x lock x outcome` cross would declare 18 cells that only a broken DUT
could fill, and the program-succeeds / lock-refuses contract belongs to the
test's checker.

Everything is decoded frontdoor from `EFUSE_PROGRAM_CTRL` -- `EFUSE_ADDR` plus
`PROGRAM_GO` on the write, `PROGRAM_DONE` / `PROGRAM_STATUS` on the readback --
and the spare index comes from the generated `SEP_EFUSE_MAP_SPARE*` offsets, not
a literal. The spare count comes from the generated `LOCKS_SPARE` reserved-field
shift.

==== `sep_efuse_fail_closed_cg`

[cols="2,5",options="header"]
|===
|Coverpoint |Bins
|`cp_illegal` |`2'b00`, `2'b11` -- the encodings `efuse_read_interface` and `efuse_program_interface` declare unreachable. The legal `2'b01` / `2'b10` land in no bin, so ordinary traffic scores nothing
|`cp_fsm` |`read_if`, `program_if` (`program` is a SystemVerilog keyword)

==== `sep_lc_state_cg`

*Description*: A legal lifecycle state is sensed.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_lc` |TEST_DEV, PROD, RMA_SIP_0, RMA_SIP_1, RMA_CHIP_0, RMA_CHIP_1, PROD_END
|===

This is the one SEED-DEPENDENT group in Phase 1. A W1S write with a token match
moves PROD straight to `RMA_SIP_1` / `RMA_CHIP_1`

==== `sep_lc_transition_cg`

*Description*: A documented lifecycle transition is taken.

[cols=",",options="header"]
|===
|Coverpoint |Bins
|`cp_transition` |Two bins over the packed `{from, to}` pair: PROD to RMA_SIP_1, RMA_SIP_1 to RMA_CHIP_1
|===

`sep_lc_state_cg` records which states were SEEN; this group records which were
TAKEN. A pair is recovered from two `LC_STATE` reads in the same leaf --
`sep_lc_shadow_write_seq` reads ONCE per cell, after its write, so the pair is
two consecutive cells of one leaf, not a before/after pair around one write.
The contributors are `sep_lcc_lc_state_w1s_prod_test`, `_prod_demote_test`
and `_rma_sip_test`.

One packed coverpoint over `{from, to}`. A `cross` of two 7-bin coverpoints
auto-generates the full product; named bins inside the cross do not suppress
those cells.

Only two bins are declared. A pair needs two `LC_STATE` reads inside ONE leaf,
and the `+lc_start` leaves are sensed at PROD, RMA_SIP_0, RMA_CHIP_0 or
PROD_END -- none at TEST_DEV -- so TEST_DEV to PROD has no producer; the
PROD_END/transient leaf advances `0x8` to `0xA`, which is not a named pair, so
it produces nothing here. TEST_DEV to PROD_END and TEST_DEV to RMA_SIP have no
walk either, and PROD to PROD_END is impossible under write-1-to-set at all:
`0x1 | 0x8` is `0x9`. The transition-legality claim stays on
`sep_lcc_golden.lc_state_next`.

=== Maintenance

Add a Phase 1 bin only when an `all`-group test already walks that cell, or
when a new test is added in the same change. A cell the suite does not walk
belongs in the Phase 2 named set. Keep covergroup instance names stable
when a module is added: the URG Group report matches them by hierarchy name.
