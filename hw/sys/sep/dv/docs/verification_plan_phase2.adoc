== What this document is

The record of what Phase 2 verifies and what evidence backs each claim. It follows
`oss_dv_plan.adoc`: one *iconic* feature per in-scope IP, randomized when the feature
has a legal matrix or knob space, plus the cross-IP edges a per-IP bench cannot
see. Phase 1 + Phase 2 together are the cocotb baseline (*> 60%* of SEP,
counted as `PROVEN` *feature* rows on
link:oss_dv_plan.adoc#iconic-scorecard[the iconic scorecard],
not as a count of `PROVEN` checkers). The architecture spec is the denominator; AGP,
local UART/GPIO, proprietary SPI PHY, ROM patch, next-gen DMA-AES, DCLS-in-SEP
and PCR vault are out of that count. A `FAILED` spec-gap is not a 60% credit.

It uses the same grade rules as `verification_plan_phase1.adoc`. Those rules are
not restated here. Read that document first if you are auditing this one.

The short form of the contract: *a row exists only if a run can prove it.* Every
checker names log text a kept Verilator run actually contains. A matching tag in
that log is not the proof — an independent audit still has to show the checker
can fail.

What this document is *not*: a coverage percentage, a 69-name breadth ledger, or
a second copy of Phase 1. Boot ROM *firmware* contracts are out of this plan
(ROM-FW owner). ROM *hardware* access stays: IFU fetch and LSU read/write-ignore.

=== Scope

Phase 2 builds on the Phase 1 baseline rather than replacing it. The 21 Phase 1
representatives are graded only in `verification_plan_phase1.adoc`. This document
grades the net-new Phase 2 entries and *names* the iconic work that is still
open. New tests are created from <<iconic-remaining>> (and from
`verification_plan_phase3.adoc` for corners). Existing tests that still need a
matrix or a stronger checker are <<existing-upgrades>>. A leftover directed
name is not coverage. There is no separate improvement worklist.

[[audit]]
== The audit behind these grades

Every entry graded here was audited against a kept log by an agent that had not written
the test, with one instruction: find checks that cannot fail. That produced 26 findings
across the 22 entries. All 26 are fixed; the fixes are in this branch's history, one
commit per group.

Recording the classes, because they recur and because a reader deciding how much to trust
these grades should know what was wrong before:

*An expectation that shares a source with the thing it measures.* The worst instance:
`sep_hmac_sha_variant_rand_test` ran the engine, asked which of two candidate key word
orders reproduced its digest, and used the winner as the golden for all fourteen keyed
cells. A key-word-order RTL bug would have been selected into the golden and every cell
would have passed — and key word order is exactly the bug class those cells exist to
catch. The convention is now taken from the IP's own register specification --
`vendor/lowRISC/opentitan/upstream/hw/ip/hmac/data/hmac.hjson:446-447` states
`key[1023:0] = {KEY0, KEY1, ... , KEY31}`, so `KEY_0` is the most-significant word and
the software path needs no reversal. The RTL agrees (`hmac.sv:219-221` assigns the key
CSRs into the secret-key vector in reverse index order), and that agreement is
corroboration rather than the source: a golden transcribed from the RTL cannot disagree
with the RTL, which is the same defect class this section is about. The two-candidate
scan survives only as a failure diagnostic that distinguishes a word-order regression
from a general digest fault.

*Golden compared against golden.* Nine asserts across the crypto entries compared a
result already pinned bit-exact to its golden against another output of the same Python
model. Those hold with the simulator switched off. One was weaker still: a KMAC
wrong-mode golden returned four words against an eight-word digest, so the assert
compared list lengths rather than separating domains.

*A guard whose own constructor makes it unfalsifiable.* `sep_sram_datapath_breadth_test`
wrote one address and required a second, *unwritten* address to differ from the written
pattern — but that address holds zero-initialised memory and the pattern is built as
`getrandbits(64) | 1`, so the check was `0 != nonzero`. It could not detect the stuck read
path it names. `sep_fabric_remap_filter_csr_bank_test` anchored non-vacuity on
`start_lo != 0` where the config builds that value as `(random & ~0xFFF) or 0x1000`.

*A stimulus with no fan-out.* `sep_cpu_dbg_reset_independence_test` pulsed `dbg_rstb_i`
and asserted two reset observables stayed released. `hw/sys/sep/doc/port_table.adoc`
names the pin as EL2 debugger reset; it does not require isolation from system reset.
The pin is routed only into `sep_cpu`, and this entry runs the CPU stub, where the
port is unread. The isolation pulse was dropped from the claim — it was a DV-invented
scenario, not a spec hole.

*A tolerance wider than the signal.* `sep_wdt_aon_timer_internals_test` allowed a post-pet
count of up to `0x100` while the pre-pet count only reached 57, so a pet that was ignored
passed. The window is now long enough that the count reaches `0x400`+ first.

*A check that reads back nothing.* `sep_dma_basic_test`'s width walk set `TRANSFER_WIDTH`
to three encodings and never read it back; 16 bytes is a whole multiple of 1, 2 and 4, so
a register stuck at its reset produced byte-identical output all three times.

*Entailed guards.* Complementary-arm ROM-marker absences and flash-WIP DEFERRED
lines were deleted from this plan. They are not checkers. The ROM tests still
assert forbidden markers do not appear; a dual-print still fails the test.

== Grades used here

The same set as Phase 1, with the same meanings. A running test's checkers are
`PROVEN` or `FAILED`. `PARTIAL`, `GUARD`, and `INSUFFICIENT-EVIDENCE` are unused
here. The one `FAILED` row is CHK-OWNERSHIP-WINDOW (RTL vs `hw/sys/sep/doc/fabric.adoc`).

[[entries]]
== Entries

Each entry names its run mode, states what it proves, and lists its checkers with the
evidence that backs them. Proof strings are quoted to their seed-stable prefix: several of
these entries randomise addresses, region indices and message lengths per seed, and the
contract forbids quoting a value that varies with the run.

[[sep_crypto_edn_round_robin_grant_test]]
=== sep_crypto_edn_round_robin_grant_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force`
Testlist:: `crypto.toml` (enrolled in `no_cpu` and `all`)
Status:: Graded. Kept Verilator log `20260820_210207`.

==== Description

`hw/sys/sep/doc/crypto.adoc`: `u_axis_edn_crypto_s3c_scan`
(`drbg_axis_edn_adapter`) is a small round-robin native-protocol EDN fan-out
to AES, KMAC, OTBN RND, and OTBN URND. <<sep_crypto_edn_multisink_arbitration_test>>
proves two clients complete and that their beat *time spans* overlap. It cannot
create a same-cycle dual `edn_req`: AES/KMAC masking reseeds are short pulses
separated by AXI configuration. `sep_drbg_km_vs_crypto_endpoint_concurrency_test`
(compressed into the grant test) is KM vs the crypto *leg*, a different adapter. Extending either
fork does not hold two `edn_req` bits high together.

This test holds AES (crypto_edn[0]) and OTBN URND (crypto_edn[3]) requesting at
once, then brings up the real entropy chain so `prim_arbiter_ppc` inside the
adapter has to grant both. AES masking reseeds pulse `edn_req` per beat, so a
same-cycle dual-req sample at ack often sees only AES; consecutive post-adapter
grants still alternate (AES then URND). That is the round-robin decision.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode with fuse sense skipped.
| `Skipping fuse sense`
| LOGGED

| 2
| Hold AES PRNG reseed and OTBN URND `edn_req` together before EDN is enabled.
| `CHK-DUAL-REQ PASS: crypto_edn_req bits`
| LOGGED

| 3
| Bring up the entropy stack (noise force, seed, then enable EDN).
| `CHK1 golden seeded from live ff_stage`
| LOGGED

| 4
| Sample `crypto_edn_ack_o` until both clients have been granted and consecutive
  grants differ.
| `CHK-NO-STARVE PASS: both clients acked` and `CHK-GRANT-ALT PASS: consecutive grants alternate`
| LOGGED
|===

==== Checkers

[cols="1,4,4,1",options="header"]
|===
| ID | Check | Proof | Status

| PROVEN

NOTE: Standing rule — any test that moves data across the DRBG runs CHK1..CHK4
(strict scoreboard, FIFO drain, `report()`) and enables CHK5 on every live sink.
CHK5 mode is the strongest the stimulus allows: golden when one sink and the pull
order is predictable; membership when more than one crypto sink is live; observe
when firmware-driven order is not golden-predictable (`rom_main`). This test uses
membership. `sep_aes_mode_keysize_rand_test` and
`sep_kmac_mode_strength_rand_test` park unused clients and use routing golden.

[[rom-fw-out-of-scope]]
== Boot ROM firmware — out of this plan

Production Boot ROM firmware contracts (SPI manifest/payload boot, DMA vs PIO
drain, secure-boot RSA, integrity reject / fail loop) are not graded here.
They belong to the ROM-FW owner. This plan keeps ROM *hardware* access only:
`sep_boot_rom_smoke_test` and `sep_rom_sanity_test` in Phase 1 (IFU fetch),
and <<sep_boot_rom_lsu_read_test>> (LSU read / write-ignored). The
`sep_rom_uvm_*` names in <<compress>> are the same HW-access class.

The four implemented ROM-FW tests live in `testlists/rom_fw.toml` and run in
the `all` and `rom_fw` groups, not `cpu` (a CPU-class run is one RTL target).
This plan does not grade them:

* `sep_rom_non_secure_boot_test`
* `sep_rom_ot_dma_boot_test`
* `sep_rom_ot_pio_boot_test`
* `sep_rom_ot_secure_boot_test`

`sep_rom_ot_integrity_reject_test` was deleted with the ROM-FW drop; it is not
a source and is not enrolled. Ownership is recorded in `rom_fw.toml`; when a
ROM-FW plan exists, those four names are graded there.
