== What this document is

The record of what Phase 2 verifies and what evidence backs each claim. It follows the
same contract as `verification_plan_phase1.adoc`, and that document holds the full
statement of the rules — grade definitions, the rejection criteria, the proof-string
requirements. They are not restated here. Read it first if you are auditing this one.

The short form of the contract: *a row exists only if a run can prove it.* Every checker
names log text a kept Verilator run actually contains. A matching tag in that log is not
the proof — an independent audit still has to show the checker can fail.

What this document is *not*: a coverage percentage, and not a forward contract. Phase 2
names 112 testcase-shaped identifiers. One of those, `sep_base_test`, is a base class
rather than a testcase, so there are *111* real candidates: 42 implemented and 69 not.
`sep_drbg_gen_segmentation_test` (named in no original plan) plus
`sep_crypto_edn_round_robin_grant_test` (kept log `20260820_210207`) are extra graded
entries. Boot ROM *firmware* contracts (production ROM boot, SPI manifest/payload
path, secure-boot RSA, integrity reject) are out of this plan — ROM-FW owner, not
this VPLAN. ROM *hardware* access stays: IFU fetch and LSU read/write-ignore.

Implemented hardware entries are graded; the 69 unimplemented original names are
listed in <<backlog>> as names, with no rows and no claims. The `sep_rom_uvm_*`
backlog names are ROM-HW access, not ROM-FW boot.

=== Scope: 43 graded, 22 here

Phase 2 builds on the Phase 1 baseline rather than replacing it, so 21 of the 43 are
already graded in `verification_plan_phase1.adoc`. Those are *not* duplicated here. A
checker with two rows in two documents is a maintenance hazard, and this branch has been
bitten by that shape twice already — an eFuse field map held in both Python and C, and a
set of disable vectors held in both a test and its prestage. Both went stale in one place
and stayed consistent with the other.

== The audit behind these grades

Every entry graded here was audited against a kept log by an agent that had not written
the test, with one instruction: find checks that cannot fail. That produced 26 findings
across the 23 entries. All 26 are fixed; the fixes are in this branch's history, one
commit per group.

Recording the classes, because they recur and because a reader deciding how much to trust
these grades should know what was wrong before:

*An expectation that shares a source with the thing it measures.* The worst instance:
`sep_hmac_sha_variant_rand_test` ran the engine, asked which of two candidate key word
orders reproduced its digest, and used the winner as the golden for all fourteen keyed
cells. A key-word-order RTL bug would have been selected into the golden and every cell
would have passed — and key word order is exactly the bug class those cells exist to
catch. The convention is now taken from the IP's own register specification --
`vendor/lowRISC/opentitan/upstream/hw/ip/hmac/data/hmac.hjson:446-447` states
`key[1023:0] = {KEY0, KEY1, ... , KEY31}`, so `KEY_0` is the most-significant word and
the software path needs no reversal. The RTL agrees (`hmac.sv:219-221` assigns the key
CSRs into the secret-key vector in reverse index order), and that agreement is
corroboration rather than the source: a golden transcribed from the RTL cannot disagree
with the RTL, which is the same defect class this section is about. The two-candidate
scan survives only as a failure diagnostic that distinguishes a word-order regression
from a general digest fault.

*Golden compared against golden.* Nine asserts across the crypto entries compared a
result already pinned bit-exact to its golden against another output of the same Python
model. Those hold with the simulator switched off. One was weaker still: a KMAC
wrong-mode golden returned four words against an eight-word digest, so the assert
compared list lengths rather than separating domains.

*A guard whose own constructor makes it unfalsifiable.* `sep_sram_datapath_breadth_test`
wrote one address and required a second, *unwritten* address to differ from the written
pattern — but that address holds zero-initialised memory and the pattern is built as
`getrandbits(64) | 1`, so the check was `0 != nonzero`. It could not detect the stuck read
path it names. `sep_fabric_remap_filter_csr_bank_test` anchored non-vacuity on
`start_lo != 0` where the config builds that value as `(random & ~0xFFF) or 0x1000`.

*A stimulus with no fan-out.* `sep_cpu_dbg_reset_independence_test` pulsed `dbg_rstb_i`
and asserted two reset observables stayed released. `hw/sys/sep/doc/port_table.adoc`
names the pin as EL2 debugger reset; it does not require isolation from system reset.
The pin is routed only into `sep_cpu`, and this entry runs the CPU stub, where the
port is unread. The isolation pulse was dropped from the claim — it was a DV-invented
scenario, not a spec hole.

*A tolerance wider than the signal.* `sep_wdt_aon_timer_internals_test` allowed a post-pet
count of up to `0x100` while the pre-pet count only reached 57, so a pet that was ignored
passed. The window is now long enough that the count reaches `0x400`+ first.

*A check that reads back nothing.* `sep_dma_basic_test`'s width walk set `TRANSFER_WIDTH`
to three encodings and never read it back; 16 bytes is a whole multiple of 1, 2 and 4, so
a register stuck at its reset produced byte-identical output all three times.

*Entailed guards.* Complementary-arm ROM-marker absences and flash-WIP DEFERRED
lines were deleted from this plan. They are not checkers. The ROM tests still
assert forbidden markers do not appear; a dual-print still fails the test.

== Grades used here

The same set as Phase 1, with the same meanings. A running test's checkers are
`PROVEN` or `FAILED`. `PARTIAL`, `GUARD`, and `INSUFFICIENT-EVIDENCE` are unused
here. The one `FAILED` row is CHK-OWNERSHIP-WINDOW (RTL vs `fabric.adoc`).

== Entries

Each entry names its run mode, states what it proves, and lists its checkers with the
evidence that backs them. Proof strings are quoted to their seed-stable prefix: several of
these entries randomise addresses, region indices and message lengths per seed, and the
contract forbids quoting a value that varies with the run.

[[sep_aes_mode_keysize_rand_test]]
=== sep_aes_mode_keysize_rand_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force`
Testlist:: `crypto.toml`

==== Description

Walks the nine-cell product of {ECB, CBC, CTR} x {128, 192, 256} in one invocation, with
key, IV and plaintext randomised per cell. Each cell's ciphertext is compared bit-exact
against `env/sep_aes_golden.py`, which self-tests at import against FIPS-197 C.1/C.2/C.3
and SP800-38A F.2.1/F.5.1 — so the expectation is independent of the DUT.

==== Steps

@@STEPS:sep_aes_mode_keysize_rand_test@@

==== Checkers

[cols="1,4,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-CELL
| Per cell: the ciphertext equals the golden, the round trip returns the plaintext, and
  no alert fired. For ECB and CBC the round trip programs a real DECRYPT operation; for
  CTR it re-runs ENCRYPT, which is a keystream-determinism check rather than a decrypt.
| `CHK-CELL PASS AES-ECB-128: ct==golden, round-trip==pt, no alert, non-vacuous`
| PROVEN

| CHK-RAND-REP
| All nine cells ran in one invocation, and produced nine *distinct* ciphertexts — so
  they really did program nine different configurations. Two cells that silently ran the
  same mode and key size on the same inputs would collide.
| `CHK-RAND-REP PASS: walked all 9 discrete cells`
| PROVEN
|===

Testlist:: `crypto.toml`

==== Description

Walks 17 cells: keyed HMAC over every legal key length for each of SHA-256/384/512, plus

==== Steps

@@STEPS:sep_hmac_sha_variant_rand_test@@

==== Checkers

[cols="1,4,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-CONV
| The engine honours the *specified* software-key register convention.
  `hmac.hjson:446-447` defines `key[1023:0] = {KEY0, ... , KEY31}`, so `KEY_0` is the

  The convention is pinned from the specification, not discovered by asking the engine
  which one it agrees with, and not transcribed from the RTL it checks — see <<audit>>. On mismatch

| `CHK-CONV PASS: engine honours the specified SW-key convention`
| PROVEN

| Per cell: the digest equals the golden, the done interrupt sets and clears on
  write-one-to-clear, and the error status is clean.
| `CHK-CELL PASS HMAC-SHA256/Key_128: DIGEST==golden, RW1C done, ERR clean, non-vacuous (msg=`
| PROVEN

| CHK-RAND-REP
| All 17 cells ran, producing 17 distinct digests.
| `CHK-RAND-REP PASS: walked all 17 discrete cells`
| PROVEN
|===

NOTE: `CHK-ERR` is a passive observation — `ERR_CODE` and the error interrupt bit are
read and required to be zero, but nothing in this entry induces an error, so there is no
positive control that the register can ever be non-zero on this path.

[[sep_crypto_edn_round_robin_grant_test]]
=== sep_crypto_edn_round_robin_grant_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force`
Testlist:: `crypto.toml` (enrolled in `no_cpu` and `all`)
Status:: Graded. Kept Verilator log `20260820_210207`.

==== Description

`hw/sys/sep/doc/crypto.adoc`: `u_axis_edn_crypto_s3c_scan`
(`drbg_axis_edn_adapter`) is a small round-robin native-protocol EDN fan-out
to AES, KMAC, OTBN RND, and OTBN URND. <<sep_crypto_edn_multisink_arbitration_test>>
proves two clients complete and that their beat *time spans* overlap. It cannot
create a same-cycle dual `edn_req`: AES/KMAC masking reseeds are short pulses
separated by AXI configuration. `sep_drbg_km_vs_crypto_endpoint_concurrency_test`
in the backlog is KM vs the crypto *leg*, a different adapter. Extending either
fork does not hold two `edn_req` bits high together.

This test holds AES (crypto_edn[0]) and OTBN URND (crypto_edn[3]) requesting at
once, then brings up the real entropy chain so `prim_arbiter_ppc` inside the
adapter has to grant both. AES masking reseeds pulse `edn_req` per beat, so a
same-cycle dual-req sample at ack often sees only AES; consecutive post-adapter
grants still alternate (AES then URND). That is the round-robin decision.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode with fuse sense skipped.
| `Skipping fuse sense`
| LOGGED

| 2
| Hold AES PRNG reseed and OTBN URND `edn_req` together before EDN is enabled.
| `CHK-DUAL-REQ PASS: crypto_edn_req bits`
| LOGGED

| 3
| Bring up the entropy stack (noise force, seed, then enable EDN).
| `CHK1 golden seeded from live ff_stage`
| LOGGED

| 4
| Sample `crypto_edn_ack_o` until both clients have been granted and consecutive
  grants differ.
| `CHK-NO-STARVE PASS: both clients acked` and `CHK-GRANT-ALT PASS: consecutive grants alternate`
| LOGGED
|===

==== Checkers

[cols="1,4,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-DUAL-REQ
| At least one cycle both selected clients have `edn_req` high. Without this,
  CHK-GRANT-ALT is vacuous.
| `CHK-DUAL-REQ PASS: crypto_edn_req bits 0x9 (AES bit 0 + URND bit 3)`
| PROVEN

| CHK-GRANT-ALT
| After that dual request, consecutive post-adapter grants go to different
  clients — the round-robin decision, not interval-span overlap.
| `CHK-GRANT-ALT PASS: consecutive grants alternate (grants=[0, 3]`
| PROVEN

| CHK-NO-STARVE
| Each requesting client receives at least one `edn_ack` in the window.
| `CHK-NO-STARVE PASS: both clients acked (AES grants=1 URND grants=1)`
| PROVEN
|===

NOTE: Next PR — standing rule, not this change-set. Any test that moves data
across the DRBG must run CHK1..CHK4 (`strict=True`, FIFO drain, `report()`) and
enable CHK5 on every live sink. CHK1..CHK4 are always allowed on a real entropy
bring-up. CHK5 mode is the strongest the stimulus allows: `golden` when one sink
and the pull order is predictable; `membership` when more than one crypto sink is
live (each word is a CHK4 genbits word; dual-sink bit-exact routing needs the
unported arbiter-assignment trace); `observe` when firmware-driven order is not
golden-predictable (`rom_main`). This test, `sep_aes_mode_keysize_rand_test`, and
`sep_kmac_mode_strength_rand_test` currently cross DRBG with `strict=False` and
no `report()`.

[[sep_drbg_gen_segmentation_test]]
=== sep_drbg_gen_segmentation_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force +km_rom_hex=km_rom_entropy.parhex`
Testlist:: `crypto.toml`
Randomization:: RAND-NONE — directed `glen=4`. One length is the feature.

==== Description

Phase 2 DRBG iconic feature: a CSRNG Generate command completes at the commanded
length, `gen_last` asserts, and the trailing CTR_DRBG Update runs. Every other
entropy test leaves that half of CHK4 unexercised because `EDN.BOOT_GEN_CMD`
resets to `glen=4095` and `EDN_CTRL_AUTO` sets `BOOT_REQ` — so the first Generate
is the boot command, not `GENERATE_CMD`.

`SepEntropyCfg(glen=4, program_boot_generate=True)` is the single source of truth:
it writes `BOOT_GEN_CMD`, `GENERATE_CMD`, and the golden. Existing tests leave
`program_boot_generate` False so their one-open-command CHK4 budgets stay put.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

| 1
| Bring up in `no_cpu` mode with fuse sense skipped.
| `SEP timing: sys_clk_period=` then `Skipping fuse sense`
| LOGGED

| 2
| Release the Key Manager with the small entropy-consuming ROM image.
| `AXI write 0x10803000 <- 0x1f (ok=True resp=0)`
| LOGGED

| 3
| Program the boot Generate and the auto Generate to `glen=4` from the same config
  object that feeds the golden.
| `AXI write 0x1091581c <- 0x4903 (ok=True resp=0)` and `AXI write 0x10915830 <- 0x4903 (ok=True resp=0)`
| LOGGED

| 4
| Bring up the entropy stack, drain the source queue through the front door, and
  wait for generated bits and a Key Manager consume.
| `CHK1 golden seeded from live ff_stage` and `CHK2 frontdoor: drained`
| LOGGED

| 5
| Require at least one completed Generate of exactly four blocks, then report the
  strict CHK1..CHK5 scoreboard.
| `CHK4-SEGMENTATION PASS:` then `==== sep_drbg_scoreboard CHK1..CHK5 report ====`
| LOGGED
|===

==== Checkers

[cols="1,4,4,1",options="header"]
|===
| ID | Check | Proof | Status

| CHK-SEGMENTATION
| At least one Generate command completed, and every completed command carried exactly
  the commanded `glen=4` blocks — so `gen_last` was observed, the trailing Update ran,
  and a segment of any other length would fail.
| `CHK4-SEGMENTATION PASS:`
| PROVEN

| CHK1..CHK4
| The entropy stack matches its golden bit-exactly at each stage, including across the
  Update boundary this entry forces, strict mode, reported.
| `CHK4_genbits   dut_items=4 match=4 mismatch=0`
| PROVEN

| CHK5

then stops producing genbits -- the Key Manager ROM reads one word and parks.
That is enough for the legality check to execute. A second AUTO Generate after
the Update is not claimed.

== Boot ROM firmware — out of this plan

Production Boot ROM firmware contracts (SPI manifest/payload boot, DMA vs PIO
drain, secure-boot RSA, integrity reject / fail loop) are not graded here.
They belong to the ROM-FW owner. This plan keeps ROM *hardware* access only:
`sep_boot_rom_smoke_test` and `sep_rom_sanity_test` in Phase 1 (IFU fetch),
and <<sep_boot_rom_lsu_read_test>> (LSU read / write-ignored). The
`sep_rom_uvm_*` names in <<backlog>> are the same HW-access class.
