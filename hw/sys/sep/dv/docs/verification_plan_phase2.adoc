== What this document is

The record of what Phase 2 verifies and what evidence backs each claim. It follows
`oss_dv_plan.adoc`: one *iconic* feature per in-scope IP, randomized when the feature
has a legal matrix or knob space, plus the cross-IP edges a per-IP bench cannot
see. Phase 1 + Phase 2 together are the cocotb baseline: floor 18 of 40,
goal 25 of 40 in-scope rows, counted as `PROVEN` *feature* rows on
link:oss_dv_plan.adoc#iconic-scorecard[the iconic scorecard],
not as a count of `PROVEN` checkers and not as line coverage. Those are
scorecard goals, not coverage measurements. The architecture spec is the
denominator. Excluded for OSS hygiene: peripherals outside bare SEP, and
proprietary IPs in nonfree. Excluded as deferred: AGP, local UART/GPIO,
ROM patch, next-gen DMA-AES, DCLS-in-SEP and PCR vault. A `FAILED`
spec-gap is not a feature credit.

It uses the same grade rules as `verification_plan_phase1.adoc`. Those rules are
not restated here. Read that document first if you are auditing this one.

The short form of the contract: *a row exists only if a run can prove it.* Every
checker names log text a kept Verilator run actually contains. A matching tag in
that log is not the proof — an independent audit still has to show the checker
can fail.

What this document is *not*: a code-coverage number, a 69-name breadth
ledger, or a second copy of Phase 1. RTL line, expression, and user
coverage are collected by the nightly Verilator run and graded nowhere
yet; this document grades features. Boot ROM *firmware* contracts are out
of this plan (ROM-FW owner). ROM *hardware* access stays: IFU fetch and
LSU read/write-ignore.

=== Scope

Phase 2 builds on the Phase 1 baseline rather than replacing it. The 21 Phase 1
representatives are graded only in `verification_plan_phase1.adoc`. This document
grades the net-new Phase 2 entries and *names* the iconic work that is still
open. A leftover from the signed-off Phase 1 handoff table is covered
here: extend a Phase 2 test that already owns that claim, or add the
named new test.
Do not stretch the Phase 1 e2e / smoke entry. New tests are created
from <<iconic-remaining>> when no Phase 2 vehicle exists. <<phase2-plus>>
is the completeness extension: same cocotb environment, goal 34 of 40
`PROVEN` scorecard rows. <<phase2-plus-plus>> is block activation (38 of
40); it is planned here and implemented in a follow-on PR, before Phase 3
starts a UVM bench.
Phase 3 corners stay T.B.D. in `verification_plan_phase3.adoc`. A leftover
directed name is not coverage. There is no separate improvement
worklist.

The active attention set is entropy (ESRC / DRBG / EDN), lifecycle,
eFuse, and Key Manager. See <<attention>>.

[[audit]]
== The audit behind these grades

Every entry graded here was audited against a kept log by an agent that had not written
the test, with one instruction: find checks that cannot fail. That produced 26 findings
across the 22 entries. All 26 are fixed.

Recording the classes, because they recur and because a reader deciding how much to trust
these grades should know what was wrong before:

*An expectation that shares a source with the thing it measures.* The worst instance:
`sep_hmac_sha_variant_rand_test` ran the engine, asked which of two candidate key word
orders reproduced its digest, and used the winner as the golden for all fourteen keyed
cells. A key-word-order RTL bug would have been selected into the golden and every cell
would have passed — and key word order is exactly the bug class those cells exist to
catch. The convention is now taken from the IP's own register specification --
`vendor/lowRISC/opentitan/upstream/hw/ip/hmac/data/hmac.hjson:446-447` states
`key[1023:0] = {KEY0, KEY1, ... , KEY31}`, so `KEY_0` is the most-significant word and
the software path needs no reversal. The RTL agrees (`hmac.sv:219-221` assigns the key
CSRs into the secret-key vector in reverse index order), and that agreement is
corroboration rather than the source: a golden transcribed from the RTL cannot disagree
with the RTL, which is the same defect class this section is about. The two-candidate
scan survives only as a failure diagnostic that distinguishes a word-order regression
from a general digest fault.

*Golden compared against golden.* Nine asserts across the crypto entries compared a
result already pinned bit-exact to its golden against another output of the same Python
model. Those hold with the simulator switched off. One was weaker still: a KMAC
wrong-mode golden returned four words against an eight-word digest, so the assert
compared list lengths rather than separating domains.

*A guard whose own constructor makes it unfalsifiable.* `sep_sram_datapath_breadth_test`
wrote one address and required a second, *unwritten* address to differ from the written
pattern — but that address holds zero-initialised memory and the pattern is built as
`getrandbits(64) | 1`, so the check was `0 != nonzero`. It could not detect the stuck read
path it names. `sep_fabric_remap_filter_csr_bank_test` anchored non-vacuity on
`start_lo != 0` where the config builds that value as `(random & ~0xFFF) or 0x1000`.

*A stimulus with no fan-out.* `sep_cpu_dbg_reset_independence_test` pulsed `dbg_rstb_i`
and asserted two reset observables stayed released. `hw/sys/sep/doc/port_table.adoc`
names the pin as EL2 debugger reset; it does not require isolation from system reset.
The pin is routed only into `sep_cpu`, and this entry runs the CPU stub, where the
port is unread. The isolation pulse was dropped from the claim — it was a DV-invented
scenario, not a spec hole.

*A tolerance wider than the signal.* `sep_wdt_aon_timer_internals_test` allowed a post-pet
count of up to `0x100` while the pre-pet count only reached 57, so a pet that was ignored
passed. The window is now long enough that the count reaches `0x400`+ first.

*A check that reads back nothing.* `sep_dma_basic_test`'s width walk set `TRANSFER_WIDTH`
to three encodings and never read it back; 16 bytes is a whole multiple of 1, 2 and 4, so
a register stuck at its reset produced byte-identical output all three times.

*Entailed guards.* Complementary-arm ROM-marker absences and flash-WIP DEFERRED
lines were deleted from this plan. They are not checkers. The ROM tests still
assert forbidden markers do not appear; a dual-print still fails the test.

== Grades used here

The same set as Phase 1, with the same meanings. A running test's checkers are
`PROVEN` or `FAILED`. `PARTIAL`, `GUARD`, and `INSUFFICIENT-EVIDENCE` are unused
here. Two `FAILED` checkers are RTL vs spec: CHK-OWNERSHIP-WINDOW
(`hw/sys/sep/doc/fabric.adoc`) and CHK-DEADSPACE-REFUSE
(`hw/sys/sep/doc/memory_map.adoc`,
https://github.com/tenstorrent/tt-oca-harness/issues/228).

[[entries]]
== Entries

Each entry names its run mode, states what it proves, and lists its checkers with the
evidence that backs them. Proof strings are quoted to their seed-stable prefix: several of
these entries randomise addresses, region indices and message lengths per seed, and the
contract forbids quoting a value that varies with the run.

[horizontal]

[[sep_crypto_edn_round_robin_grant_test]]
=== sep_crypto_edn_round_robin_grant_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force`
Testlist:: `crypto.toml` (enrolled in `no_cpu` and `all`)
Status:: Graded. Kept Verilator log `20260822_135844`.

==== Description

`hw/sys/sep/doc/crypto.adoc`: `u_axis_edn_crypto_s3c_scan`
(`drbg_axis_edn_adapter`) is a small round-robin native-protocol EDN fan-out
to AES, KMAC, OTBN RND, and OTBN URND. <<sep_crypto_edn_multisink_arbitration_test>>
proves two clients complete and that their beat *time spans* overlap. It cannot
create a same-cycle dual `edn_req`: AES/KMAC masking reseeds are short pulses
separated by AXI configuration. `sep_drbg_km_vs_crypto_endpoint_concurrency_test`
(compressed into the grant test) is KM vs the crypto *leg*, a different adapter. Extending either
fork does not hold two `edn_req` bits high together.

This test holds AES (crypto_edn[0]) and OTBN URND (crypto_edn[3]) requesting at
once, then brings up the real entropy chain so `prim_arbiter_ppc` inside the
adapter has to grant both. AES masking reseeds pulse `edn_req` per beat, so a
same-cycle dual-req sample at ack often sees only AES; consecutive post-adapter
grants still alternate (AES then URND). That is the round-robin decision.

[[sep_drbg_gen_segmentation_test]]
=== sep_drbg_gen_segmentation_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu` (`lsu_stub_all_live`), `+skip_fuse_sense +esrc_noise_force +km_rom_hex=km_rom_entropy.parhex`
Testlist:: `crypto.toml`
Randomization:: RAND-NONE — directed `glen=4`. One length is the feature.

==== Description

Phase 2 DRBG iconic feature: a CSRNG Generate command completes at the commanded
length, `gen_last` asserts, and the trailing CTR_DRBG Update runs. Every other
entropy test leaves that half of CHK4 unexercised because `EDN.BOOT_GEN_CMD`
resets to `glen=4095` and `EDN_CTRL_AUTO` sets `BOOT_REQ` — so the first Generate
is the boot command, not `GENERATE_CMD`.

`SepEntropyCfg(glen=4, program_boot_generate=True)` is the single source of truth:
it writes `BOOT_GEN_CMD`, `GENERATE_CMD`, and the golden. Existing tests leave
`program_boot_generate` False so their one-open-command CHK4 budgets stay put.

==== Steps

[cols="1,4,4,1",options="header"]
|===
| # | Step | Proof | Status

[[open-items]]
== Open items

Hard `FAILED` spec-vs-RTL (keep hard; do not XFAIL):

* CHK-DEADSPACE-REFUSE — an access to the unpopulated remainder of a block's
  address window owns no register and must be refused per
  `hw/sys/sep/doc/memory_map.adoc`. In several blocks the RTL truncates the
  address, wraps it inside the block, hits a live register and answers OKAY.
  Owned by `sep_fabric_deadspace_decode_test`. Keep the full probe set; do
  not shrink it to the addresses that already pass.

* CHK-OWNERSHIP-WINDOW — only the SEP CPU may program the inbound filter per
  `hw/sys/sep/doc/fabric.adoc`; the RTL answers OKAY instead of DECERR to
  another master. Owned by `sep_fabric_inbound_filter_rule_matrix_test`.

Spec-vs-RTL divergences found by review, not yet owned by a checker. Each is a
document or manifest defect rather than a failing test; none is XFAILed, because
no test asserts them today:

* `hw/sys/sep/doc/crypto.adoc` numbers the two entropy-pool interrupts one lower
  than the canonical table in `hw/sys/sep/doc/interrupts.adoc`. PIC source IDs
  are 1-based, so aggregation index 36/37 is PIC source 37/38; `crypto.adoc`
  quotes the 0-based index. Firmware following it would enable and mask the
  wrong two sources.
* `hw/sys/sep/doc/cpu.adoc` documents a CPU reset-vector TDR selected by a JTAG
  opcode, through which a debugger may redirect the first instruction fetch. The
  vendored tap implements no such register; the vector reaches the CPU through a
  direct wrapper input. The testbench shifts that opcode on every CPU-boot run
  and says in its own comment that the sequence is inert — a stimulus that reads
  as coverage and cannot fail. Remove it or give the claim an owner.
* `hw/sys/sep/doc/fabric.adoc` gives the AP/STEE remappers a cacheable attribute
  and says unprogrammed regions are transparent pass-throughs. The RTL register
  has neither a valid bit nor a cacheable bit, and rewrites the address
  unconditionally, so an unprogrammed region zeroes the upper address bits
  instead of passing through. Phase 2+ `sep_fabric_local_alias_datapath_test`
  owns the live-beat offset proof and keeps any missing-bit check a hard
  FAIL. Do not XFAIL.
* `hw/sys/sep/doc/attack_countermeasures.adoc` states "exactly 10" Class 2 scan
  roots. The RTL instantiates an eleventh on the entropy-pool EDN leg that is
  absent from the list, and nothing lints the manifest against the RTL. The
  manifest is the sole input deciding what is never scan-dumpable.
* `hw/sys/sep/doc/fabric.adoc` does not name the wrap same-page 4 KB
  widen in `hw/common/axi/axi_filter/rtl/axi_filter_wrap.sv`. With
  `allow_burst=1`, a programmed window that sits in one 4 KB page is
  rewritten to that whole page, so a range smaller than a page
  over-grants. The matrix programs a two-page window so that rewrite
  does not fire and does not assert the over-grant. Spec owner to name
  or reject the behavior; until then it is not a third `FAILED`.

DV-tree hygiene, tracked here so it is not mistaken for coverage: of the
firmware tests under `fw/tests/`, only a small minority are named by any
testlist or cocotb test; the rest cannot run. Some are superseded by cocotb
vehicles and some are parked Phase 3 stubs, but nothing distinguishes those
from tests that should be running — two of them would close scorecard rows
above. Triage is needed before any of them is cited as evidence.

[[sep_fabric_deadspace_decode_test]]
=== sep_fabric_deadspace_decode_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu`, `+skip_fuse_sense`
Testlist:: `system.toml`
Randomization:: RANDCFG — the twelve known-bad offsets from
https://github.com/tenstorrent/tt-oca-harness/issues/228 every seed,
plus two seed-selected dead offsets per block window

Negative control, and a hard `FAILED` on landing. Each block owns an
address window and populates only part of it. Per
`hw/sys/sep/doc/memory_map.adoc` the unpopulated remainder owns no
register and the access must be refused. In several SEP blocks the RTL
truncates the address instead, wraps it back inside the block, lands on a
live register and answers OKAY, so software is never told. A one-byte
write nearly 4 kB past the end of the Key Manager mailbox block sets both
error bits in its `SEP_CTRL`; the mailbox keeps five address bits, the
watchdog six, EDN and CSRNG seven, the entropy source and Secure DMA nine.

The address windows themselves match the specification. The defect is the
truncation before the register block, not a window that is too wide — do
not "fix" this by narrowing a window in the plan. Allocated size comes
from the generated export; window end comes from `memory_map.adoc`. RTL
decode width is never the legality judge.

Refuse means not-OKAY (DECERR or SLVERR). A write probe must also leave
every allocated register unchanged. A checker that only inspects the
response would pass the day the RTL starts answering DECERR while still
writing the register.

Keep the probe set whole. Shrinking it to the offsets that already pass
turns a hard red green without changing any RTL, which is the one outcome
this entry exists to prevent. Do not XFAIL it.

== Phase 2++ — block activation, 38 of 40

Same cocotb / PyUVM + Verilator environment. <<phase2-plus>> closes the
feature rows the plan scoped. Phase 2++ closes a different hole: blocks the
DUT instantiates that no registered test reaches at all. A block with no
scorecard row cannot show up as a `GAP`, so these were invisible rather
than deferred. The exit criterion is stated as a rule, not a count: every
block instantiated in the SEP DUT is exercised by at least one registered
test.

*This is not a code-coverage close-out.* RTL line, expression and user
coverage stay Phase 3 and are gated by no threshold here. "38 of 40" is a
scorecard-row count, not a percentage of anything, and the two numbers
must not be quoted together. What Phase 2++ closes is block activation:
every instantiated block has a registered test that can fail.

Implementation order, cheapest and most certain first. Do not start with
Adams Bridge:

. The isolate extension — no new vehicle, no firmware, and the in-window
  refuse plus sibling-OKAY pair is a real new check.
. The entropy pool aperture — reuses the existing entropy bring-up.
. The KM CRC known-answer test — dedicated ROM, independent golden.
. The KPV scrambler — dedicated ROM. Settle first whether the scrambler
  enable is a firmware-legal CSR toggle, and confirm it is *not* the KM
  SRAM scrambler that `rom_main` already locks; those are different
  claims and conflating them would invalidate the vehicle.
. Adams Bridge keyGen last — time one masked ML-DSA-87 before writing any
  checker. If wall-clock demands it, drop the sensitivity leg; never drop
  the NIST compare. Anchor the aperture on `sep_crypto_pkg`, not the
  firmware header.

Outside Phase 2++, and still open after 38 of 40 — these are not blocks,
so closing this phase must not be read as closing them: the LCC debug-gate
outputs (unobserved ports, Phase 3); a non-zero inbound global aperture,
where DV only ever runs the identity case that production does not use;
the 4 KB filter over-grant, an open specification question; and the Key
Manager command set, which stays parked.

=== Planned: sep_abr_mldsa_keygen_kat_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu`, `+skip_fuse_sense`
Testlist:: `crypto.toml`
Randomization:: RANDCFG — the masking entropy words, and the seed word and
bit flipped in the sensitivity leg, from the run seed

The aperture is a `sep_crypto` demux rule at `ABR_REG_MAP_BASE_ADDR`
(`hw/sys/sep/rtl/sep_crypto_pkg.sv`), reachable from the CPU-LSU master the
way the OTBN tests already reach their block. It is *not* behind

Two facts the implementer must not rediscover. First, the aperture is a
SystemVerilog localparam, not a generated address-map symbol — the
firmware header's hardcoded base is correct but unanchored, and nothing
fails if the localparam moves. Anchor on the package, and say so.
Second, `hw/sys/sep/dv/shims/crypto/abr_wrapper_key_reg_stub.sv` replaces
the *Key-Manager-side* key CSR block only; the ABR register block behind
this aperture is real RTL. But that stub ties every key share and
`key_valid` to zero, so the key-vault seed path cannot produce a real key
in this build. Only the software-written seed path is honest here.

Checkers (planned):: the identity registers read the documented block
name; the block leaves reset ready, not valid, not errored; the public key
read back after keyGen equals the vendored NIST vector word for word; the
completion status asserts within budget with no error; the notification
PIC source rises on completion and the error source stays low.

Anti-vacuity control:: the proof artefact is a public key that is a
cryptographic function of the seed words written over the bus, so a write
path that does not land yields a different key, not a passing one. There
is no "did not change" check anywhere on the proof path. The sensitivity
leg makes it explicit: flip one seed bit, and the key must differ from the
vector the previous leg just matched. An engine returning a cached or
constant result passes the first leg and fails the second.

Settle before coding, in this order. Time one keyGen before writing any
checker — ML-DSA-87 with masking on is Keccak- and NTT-heavy, and if it is
too slow for a daily regression the fallback is to drop the sensitivity
leg's second keyGen, never the known-answer check. Then confirm the
sequence places 32-bit beats correctly on the 64-bit port at an odd word
offset, because this path has no width converter and a lane-placement bug
would look exactly like a functional failure. Then read the vendored
register description for the real offsets rather than trusting the
firmware header, which nothing has ever run.

Two existing firmware tests target this block and are in no testlist. The
CSR one checks a version register against "nonzero", which is a guess
rather than a contract and can fail a correct DUT. The keyGen one seeds
arbitrarily and checks only that the key is not all zero, which any engine
emitting anything at all would pass. Fix them to use the NIST vectors and
keep them as a firmware-path companion, or delete them — but do not
register them as they stand.

The block is a 64 KB crossbar target reachable from the same master the

Checkers (planned):: a pop on an empty pool is refused and a pop with data
is not; a pop decrements the level by exactly one; the status fields agree
with the observed level and the pool never reports an internal error; the

sources track their status bits.

Anti-vacuity control:: four ordered facts, all required. The pool must be
observed at or above the watermark at least once — if it never filled,
every refusal in the test is meaningless and the test fails rather than
skips. Both an accepted pop and a refused pop must occur, accepted first.
The low-water flag must be seen high, then low, then high again, proving
traversal rather than a stuck signal. And at least one popped word must be
non-zero with two popped words differing, because the FIFO returns zero
when empty by construction and a dead datapath would otherwise produce a
refusal-shaped pass.

Known design hazard:: while the entropy source is still streaming, the
pool can refill between the drain burst and the status read, so the
watermark crossing may not be observed. Take that observation after
disabling the entropy source, not before. The disable value must keep every
multi-bit field at a legal encoding so the write does not provoke a
recoverable alert.

ISR re-entry — needs CPU mode and a firmware image. This test observes the
aggregator bits only, the same evidence class as the existing aggregator
test. Pool drain, watermark and stall corners stay deferred in
`verification_plan_phase3.adoc`.

=== Planned: sep_km_crc_pcpi_kat_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu`, `+skip_fuse_sense`, dedicated KM ROM image
Testlist:: `km.toml`
Randomization:: RANDCFG — the vector set, from the run seed

The CRC engine has no register interface at all. It is a PicoRV32 PCPI
co-processor reached by a custom-0 instruction, so the only honest
activation is KM firmware, in the ROM pattern the vault test established.
The assembler has no mnemonic for the instruction, so the image emits
encoded words; the KM core is built without the upper register file, so
the encoding macro must reject a register number outside the lower half at
assembly time rather than silently misbehaving.

Checkers (planned):: each mode's result equals an independently written
host-side golden; the word mode and the byte mode agree with each other
when chained, which is a hardware-only cross-check independent of the
golden; the two polynomial modes give different results for the same
input; and the narrow mode leaves the upper result bits clear.

Anti-vacuity control:: the golden values are asserted non-zero and
pairwise distinct before any comparison, so a vector set that degenerates
to zero fails at construction rather than passing. The vector generator
rejects inputs whose golden equals an operand. And one vector is computed
in the deliberately wrong mode and asserted to *differ* — a co-processor
stubbed to return a plausible constant passes a known-answer test but
fails a required difference.

Warning for the implementer:: the engine applies no initial value and no
final inversion. Reusing the wrapped CRC helper already in the sequence
library gives a wrong golden — and the dangerous outcome is not the false
failure, it is someone then "fixing" the golden to match the DUT. Write
the bare stepping function independently and check it against the register
description.

=== Planned: sep_km_kpv_scrambler_test

[horizontal]
Tier:: Tier 2
Run mode:: `no_cpu`, `+skip_fuse_sense`, dedicated KM ROM image
Testlist:: `km.toml`
Randomization:: RANDCFG — the scrambler key, the target slot and word, and
the plaintext, from the run seed

The vault is reachable only from the KM side, so this needs its own ROM
image. The design avoids a hierarchical peek entirely: with the scrambler
disabled the vault addresses its register file with the logical index and
passes data through unmodified, so firmware can write plaintext with
scrambling on, disable it, and read the raw stored words back through a
legitimate frontdoor. Do not set the key lock until the final checker —
locking is sticky.

Checkers (planned):: the written word round-trips exactly with scrambling
enabled; exactly one word in the raw scan is non-zero and it differs from
the plaintext; that word sits at a different index than the logical one,
proving the address tweak; the same plaintext under a different key stores
a different word, proving the scrambler is actually keyed; and after the
key lock the key register reads back zero while the round-trip still
recovers the plaintext, which is the security contract of the lock.

Anti-vacuity control:: requiring *exactly one* non-zero word in the raw
scan is what makes the confidentiality claim real. A write that never
landed gives zero non-zero words and fails; a read path stuck at zero
gives zero and fails. A bare "stored differs from plaintext" check would
pass in both cases. Round-trip is a required conjunct, so a scrambler that
destroys data cannot pass by looking scrambled. The plaintext is chosen
with mixed nibbles because the substitution is nibble-wise and a uniform
value would weaken the difference signal.

Not claimed here:: the eraser's use of the shared scrambler, the seal and
retire contracts already owned by the vault test, and key wipe.

=== Extension: sep_crypto_per_ip_reset_isolation_test

`sep_crypto_axi_isolate` sits between the crypto demux and the four engine
wrappers, and each wrapper's reset is the isolate's gated output — so the
existing test already drives its state machine on every reset pulse. The
block is unproven, not unactivated: nothing is checked during the window.
The pulse already holds reset for a fixed span with no bus traffic, and
that dead time is the isolation window.

Checkers (planned):: during the window a read and a write to the resetting
engine are refused rather than served or hung; the reset request is
confirmed to have landed in the register, so a refusal cannot be blamed on
a write that never took; a sibling engine answers normally in the same
window, proving isolation is port-scoped; the port reopens after release;
and the engine's registers read their reset defaults afterwards.

Anti-vacuity control:: the same address, from the same driver, in the same
run, must answer OKAY before the request, refused during it, and OKAY
again after release. An unmapped or permanently dead address cannot
produce that sequence. The pre-window read also returns the engine's live
result, which is already value-checked against an independent golden, so
"the engine was alive at that address" is established rather than assumed.

Not claimed, and recorded as such:: the drain-before-reset ordering. The
AXI agent issues one blocking single-beat transaction at a time, so no
transaction can be left outstanding when the request is asserted; a
long-running crypto operation does not help, because the isolate counts
outstanding bus transactions rather than engine busyness, and there is no
second master on the crypto demux. The properties inside the unit that
would show the ordering are compiled out under the acceptance simulator.
Closing this needs a non-blocking mode in the AXI agent or a simulator
where those properties are live — both separate work. Do not reach for a
`force` to manufacture the observation.

If an in-window access hangs instead of being refused, that is the fabric
stall this block exists to prevent. File it; do not relax the checker.
