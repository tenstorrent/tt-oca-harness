= Direct Memory Access (DMA)

[[sep-dma]]

ifdef::backend-html5[]
++++
<span id="direct-memory-access-controller-dma-direct-memory-access-controller-dma"></span>
++++
endif::backend-html5[]

The SEP DMA copies data between addressable memories and peripheral registers,
with optional inline SHA-256, SHA-384 or SHA-512 hashing. It uses the
https://opentitan.org/book/hw/ip/dma/index.html[OpenTitan DMA Controller]
inside an AXI wrapper. The integration below defines which upstream ports
and hardware triggers are available in SEP.
The Programmer's Guide gives the
ifdef::backend-html5[]
xref:ocah-programmer-guide::index.adoc#sep-dma[programming guidance]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-programmer-guide/latest/index.html#sep-dma[programming guidance]
endif::backend-pdf[]
for this block.

Source and destination addresses independently support incrementing, fixed
address and wrap-at-chunk-boundary operation. Use incrementing addresses for
memory and a fixed address for a peripheral FIFO. Transfers use 1-, 2- or
4-byte accesses; inline hashing requires 4-byte transfers. The core issues
individual TL-UL transactions, so the AXI wrapper does not turn a copy into
a burst transfer. Hash results are read from the DMA digest registers.

[[och-modifications]]
== OCAH Modifications

<<sep-dma-integration-figure>> shows how `sep_dma_wrap` connects the DMA core
to the SEP local crossbar. The register path runs left to right along the top
and the host path right to left along the bottom; green boxes are converters,
and the dashed ports are tied off.

[[sep-dma-integration-figure]]
.SEP secure DMA integration
image::sep-dma.svg[alt="sep_dma_wrap with the secure_dma core, its register-path and host-path converters, the local alias remap and the tied-off CTN and SYS ports",width=100%,pdfwidth=100%]

The wrapper exposes separate AXI4 register-slave and DMA-master interfaces,
both with 32-bit addresses and 64-bit data. Internally, the register path
converts AXI4 to 32-bit AXI4-Lite and then TL-UL; the data path converts the
core's TL-UL host port back to AXI4. A local-alias remapper precedes the SEP
crossbar and leaves the CPU TCM backdoor range available to DMA.

Address-space ID `0x7` selects the core's internal host port, the only route
in this wrapper. The upstream SoC control and system ports are tied off; their ASIDs do not provide
additional SEP routes. Reachability is governed by the SEP fabric and filters.

The master path leaves AxUSER at zero and drives AxPROT `0b001` (privileged,
secure, data), the value the SEP CPU's LSU drives; TL-UL carries no protection
attributes, so the wrapper sets it. The register and host bridges latch
faults on `dma_reg_bus_err_o` and `dma_host_intg_err_o`, cleared through
`DMA_BUS_ERR_CLEAR`; local alert receivers aggregate the core alerts into
`dma_alert_o`. Selecting the tied-off CTN or SYS address space does not complete.

Only handshake input 0 is connected, to the SPI host's LSIO trigger.
All other trigger inputs are tied low; SEP does not wire UART or I3C handshake paths.
This does not prevent software-initiated accesses to reachable peripheral registers.

[[sep-dma-completion]]
=== Completion Reporting

The core reports transaction completion, chunk completion and error separately.
Chunk completion applies to multi-chunk transfers without hardware handshake;
it is not a per-trigger interrupt in handshake mode. Status completion and error
bits are write-one-to-clear; the detailed register map defines each bit. Inline
hashing requires 4-byte transfers, and `DIGEST_SWAP` controls byte order within
each digest register, not register order. The
ifdef::backend-html5[]
xref:ocah-programmer-guide::index.adoc#sep-dma[SEP DMA section]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-programmer-guide/latest/index.html#sep-dma[SEP DMA section]
endif::backend-pdf[]
of the Programmer's Guide gives the copy, hashing, handshake and abort
sequences.

[[future-enhancements]]
== Future Enhancements

The following are proposals, not capabilities of the current SEP integration:

* Inline AES encryption or decryption (with/without inline hashing)
* Inline hashing with only digest written to target slave
* Optimize implementation by using cryptographic resources (AES,
HMAC-SHA2) engines inside the cryptographic subsystem and adding
streaming interfaces

* Replace the FSM controller with a microsequencer or simple CPU, potentially
  shared with the Key Manager
