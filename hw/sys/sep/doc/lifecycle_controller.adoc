[[life-cycle-controller-lcc-life-cycle-controller-lcc]]

The Life Cycle Controller (LCC) converts the OTP lifecycle state and owner
restrictions into `feat_ctrl_o`, the 64-bit vector that enables debug and
functional features. Two volatile demotion controls can change the debug
profile for the current boot without changing OTP.

The OTP controller supplies `LC_STATE`, `SIP_DIS` and `SYS_DIS` after fuse
sensing. The LCC checks the differentially encoded state and disables features
on an integrity error, except when the final `SEC_DIS` override forces them on.
Downstream logic uses these outputs to gate debug, test and functional paths.

The sections below explain states and security domains, feature-control rules,
demotion, scan protection and firmware authorization. Hardware gating is
implemented; the secure-boot signing model in <<demote-signing-model,Firmware Authorization>>
specifies the manifest policy the 1.0 SEP Boot ROM enforces. The 0.5 ROM does
not implement it.

<<sep-lifecycle-controller-figure>> shows a high-level view of the Life Cycle Controller
components.

[[sep-lifecycle-controller-figure]]
.SEP lifecycle controller
image::sep-lifecycle-controller.svg[alt="sep_lifecycle_ctrl: LC_STATE decoder, feature control decode, security-disable override, debug and DFT disable derivation, register block and demotion encoders",width=100%,pdfwidth=100%]

In <<sep-lifecycle-controller-figure>>, the inputs enter on the left and the
outputs leave on the right, each labelled with its consumer. `u_lc_state_dec`
decodes the differentially encoded LC_STATE from the eFuse shadow registers and
raises `lc_sigint_err` on a non-complementary codeword, which forces the feature
control decode to all zeros. While `security_disable_i` is high, the
multiplexer replaces the decoded vector with all ones, even on an integrity
error. The `lc_sigint_err` line crosses the `security_disable_i` line without
connecting; the gap marks the crossing.

The debug and DFT disable derivation turns the `sip_debug`, `chiplet_dbg`,
`sep_debug`, `sep_fuse_dbg` and `smc_fuse_dbg` bits of the result into the 11
debug disables for the DTP and the two fuse DFT disables. No functional logic
consumes the fuse DFT disables; they leave the SMU for adopter DFT insertion.
The `demote` and `lock` bits of DEMOTE_1 and DEMOTE_2 are set-only: firmware
can set `demote` only while `lock` is clear, and both hold until SEP cold
reset. The demote bits feed the feature control decode and, through the
differential encoders, the Key Manager and the SEP outputs.

[[lc-state-machine]]
== Lifecycle States

The LCC decodes the OTP controller's `LC_STATE` shadow output; it does not
sequence lifecycle transitions itself. Before fuse sensing completes, that
output holds INVALID (`4'b1111`). The LCC then follows the sensed state and
its feature-control profile.

The raw four-bit OTP value is carried as a complementary code in the shadow
path. A failed integrity check sets `lc_sigint_err` and forces the base feature
vector to zero. `SEC_DIS` is applied afterward and can override that result;
see <<feat-ctrl-overrides-and-gates>>.

Hardware orders the RMA token transitions: `RMA_SIP_TOKEN` first admits
RMA_SIP, then `RMA_CHIPLET_TOKEN` admits RMA_CHIPLET. Volatile demotion is
separate from those transitions and does not change the OTP state.

Key Manager includes DEMOTE_1/2 with CHIPLET_UID, SIP_UID, SYS_UID and LC_STATE
in key derivation, separating demoted-state keys from non-demoted production
keys.

[[multiple-security-domains]]
== Multiple Security Domains

The SiP owner controls the debug-access network between chiplets. Each chiplet
owner controls access to its own local assets. A system has one shared
SiP-owner domain and a local domain for each chiplet with independently
protected assets.

`SIP_DBG` admits and forwards external debug traffic at each chiplet with a
local SEP/LCC. Access to local resources additionally requires `CHIPLET_DBG`;
SEP resources also require `SEP_DBG`. Opening another chiplet's local debug
gate is unnecessary when traffic only passes through it.

A chiplet without a local SEP/LCC contributes no local disable vector.
The preceding LCC-bearing chiplet controls forwarding to it, as described
in <<non-primary-chiplets>>.

In <<sep-security-domains-figure>>, each chiplet with a SEP gates the debug
path from its PTAP downwards: SIP_DBG opens the Case 1 targets, CHIPLET_DBG adds
the Case 2 targets and SEP_DBG adds the Case 3 targets, each listed to the right
of its gate. The targets are the debug paths that `sep_lifecycle_ctrl` disables
through `dbg_disable_o` and the two fuse DFT disables, as given in
<<dtp-path-gating>>; the fuse DFT paths also need their own SEP_FUSE_DBG or
SMC_FUSE_DBG bit. The green gate belongs to the SiP-owner domain and is a DBG_2
bit, opened in the field by Demotion 2. The cream gates belong to the

* Chiplet 2 access requires `SIP_DBG(1)`; chiplet 2 adds no local gate.
* Chiplet 3 local debug requires `SIP_DBG(1)`, `SIP_DBG(3)` and
  `CHIPLET_DBG(3)`. It does not require `CHIPLET_DBG(1)`.

The per-path conjunctions are listed in <<dtp-path-gating>>.

[[debug-test-and-functional-feature-control-vectors-debug-test-and-functional-feature-control-vectors]]
== Debug and Functional Feature Control

`feat_ctrl_o` uses positive logic: 1 enables a feature. The 64-bit
`SIP_DIS` and `SYS_DIS` shadows use negative logic: 1 restricts a feature.
The applicable masks depend on lifecycle state and demotion. Where both
apply, the enable is `~(SIP_DIS | SYS_DIS)`.

<<feature-control-table>> gives the complete state-dependent formulas.
The final `SEC_DIS` override is described in <<feat-ctrl-overrides-and-gates>>.

[[feature-control-vector-definition]]
=== Disable Vector Format (SIP_DIS / SYS_DIS)

<<sep-feature-disable-vector-table>> defines the *disable* vector format -- the bit layout shared by
both SIP_DIS and SYS_DIS (each is 64 bits). Each defined bit gates a specific
feature or its associated scan chain; the remaining bits are
reserved for adopter extension (see <<asset-and-scan-chain-protection>> and
<<adopter-extension>>).

In the policy tables, `T` means enabled and `F` means disabled.
A clear disable bit permits a feature only where the lifecycle profile
allows it; it does not by itself open a production debug path.

DBG_1 covers `[23:0]` and is controlled by Demotion 1. DBG_2 covers `[47:24]`
and is controlled by Demotion 2. Function bits occupy `[63:48]`.

[[dis-vector-ownership]]
=== DIS Vector Ownership: Predecessor-Programs-Disables

The vector name identifies the receiving owner, not the programmer:

* The chiplet creator programs `SIP_DIS` before SiP handoff. Its restrictions
  remain effective in RMA_SIP and are bypassed in RMA_CHIPLET.
* The SiP owner programs `SYS_DIS` before system handoff. Its restrictions
  are bypassed in RMA_SIP and RMA_CHIPLET.

RMA bypass does not erase either fuse vector. The system owner has no
successor and therefore no third disable vector. It provisions its own
`SYS_PUBK_HASH` and `SYS_UID` before TEST_DEV-to-PROD transition; see the
OTP Fuse Controller chapter for the provisioning sequence.

[[dis-vector-or-rationale]]
=== Combining Rule: OR then Invert

Where both owner masks apply, a feature is disabled if either mask has its
bit set. OR combines the restrictions; inversion produces the positive-logic
enable. Since an OTP bit can only change from 0 to 1, a later owner cannot
erase an earlier owner's programmed restriction. Lifecycle profiles can
bypass masks for RMA access without changing OTP.

[[feat-ctrl-overrides-and-gates]]
=== Overrides and Final Gates (SEC_DIS)

Two controls sit *on top of* the per-LC-state / DIS-vector computation, applied in
this order (a later step overrides an earlier one):

. *Signal-integrity fail-closed (base):* if the differentially encoded LC_STATE
fails its integrity check (`lc_sigint_err`), the base `feat_ctrl` is forced to
all-0s (all features disabled).

. *SEC_DIS override:* when `SEC_DIS = 1`, `feat_ctrl` is forced to all-1s -- every
feature enabled, regardless of the LC state, the DIS vectors, or the sigint
result (an emergency bring-up bypass on A0 silicon; see the Security Disable
section).

`SECURE_TM` is *not* a term in `feat_ctrl_o`. No feature control bit is qualified
by secure test mode: the debug group `[47:0]` and the function group `[63:48]`
are both determined solely by the LC state, the DIS vectors, and the SEC_DIS
override. `secure_tm` acts on the scan path and on the fuse controller rather
than on feature control -- see <<secure-tm-vs-scandump>>.

[[demote-1-2-in-field-debug-demotion]]
== In-Field Debug Demotion

`DEMOTE_1` and `DEMOTE_2` each contain a `demote` bit and a `lock` bit.
They are two registers, not separate demotion and lock register banks.
Cold reset clears both and removes the volatile debug profile.

[cols="1,1,3",options="header"]
.SEP demotion controls
|===
|Register |Feature group |Scope
|`DEMOTE_1` |DBG_1, bits `[23:0]` |Local debug, including SEP and chiplet gates.
|`DEMOTE_2` |DBG_2, bits `[47:24]` |Inter-chiplet debug access and forwarding, including `SIP_DBG`.
|===

The controls are independent: either may be set first or used alone.
In TEST_DEV, demotion forces its group open; in PROD, it enables the group
subject to the disable vectors. Other lifecycle profiles and function bits
are unchanged. The complete formulas are in <<feature-control-table>>.

Opening local debug does not open the external access path. For example,
a Case 3 SEP debug path requires both groups; see <<dtp-path-gating>>.
The LCC applies register values without authenticating the writer or a
manifest. Firmware authorization is discussed under
<<lcc-firmware-policy,Firmware Authorization>>.

[[demote-lock-behavior]]
=== Programming and Locking

Both `demote` (bit 0) and `lock` (bit 1) are write-one-to-set fields.
Writing zero does not clear them. While `lock` is zero, firmware can set
`demote`; once locked, the demotion decision cannot change until cold reset.
The lock can commit either a demoted or a non-demoted state. The
ifdef::backend-html5[]
xref:ocah-programmer-guide::index.adoc#sep-lifecycle-demotion[demotion sequence]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-programmer-guide/latest/index.html#sep-lifecycle-demotion[demotion sequence]
endif::backend-pdf[]
is in the Programmer's Guide.

This is the hardware mechanism. Authorization follows the signing policy: the
demotion registers are written by a boot stage whose manifest was authenticated
against the `REQUIRED_SIGNERS` and `REQUIRED_ALGS` values in force for that
manifest (<<secure-boot-signing-model>>), so an owner whose co-signature those
values require on that manifest controls the demotion decision. The 0.5 ROM's
manifest handling is documented in the Boot ROM chapter.

[[demote-reset-behavior]]
=== Reset Behavior

SEP cold reset clears the `demote` and `lock` fields in both registers.
The LCC then applies the profile of the sensed OTP state without demotion.

[[asset-and-scan-chain-protection]]
== Asset and Scan-Chain Protection

Two distinct DFT operations use the scan chains, and the protection model
treats them differently:

* *Scan test* -- shift in a test pattern, run the functional clock for one or
two cycles, then shift the result out. Used for manufacturing / DFT coverage.
* *Scan dump* -- shift the live internal state out directly. Used for debug.

The integration must preserve test coverage without exposing live secrets.
The rules below define the required scan partitioning and command gates;
feature-vector generation alone does not implement or verify DFT insertion.

[[asset-classes]]
=== Asset Classes

SEP assets are partitioned into three classes. Class 1 (non-scannable) and
Class 2 (scannable for test coverage but *never* scan-dumpable) are each split by
protection rationale -- *a* for confidentiality and *b* for integrity. Class 3 is
everything else.

<<sep-security-asset-classes-table>> relates the asset classes to scan and scan-dump
treatment.

[[secure-tm-vs-scandump]]
=== `secure_tm` and the Secure Scan Chain

`secure_tm` is the secure-test-mode indicator: the `TEST_EN` strap latched into
the internal `SECURE_TM` signal. It is latched when SEP fuse sensing completes
if `SEC_DIS` is not asserted, or on chiplet cold-reset release if `SEC_DIS` is
asserted (see the Test Mode section).

`secure_tm` establishes the required test configuration; it does not identify
or authenticate the owner at the JTAG port. The protection rules require it to:

. Admit test commands on the secure chain only while asserted.
. Block updates to `LOCKS`, `LC_STATE`, `SIP_DIS` and `SYS_DIS` from SEP,
  OTP, JTAG and TRoot while the part is shiftable.
. Hold OTP write-enable inputs inactive.
. Disconnect UID and `CLASS_KEY` shadow outputs from downstream consumers.

Secure-chain access requires both an open SIB, under the feature gates in
<<dtp-path-gating>>, and an allowed command. Test commands require
`secure_tm = 1`; dump commands are never allowed, for any owner or lifecycle
state. With `secure_tm = 0`, no command is admitted on that chain.

These conditions distinguish Class 1 from Class 2. Class 1 registers contain
secrets or state that directly controls protection, so they are excluded from
scan. Class 2 consumers and fuse-program controls may be scanned only with
their secret sources disconnected and the fuse-write path blocked. The
feature bits control reachability; they do not waive these command rules.

The adopter's DFT implementation must enforce this separation. General
Class 3 chains follow their debug gates and do not use `secure_tm` as an
additional gate.

[[non-primary-chiplets]]
== Non-Primary Chiplets

Primary chiplets always include a local SEP and LCC; the asset
partitioning described in <<asset-and-scan-chain-protection>> applies
directly. *Non-primary* chiplets may not include a local SEP, in which
case debug access is governed by the *SiP-owner domain*. The primary
chiplet's SiP-owner feature control gates the DFT traffic before forwarding
it to the non-primary chiplet (see <<multiple-security-domains>>).

For non-primary chiplets, the adopter is responsible for:

* Identifying which non-primary chiplet assets require protection.
* Partitioning those assets across scan chains analogous to the
class scheme in <<asset-classes>> (1a/1b, 2, 3).
* Routing the non-primary chiplet's scan / DFT traffic through the
appropriate DTP path on the primary chiplet, where SiP-owner feature
control gates forwarding.
* Applying the same scan-protection treatment to any non-primary chiplet
logic that handles secrets: Class 1 excluded from scan chains, Class 2
never scan-dumpable.

The `SIP_DBG` mechanism documented in
<<feature-control-vector-definition>> gates the DTP path on the primary
chiplet. The primary LCC therefore governs debug access to a non-primary
chiplet by controlling whether DFT traffic is forwarded to it.

[[adopter-extension]]
== Adopter Extension

If an adopter integrates SEP into a chiplet with assets that require
their own scan-chain protection -- assets not covered by the
chiplet-scope SEP scan chain or the general-logic scan chain in
<<asset-and-scan-chain-protection>> -- the LCC architecture
accommodates this via the *reserved bits* in `feat_ctrl_o` (and the
matching positions in SIP_DIS / SYS_DIS):

* Debug group: bits 5-23 (DBG_1, 19 reserved bits) and bits 25-47 (DBG_2, 23 reserved bits)
* Function group: bits 48-63 (16 reserved bits)

OCAH assigns no standard function to these reserved bits. An adopter may
allocate a DBG_2 bit to an additional inter-chiplet DFT forwarding path; the
bit is consumed on the LCC-bearing chiplet to gate the corresponding traffic
before it is forwarded downstream.

Each new scan chain or forwarding path is gated by exactly one reserved bit. The
corresponding bit position in SIP_DIS or SYS_DIS (chosen by which
predecessor owner sets the default policy -- see
<<dis-vector-ownership>>) determines the default OTP-programmed
restriction.

Constraints any adopter extension must satisfy:

* *One feature control bit per scan chain.*

* *Asset-class compliance.* Secret-bearing fields used by the new chain
must follow the asset-class scheme (see <<asset-and-scan-chain-protection>>):
actual secrets and integrity-critical state are excluded from scan chains
(Class 1). A Class 2 chain must never admit a dump command. It may admit
test commands only while `secure_tm = 1`, with secret sources disconnected
and fuse programming blocked as specified above. The chain's feature-control
bit controls reachability; it does not authorize a dump.

* *Per-LC-state policy.* The new bit follows the standard
per-LC-state formulas for its group (see <<feature-control-table>>).
DBG_1 and DBG_2 are disabled in undemoted PROD and in PROD_END;
their respective demotion controls relax PROD to honor the disable vectors.
Function bits continue to honor `~(SIP_DIS.FUNC | SYS_DIS.FUNC)` in both
production states and are unaffected by demotion. All groups follow their
listed TEST_DEV and RMA policies and the SEC_DIS override.

NOTE: The specific bit-allocation convention -- which reserved bits
are reserved for which adopters, and how bit assignments are advertised
in the RDL / package outputs -- is currently *open* and will be defined
in a future revision of this specification.

[[secure-boot-signing-model]]
=== Secure-Boot Signing Model

#*[Changed]*#
This section specifies the manifest signing policy that the 1.0 SEP Boot ROM
enforces whenever the Secure Boot Decision above requires a verified manifest.
SEP ROM is a Consumer of the OCA Payload Manifest. It verifies every signature
a manifest declares, as that specification requires, and it adds the device
policy held in four fields of the OTP Fuse Controller: `REQUIRED_SIGNERS`,
`REQUIRED_ALGS`, `SIGNATURE_REVOKE` and `PUBK_REVOKE`. The policy applies to
every OCA Payload Manifest the boot chain verifies. The 0.5 ROM does not
implement this model.

#*[Changed]*#
A public key is trusted only if its digest matches a digest embedded in SEP ROM
or one of the fused digests `CHIPLET_PUBK_HASH0/1`, `CHIPLET_PUBK_PQC_HASH0/1`,
`SIP_PUBK_HASH0/1`, `SIP_PUBK_PQC_HASH0/1`, `SYS_PUBK_HASH` and
`SYS_PUBK_PQC_HASH`, and only while that key is not revoked.

#*[Changed]*#
*Terms.* The following terms are used throughout this section. Each one names
specific bits of a fuse field or of the manifest.

ROOT:: #*[New]*# the entity that signs the main manifest, or the verifier key entry when the
manifest sets `use_verifier_key`. The manifest names its ROOT key by its key
number N: it sets bit N of `public_key_select_classic` or
`public_key_select_pqc`, and the owner of key N is the ROOT. Key numbers are
those of `PUBK_REVOKE`, where bit N revokes key N. The ROOT of the BL1 manifest,
which SEP ROM verifies, shall be the chiplet creator. The ROOT of a later-stage
manifest, which BL1 or a later boot stage verifies, shall be the owner named by
the ROOT owner code.
ROOT owner code:: #*[New]*# `REQUIRED_SIGNERS[43:40]`, a one-hot value defined in
<<sep-cosigner-owner-codes-table>> that names the ROOT of a later-stage
manifest. All-zero names the chiplet creator, as `0b0010` does. SEP ROM does
not use it.
Engaged entity:: #*[New]*# an entity whose signatures a given manifest carries: the
ROOT always; the verifier key when the manifest sets
`use_verifier_key`; co-signer N when the manifest sets `co_signer_enable` bit
N-1.
Declared signature:: #*[New]*# a signature the manifest itself says it carries. For the
ROOT these are selected by `secure_boot_classic` and `secure_boot_pqc` in the
manifest's `secure_boot_control`; for the verifier key, by
`verifier_key_classic` and `verifier_key_pqc` in the verifier key entry's
`verifier_flags`; for co-signer N, by `co_signer_signed_classic` and
`co_signer_signed_pqc` in that co-signer entry's `co_signer_flags`.
Type field:: #*[New]*# the manifest field that names the algorithm of a declared signature:
`signature_type_classic` and `signature_type_pqc` for the ROOT,
`verifier_signature_type_classic` and `verifier_signature_type_pqc` for the
verifier key, and `co_signer_signature_type_classic` and
`co_signer_signature_type_pqc` for a co-signer.
Required-co-signer mask:: `REQUIRED_SIGNERS[7:0]`. Bit N-1 set means
co-signer N is required (bit 0 is co-signer 1, bit 7 is co-signer 8).
Owner code of co-signer N:: #*[Changed]*# `REQUIRED_SIGNERS[4N+7:4N+4]`, a one-hot value
defined in <<sep-cosigner-owner-codes-table>>. It is used only when
`REQUIRED_SIGNERS` bit N-1 is set.
Anchored key:: #*[New]*# a co-signer entry's public key whose digest matches one of the
device digests in <<sep-cosigner-owner-codes-table>> and that is not revoked.
A co-signer entry carries one key for each signature it declares. The entry is
anchored to an owner when every one of those keys is an anchored key of that
owner, whether or not the signature made with it is skipped. The OCA Payload
Manifest does not authenticate co-signer keys; anchoring is how SEP does.
Algorithm minimum of an entity:: #*[Changed]*# the two bits of `REQUIRED_ALGS` that say which
groups that entity's declared signatures must include. The ROOT's
are `REQUIRED_ALGS[0]` (classical) and `REQUIRED_ALGS[1]` (post-quantum); the
verifier key's are `REQUIRED_ALGS[4]` and `REQUIRED_ALGS[5]`; co-signer N's are
`REQUIRED_ALGS[4N+4]` and `REQUIRED_ALGS[4N+5]`. A set bit means the entity
must declare a signature of that group. Both bits clear set no minimum. The
two bits above each pair, `REQUIRED_ALGS[3:2]`, `[7:6]` and `[4N+7:4N+6]`, are
reserved. Co-signer N's four bits, `REQUIRED_ALGS[4N+7:4N+4]`, occupy the same
positions as its owner code in `REQUIRED_SIGNERS`.
Signature-algorithm class:: #*[Changed]*# one entry of the `SIGNATURE_REVOKE` bit map, as
listed in <<sep-signature-classes-table>>. The classical classes are
`SIGNATURE_REVOKE[7:0]` and the post-quantum classes `SIGNATURE_REVOKE[31:24]`.
The class of a declared signature is the one the table lists for the value of
its type field. A value the table does not list is reserved and has no class.
Revoked class:: #*[Changed]*# a class whose `SIGNATURE_REVOKE` bit is set.
Disabled group:: #*[Changed]*# the classical group when `SIGNATURE_REVOKE[15:8]` holds the
constant `0xCA`, or the post-quantum group when `SIGNATURE_REVOKE[39:32]` holds
`0xAC`. These two bytes are the group codes; see _Group codes_ under
<<signature-algorithm-revocation>>.
Revoked key:: #*[Changed]*# a key whose bit in `PUBK_REVOKE` is set. For one manifest only, a
key is also revoked when that manifest carries it, as a ROOT key it selects or
as a key of one of its co-signer entries, and sets the bit of that key in its
own `public_key_classic_revoke` or `public_key_pqc_revoke`.
See _Revoking a key_ under <<policy-fuse-updates>>. Key revocation is
independent of class revocation.
Policy in force:: #*[Changed]*# the values held in the shadow registers of the four policy
fields when a manifest is verified. At cold reset they hold the fused values; a
later boot stage may change `REQUIRED_SIGNERS` and `REQUIRED_ALGS` as described
under _Policy propagation_ below.

#*[Changed]*#
*Verification entities.* An OCA Payload Manifest can carry signatures from
three kinds of entity. The _ROOT_ signs the main manifest with a key whose
digest the device holds. The ROOT of the BL1 manifest is the chiplet creator,
whose digests are embedded in SEP ROM or fused in `CHIPLET_PUBK_HASH0/1` and
`CHIPLET_PUBK_PQC_HASH0/1`. The ROOT of a later-stage manifest is the owner
that the ROOT owner code names: the chiplet creator, unless the role has been
handed to the SiP owner or the system owner. A _verifier key_ is a second
public key carried in a verifier key entry appended to the manifest and itself
signed by the ROOT; when the manifest sets `use_verifier_key`, the main manifest is
signed by the verifier key rather than by the ROOT directly, so the chain is
ROOT -> verifier key entry -> main manifest. This lets the ROOT keep its keys
offline and authorize a developer or third-party signer without
provisioning that signer's key. _Co-signers_ are up to eight further signature
entries appended to the manifest; the manifest enables each with a bit of its
`co_signer_enable` field, and each entry carries its own public key(s),
signature(s) and type fields. The OCA Payload Manifest defines the
co-signer mechanism but leaves to the Consumer which co-signers must be present
and whose keys they must use; for SEP, `REQUIRED_SIGNERS` supplies that choice.

NOTE: #*[New]*# The OCA Payload Manifest also keeps two device-stored values for verifier
keys: a verifier-key revocation state, updated from `verifier_key_id_revoke`,
and a verifier security version, updated from `verifier_security_version`.
This revision defines no fuse field for either. Until it does, a verifier key
cannot be revoked on a part, and the verifier security version cannot be
enforced.

|`0b1000` |System owner

#*[New]*#
Every other value, including `0b0001`, is reserved. There is no owner code that
accepts a key no device digest vouches for.

#*[Changed]*#
*Requirement rule.* SEP ROM authenticates a manifest only if all of the
following hold. Each later boot stage applies the same rule to the manifest it
verifies, using the policy in force at that time. On a boot in which SEP ROM
authenticated the BL1 manifest, each later stage shall verify the manifest it
loads. Steps 1 to 5 verify what the manifest declares, as the OCA Payload
Manifest requires of a Consumer. Step 6 adds the device's minimum. A manifest
shall also pass the two format checks on `signature_class_revoke` given under
_Group codes_ in <<signature-algorithm-revocation>>. A manifest shall also
carry, in `manifest_identifier`, the value defined for the stage that verifies
it: SEP ROM accepts only the value of the BL1 manifest, and each later stage
only its own. The values are defined with the SEP Boot ROM.

. #*[New]*# *A ROOT signature is declared.* The manifest sets
`secure_boot_classic`, `secure_boot_pqc` or both. A manifest that declares no
ROOT signature is rejected, whatever the fuses hold.
. #*[Changed]*# *The class of every signature to be verified is implemented and not revoked.*
This step applies to each declared signature of the ROOT, of the verifier key
and of every enabled co-signer entry. SEP ROM takes the class of the signature
and applies the first of these that fits.
If no declared ROOT signature is left to verify after skipping, the manifest is
rejected. When `use_verifier_key` is set, the manifest is also rejected if no
declared signature of the verifier key is left to verify after skipping.
* #*[Changed]*# A signature of a disabled group is _skipped_: it is not verified and does not
cause rejection.
* #*[New]*# A signature that has no class, or whose class this ROM does not implement,
causes the manifest to be rejected.
* #*[Changed]*# A revoked class causes the manifest to be rejected, whether or not the
signature would verify mathematically.
. #*[Changed]*# *ROOT.* For each declared ROOT signature, the select field of its group,
`public_key_select_classic` or `public_key_select_pqc`, shall have exactly one
bit set. That bit shall name a key of that group that is not reserved, whose
digest is programmed and that is not a revoked key, and the public key the
manifest carries shall match the digest of that key. A fused digest that reads
all-zero is not programmed. The owner of the key, as given in
<<sep-cosigner-owner-codes-table>>, shall be the chiplet creator for the BL1
manifest, and the owner named by the ROOT owner code, `REQUIRED_SIGNERS[43:40]`,
for a later-stage manifest. These conditions apply even when the signature is
skipped. Each declared ROOT signature that is not skipped shall then verify
under that key. When `use_verifier_key` is clear these signatures cover the
main manifest; when it is set they cover the verifier key entry.
. #*[Changed]*# *Verifier key.* When `use_verifier_key` is set, the verifier key entry is
authenticated as in step 3, and each declared signature of the verifier key
over the main manifest that is not skipped verifies under the public key
carried in the entry.
. #*[Changed]*# *Co-signers.* Every co-signer entry the manifest enables passes the
structural checks the OCA Payload Manifest requires of a Consumer: exactly one
entry for each enabled slot, no entry without an enable bit, a matching entry
hash, the correct entry size and a valid combination of signed flags. A
manifest that leaves co-signer N disabled while `REQUIRED_SIGNERS` bit N-1 is
set is rejected. For each enabled co-signer N:
* #*[Changed]*# Each declared signature of the entry that is not skipped shall verify under
the public key the entry carries for it, and at least one declared signature
shall be left to verify after skipping; otherwise the manifest is rejected.
This applies whether or not co-signer N is required and whether or not the
entry is anchored.
* #*[Changed]*# If `REQUIRED_SIGNERS` bit N-1 is set, the entry shall be anchored to the
owner named by `REQUIRED_SIGNERS[4N+7:4N+4]`; otherwise the manifest is
rejected.
* #*[Changed]*# An entry that is not anchored names no owner. Its signatures show only
that the entry is well formed.
* #*[New]*# If a key the entry carries is a revoked key, the manifest is rejected,
whether or not co-signer N is required and whether or not the signature made
with that key is skipped.
. #*[Changed]*# *Minimum.* For each engaged entity, the declared signatures include every
group whose bit is set in that entity's algorithm minimum, unless that group is
disabled. A co-signer's minimum applies only when its `REQUIRED_SIGNERS` bit is
set. `REQUIRED_ALGS` sets a minimum and never selects what is verified: a
manifest that declares more than the minimum must have all of it verify, and
both bits clear mean only that no particular group is demanded.

#*[Changed]*#
*Policy propagation.* The fused values of `REQUIRED_SIGNERS` and
`REQUIRED_ALGS` set the policy for the BL1 manifest. At cold reset the
fuse-sensing FSM loads both fields into their shadow registers, and SEP ROM
verifies the BL1 manifest against the shadow registers, which at that point
hold the fused values. A boot stage whose manifest has been authenticated may
then change the shadow registers to set the policy for the next manifest it
verifies:

* #*[Changed]*# In the `REQUIRED_SIGNERS` shadow register it may set or clear bits of `[7:0]`
and change an owner code, so a later manifest can require more co-signers,
fewer, or different ones. It may also change the ROOT owner code, `[43:40]`, to
hand the ROOT role for later manifests to another owner.
* #*[Changed]*# The `REQUIRED_ALGS` shadow register is set-only. A stage may raise an
entity's minimum for later manifests and cannot lower it, which keeps the
device minimum the one-way ratchet the OCA Payload Manifest defines.

#*[Changed]*#
The next cold reset reloads the fused values. Firmware enforces this
propagation; there is no hardware gate on the policy, and a stage whose
manifest has been authenticated is trusted to set the policy for its successor.
The write-locks BL1 sets on these two fields close their fuses only, as
<<policy-fuse-updates>> specifies, so later stages can still write the shadow
registers.

#*[Changed]*#
The chiplet creator is the ROOT of the BL1 manifest, and remains the ROOT of
every later manifest until a stage hands the role over: the ROOT owner code is
all-zero unless it has been fused or written otherwise. After a hand-over to
the SiP owner or the system owner, a later-stage manifest carries no
chiplet-creator signature. No shadow value removes the ROOT signature itself:
step 1 requires one whatever `REQUIRED_ALGS[1:0]` holds.

#*[Changed]*#
`SIGNATURE_REVOKE` and `PUBK_REVOKE` are not propagated. Their shadow registers
are set-only and are write-locked by BL1 before hand-off, so only BL1 can change
them, and only by adding revocations. BL1 writes to them only the bits it has
programmed.

[[signature-algorithm-revocation]]
=== Signature Algorithm Revocation

#*[Changed]*#
`SIGNATURE_REVOKE` holds the set of revoked signature-algorithm classes. Where
the `BL1_VERSION` and `BL2_VERSION` flags retire a manifest by version, this
field retires an algorithm class for every manifest and every entity, so that a
broken or deprecated algorithm can be withdrawn without re-provisioning keys.
Its effect on verification is given by step 2 of the requirement rule in
<<secure-boot-signing-model>>. This section defines the classes and the group
codes, and <<policy-fuse-updates>> specifies how the field is updated. The
field has the layout of the OCA Payload Manifest's `signature_class_revoke`
field, through which a manifest requests an update. The fuse, through its
shadow register, is the only class-revocation input to verification: the
manifest's own `signature_class_revoke` value is never used to decide which
signatures of that manifest are verified, so a manifest cannot re-enable a
revoked class. That value is checked only for its format, as described under
_Group codes_.

#*[New]*#
*Classes.* <<sep-signature-classes-table>> lists the class of each value a type
field can hold. The same values apply to the type fields of the ROOT, of the
verifier key and of a co-signer. A value not listed is reserved.

#*[Changed]*#
The two adopter-defined classes exist because OCAH is open-sourced: an adopter
that selects its own scheme through the implementation-defined range of the
type fields needs a way to retire it.

#*[New]*#
A ROM release verifies only the classes it implements and rejects a declared
signature of any other class. The classes a release implements are listed with
that release of the SEP Boot ROM. The SEP hardware provides one post-quantum
class, ML-DSA-87, and the 0.5 ROM implements one classical class, RSA-3072.
Where a release implements a single class of a group, revoking that class
leaves no class of the group to migrate to, so the group can be retired only as
a whole, with its group code.

NOTE: #*[New]*# SEP 1.0 verifies one post-quantum class, ML-DSA-87, the only post-quantum
signature algorithm the SEP hardware provides. Revoking it alone, with
`SIGNATURE_REVOKE[26]`, has a side effect: a manifest that declares an
ML-DSA-87 signature is rejected, and where the algorithm minimum demands a
post-quantum signature, no class is left that can meet it, so every manifest is
rejected. On such a part ML-DSA-87 is retired only together with the
post-quantum group, by a manifest that also requests the group code `0xAC`.
Once a release implements a second post-quantum class, a single class can be
revoked and signers move to the other.

#*[Changed]*#
*Group codes.* Each group of `SIGNATURE_REVOKE` has two kinds of bits. A class
bit (`[7:0]` classical, `[31:24]` post-quantum) revokes one class. The group
code (`[15:8]` classical, `[39:32]` post-quantum) disables the whole group. The
rules on the constants below are those the OCA Payload Manifest defines for
`signature_class_revoke`. Two of them are checks on the format of a manifest:
the group-code byte and the interlock. Every stage applies these two to every
manifest it verifies, whether or not `manifest_security_control` suppresses the
request, and to `verifier_authorized_signature_class_revoke` in a verifier key
entry.

A group code is a constant, not a bit mask:: #*[Changed]*# A group is disabled only when its
byte equals its constant, `0xCA` or `0xAC`. SEP ROM compares the whole byte. Any
other value means that the group is not disabled, and the class bits still
apply. The individual bits of the constant have no meaning of their own, so a
byte such as `0x40` is not a partial revocation. A manifest whose
`signature_class_revoke` carries a group-code byte other than `0x00` or the
constant is rejected, as the OCA Payload Manifest requires.

Why a constant:: The fuse accumulates by OR across every manifest the device
accepts over its life. If "every classical class revoked" were simply the state
in which all of `SIGNATURE_REVOKE[7:0]` happen to be set, a device could reach
it through a series of unrelated, individually reasonable revocations, with no
manifest ever having declared that intent, and the same manifest would have
that effect on some devices and not on others, depending on what each had
already accumulated:
+
[width="100%",cols="<8%,<12%,<50%,<30%",options="header",]
.Accumulated class revocations without a group code
|=======================================================================
|Year |Manifest |Revokes |`SIGNATURE_REVOKE[7:0]` after

|1 |A |RSA-3072, deprecated (bit 0) |`0000_0001`
|2 |B |P-256 and Ed25519, implementation side channel (bits 2, 5) |`0010_0101`
|3 |C |RSA-4096 and P-521, dropped from the product line (bits 1, 4) |`0011_0111`
|4 |D |P-384 retired; adopter class unused (bits 3, 7) |`1011_1111`
|5 |E |Ed448, implementation bug (bit 6) |`1111_1111`
|=======================================================================
+
#*[Changed]*#
Under an all-bits rule, manifest E, intended to retire Ed448, would have retired
classical cryptography on every device that had also seen A to D, and not on a
device that had missed C. With the group code, retiring the last class requires
a manifest that also writes `0xCA`: a deliberate, auditable act with the same
meaning on every device.

The interlock:: #*[Changed]*# A manifest whose `signature_class_revoke` sets every defined class
bit of a group while that group's code is `0x00` is rejected, as the OCA
Payload Manifest requires. The defined class bits are `[7:0]` for the classical
group and `[26:24]`, `[30:28]` and `[31]` for the post-quantum group; bit 27 is
reserved and is not counted. Because class bits add up in the fuse across
manifests, BL1 also programs no request that would leave every defined class
bit of a group set in the fuse while that group's code is not its constant. The
last class of a group can therefore only be retired by a manifest that also
writes the group code, the producer's explicit acknowledgement that nothing in
the group will remain usable.

Fragments:: #*[Changed]*# No accepted manifest can contribute part of a constant, because
every accepted manifest carries exactly `0x00` or exactly the constant in the
byte. A fragment can still appear in the fuse: the four set bits of a constant
are programmed one at a time, and power can be lost between them. SEP ROM reads
a fragment as "not disabled" and reports it, so the part boots as before, and
BL1 completes the byte on a later boot because the manifest still carries the
request. A byte that holds a bit outside its constant can never be completed.
SEP ROM reads it as "not disabled" and reports it, and that group can never be
disabled on that part.

What a disabled group changes:: #*[Changed]*# Two things, for every entity. SEP ROM does not
enforce that group's bit in the algorithm minimum: with `0xCA`,
`REQUIRED_ALGS[0]`, `[4]` and every `[4N+4]`; with `0xAC`, `REQUIRED_ALGS[1]`,
`[5]` and every `[4N+5]`. And SEP ROM skips a declared signature of that group
instead of verifying it or rejecting the manifest for it. Nothing else changes:
the other group's minimum bits, key revocation and the Secure Boot Decision
apply as before, `REQUIRED_ALGS` and its shadow register keep their programmed
values, and a single class bit has neither effect. Without the first rule, a
fused `REQUIRED_ALGS[1]` = 1 could never be escaped once every post-quantum
class had to be retired, because fuses cannot be cleared. Without the second,
the manifest that requests the group code, which has to declare a signature of
that group for as long as the minimum demands one, would be rejected at the
next cold reset.

The brick guard:: #*[Changed]*# A manifest may carry both group codes. With both groups
disabled every declared signature is skipped, step 2 of the requirement rule
leaves no ROOT signature to verify, and the manifest is rejected. The
survivability check of <<policy-fuse-updates>> therefore refuses such a request.
SEP defines no decommissioning override. Should both group codes nevertheless
be found set in the fuse, SEP ROM rejects every manifest.

[[policy-fuse-updates]]
=== Policy Fuse Updates

#*[New]*#
This section specifies who may program the four policy fields, `PUBK_REVOKE`,
`REQUIRED_SIGNERS`, `REQUIRED_ALGS` and `SIGNATURE_REVOKE`, and under which
conditions. It relies on the hardware rules in the Shadow Register and JTAG
Access Control section of the OTP Fuse Controller chapter: the four fields
ignore their lock fuse bits and cannot be read-locked; a write-lock on them
exists only in the `LOCKS` and `LOCKS_SPARE` shadow registers, for the current
boot; and for
`REQUIRED_SIGNERS` and `REQUIRED_ALGS` that write-lock closes the fuse and
leaves the shadow register writable.

#*[New]*#
*On a boot without a verified manifest.* Whether SEP ROM requires a verified
manifest is decided on every boot by the Secure Boot Decision, so the same part
can be in either case from one boot to the next. On a boot in which SEP ROM did
not require one, as during `TEST_DEV` provisioning, the owner holding the part
provisions the four fields, as it does the disable vectors and the token
digests. BL1 acts on no request of its manifest, which nothing has
authenticated, and the programming requirements below do not apply.
`REQUIRED_SIGNERS` can be programmed only on such a boot.

#*[Changed]*#
*On a boot with a verified manifest.* On a boot in which SEP ROM authenticated
the BL1 manifest, only BL1 programs the four fields, and only on a request
carried by that manifest. SEP ROM never
programs a fuse, and a request carried by a later-stage manifest is not acted
on. <<sep-policy-update-requests-table>> lists the requests. Each request has
the layout of its field and is applied bit for bit; it can set bits and never
clear one. The ROOT-authorization rules the manifest places on these requests
when `use_verifier_key` is set are enforced as part of manifest verification
and are not restated here.

#*[New]*#
*Revoking a key.* A request in `public_key_classic_revoke` or
`public_key_pqc_revoke` takes effect only after the manifest that carries it has
been verified. BL1 then programs the bit into `PUBK_REVOKE` as this section
specifies, and the key is revoked for every later manifest. To revoke a key,
its owner therefore signs the manifest with another of its keys. Example: to
revoke the key of `CHIPLET_PUBK_HASH0`, the manifest sets bit 17 of
`public_key_select_classic`, is signed with the key of `CHIPLET_PUBK_HASH1`, and
sets bit 16 of `public_key_classic_revoke`. A manifest cannot revoke a key it
carries: SEP ROM rejects a manifest that sets the revoke bit of a key it
selects or of a key of one of its own co-signer entries. A key can therefore be
revoked only while its owner has another key to sign with. The system owner has
one key of each group, `SYS_PUBK_HASH` and `SYS_PUBK_PQC_HASH`: it can revoke
one of them by co-signing with the other, and the one that remains cannot be
revoked. Neither can be revoked while the system owner's algorithm minimum in
`REQUIRED_ALGS` demands both groups.

#*[New]*#
*Whose keys a manifest may revoke.* BL1 programs a requested `PUBK_REVOKE` bit
only if the owner of that key signed the manifest. A requested bit that fails
this condition is not programmed and is reported. So is a requested bit that
names no key: a reserved key number, or a number above 31.

* #*[New]*# Bits of chiplet-creator keys, `[5:0]`, `[13:8]` and `[19:16]`, need nothing
further, because the chiplet creator signs the BL1 manifest.
* #*[New]*# Bits of SiP-owner keys, `[20]`, `[21]`, `[24]` and `[25]`, are programmed only
if the manifest carries a co-signer entry that is anchored to the SiP owner and
of which SEP ROM verified at least one signature.
* #*[New]*# Bits of system-owner keys, `[22]` and `[23]`, are programmed only if the
manifest carries a co-signer entry that is anchored to the system owner and of
which SEP ROM verified at least one signature.

#*[Changed]*#
*Manifest data for BL1.* The requirements below need fields of the BL1 manifest
that SEP ROM has already parsed and authenticated, and the manifest itself need
not remain in SEP memory after hand-off. SEP ROM shall make the following
available to BL1 regardless: the request fields of
<<sep-policy-update-requests-table>> and `manifest_security_control`;
`use_verifier_key` and `co_signer_enable`; and, for each engaged entity whose
signatures SEP ROM verified, the class of each verified signature and, for the
ROOT and for a co-signer, the key number of each key it verified with. A
verifier key has no key number, and neither has a co-signer key that matches no
device digest. The form of this hand-off record is defined with the SEP Boot
ROM.

#*[Changed]*#
*Programming requirements.* On a boot in which SEP ROM authenticated the BL1
manifest, BL1 shall meet the following between SEP ROM's hand-off to it and its
own hand-off to the next stage. The programming procedure that meets them is
specified with the SEP Boot ROM and BL1 firmware, not here.

* #*[Changed]*# Program a request only after the survivability check below has passed, and
the interlock of <<signature-algorithm-revocation>> is respected, for all the
requests of the manifest taken together. If either fails, BL1 programs none of
them and reports it. A request that is not programmed remains in the manifest
and is evaluated again at the next boot.
* #*[New]*# Program the bits of a group code, and read them back from the fuse, before
any other bit requested by the same manifest. A group code only relaxes what
SEP ROM demands, and every other bit only tightens it, so this order keeps the
BL1 manifest acceptable to SEP ROM if power is lost at any point. If a fuse bit
does not read back as programmed, BL1 shall program it again, up to the maximum
number of programming pulses the fuse vendor allows for one bit, counted over
the life of the part, and shall report a bit that still does not read back as
damaged. If a group code is then still not its constant, BL1 shall evaluate the
survivability check and the interlock again with the group code as it reads
back, and shall program the remaining requested bits only if both pass.
* #*[Changed]*# Write each programmed value to the shadow register of its field. Programming
a fuse does not update its shadow register until the next fuse sensing, so this
write is what puts the change into the policy in force before BL1 verifies the
next-stage manifest.
* #*[Changed]*# Set the write-lock bits of the four fields in the `LOCKS` and `LOCKS_SPARE`
shadow registers on every such boot, whether or not it programmed anything:
`LOCKS[16]` for
`PUBK_REVOKE`, `LOCKS[42]` for `REQUIRED_SIGNERS`, `LOCKS[44]` for
`REQUIRED_ALGS` and `LOCKS_SPARE[0]` for `SIGNATURE_REVOKE`. From then until
the next cold reset no stage can program any of the four fuses.
* #*[Changed]*# Report a requested bit it did not program and a fuse that failed to program.

#*[Changed]*#
*Survivability check.* A policy update shall never make SEP ROM reject, at the
next cold reset, the BL1 manifest that requested it. Before programming, BL1
shall evaluate the requirement rule of <<secure-boot-signing-model>> against its
own manifest under the policy SEP ROM will apply at that cold reset: each of
the four fields is taken as the value its fuse will hold once the requests are
programmed, which is the bits already programmed together with the bits BL1 may
program. Values that BL1 has written to the shadow registers for the next stage
are not used.

#*[Changed]*#
The evaluation covers every entity whose signatures SEP ROM verified: the
chiplet creator; the verifier key, when the manifest sets `use_verifier_key`;
and each enabled co-signer entry. It uses the class and the key of each
verified signature from the hand-off record, together with the policy. No
signature is verified again. Two cases show what it catches:

* #*[Changed]*# _A class._ Co-signer 1 is required, is the SiP owner and signs RSA-3072. A
request for `SIGNATURE_REVOKE[0]` would make that signature one of a revoked
class, so nothing is programmed until the SiP owner signs with another class.
* #*[New]*# _A minimum._ The manifest declares a classical chiplet-creator signature only
and requests `REQUIRED_ALGS[1]`. The request would demand a post-quantum
signature the manifest does not declare, so nothing is programmed. The request
must be carried by a manifest that declares both.

#*[Changed]*#
The check covers the BL1 manifest only. The next-stage manifest is verified
under the new policy before hand-off in any case, but its outcome is not a
condition for programming: a deployment that changes the policy is responsible
for migrating the later stages it ships, and making the fuse update depend on
first loading and authenticating the next stage would impose an order of
operations on every BL1 implementation.

#*[Changed]*#
If the check fails, nothing is programmed and the boot continues under the
unchanged policy. The check is defined through the requirement rule and follows
whatever that rule says.

#*[New]*#
*Example: retiring the post-quantum group.* The fused policy is
`REQUIRED_ALGS[1:0]` = `11` and `REQUIRED_SIGNERS[7:0]` = `0x00`. The BL1
manifest declares a classical and an ML-DSA-87 chiplet-creator signature and
requests `SIGNATURE_REVOKE[39:32]` = `0xAC` together with bit 26.

. #*[New]*# SEP ROM verifies both signatures, because nothing is revoked yet, and hands
off.
. #*[New]*# BL1 evaluates the request. With the post-quantum group disabled,
`REQUIRED_ALGS[1]` is not enforced and the ML-DSA-87 signature is skipped; the
classical signature still verifies. The survivability check passes.
. #*[New]*# BL1 programs the four set bits of `0xAC` and reads them back, then programs
bit 26, writes the shadow register and sets the four write-locks. The
next-stage manifest is verified with the post-quantum group disabled.
. #*[New]*# If power is lost before `0xAC` is complete, the fragment reads as "not
disabled", SEP ROM verifies both signatures as before, and BL1 completes the
byte. If power is lost after `0xAC` and before bit 26, the group is already
disabled and SEP ROM authenticates the manifest on its classical signature.
. #*[New]*# From the next cold reset SEP ROM verifies only the classical signature. Later
manifests may stop declaring a post-quantum signature and use the classic
manifest variant.
