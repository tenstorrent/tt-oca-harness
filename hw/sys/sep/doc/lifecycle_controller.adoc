[[life-cycle-controller-lcc-life-cycle-controller-lcc]]

The Life Cycle Controller (LCC) converts the OTP lifecycle state and owner
restrictions into `feat_ctrl_o`, the 64-bit vector that enables debug and
functional features. Two volatile demotion controls can change the debug
profile for the current boot without changing OTP.

The OTP controller supplies `LC_STATE`, `SIP_DIS` and `SYS_DIS` after fuse
sensing. The LCC checks the differentially encoded state and disables features
on an integrity error, except when the final `SEC_DIS` override forces them on.
Downstream logic uses these outputs to gate debug, test and functional paths.

The sections below explain states and security domains, feature-control rules,
demotion, scan protection and firmware authorization. Hardware gating is
implemented; the secure-boot signing model in <<demote-signing-model,Firmware Authorization>>
specifies the manifest policy the 1.0 SEP Boot ROM enforces. The 0.5 ROM does
not implement it.

<<sep-lifecycle-controller-figure>> shows a high-level view of the Life Cycle Controller
components.

[[sep-lifecycle-controller-figure]]
.SEP lifecycle controller
image::sep-lifecycle-controller.svg[alt="sep_lifecycle_ctrl: LC_STATE decoder, feature control decode, security-disable override, debug and DFT disable derivation, register block and demotion encoders",width=100%,pdfwidth=100%]

In <<sep-lifecycle-controller-figure>>, the inputs enter on the left and the
outputs leave on the right, each labelled with its consumer. `u_lc_state_dec`
decodes the differentially encoded LC_STATE from the eFuse shadow registers and
raises `lc_sigint_err` on a non-complementary codeword, which forces the feature
control decode to all zeros. While `security_disable_i` is high, the
multiplexer replaces the decoded vector with all ones, even on an integrity
error. The `lc_sigint_err` line crosses the `security_disable_i` line without
connecting; the gap marks the crossing.

The debug and DFT disable derivation turns the `sip_debug`, `chiplet_dbg`,
`sep_debug`, `sep_fuse_dbg` and `smc_fuse_dbg` bits of the result into the 11
debug disables for the DTP and the two fuse DFT disables. No functional logic
consumes the fuse DFT disables; they leave the SMU for adopter DFT insertion.
The `demote` and `lock` bits of DEMOTE_1 and DEMOTE_2 are set-only: firmware
can set `demote` only while `lock` is clear, and both hold until SEP cold
reset. The demote bits feed the feature control decode and, through the
differential encoders, the Key Manager and the SEP outputs.

[[lc-state-machine]]
== Lifecycle States

The LCC decodes the OTP controller's `LC_STATE` shadow output; it does not
sequence lifecycle transitions itself. Before fuse sensing completes, that
output holds INVALID (`4'b1111`). The LCC then follows the sensed state and
its feature-control profile.

The raw four-bit OTP value is carried as a complementary code in the shadow
path. A failed integrity check sets `lc_sigint_err` and forces the base feature
vector to zero. `SEC_DIS` is applied afterward and can override that result;
see <<feat-ctrl-overrides-and-gates>>.

Hardware orders the RMA token transitions: `RMA_SIP_TOKEN` first admits
RMA_SIP, then `RMA_CHIPLET_TOKEN` admits RMA_CHIPLET. Volatile demotion is
separate from those transitions and does not change the OTP state.

Key Manager includes DEMOTE_1/2 with CHIPLET_UID, SIP_UID, SYS_UID and LC_STATE
in key derivation, separating demoted-state keys from non-demoted production
keys.

[[multiple-security-domains]]
== Multiple Security Domains

The SiP owner controls the debug-access network between chiplets. Each chiplet
owner controls access to its own local assets. A system has one shared
SiP-owner domain and a local domain for each chiplet with independently
protected assets.

`SIP_DBG` admits and forwards external debug traffic at each chiplet with a
local SEP/LCC. Access to local resources additionally requires `CHIPLET_DBG`;
SEP resources also require `SEP_DBG`. Opening another chiplet's local debug
gate is unnecessary when traffic only passes through it.

A chiplet without a local SEP/LCC contributes no local disable vector.
The preceding LCC-bearing chiplet controls forwarding to it, as described
in <<non-primary-chiplets>>.

In <<sep-security-domains-figure>>, each chiplet with a SEP gates the debug
path from its PTAP downwards: SIP_DBG opens the Case 1 targets, CHIPLET_DBG adds
the Case 2 targets and SEP_DBG adds the Case 3 targets, each listed to the right
of its gate. The targets are the debug paths that `sep_lifecycle_ctrl` disables
through `dbg_disable_o` and the two fuse DFT disables, as given in
<<dtp-path-gating>>; the fuse DFT paths also need their own SEP_FUSE_DBG or
SMC_FUSE_DBG bit. The green gate belongs to the SiP-owner domain and is a DBG_2
bit, opened in the field by Demotion 2. The cream gates belong to the
chiplet-owner domain and are DBG_1 bits, opened by Demotion 1. The I/O STAP
forwards the chain to the next chiplet's PTAP.

and chiplet 3 has its own LCC:

* Chiplet 1 local debug requires `SIP_DBG(1)` and `CHIPLET_DBG(1)`.
* Chiplet 2 access requires `SIP_DBG(1)`; chiplet 2 adds no local gate.
* Chiplet 3 local debug requires `SIP_DBG(1)`, `SIP_DBG(3)` and
  `CHIPLET_DBG(3)`. It does not require `CHIPLET_DBG(1)`.

The per-path conjunctions are listed in <<dtp-path-gating>>.

[[debug-test-and-functional-feature-control-vectors-debug-test-and-functional-feature-control-vectors]]
== Debug and Functional Feature Control

`feat_ctrl_o` uses positive logic: 1 enables a feature. The 64-bit
`SIP_DIS` and `SYS_DIS` shadows use negative logic: 1 restricts a feature.
The applicable masks depend on lifecycle state and demotion. Where both
apply, the enable is `~(SIP_DIS | SYS_DIS)`.

<<feature-control-table>> gives the complete state-dependent formulas.
The final `SEC_DIS` override is described in <<feat-ctrl-overrides-and-gates>>.

[[feature-control-vector-definition]]
=== Disable Vector Format (SIP_DIS / SYS_DIS)

<<sep-feature-disable-vector-table>> defines the *disable* vector format -- the bit layout shared by
both SIP_DIS and SYS_DIS (each is 64 bits). Each defined bit gates a specific
feature or its associated scan chain; the remaining bits are
reserved for adopter extension (see <<asset-and-scan-chain-protection>> and
<<adopter-extension>>).

In the policy tables, `T` means enabled and `F` means disabled.
A clear disable bit permits a feature only where the lifecycle profile
allows it; it does not by itself open a production debug path.

DBG_1 covers `[23:0]` and is controlled by Demotion 1. DBG_2 covers `[47:24]`
and is controlled by Demotion 2. Function bits occupy `[63:48]`.

[[dis-vector-ownership]]
=== DIS Vector Ownership: Predecessor-Programs-Disables

The vector name identifies the receiving owner, not the programmer:

* The chiplet creator programs `SIP_DIS` before SiP handoff. Its restrictions
  remain effective in RMA_SIP and are bypassed in RMA_CHIPLET.
* The SiP owner programs `SYS_DIS` before system handoff. Its restrictions
  are bypassed in RMA_SIP and RMA_CHIPLET.

RMA bypass does not erase either fuse vector. The system owner has no
successor and therefore no third disable vector. It provisions its own
`SYS_PUBK_HASH` and `SYS_UID` before TEST_DEV-to-PROD transition; see the
OTP Fuse Controller chapter for the provisioning sequence.

[[dis-vector-or-rationale]]
=== Combining Rule: OR then Invert

Where both owner masks apply, a feature is disabled if either mask has its
bit set. OR combines the restrictions; inversion produces the positive-logic
enable. Since an OTP bit can only change from 0 to 1, a later owner cannot
erase an earlier owner's programmed restriction. Lifecycle profiles can
bypass masks for RMA access without changing OTP.

[[feat-ctrl-overrides-and-gates]]
=== Overrides and Final Gates (SEC_DIS)

Two controls sit *on top of* the per-LC-state / DIS-vector computation, applied in
this order (a later step overrides an earlier one):

. *Signal-integrity fail-closed (base):* if the differentially encoded LC_STATE
fails its integrity check (`lc_sigint_err`), the base `feat_ctrl` is forced to
all-0s (all features disabled).

. *SEC_DIS override:* when `SEC_DIS = 1`, `feat_ctrl` is forced to all-1s -- every
feature enabled, regardless of the LC state, the DIS vectors, or the sigint
result (an emergency bring-up bypass on A0 silicon; see the Security Disable
section).

`SECURE_TM` is *not* a term in `feat_ctrl_o`. No feature control bit is qualified
by secure test mode: the debug group `[47:0]` and the function group `[63:48]`
are both determined solely by the LC state, the DIS vectors, and the SEC_DIS
override. `secure_tm` acts on the scan path and on the fuse controller rather
than on feature control -- see <<secure-tm-vs-scandump>>.

[[demote-1-2-in-field-debug-demotion]]
== In-Field Debug Demotion

`DEMOTE_1` and `DEMOTE_2` each contain a `demote` bit and a `lock` bit.
They are two registers, not separate demotion and lock register banks.
Cold reset clears both and removes the volatile debug profile.

[cols="1,1,3",options="header"]
.SEP demotion controls
|===
|Register |Feature group |Scope
|`DEMOTE_1` |DBG_1, bits `[23:0]` |Local debug, including SEP and chiplet gates.
|`DEMOTE_2` |DBG_2, bits `[47:24]` |Inter-chiplet debug access and forwarding, including `SIP_DBG`.
|===

The controls are independent: either may be set first or used alone.
In TEST_DEV, demotion forces its group open; in PROD, it enables the group
subject to the disable vectors. Other lifecycle profiles and function bits
are unchanged. The complete formulas are in <<feature-control-table>>.

Opening local debug does not open the external access path. For example,
a Case 3 SEP debug path requires both groups; see <<dtp-path-gating>>.
The LCC applies register values without authenticating the writer or a
manifest. Firmware authorization is discussed under
<<lcc-firmware-policy,Firmware Authorization>>.

[[demote-lock-behavior]]
=== Programming and Locking

Both `demote` (bit 0) and `lock` (bit 1) are write-one-to-set fields.
Writing zero does not clear them. While `lock` is zero, firmware can set
`demote`; once locked, the demotion decision cannot change until cold reset.
The lock can commit either a demoted or a non-demoted state. The
ifdef::backend-html5[]
xref:ocah-programmer-guide::index.adoc#sep-lifecycle-demotion[demotion sequence]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-programmer-guide/latest/index.html#sep-lifecycle-demotion[demotion sequence]
endif::backend-pdf[]
is in the Programmer's Guide.

This is the hardware mechanism. Authorization follows the signing policy: the
demotion registers are written by a boot stage whose manifest was authenticated
against the `REQUIRED_SIGNERS` and `REQUIRED_ALGS` values in force for that
manifest (<<secure-boot-signing-model>>), so an owner whose co-signature those
values require on that manifest controls the demotion decision. The 0.5 ROM's
manifest handling is documented in the Boot ROM chapter.

[[demote-reset-behavior]]
=== Reset Behavior

SEP cold reset clears the `demote` and `lock` fields in both registers.
The LCC then applies the profile of the sensed OTP state without demotion.

[[asset-and-scan-chain-protection]]
== Asset and Scan-Chain Protection

Two distinct DFT operations use the scan chains, and the protection model
treats them differently:

* *Scan test* -- shift in a test pattern, run the functional clock for one or
two cycles, then shift the result out. Used for manufacturing / DFT coverage.
* *Scan dump* -- shift the live internal state out directly. Used for debug.

The integration must preserve test coverage without exposing live secrets.
The rules below define the required scan partitioning and command gates;
feature-vector generation alone does not implement or verify DFT insertion.

[[asset-classes]]
=== Asset Classes

SEP assets are partitioned into three classes. Class 1 (non-scannable) and
Class 2 (scannable for test coverage but *never* scan-dumpable) are each split by
protection rationale -- *a* for confidentiality and *b* for integrity. Class 3 is
everything else.

<<sep-security-asset-classes-table>> relates the asset classes to scan and scan-dump
treatment.

[[secure-tm-vs-scandump]]
=== `secure_tm` and the Secure Scan Chain

`secure_tm` is the secure-test-mode indicator: the `TEST_EN` strap latched into
the internal `SECURE_TM` signal. It is latched when SEP fuse sensing completes
if `SEC_DIS` is not asserted, or on chiplet cold-reset release if `SEC_DIS` is
asserted (see the Test Mode section).

`secure_tm` establishes the required test configuration; it does not identify
or authenticate the owner at the JTAG port. The protection rules require it to:

. Admit test commands on the secure chain only while asserted.
. Block updates to `LOCKS`, `LC_STATE`, `SIP_DIS` and `SYS_DIS` from SEP,
  OTP, JTAG and TRoot while the part is shiftable.
. Hold OTP write-enable inputs inactive.
. Disconnect UID and `CLASS_KEY` shadow outputs from downstream consumers.

Secure-chain access requires both an open SIB, under the feature gates in
<<dtp-path-gating>>, and an allowed command. Test commands require
`secure_tm = 1`; dump commands are never allowed, for any owner or lifecycle
state. With `secure_tm = 0`, no command is admitted on that chain.

These conditions distinguish Class 1 from Class 2. Class 1 registers contain
secrets or state that directly controls protection, so they are excluded from
scan. Class 2 consumers and fuse-program controls may be scanned only with
their secret sources disconnected and the fuse-write path blocked. The
feature bits control reachability; they do not waive these command rules.

The adopter's DFT implementation must enforce this separation. General
Class 3 chains follow their debug gates and do not use `secure_tm` as an
additional gate.

[[non-primary-chiplets]]
== Non-Primary Chiplets

Primary chiplets always include a local SEP and LCC; the asset
partitioning described in <<asset-and-scan-chain-protection>> applies
directly. *Non-primary* chiplets may not include a local SEP, in which
case debug access is governed by the *SiP-owner domain*. The primary
chiplet's SiP-owner feature control gates the DFT traffic before forwarding
it to the non-primary chiplet (see <<multiple-security-domains>>).

For non-primary chiplets, the adopter is responsible for:

* Identifying which non-primary chiplet assets require protection.
* Partitioning those assets across scan chains analogous to the
class scheme in <<asset-classes>> (1a/1b, 2, 3).
* Routing the non-primary chiplet's scan / DFT traffic through the
appropriate DTP path on the primary chiplet, where SiP-owner feature
control gates forwarding.
* Applying the same scan-protection treatment to any non-primary chiplet
logic that handles secrets: Class 1 excluded from scan chains, Class 2
never scan-dumpable.

The `SIP_DBG` mechanism documented in
<<feature-control-vector-definition>> gates the DTP path on the primary
chiplet. The primary LCC therefore governs debug access to a non-primary
chiplet by controlling whether DFT traffic is forwarded to it.

[[adopter-extension]]
== Adopter Extension

If an adopter integrates SEP into a chiplet with assets that require
their own scan-chain protection -- assets not covered by the
chiplet-scope SEP scan chain or the general-logic scan chain in
<<asset-and-scan-chain-protection>> -- the LCC architecture
accommodates this via the *reserved bits* in `feat_ctrl_o` (and the
matching positions in SIP_DIS / SYS_DIS):

* Debug group: bits 5-23 (DBG_1, 19 reserved bits) and bits 25-47 (DBG_2, 23 reserved bits)
* Function group: bits 48-63 (16 reserved bits)

OCAH assigns no standard function to these reserved bits. An adopter may
allocate a DBG_2 bit to an additional inter-chiplet DFT forwarding path; the
bit is consumed on the LCC-bearing chiplet to gate the corresponding traffic
before it is forwarded downstream.

Each new scan chain or forwarding path is gated by exactly one reserved bit. The
corresponding bit position in SIP_DIS or SYS_DIS (chosen by which
predecessor owner sets the default policy -- see
<<dis-vector-ownership>>) determines the default OTP-programmed
restriction.

Constraints any adopter extension must satisfy:

* *One feature control bit per scan chain.*

* *Asset-class compliance.* Secret-bearing fields used by the new chain
must follow the asset-class scheme (see <<asset-and-scan-chain-protection>>):
actual secrets and integrity-critical state are excluded from scan chains
(Class 1). A Class 2 chain must never admit a dump command. It may admit
test commands only while `secure_tm = 1`, with secret sources disconnected
and fuse programming blocked as specified above. The chain's feature-control
bit controls reachability; it does not authorize a dump.

* *Per-LC-state policy.* The new bit follows the standard
per-LC-state formulas for its group (see <<feature-control-table>>).
DBG_1 and DBG_2 are disabled in undemoted PROD and in PROD_END;
their respective demotion controls relax PROD to honor the disable vectors.
Function bits continue to honor `~(SIP_DIS.FUNC | SYS_DIS.FUNC)` in both
production states and are unaffected by demotion. All groups follow their
listed TEST_DEV and RMA policies and the SEC_DIS override.

NOTE: The specific bit-allocation convention -- which reserved bits
are reserved for which adopters, and how bit assignments are advertised
in the RDL / package outputs -- is currently *open* and will be defined
in a future revision of this specification.

[[secure-boot-signing-model]]
=== Secure-Boot Signing Model

This section specifies the manifest signing policy that the 1.0 SEP Boot ROM
enforces whenever the Secure Boot Decision above requires a verified manifest.
The policy is carried by three fields of the OTP Fuse Controller, defined in
the Fuse Fields table of that chapter: `REQUIRED_SIGNERS`, `REQUIRED_ALGS` and
`SIGNATURE_REVOKE`. It applies to every OCA Payload Manifest the boot chain
verifies. A public key is trusted only if its digest matches a digest embedded
in SEP ROM or one of the fused digests `CHIPLET_PUBK_HASH0/1`,
`CHIPLET_PUBK_PQC_HASH0/1`, `SIP_PUBK_HASH0/1`, `SIP_PUBK_PQC_HASH0/1`,
`SYS_PUBK_HASH` and `SYS_PUBK_PQC_HASH`, and only while the bit assigned to
that digest in `CHIPLET_PUBK_REVOKE` is clear. The 0.5 ROM does not implement
this model.

*Terms.* The following terms are used throughout this section. Each one names
specific bits of a fuse field.

Required-co-signer mask:: `REQUIRED_SIGNERS[7:0]`. Bit N-1 set means
co-signer N is required (bit 0 is co-signer 1, bit 7 is co-signer 8).
Owner code of co-signer N:: `REQUIRED_SIGNERS[4N+7:4N+4]`, a one-hot value
defined in <<sep-cosigner-owner-codes-table>>.
Algorithm nibble of an entity:: the four bits of `REQUIRED_ALGS` assigned to
that entity: `REQUIRED_ALGS[3:0]` for the chiplet creator,
`REQUIRED_ALGS[7:4]` for the verifier key, and `REQUIRED_ALGS[4N+7:4N+4]` for
co-signer N. Bit 0 set requires a classical signature (RSA, ECDSA or EdDSA);
bit 1 set requires a post-quantum signature (ML-DSA); bits 3:2 are reserved. A
nibble with both bits set is called _hybrid_. For co-signer N the owner code
and the algorithm nibble occupy the same bit positions in their respective
fields.
Revoked algorithm family:: an algorithm family whose bit in
`SIGNATURE_REVOKE` is set.
Revoked key digest:: a ROM-embedded or fused public-key digest whose bit in
`CHIPLET_PUBK_REVOKE` is set. This is key revocation and is independent of
algorithm-family revocation.
Policy in force:: the values held in the `REQUIRED_SIGNERS` and
`REQUIRED_ALGS` shadow registers when a manifest is verified. At cold reset
the shadow registers hold the fused values; a later boot stage may rewrite
them as described under _Policy propagation_ below.

*Verification entities.* An OCA Payload Manifest can carry signatures from
three kinds of entity. The _chiplet creator_ signs with its root keys, whose
digests are embedded in SEP ROM or fused in `CHIPLET_PUBK_HASH0/1` and
`CHIPLET_PUBK_PQC_HASH0/1`. A _verifier key_ is a second public key carried in
a verifier key entry appended to the manifest and itself signed by the chiplet
creator; when the manifest sets `use_verifier_key`, the main manifest is signed
by the verifier key rather than by the chiplet creator directly, so the chain
is chiplet creator -> verifier key entry -> main manifest. This lets the
chiplet creator keep its root keys offline and authorize a developer or
third-party signer without provisioning that signer's key. _Co-signers_ are up
to eight further signature blocks appended to the manifest; the manifest
enables each with a bit of its `co_signer_enable` field, and each block
carries its own public key(s), signature(s) and signature-type fields.

*Requirement rule.* SEP ROM authenticates a manifest only if all of the
following hold. Each later boot stage applies the same rule to the manifest it
verifies, using the policy in force at that time.

. *Revoked algorithm families are removed first.* For each entity, a
signature whose algorithm family has its `SIGNATURE_REVOKE` bit set is treated
as not present, and the bit of that entity's algorithm nibble that the
signature would have satisfied -- bit 0 for a classical signature, bit 1 for a
post-quantum signature -- is treated as 0 for this verification only; the
shadow register is not changed. If this leaves an entity's algorithm nibble
all-zero although its value in the shadow register is not all-zero, the
manifest is rejected: a requirement existed and nothing still trusted can
satisfy it. Hence a hybrid manifest whose post-quantum signature belongs to a
revoked family authenticates on its classical signature alone, while a
manifest whose required signatures all belong to revoked families is rejected.
. *Chiplet creator.* The chiplet-creator signatures required by
`REQUIRED_ALGS[3:0]` are present and verify under a public key whose digest
matches a ROM-embedded chiplet-creator digest, `CHIPLET_PUBK_HASH0/1` or
`CHIPLET_PUBK_PQC_HASH0/1`, and whose `CHIPLET_PUBK_REVOKE` bit is clear. When
`use_verifier_key` is clear these signatures cover the main manifest; when it
is set they cover the verifier key entry.
. *Verifier key.* When `use_verifier_key` is set, the verifier key entry is
authenticated as in step 2, and the verifier key's signatures over the main
manifest required by `REQUIRED_ALGS[7:4]` are present and verify under the
public key carried in the verifier key entry.
. *Required co-signers.* For every N such that `REQUIRED_SIGNERS` bit N-1 is
set: the manifest sets `co_signer_enable` bit N-1; co-signer block N is present
and populated; the public key in the block satisfies the owner code
`REQUIRED_SIGNERS[4N+7:4N+4]` as defined in <<sep-cosigner-owner-codes-table>>,
including that the `CHIPLET_PUBK_REVOKE` bit of the matched digest is clear;
and the signatures required by `REQUIRED_ALGS[4N+7:4N+4]` are present and
verify under that public key.
. *Algorithms.* In an entity's algorithm nibble, bit 0 set requires a
classical signature and bit 1 set requires a post-quantum signature; when both
are set, both signatures shall be present and both shall verify. The scheme
and parameter set (for example ML-DSA-44, -65 or -87) are those declared by the
entity's own signature-type fields in the manifest and shall match the
entity's key; `REQUIRED_ALGS` does not select them. An all-zero algorithm
nibble requires no signature from that entity. For a required co-signer, and
for the verifier key when `use_verifier_key` is set, an all-zero nibble causes
the manifest to be rejected. For the chiplet creator, an all-zero
`REQUIRED_ALGS[3:0]` means that no chiplet-creator signature is required for
this manifest; this value is legitimate only when written to the shadow
register by a boot stage as described under _Policy propagation_, never as the
fused value.
. *Non-required co-signers.* A co-signer block N for which `REQUIRED_SIGNERS`
bit N-1 is clear is ignored: it is not verified, and its presence, absence or
validity has no effect on the result.

*Policy propagation.* The fused values of `REQUIRED_SIGNERS` and
`REQUIRED_ALGS` set the policy for the first manifest only. At cold reset the
fuse-sensing FSM loads both fields into their shadow registers, and SEP ROM
verifies the BL1 manifest against the shadow registers, which at that point
hold the fused values. Both shadow registers are SW-writable: a boot stage
whose manifest has been authenticated may rewrite them to set the policy for
the next manifest it verifies -- setting or clearing bits of
`REQUIRED_SIGNERS[7:0]`, changing an owner code, or changing an algorithm
nibble -- and may then set the write-lock bits of both fields in the `LOCKS`
shadow register to freeze that policy for the rest of the boot. The chiplet
creator has no bit in `REQUIRED_SIGNERS[7:0]`; a stage removes the
chiplet-creator requirement from the next manifest by writing
`REQUIRED_ALGS[3:0]` to `0b0000` in the shadow register. The next cold reset
reloads the fused values. Firmware enforces this propagation; there is no
hardware gate on the policy, and a stage whose manifest has been authenticated
is trusted to set the policy for its successor.

`SIGNATURE_REVOKE` is not propagated in this way. Its shadow register is
set-only and is write-locked by BL1 before hand-off, so only BL1 can change it,
and only by adding revoked families. A revocation requested by the BL1 manifest
applies from BL1's verification of the next-stage manifest onward in the same
boot, and from SEP ROM's verification of the BL1 manifest at every later cold
reset. <<signature-algorithm-revocation>> specifies the update.

The chiplet creator shall burn `REQUIRED_ALGS[3:0]` to a non-zero value before
a part leaves its control. A fused `REQUIRED_ALGS[3:0]` of `0b0000` is a
provisioning error, not a policy: it would let the BL1 manifest be accepted
without a chiplet-creator signature.

[[signature-algorithm-revocation]]
=== Signature Algorithm Revocation

`SIGNATURE_REVOKE` holds the set of revoked algorithm families. Its effect on
verification is given by step 1 of the requirement rule in
<<secure-boot-signing-model>>; this section specifies how the field is updated.
The OCA Payload Manifest requests an update through its `signature_class_revoke`
field, whose value is applied to the device after the manifest has been
authenticated. SEP applies such a request as follows.

*Authority.* Only BL1 programs `SIGNATURE_REVOKE`. SEP ROM never programs a
fuse, and no boot stage after BL1 can program this field or write its shadow
register, because BL1 write-locks it before handing off. The request acted on
is the `signature_class_revoke` field of the BL1 manifest -- the manifest SEP
ROM authenticated under the policy in force -- and only when
`signature_class_revoke_update_disable` in that manifest's
`manifest_security_control` is clear. The ROOT-authorization rules the manifest
places on this field when `use_verifier_key` is set (the
`verifier_authorized_signature_class_revoke` copy and
`modify_allowed_signature_class_revoke`) are enforced as part of manifest
verification and are not restated here. A `signature_class_revoke` value
carried by any later-stage manifest is not acted on by SEP.

*Update sequence.* After SEP ROM has handed off to BL1, and before BL1 hands off
to the next stage, BL1 shall:

. Read the `SIGNATURE_REVOKE` shadow register, which at this point holds the
fused value, and compute _requested_ = shadow OR the manifest's
`signature_class_revoke` value mapped onto `SIGNATURE_REVOKE` as defined in the
OTP Fuse Controller chapter. If _requested_ equals the shadow value, there is
nothing to program; continue at step 5.
. Perform the survivability check below with `SIGNATURE_REVOKE` taken as
_requested_. If it fails, do not program the fuse, report the rejected request,
and continue at step 5.
. Program the bits of _requested_ not already set in the fuse, through the
fuse-programming function of the OTP Fuse Controller, and read the fuse back.
A read-back that differs from _requested_ is a fuse-programming failure and is
reported; the sequence continues, and because the manifest still carries the
request it is retried at the next boot.
. Write _requested_ to the `SIGNATURE_REVOKE` shadow register. Programming a
fuse does not update its shadow register until the next fuse sensing, so this
write is what makes the revocation part of the policy in force for the rest of
this boot. The shadow register is set-only, so the write can only add revoked
families.
. Set the write-lock bit of `SIGNATURE_REVOKE`, `LOCKS_SPARE[18]`, in the LOCKS
shadow register. A write-lock blocks both fuse programming and shadow writes,
so from this point no stage in this boot can change the field. The LOCKS
_fuse_ bit for this slot is never programmed: the lock clears at the next cold
reset, which is what allows a further family to be revoked in a later boot.
. Verify the next-stage manifest against the policy in force, which now
includes the revocation, and hand off.

Step 5 is performed on every boot, whether or not steps 3 and 4 ran, so that
BL1 is the only stage that can ever program this field.

*Survivability check.* A revocation shall never leave the device unable to
boot. Before programming, BL1 shall confirm that both of the following
manifests satisfy the requirement rule of <<secure-boot-signing-model>> with
`SIGNATURE_REVOKE` taken as _requested_ and the rest of the policy in force
unchanged:

* the BL1 manifest itself, so that SEP ROM accepts it again at the next cold
reset. SEP ROM has already verified its signatures, so this is evaluated from
the manifest's signature-type fields and the policy, without repeating the
signature verification; and
* the next-stage manifest, if BL1 loads one, so that this boot completes. BL1
verifies that manifest in step 6 in any case; performing that verification
under _requested_ before step 3 satisfies this condition.

If either manifest fails, the request is not programmed and the boot continues
under the unchanged policy. SEP defines no override for a request that would
leave no trusted algorithm family: such a request is never programmed.

Because the check is defined through the requirement rule, it follows whatever
that rule says about revoked families and needs no separate definition.

*Example.* The fused policy is `REQUIRED_ALGS[3:0]` = `0b0011`,
`REQUIRED_SIGNERS[7:0]` = `0x00` and `SIGNATURE_REVOKE` = 0. A BL1 manifest
arrives signed classical and ML-DSA, carrying a `signature_class_revoke` value
that maps to `SIGNATURE_REVOKE` bit 6 (ML-DSA).

. SEP ROM verifies both chiplet-creator signatures and hands off.
. BL1 computes _requested_ = bit 6. Under step 1 of the requirement rule, its
own manifest still authenticates on its classical signature, as does the
next-stage manifest; the check passes.
. BL1 programs bit 6, writes the shadow register, sets `LOCKS_SPARE[18]` in the
LOCKS shadow, verifies the next-stage manifest with ML-DSA revoked, and hands
off.
. At the next cold reset SEP ROM verifies the same BL1 manifest with
`SIGNATURE_REVOKE` bit 6 fused: the ML-DSA signature is not checked and the
classical signature alone authenticates it.
