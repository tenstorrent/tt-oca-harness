[[sep-reset-controller,SEP Reset Controller]]

The SEP Reset Controller provides software-controllable resets for the Key Manager, crypto accelerators, and internal TRNG complex. It is accessible via AXI4 at generated base address `0x1080_3000`.

Controller.

== Software Reset Register

<<sep-sw-reset-n-fields-table>> defines the software reset controls and their reset
values.

[[sep-sw-reset-n-fields-table]]
[cols="<10%,<20%,<10%,<10%,<50%",options="header",]
.SEP SW_RESET_N fields
|=======================================================================
|Bit |Field |Access |Default |Description
|0 |km_sw_rst_n |RW |0 |KM reset (0=assert, 1=release)
|1 |otbn_sw_rst_n |RW |1 |OTBN reset (0=assert, 1=release)
|2 |aes_sw_rst_n |RW |1 |AES reset (0=assert, 1=release)
|3 |hmac_sw_rst_n |RW |1 |HMAC reset (0=assert, 1=release)
|4 |kmac_sw_rst_n |RW |1 |KMAC reset (0=assert, 1=release)
|5 |trng_sw_rst_n |RW |1 |Shared ESRC + CSRNG + EDN reset request (0=assert, 1=release)
|6 |abr_sw_rst_n |RW |1 |Adams Bridge reset (0=assert, 1=release)
|=======================================================================

On power-up, `SW_RESET_N` resets to `0x7E`: KM is held in reset, while OTBN,
AES, HMAC, KMAC, the TRNG, and Adams Bridge are released. The SEP host firmware
writes `1` to release an IP from reset and writes `0` to request its software
reset.

== Isolation and Reset Sequencing

Each `SW_RESET_N` bit is a request to a per-domain sequencer. Before the domain
enters reset, the sequencer isolates every AXI path into it, so that no
transaction is in flight when reset asserts. <<sep-axi-isolation-diagram>>
shows the isolated paths through the crypto interconnect.

[[sep-axi-isolation-diagram]]
.SEP crypto AXI isolation
image::SEP_AXIIsolation_FIG030.png[alt="SEP crypto AXI isolation",width=100%,pdfwidth=100%]

Each accelerator has two isolated paths: its host CSR path from the crypto
demux and its key path from the Key Manager. The Key Manager also has an
isolated path to the eFuse wrapper, and the TRNG has one host path each for
ESRC, CSRNG, and EDN. The demux ports to the Key Manager mailbox, eFuse
wrapper, lifecycle controller, and external TRNG are not isolated.

A software reset proceeds as follows:

. The SEP host firmware writes `0` to the domain's `SW_RESET_N` bit.
. The sequencer requests isolation on each of the domain's paths. From then
on, new transactions on those paths complete with SLVERR and read data
`0x1501A7ED`.
. Each isolate unit waits for the transactions it has already accepted to
complete, then reports its path isolated.
. Once every path in the domain reports isolated, the sequencer asserts the
domain's reset. Isolation stays in place for as long as the reset is held.
. The SEP host firmware writes `1` to the bit. Reset and isolation are
released together.

<<sep-isolation-paths-table>> lists the paths each domain waits on before its
reset asserts.

[[sep-isolation-paths-table]]
[cols="<30%,<70%",options="header"]
.Paths isolated before each software reset
|===
|Domain |Paths that must report isolated
|OTBN, AES, HMAC, KMAC, Adams Bridge |The accelerator's host path and its Key Manager key path
|Key Manager |The key paths to all five accelerators, and the eFuse path
|TRNG |The ESRC, CSRNG, and EDN host paths
|===

A key path isolates when either of its endpoints is being reset, so neither
the Key Manager nor an accelerator can enter reset with a key transfer in
flight between them.

The sequenced resets are ANDed with `sep_reset_n`, which holds every IP in reset
until eFuse sensing completes during boot. JTAG can drive `sep_reset_n` in
place of the eFuse reset through the SEP slice of the IC_RESET TDR (see
{dtp-ic-reset-overrides-ref} in the DTP chapter), which releases it on a part
whose fuse sensing does not complete. The per-IP JTAG override muxes are
applied last, allowing debug to force reset without waiting for isolation.

[[sep-km-reset]]
== Resetting the Key Manager

The sequenced Key Manager reset drives the Key Manager's warm reset input, and
`sep_reset_n` drives its cold reset input. A software reset therefore restarts
the Key Manager CPU, its internal fabric, and its warm-domain state, but keeps
cold-domain state such as the SRAM scrambler lock, the SEP-facing mailbox
FIFOs, and the cold OTP read locks. {km-reset-conditioning-ref} shows how the
Key Manager conditions both inputs and lists the state each one resets.

The mailbox port is not isolated. Its SEP-facing side is reset only by
`sep_reset_n`, so the SEP host can still reach it while the Key Manager is in
software reset.

Key Manager firmware can also request a warm reset through its own
`SOFT_RST_CODE` register. That reset does not pass through the SEP Reset
Controller, so its key and eFuse paths are not isolated first.

[[sep-trng-reset]]
== Resetting the TRNG

The TRNG reset bit controls one reset domain containing the entropy source,
CSRNG, EDN, and DRBG endpoint state. ESRC, CSRNG, and EDN occupy three
independent demux ports, so the TRNG sequencer isolates all three host paths
and does not assert the TRNG reset until all three report isolated. Reset and
isolation are released together.

The fabric entropy-pool AXI responder is not reset, so accesses remain
responsive. While the TRNG reset is active, both post-mux EDN adapters and the
pool synchronously clear their pending and buffered state, including the pool's
half-packed word, FIFO contents, and fill-stall state.

Consumers are not part of the TRNG reset sequence. Native EDN requests from AES,
KMAC, and OTBN receive no acknowledgement while the post-mux adapter is
clearing, remain asserted, and are serviced with fresh entropy after the chain
restarts. Software may wait for those consumers to become idle and hold them in
reset when policy requires aborting in-flight operations, but that is not
required to assert the TRNG reset.

The Key Manager stream has no post-mux adapter, so TRNG reset does not scrub
it. If the DRBG sampler is requesting or assembling a word when the reset
asserts, the next DATA read can mix leftover bytes with new beats, or the
sampler can flag a stream error. The SEP host must keep the Key Manager idle
before asserting the TRNG reset. Holding KM in software reset is sufficient;
hardware does not enforce the ordering.

Following reset release, software reprograms ESRC, waits for startup health
testing, locks the certified configuration, instantiates CSRNG, and enables EDN.
Consumers are released only after fresh endpoint/pool progress is observed.
