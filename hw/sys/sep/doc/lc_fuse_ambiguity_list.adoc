= SEP LC/Fuse-Map Spec Alignment: Ambiguity List for Arch Sign-Off
:toc:
:sectnums:

This document captures the deviations between the RTL ported from old-branch
`3539-per-owner-signing-policy-model-updates` (commit `0c06e4646`) and the
harness specification documents (`lifecycle_controller.adoc`,
`periphs.adoc`, `jtag_ptap/doc/architecture.adoc`).

Each item is tagged with an in-RTL `TODO(AMBIG-N)` comment pointing back here.
All items require explicit arch sign-off before the next tapeout milestone.

== AMBIG-1: SIP_DBG used as a universal outer gate

*File:* `hw/sys/sep/rtl/sep_lifecycle_ctrl.sv`

*Ported equation:*

[source,systemverilog]
----
assign dbg_disable_o.stap_io = !feat_ctrl_secure_tm.sip_debug;
assign dbg_disable_o.stap_smc = !feat_ctrl_secure_tm.sip_debug || !feat_ctrl_secure_tm.chiplet_dbg;
// ... all others identical pattern
----

*Problem:* `sip_debug` (SIP_DBG) sits at bit-16 in the **DBG_2** group, which is
gated by DEMOTE_2.  According to `lifecycle_controller.adoc`, DBG_2 is the
inter-chiplet debug-bypass gate; DBG_1 (SEP_DBG/CHIPLET_DBG at bits 0/1) is
the *local* debug gate opened by DEMOTE_1.

With `sip_debug` as the universal outer gate, asserting DEMOTE_1 alone does not
open *any* debug interface because SIP_DBG (DBG_2) remains 0.  This
contradicts the spec table which shows "DEMOTE_1 opens local debug group (DBG_1)".

Revisions 0.5.20/0.5.21 add "SIP_DBG is the SiP debug-access gate… external
access additionally requires the SIP_DBG path" — this *may* sanction the
current equation, but the DEMOTE_1 table row does not.

*Question for arch:*

* Should DEMOTE_1-gated bits (stap_io, stap_sep) open without DEMOTE_2 also
  being asserted?
* If yes, the equations need to be split per group:
  `stap_io = !feat_ctrl.sep_debug; stap_smc = !feat_ctrl.sip_debug || ...`

*Priority:* Highest.

== AMBIG-2: OTP JTAG-to-AXI bridges hardcoded open in all LC states

*File:* `hw/sys/sep/rtl/sep_lifecycle_ctrl.sv`

[source,systemverilog]
----
assign dbg_disable_o.smc_otp_jtag2axi = 1'b0; // permanently enabled
assign dbg_disable_o.sep_otp_jtag2axi = 1'b0; // permanently enabled
----

*Problem:* These bridges are enabled (disabled=0) in every LC state, including
PROD and PROD_END.  Commit `4983206ad` had them correctly gated by
`smc_fuse_test` / `sep_fuse_test`; commit `0c06e4646` ("Update disable bit
logic based on arch feedback") removed the gating without explanation.

`jtag_ptap/doc/architecture.adoc` still specifies that these bridges require
`fuse_test && soc_debug && ap_debug` (and `+ sep_debug` for SEP OTP) to be
enabled.

*Question for arch:* Is the hardcoded-open state intentional (e.g. fuse-test
gating happens elsewhere), or is this a regression from the refactor?

== AMBIG-3: `dft_secure` lost its fuse-test and SECURE_TM gates

*File:* `hw/sys/sep/rtl/sep_lifecycle_ctrl.sv`

[source,systemverilog]
----
assign dbg_disable_o.dft_secure = !feat_ctrl_secure_tm.sip_debug || !feat_ctrl_secure_tm.chiplet_dbg;
----

*Problem:*

. The previous gating was `!fuse_test || !sep_debug || !soc_debug || !ap_debug`.
  The fuse-test gate was removed by commit `0c06e4646` without documented
  rationale.
. `dft_secure` is derived purely from debug-group bits, so the `SECURE_TM`
  final gate (which forces `feat_ctrl[47:32] = 0`) has no influence on it.
  Commit `2a6080922` queried this open: "Should dft_secure be gated by
  secure_tm? Or is this expected to be done elsewhere?"
. The SECURE_TM final gate in `sep_lifecycle_ctrl.sv` only clears the Test
  group [47:32], but `dft_secure` is in `dbg_disable_o` (not `feat_ctrl`),
  so it is never cleared by SECURE_TM.

*Question for arch:*

* Should `dft_secure` be gated by `smc_fuse_test` (or `sep_fuse_test`) as
  before, or is its gating purely debug-group based as ported?
* Should `dft_secure` be blocked when `SECURE_TM` is active (to prevent
  scan-path exposure of secrets through the DFT chain during secure test mode)?

== AMBIG-4: Stale gating tables in JTAG documentation

*Files:*

* `hw/ip/jtag/jtag_intf_unit/doc/architecture.adoc`
* `hw/ip/jtag/jtag_ptap/doc/architecture.adoc`
* `doc/integrator/src/index.adoc`

*Problem:* All three documents still specify debug-enable conditions in terms of
`soc_debug`, `ap_debug`, and `fuse_test` — fields that this change deletes.
They will be inaccurate the moment the RTL lands.

*Action required:* Update the doc gating tables to match the new
`dbg_disable_t` signal names and the equations in `sep_lifecycle_ctrl.sv`.
This is a documentation-only update (no RTL effect) but blocks any external
integrator relying on the docs.

== AMBIG-5: `SMC_FUSE_TEST` and `FUSE_VENDOR_TEST` have no RTL consumers

*File:* `hw/sys/sep/regs/blocks/sep_efuse_map/sep_efuse_map.rdl`

*Problem:*

* Bit 37 (`smc_fuse_test`): The RDL description says "Exported on SEP
  boundary; consumed by SMC to gate its fuse-test path."  However, this
  change removes the `feat_ctrl_i` port from SMC (the only path that
  previously carried this intent) without adding a replacement SEP output
  port.  The bit is fused but nothing reads it in the RTL.
* Bit 38 (`fuse_vendor_test`): Similarly described as enabling
  vendor-specific OTP test, but has no RTL consumer.

*Question for arch:*

* What is the forwarding mechanism for `smc_fuse_test`? A new dedicated SEP
  output port?  An AXI register read by SMC firmware?  Or is this bit
  obsoleted by the new architecture?
* Same question for `fuse_vendor_test`.

== AMBIG-6: No-SEP stub polarity flip

*File:* `hw/sys/smu/rtl/smu.sv`

[source,systemverilog]
----
// Old:
sep_efuse_pkg::sep_efuse_map_lc_disable_reg_t sep_feat_ctrl;
if (!SEP_PRESENT) sep_feat_ctrl = '1; // all features disabled

// New (ported):
sep_lifecycle_ctrl_pkg::dbg_disable_t sep_dbg_disable;
if (!SEP_PRESENT) sep_dbg_disable = '0; // all debug gates open (not disabled)
----

*Problem:* Semantically equivalent under the polarity inversion (feat_ctrl
was active-low disable; dbg_disable is active-high disable), so `'1 → '0`
is correct.  However, in the no-SEP stub configuration the *safer* default
is arguably `'1` (all debug gates closed), not `'0` (all gates open).

The current ported default (`'0`) opens all debug interfaces when SEP is
absent — which may be intentional for bring-up, or may be a security gap
depending on the intended use case.

*Question for arch:* Should the no-SEP stub default be `'0` (all open, as
ported) or `'1` (all closed)?

== AMBIG-7: Fuse-map version skew between docs and RTL

*Files:* `hw/sys/sep/doc/periphs.adoc`, `doc/trm/src/revision.adoc`

*Problem:* `periphs.adoc` documents the 32-field v0.5.19–0.5.21 fuse map.
`revision.adoc` records a v0.5.22 expansion to 48 fields with a 96-bit LOCK.
This implementation adds the v0.5.22 *fields* (SEP_CHIPLET_ID, SEP_SIP_ID,
SEP_SYS_ID, spare0–7) but retains the 64-bit LOCK with coarse range locks
covering the tail (idx 29 and 30).

The repository now contains:

* RDL with v0.5.22 fields + 64-bit LOCK (this change)
* `periphs.adoc` still describing the 32-field v0.5.21 map (needs update)
* `revision.adoc` still describing the full 96-bit v0.5.22 expansion (not implemented)

*Action required:* Update `periphs.adoc` to reflect the implemented
intermediate state (v0.5.22 fields, 64-bit LOCK, coarse tail locks).
The LOCK widening to 96 bits is a separate future task (tagged with
`TODO(v0.5.22-locks)` in the RDL and `sep_efuse_pkg.sv`).

== AMBIG-8: DEMOTE lock CSR shape

*File:* `hw/sys/sep/regs/blocks/sep_lifecycle_ctrl/sep_lifecycle_ctrl.rdl`

*Background:* The spec prose names four separate CSRs:
`DEMOTE_1`, `DEMOTE_2`, `DEMOTE_LOCK_1`, `DEMOTE_LOCK_2`.  The implemented
RDL has `lock` as bit-1 *inside* each DEMOTE register (i.e. two CSRs, each
with a `demote` bit and a `lock` bit).

*Status:* Pre-existing discrepancy, not introduced by this change.  Ported
as-is with no modification.

*Question for arch:* Is the implemented two-register shape (DEMOTE_1 and
DEMOTE_2, each containing demote + lock) the intended final architecture, or
should the lock bits be in separate DEMOTE_LOCK_1/2 CSRs per the prose?
