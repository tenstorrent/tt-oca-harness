[[shared-vip-deployment]]
== Installation and DUT Deployment

[[shared-vip-python-environment]]
=== Python Environment

The native runner provisions the locked DV environment automatically:

[source,bash]
----
python3 tools/dv/run_dv.py --validate-configs
python3 tools/dv/run_dv.py --doctor --dut dtp --tool verilator
----

For standalone development, install the shared package from the repository
root:

[source,bash]
----
python3 -m pip install -e hw/common/dv
----

Supported Python versions are 3.11 through 3.13; the lock refuses a 3.14
interpreter with the project's `requires-python` range. Package dependencies
are declared in `hw/common/dv/pyproject.toml` and resolved through the
repository `uv.lock`, which pins every resolved version; `uv sync --locked`
installs exactly that set or fails.

[[shared-vip-clean-environment]]
=== Clean-Environment Qualification

A clean supported environment is a fresh interpreter of a supported version
with only the locked `dv` group installed. The sequence below is the
qualification of a candidate on each supported Python version; it needs no
simulator until the last step.

[source,bash]
----
export UV_PROJECT_ENVIRONMENT=/tmp/ocah-dv-3.11
uv sync --locked --group dv --python 3.11
uv run --locked --group dv --python 3.11 python -c \
  'import ocah_axi_vip, ocah_jtag_vip, ocah_spi_vip, ocah_uart_vip, ocah_checker, ocah_lib'
uv run --locked --group dv --python 3.11 python -m py_compile \
  hw/common/dv/vip/*/cocotb/examples/example_*.py
for selftest in hw/common/dv/vip/*/cocotb/examples/example_*_selftest.py; do
  PYTHONPATH=hw/common/dv/vip uv run --locked --group dv --python 3.11 python "$selftest"
done
python3 tools/dv/run_dv.py --doctor --dut ocah_axi_vip --tool verilator
----

The `example_*_selftest.py` files run without a simulator and print a pass
marker; the other examples are API snippets that compile here and run as the
`--dut ocah_<protocol>_vip` harness selftests (<<shared-vip-supported-simulators>>).
`--doctor` reports the interpreter, the locked packages, the namespace
bridge, the import of every testlist module with the run's `PYTHONPATH`, the
simulators on `PATH`, and the license variables each licensed tool expects.

`run_dv.py --list --json` is the authoritative framework/tool matrix.

|`ocah_jtag_vip`

|`ocah_uart_vip`
|harness `smoke`, SMC bench

Verilator is the license-free baseline that hosted CI runs. Optional-backend
qualification records the tool release outside the repository. The following
combinations are unsupported, each with the diagnostic it produces:

[cols="<3,<4,<4",options="header"]
|===
|Combination |Diagnostic |Rule

|Python 3.14 or newer
|`uv sync` refuses the interpreter against `requires-python >=3.11,<3.14`

|A `cocotbext-*` backend missing from the environment

[[shared-vip-import-contract]]
=== Import Contract

Always import the top-level OCAH package:

[source,python]
----
from ocah_axi_vip import OcahAxiMasterAgent
from ocah_jtag_vip import OcahJtagMasterDriver
from ocah_checker import OcahChecker
----

Do not import:

* implementation modules such as `ocah_axi_vip.cocotb.ocah_axi_master`;
* backend packages such as `cocotbext.axi` in new tests;
* private backend transaction/channel types for normal checking.

The root package is the compatibility boundary and may change its backend
without changing test code.

[[shared-vip-cocotb-deployment]]
=== Cocotb Deployment Pattern

A DUT environment typically performs four steps:

. construct and bind the VIP;
. initialize outputs before time advances;
. wait for DUT reset release;
. start stimulus/monitor tasks and retain their handles.

[source,python]
----
master = OcahAxiMasterAgent.from_prefix(
    dut,
    "s_axi",
    dut.clk_i,
    dut.rst_ni,
    reset_active_level=False,
    timeout_ns=50_000,
).sequence
master.init_signals()
await master.wait_for_reset()

result = await master.write_result(
    0x1000,
    0xA5A5_5A5A,
    check_response=False,
)
----

The DUT-local agent converts `result` into its sequence item, scoreboard event,
or checker evidence. Tests should not inspect `result.raw` except during
backend debug.

[[shared-vip-monitor-deployment]]
=== Monitor and Checker Lifecycle

Passive monitors do not drive signals:

[source,python]
----
monitor = OcahAxiMonitor.from_prefix(dut, "s_axi", dut.clk_i)
checker = OcahAxiChecker(raise_on_error=False)
checker.attach_monitor(monitor)

await monitor.start()
# Drive DUT traffic.
await monitor.stop()
checker.assert_clean()
----

Monitor callbacks catch and log subscriber exceptions so one
subscriber cannot terminate observation. A checker attached to a monitor must
retain findings before raising, and the owning test or scoreboard must finalize
after traffic. Named evidence should be finalized through the per-protocol
checker when it composes `ocah_checker`.

[[shared-vip-split-port]]
=== Open-Drain Split-Port Binding

I2C/I3C testbenches may expose:

* a resolved bus input read by cocotb;
* an `ext_low` input where `1` means the testbench pulls the line low.

This polarity differs from many backend APIs, where `1` means release. Keep the
signal-name and polarity binding in a DUT-local adapter, while implementing
wired-AND and reusable protocol behavior in the shared split-port helper.

[source,text]
----
resolved_sda  <- DUT drive AND testbench pull-low votes
ext_sda_low   <- DUT-local adapter output
shared VIP    <- protocol state and transaction API
----

Never resolve an open-drain bus by letting independent VIP instances overwrite
one another's output. Use the shared package's per-bus wired-AND mechanism.

[[shared-vip-multiple-instances]]
=== Multiple Instances

Each VIP instance must have:

* a unique log name;
* an explicit signal prefix or map;
* independent statistics and retained history;
* deterministic configuration;
* bounded history where monitoring can be long-lived.

Do not use module-level singleton state unless it represents one physical bus
and is keyed by the bound signal identity.

[[shared-vip-uvm-deployment]]
=== SystemVerilog UVM Deployment

Protocols with UVM collateral provide a shared interface, module collateral
(SVA checkers, behavioral responders), and a UVM package with VIP-level
environments and agents. The framework-level mechanics — sim-config
declaration, VIP consumption through the VIP-owned `uvm/sources.toml`
manifests with their load-bearing compile order, and the bring-up
walkthrough — live in the SystemVerilog UVM Framework section of this guide
(`uvm-framework.adoc`); this section covers the deployment pattern inside
the testbench.

*Interface publication.* The DUT top instantiates the shared interface and
places it in `uvm_config_db`; the DUT environment retrieves it:

[source,systemverilog]
----
ocah_jtag_if jtag_if();

initial begin
    uvm_config_db#(virtual ocah_jtag_if)::set(
        null, "*", "jtag_vif", jtag_if
    );
end
----

*Configuration and environment.* The DUT environment assigns the retrieved
interface to the VIP config object (`ocah_jtag_master_config`,
`ocah_axi_config`, ...), sets geometry, gating, and the evidence `name_tag`
there, and publishes the config to the VIP-level environment it
instantiates. The VIP environments and agents are the factory seam:
optional backend integrations override them by type, so DUT code creates them
through the factory and never hard-codes backend classes.

*Sequences.* DUT sequences drive a VIP only through its `*_sequence` API
classes (for AXI: `write_result`/`read_result`/`burst_*_result` on the
master sequence; backdoor and injection operations on the slave sequence).
A missing operation is added to the VIP API, never inlined as raw driver or
virtual-interface manipulation in DUT code. DUT scoreboards consume OCAH
events or monitor items; nothing reaches into driver internals.

*Reactive responders.* The shared AXI slave agent answers every
DUT-mastered AXI boundary: the testbench wires the DUT-driven signals into
the slave interface instance, the agent's driver drives the responder-side
signals back, and memory preloads and error injection are programmed by
sequences through `ocah_axi_slave_sequence` rather than through testbench
ports or hierarchical writes. A port the bench flattens to pins is wired
directly; a port that stays a request/response struct inside the testbench
top is placed on an `ocah_axi_if` instance through
`interface/ocah_axi_struct_bridge.sv` and answered the same way.

*Passive checking.* The passive stack (monitor, reference model,
scoreboard) attaches per bus behind cfg gating; every checker extends the
shared evidence base (`ocah_checker_uvm_pkg::ocah_checker`, see
<<shared-checker-model-contract>>), and the owning component finalizes it
exactly once after traffic — the AXI scoreboard in its `check_phase`, DUT
subscribers from the environment. The protocol SVA modules
(`sva/ocah_*_sva.sv`) are instantiated in the testbench top on the raw
signals, enabled through a testbench-interface control.

*Backend hooks.* Each VIP config carries the opaque `vendor_cfg` extension
and the `en_monitor` knob, and each shared interface carries a guarded
vendor-interface nest for optional integrations; see
<<shared-vip-backend-deployment>>.

[[shared-vip-backend-deployment]]
=== Optional Backend Deployment

An optional VIP backend is adopter-owned. The normative integration
contract is the *Template Contract* section of
`hw/common/dv/vip/ocah_jtag_vip/README.md`: the open tree carries only the
hooks — the opaque `vendor_cfg` extension, the `cfg.en_monitor` knob, the
guarded vendor-interface nest, and the factory-overridable VIP
environments. Adopter overlays supply backend implementations without adding
a dependency from the open tree.

License-free contributor tests must remain runnable without optional
packages, and an integration preserves OCAH item/config/result semantics so
tests, VPLAN evidence, and DUT scoreboards stay backend-independent.

[[shared-vip-error-deployment]]
=== Error and Timeout Handling

Positive tests normally use strict response checking. Negative tests use result
APIs with checking disabled, then compare the exact response:

[source,python]
----
result = await master.write_result(
    blocked_addr,
    data,
    check_response=False,
    timeout_ns=50_000,
)
checker.expect_equal(
    "CHK-DECERR",
    result.resp,
    RESP_DECERR,
    context=f"addr={blocked_addr:#x}",
)
checker.expect_not_timed_out(
    "CHK-COMPLETION",
    timed_out=result.timed_out,
    timeout_ns=50_000,
)
----

`allow_timeout=True` makes a timeout observable; it does not make the operation
successful. An expected timeout requires explicit VPLAN intent, a declared
bound, and `expect_timeout()` evidence. Every blocking master operation is
bounded even without a `timeout_ns` argument: the instance bound applies, else
the package default (`DEFAULT_TIMEOUT_NS`, 500 µs, or the
`+OCAH_AXI_TIMEOUT_NS` plusarg).

[[shared-vip-deployment-validation]]
=== Deployment Validation

Before relying on a new binding:

[source,bash]
----
python3 -m py_compile <changed-python-files>
python3 tools/dv/run_dv.py --validate-configs
python3 tools/dv/run_dv.py --doctor --dut <dut> --tool <tool>
python3 tools/dv/run_dv.py \
  --dut <dut> --items <test> --tool <tool> --seed 1 --dry-run
python3 tools/dv/run_dv.py \
  --dut <dut> --items <test> --tool <tool> --seed 1
----

Retain the run-level `result.json`, structured test result, relevant log, tool
versions, seed, and commit SHA in the CI artifact store or another external
qualification record.

[[shared-vip-deployment-troubleshooting]]
=== Troubleshooting

[cols="<3,<7",options="header"]
|===
|Symptom |Action

|Top-level OCAH import fails
|Run through `tools/dv/run_dv.py`, reinstall `hw/common/dv` editable, and verify
the generated Python namespace bridge.

|Backend import fails
|Check `hw/common/dv/pyproject.toml`, package README version/license notes, and
`PYTHONPATH` for vendored dependencies.

|Transaction never completes
|Verify reset polarity and clock, require a finite `timeout_ns`, and check that
the DUT has a responder for the selected address.

|Monitor sees no items
|Confirm it was started before traffic, the prefix matches the flattened bus,
and the test calls `stop()`/finalization after traffic.

|Checker logs an error but test passes
|The monitor may have caught the callback exception. Ensure the checker retained
the finding and the owning test or scoreboard calls `finalize()` or
`assert_clean()`.
|===
