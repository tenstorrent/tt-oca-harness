= User IP Integration
:doctype: book
:sectanchors:
:sectlinks:
:sectnums:
:source-highlighter: highlight.js

This chapter describes how to add adopter-owned IP to a chiplet containing the
Open Chiplet Atlas Harness (OCAH). It covers three distinct attachment classes:
management peripherals, security extensions, and application logic in the user
subsystem. Choosing the correct class matters because connecting an IP to an
OCAH bus does not automatically make it trusted, securely booted,
lifecycle-controlled, or protected from other initiators.
[REQ-UIP-MOD-1] The integrator shall define those properties and provide the
fabric, firewalls, IOMMU, secure-boot handoff, and physical implementation
needed to enforce them.

OCAH Phase 1 does not contain the general-purpose System Management Network
(SMN), die-to-die fabric, or user-subsystem interconnect shown in the system
block diagram. The application subsystem remains an adopter-owned black box.
Consequently, the application path in this chapter is an integration contract,
not a drop-in RTL port on `smu.sv`. The adopter owns the application fabric,
address decode, clock and power domains, and application software stack; OCAH
provides management and security services around that subsystem.

[[user-ip-integration-model]]
== Select the trust and attachment model

First decide whether SMC firmware owns the IP as part of the management domain,
SEP firmware owns it inside or in direct support of the security boundary, or
application firmware or an OS owns it in the adopter application domain. An
application-domain IP remains outside the OCAH trusted computing base unless a
threat-model review explicitly places it inside. This classification determines
the correct CSR, interrupt, data, boot, and debug paths; the classes are not
interchangeable.

.User IP attachment classes
[cols="18%,22%,23%,20%,17%",options="header"]
|===
|Class |Runtime and trust owner |CSR connection |DMA or data connection
|Interrupt destination

|SMC-managed peripheral
|SMC firmware; management-plane policy
|The supplementary portion of the SMC adopter peripheral window,
`smc_external_req_o` / `smc_external_resp_i`
|Usually none; attach any independent manager to an adopter-owned fabric
|An assigned bit of SMU `ext_interrupts_i`

|SEP security extension
|SEP firmware; inside or directly supporting the security boundary
|The SEP external region through `sep_external_req_o` /
`sep_external_resp_i`
|The SEP extension port is a manager-to-subordinate path. Any extension DMA
manager uses a separately contained adopter-fabric connection
|An assigned bit of `sep_extintsrc_req_i`

|Application-owned accelerator
|Application firmware or OS; outside the OCAH trusted computing base unless a
threat-model review explicitly places it inside
|An adopter SoC CSR fabric
|The IP's AXI manager connects through an IOMMU or equivalent firewall to the
adopter memory fabric
|The application interrupt controller; optionally also an assigned bit of SMU
`ext_interrupts_i` for management or fault notification
|===

Before selecting a class, record:

* the code, configuration, keys, model weights, and user data handled by the IP;
* which of those assets require integrity, confidentiality, or anti-rollback;
* whether the IP and its supply chain are trusted;
* which boot stage authenticates and releases the IP;
* which initiators may access its CSRs and memory;
* the least-privilege AXI security attributes and source identity it receives;
* its debug, scan, test, and production-lifecycle policy; and
* where security and fatal faults are reported.

The OCAH SMC and SEP inbound/outbound filters protect their own traffic paths.
They do not automatically protect an IP attached to the adopter fabric.
[REQ-UIP-MOD-2] The integrator shall use default-deny hardware policy at every
new trust boundary and prevent less trusted software or the IP itself from
rewriting or spoofing that policy.

[REQ-UIP-MOD-3] The integrator shall not connect an adopter DMA manager to
`smu_axi_out_req_o`. That port is an OCAH *manager output*: it carries
transactions initiated by the SMC or SEP to the adopter fabric. A user IP's
DMA interface is another manager on that fabric.

[source,text]
----
                         +--------------------------------------+
SMC / SEP -- SMU AXI out |                                      |
                         | adopter SMN / application fabric     |--> memory
Application CPU -------->|                                      |
User IP DMA --> IOMMU --->|                                      |
                         +--------------------------------------+
----

The SMU inbound AXI port is also not a route from an external manager to an
arbitrary user-subsystem target. Its internal crossbar routes inbound traffic
only to the programmed SMC and SEP apertures. Unmatched inbound requests return
a decode error.

[[smc-managed-user-ip]]
== Integrate an SMC-managed peripheral

[REQ-UIP-SMC-1] The integrator shall use this model only for product-specific
control and status logic that SMC firmware configures or monitors, such as a
sensor, pad controller, or small management engine.

=== Allocate the SMC supplementary window

`smc_external_req_o` and `smc_external_resp_i` form a 32-bit AXI4-Lite
request/response pair. The complete adopter peripheral window starts at SMC
local `BASE + 0x040_0000` and is 4 MiB. The mandatory region contains the
technology-specific GPIO, PLL, PVT, and eFuse SHIM blocks. Optional adopter IP
belongs in the supplementary region beginning at local
`BASE + 0x040_4000`.

The as-shipped `smc_ip_integration.sv` decoder applies modulo-0x4000 address
folding (`addr % ExtWindowSize`) before comparing against the mandatory-region
device offsets (GPIO at `0x1100`, PLL at `0x2000`, PVT at `0x3000`). A
supplementary-region address with a low-12-bit offset that falls within a
mandatory device range will alias to that device.
[REQ-UIP-SMC-2] The adopter shall replace or extend the decoder in
`hw/top/smc_ip_integration.sv` so that supplementary-region addresses are not
subject to modulo folding before mandatory-device comparison. The modulo decoder
shall not remain in place in front of the supplementary region.

[REQ-UIP-SMC-3] The downstream decoder shall reserve a naturally aligned range large enough for the IP register map.
[REQ-UIP-SMC-4] The downstream decoder shall reject overlaps with mandatory blocks and other adopter allocations.
[REQ-UIP-SMC-5] The downstream decoder shall route both read and write channels to the same subordinate.
[REQ-UIP-SMC-6] The downstream decoder shall return `DECERR` for an unallocated address and propagate an IP error as `SLVERR`.
[REQ-UIP-SMC-7] The integrator shall keep the allocation in the chiplet address-map source of truth used by RTL, firmware, verification, and documentation.

The SMC `GLOBAL_BASE` and `REGION_SIZE` CSRs describe the complete SMC aperture;
they are not per-IP aperture registers. Adding a peripheral to the supplementary
window does not create another OCAH aperture CSR.

=== Adapt the register protocol

No adapter is needed for an IP with a compatible 32-bit AXI4-Lite subordinate.
For a standard OCAH/OpenTitan-style TL-UL subordinate, the repository provides
`hw/common/axi/axi_lite_to_tlul.sv`. It accepts packed AXI request/response
types and produces packed `tlul_pkg::tl_h2d_t` / `tlul_pkg::tl_d2h_t` values,
including TL-UL command and data integrity.

That converter is not a drop-in adapter for an IP exposing a flattened subset
of TL-UL. In that case, use an IP-supplied wrapper or add an explicit shim and
verify every field, response, byte-enable, and error mapping. The
<<npu-worked-example,NPU worked example>> uses the NPU's own AXI4-Lite wrapper
for this reason.

=== Route the interrupt

Assign each SMC-visible source a bit of SMU `ext_interrupts_i`, whose integration
width is set by the `NUM_INT_TO_SMC` configuration parameter. The SMC
synchronizes this vector into its clock domain. Masking the interrupt does not
clear its source, and an un-stretched one-cycle pulse may be lost across this
boundary.

[REQ-UIP-SMC-8] A source asynchronous to the SMC clock shall hold the interrupt
asserted until SMC firmware reads and clears the status register in the
peripheral using the peripheral-defined clear operation such as W1C.

[REQ-UIP-SMC-9] The integrator shall record the bit assignment in the platform
interrupt map and use the same value in RTL, SMC firmware, and the verification
environment.

[REQ-UIP-SMC-10] `sep_extintsrc_req_i` is a separate SEP interrupt input and
shall not be substituted for `ext_interrupts_i`.

[[sep-security-extension-ip]]
== Integrate a SEP security extension

Use this model only for logic that SEP firmware must own as part of, or in
direct support of, the chiplet security boundary. Examples include a
security-policy engine or an adopter cryptographic service.
[REQ-UIP-SEP-1] The integrator shall not place an ordinary application
accelerator behind the SEP extension port merely to make it appear trusted.

=== Allocate the SEP external region

`sep_external_req_o` and `sep_external_resp_i` expose the SEP local crossbar's
32-bit-address, 64-bit-data AXI4 extension target at local addresses
`0x2000_0000` through `0x3fff_ffff`. The first four bytes at `0x2000_0000` are
intercepted by `sep.sv` for the eFuse SHIM.
[REQ-UIP-SEP-2] The adopter decoder shall not allocate any block overlapping
`0x2000_0000`--`0x2000_0003`. Use `hw/sys/sep/dv/models/regs/sep_external.rdl`
and the generated `OCH_SEP_TOP_SEP_EXTERNAL_EFUSE_SHIM_CTRL_BASE_ADDR` and
`OCH_SEP_TOP_SEP_EXTERNAL_EFUSE_SHIM_CTRL_SIZE` constants in
`hw/sys/sep/regs/gen/sv/sep_addrmap_pkg.sv` as the machine-readable source of
truth; the map may evolve independently of this guide.
[REQ-UIP-SEP-3] The adopter decoder shall reserve naturally aligned,
non-overlapping ranges in the remainder and return `DECERR` for holes.

The as-shipped `sep_ip_integration.sv` terminates `axi_extension_axi_req_i` /
`axi_extension_axi_resp_o` with an `axi_err_slv` instance that returns `DECERR`
for all transactions. These signals are module-level ports.
[REQ-UIP-SEP-4] To use the SEP extension region, the adopter shall modify
`hw/top/sep_ip_integration.sv` to replace the `u_axi_extension_err_slv` instance with their own
decoder. An outer wrapper module cannot override an internal instance connection; the adopter must
edit or replace the integration file directly.

The port is a transaction path from SEP-local initiators to adopter
subordinates. It is not a connection for an adopter IP's DMA manager. The SEP
CPU LSU/debug paths, SEP DMA, and the filtered system-interface path have
crossbar connectivity to the extension target. External system access remains
subject to the SEP inbound filter, which is block-by-default after reset.
[REQ-UIP-SEP-4a] SEP firmware shall open the inbound filter deliberately; it is not unlocked by hardware default.

[REQ-UIP-SEP-5] The integrator shall preserve the AXI ID, `PROT`, and
user/source information carried by the packed SEP request type.
[REQ-UIP-SEP-6] When adapting to another protocol or a narrower data path, the
integrator shall verify the adapter explicitly.
[REQ-UIP-SEP-7] The integrator shall cover burst conversion, byte strobes,
ordering, response IDs, and error propagation.

=== Apply SEP security policy

Placing a block behind the SEP extension port only changes reachability; it
does not prove that the block is trustworthy.
[REQ-UIP-SEP-8] The security design shall include executable or mutable extension state in the appropriate verified-boot and anti-rollback policy.
[REQ-UIP-SEP-9] The security design shall prevent non-secure or incorrectly identified initiators from reaching protected registers.
[REQ-UIP-SEP-10] The security design shall exclude roots, keys, and integrity-critical state from scan, and classify any secret-consuming state under the SEP scan policy.
[REQ-UIP-SEP-11] The security design shall define zeroization and reset behavior for sensitive state.
[REQ-UIP-SEP-12] The integrator shall constrain any extension DMA manager independently at the adopter fabric.
[REQ-UIP-SEP-13] The security design shall route integrity, tamper, and fatal errors to a security or safety handler that cannot be masked by application software.

[REQ-UIP-SEP-14] The integrator shall assign each SEP-visible interrupt an
allocated bit of `sep_extintsrc_req_i`.
[REQ-UIP-SEP-15] The integrator shall synchronize every asynchronous
`sep_extintsrc_req_i` source to the SEP clock domain before the SEP boundary.
`sep.sv` concatenates `extintsrc_req` into the interrupt vector combinationally
with no internal synchronizer; metastability is the integrator's responsibility.
[REQ-UIP-SEP-15a] A pulse interrupt source shall additionally use level
retention, a toggle handshake, or a pulse stretcher to prevent event loss across
the synchronizer.
[REQ-UIP-SEP-16] The integrator shall not route a SEP interrupt source to SMU
`ext_interrupts_i` unless SMC also has an independent management reason to
receive the event.

[[application-owned-user-ip]]
== Integrate an application-owned accelerator

Use this model when an application processor owns the command queue, buffers,
and normal interrupt service for an accelerator.

NOTE: Validation status: this section is integration guidance. OCAH Phase 1
provides neither the application fabric/SMN nor an application-owned
accelerator attachment, so the complete path described here has not been
implemented or exercised in OCAH simulation.
[REQ-UIP-APP-1] Adopters shall record product-level RTL, CDC/RDC, simulation,
firmware, and security-review evidence.

=== Connect control and DMA independently

Place the CSR subordinate on the adopter's application CSR fabric. In a future
full-harness integration this fabric may be the SMN shown in the OCAH system
architecture; Phase 1 supplies no SMN RTL. [REQ-UIP-APP-2] The integrator shall connect the DMA manager through a trusted
ingress point to the adopter memory fabric as a peer of the application CPU and
the OCAH outbound manager.
[REQ-UIP-APP-3] The fabric shall supply any required address-width, data-width,
ID-width, clock-domain, security, and coherency adapters.

For a manager with an address width narrower than the fabric, zero-extend its
addresses. Zero-extension restricts the manager to the low part of the physical
address space; it is not address translation or security containment.

[REQ-UIP-APP-4] The integrator shall treat a third-party or application-owned
DMA engine as untrusted by default.
[REQ-UIP-APP-5] The integrator shall place an IOMMU or equivalent
address-and-permission firewall between the DMA engine and memory.
[REQ-UIP-APP-5a] The integrator shall assign a non-spoofable stream/source
identity to the DMA engine at the trusted fabric ingress.
[REQ-UIP-APP-5b] The integrator shall configure the firewall to permit only the
buffers and operations required for the current workload.
[REQ-UIP-APP-5c] An integration may omit containment only when a threat-model
review explicitly accepts the IP inside the relevant trust boundary or proves the
hardware connection cannot reach another asset.

[REQ-UIP-APP-6] If the IP does not generate AXI `AxPROT` or fabric user/source
fields, the trusted adapter shall supply least-privilege values. Application IP
normally originates non-secure, unprivileged data transactions
(`AxPROT = 3'b010`).
[REQ-UIP-APP-7] The integrator shall not let an untrusted IP assert secure
privilege or choose its own authenticated source ID.
[REQ-UIP-APP-8] The integrator shall validate unsupported transaction types,
including atomics and exclusive accesses, at the ingress.

[REQ-UIP-APP-9] The system address map shall define the CPU-visible CSR aperture independently.
[REQ-UIP-APP-10] The system address map shall define the DMA-visible memory aperture independently.
[REQ-UIP-APP-11] The system address map shall state whether the SMC or SEP can also reach the CSR aperture through `smu_axi_out_req_o`.
[REQ-UIP-APP-12] The system address map shall state which initiators and security states are permitted by the adopter fabric.
[REQ-UIP-APP-13] The system address map shall state the IOMMU/firewall context and non-spoofable source identity.
[REQ-UIP-APP-14] The system address map shall state which security policy registers become locked before the IP is released.

=== Route application and management interrupts

Route completion and recoverable work errors to the application interrupt
controller. A separate fault signal, or an intentional duplicate of a retained
level interrupt, may also be assigned to SMU `ext_interrupts_i` for SMC
management or fault recovery.

[REQ-UIP-APP-15] The integrator shall not join two independently cleared
interrupt controllers to a pulse.
[REQ-UIP-APP-16] The integrator shall define the ownership of status
acknowledgement and masking so one handler cannot hide an event from the other.

[[user-ip-security-lifecycle]]
== Integrate secure boot, lifecycle, debug, and test

=== Establish a trusted release sequence

[REQ-UIP-BOOT-1] The integrator shall hold application IP in reset while the
chiplet root of trust is establishing policy.
[REQ-UIP-BOOT-1a] The integrator shall keep the IP's bus-master capability
blocked while the chiplet root of trust is establishing policy.

Before enabling transactions:

. [REQ-UIP-BOOT-2] SEP shall authenticate every executable or mutable configuration item
  required by the product threat model, check its security version, and extend the
  measurement into attestation when required.
. [REQ-UIP-BOOT-3] Trusted firmware shall configure the CSR firewall, DMA stream identity,
  IOMMU/firewall ranges, interrupt ownership, and fault routing.
. [REQ-UIP-BOOT-4] Trusted firmware shall lock policy that application software and the IP
  shall not change.
. [REQ-UIP-BOOT-5] SMC shall complete the power, clock, reset, and isolation sequence.
. [REQ-UIP-BOOT-6] The secure-management handoff shall record success before the application
  driver enables queues or DMA.

OCAH does not provide a generic manifest loader or release API for arbitrary
user IP.
[REQ-UIP-BOOT-7] The adopter shall extend the verified-boot policy and trusted
firmware for the selected IP, or integrate an equivalent platform
root-of-trust service, then verify that implementation as part of the product
security case.

The authenticated set is product-specific. For an accelerator it may include
microcode, firmware, register presets, bitstreams, or integrity-sensitive model
metadata. Bulk user data need not be part of verified boot, but it still needs
runtime access control. A hardwired accelerator with no mutable executable
state still requires identity/version checks and containment before release.

[REQ-UIP-BOOT-8] The release sequence shall fail closed.
[REQ-UIP-BOOT-9] An authentication, rollback, policy-lock, or firewall setup
failure shall leave the IP reset or bus-blocked.
[REQ-UIP-BOOT-10] An authentication, rollback, policy-lock, or firewall setup
failure shall produce a diagnosable security event.
[REQ-UIP-BOOT-11] Application software shall not be able to convert that failure
into a release.

=== Apply lifecycle and scan policy

Classify adopter IP state using the SEP lifecycle asset model:

* Class 1 confidentiality or integrity assets are excluded from scan;
* Class 2 secret-consuming state is placed on a dedicated chain that is never
  scan-dumpable and observes the secure-test rules; and
* Class 3 general logic is accessible only when the applicable owner and
  lifecycle debug policy permit it.

The SEP lifecycle architecture reserves adopter bits in its feature-control
vector for additional debug, test, and functional gates. The bit-allocation
convention is currently open. The current SMU boundary exposes `lc_state_o`, an
8-bit differential encoding of the four-bit lifecycle state, and `secure_tm_o`,
a single-bit secure-test-mode indication, but not the complete feature-control
vector. An IP that needs lifecycle-controlled enables therefore requires an
explicitly reviewed extension to the integration wrapper and lifecycle/RDL
allocation.
[REQ-UIP-BOOT-12] An IP that needs lifecycle-controlled enables shall not infer
an ad-hoc debug authorization from `lc_state_o` alone.

`secure_tm_o` indicates secure test mode; it is not a general functional-access
authorization.
[REQ-UIP-BOOT-13] The integrator shall document how the IP's DTP/scan path, test
enables, JTAG-visible registers, SRAM test, and secret zeroization behave in
every production, development, RMA, and secure-test condition used by the
product.

[[user-ip-clocks-resets-power]]
== Integrate clocks, reset, and power

=== Single-clock IP

An IP may use an existing adopter functional clock when its timing target and
power state match that domain.
[REQ-UIP-CLK-1] The integrator shall generate an asynchronous-assert,
synchronous-deassert reset for that clock.
[REQ-UIP-CLK-2] The integrator shall not use an SMC-domain reset output as a
synchronous reset in an unrelated clock domain without a reset-domain adapter.

=== Independent-clock IP

When the user IP runs at a different frequency, the integrator shall place CDC logic at every boundary.
[REQ-UIP-CLK-3] The integrator shall use an asynchronous AXI bridge or correctly sized channel FIFOs for the CSR or DMA interface.
[REQ-UIP-CLK-4] The integrator shall synchronize retained status levels across the clock boundary.
[REQ-UIP-CLK-5] The integrator shall transfer pulses with a toggle, handshake, or pulse stretcher.
[REQ-UIP-CLK-6] The integrator shall constrain every asynchronous clock relationship in the SoC timing-constraint file.
[REQ-UIP-CLK-7] The integrator shall run static CDC and reset-domain-crossing analysis on the assembled SoC.

An AXI register slice is not a CDC bridge.
[REQ-UIP-CLK-8] All five AXI channels shall obey the same clocking contract.

=== Power and isolation sequence

OCAH exposes the 32-bit vectors `ss_config_o`, `isolate_req_o`, and
`ss_reset_complete_i`, plus
`smc_reset_unit_pkg::reset_ctrl_t ss_reset_ctrl_o[31:0]`. The latter is a
32-element unpacked array of reset-control structures, not a plain 32-bit
vector; use the field definitions in `smc_reset_unit_pkg` when connecting it.
These interfaces provide adopter-defined subsystem lifecycle control.

[REQ-UIP-CLK-9] The adopter shall assign a subsystem index from the
`ss_reset_ctrl_o` array to the user IP.
[REQ-UIP-CLK-9a] The adopter shall translate the
`smc_reset_unit_pkg::reset_ctrl_t` fields for that index into
technology-specific reset and power-switch controls.
[REQ-UIP-CLK-9b] The adopter shall insert isolation cells on all outputs and
retention cells on state that must survive power removal.
[REQ-UIP-CLK-9c] The adopter shall define the completion condition that drives
`ss_reset_complete_i` for that index.

OCAH does not instantiate the user IP's power controller.

Use this ordering for a switchable user domain:

. [REQ-UIP-CLK-10] The integrator shall hold the IP in reset, isolate its outputs, and block its manager ports.
. [REQ-UIP-CLK-11] The integrator shall enable the domain supply and wait for the adopter power-good indication.
. [REQ-UIP-CLK-12] The integrator shall start and qualify the functional clock. Clock qualification includes
  confirming PLL lock or equivalent clock-gating stability before the clock is
  considered clean.
. [REQ-UIP-CLK-13] The integrator shall configure and lock the trusted fabric ingress, IOMMU/firewall, and fault
  routing while the IP remains blocked.
. [REQ-UIP-CLK-14] The integrator shall complete the required authentication and secure-management release checks.
. [REQ-UIP-CLK-15] The integrator shall deassert the IP reset synchronously to its clock only after release is
  authorized.
. [REQ-UIP-CLK-16] The integrator shall complete any IP-local memory initialization.
. [REQ-UIP-CLK-17] The adopter logic shall assert the assigned `ss_reset_complete_i` bit only when
  the IP is internally initialized and ready to accept transactions once isolation is removed.
  SMC firmware polls the SS_RESET_COMPLETE CSR (which synchronises `ss_reset_complete_i` through a
  3-stage synchronizer) and, when set, clears the applicable isolation request source(s) for that
  subsystem index. `isolate_req_o[i]` is the OR of three sources: `isolate_req_reg[i]` (per-subsystem
  software isolation, the normal sequencing path), the pin source when `isolate_req_pinen_reg[i]` is
  set, and the FLR source when `isolate_req_smcen_reg[i]` and the global `isolate_req_smc_reg` are
  both set. [REQ-UIP-CLK-17a] All contributing isolation sources for that index shall be inactive
  before `isolate_req_o[i]` de-asserts.
  [REQ-UIP-CLK-17b] The adopter logic shall deassert `ss_reset_complete_i` for each subsystem index
  before that index enters a new reset or power cycle. SMC firmware shall confirm that the
  SS_RESET_COMPLETE CSR reads zero for that index before beginning or accepting completion of a
  new sequence, ensuring the three-stage synchronizer has propagated the deassertion low before
  firmware acts on any new assertion.
. [REQ-UIP-CLK-18] The adopter logic shall remove isolation clamps only after observing
  `isolate_req_o[i]` de-asserted for that subsystem index.
. [REQ-UIP-CLK-19] The integrator shall enable DMA transactions only after isolation clamps are
  removed and the manager path is explicitly unblocked.

NOTE: The ordering between `ss_reset_complete_i` assertion, SMC clearing
`isolate_req_o`, and removal of isolation clamps is enforced by firmware
convention, not by RTL interlock. REQ-UIP-CLK-18 requires the adopter
integration to observe `isolate_req_o` de-asserted before removing clamps.

Reverse the dependencies when powering down: stop new work, drain or abort DMA,
mask interrupts, isolate outputs, assert reset, stop the functional clock, and
then remove power.
[REQ-UIP-CLK-20] The integrator shall not remove power while an AXI transaction
can still return a response.

[[user-ip-software]]
== Integrate software and firmware

=== Maintain one platform contract

[REQ-UIP-SW-1] Software-visible allocations shall be generated from, or checked against, the hardware address and interrupt maps.
[REQ-UIP-SW-2] The platform contract shall record the CSR base and span.
[REQ-UIP-SW-3] The platform contract shall record the interrupt number, trigger type, polarity, and owner.
[REQ-UIP-SW-4] The platform contract shall record the DMA address width and accessible ranges.
[REQ-UIP-SW-5] The platform contract shall record the DMA stream/source identity, IOMMU context, and permission owner.
[REQ-UIP-SW-6] The platform contract shall record the AXI security/privilege attributes and allowed CSR initiators.
[REQ-UIP-SW-7] The platform contract shall record the coherency and cache-maintenance policy.
[REQ-UIP-SW-8] The platform contract shall record the reset and power-domain index.
[REQ-UIP-SW-9] The platform contract shall record the IP configuration or ABI version, authenticated components, minimum security
  versions, and secure-release indication.

Use the generated `*_addr.h` and register headers under a block's
`regs/gen/c/` directory when its register map is supplied as SystemRDL.
[REQ-UIP-SW-10] An external IP without SystemRDL shall supply an equivalent
reviewed header.
[REQ-UIP-SW-11] The integrator shall not infer register offsets from generated
SystemVerilog or duplicate unexplained numeric addresses in multiple drivers.

=== Place initialization in the boot flow

[REQ-UIP-SW-12] For an SMC-managed peripheral, the integrator shall initialize
it after the SMC has completed fuse sensing and required memory repair,
programmed the SMC/SEP global apertures, and made the peripheral's clock and
power domain available, then configure and clear the peripheral before enabling
its SMC interrupt source.

[REQ-UIP-SW-13] For a SEP security extension, SEP firmware shall validate the
extension identity and version, establish access policy, initialize sensitive
state, clear pending status, and enable its SEP interrupt only after the
relevant verified-boot stage succeeds.

For an application-owned accelerator, trusted SEP/SMC firmware first performs
the authenticated release and containment sequence.
[REQ-UIP-SW-14] Application firmware or the OS driver shall verify that secure
release succeeded before enabling queues or DMA.
[REQ-UIP-SW-15] The driver shall validate the hardware/ABI version against the
authenticated minimum before use.
[REQ-UIP-SW-16] The driver shall allocate DMA-safe buffers through the assigned
IOMMU context.
[REQ-UIP-SW-17] The driver shall clear stale interrupt status and register the
application interrupt handler before enabling work.
[REQ-UIP-SW-18] A driver shall not substitute its own version check for the
secure boot decision.

=== Handle DMA coherency

[REQ-UIP-SW-19] If the user IP is not coherent with CPU caches, software shall
use uncached buffers or perform cache maintenance.
[REQ-UIP-SW-20] Before starting device reads, the driver shall clean CPU dirty
lines and execute the platform's required write barrier.
[REQ-UIP-SW-21] After device writes complete, the driver shall execute the
completion/read barrier and invalidate affected CPU cache lines before consuming
results.
[REQ-UIP-SW-22] The driver shall prevent buffers from being unmapped or reused
while DMA is active.

=== Bound failures and recovery

[REQ-UIP-SW-23] Every wait shall have a timeout.
[REQ-UIP-SW-24] On failure, the driver shall capture the IP error registers and
fabric response before clearing them.
[OPT-UIP-SW-1] Recovery should progress from least to most disruptive.
. [OPT-UIP-SW-2] The driver should stop new submissions and mask the IP interrupt first.
. [OPT-UIP-SW-3] The driver should acknowledge retained interrupt status.
. [OPT-UIP-SW-4] The driver should request an IP-local soft reset, if supported.
. [OPT-UIP-SW-5] The integrator should assert the adopter subsystem reset after DMA has quiesced.
. [OPT-UIP-SW-6] The integrator should power-cycle the domain only after isolation is asserted.

Document which state survives each reset. A soft reset that leaves a datapath
or DMA engine in an error state is not a complete recovery mechanism.

[[npu-worked-example]]
== Worked example: application-owned NPU

This example uses the external NPU as a representative DMA-capable accelerator.
The OCAH tree does not contain or redistribute NPU source. The example adapter
instantiates the external `npu_axi_csr_wrap`, not the raw `npu_top`. It is an
illustrative boundary adapter, not a self-contained public regression: an
open-source integrator cannot compile it without separately obtaining the NPU
package and wrapper.
[REQ-UIP-EX-0] A release-quality reproducible example shall pin an
open-source dependency or replace this block with an in-tree reference model.

The example classifies the NPU as application-owned and outside the OCAH
trusted computing base. It receives no device roots or secret keys, originates
non-secure unprivileged transactions, and remains reset/bus-blocked until
trusted firmware has configured its IOMMU/firewall context and authorized
release. A product that makes the NPU part of its trusted computing base needs a
separate threat-model and verification argument; changing an AXI attribute is
not sufficient.

The reference NPU wrapper exposes:

[cols="25%,18%,57%",options="header"]
|===
|Interface |Role |Integration

|`s_axil_*`
|32-bit AXI4-Lite subordinate
|[REQ-UIP-EX-1] Connect to the application CSR fabric through a 4 KiB aperture. Rebase the
fabric address to a zero-based offset, even though the current NPU register
decoder consumes only address bits `[11:0]`.

|`m_axi_*`
|64-bit AXI4 manager
|[REQ-UIP-EX-2] Connect through a trusted IOMMU/firewall ingress. Zero-extend
`m_axi_awaddr_o[31:0]` and `m_axi_araddr_o[31:0]` on a wider fabric, assign a
non-spoofable stream ID, and constrain all untranslated addresses below 4 GiB.
The adapter supplies `AxPROT=3'b010` because the NPU wrapper has no protection
outputs.

|`intr_done_o`, `intr_error_o`
|Retained level interrupts
|[REQ-UIP-EX-3] Route to separate application interrupt sources. Optionally route the error
level to an assigned SMU `ext_interrupts_i` bit for SMC fault handling; a fatal
security violation from the trusted ingress shall not depend on the NPU's own
interrupt.

|`clk_i`, `rst_ni`
|Single NPU clock and asynchronous active-low reset
|[REQ-UIP-EX-4] Use an adopter clock/reset domain. Before the adapter input, condition
`rst_ni` to assert asynchronously and deassert synchronously to `clk_i`. Meet
the implementation technology's minimum reset pulse width; the NPU architecture
does not prescribe a clock-cycle count. The NPU contains no internal CDC.

|`security_release_i`
|Trusted release into the example adapter
|[REQ-UIP-EX-5] Keep low until authentication and containment setup succeed. Before the
adapter input, synchronize its rising edge to `clk_i`; a falling edge may
asynchronously force the NPU back into reset. This signal does not replace the
external DMA firewall.
|===

The example adapter combines `rst_ni` and `security_release_i` with a
combinational AND gate. It contains no synchronizer: the caller is responsible
for presenting both rising edges synchronously to `clk_i` so the combined NPU
reset deasserts synchronously.

The `security_release_i` signal in the example adapter is an active-high
persistent level. It holds the NPU in reset while low; a rising edge deasserts
reset and a falling edge re-asserts it. The adapter contains no synchronizer:
the caller is responsible for synchronizing the rising edge to `clk_i` before
asserting. A falling edge may be asynchronous and will immediately re-assert
reset.

The software-visible counterpart is `platform_npu_security_release_confirmed()`,
which the adopter shall implement as a read of a firmware-written,
application-read-only status word. Trusted SEP or SMC firmware writes this word
as part of the authenticated release sequence and application software shall not
be able to manufacture or overwrite it. The hardware `security_release_i` and
the software `platform_npu_security_release_confirmed()` shall share a common
source: the same firmware release step that asserts `security_release_i` shall
also write the software-readable status word, so the two signals are coherent.

[REQ-UIP-EX-6] The integrator shall implement
`platform_npu_security_release_confirmed()` as a read of a firmware-written
application-read-only status word.
[REQ-UIP-EX-7] The hardware `security_release_i` and the software
release-confirmed indication shall be written by the same firmware release step.
[REQ-UIP-EX-8] `security_release_i` shall remain asserted for the lifetime of
the NPU operating session; de-assertion shall re-assert reset and the software
release indication shall be cleared atomically or before `security_release_i`
de-asserts.
[REQ-UIP-EX-9] The integrator shall ensure that every AXI transaction to the NPU CSR aperture
while `npu_rst_ni` is asserted receives a complete, bounded error response. Specifically:

* One accepted AR shall produce exactly one R response with `RRESP = SLVERR` or `RRESP = DECERR`.
  Response latency is measured from the AR handshake to assertion of RVALID and does not include
  the manager's RREADY de-assertion time.
* One accepted AW combined with its accepted W (collected in either legal order) shall produce
  exactly one B response with `BRESP = SLVERR` or `BRESP = DECERR`. A subordinate shall not
  issue B after accepting only AW if W has not yet arrived. Response latency is measured from
  the later of the AW and W handshakes to assertion of BVALID.
* If NPU reset asserts after only one half of a write handshake has completed, the integration
  shall use one of two designs: (a) a boundary element outside `npu_rst_ni` that remains
  operational while the NPU resets, accepts the missing AW or W channel, and returns B
  independently of the NPU state; or (b) a coherent AXI interface reset that legally discards
  the partial transaction at both ends. The boundary shall not delay assertion of NPU reset
  waiting for the missing AXI channel; security reset shall be immediate.
* The maximum response latency from the defining handshake to RVALID or BVALID assertion shall
  be defined as a platform-contract parameter and enforced; an unbounded wait is not permitted.

[REQ-UIP-EX-10] The NPU's mutable executable/configuration surface shall be
established for the selected product configuration.
[REQ-UIP-EX-11] If it loads microcode or other executable state, the integrator
shall authenticate it and enforce a minimum security version before release.
[REQ-UIP-EX-12] If descriptors or model metadata influence a security decision,
the integrator shall authenticate those items under the corresponding policy.
Ordinary application tensors can remain runtime data, protected by the
IOMMU/firewall rather than measured boot.

The complete adapter is in
`doc/integrator/examples/npu/ocah_npu_fabric_adapter.sv`. The significant
address connection is:

[source,systemverilog]
----
logic [31:0] npu_dma_awaddr;
logic [31:0] npu_dma_araddr;

// Sized casts zero-extend these unsigned 32-bit addresses.
assign m_axi_awaddr_o = FabricAddrWidth'(npu_dma_awaddr);
assign m_axi_araddr_o = FabricAddrWidth'(npu_dma_araddr);

// The external wrapper supplies no AxPROT; use least privilege at this ingress.
assign m_axi_awprot_o = 3'b010; // data, non-secure, unprivileged
assign m_axi_arprot_o = 3'b010;
----

The example allocation in `npu_platform.h` is illustrative, not an OCAH fixed
map:

[cols="30%,25%,45%",options="header"]
|===
|Resource |Example assignment |Requirement

|NPU CSRs |`0x3000_0000`--`0x3000_0fff` |4 KiB aligned application CSR aperture
|DMA buffer memory |`0x4000_0000`--`0x4007_ffff` |Uncached 512 KiB range below
4 GiB; the IOMMU/firewall permits this range and rejects adjacent addresses
|Done interrupt |Application IRQ 42 |Retained level; W1C at NPU `INTR_STATE[0]`
|Error interrupt |Application IRQ 43 |Retained level; W1C at NPU `INTR_STATE[1]`

[REQ-UIP-EX-13] The platform integration shall review and either replace or explicitly adopt the
example address assignments. The integration shall establish a correct DMA address contract that
distinguishes the following address domains and mapping state, even when their numeric values
happen to coincide:

* the CPU virtual address used by software to access the buffer;
* the backing physical pages to which that virtual address resolves;
* the device-visible DMA address programmed into `NPU_DMA_EXT_BASE` (an IOVA when an IOMMU
  translates device transactions, or a physical address in identity-mapped systems); and
* for dynamic IOMMU mappings, a platform-specific mapping token (a DMA address, mapping handle,
  or equivalent opaque record, depending on the OS or firmware API) that the platform shall keep
  valid for the entire duration of the DMA operation. A static bare-metal platform with no
  runtime IOMMU mapping may substitute a persistent platform configuration record that serves
  the same role.

When an IOMMU is present, the mapping shall ensure the device-visible DMA address resolves to
the exact same byte range within the same backing physical pages as the CPU virtual address,
with transfer direction and permissions that are no more permissive than the operation requires.

NOTE: The example `npu_smoke.c` passes the same `buffer` value to
`platform_dma_prepare()` (CPU-side cache maintenance) and to
`npu_write(NPU_DMA_EXT_BASE, (uint32_t)buffer)` (device DMA register). This is
only valid for an identity-mapped bare-metal system where the CPU virtual address,
backing physical address, and device-visible DMA address are numerically equal.
On a system with an IOMMU these are distinct address domains. REQ-UIP-EX-13
therefore requires production integrations to treat the CPU virtual address and
device-visible DMA address as separate interface parameters and to use the
platform mapping mechanism to establish that they resolve to the exact same byte
range within the same backing physical pages where an IOMMU is present.

=== Polling smoke path

[REQ-UIP-EX-14] The integrator shall run the example only after trusted firmware
reports successful authentication, containment setup, policy lock, and NPU
release.
[REQ-UIP-EX-15] The application shall not be able to manufacture that
indication. The example `npu_smoke.c` accepts a valid NPU descriptor supplied
by the test application. It clears stale state, programs the 32-bit DMA base,
queues the descriptor, starts the NPU, and polls `STATUS.done` / `STATUS.error`
with a bounded timeout. The example's `timeout` values count polling-loop
iterations, not units of elapsed time.
[REQ-UIP-EX-16] The integrator shall replace `timeout` values with a platform
timer when the integration requires a wall-clock deadline.
Passing the test requires:

* successful CSR read and write transactions;
* DMA reads and writes only inside the assigned buffer range;
* a completed descriptor before timeout;
* no AXI `SLVERR` or `DECERR`; and
* the expected output data after the required cache maintenance.

Security negative tests shall also prove the following.
[REQ-UIP-EX-17] The integrator shall verify that the NPU remains reset or bus-blocked after a failed authentication or policy setup.
[REQ-UIP-EX-18] The integrator shall verify that DMA immediately below and above the permitted range is rejected and reported.
[REQ-UIP-EX-19] The integrator shall verify that the NPU cannot select a secure/privileged attribute or another stream ID.
[REQ-UIP-EX-20] The integrator shall verify that application software cannot rewrite locked firewall policy.
[REQ-UIP-EX-21] The integrator shall verify that production lifecycle/debug policy prevents unauthorized register, JTAG, and scan access.

=== Interrupt smoke path

[REQ-UIP-EX-22] Before enabling the CPU interrupt, the integrator shall clear
NPU `INTR_STATE` with a write-one-to-clear value and install the handler. The
handler records the state and clears the asserted bits.
[REQ-UIP-EX-23] The test shall retain a timeout source independent of the NPU
interrupt so a missing interrupt cannot sleep forever.

Exercise both the real completion path and `INTR_TEST`: the former verifies
work-to-interrupt integration, while the latter isolates interrupt routing from
the compute and DMA paths.
[REQ-UIP-EX-24] The integrator shall not count an `INTR_TEST` result as proof
of DMA or descriptor execution.
