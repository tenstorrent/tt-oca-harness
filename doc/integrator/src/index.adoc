[[smu-top-level-integration]]
== SMU Top-Level Integration

The System Management Unit (SMU) comprises three peer subsystems: the System
Management Controller (SMC), the Debug & Test Ports (DTP), and the Security
Processor (SEP). The subsections below describe each subsystem's interfaces
independently, followed by the <<smu-composition,SMU Composition>> section that
explains how they are wired together inside the SMU and how to select between the
`smu.sv` logic-level core and the `smu_wrapper.sv` reference integration.

[[address-map-integration]]
=== Address Map Integration

The OCAH address map has three levels, and the assignment contract splits across
the integrator, SEP firmware, and SMC firmware. Assign and program them from this
section; the deeper subsystem and crossbar sections referenced below give the
per-block detail.

* *Chiplet envelope (integrator).* The SoC/chiplet address map assigns each
  subsystem a global base and reserved size, and the adopter's fabric decoder
  routes those ranges to the SMU. The SMU crossbar preserves offsets and does not
  constrain envelope size, so the integrator owns non-overlap and containment at
  the SoC level.
* *SEP and SMC chiplet apertures (firmware).* Each subsystem exposes a
  chiplet-visible aperture whose base and size are programmable at runtime.
  Inbound transactions to an aperture are remapped global-to-local before they
  reach the subsystem.
* *Local-alias views (fixed in RTL).* Internally each subsystem addresses its
  own resources through a fixed local map: the SMC at `0xC000_0000` (see
  <<smc-address-map-integration>>), the SEP through its own local map. These are
  RTL-fixed and not integrator-assigned.

.Address-map assignment contract
[width="100%",cols="26%,20%,54%",options="header"]
|=======================================================================
|Level |Owner |Assigned / programmed by
|Chiplet envelope |Integrator |SoC/chiplet address map + adopter fabric decode
|SEP chiplet aperture |SEP firmware |`SEP_GLOBAL_BASE_ADDR` / `SEP_REGION_SIZE`
(the `sep_cpu_ctrl` CSRs)
|SMC chiplet aperture |SMC firmware |`GLOBAL_BASE` / `REGION_SIZE` (the SMC CPU
Control CSRs at `0xC001_0000`)
|SEP / SMC local view |Fixed (RTL) |Offsets within each subsystem's local map
(SMC local base `0xC000_0000`)
|=======================================================================

Programming order and constraints: firmware programs the SEP and SMC aperture
CSRs during early boot, *before any cross-subsystem AXI traffic is issued*, and
must keep the two apertures non-overlapping and inside the chiplet envelope the
integrator assigned. The full runtime crossbar behaviour and the exact CSR
plumbing are in <<smu-firmware-programming-order>> under <<smu-composition>>.

[[smc-integration]]
=== System Management Controller (SMC) Integration

The System Management Controller (SMC) is a subsystem responsible for power
management, clock control, reset sequencing, and peripheral interface
coordination. The `smc.sv` module exposes logic-level interfaces; all
technology-specific components (PLLs, PVT sensors, eFuses, memory macros,
GPIO padrings) are instantiated externally by the adopter. See the
<<smu-module-variants,SMU Module Variants>> section for how the reference
wrappers demonstrate this integration.

For detailed architectural documentation about the SMC internal design, refer to
`hw/sys/smc/doc/`. The public integration examples are
`hw/top/smc_wrapper.sv` and `hw/top/smc_ip_integration.sv`.

==== Clock and Reset

The SMC requires three external clock inputs: `clk_smc_i` (primary system clock
driving the CPU cluster, fabric, and peripherals), `clk_periph_i` (peripheral clock
driving the peripherals), and `clk_ref_i` (reference
clock for timing-sensitive operations). All must be generated externally by the
adopter's PLL infrastructure; the SMC provides AXI-Lite control outputs for PLL
configuration (see <<smc-peripheral-connections>>). The peripheral clock is used
to drive the I3C interface, I2C interface, UART interface, and AVSBus interface.

Assert `powergood_i` after power-up sequence completion. Deassert `rst_cold_ni` after the power-up sequence completion.

The SMC generates AASD (async-assert / sync-deassert) reset outputs: `rst_primary_smc_clk_no` for the
main clock domain, `rst_primary_periph_clk_no` for the peripheral clock domain, and `rst_primary_ref_clk_no` for the reference clock domain.
These ensure clean reset release without metastability across the system
hierarchy.

Optional reset override inputs (`rst_cold_override_ni`, `rst_cool_override_ni`,
`rst_core_override_ni`) allow external control of specific reset domains for
test and debug scenarios. Most integrations leave these override enables
deasserted; the DTP drives them through JTAG IC_RESET controls when enabled
(see <<smc-dtp-interconnection>>).

[[smc-address-map-integration]]
==== Address Map and Aperture

The SMC has a chiplet-visible aperture and an internal local address
view. Internally, the SMC uses a fixed local base address of
`0xC000_0000` and a fixed local window size of 16 MiB. SMC-local
addresses (registers, memories, remapped regions) are defined as offsets
from that base. The chiplet-visible aperture is adopter-defined: the
chiplet or SoC address map assigns the global base and size that
external masters can use to reach SMC through the SMU crossbar.

When integrating the SMC into a chiplet or SoC, the adopter assigns a
system base address and reserved size for the SMC window. The system
base (e.g. `0x0800_0000` in a chiplet address map) may be different from
the SMC-local base `0xC000_0000`. Firmware programs the SMC
`GLOBAL_BASE` / `REGION_SIZE` CSRs during early boot to match that
assignment. The adopter's fabric or address decoder must route the
reserved system range to the SMC block so that offsets are preserved:
system base + offset maps to SMC-local `0xC000_0000` + offset.

.Address Base Mapping
[width="100%",cols="30%,30%,40%",options="header"]
|=======================================================================
|View |Base Address |Description
|SMC-local (internal) |`0xC000_0000` |Local alias address (fixed).
Used by SMC CPU, firmware, and fabric.
|System (adopter) |Adopter-defined |Base of the chiplet/SoC aperture
assigned to SMC.
|=======================================================================

The SMC fabric uses three registers in the CPU Control block
(`0xC001_0000`) to distinguish local from remote addresses:

* `LOCAL_BASE` (read-only, fixed at `0xC000_0000`): The local alias
  base. Together with `REGION_SIZE`, this is the address space the SMC
  CPU and internal fabric use to access SMC resources.
* `GLOBAL_BASE` (read-write, defaults to `0x4000_0000`): The
  system-level base address. Firmware must program this during early boot
  to match the adopter's system address assignment, enabling the SMC to
  issue outbound transactions using global system addresses.
* `REGION_SIZE` (read-write, resets to `0x0100_0000` / 16 MiB): The size
  of both the local alias window and the global aperture. It sizes the
  SMC input fabric's local/global split as well as SMU-level routing and
  SEP-to-SMC decode. Firmware must not program it to zero, and must keep
  `LOCAL_BASE + REGION_SIZE` inside the 32-bit SMC-local address space.

For full details on alias remapping and outbound routing, see the SMC
Fabric documentation (`hw/sys/smc/doc/fabric.adoc`).

For a detailed breakdown of all components within the SMC local map,
refer to the SMC Memory Map documentation (`hw/sys/smc/doc/memmap.adoc`).

==== AXI Interface Configuration

The SMC provides three distinct AXI interface groups serving different access
paths. The `sys_axi_in` interface accepts requests from external system masters
requiring access to SMC-managed resources. This interface uses a 56-bit address
space with 64-bit data width and 6-bit transaction IDs. Connect this interface
to your system fabric for normal operational access from application processors
or DMA controllers.

The `sep_axi_in` interface provides dedicated access from the Security Processor
(SEP) subsystem. This interface shares the same sizing parameters as the system
input but operates independently to maintain security domain separation. Use
this interface only when integrating alongside the SEP subsystem. The interface
may remain unconnected if your integration does not include SEP.

The `output_axi` interface carries filtered and remapped requests from the SMC
to external system resources. This interface uses an 8-bit transaction ID field
to accommodate merged traffic from multiple input paths. Connect this interface
to your system interconnect to allow SMC components access to external memory
and peripherals. The testbench shows example connections using AXI VIP
components that can be replaced with your system fabric.

The `jtag_axi_in` interface provides debug access through JTAG mechanisms. This
interface uses reduced 2-bit transaction IDs and connects to your JTAG debug
infrastructure. The testbench demonstrates typical debug access patterns through
this interface.

==== GPIO Pad Integration

GPIO pad integration requires careful attention to function assignment and pull
requirements. The GPIO table below lists each signal, bump location, function,
recommended pull, and integration notes. Default input/output direction is
defined by `smc_padring_pkg::DefaultDirectionMap`, not by the table.

The public `hw/top/smc_wrapper.sv` and `hw/top/smc_ip_integration.sv` examples
show the pad connections. For bidirectional pins, implement proper tri-state
buffers controlled by the `gpio_out_en_o` signals. Connect multiplexed UART,
I2C, I3C, and SPI pins to external devices according to the function assignments
in the GPIO table.

Configuration straps are captured separately from the GPIO table. Establish
them before cold reset deassertion and keep them stable during capture. The
generated reset-unit `STRAPS_LO` and `STRAPS_HI` register descriptions define
the decoded bit assignments, including `BYPASS_SRAM_REPAIR` at
`STRAPS_LO[13]` and `TEST_EN` at `STRAPS_LO[14]`.

[[smc-peripheral-connections]]
==== Peripheral Interface Connections

The SMC exposes logic-level interfaces to several technology-specific
subsystem components that the adopter instantiates externally. The
subsections below describe each connection in turn.

[[smc-external-connection]]
===== Adopter Peripheral Window

The `smc_external_req_o` and `smc_external_resp_i` signals form a 32-bit
AXI-Lite interface to the adopter's own peripheral register maps. Any
technology- or product-specific block that SMC firmware needs to reach sits
behind this window rather than on a dedicated per-peripheral port.

The window is the recommended home for the control/status registers of logic
that the SMC must configure or monitor but that the SMC itself does not
implement -- padring configuration logic, clock generation, on-die sensors,
memory-technology SHIMs, and similar adopter-owned blocks are typical examples.
For example, runtime reconfiguration of pin directions, pull settings, and peripheral
multiplexing is expected to be reachable here. The SMC decodes the aperture and
forwards the transaction; what lives behind it is entirely adopter-defined.

The window is split into a mandatory region, whose contents and placement the
SMC memory map fixes and every integration must implement, and a supplementary
region for anything else the adopter chooses to expose. For placement and the
full register layout, refer to the SMC Memory Map documentation
(`hw/smc/doc/memmap.adoc`).

[[smc-efuse-connection]]
===== eFuse Interface

The eFuse interface consists of two parts:

* `efuse_bank_ctrl` -- a 32-bit AXI-Lite interface used to access the SHIM
control CSRs (for example, foundry-specific bank timing such as the
initialization delay before sensing can begin).
* `efuse_shim_command` -- the custom fuse command interface used to issue
read, program, and program/read-back operations to the eFuse bank.

*Adopter responsibility.* The `efuse_shim_command` interface is intentionally
generic and technology-neutral. The adopter must implement an Interface SHIM
that converts these generic commands into the hardware signals required by
their OTP macro. The conversion is driven by the adopter's own read and
program state machines inside the SHIM; OCAH only defines the command/response
contract, not the macro-side signaling.

The command and response payloads are exchanged as packed structs:

[source,sourceCode,systemverilog]
----
// Controller -> SHIM
typedef struct packed {
    addr_t                address;             // Target address (in bits)
    logic                 program_data;        // Data to program (when programming)
    access_length_words_t access_length_words; // Number of WORD_WIDTH words to access
    command_t             command;             // READ / PROGRAM / PROGRAM_READ_BACK
    logic                 valid;               // Request valid
} fuse_command_req_t;

// SHIM -> Controller
typedef struct packed {
    data_t data;   // Read data (one WORD_WIDTH word)
    logic  status; // Operation status (0 = OK, 1 = error)
    logic  valid;  // Response valid (qualifies `data` for one cycle)
} fuse_command_resp_t;
----

*Fuse sensing protocol.* During automatic sensing the controller issues a
single read with `access_length_words` set to the entire bank (all
`NUM_WORDS` words). The SHIM is expected to stream the bank back one
`WORD_WIDTH` word at a time: for each OTP access it drives the read `data`
onto `fuse_command_resp_o.data` and asserts `valid` for *exactly one cycle*.
The controller consumes one word per cycle that `valid` is high, advancing to
the next eFuse word on each assertion.

[WARNING]
====
`valid` must be asserted for only a single cycle per returned word. If the
SHIM holds `valid` high for two cycles, the controller will sample the same
`data` value a second time and count it as the data for the *next* eFuse word,
shifting all subsequent words and corrupting the sensed shadow contents. The
adopter's SHIM FSM is responsible for producing a clean one-cycle `valid`
strobe per `WORD_WIDTH` access.
====

The `shadow_regs_o` output provides read-only access to the sensed fuse
values. During bring-up the SMC automatically senses the fuse contents and
propagates them through the shadow registers; the `fuse_sense_done_o` signal
indicates completion of this sensing operation.

==== Memory Subsystem Integration

The SMC includes an embedded RISC-V CPU cluster with associated memory
interfaces. The `rom_intf_req_o` and `rom_intf_rsp_i` signals connect to boot
ROM containing the SMC firmware. The ROM must be populated with valid firmware
images before initiating the boot sequence.

Scratch RAM interfaces (`scratch_ram_intf_req_o` and `scratch_ram_intf_rsp_i`)
connect to 32 independent RAM banks totaling the scratchpad memory space. Cache
memory interfaces for L1 instruction and data caches (`l1_icache_*` and
`l1_dcache_*`) connect to tag and data RAM banks as specified in the port table.

The `disable_sram_auto_init_i` input controls automatic memory initialization
behavior. When deasserted, the SMC automatically zeroes all SRAM contents during
bring-up. The `init_mem_done_o` output indicates completion of this
initialization sequence. The `SRAM_AUTO_ZERO_DISABLE` strap
(`STRAPS_LO[26]`) can
disable this automatic zeroing behavior if your integration requires preserved
SRAM contents across resets.

==== Memory Repair Integration

The SMC implements Built-In Redundancy Analysis (BIRA) memory repair to address
manufacturing defects in SRAM arrays. Repair uses redundant memory elements
configured with data stored in eFuse memory, replacing defective cells detected
during manufacturing test.

Memory repair executes automatically during boot after eFuse sensing completes
and before MBIST operations. The process must complete successfully before the
CPU cluster can safely access SRAM arrays. Repair is required on every cold
reset but can be bypassed during Function Level Reset (FLR) operations for
faster recovery.

**Control Signals:**

* `fuse_sense_done_o`: eFuse controller output indicating fuse sensing
completion.
  External DFT logic monitors this signal to trigger repair operations.

* `skip_mem_repair_o`: Reset unit output indicating repair should be bypassed. Asserts
  during FLR operations or when the `BYPASS_SRAM_REPAIR` strap is set. When
  asserted, external repair logic should skip operations and immediately assert
  completion status.

* `ext_boot_seq_done_i`: External signal indicating the external boot sequence (memory
  repair and shadow register override) is complete. Held low to pause reset release until
  the external agent gives the go-ahead; required before the system can continue its boot
  sequence

**Repair Data:**

Repair data is stored in the eFuse BIRA shadow register as a 16-kilobit
`repair_data` field. The eFuse controller reads this data during fuse sensing
and makes it available through shadow registers. The external memory repair
controller must read repair data from `shadow_regs_o` and apply it to SRAM
arrays according to your memory architecture.

**Status Monitoring:**

Repair completion and success are reported through
`DFX_CTRL_STATUS.STATUS_SMU` at `0xC000_B800`. The `mem_repair_done` bit
indicates completion regardless of success, while `mem_repair_success` indicates
successful repair. Both bits are set by the external repair controller. The SMC
ROM firmware monitors these bits during initialization to verify repair
completion.

**Bypass Configuration:**

The `BYPASS_SRAM_REPAIR` configuration strap (`STRAPS_LO[13]`) bypasses
repair logic when asserted high, causing `skip_mem_repair_o` to assert. Use
bypass mode only when SRAM arrays are guaranteed defect-free, such as during
development or with known-good components.

**Integration Requirements:**

Provide an external memory repair controller that monitors `fuse_sense_done_o`
to initiate repair, respects `skip_mem_repair_o` for bypass control, reads
repair data from eFuse shadow registers, applies repair configuration to SRAM
arrays, asserts ext_boot_seq_done_i and updates DFT Control Status registers
with completion status. The controller operates independently of the SMC core
and must complete before the CPU cluster accesses SRAM. The testbench demonstrates
example integration patterns adaptable to your DFT infrastructure.

For direct access to the eFuse besides from the shim, i.e. from a DFT fuse controller,
adopters must ensure the integrated logic will not interfere with accesses from the
OCAH's efuse interface.

During FLR operations, repair is automatically bypassed via `skip_mem_repair_o`
to enable rapid reset sequences. Normal cold reset sequences always execute
repair unless explicitly bypassed via strap configuration.

==== Telemetry and Debug Integration

For system-level debug and telemetry, the SMC implements ATB (Advanced Trace Bus) receiver
interfaces. The telemetry interface group (`telemetry_atdata_i`, `telemetry_atid_i`,
`telemetry_atvalid_i`, `telemetry_atready_o`) operates in a dedicated `clk_telemetry_i`
clock domain with separate `rst_telemetry_ni` reset. Connect these signals to ATB trace
sources for debug data collection.

The `ext_debug_bus_i` provides a 512-bit wide debug observation bus for internal signal
monitoring. The cross-trigger interface (`xtrigger_pads_i`, `xtrigger_pads_o`, `xtrigger_ss_i`,
`xtrigger_ss_o`) enables coordinated debug triggering across multiple subsystems. The
`halt_clock_global_i` input array accepts clock halt requests from external debug agents.

Trace memory interfaces (`trace_mem_req_o` and `trace_mem_resp_i`) connect to trace RAM
instances for storing captured debug data. The testbench shows example debug infrastructure
connections that can be adapted to your debug requirements.

==== Bring-Up Sequence

The recommended bring-up sequence begins with asserting `rst_cold_ni` while stabilizing
power supplies and clocks. Once all supplies reach nominal voltages, deassert `rst_cold_ni`
to initiate the SMC boot sequence. The SMC immediately begins fuse sensing to read configuration
values and security credentials.

Monitor the `fuse_sense_done_o` signal to detect completion of fuse sensing. Configuration
straps sampled during this phase determine boot modes and operational settings. After fuse
sensing completes, the SMC releases internal subsystem resets based on the programmed reset
sequencing configuration.

The CPU cluster begins firmware execution from the boot ROM after reset release. The firmware
performs additional initialization including peripheral configuration, memory testing (unless
disabled), and system health checks. The `init_mem_done_o` signal indicates completion of
memory initialization if automatic SRAM zeroing is enabled.

For Function Level Reset (FLR) support, assert `cfg_flr_pf_active_i` to trigger a warm reset
sequence. This isolates subsystems through `isolate_req_o` signals and performs controlled
reset propagation. Monitor `ss_reset_complete_i` signals to verify subsystem reset completion
before releasing isolation.

The testbench file demonstrates the complete power-on sequence including clock initialization,
reset timing, strap configuration, and peripheral bring-up. Reference this testbench when
implementing your integration-specific bring-up procedures.

[[dtp-integration]]
=== Debug & Test Ports (DTP) Integration

==== Configuration

The cross-trigger topology is fixed at elaboration by `dtp_pkg`, a committed
source file at `hw/sys/dtp/rtl/dtp_pkg.sv`. `DEFAULT_NUM_CTP`,
`DEFAULT_NUM_INT_CT`, and `DEFAULT_NUM_CLK_STOP_REQ` there set the
`XTRIG_NUM_CTP`, `XTRIG_NUM_INT_CT`, and `XTRIG_NUM_CLK_STOP_REQ` localparams of
`dtp`, so a different port count is applied by editing that package rather than
by overriding parameters at the instantiation. The remaining DTP parameters,
including `XTRIG_INT_CT_MODE` and every `JTAG_*` enable, are set at the
instantiation as shown below.

Include the DTP in your build using Bender target `dtp`, which pulls in the DTP
RTL together with the JTAG and cross-trigger IPs it instantiates. The legacy
filelist `hw/sys/dtp/rtl/config/dtp.f` covers only the JTAG portion of the
hierarchy and is not a complete DTP recipe.

==== Instantiation

[source,systemverilog]
----
dtp #(
    // JTAG Configuration
    .JTAG_BSR_ENABLE          (1'b1),
    .JTAG_TMP_ENABLE          (1'b1),
    .JTAG_SMC_DBG_ENABLE      (1'b1),
    .JTAG_SEP_DBG_ENABLE      (1'b1),
    .JTAG_IDCODE_MFR_ID       (11'h15A),
    .JTAG_IDCODE_PART_NUM     (16'h1234),
    .JTAG_IDCODE_SI_REV       (4'h1),
    // Cross Trigger Configuration
    .XTRIG_INT_CT_MODE        (10'b0000000000)
) u_dtp (
    .clk_i                    (clk),
    .rst_n_i                  (rst_n),
    .pwr_on_rst_ni            (pwr_on_rst_n),
    // JTAG, Boundary Scan, Cross Trigger interfaces...
);
----

==== Clock and Reset

* *TCK Domain*: JTAG logic operates on external Test Clock
* *System Clock* (`clk_i`): Cross trigger logic and JTAG2AXI bridges
* *System Reset* (`rst_n_i`): Resets cross trigger and AXI; does not affect TAP controller
* *Power-On Reset* (`pwr_on_rst_ni`): Asynchronous reset for JTAG state machine

==== Constraints

* JTAG interface: 10-50 MHz TCK frequency
* Cross trigger signals synchronized to system clock
* DTP remains active during clock stop for debug access
* External CTP signals require pad ring integration with ESD protection

==== STAP Scan Chain Topology

The DTP secondary scan path chains multiple STAPs on a single PTAP-managed scan
string. The fixed order on this string is: PTAP, I/O STAP (if
`JTAG_STAP_IO_ENABLE=1`), SMC debug STAP (if `JTAG_SMC_DBG_ENABLE=1`), SEP
debug STAP (if `SEP=1` in the SMU), extra STAP[N-1:0], and return to PTAP.

Both the SMC and SEP debug STAP host interfaces are internal to the SMU and are
not exported on the SMU boundary. The SMU wires the SMC debug STAP host outputs
to the SMC CPU/system JTAG ports (`smc_cpu_jtag_*`) when
`JTAG_SMC_DBG_ENABLE=1`; when disabled, the DTP bypasses this STAP in the
secondary scan chain and drives the internal host outputs low. The SEP debug
STAP connects to the SEP JTAG debug port when `SEP=1`; when `SEP=0`, the SMU
ties `sep_stap_tdo_to_dtp = 1'b0` to bypass the SEP STAP return path.

Each STAP host interface is gated by lifecycle feature controls, synchronized to
TCK inside the DTP. `feat_ctrl_i` is enable-polarity (1 = feature enabled), so a
STAP host interface is enabled only when all of its required enables are asserted
and is disabled when any one of them is deasserted.

[cols="<25%,<35%,<40%",options="header"]
|===

[[sep-integration]]
=== Security Processor (SEP) Integration

The Security Processor (SEP) is the Root of Trust for the chiplet, providing
a physically isolated execution environment for security-critical services
such as secure boot, lifecycle control, device attestation, cryptographic
acceleration, and key management. This section provides practical integration
procedures for adopters integrating the SEP as part of the SMU or as a
standalone out-of-context IP.

For detailed architectural documentation about the SEP internal design, refer to
the dedicated SEP documentation located in `hw/sys/sep/doc/`. The SEP hardware
overview and interconnect fabric are described in
`hw/sys/sep/doc/overview.adoc` and `hw/sys/sep/doc/fabric.adoc` respectively.

==== Module Overview

The `sep.sv` module provides the complete SEP functionality with logic-level
interfaces. Technology-specific components -- SRAM, ROM, and eFuse shims -- are
instantiated by the adopter outside SEP, following the same vendor-neutral
philosophy used for the SMC.

Separately, SEP exposes interfaces for supplementary peripherals an adopter may
add on rather than substitute: an external TRNG and an additional SPI
controller. These are not technology-specific -- SEP contains its own entropy
source and SPI host -- so the interfaces exist to supplement what SEP already
provides, and may be left unused.

When integrated inside the SMU, the SEP's external interfaces are passed through
the SMU boundary with a `sep_` prefix.

==== Clock and Reset Requirements

The SEP requires two clock inputs. Connect `clk_i` to the primary system clock
driving all SEP internal logic. Connect `clk_wdt_i` to a 200 kHz clock source
for the watchdog timer; this clock must be independent of the system clock so
that the WDT can detect system clock failures.

The primary reset `rst_ni` follows the standard active-low, asynchronous
assertion / synchronous deassertion convention. The `dbg_rstb_i` input provides
a separate reset for the EL2 CPU debug module. The `wdt_rst_ni` input receives
the watchdog reset generated by the SMC reset unit. The SEP outputs
`wdt_timer_rst_req_o` when the WDT triggers a reset request.

==== AXI Interfaces

The SEP connects to the system through three AXI paths. The `smn_outbound_axi`
master interface allows SEP firmware to access system resources outside the SEP
domain, such as SMC registers or external memory. The `smn_inbound_axi` slave
interface accepts requests from system masters requiring access to SEP-managed
resources. The `sep_ext_to_smc_axi` output provides a dedicated AXI path for
SEP-to-SMC transactions, connecting to the SMC's `sep_axi_in` port.

An additional AXI extension port (`axi_extension_axi`) enables adopters to
attach custom peripherals to the SEP interconnect fabric without modifying the
SEP core. When unused, tie the response input to return DECERR.

==== Memory Interfaces

All SEP memory macros are instantiated externally and connected through
dedicated request/response interfaces. The `sep_cpu_tcm` interface provides
tightly-coupled memory (ICCM and DCCM) for the VeeR EL2 CPU. The `sep_sram`
interface connects scratch SRAM used for firmware data. The `sep_boot_rom`
interface provides the BL0 ROM containing the first-stage bootloader.

The crypto subsystem requires additional memory interfaces.
`sep_crypto_pka_imem_sram` and `sep_crypto_pka_dmem_sram` connect to the OTBN
public key accelerator instruction and data memories respectively.
`km_rom_mem` and `km_sram_mem` connect to the Key Manager's dedicated ROM and
SRAM macros.

==== Cryptographic Subsystem Connections

The SEP includes an internal entropy source that requires a ring-oscillator
sample clock connected to `entropy_rosc_sample_clk_i`. This clock must be
asynchronous to `clk_i` and typically runs between 100 and 400 MHz.

For adopters providing an external TRNG, the `ext_trng_axil` AXI-Lite interface
connects to the external TRNG's control registers, while the `ext_trng_axis`
AXI-Stream interfaces carry entropy data. The `ext_trng_irq_i` input is routed
to the PIC; `ext_trng_alarm_i` is reserved for RAS.

==== eFuse and Lifecycle

The SEP accesses its own eFuse bank through the `efuse_bank_ctrl` AXI-Lite
interface and the `efuse_shim_command` custom interface, mirroring the pattern
used by the SMC. The SEP must wait for the SMC fuse sense to complete
(`smc_fuse_sense_done_i`) before initiating its own fuse operations, and it
signals completion through `sep_fuse_sense_done_o`.

The lifecycle controller outputs `lc_state_o` (differentially encoded),
`feat_ctrl_o` (feature control vector), `lc_sigint_err_o` (signal integrity
error), and `security_disable_o`. These outputs gate debug access through the
DTP and control feature availability across the chiplet. The `lcc_demote_state`
outputs report lifecycle demotion events to the SMC.

An OTP debug AXI-Lite port (`axil_sep_otp_jtag`) connects to the DTP for JTAG
access to SEP fuses. When SEP is disabled (`SEP=0` at the SMU level), the SMU
instantiates an AXI-Lite error slave on this path.

==== SPI Host Interface

The SEP provides a SPI host controller through the `sep_io_spi` interface,
supporting single and quad modes. The controller's own interrupt leaves the
module as the `irq` field of `sep_io_spi_req_o`, so no separate interrupt
output is needed.

The `spi_irq_i` input is a separate SPI interrupt request routed to the SEP
PIC. Adopters that replace or supplement the internal SPI host with an external
SPI controller connect that controller's interrupt here; adopters that use only
the internal controller may loop back the `irq` field of `sep_io_spi_req_o` or,
if a mux over multiple SPI sources is needed, drive the selected interrupt from
their own integration logic. Tie the input low when unused.

==== Bring-Up Considerations

The SEP boot sequence begins after the SMC completes fuse sensing and releases
the SEP reset. The SEP BL0 ROM firmware verifies the BL1 software image using
non-volatile public keys before transferring control. Feature controls derived
from secure boot authentication and lifecycle state govern what operations are
permitted after boot.

The `sep_straps_i` input provides configuration straps for SEP-specific
settings. The `rst_vec`, `jtag_id`, and `core_id` inputs must be tied to
appropriate constants in the top-level integration.

[[smu-composition]]
=== SMU Composition and Internal Wiring

The System Management Unit (SMU) combines the SMC, DTP, and optionally the
SEP into a unified subsystem. The interface descriptions in the preceding
sections apply directly when integrating the SMU, since the SMU inherits all
three subsystems' ports. This section covers the module variants available to
adopters, how the SMU wires its subsystems together internally, and what
additional configuration it exposes.

[[smu-module-variants]]
==== Module Variants and IP Integration

OCAH core modules (`smc.sv`, `sep.sv`, `dtp.sv`, and the composite `smu.sv`)
expose logic-level interfaces only. All technology-specific components -- PLLs,
PVT sensors, eFuse shims, memory macros, GPIO padrings, SPI controllers, and
external TRNG -- are instantiated outside the core modules by the adopter. This
separation keeps the OCAH deliverable technology-neutral.

The repository provides reference wrappers that demonstrate how to bridge the
gap between OCAH core interfaces and adopter-specific IP:

* `smu_wrapper.sv` wraps `smu.sv` with pad-level signal handling for clocks,
  resets, GPIO, eFuse, and JTAG interfaces. It internally instantiates
  `smc_ip_integration.sv` for SMC-related vendor IP and (when `SEP=1`)
  `sep_ip_integration.sv` for SEP-related vendor IP.
* `smc_wrapper.sv` provides an equivalent reference wrapping `smc.sv` alone,
  useful when integrating the SMC without the DTP/SEP subsystems.

Neither the wrappers nor the IP integration modules are part of the OCAH
deliverable; they exist as integration guides and for Tenstorrent internal
usage. Adopters must develop their own equivalents following the interface
patterns demonstrated in these modules. The interface contracts at the module
boundaries ensure technology substitution without modifying the verified OCAH
logic.

wrapper layer, and the IP integration modules.

===== IP Integration Modules

`smc_ip_integration.sv` demonstrates integration of SMC-side technology
components: PLL wrappers (generating `pll_cgm_clk_o` and `pll_awm_clk_o`),
PVT sensor interfaces, eFuse shims, GPIO padring logic, memory macros (ROM,
scratchpad RAM, cache tag and data arrays), and trace memory instances.

`sep_ip_integration.sv` demonstrates integration of SEP-side technology
components: SEP memory macros (TCM, scratch SRAM, boot ROM, OTBN IMEM/DMEM,
Key Manager ROM/SRAM), eFuse shim, external TRNG, and SPI controller selection.

===== Wrapper Clock and PLL Architecture

The `smu_wrapper.sv` (and `smc_wrapper.sv`) reference accepts `BP_REFCLK` at
the pad level and processes it through the integrated padring to produce internal
reference timing. A `pll_wrapper` module generates system clocks `pll_cgm_clk_o`
and `pll_awm_clk_o` from the padring-processed reference. The SMC controls this
PLL through the same AXI-Lite interface exposed by the core module. However, the
core receives its clocks through DFX inputs `pll_cgm_clk_dfx_i` and
`ref_clk_vdd_sys_dfx_i`, so the adopter must route PLL outputs through the clock
distribution network and feed them back through these DFX inputs.

==== Clock and Reset Architecture

Connect `clk_smu_i` to the primary system clock and `clk_ref_i` to a stable
reference source. The DTP operates on TCK for JTAG logic and on the system clock
for cross-trigger and AXI bridges. Reset sequencing follows the SMC flow; the
DTP JTAG state machine uses `pwr_on_rst_ni`, which the SMU connects to
`rst_cold_ni`. The SMU internally connects DTP debug paths to the SMC and
optionally instantiates the SEP when the `SEP` parameter is set to 1. The full
interconnection details are described in <<smc-dtp-interconnection>> and
<<sep-conditional-wiring>> below.

[[smu-axi-xbar-address-map]]
==== SMU AXI Crossbar Address Map

Inside the SMU, the `smu_axi_xbar` module routes traffic between three
AXI4 manager/subordinate pairs: the SEP outbound master (`sep_out`),
the SMC outbound master (`smc_out`), and the external SMU AXI input
(`ext_in` / `smu_axi_in`). The corresponding targets are the SEP and
SMC inbound subordinates, and the external SMU AXI output
(`ext_out` / `smu_axi_out`).

ifdef::backend-html5[]
Connectivity is described in
xref:ocah-docs:ROOT:architecture.adoc#smu-axi-crossbar[SMU AXI Crossbar];
the split between hardware-fixed behaviour and firmware-programmable apertures
is documented in
xref:ocah-docs:ROOT:architecture.adoc#ocah-memory-map[OCAH Memory Map].
endif::backend-html5[]
ifdef::backend-pdf[]
See the _SMU AXI Crossbar_ and _OCAH Memory Map_ sections of the Technical
Reference Manual for connectivity and the responsibility split between
hardware-fixed and firmware-programmable apertures.
endif::backend-pdf[]

The crossbar uses a *runtime* address map. Only the SEP and SMC
apertures are programmable at runtime; the `ext_out` rule is static:

* `sep_global_base_addr_i` / `sep_region_size_i` come from the
  `sep_cpu_ctrl` CSRs `SEP_GLOBAL_BASE_ADDR` / `SEP_REGION_SIZE`,
  exposed at both the `sep.sv` and `smu.sv` boundaries as
  `sep_global_base_addr_o` / `sep_region_size_o` (both 56-bit).
  `SEP_REGION_SIZE` is a 32-bit CSR field, zero-extended to 56-bit at
  the SEP system CSR; the xbar input takes only the lower 32 bits.
  `SEP_REGION_SIZE` defines the SEP global/chiplet aperture for SMU
  routing and SEP inbound global-to-local remap. It is distinct from the
  SEP CPU's architectural local-alias span. `SEP_REGION_SIZE` currently
  resets to `0x0100_0000` (16 MiB). Tied to `'0` at the `smu.sv`
  boundary when the `SEP` parameter is `0`.
* `smc_global_base_addr_i` / `smc_region_size_i` come from the SMC CPU
  control CSRs `GLOBAL_BASE` / `REGION_SIZE`, exposed at both the
  `smc.sv` and `smu.sv` boundaries as `smc_global_base_o` (56-bit) /
  `smc_region_size_o` (32-bit). `REGION_SIZE` resets to `0x0100_0000`
  (16 MiB).

SEP, SMC, and `smu_axi_xbar` all run on `clk_smu_i`, so these
quasi-static CSR fields need no clock-domain crossing. The crossbar's
address arithmetic is done on 57-bit widened sums; `ext_out` covers
`0x0000_8000_0000` up to the top of the 56-bit address space.

[[smu-firmware-programming-order]]
===== Firmware programming order

Firmware must program `SEP_GLOBAL_BASE_ADDR` / `SEP_REGION_SIZE` and
SMC `GLOBAL_BASE` / `REGION_SIZE` during early boot, *before any
cross-subsystem AXI traffic is issued*, and must ensure the two
apertures do not overlap and both fall within the chiplet-visible SMU
envelope assigned by the integrator. The SMU crossbar does not itself
constrain envelope size.

See xref:ocah-docs:ROOT:architecture.adoc#ocah-memory-map[OCAH Memory Map] for

address maps.
endif::backend-html5[]

`JTAG_IC_RESET_ENABLE` when no external overrides are required.

===== Cross Trigger Matrix Interface

[cols="<30%,<10%,<20%,<40%",options="header"]
|===
|Port |Direction |Width |SMU Connection

|`xtrig_ctm_src_req_o` |output |[XTRIG_NUM_INT_CT-1:0] |[1:0]: SMU internal (SMC), [9:2]: SMU external `xtrig_ctm_src_req_o[7:0]`
|`xtrig_ctm_src_ack_i` |input |[XTRIG_NUM_INT_CT-1:0] |[1:0]: Tie-off (SMC), [9:2]: SMU external `xtrig_ctm_src_ack_i[7:0]`
|`xtrig_ctm_dst_req_i` |input |[XTRIG_NUM_INT_CT-1:0] |[1:0]: SMC `xtrigger_ss_o[1:0]`, [9:2]: SMU external `xtrig_ctm_dst_req_i[7:0]`
|`xtrig_ctm_dst_ack_o` |output |[XTRIG_NUM_INT_CT-1:0] |[1:0]: Unused (SMC connection), [9:2]: SMU external `xtrig_ctm_dst_ack_o[7:0]`
|===

Internal cross trigger ports [1:0] are reserved for SMC (both bits of
`xtrigger_ss_o`). The SMU exposes ports [9:2] as external ports [7:0], so the
SMU `XTRIG_NUM_INT_CT` parameter is two less than DTP's (8 vs 10). The SMC uses
pulse-synchronization mode, so ack signals for ports [1:0] are unused:
`xtrig_ctm_src_ack_i[1:0]` should be tied to `2'b00` and
`xtrig_ctm_dst_ack_o[1:0]` are left unconnected. The usage of ack signals
depends on the `XTRIG_INT_CT_MODE` parameter: when a mode bit is 0 (pulse
synchronization), the corresponding ack is unused; when 1 (req/ack handshaking),
the ack must be connected to the cross trigger endpoint.

[[simulation-define]]
=== `SIMULATION`

`SIMULATION` selects the verification view of OCAH RTL. Set it on every

[cols="<40%,<60%",options="header"]

|Plusarg |Effect

|`+skip_fuse_sense`

|`+smc_shadow_reg_preload=<file>`,

other than Verilator (`+prim_lfsr_use_default_seed=1` pins it). Two runs of one
test are therefore not identical unless the simulator seed is fixed; record the
seed with any failure you intend to reproduce.

[[prim-cell-replacement]]
== Prim Cell Replacement and Don't-Touch Constraints

OCAH primitives (`prim_stdbuf`, `prim_and2`, `prim_clkgater`, the
`prim_flop_*sync*` family, and so on) ship as behavioral models with a
reference technology mapping. Adopters replace them with cells from their own
library.

Two rules govern those replacements. Both are the adopter's responsibility --
OCAH provides the instance names, but the names have no effect until the
adopter's synthesis and place-and-route flows constrain them.

[[prim-cell-replacement-naming]]
=== Naming Requirement

*Every library cell instantiated inside a replacement primitive must have
`d0nt_` in its instance name.*

The marker is deliberately misspelled with a zero. `dont_touch` is a reserved
keyword in several tools and a common substring in ordinary comments and signal
names; `d0nt_` occurs only where the protection is intended, so a name-based
match cannot pick up unrelated cells.

Clock-path cells take the extended prefix `d0nt_clk`, which selects the stricter
rule below. The reference mapping uses these names:

[cols="<25%,<20%,<55%",options="header"]
|===
|Instance name |Rule |Primitive

|`d0nt_clkgate`   |Don't touch |`prim_clkgater`
|`d0nt_clkbuf`    |Don't touch |`prim_clock_buf`
|`d0nt_clkinv`    |Don't touch |`prim_clock_inv`
|`d0nt_clkmux`    |Don't touch |`prim_clock_mux2`
|`d0nt_clknand`   |Don't touch |`prim_clock_nand2`
|`d0nt_clkxor`    |Don't touch |`prim_xor2`
|`d0nt_stdbuf`    |Size only   |`prim_stdbuf`
|`d0nt_stdinv`    |Size only   |`prim_flop_*sync_*` reset inverter
|`d0nt_an`        |Size only   |`prim_and2`
|`d0nt_ao222`     |Size only   |`prim_ao222`
|`d0nt_wrap_sync` |Size only   |`prim_flop_*sync_*` synchronizer flops
|===

Keep the same names when substituting your own cells. Adopters who rename must
apply the equivalent constraints to whatever names they use.

[[prim-cell-replacement-constraints]]
=== Constraint Requirement

*In synthesis, apply `set_size_only` to every cell matching `d0nt_`, then
`set_dont_touch` to every cell matching `d0nt_clk`. Every step after synthesis
needs `size_only` alone -- on all `d0nt_` cells, clock cells included.*

[source,tcl]
----
# Order matters: d0nt_clk* also matches d0nt_*, so the clock rule is applied
# second and overrides size-only for those cells.
set_size_only  [get_cells -hierarchical -filter "full_name =~ *d0nt_*"]
set_dont_touch [get_cells -hierarchical -filter "full_name =~ *d0nt_clk*"]
----

`size_only` keeps the instance in the netlist -- the tool may not delete, merge,
absorb, restructure, or buffer through it -- while still allowing it to be
swapped for another library cell of the same logic function, typically to change
drive strength or threshold-voltage flavor for timing, area, and EM closure.
That is the intent for every replacement cell: these primitives exist because
the structure matters, not because the logic function could not be inferred.
Synthesis will otherwise remove them -- an inverter pair that cancels,
redundant AND gates that always agree, a buffer driving a single load are all
dead weight to an optimizer.

Clock cells need the stronger `dont_touch` because that swap is exactly the
problem. Under `size_only` the tool treats the logic function as the contract
and every other property of the cell as free to change. On the clock path the
function is the least of the reasons the cell was chosen. Clock buffers,
inverters, muxes, and gaters are picked for electrical characteristics the
function does not capture -- matched rise and fall times above all, and with
them duty-cycle preservation, balanced input-to-output delay, and low delay
variation across PVT. A functionally identical cell pulled from the
general-purpose library guarantees none of that. The netlist still says
"inverter", functional simulation still passes, and the duty-cycle distortion
shows up only in silicon or in a timing run late enough to be expensive.

`dont_touch` removes the tool's discretion: the cell the designer selected is
the cell that reaches the netlist. Sizing and insertion-delay decisions on the
clock path belong to clock tree synthesis, which owns them explicitly, rather
than to a logic-optimization pass making a substitution it believes is free.

[[prim-cell-replacement-post-synthesis]]
==== After Synthesis

The `dont_touch` on `d0nt_clk*` is a synthesis-only constraint. Once synthesis
has handed off the netlist, release the clock cells to `size_only` and carry
that -- and nothing stronger -- through placement, clock tree synthesis,
routing, and optimization:

[source,tcl]
----
# Post-synthesis: uniform size_only, clock cells included.
set_dont_touch [get_cells -hierarchical -filter "full_name =~ *d0nt_clk*"] false
set_size_only  [get_cells -hierarchical -filter "full_name =~ *d0nt_*"]
----

The stricter rule exists to stop logic optimization from choosing the cell.
Downstream, clock cell sizing is CTS's job: it cannot balance skew or close
transition violations with the cells it needs to resize frozen, and freezing
them there buys nothing. Keeping `size_only` in place still prevents deletion,
merging, and restructuring for the rest of the flow.

Restrict the physical flow to the library's clock-cell list so a resize stays
inside the same clock cell family. Sizing a `CLKBUF_D4` up to a `CLKBUF_D8`
keeps the matched rise and fall behavior the cell was chosen for; substituting a
general-purpose buffer of equivalent drive does not.

Additional requirements:

* *Carry `size_only` through PnR.* The `dont_touch` is synthesis-only, but
  `size_only` is not. A cell protected in synthesis and left entirely
  unprotected downstream is not protected.
* *Verify the match is non-zero.* A typo in the filter, or a flow that renames
  instances before the constraint is read, silently protects nothing. Check the
  collection size and error out if it is empty.
* *Preserve the names.* Uniquification, flattening, and name mapping must not
  strip the `d0nt_` substring. If your flow renames instances, derive the
  collections before flattening and carry them forward.
* *Restore protection after ECOs.* Flows that relax preservation constraints for
  clock-tree or filler ECOs -- clearing `eco_honor_dont_touch`, for example --
  must restore `size_only` before any subsequent optimization pass.
* *Check the final netlist,* not just the post-synthesis one.

Flows other than Design Compiler and Fusion Compiler must apply the equivalent
`size_only` and `dont_touch` attributes to the same collections.

[[prim-cell-replacement-simulation]]
=== Simulation

These constraints have no functional effect and no simulation impact. All OCAH
simulation flows compile with `+define+NO_LIBCELL`, which selects the behavioral
model inside every primitive, so no library cell is ever elaborated by a
simulator.

Confirming that the protected cells survived is therefore a gate-level netlist
check. RTL simulation cannot detect their loss.

[[cdc-timing-constraints]]
== CDC Timing Constraints

OCAH ships synthesis constraints that bound every clock-domain crossing in the
SMC, SEP, DTP and SMU. This section explains what those constraints do, how they
are produced, and what an adopter has to change when integrating OCAH into their
own flow and cell library.

The collateral ships with the harness. Each block carries its own constraints in
`hw/sys/<block>/synth/`:

* `constraints.sdc` -- the block's full timing intent, including the clock
definitions and the asynchronous clock groups. It sources the two files below.
* `<block>_cdc_max_delay.tcl` -- generated-clock periods and any hand-written
overrides.
* `<block>_cdc_max_delay_generated.tcl` -- the per-instance calls.

The two pieces shared by every block live in `flows/synth/constraints/`:
`async_clock_groups.tcl` and `cdc_max_delay_procs.tcl`.

=== Why crossings are bounded rather than timed

A clock-domain crossing has no fixed phase relationship, so it cannot be timed
against a capture edge. Its correctness still depends on delay, though: every CDC
element assumes the data reaches the receiver within a bounded time.

OCAH therefore keeps the crossings visible to the tool and gives each one an
explicit upper bound, sized from the clock that captures it. This asserts no phase
relationship -- it states only how much delay the crossing tolerates while its CDC
element's guarantee still holds.

=== What is constrained

Every CDC element in each block is enumerated and given its own `set_max_delay`,
sized from the clock that actually captures it as read from the netlist. Muxed
domains resolve to several clocks; the tightest period wins.

The elements covered are `prim_sync2/3/4` and their reset and set variants, the
pulp `sync` shim, `prim_sync_reset`, `prim_sync3_pulse`, `prim_fifo_async`,
`avsbus_async_fifo`, `cdc_fifo_gray`, `axi_cdc`, `prim_reg_cdc`,
`prim_sync_reqack_data`, `prim_sync_data_autohs`, `cdc_2phase`, `dmi_wrapper` and
Rocket `AsyncQueue`.

The bound depends on what protects the crossing:

[options="header"]
|===
| Kind of path | Bound | Reason

| Synchronizer data input
| `0.5 * T_dst`
| Leaves half a destination period of settling margin before the capture edge the synchronizer relies on.

| Protocol-protected data
| `1.0 * T_dst`
| Conservative. The requirement is set by the pointer synchronizer's depth -- see below.

| Two-phase handshake nets
| `min(T_src, T_dst)`
| `cdc_2phase` runs the handshake in both directions, so the tighter domain governs. This is the module's own stated requirement.
|===

`T_dst` rather than `min(T_src, T_dst)` in the general case because the gating
synchronizer is clocked by the destination, so its settling window is `S * T_dst`
and `T_src` does not enter the guarantee. This makes slow-to-fast and fast-to-slow
equally safe.

==== Why protocol-protected data still needs a bound

The payload of a gray-pointer FIFO or a req/ack handshake never passes through a
synchronizer -- only the pointer or request does. So this is not a metastability
constraint, and it is reasonable to ask why such a path needs a bound at all, or
why a single blanket bound covering every crossing in the design would not be
enough.

Because the protocol guarantees *ordering*, not *arrival*. The read side will not
look at an entry until the write pointer has crossed, which takes `SYNC_STAGES`
destination cycles, where `SYNC_STAGES` is the depth of the pointer
synchronizer. Nothing in the protocol ensures the data physically arrived within 
that window; that is a timing property, and only a `max_delay` states it. Miss it 
and the consumer samples the entry's previous contents. There is no violation
report and no metastability event, just wrong data.

So the requirement is `data path < SYNC_STAGES * T_dst`. It is not a fixed number
of nanoseconds: it scales with the clock that captures the crossing, and the
destination periods within one design span an order of magnitude.

[options="header"]
|===
| Destination period | Guarantee at 3 stages

| 1 ns  | 3 ns
| 5 ns  | 15 ns
| 10 ns | 30 ns
|===

That is why the bound is applied per instance rather than as one global value. A
single blanket `max_delay` has to be chosen once for the whole design: loose
enough to be feasible on the slowest domains, it permits several times more delay
than a fast crossing's pointer scheme tolerates; tight enough for the fastest
domain, it over-constrains every slow crossing and burns effort closing paths
that were never at risk. Sizing each crossing from its own capturing clock is the
only bound that tracks the requirement.

The blanket default that the clock-group layer applies (see <<cdc-two-layers,The
two layers>>) is deliberately on the loose side, and for slow destination domains
it is already sufficient -- there the explicit per-instance constraint is
redundant. It is the fast crossings that need it.

`1.0 * T_dst` is therefore conservative by a factor of two to three. It is kept
simple deliberately, but if wide payloads such as AXI data will not close, raising
`cdc_data_delay` to `2.0 * T_dst` stays inside a three-stage guarantee with a
cycle to spare. An adopter whose synchronizer cells use a different depth should
recompute from their own `SYNC_STAGES` rather than inheriting this factor.

Enumeration and clock resolution run once, offline, against an elaborated design,
and their output is an explicit per-block file of constraint calls that is reviewed
and checked in. The flow itself does no discovery. This matters to an integrator
because those files are written against the OCAH hierarchy and OCAH's clock names.
If you instantiate a block as delivered, you do not need to regenerate or hand-edit
them: set `::cdc_hier_prefix` to where the block sits in your hierarchy, and
optionally `::cdc_clock_alias` to map OCAH clock names onto your own. Regeneration
is needed only when the block is reconfigured in a way that changes which CDC
elements exist, since no prefix can conjure constraints for elements the file never
listed (see <<cdc-integration-checklist,Integration checklist>> item 2).

[[cdc-two-layers]]
=== The two layers

The per-instance bounds take effect only on top of a correctly configured
clock-group layer. That layer decides whether the tool considers inter-domain
paths at all, so it must be established first; the per-instance exceptions then
refine it.

*Layer 1* is `set_async_clock_groups`, defined in
`flows/synth/constraints/async_clock_groups.tcl` and called from each block's
`constraints.sdc`. It declares the asynchronous groups *with `-allow_paths`* and
applies a loose 20 ns / -20 ns default to every inter-group clock pair.

[IMPORTANT]
====
`-allow_paths` is a prerequisite, not a refinement. In DC and PrimeTime exception
priority, `set_false_path` outranks `set_max_delay` regardless of which is more
specific, so a bare `set_clock_groups -asynchronous` silently masks *every*
per-instance constraint. There is no warning; the exceptions simply have no
effect.
====

The 20 ns default is what makes `-allow_paths` safe to enable. Once paths are
allowed, every crossing without a specific constraint would otherwise be timed
against a meaningless launch-capture relationship and fail. The default bounds
them loosely so that only deliberately tightened paths appear as real
requirements. It is emitted per ordered clock pair, never group-wide, because a
20 ns bound inside a group would mask genuine setup failures on synchronous paths.

*Layer 2* is the per-instance `set_max_delay` output of the three steps above, with
two deliberate carve-outs:

* *Paths from primary inputs revert to the default.* A synchronizer input
  reachable from a top-level port carries that port's `set_input_delay`, which is a
  budget figure rather than real logic and can alone exceed the tightened bound.
  Only the parent block sees both ends, so there is nothing to tighten at block
  level.
* *Same-clock instances are skipped.* A two-clock element wired to one clock is not
  a crossing, and applying `set_max_delay -ignore_clock_latency` there would
  replace a proper setup check with a flat budget that discards skew and
  uncertainty. These are emitted commented out. OCAH has five, where OpenTitan
  AES, KMAC and OTBN instantiate `prim_sync_reqack_data` on EDN and OTP interfaces
  that are separate domains upstream but share a clock in SEP.

=== What is covered

[options="header"]
|===
| Block | CDC elements constrained | Exceptions emitted

| SMC | 365 | 412
| SEP | 18 | 21
| DTP | 250 | 270
| SMU | 758 | 838
|===

SMU is a flat build containing the other three, so its instance paths carry
`u_smc/`, `gen_sep.u_sep/` and `u_dtp/` prefixes. It is not the sum of the parts:
DTP contributes 375 elements inside SMU against 250 standalone, because it
instantiates three JTAG2AXI bridges in the SMU configuration and two on its own.

[[cdc-integration-checklist]]
=== Integration checklist

Five things must change, three should be checked. None of them requires editing
per-instance data by hand; every change is either a one-line policy edit or a
regeneration.

==== 1. Repoint the constraints at the pin of the cell inside the prim wrapper

This is the most important change.

As shipped, the procs target the prim wrapper's own port, `prim_sync3/i_d`. That
port exists only as long as the wrapper survives as a hierarchical boundary, and a
prim cell is ordinary RTL: nothing stops synthesis from ungrouping it and
dissolving its ports.

[WARNING]
====
Do not rely on the wrapper port surviving. Anchor the constraint to the pin of the
cell instantiated *inside* the wrapper. When you swap in your own synchronizer,
that cell is a real library cell or macro -- a leaf that cannot be flattened -- so
its pins persist through optimisation regardless of what happens to the RTL
hierarchy around it.
====

[source,tcl]
----
proc set_cdc_max_delay_prim_sync3 { inst dst_clk {delay {}} } {
    cdc_emit "prim_sync3 $inst" [cdc_sync_delay $dst_clk $delay] to \
        {} [get_pins "$inst/u_my_sync_cell/D" -quiet]
}
----

`$inst` stays the wrapper instance path the generator recorded; you extend it down
to the leaf. If your cell is instantiated in a generate loop or per bit, the path
needs a glob. Note that generate scopes are separated by `.`, not `/`:

[source,tcl]
----
[get_pins "$inst/g_bits*.u_my_sync_cell/D" -quiet]
----

Anchoring this way makes hierarchy preservation a safety margin rather than a
load-bearing dependency.

If you keep the prim wrappers unchanged, the shipped port names work as-is, but
your flow must then preserve those wrapper boundaries. A `destination empty`
warning appearing after `compile` where there was none at constraint-load time
means a boundary was dissolved.

If you go further and replace a wrapper with a module of your own name, the
enumeration that produced `<block>_cdc_max_delay_generated.tcl` knows nothing
about it and those crossings end up with no per-instance bound at all. Nothing
warns -- an element that was never listed cannot report itself missing. Add the
calls for it to `<block>_cdc_max_delay.tcl` by hand; the procs take an instance
path and the capturing clock regardless of the module they were named after.

==== 2. Point the files at your hierarchy, or regenerate

The checked-in `<block>_cdc_max_delay_generated.tcl` files are written against the
OCAH hierarchy, with paths relative to the block's own top and clocks named as
OCAH names them. Two ways to make them apply to your design.

*If you instantiate the block as delivered*, reuse the files and set two
variables. Both default to no-ops, so leaving them alone reproduces the shipped
behaviour exactly.

[source,tcl]
----
# where the block sits in your hierarchy, with a trailing slash
set ::cdc_hier_prefix "u_chiplet/u_mgmt/u_smc/"

# optional: map an OCAH clock name onto the clock you actually drive it with
set ::cdc_clock_alias(SMCCLK) MY_SYS_CLK
----

The prefix is prepended to every instance path. The alias is applied wherever a
clock name reaches the tool, so OCAH's names become labels in your design. You can
also skip the alias and supply the period directly with
`set ::cdc_clock_period(SMCCLK) <ps>`, which is enough for the synchronizer
constraints; the alias additionally matters for the data-path constraints, which
name the destination clock as a timing endpoint and so need it to exist.

*If you reconfigure the block*, regenerate instead. Changing parameters that add
or remove CDC elements makes the shipped file stale in the silent direction -- the
constraints that should exist for new elements simply will not, and nothing warns.
The prefix does not help with that.

A wrong prefix fails loudly: every path resolves to nothing, so you get a warning
per constraint against a zero exception count, and `SUMMARY 0 exceptions` is itself
reported as a setup failure.

Regeneration is also the right answer whenever a parent build contains the block.
Instance counts there can differ from the standalone build, so a parent's file is
not the child's file with a prefix.

==== 3. Set the default bound

The 20 ns / -20 ns figures are a starting point. Both are
`info exists`-guarded in `flows/synth/constraints/async_clock_groups.tcl`, so
setting them before that file is sourced overrides without editing it. `set_async_clock_groups` also
accepts per-call overrides, which is the cleaner way to give one block a different
default:

[source,tcl]
----
set_async_clock_groups { {CLK_A} {CLK_B} } -max_delay 8000 -min_delay -8000
----

Two constraints on the choice. The default must exceed every per-instance bound
you tighten, because it also governs paths from primary inputs into synchronizers;
if it is tighter than `0.5 * T_dst` it becomes the binding constraint there. And
tighter is not automatically better: this is a net for crossings you have not
enumerated, so set it loose enough that those do not fail and rely on layer 2 for
the paths that matter.

The minimum is negative deliberately. With `-allow_paths` a crossing has no
meaningful hold relationship, and a zero floor would report hold violations where
hold is not a real requirement.

==== 4. Declare your own clock groups

`set_async_clock_groups` is called from each block's `constraints.sdc` with that
block's group list. Each inner list is one asynchronous group and globs are
allowed. Globs resolve when the call runs, so it has to come after every
`create_clock` and `create_generated_clock` it is meant to cover.

[source,tcl]
----
set_async_clock_groups {
    {CLK_A CLK_A_DERIVED_*}
    {CLK_B}
    {JTAG_TCK}
} -exclude {{PATTERN_X* PATTERN_Y*}}
----

`-exclude` takes pairs of patterns and suppresses that part of the cross product,
for clock pairs that already have a `-logically_exclusive` or
`-physically_exclusive` relationship that `-allow_paths` would contradict. Omit it
unless you hit a `TIM-184` conflict.

==== 5. Declare periods for generated clocks

A generated clock exposes no readable `period` attribute in Design Compiler, so
any generated clock that clocks a CDC element needs an explicit entry in
`<block>_cdc_max_delay.tcl`:

[source,tcl]
----
set ::cdc_clock_period(MY_DIV_CLK) [expr {4 * $clock_periods(MY_MASTER_PERIOD)}]
----

Omitting one is loud -- a `no period for clock` warning per affected element -- so
a clean run means you have them all. Keep them in step with your
`create_generated_clock` divide factors; nothing cross-checks them.

==== Also check

*Hierarchy preservation.* The reference flow applies `set_ungroup false` and
`set_boundary_optimization false` to the CDC designs before `compile`. How much
this matters depends on item 1: with leaf cell pins it is a safety margin, with
wrapper ports it is load-bearing. Either way, your flow needs the equivalent, and
it needs to name your cells rather than OCAH's.

*Delay factors.* `0.5 * T_dst` and `1.0 * T_dst` are policy, not physics. If your
methodology wants more settling margin, change `cdc_sync_delay` and
`cdc_data_delay` in `flows/synth/constraints/cdc_max_delay_procs.tcl`.
Per-instance overrides are also available without editing procs: every proc takes
an optional trailing delay in picoseconds, and re-stating a call in
`<block>_cdc_max_delay.tcl` after the `source` wins.

*Tool differences.* Two Design Compiler specific choices to revisit under
PrimeTime. `get_attribute <pin> clocks` is used because `get_clocks -of_objects`
is PrimeTime-only, and generated clocks may expose a readable `period` in
PrimeTime, making item 5 unnecessary.

=== Confirming it worked

Load the constraints and check the summary:

....
INFO: cdc_max_delay: SUMMARY <n> exceptions, 0 warnings
....

Zero warnings is necessary but not sufficient. A pin pattern that matches nothing
warns, but one that matches the *wrong* thing does not. Two stronger checks:

* *Predict the count.* Multiply each proc's number of emitted exceptions by its
  number of calls and compare against the summary. A mismatch localises the
  failure, because the size of the shortfall identifies which proc did not fire.
* *Confirm the precedence.* Layer 2 is on pins and layer 1 on clocks, and the
  design assumes the more specific specification wins. Verify once in your tool:

[source,tcl]
----
report_timing -to [get_pins <a synchronizer>/i_d] -nworst 1
----

The `max_delay` line must show your `0.5 * T_dst` value rather than the default. If
it shows the default, layer 2 is inert and nothing else in this section applies.

`SUMMARY 0 exceptions` is treated as a setup failure and warns as such. It means
the constraints did not load, not that the design has no crossings.

=== Scope and limitations

The 20 ns default is loose by design. Against a 1 ns clock it permits twenty clock
periods of delay into a synchronizer input. It is a safety net that keeps
`-allow_paths` usable, not a real constraint; any crossing that matters belongs in
layer 2.

Enumeration works from a fixed list of module names, so a hand-written two-flop
synchronizer that uses none of them will not be found. Structural detection of
crossings is what a static CDC tool does, and this flow does not attempt it. These
constraints time crossings already known to exist; they are not a substitute for
CDC signoff.

Because the instance list is generated offline, removals are loud but additions
are silent. A stale instance path warns, but a synchronizer added without
regenerating produces no warning: the constraint never exists, the path falls back
to the default, and it passes timing. Regenerate and diff the result against what
is checked in whenever the RTL changes.
