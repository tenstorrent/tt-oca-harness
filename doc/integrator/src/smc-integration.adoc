= System Management Controller (SMC) Integration
:trm-url: https://tenstorrent.github.io/tt-oca-harness/ocah-docs/latest
:page-role: integrator-guide

[[smc-integration]]
Connect the SMC's logic-level interfaces to the adopter's clocks, power/reset
controller, peripherals and memory macros. The reference wrappers are described
in xref:smu-integration.adoc#smu-module-variants[SMU Module Variants].
For internal architecture, see
{trm-url}/smc/overview.html#overview[OCAH TRM — SMC Overview].

== Clock and Reset

The SMC requires three external clock inputs: `clk_smc_i` (primary system clock
driving the CPU cluster, fabric, and peripherals), `clk_periph_i` (peripheral clock
driving the peripherals), and `clk_ref_i` (reference
clock for timing-sensitive operations). All must be generated externally by the
adopter's PLL infrastructure; the SMC provides AXI-Lite control outputs for PLL
configuration (see xref:smc-integration.adoc#smc-peripheral-connections[Peripheral Interface Connections]). The peripheral clock is used
to drive the I3C interface, I2C interface, UART interface, and AVSBus interface.

Hold `rst_cold_ni` asserted (low) while power supplies and clocks stabilize.
Assert `powergood_i` once supplies reach nominal, then deassert `rst_cold_ni`
(drive high) to start the boot sequence.

The SMC generates AASD (async-assert / sync-deassert) reset outputs: `rst_primary_smc_clk_no` for the
main clock domain, `rst_primary_periph_clk_no` for the peripheral clock domain, and `rst_primary_ref_clk_no` for the reference clock domain.
These ensure clean reset release without metastability across the system
hierarchy.

Reset domain overrides are delivered through a single typed input,
`jtag_reset_ctrl_i` (`smc_pkg::jtag_smc_reset_ctrl_t`), which carries all
SMC reset override enables and active-low values. The DTP drives this input
through the JTAG IC_RESET mechanism (see xref:smu-integration.adoc#smc-dtp-interconnection[SMC-DTP Internal Interconnection]); most
integrations leave all override enables deasserted.

[[smc-address-map-integration]]
== Address Map and Aperture

Assign a non-overlapping chiplet/SoC address range for SMC. Its global base may
differ from the fixed SMC-local base `0xC000_0000`; firmware programs the
`GLOBAL_BASE` and `REGION_SIZE` CSRs to match your assignment during early boot.
Route the assigned range to SMC while preserving offsets: global base + offset
maps to SMC-local `0xC000_0000` + offset. The default local window is 16 MiB.

The SMC fabric uses three registers in the CPU Control block
(`0xC001_0000`) to distinguish local from remote addresses:

* `LOCAL_BASE` (read-only, fixed at `0xC000_0000`): The local alias
  base. Together with `REGION_SIZE`, this is the address space the SMC
  CPU and internal fabric use to access SMC resources.
* `GLOBAL_BASE` (read-write, defaults to `0x4000_0000`): The
  system-level base address. Firmware must program this during early boot
  to match the adopter's system address assignment, enabling the SMC to
  issue outbound transactions using global system addresses.
* `REGION_SIZE` (read-write, resets to `0x0100_0000` / 16 MiB): The size
  of both the local alias window and the global aperture. It sizes the
  SMC input fabric's local/global split as well as SMU-level routing and
  SEP-to-SMC decode. Firmware must not program it to zero, and must keep
  `LOCAL_BASE + REGION_SIZE` inside the 32-bit SMC-local address space.

See {trm-url}/smc/fabric.html#fabric[OCAH TRM — SMC Fabric] for remapping and
routing, and {trm-url}/smc/memmap.html#smc-memory-map[OCAH TRM — SMC Memory Map]
for the register and memory layout.

== AXI Interface Configuration

The SMC provides four AXI interface groups serving different access
paths. The `sys_axi_in` interface accepts requests from external system masters
requiring access to SMC-managed resources. This interface uses a 56-bit address
space with 64-bit data width and 6-bit transaction IDs. Connect this interface
to your system fabric for normal operational access from application processors
or DMA controllers.

The `sep_axi_in` interface provides dedicated access from the Security Processor
(SEP) subsystem. This interface shares the same sizing parameters as the system
input but operates independently to maintain security domain separation. Use
this interface only when integrating alongside the SEP subsystem. The interface
may remain unconnected if your integration does not include SEP.

The `output_axi` interface carries filtered and remapped requests from the SMC
to external system resources. This interface uses an 8-bit transaction ID field
to accommodate merged traffic from multiple input paths. Connect this interface
to your system interconnect to allow SMC components access to external memory
and peripherals. An AXI VIP or equivalent BFM is a suitable stand-in during
integration verification before the real system fabric is available.

The `jtag_axi_in` interface provides debug access through JTAG mechanisms. This
interface uses reduced 2-bit transaction IDs and connects to your JTAG debug
infrastructure.

== GPIO Pad Integration

Use xref:gpio-reference.adoc[GPIO Pin Requirements] to assign pins and pulls. Default input/output direction is
defined by `smc_padring_pkg::DefaultDirectionMap`, not by the table.

The public `hw/top/smc_wrapper.sv` and `hw/top/smc_ip_integration.sv` examples
show the pad connections. For bidirectional pins, implement proper tri-state
buffers controlled by the `core2pad_en_o` signals. Connect multiplexed UART,
I2C, I3C, and SPI pins to external devices according to the function assignments
in the GPIO table.

Configuration straps are captured separately from the GPIO table. Establish
them before cold reset deassertion and keep them stable during capture. The
generated reset-unit `STRAPS_LO` and `STRAPS_HI` register descriptions define
the decoded bit assignments, including `BYPASS_SRAM_REPAIR` at
`STRAPS_LO[13]` and `TEST_EN` at `STRAPS_LO[14]`.

[[smc-peripheral-connections]]
== Peripheral Interface Connections

The SMC exposes logic-level interfaces to several technology-specific
subsystem components that the adopter instantiates externally. The
subsections below describe each connection in turn.

[[smc-external-connection]]
=== Adopter Peripheral Window

The `smc_external_req_o` and `smc_external_resp_i` signals form a 32-bit
AXI-Lite interface to the adopter's own peripheral register maps. Any
technology- or product-specific block that SMC firmware needs to reach sits
behind this window rather than on a dedicated per-peripheral port.

The window is the recommended home for the control/status registers of logic
that the SMC must configure or monitor but that the SMC itself does not
implement -- padring configuration logic, clock generation, on-die sensors,
memory-technology SHIMs, and similar adopter-owned blocks are typical examples.
For example, runtime reconfiguration of pin directions, pull settings, and peripheral
multiplexing is expected to be reachable here. The SMC decodes the aperture and
forwards the transaction; what lives behind it is entirely adopter-defined.

The window is split into a mandatory region, whose contents and placement the
SMC memory map fixes and every integration must implement, and a supplementary
region for anything else the adopter chooses to expose. For placement and register layout, see
{trm-url}/smc/memmap.html#smc-memory-map[OCAH TRM — SMC Memory Map].

[[smc-efuse-connection]]
=== eFuse Interface

The eFuse interface consists of two parts:

* `efuse_bank_ctrl` -- a 32-bit AXI-Lite interface used to access the SHIM
control CSRs (for example, foundry-specific bank timing such as the
initialization delay before sensing can begin).
* `efuse_shim_command` -- the custom fuse command interface used to issue
read, program, and program/read-back operations to the eFuse bank.

*Adopter responsibility.* The `efuse_shim_command` interface is intentionally
generic and technology-neutral. The adopter must implement an Interface SHIM
that converts these generic commands into the hardware signals required by
their OTP macro. The conversion is driven by the adopter's own read and
program state machines inside the SHIM; OCAH only defines the command/response
contract, not the macro-side signaling.

The command and response payloads are exchanged as packed structs:

[source,sourceCode,systemverilog]
----
// Controller -> SHIM
typedef struct packed {
    addr_t                address;             // Target address (in bits)
    logic                 program_data;        // Data to program (when programming)
    access_length_words_t access_length_words; // Number of WORD_WIDTH words to access
    command_t             command;             // READ / PROGRAM / PROGRAM_READ_BACK
    logic                 valid;               // Request valid
} fuse_command_req_t;

// SHIM -> Controller
typedef struct packed {
    data_t data;   // Read data (one WORD_WIDTH word)
    logic  status; // Operation status (0 = OK, 1 = error)
    logic  valid;  // Response valid (qualifies `data` for one cycle)
} fuse_command_resp_t;
----

*Fuse sensing protocol.* During automatic sensing the controller issues a
single read with `access_length_words` set to the entire bank (all
`NUM_WORDS` words). The SHIM is expected to stream the bank back one
`WORD_WIDTH` word at a time: for each OTP access it drives the read `data`
onto `fuse_command_resp_o.data` and asserts `valid` for *exactly one cycle*.
The controller consumes one word per cycle that `valid` is high, advancing to
the next eFuse word on each assertion.

[WARNING]
====
`valid` must be asserted for only a single cycle per returned word. If the
SHIM holds `valid` high for two cycles, the controller will sample the same
`data` value a second time and count it as the data for the *next* eFuse word,
shifting all subsequent words and corrupting the sensed shadow contents. The
adopter's SHIM FSM is responsible for producing a clean one-cycle `valid`
strobe per `WORD_WIDTH` access.
====

The `shadow_regs_o` output provides read-only access to the sensed fuse
values. During bring-up the SMC automatically senses the fuse contents and
propagates them through the shadow registers; the `fuse_sense_done_o` signal
indicates completion of this sensing operation.

[[smc-sram-cache-integration]]
=== SRAM and Cache Array Integration

Scratch RAM interfaces (`scratch_ram_intf_req_o` and `scratch_ram_intf_rsp_i`)
connect to 32 independent RAM banks totaling the scratchpad memory space. Cache
memory interfaces for L1 instruction and data caches (`l1_icache_*` and
`l1_dcache_*`) connect to tag and data RAM banks as specified in the port table.

The `disable_sram_auto_init_i` input controls automatic memory initialization
behavior. When deasserted, the SMC automatically zeroes all SRAM contents during
bring-up. The `init_mem_done_o` output indicates completion of this
initialization sequence. The `SRAM_AUTO_ZERO_DISABLE` strap
(`STRAPS_LO[26]`) can
disable this automatic zeroing behavior if your integration requires preserved
SRAM contents across resets.

== Memory Repair Integration

The SMC implements Built-In Redundancy Analysis (BIRA) memory repair to address
manufacturing defects in SRAM arrays. Repair uses redundant memory elements
configured with data stored in eFuse memory, replacing defective cells detected
during manufacturing test.

Memory repair executes automatically during boot after eFuse sensing completes
and before MBIST operations. The process must complete successfully before the
CPU cluster can safely access SRAM arrays. Repair is required on every cold
reset but can be bypassed during Function Level Reset (FLR) operations for
faster recovery.

**Control Signals:**

* `fuse_sense_done_o`: eFuse controller output indicating fuse sensing
completion.
  External DFT logic monitors this signal to trigger repair operations.

* `skip_mem_repair_o`: Reset unit output indicating repair should be bypassed. It
  is driven by the isolation request inputs (`isolate_req_pin_sync_smc` or the
  SMC isolation register), not directly by the strap. When asserted, external
  repair logic should skip operations and immediately assert completion status.

* `ext_boot_seq_done_i`: External signal indicating the external boot sequence (memory
  repair and shadow register override) is complete. Held low to pause reset release until
  the external agent gives the go-ahead; required before the system can continue its boot
  sequence

**Repair Data:**

Repair data is stored in the eFuse BIRA shadow register as a 16-kilobit
`repair_data` field. The eFuse controller reads this data during fuse sensing
and makes it available through shadow registers. The external memory repair
controller must read repair data from `shadow_regs_o` and apply it to SRAM
arrays according to your memory architecture.

**Status Monitoring:**

Repair completion and success are reported through
`DFX_CTRL_STATUS.STATUS_SMU` at `0xC000_B800`. The `mem_repair_done` bit
indicates completion regardless of success, while `mem_repair_success` indicates
successful repair. Both bits are set by the external repair controller. The SMC
ROM FW monitors these bits during initialization to verify repair
completion.

**Bypass Configuration:**

The `BYPASS_SRAM_REPAIR` configuration strap (`STRAPS_LO[13]`) is captured into
the reset-unit strap registers. Keep these three mechanisms distinct:

* No RTL path drives `skip_mem_repair_o` from this strap directly.
  `skip_mem_repair_o` is driven from the isolation request path.
* Production ROM reads the strap and, when asserted, skips repair-status
  validation and writes `MBIST_STATUS_MEM_REPAIR_BYPASSED` to scratchpad
  register 15 (`SMC_SCRATCH_MBIST_STATUS`, `0xC003_90F8`). It does not
  cause the external repair controller to skip physical repair.
* External repair logic independently honors `skip_mem_repair_o` to decide
  whether to bypass physical repair operations.

Use bypass mode only when SRAM arrays are guaranteed defect-free, such as
during development or with known-good components.

**Integration Requirements:**

Provide an external memory repair controller that monitors `fuse_sense_done_o`
to initiate repair, respects `skip_mem_repair_o` for bypass control, reads
repair data from eFuse shadow registers, applies repair configuration to SRAM
arrays, asserts `ext_boot_seq_done_i` and updates DFT Control Status registers
with completion status. The controller operates independently of the SMC core
and must complete before the CPU cluster accesses SRAM.

For direct access to the eFuse besides from the shim, i.e. from a DFT fuse controller,
adopters must ensure the integrated logic will not interfere with accesses from the
OCAH's efuse interface.

During FLR operations, the isolation request path asserts `skip_mem_repair_o`
to bypass repair for rapid reset sequences. Normal cold reset sequences always
execute repair unless isolation is already asserted.

== Interrupt Integration

The SMC routes its interrupt sources to the embedded CPU cluster's PLIC.
Connect adopter interrupt inputs and outbound notifications as listed below.
The internal bit assignments are documented in
{trm-url}/smc/interrupts.html#cpu-interrupt-vector-map[OCAH TRM — SMC CPU Interrupt Vector Map].

The SMC PLIC and CPU interrupt vector are internal. `sync_irq_o` is *not* the
interrupt aggregate -- it is the software-controlled `SYNC_REG.sync` global
synchronisation bit in the reset unit, unrelated to PLIC interrupt delivery.
Do not connect an external interrupt controller to `sync_irq_o`.

External interrupt sources visible to the adopter are `ext_interrupts_i` (SMC
external interrupt input vector, width `NUM_INT_TO_SMC`),
`ext_mailbox_interrupts_o` (outbound mailbox notifications, width
`NUM_MAILBOXES`), `gpio_interrupt_o` (GPIO edge/level events, width
`NUM_GPIO_WRAPS`), and `uart_interrupt_o` (UART TX/RX events, width `NUM_UART`).


== Telemetry and Debug Integration

For system-level debug and telemetry, the SMC implements ATB (Advanced Trace Bus) receiver
interfaces. The telemetry interface group (`telemetry_atdata_i`, `telemetry_atid_i`,
`telemetry_atvalid_i`, `telemetry_atready_o`) operates in a dedicated `clk_telemetry_i`
clock domain with separate `rst_telemetry_ni` reset. Connect these signals to ATB trace
sources for debug data collection.

At the SMC boundary, `ext_debug_bus_i` is 512 bits wide; the SMU concatenates
the adopter-visible 128-bit input with the SEP's internal 384-bit bus before
driving SMC. The typed `xtrigger_ss_i` / `xtrigger_ss_o` ports are the only
cross-trigger signals at the SMC boundary. The adopter-visible SMU cross-trigger
interfaces are `xtrig_ctm_*`, `xtrig_clk_stop_req_i`, and the CTP groups.

Trace memory interfaces (`trace_mem_req_o` and `trace_mem_resp_i`) connect to trace RAM
instances for storing captured debug data. `smc_ip_integration.sv` shows an example set of
RAM instances that can be adapted to your debug requirements.

== Bring-Up Sequence

The recommended bring-up sequence begins with asserting `rst_cold_ni` while stabilizing
power supplies and clocks. Once all supplies reach nominal voltages, deassert `rst_cold_ni`
to initiate the SMC boot sequence. The SMC immediately begins fuse sensing to read configuration
values and security credentials.

Monitor the `fuse_sense_done_o` signal to detect completion of fuse sensing. Configuration
straps sampled during this phase determine boot modes and operational settings. After fuse
sensing completes, the SMC releases internal subsystem resets based on the programmed reset
sequencing configuration.

The CPU cluster begins executing the ROM FW after reset release. The ROM FW
performs additional initialization including peripheral configuration, memory
testing (unless disabled), and system health checks. The `init_mem_done_o`
signal indicates completion of memory initialization if automatic SRAM zeroing
is enabled.

To support Function Level Reset (FLR), assert `cfg_flr_pf_active_i` to trigger
a warm reset sequence. The SMC asserts `isolate_req_o` bits for the affected
subsystem indices. The adopter's power controller drives `ss_reset_complete_i`
high once the subsystem reset is complete; the SMC synchronizes this into the
readable `SS_RESET_COMPLETE` register. Isolation remains asserted until cleared by software: SMC firmware must poll
`SS_RESET_COMPLETE` and then write `ISOLATE_REQ_SMC_REG` to clear the FLR
isolation latch. Do not assume isolation releases automatically on
`ss_reset_complete_i`.

See `hw/top/smu_wrapper.sv` and `hw/top/smc_ip_integration.sv` for reference
bring-up wiring examples covering clock, reset, strap, and peripheral connections.

See xref:smc-ports.adoc#smc-port-interface[SMC Port Interface] for the complete port inventory.
See xref:gpio-reference.adoc#gpio-pin-requirements[GPIO Pin Requirements] for the pad assignment table.
