This document specifies the development methodology for this project.

=== Standards

The OCAH design will follow industry or FOSS standards where
appropriate:

* SystemVerilog RTL
* AMBA system buses
* SystemRDL memory map
* AsciiDoc documentation with Asciidoctor

The hardware design is written in a synthesizable subset of
SystemVerilog RTL language. The coding standards are adopted from the
lowRISC organization which are also used in OpenTitan.

System interconnect is implemented with AMBA standard buses. AXI4 and
AXI4-lite is used for data interfaces and is generally configured with
64-bit data and address. Control buses for accessing CSRs and other low
speed sources are implemented with 32-bit APB.

The system memory map and component CSRs (Configuration and Status
Registers) are defined in SystemRDL. This is the single source of truth
and all downstream representations are rendered from this source.
Examples are documentation (HTML), C headers, SystemVerilog UVM DV and
SystemVerilog RTL.

=== Third Party Code

The OCAH project leverages third party open source RTL code whenever
practical in order to boost productivity and not "reinvent the wheel".
The primary projects we reference are:

* https://pulp-platform.org[ETH PULP]
* https://opentitan.org[lowRISC OpenTitan]
* https://www.opencompute.org/products/575/caliptra[OCP Caliptra]

This is not an exclusive list and there will inevitably be other open
source projects added. Furthermore, we will leverage open source tools
project which are described in more detail below.

There are strict rules around the use of open source RTL. OCAH must not
incorporate any code governed under a GPL license. We will only permit
incorporation of code governed under the liberal Apache 2.0 or
equivalent licenses such as Solderpad. The reason is that we do not want
to be encumbered by any GPL-like restrictions as we intend to ultimately
release the OCAH design with a liberal Apapche 2.0 type licence. If you
have any doubts or questions, contact OCAH project managers for
guidance.

The licences discussed above are documented here. We may add some others
to this list.

* https://www.apache.org/licenses/LICENSE-2.0
* https://solderpad.org/licenses/SHL-2.1/

Third party components will be forked into the OCAH repository to
decouple them from the originating project. We may still track the
original project and update these forked versions if there is a good
reason. Some reasons include incorporating bug fixes and feature
enhancements.

We fully expect that third party components will be modified to some
extent. This would be done by adding a wrapper around the design or
portions of it, attempting to leave the core functionality unmodified.
This may not always be possible, so the exact method of modification
will vary.

An example modification would be the CSR (Configuration and Status
Register) design. As described further below, we intend to use SystemRDL
for this purpose and generate those implementations. OpenTitan
components for example, use a different CSR mechanism which will be
replaced so that requires modifications. Another example is that
OpenTitan components use TileLink for their system bus interfaces. OCAH
will use AMBA APB and AXI4, so again, these will need to be replaced.

When adopting and potentially modifying third party modules, make sure
to follow all of the license rules such as keeping all attribution
comments in the file headers.

=== Development Tools

We aim to primarily use open source tools for the development of OCAH in
order to eliminate commercial dependencies and enabling open-sourcing
not only the design, but also the associated tools.

The goal is to enable new adopters of OCAH to be able to immediately
perform simulations and other analyses of the design using readily
available free tools.

For internal development and testing we will employ commercial tools to
validate the OCAH design, proving readiness for chip deployment i.e.
tapeout. This include:

* UVM verification
* lint tools for code quality
* logic synthesis

=== Document Processing

OCAH uses AsciiDoc for documentation:

* *Component README files*: Written in Markdown (.md) format for GitHub
compatibility
* *Detailed documentation*: Written in AsciiDoc (.adoc) format for structured
documentation
* *Auto-generated registers*: Generated as AsciiDoc (.adoc) files from SystemRDL
sources

This approach provides:

* GitHub-native rendering for README files
* Professional documentation rendering with Asciidoctor for detailed specs
* Human readable document source text that can be revision controlled
* Multiple output formats (PDF, HTML) with cross-referencing
capabilities

=== Build Process

Generate HTML documentation:

....
cd doc && make html
....

Generate PDF documentation:

....
cd doc && make pdf
....

Diagrams are most easily created using the DrawIO program. Generate SVG
files and embed them directly in the AsciiDoc document.

Timing diagrams are created with the Wavedrom program. The interactive
application makes it easy to create the JSON source files and edit them
while the CLI version of the application is used to create the output
SVG files that are embedded in the AsciiDoc document.

Install Wavedrom waveform generator and viewer:

....
pip3 install wavedrom

sudo npm install -g wavedrom  # for the interactive editor

sudo npm install wavedrom-cli -g # for the CLI application
....

The editor is launced with `wavedrom-editor` or directly from the
website. Save the JSON source file for the figure and generate the SVG
rendering as follows:

....
wavedrom-cli -i mywaveform.json5 > mywaveform.svg
....

Then embed the SVG figure into the AsciiDoc document.

References:

* https://asciidoctor.org[Asciidoctor]
* https://www.drawio.com[drawio]
* https://wavedrom.com[wavedrom]

=== GitHub Source Code Control and Development

OCAH development is hosted on GitHub under the Tenstorrent organization.
Clone the public repository and use standard GitHub workflows for issues,
pull requests, and code review.

Development can proceed on either macOS or Linux. Open-source tools work on
both platforms; commercial EDA tools such as VCS and Design Compiler are
typically available on shared Linux build hosts when needed.

Follow these steps to get set up and started with development.

\1. Create a GitHub account if you do not already have one.

\2. Configure Git credential management on your machine:
+
....
brew install git-credential-manager
....

\3. Generate an SSH key pair:
+
....
ssh-keygen -t ed25519
....

\4. Start the SSH agent and add your key. You may want to add this to your
shell startup script:
+
....
eval "$(ssh-agent -s)"
ssh-add <name of your key>
....

\5. Add the public key to your GitHub account under
https://github.com/settings/keys. Verify the key with:
+
....
ssh-add -l
....

\6. Clone the repository and create a feature branch for your work.
+
....
git clone git@github.com:tenstorrent/tt-oca-harness.git
cd tt-oca-harness
git checkout -b <your-branch>
....

=== Tracking Tasks and Bugs with GitHub

Development tasks are managed with GitHub issues. Issues may have parent
and child issues, documenting task dependencies throughout the design.
Issues are assigned to milestones to track overall development progress,
and completion of milestones may trigger design reviews or progress
updates as necessary. Tags help filter and sort issues that have certain
properties.

Issues can also track bugs. Design, verification, and firmware engineers
may file bug issues against the design. Bug issues should be assigned to
the owner of the affected code, who may then reassign the issue as
appropriate. Bug issues should have a thorough explanation of the
observed problem including:

* A copy of, or link to, the program or simulator output.
* Any suggested resolution to the problem.
* Most importantly, information on how to reproduce the issue.
** Git hash
** Executed command
** Program input
** Simulation seed
** etc.

An issue template will assist users in filling out all of the relevant
information.

=== Pull Requests

A pull request (PR in GitHub terminology or MR, merge request, in GitLab
terminology) is GitHub's process of controlled merging between branches.
We make use of this to document major changes to the codebase and
facilitate code review.

=== Generated Content

Content automatically generated from source should _not_ be tracked with
Git. Makefiles and scripts should generate this content on-demand as
part of build and simulation flows. Tracking generated content has many
downsides including:

* Repository bloat from constantly changing generated content
(especially from binary files).
* Unintended inconsistencies between source and generated content (e.g.
bad code goes to tapeout because a designer forgot to run the RTL code
generation script before checking in critical source script changes.)
Missing content is always preferable to incorrect content.
* Unnecessary and confusing merge conflicts that may not be resolved
properly, potentially leading to the same sort of design errors
mentioned above.

The following list contains exceptions for tracking generated content:

* Published specs and documentation generated from source for viewing
directly from GitHub.

We can consider setting up https://git-lfs.com/[Git LFS] to track large
binary content if absolutely necessary.

=== Development Flow

We strive for a development process that balances agility and sanity. To
that end, we use the following conventions and processes:

=== Main/release branch proposal

* Development of each feature should happen on its own, dedicated
branch, preferably attached to a GitHub issue to facilitate discussion
and review.
* The `main` branch is the target for all feature PRs.
** Direct commits to `main` are not allowed. All changes must come
through a PR. The main branch will be protected and no direct pushes are
allowed.
** All PRs targeting `main` must pass a battery of basic smoke tests
automatically run by the GitHub CI before a merge is allowed. (Note:
early in the project, there may not be meaningful tests, but these will
be added as the project matures.)
** The `main` branch should be kept 'working' at all times, meaning that
every version should be useful for continued development and testing.
Developers should be able to pull the latest `main` branch and run the
code without major issues.
* When a release is close to ready a release branch is created from
`main` and named with the release major.patch version. This branch is
used to finalize the release, e.g. by updating documentation, fixing any
last minute bugs, etc.
** All changes to the release branch are based on PRs with GitHub issues
targeting the release branch. If these changes also apply to `main`,
then a PR should be created against those branches as well.
** The release branch is also protected and no direct pushes are
allowed.
** All changes targeting the release branch must pass a battery of basic
smoke tests automatically run by the GitHub CI before a merge is allowed
as well as additional release specific tests.
** Since changes to the release branch are also applied to `main`, the
release branch is not merged back into `main` when the release is
finalized. A trial merge can be done to ensure that all relevant changes
are applied to `main`, but this is not strictly necessary.
** When the release is finalized, the release branch is tagged with the
release version.
** Minor (point) releases are made on the same major release branch,
e.g. `v1.0.x`, where `x` is the minor version number. This allows users
to pull from the 'v1.0.x' branch to get the latest bug fixes and minor
enhancements without having to switch to a new major release branch.

=== Versioning

The OCAH project will use semantic versioning (semver) version 2 for
releases. The version format is `MAJOR.MINOR.PATCH`, where:

* MAJOR version when you make incompatible API changes
* MINOR version when you add functionality in a backward compatible
manner
* PATCH version when you make backward compatible bug fixes

Additional labels for pre-release and build metadata are available as
extensions to the MAJOR.MINOR.PATCH format.

See https://semver.org[semver] for more details.

=== Simulation with Verilator

We will use open source tools as much as possible and hence will focus
on using Verilator for unit tests. Verilator has comprehensive
SystemVerilog (SV) support and is widely used in industry.

Verilator ingests the RTL code along with the test code written in C/C++
to generate a program which is compiled and run with gcc. Writing tests
in C/C++ has many benefits:

* high performance, typically better than commercial simulators
* incorporate third party reference code for ciphers as an example
* incorporate code for analysis
* enable development of emulation systems for firmware developers
* can be migrated to DPI based DV environments for sign-off verification

References:

* https://www.veripool.org/verilator[Verilator documents]

=== Testbench and Test Sequence

Verilator is our main simulation engine, and we have several choices on
how to create unit test benches and sequences for IP components and the
SEP subsystem:

* Plain _vanilla_ SystemVerilog
* C/C++
* Python with cocotb

The VeeR EL2 CPU which is used in SEP has cocotb based testbenches,
while Caliptra uses mostly C with Verilator. Either choice will be fine
and it is _TBD_ which one we shall emphasize.

We expect that chip integrators and TT verification engineers will use
UVM in their verification flows. The UVM flow is however not in scope
for the open source release of the OCAH project currently. We _may_
release the UVM verification infrastructure to assist teams in full chip
integration efforts, but that remains TBD.

Antmicro has recently released a code coverage dashboard tool which
works with Verilator. This _may_ be used in the verification flows, but
is TBD based on future evaluations.

References:

* https://www.cocotb.org[cocotb]
* https://github.com/antmicro/coverview[Coverview]

=== Component Design

Individual components of the OCAH are packaged in a manner that allows
them to also be used as standalone IP components and be easily
integrated in other designs. Each component directory includes
everything necessary for its use:

* AsciiDoc documentation
* SystemVerilog RTL implementation
* SystemRDL CSR specification
* Unit tests may be one or more of the following
** Verilator unit tests written in C/C++
** Cocotb unit tests written in Python
* Lint tool waivers
* Synthesis constraints
* Software driver code in C/Rust
** Firmware unit tests can be running on the connected host

The design philosophy is to aim to keep the design easy to understand
and easy to integrate in OCAH or elsewhere. That means using consistent
hardware interfaces and consistent naming schemes. For example, if we
decide to use active low resets throughout OCAH, then we should have an
input named rstn_i on all components. All RTL modules should have a
common name prefix. For example, an AES cipher block should have all
submodules named link:[aes]*.sv.

The components themselves should have minimal dependencies. If there are
subcomponent and package library dependencies then they should be
clearly identified and easy to extract and bundle with a component for
use in other non-OCAH systems. We want to avoid obfuscated, complex
dependencies within the design that are difficult to unravel.

=== CSRs : Configuration and Status Registers

Register and memory map descriptions are written in SystemRDL. Output
renderings include:

* synthesizable Verilog RTL
* HTML documentation
* C header
* IP-XACT XML

We use the PeakRDL tool to generate the various renderings. The tool is
open-source and written in Python. It is possible to write custom
Exporter features using Python plugins.

The Verilog generator will create the CSR implementation as well as a
matching AMBA bus slave interface, either APB or AXI-lite. Every
component will have a CPU software accessible memory mapped CSR block
accessible via a 32-bit APB link to enable programming control and
configuration register and reading status registers. Interrupt are also
defined here.

Cryptographic components will have an additional private key block
accessible via a 64-bit AXI4-lite link. Only the key manager will be
able to write to individual component's key blocks. The separate key bus
enables a design in which the CPU software never has direct access to
the secret key data, whether intentionally or inadvertently. As this is
a write only interface, we will not implement the read address and read
data channels. This will be done by tying off the applicable pins. for
key distribution from the key manager to various cipher blocks and is
therefore a write-only interface. We can consider tying off the Read
Address and Read Data Channel interface pins on the component to remove
any read capability.

OpenTitan components have their CSRs described in a Python DSL and use
reggen to generate outputs. We'll need to convert those into SystemRDL.
Many have already been converted by the Caliptra team. Others like OTBN,
we'll need to handle ourselves. Fortunately there is a tool called
PeakRDL-opentitan which should manage most of this process,
semi-autmatically i.e. I expect we'll make some tweaks to the output,
but it's a great starting point.

....
git clone https://github.com/Risto97/PeakRDL-opentitan.git
cd PeakRDL-opentitan
pip install -e .
....

=== Special Considerations for Cryptographic Components

As mentioned above, crypto components will have an AXI4-Lite private key
bus interface mastered by the Key Manager.

In addition, there will be some facilities for physical attack
countermeasures such as side channel analysis (SCA) and fault injection
(FI):

* Entropy noise input used for masking, and random stall cycle or decoy
cycle insertion
* Random clock stall or decoy instructions
* Wipe input command for rapid clearing or randomization of sensitive
state to prevent data exfiltration

=== Unit Testbenches

Component functionality will be mostly verified at the individual unit
level. This means that we will have at least one unit testbench and test
sequence for each. Unit tests are run on Verilator and primarily written
in C/C++, although portions may be in standard SystemVerilog. We will
not use UVM for unit test. UVM _is_ used by the DV team for chip level
sign off tests, but that is beyond the scope of OCAH as a standalone
project.

Unit tests live under the directory <component_name>/sim. Each
component's sim directory will have a <component_name>_tests.adoc. This
document will have an initial section describing how to run any of the
tests followed by a description of each test.

Tests must cover at least the following:

* Data transfer over its AMBA bus interfaces (ABP, AXI4 etc.)
* CSR features for control, status and interrupts
* Mission mode functions

All testbenches and test sequence files will have the <component_name>
as a prefix.

=== Fuse Map

The fuse map will be described in an abstract format, similar to CSRs
and from which all downstream representations are generated.

=== Interconnect Crossbar Generators

The OCAH project will be using industry standard AMBA bus protocol for
physical interconnect between components as mentioned earlier. To
support this, we will have tools to generate interconnection crossbars
for both AXI4 and APB4. The interconnect matrix is specified in YAML.

The OpenTitan components are using TL-UL (TileLink Ultralight) for
interconnect and we will either add shim logic to translate to AMBA or
replace those interfaces with AMBA versions.

=== Component Directory Organization

All components will have a uniform directory structure which has the
following elements:

* README.md : component overview and quick start guide in Markdown
format
* doc/ : detailed AsciiDoc documentation (architecture.adoc, interface.adoc,
memmap.adoc, index.adoc)
* rtl : all SystemVerilog modules <component>_*.sv
* tb : unit level Verilator tests
* regs/ : <component>.rdl SystemRDL CSR memory map definition and generated collateral
* syn : logic synthesis constraints (optional)
* lint : lint waiver files

=== SystemVerilog Coding Guidelines

The high level goals are:

* avoid SystemVerilog constructs that are error prone or not
consistently supported, particularly across open source tools
* ensure that the code is tidy and easy to read
* keep the code style consistent across the project's code base
regardless of who authored it

OCAH will _mostly_ follow the OpenTitan SystemVerilog coding rules
defined by lowRISC group in
https://github.com/lowRISC/style-guides/blob/master/VerilogCodingStyle.md[Verilog
Coding Style] That document is locally copied for convenience.

This section highlights a few of the most important aspects as well as a
few deviations from the OpenTitan rules. If there is a conflict between
the two, the specification here takes precedence.

* Use two spaces for indentation, matching the lowRISC style guide.
* Use all upper case letters to name enums, constants (localparam), and
parameters instead of UpperCamelCase.
* As stated in the lowRISC guidelines, SystemVerilog Interfaces can be
limited in terms of tool support, so we _highly discourage_ their use as
they are not uniformly supported by open source tools. As an
alternative, struct types can be used instead to bundle groups of input
or output signals to make ports more abstract.
* Finite State Machines (FSMs) are powerful sequence control constructs
but can spiral out of control quickly. Consequences are difficult to
understand "next state" logic and long timing paths. Separate the
combinatorial "next state" logic from the sequential state update into
distinct always blocks. *Do not* combine the two into a single clocked
always block. Opt for a
https://en.wikipedia.org/wiki/Moore_machine[Moore machine]
implementation when possible to aid in timing closure. If you have
complexity of more than ten states or so, use a microsequencer approach.
This is more scalable and maintainable.

There will be additional rules that apply to security sensitive
components such as ciphers. These will be documented in more detail, but
here is a summary for now:

* FSM state encodings are one-hot with error checking
* Error detection is implemented on storage elements and some bus and
computational elements
* Secret data is transferred and stored in secret-split fashion

=== RTL Code Comments

RTL code comments have a tendency to get out of sync with the code or
simply be redundant, adding little or negative value. Hence, keep
comments in the RTL as minimal as possible and prefer to make the code
self explanatory. Include a description of the purpose and overall
function of the module in the header. If there is a tricky bit of code
with some nuance, it's fine to add a comment describing the overall goal
or strategy of the code. However do not just add an English translation
of what the Verilog code is doing as that is in best case redundant.

=== Configuration

Configuration files are used for specifying structure or behavior in
applications like interconnect crossbars, fuse maps, memory maps etc. We
have several different flavors of configuration files in the codebase
today but ideally would like to standardize on one such as HJSON or
JSON.

As described earlier, memory maps and CSRs we will be declared in
SystemRDL.
