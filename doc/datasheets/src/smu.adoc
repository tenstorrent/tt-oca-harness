HIGHLIGHTS

* Composes OCAH management, debug/test, and optional security subsystems
* Full reference configuration integrates SMC, SEP, DTP, and a 3-by-3 AXI4 fabric
* Alternate no-SEP configuration preserves SMC, DTP, and external AXI interfaces
* Runtime-programmed SMC/SEP apertures with fixed, loop-free connectivity
* Integrated reset, clock-stop, lifecycle, mailbox, interrupt, and debug handoffs
* Technology-neutral core plus an open reference wrapper for macro substitution

// datasheet-section: system-role
[.datasheet-section]
SYSTEM ROLE

SMU is the composed management boundary between the chiplet system fabric,
external debug and test equipment, adopter implementation resources, and the
OCAH SMC, DTP, and optional SEP. It supplies their integration wiring and
control handoffs; the adopter owns chiplet-level address assignment, clocks,
power/reset sequencing, pads, technology macros, firmware policy, and product
security authorization.

a|
// datasheet-section: overview
[.datasheet-section]
OVERVIEW

The System Management Unit (SMU) combines the System Management Controller
(SMC), Debug and Test Ports (DTP), and, by default, the Security Processor
(SEP). In the full configuration, a 3-input, 3-output AXI4 crossbar routes SMC,
SEP, and external-system traffic using runtime-programmed SMC and SEP apertures.
DTP connects JTAG, scan, reset override, cross-trigger, and debug-access paths;
SMC coordinates management, resets, clocking, interrupts, and peripheral
services; SEP supplies lifecycle-derived debug controls and security services.

The `smu` RTL top keeps technology-specific memories, OTP/eFuse, clocking,
sensors, pads, entropy, and selected I/O behind typed integration interfaces.
The open `smu_wrapper` attaches generic models and example termination for a
reference build, but is not a characterized production implementation. Setting
`SEP=0` removes SEP and the 3-by-3 crossbar, connects SMC directly to the stable
external AXI boundary through ID converters, and applies defined SEP tie-offs.

// datasheet-section: capabilities
[.datasheet-section]
CAPABILITIES

*Composition and control*

* SMC and DTP always instantiated; SEP selected at elaboration
* Internal wiring for DTP-to-SMC debug fabric and OTP, DTP-to-SEP debug and OTP,
  SEP-to-SMC mailbox/reset/security status, and SMC-to-DTP cross-trigger control
* SMC-owned primary reset sequencing, 32 subsystem reset/isolation slots,
  external boot/repair gate, watchdog handoffs, and DTP clock-stop output
* Lifecycle-derived SEP debug-disable controls feed DTP in the full configuration

*Full-configuration fabric*

* SEP can target SMC or the external output; SMC can target SEP or the external
  output; the external input can target SEP or SMC
* Runtime SMC and SEP aperture base/size rules; no same-port loops and no
  external-input-to-external-output path
* Unmatched SMC/SEP outbound traffic uses the external output; unmatched
  external inbound traffic receives a decode error
* AXI ID-width conversion at SMC/SEP targets; atomic operations disabled
* Fixed 1 GiB SEP-to-SMC local-alias window in the checked-in RTL

*No-SEP behavior*

* Direct external-to-SMC and SMC-to-external AXI paths retain the public widths
* SEP memory, entropy, I/O, mailbox, lifecycle-error, and status ports are tied
  to defined inactive values; the SEP aperture reports zero size
* SEP OTP debug accesses receive DECERR and the SEP secondary TAP has no target

// datasheet-section: integration-dependencies
[.datasheet-section]
INTEGRATION DEPENDENCIES

* Select `DefaultCfg`/`SEP=1` or `NoSepCfg`/`SEP=0`; preserve the complete
  parameter manifest with the release.
* Assign non-overlapping chiplet envelopes and program non-overlapping SMC/SEP
  apertures. Keep aperture controls stable while transactions are in flight and
  route unsupported atomic requests according to system policy.
* In `SEP=0`, DTP receives an all-zero debug-disable vector and the lifecycle
  output uses a fixed tie-off. Do not treat those values as product security
  authorization; define an acceptable no-SEP debug and lifecycle policy.
* Replace zero-valued JTAG identity and SEP security-token fields; supply
  reviewed firmware, provisioning, recovery, and update policy.
* Provide production clocks, reset/CDC constraints, power sequencing, pads,
  memories, OTP/eFuse, sensors, entropy, I/O, and physical implementation.
  Reference-wrapper models and error-slave terminations are examples only.
* Connect or terminate every external fabric, scan, trigger, interrupt,
  mailbox, reset/isolation, macro, and adopter-extension interface.

// datasheet-section: verification-and-maturity
[.datasheet-section]
VERIFICATION AND MATURITY

[.beta-note]
--
The OCAH documentation website publishes the current verification and maturity status.
Hosted cocotb/PyUVM smoke and regression use the bare `smu` DUT with `SEP=0`;
the 53-test `sep0_all` group exercises SMC/DTP composition, direct external AXI,
filters, ID conversion, atomic rejection, JTAG-to-AXI/OTP, reset, mailbox,
cross-trigger, and clock-stop scenarios. This does not credit the full 3-by-3
fabric or live SEP interoperability.

A separate `smu_wrapper` catalog has four smoke entries spanning no-SEP and
real-SEP profiles, including firmware and SEP boot-readiness observations.
Additional real-SEP groups are separately enrolled or blocked and are not part
of hosted SMU signoff. Wrapper results are not combined with bare-SMU results.

There is no agreed functional-coverage closure target or SMU RTL code-coverage
configuration. No standards certification, silicon characterization, product
security assessment, or portable frequency, area, power, latency, or throughput
result is claimed.
--
