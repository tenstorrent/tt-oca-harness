[[dtp-programming-guide]]
== DTP Programming Guide

The Debug and Test Ports (DTP) are programmed from two sides: firmware or a
debugger configures the cross-trigger network through its CSR window, and an
external debugger drives the JTAG test access ports.

[[dtp-cross-trigger]]
=== Cross-Trigger Network

Cross-trigger configuration is static. Software programs every external CTP
from the SiP cross-trigger topology once per boot, then opens the CTM routes
that use those ports, and leaves both unchanged for the rest of the session.
Register offsets are relative to the CTN base address; the
ifdef::backend-html5[]
xref:ocah-docs:ip:cross_trigger_network/doc/index.adoc#ctn-address-allocation-table[CTN address allocation table]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-docs/latest/ip/cross_trigger_network/doc/index.html#ctn-address-allocation-table[CTN address allocation table]
endif::backend-pdf[]
lists the CTM and CTP windows. Firmware and an external debugger share this
window, and whichever of them programs cross triggers follows the sequence
below.

[[dtp-ctn-requirements]]
==== Requirements

* Both ends of a CTP link use the same protocol and polarity, and the board
  determines both:
** A shared wire-OR line with pull-ups uses `MODE` = 0 and `INVERT` = 0; with
   pull-downs it uses `MODE` = 0 and `INVERT` = 1.
** A point-to-point link with active-high signaling uses `MODE` = 1 and
   `INVERT` = 0; with active-low signaling it uses `MODE` = 1 and `INVERT` = 1.
* The configuration stays fixed for the session. Change a port whose routes
  are already open only through the sequence in
  <<dtp-ctn-reconfigure>>.
* After reset every CTP is in wire-OR mode with `INVERT` = 0, and every CTM
  output is disabled because each `CT_DST_SELECT` resets to zero. Until
  software writes `CONFIG`, a CTP drives neither `CT_Req_out` nor
  `CT_Ack_out`, so the board pulls set the level the far end sees on those
  lines. Choose pulls that the far end reads as deasserted.
* Internal CTPs have no registers. The `INT_CT_MODE` parameter fixes their
  protocol.
* The CTM configuration across the SiP is free of loops. A wire-OR CTP
  receives its own assertion of the shared wire, so a route from a wire-OR
  CTP back to the same CTP is a loop.

[[dtp-ctn-init]]
==== Initialization Sequence

. For each external CTP `i` that the SiP uses:
.. For a wire-OR port, write `STRETCH_MULT` with the pulse width the shared
   wire requires, minus one.
.. Write `CONFIG` with `MODE` and `INVERT` for the board in a single write,
   with `RESET` = 0.
. For each CTM output `n` that carries triggers, write
  `CT_SRC[n].CONFIG_0.CT_DST_SELECT`. Setting bit `m` forwards the triggers
  that port `m` receives to port `n`. The
ifdef::backend-html5[]
xref:ocah-docs:ip:cross_trigger_network/doc/index.adoc#ctn-matrix-port-indices-table[CTM port index table]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-docs/latest/ip/cross_trigger_network/doc/index.html#ctn-matrix-port-indices-table[CTM port index table]
endif::backend-pdf[]
maps port indices to external and internal CTPs.

The order matters. A CTM route delivers triggers to a CTP from the moment it
is written. A CTP still in its reset-default wire-OR mode transmits a trigger
by driving `CT_Req_out` to the asserted wire-OR level, which is low with
`INVERT` = 0. A point-to-point far end built for active-low signaling reads
that level as a request. Writing `MODE` and `INVERT` together keeps a port from
running, even briefly, with one field set for the board and the other still
at its reset value.

The following example configures external CTP 0 for an active-low
point-to-point link and external CTP 1 for a wire-OR line with pull-ups, then
routes triggers between them.

[source,sourceCode,c]
----
#define CTP_REG(i, reg)  (ctn_base + CROSS_TRIGGER_NETWORK_CTP_BASE_ADDR(i) + (reg))
#define CTM_ROUTE(n)     (ctn_base + CROSS_TRIGGER_NETWORK_CTM_BASE_ADDR + \
                          CROSS_TRIGGER_MATRIX_CT_SRC_CONFIG_0_BASE_ADDR(n))

#define CONFIG_MODE_P2P  (1u << 0)
#define CONFIG_INVERT    (1u << 1)
#define CONFIG_RESET     (1u << 2)

// Configure every port before opening any route.
write32(CTP_REG(0, CROSS_TRIGGER_PORT_CONFIG_BASE_ADDR), CONFIG_MODE_P2P | CONFIG_INVERT);
write32(CTP_REG(1, CROSS_TRIGGER_PORT_STRETCH_MULT_BASE_ADDR), 15); // 16-cycle pulses
write32(CTP_REG(1, CROSS_TRIGGER_PORT_CONFIG_BASE_ADDR), 0);

// Triggers received on port 1 go out on port 0, and the reverse.
write32(CTM_ROUTE(0), 1u << 1);
write32(CTM_ROUTE(1), 1u << 0);
----

[[dtp-ctn-reconfigure]]
==== Changing a Port's Configuration

Changing `CONFIG` after routes are open is discouraged. When a link must
change protocol or polarity, for example after both chiplets agree on a new
topology, reconfigure port `p` as shown below. A poll that times out means
the point-to-point far end never acknowledged; recover the port as described in
<<dtp-ctn-deadlock>>.

.Changing a CTP's configuration.
[plantuml,ocah-ctn-reconfigure,svg,width=60%,align="center"]
----
@startuml
start
:Close every route involving port p:
write 0 to CT_SRC[p] and clear bit p
in every other CT_SRC[n];
while (STATUS.BUSY of port p reads 1?) is (yes)
  if (Poll timed out?) then (yes)
    :Write CONFIG with RESET = 1,
    then with RESET = 0;
  else (no)
  endif
endwhile (no)
:Write CONFIG with the new
MODE and INVERT in one write;
:Reopen the routes;
stop
@enduml
----

The CTP holds its point-to-point handshake idle while wire-OR mode is
selected. After point-to-point mode is selected, the handshake ignores
`CT_Req_in` and `CT_Ack_in` until their synchronized levels are valid.
Closing the routes first keeps triggers from being sent or forwarded while
the two ends of the link disagree.

[[dtp-ctn-deadlock]]
==== Handshake Deadlock Recovery

A point-to-point sender waits for `CT_Ack_in` without a timeout. If the far
end stops responding, `STATUS.REQ_OUT` and `STATUS.BUSY` stay 1, and the port
transmits no further triggers.

. Write `CONFIG` with `RESET` = 1, keeping `MODE` and `INVERT` unchanged.
  `CT_Req_out` deasserts, and the port discards triggers delivered to it
  while `RESET` is set.
. Write `CONFIG` with `RESET` = 0.

`RESET` does not affect the receiving side. A far end that holds `CT_Req_in`
asserted keeps `STATUS.BUSY` at 1 until it releases the request.

[[dtp-debug-host-procedures]]
=== Debug Host Procedures

These procedures are performed by an external debugger through the chiplet's
JTAG port. An IR scan loads an instruction with the IR-Scan sequence; a DR scan
shifts the selected test data register (TDR) with the DR-Scan sequence, least
significant bit first. The TRM defines every instruction and TDR field.

[[dtp-ptap-tdr-access]]
==== Primary TAP Registers

To read or write a primary TAP TDR:

. Shift its instruction into the instruction register with an IR scan.
. Shift the TDR with a DR scan, starting with the least significant bit.
. Read the TDR contents shifted out on TDO.

The TDRs differ in what the shifted-in bits do:

* *IDCODE* and *JTAG_CAPS* are read-only. Shift in any pattern; the bits are
  ignored. Read JTAG_CAPS to discover which instructions and ports an
  instance enables before using them.
* *DEBUG_CONTROL* captures the bits shifted into its read/write fields and
  ignores those shifted into its read-only fields.
* *Boundary scan* instructions that select the boundary-scan registers shift
  their contents out on TDO. An instruction disabled in the instance behaves as
  BYPASS.

[[dtp-runbist]]
==== Running BIST

The PTAP adds no scan cell of its own to the RUNBIST path, so the attached
iJTAG network defines the length and contents of the RUNBIST DR.

. Shift RUNBIST into the instruction register with an IR scan.
. Shift the configuration vector that the attached iJTAG network defines for
  reaching the BIST TDR with a DR scan. A hierarchical network needs one DR scan
  for each level of Segment Insertion Bits (SIBs) opened on the way.
. Shift the BIST TDR contents, together with the bits of every SIB and register
  still on the scan path, with a DR scan.
. Read the captured contents of the same scan path on TDO.

[[dtp-ijtag-access]]
==== iJTAG Segment Access

The JTAG Interface Unit's iJTAG network starts with three one-bit SIBs. With
every SIB closed the DR is three bits long: bit 0 (nearest TDO, shifted in
first) is the DFD SIB, bit 1 the DFT Non-Secure SIB and bit 2 the DFT Secure
SIB. A SIB whose debug-disable field is set stays closed and captures 0.

. Shift SELECT_IJTAG, or RUNBIST to run BIST, into the instruction register
  with an IR scan.
. Open the target SIB with a three-bit DR scan: `3'b100` for DFT Secure,
  `3'b010` for DFT Non-Secure or `3'b001` for DFD. The target SIB's
  debug-disable field must be clear.
. Shift the lengthened DR with the target SIB's bit held at 1. With the DFT
  Non-Secure SIB open and an N-bit segment, the DR is N + 3 bits long: bit 0 is
  the DFD SIB, bits N to 1 are the segment with the bit nearest its scan output
  at bit 1, bit N + 1 is the DFT Non-Secure SIB and bit N + 2 is the DFT Secure
  SIB. The network attached to each segment defines its contents and length.
. Read the captured contents of the same scan path on TDO.
. Close the SIB by shifting the same DR with the target SIB's bit at 0.

[[dtp-jtag2axi-access]]
==== JTAG2AXI Bridge Access

A JTAG2AXI bridge is a RISC-V Debug Module behind two primary TAP TDRs: a 32-bit
DTMCS register and a 41-bit DMI register. The debugger reads and writes memory
with the System Bus Access (SBA) registers of the Debug Module. Each bridge has
its own instruction pair (<<dtp-jtag2axi-instructions-table>>). Read JTAG_CAPS
first: the instructions of a bridge that the instance does not have behave as
BYPASS.

[[dtp-jtag2axi-instructions-table]]
[width="100%",cols="<25%,<20%,<20%,<35%",options="header"]
.JTAG2AXI bridge instructions
|===
|Bridge |DTMCS instruction |DMI instruction |Target
|SMC OTP |`0x1B` |`0x1C` |SMC eFuse interface, AXI4-Lite
|SEP OTP |`0x1D` |`0x1E` |SEP eFuse interface, AXI4-Lite
|SMC fabric |`0x1F` |`0x20` |SMC AXI fabric, AXI4
|===

The
ifdef::backend-html5[]
xref:ocah-docs:ip:jtag_ptap/doc/index.adoc#ptap-jtag2axi-support[PTAP JTAG2AXI Support]
endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-docs/latest/ip/jtag_ptap/doc/index.html#ptap-jtag2axi-support[PTAP JTAG2AXI Support]
endif::backend-pdf[]
section of the TRM defines the two TDRs, the Debug Module registers and the AXI
transfers.

*One DMI operation*

. With the DMI instruction selected, shift a 41-bit DR scan: `op` in bits 1:0
  (1 for a read, 2 for a write), the write data in bits 33:2 and the register
  address in bits 40:34.
. Stay in Run-Test/Idle for some TCK cycles. The operation progresses only while
  TCK runs. Start with the `idle` value that the DTMCS register reports.
. Shift the next DMI DR scan. Bits 1:0 of the value shifted out are the status,
  and bits 33:2 are the data of a read. Shift `op` 0 in this scan if no other
  operation follows.

A status of 0 means the operation completed. A status of 3 means a scan arrived
while an operation was in progress, and the bridge did not take the operation of
that scan. The status stays until it is cleared:

. Clear it with a DTMCS DR scan that has `dmireset` (bit 16) set, or with a DMI
  DR scan that has `op` 3.
. Use more Run-Test/Idle cycles after each scan.
. Send the operation again. A read that is sent again can reach the Debug Module
  two times, so do not resend a read of `sbdata0` while `sbreadondata` is 1
  without a check of the address.

A status of 2 means the Debug Module refused an operation. Clear it in the same
way.

*Bring-up of a bridge*

. Select the DTMCS instruction and shift a 32-bit DR scan of zeros. Check that
  `version` (bits 3:0) is 1 and `abits` (bits 9:4) is 7.
. Select the DMI instruction.
. Write `dmcontrol` (address `0x10`) with `0x00000001` to set `dmactive`.
. Read `sbcs` (address `0x38`). `sbasize` (bits 11:5) is the address width.
  `sbaccess8`, `sbaccess16`, `sbaccess32` and `sbaccess64` (bits 0 to 3) show the
  access sizes; the largest one is the data width.

*Single write*

. Write `sbcs` with `sbaccess` (bits 19:17) set to the access size: 0 for 1 byte,
  1 for 2 bytes, 2 for 4 bytes, 3 for 8 bytes.
. If the address width is more than 32 bits, write `sbaddress1` (`0x3A`) with
  address bits 63:32.
. Write `sbaddress0` (`0x39`) with address bits 31:0. The address must be aligned
  to the access size.
. For an 8-byte access, write `sbdata1` (`0x3D`) with data bits 63:32.
. Write `sbdata0` (`0x3C`) with data bits 31:0. This write starts the AXI write.
. Read `sbcs` until `sbbusy` (bit 21) is 0, then check `sberror` (bits 14:12) and
  `sbbusyerror` (bit 22).

*Single read*

. Write `sbcs` with `sbaccess` set to the access size and `sbreadonaddr` (bit 20)
  set.
. Write `sbaddress1`, if the address width needs it, then `sbaddress0`. The
  write of `sbaddress0` starts the AXI read.
. Read `sbcs` until `sbbusy` is 0, then check `sberror` and `sbbusyerror`.
. For an 8-byte access, read `sbdata1`. Then read `sbdata0`.

*Block access*

For a block write, also set `sbautoincrement` (bit 16) in `sbcs`. Each write of
`sbdata0` then writes one element and advances the address by the access size.
The address advances only after an access that completes without an error.
After an access that sets `sberror` 2, the address is still the address of that
access.

For a block read, set `sbreadonaddr`, `sbreadondata` (bit 15) and
`sbautoincrement` in `sbcs`, then write the address. Each read of `sbdata0`
returns one element and starts the read of the next one. Before the read of the
last element, write `sbcs` again with `sbreadondata` clear, so that no access
beyond the block starts.

Give each element enough Run-Test/Idle cycles for its AXI transfer, or read
`sbcs` until `sbbusy` is 0 between elements. An access to an SBA register while
`sbbusy` is 1 sets `sbbusyerror` and does not take place.

*Errors and recovery*

* `sberror` 2: the AXI subordinate answered with an error, or the bridge is
  disabled. A disabled bridge answers every access with this error and sends no
  request to its target; `sbcs` still reads the geometry. The lifecycle state
  disables only the SMC fabric bridge. The two OTP bridges stay enabled in each
  lifecycle state.
* `sberror` 3: the address is not aligned to the access size. `sberror` 4: the
  access size is larger than the data width.
* Clear `sberror` with a write of `sbcs` that has all three `sberror` bits set.
  The bridge starts no access while `sberror` is not 0.
* Clear `sbbusyerror` with a write of 1 to bit 22 of `sbcs`.
* The bridges have no access timeout. If `sbbusy` stays 1, the target did not
  complete the transfer, and only a system reset recovers the bridge.
* A system reset clears `dmactive` and the SBA registers; do the bring-up again.
  TRST and Test-Logic-Reset do not reset the Debug Module. A write of 0 and
  then 1 to `dmactive` resets its registers. While `dmactive` is 0, a write or
  a read of an SBA register starts no AXI access. An access that is in progress
  when `dmactive` goes to 0 completes first: read `sbcs` until `sbbusy` is 0
  before the write of 1, or the registers do not reset.
* Assert and release TRST only while TCK is stopped.

*OpenOCD*

The bridges have the DTMCS and DMI registers that the OpenOCD `riscv` target
uses, but operation with OpenOCD is not validated. The setup for one bridge,
here the SMC fabric bridge, is:

[source,tcl]
----
jtag newtap chiplet ptap -irlen 6 -expected-id <idcode>
target create chiplet.smc_bridge riscv -chain-position chiplet.ptap
riscv set_ir dtmcs 0x1f
riscv set_ir dmi 0x20
riscv set_mem_access sysbus
----

`riscv set_ir` applies to the whole OpenOCD process, so one process addresses
one bridge. The one hart of the Debug Module is always unavailable: halt, resume
and register access have no function, and memory access goes through the system
bus only.

The `irscan`, `drscan` and `runtest` commands give direct access to the two TDRs
with the sequences of this section, for example `irscan chiplet.ptap 0x20`,
then `drscan chiplet.ptap 41 <value>` and `runtest <cycles>`.

[[dtp-ic-reset-overrides]]
==== IC_RESET Overrides

Each IC_RESET port has an active-low `reset_control` value and a `reset_enable`
select that is also active low: writing 0 hands the port to `reset_control`.
Consumers select between the functional reset and `reset_control` with a
hazard-free multiplexer, which holds its output only while the select moves
alone. To assert an override:

. Shift IC_RESET into the instruction register with an IR scan.
. Write the port's `reset_control` with a DR scan, leaving `reset_enable` at 1.
. Clear `reset_enable` in a second DR scan, so that its Update-DR moves only the
  select.

[[dtp-sep-reset-vector]]
==== SEP Reset Vector Redirect

The SEP CPU reset vector is held in a TDR of the EL2 debug TAP, reached through
the SEP Core Debug STAP. To start the SEP CPU from a memory other than the Boot
ROM for bring-up or failure analysis:

. Hold the SEP CPU in reset, for example with the SEP main-reset IC_RESET
  override (<<dtp-ic-reset-overrides>>).
. Select the reset-vector TDR with JTAG instruction opcode `0x18` and shift in
  the alternate address. The TDR stores address bits [31:1]; bit 0 is zero.
. Release the reset.

The value persists until it is rewritten or the TAP is reset (TRST or
Test-Logic-Reset); CPU reset alone does not restore the Boot ROM default.

[[dtp-smc-cmderr]]
==== SMC Debug Module Abstract Command Errors

The SMC Debug Module departs from the RISC-V External Debug Support
specification: a `command` write while `abstractcs.cmderr` is nonzero replaces
the stored command, and no abstract command executes until `cmderr` is cleared.
A debugger therefore:

. Reads `abstractcs` to capture the error code of a failed command before it
  writes `command` again.
. Clears `cmderr` by writing 1s to the field and confirms that it reads 0 before
  issuing the next command.

The
ifdef::backend-html5[]

endif::backend-html5[]
ifdef::backend-pdf[]
https://docs.tenstorrent.com/tt-oca-harness/ocah-docs/latest/smc/cpu.html#smc-debug-command-cmderr[SMC Debug Module description]
