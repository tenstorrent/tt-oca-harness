SMC deferred and OUT disposition

This is the disposition of record for every test name the package catalogues without a module under hw/sys/smc/dv/cocotb/tests/, and for every enrolled leaf that no scheduled tier runs (Leaves no scheduled tier runs). Nothing here is enrolled PASS. Every @pyuvm.test() module under cocotb/tests/ is in at least one testlist (smc_base_test and smc_dual_base_test are base classes, not tests); a catalogued name without a module is one of two kinds:

  • A retired test module targets this bench and its blocker is outside the test: adopter placeholder RTL, a wrapper pin that does not exist, an idle boundary, an aperture or window SEP_IN cannot write or reach, TB glue, or a VIP the bench lacks. Its code, and the seq_lib/<name>_seq.py sequence where it had one, is in git history and is restored when the blocker named in its row clears.

  • A catalog-only name never had a module here: a commercial alias whose intent a live enrolled name already proves, or a body that needs stimulus, RTL or a firmware image this bench does not have.

Buckets:

  • adopter-pending OUT — waits on adopter IP, a product pin, firmware/ROM, or a TB terminator.

  • child-TB-owned — protocol completeness belongs to a block-level TB (I3C, DTP).

  • waived — fake BFM, TB-glue, or a commercial alias already covered by a live name.

Idle smc_wrapper boundaries (OUT)

These ports have no TB terminator on --dut smc / smc_wrapper (hw/sys/smc/dv/models/README.md). They are OUT rather than terminated by a placeholder responder. Block-level I3C and DTP signoff stay on those TBs; do not count a wrapper terminator as that proof.

Bench tie-offs

A tie-off is a constant on an smc_wrapper input port in tb_top.sv (the single-instance u_dut and the smc_dual_inst wrapper instance). Every --dut smc / smc_wrapper and SMC_DUAL leaf runs under it, on every tool. Each row states the behaviour the constant keeps out of reach, the enrolled claims that would change if the pin were driven, and the control that closes the row.

Tie-off Value Behaviour made unreachable Tests whose claims would change Control / closes when Owner Review date

sep_security_disable_i (tb_top.sv, both smc_wrapper instances)

1’b0

The eFuse sense bypass (hw/ip/efuse/doc/architecture.adoc, "Security Disable Bypass Mechanism"). On the product the pin is the SEP security_disable_o token-match result (sep.sv, wired through smu.sv); inside SMC it reaches only smc_efuse_wrapper → efuse_interface_controller.security_disable_i. SMC builds the controller with HAS_LC_STATE=0 (smc_efuse_wrapper.sv), so the bypass takes the non-LC branch: the controller drives shadow_regs_o from the shadow registers whenever fuse sensing has finished or the pin is high, and drives all zeros otherwise (efuse_interface_controller.sv:449); its command mux routes the shadow-register sense FSM to the bank only while sensing is not done and the pin is low (efuse_interface_controller.sv:759). With the pin at 1 the FSM’s reads are never routed, so fuse_sense_done never rises, the shadow registers keep their all-zero reset value and are exposed unsensed, and fuse_reset_n — and with it rst_warm (smc_reset_ctrl.sv:135) — never release: the warm domain never leaves reset. With the pin at 0 every run senses the bank, which is what the product does on a chip whose SEC_DIS token did not match.

None of the enrolled claims: no leaf claims the bypass, and every eFuse leaf proves the sensed path, which is the path a 0 selects. Were the pin driven to 1 for a run, every sequence that calls wait_fuse_sense_done (40 sequence files under cocotb/seq_lib/; smc_base_test_seq.py defines the method and each leaf that needs the warm domain calls it itself) would time out on tb_fuse_sense_done, and every warm-domain CSR access would hang with no ready.

Positive control: a leaf that drives the pin to 1 and requires fuse_sense_done to stay 0 while the shadow-register window still answers. It must stay in the cold domain: the eFuse controller sits under rst_primary, ahead of rst_warm, so its shadow reads through the eFuse CSR window — over the OTP JTAG AXI-Lite port or the fabric path — are the only thing that answers under bypass; nothing in the warm domain does. It needs a driven pin (a bench input in smc_tb_signal_list.svh, idle 0) in place of the constant. Closes when that leaf is enrolled, or when SEP-integrated signoff (SMU with SEP=1) is accepted as the only place the token-match path is exercised and that acceptance is recorded here.

Bench stand-ins

A stand-in is DV-owned RTL that answers in place of a product cell or an adopter block. Two sit on proof paths of this bench. Each has an inventory row, a control row, and — where the stand-in can supply a verdict — one row per enrolled leaf stating which crossing is on its proof path, what the verdict reads, and the result of the control. hw/sys/smc/dv/README.md, tb/verilator_stubs/README.md and models/README.md describe layout and enrolment and point here; the dispositions live only here.

Kinds used in the leaf tables:

  • reads the crossing — the verdict samples the stand-in’s output itself (a CSR field or a tb_top tap wired to q_o). On Verilator that value has the stand-in as its author until the pipe has filled.

  • downstream — the verdict reads product state that the DUT derives from the crossing’s output.

  • upstream — the verdict reads the near side; the crossing carries the value away and nothing behind it is read.

  • none — no prim_sync2 / prim_sync3 is on the proof path. Listed because the audit’s reset, clock and IRQ buckets signed off as a whole.

tb/verilator_stubs/prim_sync2.sv, prim_sync3.sv

hw/common/och_prim/rtl/prim_sync2.sv / prim_sync3.sv: prim_flop_2sync / prim_flop_3sync behind prim_sync_randomized_delay. RANDOM_DELAY_ENABLE is not defined on any DV build (SYNTHESIS is defined only on [targets.dual]), so prim_sync_randomized_delay passes its input through and the product cells are also a plain flop pipe; the one behaviour the stand-in adds is initial '0 on every stage, a defined 0 on the far side before the pipe has filled where the product cell shows X on a four-state simulator.

smc_sim_cfg.toml [build].stubs, emitted ahead of the Bender filelist so Verilator’s -Wno-MODDUP first-definition-wins picks them. The product cells stay in the same compile: the generated Bender filelist build/smc_bender.f ([build].bender_filelist).

Verilator and Xcelium compile them; VCS does not. The runner (tools/dv/runlib/stages.py) filters [build].stubs only when tool == "vcs": there it drops any stub whose basename the Bender graph supplies, so the VCS compile list carries no prim_sync2/3 stub and the product cells elaborate. For every other tool in smc_sim_cfg.toml tools — Verilator and Xcelium — it keeps both files and emits them ahead of the Bender filelist, so their compile lists carry the stub and the product cell together. Verilator’s -Wno-MODDUP first-definition-wins selects the stub; no Xcelium build of this bench is recorded, so which of the pair Xcelium elaborates is not established by this record.
