[[dv-runner]]
= DV and FV Runner
:imagesdir: assets

`tools/dv/run_dv.py` is the contributor-facing launcher for native OCAH
simulation and formal flows. It resolves a DUT, validates the configuration,
builds a concrete stage plan, invokes the selected backend, and writes durable
logs and schema-version-1 result files.

_Native_ means the flow is owned by this runner end to end — stage plan,
tool invocation, and results — in contrast to wrapped or external flows.

== Architecture

image::dv-runner-architecture.drawio.svg[DV/FV runner control flow,scaledwidth=95.0%]

The entry point prepares the Python environment and
then delegates command parsing and orchestration to `tools/dv/runlib/cli.py`.
The runner modules divide responsibility as follows:

[cols="<2,<4",options="header"]
|===
|Module |Responsibility

|`runlib/cli.py`
|CLI validation, DUT selection, stage planning, scheduling, and top-level
result writing.

|`runlib/config.py`
|TOML loading, strict schema checks, profile/DUT merging, test-list expansion,
target selection, and run-mode resolution.

|`runlib/stages.py`
|Backend command rendering and execution, artifact layout, timeout handling,
coverage stages, and generated replay material.

|`runlib/logparse.py`
|Structured-result and log-evidence policy used to classify simulation output.

|`runlib/results.py`
|Run, regression, per-test, and per-attempt result schemas and status rollups.

|`runlib/waves.py`
|Wave format validation, failure-window calculation, retention, viewer
commands, and same-seed replay metadata.

|`runlib/executors/`
|The executor contract (submit, poll, cancel, collect), the local executor,
the cluster executor that runs the registry's argv templates, the LSF and
Slurm dialects that read scheduler output, and the leaf manifest that
describes one attempt.

|`runlib/worker.py`
|The `--worker-manifest` entry point: one leaf attempt on a farm machine.
|===

The runner and the dashboard do not call each other. Their integration boundary
is the run-level `result.json`.

[[runner-terminology]]
== Terminology

The runner's options, messages, and result files use a small fixed vocabulary.
Every other section of this page assumes these meanings:

DUT::
The named unit under verification together with its checked-in DV environment
(`<dut>_sim_cfg.toml`, testlists, and sources). `--dut` selects one by
registry alias (`hw/common/dv/configs/duts.toml`) or by directory convention.

Flow::
One DUT resolved for one mode into a runnable configuration: simulator
defaults, the shared profile, and the DUT configuration merged together. In
JSON output the `flow` field always holds the DUT name.

Mode::
`sim` or `formal` (`--mode`). The mode chooses which DUT configuration file is
loaded and which stages are meaningful.

Profile::
A shared configuration layer under `hw/common/dv/configs/profiles/` that a
DUT selects with its `profile` key. It supplies the test framework, tool
allowlist, stage graph, scheduler policy, and defaults that individual DUTs
would otherwise repeat.

Framework::
The test framework a flow drives, for example cocotb or SystemVerilog UVM. It
is supplied by the resolved configuration and recorded as `framework` in
`result.json`.

Tool::
A simulator or formal engine registered in
`hw/common/dv/configs/simulators.toml` (for example `verilator`, `vcs`,
`xcelium`, `sby`) and selected with `--tool`. The words _backend_ and
_simulator_ in this guide refer to the same axis: "backend" names the stage
implementation that renders and executes the tool's commands.

Test::
One entry in a DUT testlist. Its `module` field names the code that
implements it. The test name is the stable identity used in results and
reruns.

Group::
A named list of tests defined in the testlist. Groups expand in definition
order. Every member must name a test defined after include expansion —
catalog loading (on every run and under `--validate-configs`) rejects an
unresolved member, naming the declaring file, the group, and the missing
test; a test may belong to any number of groups. An optional
`expected_count` pins the exact number of listed tests; catalog loading
fails when the list and the count diverge, which keeps a documented
inventory (for example a VPLAN test-case count) honest.

Tag::
A label carried by tests, used by `--tag` as an OR filter.

Expected failure::
A test whose entry carries `expect_fail = "<reason>"`: it reproduces a filed
defect and FAILS on a DUT that still carries it. The runner grades that FAIL
as PASS and an observed PASS as FAIL (<<runner-expected-failures>>).

Item::
Any name accepted by `--items`: a test name or a group name.

Catalog::
The complete set of tests, groups, and tags after loading every testlist file
referenced by the DUT configuration — "the resolved test catalog".

Target::
A named build configuration (`[targets.<name>]`): the defines and flags that
produce one distinct build image. Shared build stages run once per unique
target.

Run mode::
A named bundle of runtime arguments and timeout (`[run_modes.<name>]`)
applied to a test without changing which test runs.

Stage::
One named step of the execution plan (`flist`, `hdl_compile`, `sim`, ...). A
stage's configured `kind` selects the backend implementation that performs
it.

Leaf::
One scheduled simulation execution, identified by `(test, target, seed)`.
Scheduler mode expands the selection into leaves; `--retry` adds attempts to
a leaf without creating a new one.

Label::
The human-readable suffix of an automatically allocated run directory: the
first selected group, the single test name, `multi`, or `build`. It is
recorded in `result.json`.

Executor::
The dispatch mechanism for leaves, declared in `executors.toml` and selected
with `--executor` or the profile's `[scheduler] default_executor`. Every
executor implements the same four operations, submit, poll, cancel, and
collect, and the regression loop runs on them (<<runner-executor-registry>>).
`local` runs leaves in this process; a cluster entry names a scheduler driver,
`lsf` or `slurm`, and runs each leaf attempt as a scheduler job through the
commands the registry declares (<<runner-cluster-dispatch>>).

== Prerequisites and bootstrap

Run the launcher with Python 3:

[source,bash]
----
python3 tools/dv/run_dv.py --list
----

Before parsing the command, the launcher:

. Finds the repository root by walking upward from `run_dv.py` until it finds
  both `Bender.yml` and `pyproject.toml`.
. Exports that path as `OCH_ROOT`.
. Re-executes the command through
  `uv run --project <repo-root> --locked --group dv`.
. Synchronizes the generated `build/dv/python` namespace bridge and adds it to
  `sys.path` and `PYTHONPATH`.

The supported Python range is 3.11 through 3.13. Install
https://docs.astral.sh/uv/[`uv`] before the first run. The locked `dv`
dependency group provides cocotb and the shared Python DV packages.
<<runner-environment-matrix>> lists every other component a run needs, the
file that pins it, and the check behind it.

`OCAH_DV_SKIP_UV=1` skips only the `uv` re-execution. Use it for a
pre-provisioned CI or developer environment that already supplies the required
packages. Repository-root discovery, `OCH_ROOT`, and namespace synchronization
still occur.

`run_dv.py --worker-manifest <manifest>` is the farm worker a cluster
executor submits (<<runner-executor-registry>>). That branch neither
re-executes through `uv` nor synchronizes the bridge: it runs on the
interpreter the coordinator provisioned, attaches the bridge the coordinator
wrote, and exits `2` when that bridge is missing, so concurrent workers never
race on a shared checkout.

[WARNING]
====
The selected stage may additionally require Bender, a simulator or formal
tool, coverage utilities, `make`, a firmware toolchain, and commercial-tool
license configuration. Use `--doctor` before a real run, but note that it is a
targeted availability check rather than a complete license or toolchain test.
====

The launcher may be invoked from any working directory because repository and
checked-in paths are resolved from the script location. Relative `--run-dir`
and `--result` paths, however, are resolved from the repository root.

==== Hosted CI and a developer host

Hosted CI is the qualified environment and the most constrained one. The
composite action installs `uv` with the pinned interpreter, Bender, and
Verilator with its runtime packages, and no container engine or RISC-V
toolchain, so every hosted row names a group that needs no toolchain;
`regress.yml` states the reason beside each row that names a group other
than `all`. A developer host adds the firmware path, and each DUT's
`[c_build.*]` command owns the toolchain choice. `sep`, and `smu` through
`hw/sys/smu/dv/fw/build_firmware.py`, use the toolchain `RISCV_TOOLCHAIN`
names when that compiler accepts `--specs=picolibc.specs` and otherwise
build in the `ocah-toolchain` container through
`scripts/docker-run.sh run-here`. `smc` uses `RISCV_TOOLCHAIN` whenever it
is set and the container otherwise, and `hw/common/dv/fw/compile.mk` fails
the build when the named compiler lacks picolibc. `make` tracks source
timestamps and not toolchain identity, so after switching paths or rebuilding
the image, run `make -f ocah.mk ocah-dv-fw-clean TARGET=<block>` before the
next simulation.

The `sep` tree carries the repository's one private submodule, under
`hw/sys/sep/bootrom/prod/tools/`, and some of its test modules import it.
The hosted `sep` jobs check it out with a repository secret before the run; a
public clone runs without it, so those modules fail to import there. An
unscoped `--doctor --dut sep` imports every testlist module and exits `2` on
that account. Scope the doctor to the selection you will run:

[source,bash]
----
python3 tools/dv/run_dv.py --doctor --dut sep --items smoke
----

With `--items` or `--tag` the module probe covers the tests the same
selection names, before a run's framework-binding and `--tool` filters drop
any, and the `test modules` row names the selection.

==== Unsupported configurations

* Python 3.14 or newer. cocotb 2.0 publishes no build for it. The launcher's
  `uv run --locked` selects an interpreter inside the range; only
  `OCAH_DV_SKIP_UV=1` exposes the host interpreter, which the doctor's
  `python` row then rejects.
* Verilator older than 5.036, including the Ubuntu 24.04 package. cocotb
  documents the floor, the registry carries it as `min_version`, and the
  doctor fails the required tool below it. Build the hosted tag from source
  as the composite action does, or install a newer release.
* A `RISCV_TOOLCHAIN` whose compiler lacks picolibc. `sep` and `smu` build
  in the container instead; `smc` fails at `c_compile` with the picolibc
  error from `compile.mk`.
* VCS, Xcelium, and the SV-UVM framework views in hosted CI
  (<<runner-ci-support-matrix>>).
* Formal mode in hosted CI (<<runner-formal>>).
* Coverage collection in hosted CI: the coverage regression runs on the
  licensed simulator flow (<<runner-ci-support-matrix>>).
* Any host outside the Host row above.

== Quick start

Start with configuration and environment checks:

[source,bash]
----
python3 tools/dv/run_dv.py --list
python3 tools/dv/run_dv.py --validate-configs
python3 tools/dv/run_dv.py --doctor --dut dtp
python3 tools/dv/run_dv.py --dut dtp --items smoke --tool verilator --dry-run
python3 tools/dv/run_dv.py --dut dtp --mode formal --dry-run
----

Run one deterministic test:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut dtp \
  --items dtp_sanity_test \
  --tool verilator
----

Run a tagged local regression:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut smc \
  --tag smoke \
  --sim-jobs 4
----

Reproduce one recorded failure with the same seed:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut dtp \
  --items dtp_sanity_test \
  --stage sim \
  --seed 12345 \
  --waves fst
----

Use `--help` as the generated, source-of-truth option summary:

[source,bash]
----
python3 tools/dv/run_dv.py --help
----

== Selection model

=== DUT and tool

`--dut NAME` selects both the design and its DV environment. Resolution checks
`hw/common/dv/configs/duts.toml` first, then the bounded conventions
`hw/<name>/dv`, `hw/sys/<name>/dv`, `hw/ip/<name>/dv`,
`hw/comp/<name>/dv`, `hw/periph/<name>/dv`, and
`hw/common/prim/<name>/dv`.

Simulation mode, the default, loads `<name>_sim_cfg.toml`. Formal mode loads
the `[duts.<name>].formal_cfg` pointer of the site layer
(<<runner-site-layer>>), else the registry's `formal_cfg` override, else
`<name>_formal_cfg.toml` beside the sim config:

[source,bash]
----
python3 tools/dv/run_dv.py --dut <dut> --mode formal --items <task>
----

A selectable DUT that one of those names is also a _formal view_: `--list`
shows it as a `fv` row and `--validate-configs` validates it as
`<name> (formal)`. A site-named file that is absent leaves the view
unavailable in both listings and is an error only when selected; a registry
`formal_cfg` that is absent fails validation. A DV root that carries a formal
config and no sim config is not a DUT. <<runner-formal>> is the contributor's
route through formal mode.

`--tool TOOL` overrides the DUT's `default_tool`, but the selected tool must be
present in the flow's `tools` allowlist and in `simulators.toml`.

The shared cocotb profile allows these simulation backends:

[cols="<2,<2,<2,<3",options="header"]
|===
|Tool |Binary |Default waves |Coverage backend

|Verilator |`verilator` |FST |`verilator_coverage`
|VCS |`vcs` |VPD |URG
|Xcelium |`xrun` |SHM |IMC
|===

The shared `native-formal` profile (`kind = "fv"`, framework `formal`) lists
the open formal backend; a licensed backend reaches the runner through the
site layer:

[cols="<2,<2,<2,<5",options="header"]
|===
|Tool |Binary |License |Toolchain

|SymbiYosys |`sby` |none |Profile default and the only formal backend the
open registry names. Yosys with the yosys-slang frontend, `yosys-smtbmc`,
`yosys-abc`, and an SMT solver on the same `PATH`. The property subset and
task-file layout are in the Formal Property Style and Layout chapter of
`hw/common/dv/docs/index.adoc`; the launch shape is in
<<runner-formal-templates>> and the `sby-summary` policy grades its runs
(<<runner-formal-grading>>).
|Site-supplied backend |from its site table |per its `license_env` |A
complete `[simulators.<name>]` table in the site layer
(<<runner-site-layer>>) with `kind = "formal"`, `frameworks = ["formal"]`,
and an `argv` launch template; the runner validates it with the registry
schema and treats it exactly like a checked-in table. A DUT formal config
that lists the name in `tools` selects it; the companion repository's site
file and formal configs are the reference deployment.
|===

The profile carries `license = "none"` because the backend it lists needs no
license; `--list` marks a site-supplied backend `(licensed)` from its
`license_env`, and `--doctor` and the launcher point at that marking when
the selected backend is absent. A DUT selects a backend only through its
formal configuration (`<name>_formal_cfg.toml`).

The shared `native` profile's `uvm` framework (SystemVerilog UVM) is a
maintainer flow whose tool allowlist is VCS only; it carries
`license = "required-commercial"`, so `--list` marks it `(licensed)` and the
launcher says so when the simulator is absent. The UVM library comes from the
simulator via `-ntb_opts uvm`, tests are selected with
`+UVM_TESTNAME=<testlist module>`, and PASS/FAIL uses the `uvm-log` parse
policy (summary `UVM_ERROR`/`UVM_FATAL` counts). Xcelium and Questa are not
in the allowlist. The reference consumer is the
DTP SV-UVM smoke flow, `--dut dtp --framework uvm`. The framework's adopter
guide — conventions plus the bring-up walkthrough for adding a UVM view to a
cocotb-only DUT — is the SystemVerilog UVM Framework section of
`hw/common/dv/docs/index.adoc` (`uvm-framework.adoc`).

`--framework NAME` selects the test framework for a DUT that implements more
than one (a DUT implements a framework by declaring a `[frameworks.<name>]`
table in its sim config); without the flag the DUT's `default_framework` runs.
In this model each testlist entry is a _scenario_: a framework-neutral test
name that maps to a concrete implementation per framework. Error messages and
`--skip-unimplemented` say "scenario" with exactly this meaning; `--items`
takes the same names it always has. A scenario binds its per-framework entry
points through `module` — a bare string binds the DUT's default framework
only, a map (`module = { cocotb = "...", uvm = "..." }`) binds each framework
explicitly. A map value of `false` (`module = { cocotb = "...", uvm = false }`)
declares the scenario out of scope for that framework: group and tag
selection skips it with no flag, and the skipped names are printed and
recorded in `result.json` under `selection.skipped_excluded`. Selecting a
scenario whose map has no entry at all for the chosen framework is an error;
`--skip-unimplemented` skips group/tag-derived scenarios of that kind instead
(printed, and recorded under `selection.skipped_unimplemented`), which is the
bring-up aid while a framework port is incomplete. An explicitly named
`--items` test errors in both cases. `--list` reports the three counts per
framework (`uvm 151/153 (2 excluded)`); a nonzero `missing` count names
scenarios that have neither a binding nor a `false` for that framework.

=== Tests, groups, and tags

`--items` accepts test names and group names from the resolved test catalog.
Groups expand in definition order. Overlapping selections are de-duplicated in
first-seen order unless `--allow-duplicates` is present.

If `--items` is omitted, the runner selects the `smoke` group when it exists;
otherwise it selects the first test in the catalog.

`--tag` is repeatable and uses OR semantics across tags:

[source,bash]
----
# All tests carrying either tag.
python3 tools/dv/run_dv.py --dut dtp --tag smoke --tag ci

# Only CI-tagged tests within the smoke group.
python3 tools/dv/run_dv.py --dut dtp --items smoke --tag ci
----

With `--items`, tags filter the expanded selection. Without `--items`, tags
search the complete catalog.

[[runner-expected-failures]]
=== Expected failures

A reproducer for a filed RTL defect is only evidence while someone runs it, and
a regression that carries it is red every day it does its job. `expect_fail`
resolves that without weakening the checker:

[source,toml]
----
[[tests]]
name = "smc_gpio_irq_mask_deassert_test"
module = "smc_gpio_irq_mask_deassert_test"
run_modes = ["smoke"]
expect_fail = "#1602: clearing DATA_CTRL.interrupt_enable while a GPIO interrupt is asserted does not de-assert interrupt_o"
----

The value is the recorded reason and must be a non-empty string; `true` is
rejected, because a flag with no reason cannot say when the entry should go.
Grading applies per leaf on the `sim` and `regress` stages, after the parser
policy has classified the log:

* an observed `FAIL` is the recorded outcome and grades `PASS`, with `reason`
  `expected_fail: <reason>`;
* an observed `PASS` means the defect is gone and grades `FAIL`, in the
  `expected_fail_passed` failure bucket -- move the test into its owning
  feature testlist and drop the key;
* `ERROR`, `TIMEOUT`, and `UNKNOWN` are not the recorded failure and keep
  their status.

The parser's `FAIL` says only that the leaf failed, not why. The leaf record
therefore carries `observed_failures`: the message of every failure/error node
in the leaf's `results/results.xml` (cocotb's `error_msg`, JUnit's `message`,
or the node text), so a reader can compare what failed with the recorded
reason. To make that comparison part of the grade, add `expect_fail_match`:

[source,toml]
----
expect_fail = "#585: dead offsets wrap onto live registers with an OKAY response"
expect_fail_match = "wrap_to_live=[1-9]"
----

With it, an observed `FAIL` grades `PASS` only when some observed failure
message matches the regex (`re.search`); otherwise the leaf failed for a
different reason than the one recorded and grades `FAIL` in the
`expected_fail_mismatch` bucket, naming the first observed message. A leaf
that recorded no failure message is a mismatch too. The key requires
`expect_fail` and must compile as a Python regex.

The leaf record carries `expected_fail` (`reason`, `observed_status`,
`observed_reason`, `observed_failures`, `observed_buckets` -- the parser's
failure bucket kinds and signatures -- and `match` when set) in its metadata
and in the regression leaf summary, and the run-level `tests` summary counts
graded leaves under `expected_failing`.
The framework's own `results/results.xml` still records the observed
failure; `result.json` is the graded, authoritative result. Keep such tests
in a group of their own (for example `rtl_issue`) so they never feed a
coverage regression as passes, and so the flip is visible as that group
going red.

=== Targets and run modes

Each selected test resolves a build target from its `target` field or the DUT
default. Shared build stages run once per unique target, serially, before the
test leaves execute. This permits one group to contain tests that consume
different build images. A test `target` or a `--target` that names no
`[targets.<name>]` entry is rejected when the run plans its builds, before
any stage executes; `--validate-configs` does not check test targets
(<<runner-validation>>).

Run-mode selection uses:

[source,text]
----
--run-mode
  > the test's first run_modes entry
  > [defaults].run_mode
  > "smoke"
----

Run-mode arguments and test arguments change runtime behavior without changing
the selected test name.

Every explicit run-mode reference must name an effective `[run_modes.<name>]`
entry (profile entries deep-merge under the DUT's). An unknown `--run-mode`
fails before stage execution, and catalog loading — on every run and under
`--validate-configs` — rejects an unknown name in a test's `run_modes` list or
in `[defaults].run_mode`, reporting the declaring file and the allowed names.
Only the built-in `smoke` fallback (used when no CLI, test, or default names a
mode) is optional: a DUT that defines no `smoke` mode then runs with no
run-mode arguments or timeout.

== Configuration and precedence

Configuration ownership is split:

[cols="<3,<4",options="header"]
|===
|Path |Owns

|`hw/common/dv/configs/duts.toml`
|Explicit DUT aliases and config-path overrides.

|`hw/common/dv/configs/profiles/*.toml`
|Shared framework, tool allowlist, scheduler policy, defaults, and stage graph.

|`hw/common/dv/configs/simulators.toml`
|Tool binaries, capabilities, wave formats, parser extensions, common
build/coverage defaults, and formal launch templates.

|`hw/common/dv/configs/executors.toml`
|Executor declarations: the `local` executor, and cluster entries that name a
scheduler driver (<<runner-executor-registry>>).

|`hw/common/dv/configs/site.local.toml` (git-ignored), or the file `OCAH_DV_SITE` names
|One deployment's tool binaries, launcher prefixes, environment hooks, added
tool tables, and companion-owned formal config pointers, merged over the two
registries above. See <<runner-site-layer>>.

|`hw/common/dv/configs/parsers.toml`
|Shared positive-evidence and failure-detection policies for simulation
logs, and the `grader = "formal"` policies that grade formal tasks.

|`<dut-dv-root>/<dut>_sim_cfg.toml`
|DUT identity, profile selection, test-list pointer, source/build intent,
targets, modes, and DUT-specific overrides.

|`<dut-dv-root>/testlists/*.toml`
|Tests, groups, tags, targets, seeds, reseed counts, timeouts, runtime
arguments, optional firmware metadata, and `expect_fail` /
`expect_fail_match` entries.

|`<dut-dv-root>/cov/config/<tool>/coverage_policy.toml`
|Optional detailed coverage thresholds, exclusions, and hole dispositions;
`--waive` re-applies it to a finished run.
|===

The broad merge order reported by `--dry-run` is:

[source,text]
----
simulator defaults < shared profile < DUT configuration < supported CLI overrides
----

Some domains have more specific rules:

* Single-test seed: `--seed` > test seed > `[defaults].seed` > `1`.
* Simulation-leaf timeout: `--timeout` > test `timeout_sec` > run-mode
  `timeout_sec` > `[defaults].timeout_sec`.
* Runtime arguments append in order: profile/DUT `[sim].args`, run-mode
  `args`, test `args`, then CLI `--sim-arg` and `--plusarg`; with `--cov`,
  the tool's `[coverage.<tool>]` `sim_args` and `test_args` follow. Run-mode
  and test `args` are rendered with `{seed}` and `{repo_root}`; the other
  lists stay literal. Across those two lists a later scalar `+key=value`
  replaces an earlier one with the same key, so a test entry overrides its
  run mode, and each dropped argument is printed as `PLUSARG: dropping ...`.
  Bare flags and `+uvm_set_*` arguments are never collapsed.
* Regression multiplicity: a test's `reseed` value overrides `--reseed` for
  that test.
* A positive `[build.options].build_jobs` value overrides CLI-derived
  build concurrency; otherwise `--build-jobs`, then `--sim-jobs`, supplies it.

CLI overrides are curated rather than arbitrary TOML replacement. Stable
settings belong in checked-in configuration; pass-through flags are intended
for one-off debugging.

[[runner-rejected-keys]]
=== Schema versions and rejected keys

The registries, each `<dut>_sim_cfg.toml`, and each testlist carry
`schema_version = 1`; the profiles carry none. The loader accepts the key
wherever it appears and enforces its value on the site file
(<<runner-site-layer>>). An unknown key anywhere in a configuration, a
misspelling included, is an error naming the file and the table.

A setting has one spelling. A key in the left column below, and a key that
duplicates a setting another table owns, is an error rather than an alias,
reported as `deprecated duplicate-purpose config` together with the key to
use:

[cols="<3,<3",options="header"]
|===
|Rejected |Use instead

|`[defaults].tool`
|top-level `default_tool`

|`[run_modes.<name>].tags`
|testlist `tags`

|`[build.options].ccache`, `[build.options].output_split`
|`[build.verilator].ccache`, `[build.verilator].output_split`

|`[targets.<name>].verilator_flags`, `.xcelium_flags`, `.vcs_flags`, and the
same keys under `[target_defaults.<name>]`
|`[targets.<name>.tools.<tool>].flags`

|`[build.<tool>].extra_build_args`
|`[build.<tool>].extra_args`

|`[coverage.<tool>].<tool>_build_args`, `_compile_args`, `_sim_args`,
`_test_args`, and the fixed names `verilator_build_args`,
`xcelium_build_args`, `xcelium_test_args`, `vcs_compile_args`, and
`vcs_sim_args` in any tool's table
|`[coverage.<tool>].build_args`, `compile_args`, `sim_args`, `test_args`

|A `[build.<tool>]` or `[coverage.<tool>]` value equal to that tool's
`simulators.toml` default
|Omit the key; the default applies
|===

`--stage filelist` is the only alias the command line accepts; it selects
`flist`.

[[runner-validation]]
=== What validation checks

`--validate-configs`, and every run before it resolves the requested DUT,
validates each selectable DUT's views in this order. The first failure names
the file and the table or entry:

. The DUT DV root exists, and every tool in the flow's `tools` list is in
  the merged registry and supports the selected framework.
. Every `[native.stages.<name>]` names a canonical stage and carries a
  `kind` that stage accepts.
. Every table of the sim config holds only the keys its schema allows, and
  every `{placeholder}` in a value is one the consuming stage defines.
. `[testlist].path` is relative, resolves inside the DUT DV root, and exists.
. Each `[coverage.<tool>]` table is well formed and each coverage policy
  file loads; a lapsed waiver is a warning, not a failure.
. The scheduler's default and allowed executors are registered.
. No key from the rejected-key table is present (<<runner-rejected-keys>>).
. The test catalog loads after include expansion: each test's `run_modes`
  and `tools` name declared entries, each scenario binds or excludes every
  framework the DUT implements, `firmware` is a string or a table,
  `expect_fail` carries a reason, every group member names a test, and each
  `expected_count` matches its list.
. The flow's parser policy extensions are registered.

Validation proves configuration consistency. It does not probe a tool or a
license (`--doctor` does), it does not check test `target` references (the
run does, when it plans its builds), and it does not check that a firmware
name builds: the `c_compile` stage rejects a test whose `firmware` names no
`[c_build.<mode>]` template, dry run included, and the build tool reports a
target the template cannot build.

[[runner-formal-templates]]
=== Formal launch templates

A formal backend is launched from an `argv` template. The registry entry of
every `kind = "formal"` tool carries one, and an app table
(`[formal.apps.<app>.<tool>]` in the DUT's formal configuration) may set its
own `argv` in its place. The app table also supplies `cwd` (the launch
directory, repo- or DUT-relative, default `.`), `script` (the tool script,
passed as written), and `args` (tokens spliced at `{args}`). A formal test
item's `module` names the app; `--app` overrides it.

A template is an array of strings. Each string renders these placeholders:

[cols="<2,<5",options="header"]
|===
|Placeholder |Value

|`{binary}` |The tool's registry `binary`.
|`{script}` |The app's `script`, as written. A template that uses it fails
when the app sets none.
|`{cwd}` |The resolved launch directory.
|`{run_dir}` |The run directory.
|`{item}` |The formal test item being run.
|`{args}` |The app's `args`, spliced in place. The placeholder is an element
on its own.
|`{formal_args}` |Every `--formal-arg` value, spliced in place. The
placeholder is an element on its own.
|`{proof_depth}` |The `--proof-depth` value. The placeholder sits inside an
optional group.
|===

A nested array is an optional group: it renders whole when `--proof-depth` is
given and is dropped otherwise, so a two-token flag stays intact.

[source,toml]
----
[formal.apps.tap_fpv.sby]
cwd = "formal/fpv/sby"
script = "dtp.sby"
args = ["tap_bmc", "tap_cover"]

[formal.apps.tap_fpv.<tool>]
argv = ["{binary}", ["-depth", "{proof_depth}"], "{script}", "{formal_args}"]
----

`--validate-configs` rejects a template that names an unknown placeholder,
embeds a list placeholder in a longer string or in a group, places an
optional placeholder outside a group, or is empty. A run rejects
`--proof-depth` or `--formal-arg` when the selected template has no
`{proof_depth}` or `{formal_args}` placeholder to carry it. `--dry-run`
prints the rendered command on the `CMD  :` line.

The SymbiYosys registry template is:

[source,toml]
----
argv = ["{binary}", "-f", "--prefix", "{run_dir}/stages/formal/{item}", "{script}", "{args}", "{formal_args}"]
----

sby resolves the task file's `[files]` entries against its working
directory, so the app's `cwd` is the directory holding the task file. Each
task's work directory lands under the run's formal stage directory as
`<item>_<task>`, and the app's `args` name the tasks to run. sby takes its
depth from the task file, so its template has no `{proof_depth}` group. A
site-supplied backend carries its template in its site tool table, where the
generic shape `{binary} {args} {script} {formal_args}` suits a Tcl-driven
tool; an app-table `argv` overrides it for one app.

[[runner-formal-grading]]
=== Formal result grading

A formal backend's exit code is not evidence: batch tools exit zero with
failed or inconclusive properties, and SymbiYosys encodes only the match
against each task's `expect` option. The `formal` stage grades an item from
what the backend wrote, through one of two sources.

*Task status lines.* The tool's registry entry names a `parser_policy` whose
`parsers.toml` table carries `grader = "formal"`. Its `task_status_patterns`
match one line per finished task in the stage log, with a `(?P<status>...)`
group and optional `(?P<workdir>...)` and `(?P<rc>...)` groups. Each task's
work directory supplies the `status` file, the task `mode` from
`config.sby`, and, with `task_results = "sby-junit"`, the JUnit report whose
`ASSERT` and `COVER` test cases are counted per property. Work directories
under the stage directory named `<item>` or `<item>_<task>` are read even
when the log carries no status line. `evidence_patterns` copy matching log
lines into `parser.evidence`; a `hard_fail_patterns` match grades the item
`ERROR`. The `sby` entry names `sby-summary`.

*Summary file.* An app table sets `[formal.apps.<app>.<tool>.evidence]` for
a backend without a native task summary. `summary` names the file the tool
script writes; it renders `{run_dir}`, `{item}`, and `{cwd}`, and a relative
path resolves against the app's `cwd`. `pass_patterns` and `fail_patterns`
are required; `inconclusive_patterns`, `cover_patterns`, and
`unreached_patterns` are optional. Every matching line feeds the property
counter of its list. The `evidence` table wins over the tool's
`parser_policy`, and `--validate-configs` rejects an app backend that has
neither.

[source,toml]
----
[formal.apps.conn.<tool>]
script = "run_conn.tcl"

[formal.apps.conn.<tool>.evidence]
summary = "{run_dir}/stages/formal/{item}/summary.txt"
pass_patterns = ["^\\S+ proven$", "^\\S+ covered$"]
fail_patterns = ["^\\S+ cex$"]
inconclusive_patterns = ["^\\S+ undetermined$"]
cover_patterns = ["^\\S+ covered$"]
unreached_patterns = ["^\\S+ unreachable$"]
----

The item status is the worst task status in the order
`ERROR > TIMEOUT > FAIL > UNKNOWN > PASS`, and then:

* an unreached cover statement is `FAIL`, whatever the task status says;
* no task status line, status file, or summary file is `UNKNOWN`;
* an inconclusive summary line is `UNKNOWN`;
* a non-zero exit code beside passing evidence is `UNKNOWN`.

`FAIL` lands in the `formal_fail` failure bucket; `ERROR`, `TIMEOUT`, and
`UNKNOWN` use `tool_error`, `timeout`, and `unknown`. Every executed formal
item counts as one item in `tests`.

Property totals count each property once across tasks: an assertion is
`failed` if any task failed it, else `inconclusive` if any task left it open
(an induction counterexample inside an `UNKNOWN` task is inconclusive), else
`proven`; a cover statement is `covered` if a cover task reached it, else
`unreached`. A task counts only the property kind its mode checks. The
stage record and the leaf `result.json` carry the totals and the task list in
a `formal` object:

[source,json]
----
"formal": {
  "grader": "sby-summary",
  "tasks": [
    {"name": "tap_bmc", "mode": "bmc", "status": "PASS", "return_code": 0,
     "workdir": "hw/sys/dtp/dv/build/runs/<run>/stages/formal/dtp_tap_fpv_tap_bmc",
     "proven": 11, "failed": 0, "inconclusive": 0, "covered": 0, "unreached": 0}
  ],
  "proven": 11, "failed": 0, "inconclusive": 0, "covered": 6, "unreached": 0
}
----

The run-level `result.json` and `regression.json` of a formal run sum the
counters over their items and add task totals:

[source,json]
----
"formal": {
  "proven": 11, "failed": 0, "inconclusive": 0, "covered": 6, "unreached": 0,
  "tasks": {"total": 3, "passing": 3, "failing": 0}
}
----

The `formal` object is additive: no simulation key changes, `tests` keeps
its item-status meaning, and `coverage` keeps its simulation meaning.

=== Adopter overlay layer

`--overlay <path>` (or the `OCAH_DV_OVERLAY` environment variable; the flag
wins) applies one adopter-owned TOML file on top of the merged DUT view. It
is the runner-side equivalent of `ocah.mk`'s adopter include hooks
(`-include nonfree/nonfree.mk`, `OCAH_ADOPTER_OVERLAY_MK`): an adopter — for
example a commercial-VIP integration living outside this tree — extends a
build without editing checked-in configs. The layer is *never*
auto-activated: the presence of an adopter checkout changes nothing until a
run names the overlay explicitly.

The overlay grammar is a restricted subset of the sim-config grammar, and
every allowed key is *append-only* — an overlay can add to the merged view
but can never replace or remove what the checked-in configs declare, so a
run with an overlay differs from the baseline only by the overlay's own
additions:

[cols="<2,<1,<3",options="header"]
|===
|Key |Merge |Purpose

|`description`
|—
|Free-form; what this overlay integrates.

|`frameworks = ["uvm", ...]`
|guard
|Optional compatibility guard. Selecting a framework outside the list is a
hard error on the run path; `--validate-configs` validates non-listed views
without the overlay and labels them `[overlay skipped: frameworks guard]`.

|`[build]` `incdirs` / `sources` / `source_lists`
|`$VAR` expansion, then dedup-append after the DUT's own entries
|Extra compile inputs. `$VAR` / `+${VAR}+` in an entry expands from the process
environment at config load; an unset variable is a hard config error naming
the variable and the overlay file. An overlay-supplied `source_lists`
manifest expands exactly like a DUT-owned one (component entries ahead of DUT
sources), so a vendor package can own its manifest the way the shipped VIPs do.

|`[target_defaults.<t>]` / `[targets.<t>]` `defines` / `flags`,
`[...tools.<tool>].flags`
|dedup-append (tables created when absent)
|Gate defines (e.g. `OCAH_AXI_VENDOR_IF`) and the extra tool flags the vendor
package needs.

|`[sim].args`
|append after the merged `[sim].args`
|Runtime args, e.g. the commercial-VIP factory override
`+uvm_set_type_override=ocah_axi_master_env,<vendor>_axi_env` — run-mode,
test, and CLI args still append after it.

|`[env]` `NAME = "value"`
|applied to the runner's process environment at run start; an overlay value
replaces an ambient one
|Runtime environment the vendor package needs, e.g. the install-root
variable a commercial VIP refuses to start without. Values are literal
strings. Every build and sim subprocess, stage `env/` snapshot, and
in-process tool runner inherits the table; `--validate-configs` and `--list`
accept it without applying it.
|===

Merge position: after the profile/DUT `[frameworks.<fw>]` merge (the overlay
extends the selected view) and before `[build].source_lists` expansion. Any
other key is rejected, as are `adopter_overlay` and `adopter_overlay_env`
appearing in a sim config or profile (the recorded keys are reserved for the
runner). Application is deterministic and repeatable: list order is
preserved, the dedup rules make re-application a no-op, and the applied path
and `[env]` table are recorded as `overlay` and `overlay_env` in
`result.json` so a result is attributable to its exact config layers.

A typical commercial-VIP overlay:

[source,toml]
----
description = "Vendor AXI VIP integration for ocah_axi_vip consumers"
frameworks = ["uvm"]

[build]
incdirs = [
  "hw/common/dv/vip/axi/uvm",                   # supplies ocah_axi_vendor_if.svh
  "$VENDOR_VIP_HOME/include",                   # headers inside the vendor install
]
source_lists = ["hw/common/dv/vip/axi/uvm/sources.toml"]

[target_defaults.default]
defines = ["OCAH_AXI_VENDOR_IF"]

[sim]
args = ["+uvm_set_type_override=ocah_axi_master_env,vendor_ocah_axi_env"]

[env]
VENDOR_VIP_HOME = "/opt/vendor/vip"             # the install root the VIP starts from
----

Paths resolve repo-relative inside the checkout the overlay extends, or
absolute. `$VAR` and `+${VAR}+` in the overlay's own `[build]` entries expand
at config load from the environment of the `run_dv.py` process with the
overlay's `[env]` table applied on top, so the emitted filelist carries the
expanded path and one overlay file serves every site, whether the site
exports the variable or the overlay declares it. An unset variable is a hard config error
naming the variable and the overlay file; `--validate-configs` reports it as
`FAIL` on each view the overlay targets. Expansion covers only the overlay's
own entries: the paths listed inside a `source_lists` manifest and every
checked-in config stay literal, repo-relative or absolute.

The `[env]` table reaches the stages through the runner's own process
environment: the run path applies it once, before the tool probes and the
first stage, and every build and sim subprocess, stage `env/` snapshot, and
in-process tool runner copies that environment. An overlay value replaces an
ambient one, so the `overlay_env` recorded in `result.json` is exactly the
environment the run saw; export the variable in the shell instead when the
site, not the overlay, should decide its value. The run log lists the
applied pairs on a `config overlay_env=...` line. The
`OCAH_<PROTO>_VENDOR_IF` defines activate the guarded
`+"`include`"+` hooks inside the shipped `ocah_<proto>_if` interfaces, which
pull `ocah_<proto>_vendor_if.svh` from an overlay incdir — the OSS tree
ships no copy of those files.

[[runner-site-layer]]
=== Site-local override layer

The checked-in registries name each tool by its default executable and find
it on `PATH`. A deployment whose tools carry other names, need an environment
hook before they start, or run inside a container describes that in one
git-ignored file, `hw/common/dv/configs/site.local.toml`, or in the file the
`OCAH_DV_SITE` environment variable names (the variable wins). The layer is
active exactly when one of those files exists; a companion checkout beside
the tree changes nothing. `site.local.example.toml` in the same directory is
a template to copy.

The file merges over `simulators.toml` and `executors.toml` before any
command reads them, so `--validate-configs`, `--doctor`, `--dry-run`, and the
run path resolve one merged registry, for simulation and formal tools alike:

[cols="<2,<1,<3",options="header"]
|===
|Key |Merge |Purpose

|`[simulators.<tool>]` `binary`
|replaces
|The executable to run, found on `PATH` after `setup_hook` has been sourced.

|`[simulators.<tool>]` `launcher = ["podman", "exec", "-i", "eda"]`
|replaces
|An argv prefix in front of every command of the tool: the container case.
`--doctor` and the run-path probe check the prefix's first token on `PATH`,
because the tool itself lives behind it.

|`[simulators.<tool>]` `argv`
|replaces
|A formal launch template (<<runner-formal-templates>>) for a formal tool;
rejected on a simulation tool.

|`[simulators.<tool>]` `license_env`
|replaces
|The license variables `--list`, `--doctor`, and the launcher hint consult.

|`[simulators.<tool>]` `extra_env = { NAME = "value" }`
|replaces
|Variables added to the tool's process environment.

|`[simulators.<tool>]` `setup_hook = "path"`
|replaces
|A shell file `bash` sources once per run before the tool's first command;
the variables it exports, changes, or unsets apply to every command of the
tool. A relative path resolves against the site file; the file must exist.

|`[simulators.<new-tool>]` (complete table)
|adds
|A tool the checked-in registry lacks. The registry schema validates it
(`kind`, `frameworks`, `license_env`, `min_version` when present, and `argv`
for a formal tool); a DUT
selects it through its config's `tools` and `default_tool`.

|`[executors.<name>]` any data key (`driver`, `binaries`, the argv
templates, `defaults`, `limits`, `env_passthrough`, `history_parser`,
`setup_hook`), or a complete table
|replaces / adds
|The same over `executors.toml` (<<runner-executor-registry>>); `kind` stays
with the registry. `setup_hook` is site-only and resolves against the site
file.

|`[duts.<dut>]` `formal_cfg = "path"`
|replaces
|The formal config `--mode formal` loads for that DUT, ahead of the
registry's `formal_cfg` and the `<name>_formal_cfg.toml` convention: how a
companion-owned formal view is reached without editing `duts.toml`. The DUT
must be selectable; the path is repo-relative or absolute. An absent file
leaves the view `unavailable` in `--list` and `--validate-configs` and is an
error only when the DUT is selected with `--mode formal`.
|===

Any other key fails validation, as does a checked-in registry that carries
`launcher`, `extra_env`, or `setup_hook`. Inside one command the stage's own
variables (`PYTHONPATH`, `RANDOM_SEED`, the coverage and wave knobs) keep
their values; below them the `setup_hook` exports win over `extra_env`,
which wins over the ambient environment. The stage's `env/` snapshot records
the result.

Where the keys reach:

* Every stage rendered from argv — the formal launch, the SV-UVM `vlogan`,
  `vcs`, and `simv` adapters, the Xcelium adapters, the standalone Verilator
  compile, and the coverage merge and report commands — runs
  `launcher + command` with the merged environment and `binary` in place of
  the tool's own executable.
* The cocotb path (`cocotb_build`, `cocotb_sim`) honours `binary`,
  `extra_env`, and `setup_hook`: cocotb's Python runner probes and spells the
  simulator executable itself, and the runner substitutes `binary` through
  the same command hook it uses for the Verilator public scope. A `launcher`
  on a tool used through cocotb is a hard error, because that runner starts
  the simulator from the `run_dv.py` process; run `run_dv.py` inside the
  container instead.

`--doctor` prints the active site file on its `site` line and a `source`
column per tool (`simulators.toml`, `simulators.toml + <site> (binary,
launcher)`, or `<site> (added)`); it sources the tool's `setup_hook` and
reports a failing hook on the tool's row. `--validate-configs` reports the
merged registries on a `site layer` line and never runs a hook. The run log
carries a `config site=...` line, and `result.json` records the file under
`site`.

A container deployment:

[source,toml]
----
schema_version = 1

[simulators.vcs]
launcher = ["podman", "exec", "-i", "-w", "/work", "eda"]
license_env = ["SNPSLMD_LICENSE_FILE"]
extra_env = { VCS_HOME = "/opt/vcs" }

[simulators.sby]
launcher = ["podman", "exec", "-i", "-w", "/work", "eda"]
----

The container sees the checkout and the run directory at the same paths as
the host, so the rendered command, the replay script under `scripts/`, and
the paths the tool prints hold on both sides. `--doctor --tool vcs` then
checks `podman`, not `vcs`.

[[runner-executor-registry]]
=== Executor registry

`hw/common/dv/configs/executors.toml` declares where leaves run. Every entry
implements the same four operations behind the regression loop: submit an
attempt, poll its state, cancel it, and collect its result. The loop never
takes a verdict from the executor; the leaf's own `result.json` grades it, and
an attempt that ends without one grades `ERROR` with a reason that starts with
`environment_error`.

[cols="<2,<1,<4",options="header"]
|===
|Key |Kind |Meaning

|`kind = "local"`
|both
|Leaves run in this process. `submit_argv = []` and `wait_mode = "inline"`
are its only other keys. At `--sim-jobs 1` an attempt runs on the calling
thread; above that, a thread pool of that size runs them.

|`kind = "cluster"`, `driver`
|cluster
|A scheduler driver, `lsf` or `slurm`. The entry validates and appears in
`--doctor`; selecting an entry whose driver the runner has no dialect for, or
whose `history_parser` that dialect does not implement, is a configuration
error.

|`binaries`
|cluster
|Every scheduler command the driver runs. `--doctor` looks each one up on
`PATH` after sourcing `setup_hook`, and a missing one on the executor a run
would select fails the doctor.

|`submit_argv`, `query_argv`, `cancel_argv` (required); `history_argv`,
`worker_argv`
|cluster
|Argv templates. A string element renders its `{placeholders}`; a nested list
is an optional group that renders whole when every placeholder in it has a
value and is dropped otherwise, so `["-q", "{queue}"]` costs nothing when no
queue is set. `{job_ids_argv}` splices one token per job id.

|`defaults`
|cluster
|The normalized resource vocabulary: `queue`, `cores`, `mem_mb`, `walltime`.
`--queue`, `--cores`, `--mem-mb`, and `--walltime` win over a stage's
`resources` table in the DUT config, which wins over these.

|`limits`
|cluster
|Coordinator knobs, with the value an unset key takes in parentheses:
`max_in_flight` (unbounded), `submit_batch_size` (25), `query_batch_size`
(100), `poll_interval_sec` (10), `artifact_grace_sec` (60), `cancel_grace_sec`
(30), `command_timeout_sec` (120), `array_chunk_size` (100).
<<runner-cluster-dispatch>> says what each one bounds.

|`arrays`
|cluster
|`true` submits the first attempts of a stage as job arrays of at most
`array_chunk_size` elements; `false` submits one job per attempt. The
checked-in `lsf` and `slurm` entries set it to `true`; a site turns it off in
its own table. An executor whose templates cannot carry an array (a Slurm
`submit_argv` without `{array_range}`, an LSF `query_argv` without `jobindex`)
submits plain jobs and says so in the executor log.

|`env_passthrough`, `history_parser`, `description`
|cluster
|Variables whose values at submission the job script exports before the
worker starts; the named parser for `history_argv` output (`lsf_bhist_long`
for LSF; `slurm_sacct` or `slurm_scontrol` for Slurm); a free-text note.

|`setup_hook`
|cluster, site layer only
|A shell file sourced before every scheduler command, relative to the site
file.
|===

[cols="<2,<4",options="header"]
|===
|Template |Placeholders

|`submit_argv`
|`{queue}` `{cores}` `{mem_mb}` `{mem_gb}` `{walltime}` `{walltime_sec}`
`{walltime_min}` `{walltime_hms}` `{jobname}` `{joblog}` `{image}` `{script}`
`{manifest}` `{python}` `{run_dir}` `{repo_root}` `{leaf_dir}` `{task_id}`
`{executor}` `{array_range}` (set only on an array submission, as `1-N`; the
LSF job name carries the range instead)

|`query_argv`, `history_argv`, `cancel_argv`
|`{job_id}` `{job_ids_csv}` `{job_ids_argv}`

|`worker_argv`
|`{python}` `{manifest}` `{repo_root}` `{run_dir}` `{leaf_dir}` `{task_id}`
|===

A wall time is written as minutes (`90`), with a unit suffix (`90m`, `2h`),
or as a clock (`HH:MM`, `HH:MM:SS`, `D-HH:MM:SS`); the template picks the
rendering its scheduler expects, so one request serves a scheduler that
counts minutes and one that wants a clock. Memory is requested in megabytes
and also renders as whole gigabytes, rounded up, for a scheduler whose unit is
the gigabyte.

The registry's LSF entry, with the values a site adds through
`site.local.toml`:

[source,toml]
----
[executors.lsf]
kind = "cluster"
driver = "lsf"
binaries = ["bsub", "bjobs", "bhist", "bkill"]
submit_argv = [
  "bsub", ["-q", "{queue}"], ["-n", "{cores}"], ["-R", "rusage[mem={mem_gb}]"],
  ["-W", "{walltime_min}"], "-J", "{jobname}", "-o", "{joblog}", "{script}",
]
query_argv = ["bjobs", "-json", "-o", "jobid jobindex stat exit_code exit_reason", "{job_ids_argv}"]
history_argv = ["bhist", "-l", "{job_ids_argv}"]
cancel_argv = ["bkill", "{job_ids_argv}"]
history_parser = "lsf_bhist_long"
env_passthrough = ["PATH", "LD_LIBRARY_PATH"]
arrays = true
defaults = { queue = "regress", cores = 1, mem_mb = 20480, walltime = "02:00" }
setup_hook = "lsf.env"

[executors.lsf.limits]
max_in_flight = 200
poll_interval_sec = 30
----

The checked-in registry is schema 2: the `local` entry plus generic `lsf`
and `slurm` tables built from each scheduler's stock flags, carrying no site
value. A site layer supplies the site's queue names, resource defaults,
limits and `setup_hook`, replaces a template whose unit or flag differs at
that site (an LSF cluster that counts memory in gigabytes renders
`{mem_gb}`), or adds an executor the registry lacks.

[[runner-cluster-dispatch]]
==== Cluster dispatch

A run selects a cluster executor with `--executor`, and the flow's
`[scheduler] allowed` list must name it: the shared native profile allows
`local`, `lsf` and `slurm`, the formal profile `local` only. `--sim-jobs` is
then the number of attempts queued or running at once, bounded by the
executor's `limits.max_in_flight`; the coordinator submits at most
`submit_batch_size` attempts between two polls and asks about at most
`query_batch_size` job ids per query command. A dry run submits nothing.
The target build runs on the submitting host before the first submission,
so an omitted `--build-jobs` derives from `--sim-jobs` capped at that host's
CPU count.

Every attempt is one job. The coordinator writes the leaf manifest, then a job
script at `<run>/stages/regress/scripts/<task>.sh` that exports the
`env_passthrough` values, changes to the checkout, and execs `worker_argv`
(`run_dv.py --worker-manifest <manifest>` unless the registry says otherwise),
and renders `submit_argv` with that script as `{script}`,
`<run>/stages/regress/logs/<task>.log` as `{joblog}`, and
`ocah.<run>.<task>` as `{jobname}`. Every scheduler command the executor runs,
with its status and output, is appended to
`<run>/stages/regress/logs/executor.log`; a leaf graded from a job carries the
job id and final scheduler state under `metadata.scheduler` and its job log
under `artifacts.executor_log`.

With `arrays = true` the first attempts the coordinator submits in one turn go
out as one job array per chunk of at most `array_chunk_size` attempts, bounded
by the in-flight cap. The chunk has one script,
`<run>/stages/regress/scripts/<stage>-arr<N>.sh`, which reads its element
index from the scheduler (`LSB_JOBINDEX`, `SLURM_ARRAY_TASK_ID`) and picks its
task from the sibling `<stage>-arr<N>.tasks` list, one
`task<TAB>manifest<TAB>leaf directory` line per element; its job name is
`ocah.<run>.<stage>-arr<N>` (`[1-N]` appended on LSF), its `{array_range}` is
`1-N`, and its `{joblog}` carries the scheduler's index token (`%I`, `%a`) so
every element logs to `<run>/stages/regress/logs/<stage>-arr<N>.<index>.log`.
From then on each element is its own job to every command, under the
scheduler's element id (`1001[3]` on LSF, `1001_3` on Slurm): polling,
history, cancellation and collection treat it exactly like a plain job, and a
leaf graded from an element also carries `array_job_id` and `array_task_id`
under `metadata.scheduler`. A `--retry` attempt and a `--waves-on-fail` rerun
are plain jobs. An array the scheduler refuses grades every element `ERROR`
(`environment_error`) and counts as one refused submission.

The scheduler decides only whether an attempt is over. Each poll maps the
driver's native states onto one lifecycle:

[cols="<2,<5",options="header"]
|===
|State |Meaning, and the leaf's grade when the job left no `result.json`

|`QUEUED`, `RUNNING`, `SUSPENDED`
|Live in the scheduler. `SUSPENDED` waits like `RUNNING`.

|`RECONCILING`
|Missing from the live query, or reported finished before its `result.json`
is visible. The completion record and `result.json` settle it first, then
`history_argv`, and `artifact_grace_sec` without either ends the wait: a
finished job grades `ERROR` (`environment_error`), a missing one is `LOST`.

|`SUCCEEDED`, `FAILED`
|The job ran to its end. The leaf's own `result.json` grades it, with the
exit code recovered from the query or the completion record when the
scheduler reports none; no `result.json` within the grace is `ERROR`
(`environment_error`).

|`TIMED_OUT`
|The scheduler's wall time expired: `TIMEOUT`, with the job log as the
leaf's log.

|`CANCELLED`
|Stopped by this run's cancellation: an interrupted leaf, as in a local run.

|`PREEMPTED`, `LOST`
|Preempted, requeued, or gone without a record: `ERROR`
(`environment_error`), which `--retry` reruns as a new attempt.
|===

A query that fails, or hangs past `command_timeout_sec`, leaves every asked
job in its previous state and doubles the next wait, up to eight times
`poll_interval_sec`; five consecutive failed queries, or three consecutive
refused submissions, abort the run, which cancels its jobs and writes the
interrupted summary with `interruption.kind = "executor"` and exit status
`2`. A single refused submission grades that attempt `ERROR`. On
interruption the coordinator renders `cancel_argv` for the run's own job ids
only, then confirms each within `cancel_grace_sec` by query; a job the
scheduler reports finished counts as confirmed, and the ids it does not know
or does not confirm are written to
`<run>/stages/regress/jobs/cancel-unconfirmed.json` for the operator and
repeated, with their leaves, under `interruption.cancellation` in the
interrupted summary. A second signal during that wait ends it; the summary
is written either way (<<runner-interrupted-checkpoints>>). A `--retry`
attempt and a `--waves-on-fail` rerun are each their own job, submitted
when the attempt they follow has been collected.

`tools/dv/tests/test_cluster_executor.py` drives both drivers through
`tools/dv/tests/fake_scheduler.py`, which answers
with the output shapes the production schedulers print, including a
submission filter's stderr banner in both its shapes, with and without a
memory request, the `ERROR` record `bjobs -json` returns
for an unknown id, `bkill`'s status 255 for a finished job, `squeue`'s
failure for an id the controller dropped, and `scancel`'s success for any id.
The `slurm-qualify` workflow, run by hand, then puts the Slurm driver against
a live scheduler: a single-node Slurm with accounting that the job installs on
the hosted runner, submitting the selected tests as jobs of the runner itself
(<<runner-ci>>). The LSF driver's live qualification runs on the maintainer
farm outside hosted CI. The state maps and parsers live in
`runlib/executors/lsf.py` and `runlib/executors/slurm.py`.

==== Leaf manifests and the worker

A cluster driver runs each attempt through `run_dv.py --worker-manifest
<run>/stages/regress/jobs/<task>.json`, a JSON brief the coordinator writes
per attempt: DUT, framework, tool, stage, item, seed, attempt, the run and leaf
directories, the resource request, and the command line the coordinator ran
with. Its `plan_digest` covers every other key, so an edited manifest is
refused, and the only command-line attributes a manifest may override are the
wave and console options a debug rerun changes. The worker verifies the digest,
the checkout, and the run tree, reloads the configuration from the tree, runs
exactly one stage, writes the leaf's `result.json` and a `<task>.done.json`
completion record beside the manifest, and exits with the leaf's status code.
A manifest that cannot be trusted or run leaves an `ERROR` result whose reason
starts with `environment_error` and exits `2`. Workers write nothing else: the
coordinator is the single writer of every aggregate in the run tree.

[[runner-formal]]
== Formal verification

Formal mode runs a property set through the same runner as a simulation:
`--mode formal` selects a DUT's formal view, an item names an app, the app
names the backend's script, and the runner renders one command, runs it, and
grades the evidence the backend wrote into `result.json`. This chapter is the
contributor's route through the pieces the reference sections define: the
toolchain, a local run and a container run, the property style, the
configuration a formal view needs, how a result is read, and where
licensed-backend collateral lives. `hw/sys/dtp/dv/` is the reference
implementation, the DTP TAP controller proven with SymbiYosys; its plan
section is "Formal Verification Plan" in `hw/sys/dtp/dv/docs/DTP_VPLAN.adoc`.
Hosted CI runs no formal job and no formal result reaches the dashboard:
formal mode is a developer-host flow (<<runner-ci-support-matrix>>).

[[runner-formal-toolchain]]
=== Toolchain

The open path is SymbiYosys (`sby`) driving Yosys with the yosys-slang
frontend, `yosys-smtbmc`, `yosys-abc`, and an SMT solver, with `bender` for
the filelist. The frontend must be a yosys-slang build that carries the
concurrent-assertion lowering (releases from 2026-05 on); the `cover` task
needs the SMT solver the task file names (`yices` in the DTP task file), and
`abc pdr` needs none. `--doctor` probes `sby` alone, so the other tools must
share its `PATH`:

[source,bash]
----
python3 tools/dv/run_dv.py --doctor --dut dtp --mode formal
----

The Open-path toolchain section of the Formal Property Style and Layout
chapter (`hw/common/dv/docs/index.adoc`) is the authority for the frontend
and solver requirements; a pip-only `sby` without a solver runs `bmc` and
`prove` on the abc engines and no `cover` task.

[[runner-formal-local-run]]
=== A local run

[source,bash]
----
python3 tools/dv/run_dv.py --list                              # the `dtp fv` row: the formal view and its tools
python3 tools/dv/run_dv.py --dut dtp --mode formal --dry-run   # the planned stages and the rendered sby command
python3 tools/dv/run_dv.py --dut dtp --mode formal             # the `smoke` group: dtp_tap_fpv
python3 tools/dv/run_dv.py --dut dtp --mode formal --items fpv # every item of the plan
python3 tools/dv/run_dv.py --dut dtp --mode formal --items dtp_tap_fpv --app tap_fpv
----

The `flist` stage writes the Bender filelist the task file reads through its
`[files]` entry, then the `formal` stage runs every task of the item's app in
one `sby` invocation from the app's `cwd`, the directory holding the task
file. Under `<run>/stages/formal/` the run leaves `logs/<item>.log`, the
replay script `scripts/formal.<item>.sh`, the `env/` snapshot, and one work
directory per task, `<item>_<task>/` (`dtp_tap_fpv_tap_bmc` for the TAP
block's `bmc` task), holding the model, the engine log, the
`status` file, the JUnit report, and on a counterexample
`engine_0/trace.vcd`; a reached cover writes its trace the same way inside
the `cover` task's directory. The console ends with the item status and the
run-level `result.json`, whose `formal` object carries the proven and covered
counts and the task totals (<<runner-formal-grading>>).

The FAIL path is checked by inverting one assertion body and running the same
command: the `bmc` task reports `FAIL` with the trace, the `prove` task
reports `FAIL`, the item is `FAIL` in the `formal_fail` bucket, and the exit
code is non-zero. Restore the property afterwards; the DTP plan section names
the assertion it uses for this check.

[[runner-formal-container-run]]
=== A container run

When the tools live in a container image, the site layer's `launcher` puts
the container command in front of every `sby` invocation while `run_dv.py`
and `bender` stay on the host (<<runner-site-layer>>). Three constraints hold:

* The container sees the checkout and the run directory at the same paths as
  the host, because the generated filelist and the rendered command carry
  host-absolute paths.
* The launcher's first token is an absolute path or a bare name found on
  `PATH`. The command starts from the app's `cwd`, so a checkout-relative
  path does not resolve there.
* The image carries a yosys-slang build with the concurrent-assertion
  lowering and an SMT solver beside `sby` (<<runner-formal-toolchain>>).

The repository's container helper meets the first constraint: `eda-run`
mounts the checkout at its own host path and runs the command inside the EDA
image (`tools/docker/README.md`). `OCAH_EDA_IMAGE` selects the image, and a
launcher inherits the tool's `extra_env`, so one site file describes the
whole arrangement:

[source,toml]
----
schema_version = 1

[simulators.sby]
launcher = ["/path/to/checkout/scripts/docker-run.sh", "eda-run"]
extra_env = { OCAH_EDA_IMAGE = "hpretl/iic-osic-tools:2026.08" }
----

`--doctor --dut dtp --mode formal` then reports `launcher found:` with the
helper's path on the `sby` row, `--dry-run` prints the prefixed command, and
`result.json` records the site file under `site`. The cocotb path cannot take
a launcher; formal mode has no such restriction because every formal command
is rendered from argv.

[[runner-formal-properties]]
=== Writing properties

The Formal Property Style and Layout chapter of `hw/common/dv/docs/index.adoc`
fixes how a property file is written so that it elaborates on the open path
and on licensed backends alike. The rules a contributor meets first:

* *Subset.* Every property body is a boolean over current and `$past` values.
  The open frontend reads no sequences, implication operators, or the
  `$stable`, `$rose`, `$fell` family; the concurrent SVA checkers
  `ocah_axi_sva` and `ocah_jtag_sva` and the `OCAH_ASSERT` macros elaborate
  on licensed backends only, while `ocah_axi_fv` and `ocah_jtag_fv` beside
  them carry the handshake rules in the subset, each side asserted or
  assumed by parameter (Accepted constructs, Shared protocol checkers).
* *Macros and guards.* `hw/common/assert/ocah_fv_macros.svh` supplies
  `OCAH_FV_ASSERT`, `OCAH_FV_ASSUME`, `OCAH_FV_COVER`, and
  `OCAH_FV_INITIAL_RESET`, all gated on `FORMAL`, which every backend script
  defines; a property file never tests `YOSYS` (Property macros, Preprocessor
  guards).
* *Attachment and labels.* A property module binds to the described block
  with downward hierarchical references, and every label starts with `ast_`,
  `asm_`, or `cov_` (Attaching a property module, Labels).
* *Reset and clocks.* An `asm_initial_reset` holds the reset in the first
  cycle; a DUT clocked on both edges of one clock models its clocks explicitly
  under `multiclock on` with an environment module that asserts and then
  releases the asynchronous resets (Reset and history, Clock modelling).
* *Layout.* `<dut-dv-root>/formal/props/` holds the property and bind files,
  `formal/<app>/sby/` the task file and the reset environment,
  `formal/build/` the generated filelist and work directories (Layout under
  the DUT DV root).
* *Reachability.* Every `cov_` label stays reachable after any assumption
  change, checked by the `cover` task of the same run; an unreached cover
  fails the item (Cover reachability after assumption changes).

A formal target starts with a plan section in the DUT's verification plan
that scopes the described block, tabulates the labels against the plan rows,
and justifies every bounded depth against the block's structural latency,
as the DTP section does.

[[runner-formal-config]]
=== Configuring a formal view

A DUT gains a formal view from `<name>_formal_cfg.toml` beside its sim
config, or from a `formal_cfg` pointer in the registry or the site layer
(Selection model). `hw/sys/dtp/dv/dtp_formal_cfg.toml` shows every key a
view on the CLI run path needs:

[cols="<3,<5",options="header"]
|===
|Key |Purpose

|`name`, `profile = "native-formal"`, `description`
|The DUT name, the shared formal profile (stage graph, `sby` as the default
tool), and the `--list` description.

|`[testlist]` `path`, `format = "toml_list"`
|The formal testlist, DUT-DV-root-relative. Each item's `module` names the
app it launches; groups collect items (`smoke` for the DTP item).

|`[native.stages.flist]` `kind = "filelist"`
|Regenerates the Bender filelist before every proof; the task file reads it
through `[files]`. `[native.stages.clean]` names what `--stage clean`
removes.

|`[build]` `top_module`, `filelist`, `bender_filelist`, `work_dir`,
`incdirs`, `common_bender_targets`, `bender_targets`
|The design closure and include order. `hw/common/assert/yosys` precedes
`hw/common/assert` so the frontend picks the assertion shim over the vendored
header; the targets name the design only, never the simulation testbench.

|`[targets.default]` `build_dir`
|The one target a formal view carries.

|`[formal.apps.<app>.<tool>]` `cwd`, `script`, `args`
|One table per backend and app: the directory the tool starts from, the
script it runs, and the tokens spliced at the template's `{args}` (the
`sby` task names). An `argv` key overrides the tool's registry template and
an `evidence` table grades a backend without a parser policy
(<<runner-formal-templates>>, <<runner-formal-grading>>).
|===

`--validate-configs` validates the view as `<name> (formal)` and `--list`
shows it as a `fv` row; `--list --json` entries carry `mode = "formal"` and
`available`. The `tools` list comes from the profile unless the config sets
its own, which a config that adds a site-supplied backend does
(<<runner-formal-licensed>>).

[[runner-formal-results]]
=== Reading a result

The runner grades an item from what the backend wrote, never from its exit
code; <<runner-formal-grading>> carries the rules and the `formal` object.
What each status means for the contributor:

[cols="<1,<4",options="header"]
|===
|Status |Meaning and next step

|`PASS`
|Every task passed and every cover was reached. A passed `bmc` task is
bounded evidence to its depth; the `prove` task is the unbounded proof.

|`FAIL`
|A counterexample, an induction failure, or an unreached cover. Open the
task's `engine_0/trace.vcd`; for an unreached cover revisit the assumptions
and the depth against the plan section's distance table before touching the
cover.

|`UNKNOWN`
|No task evidence, an inconclusive task, or a non-zero exit beside passing
evidence. "no formal task evidence" points at the launch template's
`--prefix` or the app's `cwd`; an inconclusive `prove` (an induction
counterexample) is an open proof that needs a stronger invariant or another
engine. `sby` takes depths and timeouts from the task file, so a changed
bound is a task-file edit; `--formal-arg` values reach the command only where
the template has a `{formal_args}` placeholder.

|`TIMEOUT`, `ERROR`
|The task file's `timeout` fired, or the tool failed before writing
evidence; the stage log carries the tool's diagnostic.
|===

The recorded status is the disposition. Formal results have no waiver
mechanism: coverage waivers (<<runner-waive>>) apply to coverage bins only,
and a property that is out of scope is removed from the property module with
the reason recorded in the plan section rather than waived.

[[runner-formal-licensed]]
=== Licensed backends and the companion boundary

The open tree carries the open path and nothing that names a licensed tool:
the property and bind files, the `sby` task files and reset environments, the
formal config with the `sby` app, and the plan section. The registry and the
formal profile list `sby` alone. A licensed backend reaches the runner
through the site layer (<<runner-site-layer>>), and its collateral lives in
the companion repository or in an adopter's own tree:

* *The site file* adds a complete tool table with `kind = "formal"`,
  `frameworks = ["formal"]`, the binary, the license variables, an `argv`
  launch template, and a `setup_hook` or `launcher` where the tool needs an
  environment or a wrapper. The runner validates it with the registry schema
  and treats it exactly like a checked-in table; `--list` marks it
  `(licensed)` from its `license_env`.
* *A companion-owned formal config*, named by the site file's
  `[duts.<dut>] formal_cfg`, lists `tools = ["sby", "<tool>"]` and carries
  the licensed app tables with their scripts and `evidence` hooks. Its `sby`
  app reuses the open collateral by pointing `cwd` at the open tree's task
  directory, so one view serves both backends.
* *Activation* is explicit: the file at `hw/common/dv/configs/site.local.toml`
  or the one `OCAH_DV_SITE` names. The presence of a companion checkout
  changes nothing.

[source,toml]
----
schema_version = 1

[simulators.fvtool]
kind = "formal"
binary = "fvtool"
frameworks = ["formal"]
license_env = ["FVTOOL_LICENSE_FILE"]
supports_waves = []
supports_cov = ["formal"]
default_waves = ""
argv = ["{binary}", "-batch", "{script}", "{args}", "{formal_args}"]
setup_hook = "eda/fvtool.env"

[duts.dtp]
formal_cfg = "/path/to/companion/hw/sys/dtp/dv/dtp_formal_cfg.toml"
----

[source,bash]
----
python3 tools/dv/run_dv.py --doctor --dut dtp --mode formal --tool fvtool
python3 tools/dv/run_dv.py --dut dtp --mode formal --tool fvtool
python3 tools/dv/run_dv.py --dut dtp --mode formal --tool sby
----

Both commands run the same item; the tool choice is the only difference, and
each run records the site file under `site` in its `result.json`.
`hw/common/dv/configs/site.local.example.toml` is the template for the site
file.

== Stage planning

The canonical logical stage names are:

[source,text]
----
flist
c_compile
hdl_compile
elaborate
sim
regress
cov_merge
cov_report
formal
clean
----

The actual stage set is supplied by the selected profile and DUT. A logical
stage's configured `kind` chooses its backend implementation. The shared
`native` profile declares ONE canonical graph with generic kinds (`filelist`,
`hdl_compile`, `sim`) that dispatch per (tool, framework) at run time: for
cocotb, `hdl_compile` builds the simulator model and `sim` launches the cocotb
test; for SV-UVM on VCS, `hdl_compile` runs the folded two-step build —
analyze (vlogan, with the simulator-owned UVM library precompiled first) then
elaborate to the reusable `simv` — and `sim` is one `simv` invocation per
test/seed (`+UVM_TESTNAME`). There is no separate `elaborate` stage in the
shared graph; the elaborate sub-step logs alongside the `hdl_compile` log as
`hdl_compile.elaborate.log`.

Without explicit `--stage`, simulation selects the available stages from:

[source,text]
----
flist -> c_compile? -> hdl_compile -> elaborate? -> sim
----

`c_compile` is inserted when a selected test declares firmware and the flow
provides that stage. A group or multiple selected tests use the same path, but
the simulation leaves run through the scheduler.

Important stage rules:

* `--stage NAME` is repeatable and runs the requested stages in order.
  `filelist` is accepted as an alias for `flist`; comma-separated names are not.
* `--build-only` selects available `flist`, `hdl_compile`, and `elaborate`
  stages. Firmware `c_compile` can still be inserted on this implicit path.
* `--run-only` omits planned `flist`, `hdl_compile`, and `elaborate` stages.
  Firmware `c_compile` can still be inserted, and a cocotb simulation can build
  its model when no prebuilt model is available.
* `--regress`, a group, multiple tests, `--reseed`, `--retry`, or
  `--max-failures` enables scheduler behavior.
* If `--stage regress` is requested but the flow provides only `sim`, the
  scheduler dispatches the `sim` stage.
* Explicit stages do not generally gain implicit prerequisites. For example,
  `--stage sim` expects an existing generated filelist and required firmware
  outputs. The cocotb backend can still build its model, and a parallel
  scheduler can insert an `hdl_compile`/`elaborate` prebuild before its leaves.

Stage-control precedence is explicit `--stage`, then `--build-only`, then
`--run-only`, then `--regress` or the mode default.

[WARNING]
====
`--stage clean` recursively removes every path configured for that DUT. Most
current DUTs include the complete `<dut-dv-root>/build` tree, so the command can
delete cached models and all prior runs. Inspect the `REMOVE` plan with
`--stage clean --dry-run` before executing it.
====

[[runner-build-reuse]]
=== Build reuse

A cocotb model is built into the target's `build_dir` with the tool name
appended (`<build_dir>/<tool>`, or the sibling `<build_dir>/<tool>-coverage`
under `--cov`; VCS adds one more component named after the target) and
reused by every later run of the same target and tool. The
`artifact build=<dir> (rebuild=<bool> reason=<why>)` line of a run names the
directory it used and, when the model is rebuilt, why.

cocotb's build step rebuilds a model only when a source it was handed is
newer than the model, and this flow hands it none: the sources reach the
compiler through the filelist. The runner therefore decides for it. Every
build writes `build_record.json` into the model directory with the
fingerprint of the inputs that produced the model, and the next run compares
its own fingerprint with the record: a different fingerprint (`reason=inputs
changed`), or a model directory without a record (`reason=no build record`),
forces a clean build; `--rebuild` forces one regardless (`reason=requested`).
An edit to any file the filelist reaches, including its `-f` includes, or to
any file a build argument names, such as a coverage scope file, therefore
rebuilds the model on the next run.

`[build.options]` sets the sharing policy:

* `cache_enabled = true` partitions the build directory by a fingerprint of
  the build inputs, so configurations that differ never overwrite each
  other's model and an unchanged configuration finds its build again. The
  fingerprint covers the top module, the tool version, the generated filelist
  text, a digest of every source the filelist reaches through its `-f`
  includes, a digest of every file a build argument names, the rendered build
  arguments, the selected `[targets.<name>]` table, the Verilator
  public-scope list, the wave format, whether coverage is on, and the strings
  in `cache_key_extra`.
* `rebuild = true`, or `--rebuild`, forces a clean build of the selected
  directory through the cocotb runner on every simulator, and removes a
  firmware template's declared outputs before `c_compile` runs so an
  incremental build tool cannot keep stale objects.
* `build_jobs` and `cflags`, with the `[build.<tool>]` knobs, shape the build
  command and enter the fingerprint through the arguments they add.

The shared profile leaves `cache_enabled` off, so one directory per target
and tool is rebuilt in place when its inputs change.

[[runner-dry-run-plan]]
=== Reading a dry-run plan

`--dry-run` resolves the configuration, plans the stages, and renders every
command, script, and environment snapshot the run would use, without
executing a backend tool or writing a result file. The plan for the DTP
`smoke` group on Verilator with `--ui plain`, timestamps removed and the
repository, run, and seed paths abbreviated:

[source,text]
----
run        flow=dtp tool=verilator items=2 stages=flist,hdl_compile,sim run_dir=hw/sys/dtp/dv/build/runs/<stamp>__verilator__smoke mode=regression sim_jobs=1 executor=local backend=log
config     merge_order=simulator-defaults < profile(native) < dut(hw/sys/dtp/dv/dtp_sim_cfg.toml) < cli
config     effective_defaults=simulators.toml[verilator.build_defaults], simulators.toml[verilator.coverage_defaults], profile/DUT [defaults], profile/DUT [target_defaults], profile/DUT [build.options]
stage      start name=flist item=- log=<run>/stages/flist/logs/flist.log
CMD  : bender checkout
CMD  : bender script flist-plus -t axi_rtl -t apb_rtl -t common_cells_rtl -t common_cell_sync_shim -t register_interface_l1 -t dtp -t simulation > <repo>/hw/sys/dtp/dv/build/dtp_bender.f
WRITE: <run>/stages/flist/scripts/flist.sh
WRITE: <run>/stages/flist/env/flist.env
WRITE: <repo>/hw/sys/dtp/dv/build/dtp_dut_compile.f
stage      done name=flist item=- status=PASS elapsed=0.0s
stage      start name=hdl_compile item=- log=<run>/stages/hdl_compile/logs/hdl_compile.log
artifact   build=<repo>/hw/sys/dtp/dv/build/cocotb/verilator (rebuild=False)
WRITE: <run>/stages/hdl_compile/scripts/hdl_compile.sh
WRITE: <run>/stages/hdl_compile/env/hdl_compile.env
stage      done name=hdl_compile item=- status=PASS elapsed=0.0s
regression start total=2 sim_jobs=1 executor=local seeds=1 retry=0
WRITE: <run>/dtp_sanity_test/seed_<seed>/attempt_0/scripts/sim.dtp_sanity_test.py
CMD  : <python> <run>/dtp_sanity_test/seed_<seed>/attempt_0/scripts/sim.dtp_sanity_test.py
WRITE: <run>/dtp_sanity_test/seed_<seed>/attempt_0/scripts/sim.dtp_sanity_test.sh
WRITE: <run>/dtp_sanity_test/seed_<seed>/attempt_0/env/sim.env
regression done index=1/2 status=PASS item=dtp_sanity_test seed=<seed> attempt=0 elapsed=0.0s
(the second leaf, dtp_jtag_idcode_test, repeats the five lines above)

----

Reading it:

* The `run` line is the resolved selection: the two `smoke` members became
  two leaves under the scheduler (`mode=regression`), and the implicit stage
  path is `flist -> hdl_compile -> sim` because no selected test declares
  firmware.
* The two `config` lines state the merge order and the tables that supplied
  defaults, in the order they were layered.
* `CMD` lines are the exact commands, `WRITE` lines the scripts and
  environment snapshots that a real run writes, and `REMOVE` lines, under
  `--stage clean`, the paths it deletes. Nothing after a colon has run.
* Every stage reports `status=PASS elapsed=0.0s` because the plan, not the
  tool, was executed, and the `result` line names a `result.json` that the
  dry run does not write.

A dry run also loads the locked Python environment and may refresh the
generated namespace bridge (<<runner-current-limitations>>).

=== Coverage stages

`--cov` requires the flow to declare coverage stages: on a flow whose stage
graph has no `cov_merge`/`cov_report` (for example the `uvm` framework), the
runner rejects `--cov` before any stage executes instead of failing after a
full compile and simulation with a missing coverage artifact.

On the implicit path, `--cov` instruments simulation and appends `cov_merge`
and `cov_report` when the flow provides them:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut dtp \
  --items smoke \
  --tool xcelium \
  --cov
----

With explicit stages, `--cov` enables collection but does not append merge or
report:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut dtp \
  --items dtp_sanity_test \
  --stage sim \
  --tool xcelium \
  --cov

python3 tools/dv/run_dv.py \
  --dut dtp \
  --run-dir hw/sys/dtp/dv/build/runs/latest \
  --stage cov_merge \
  --stage cov_report \
  --fail-under 80
----

Non-dry-run coverage-only replay requires an existing `result.json`. The runner
recovers the original tool, rejects a mismatched `--tool`, preserves
non-coverage stage history, and replaces the replayed coverage records. A dry
run can render a placeholder plan without that file, but cannot restore the
original tool or history. A run that did not finish (`tests.completed` is
`false`, or the record carries an `interruption`) is refused with exit code
`2`: coverage is graded over a complete regression only, so the leaves that
happen to have run cannot produce a threshold verdict.

[[runner-coverage-inputs]]
==== Which databases merge

`cov_merge` selects its inputs from the leaf `result.json` records under the
run directory, not from a directory listing. For every test and seed it
takes the final attempt that wrote a coverage database, whatever that leaf's
status, so a retried leaf contributes once and a failing or timed-out leaf
contributes what it collected. A debug-only rerun and a leaf whose database
is missing or empty are rejected with a recorded reason, and a fragment that
records another flow or tool refuses the whole merge. A run directory without
leaf records falls back to the tool's `input_glob`.

The inputs must share one target and one build fingerprint. A multi-target
run cannot be merged as one coverage database; pass `--target NAME` to
compile every selected test on one elaboration. Inputs that all lack target
and build-fingerprint provenance merge as one set, and a set that mixes
recorded and missing provenance is refused. Coverage-only replay resolves the
current/default target rather than restoring an original non-default target;
use replay only when target and build-affecting configuration still match.
This is especially important for the VCS design coverage database.

The merge and report commands, the merged database name, and the input glob
come from `[coverage.<tool>]`, layered as every other tool table is
(<<Configuration and precedence>>), so the same run directory merges the same
way on any host that has the tool. `cov/coverage.json` records the selection
(<<runner-coverage-record>>): the selection policy and source, every input
with its test, seed, attempt, status, target, and build fingerprint, every
rejection with its reason, the exclusion files, and the policy file with its
SHA-256 and `scope_epoch`.

[[runner-cov-combine]]
==== Combining finished runs

`--cov-combine RUN_DIR...` combines the coverage of two or more finished runs
into one new run directory and grades it, so a DUT whose scenarios run under
two frameworks, or whose seeds run on two hosts, gets one signoff figure:

[source,bash]
----
python3 tools/dv/run_dv.py --dut dtp \
  --cov-combine hw/sys/dtp/dv/build/runs/<cocotb-run> hw/sys/dtp/dv/build/runs/<uvm-run> \
  --run-dir hw/sys/dtp/dv/build/runs/<combined-run>
----

No simulator runs. Each input run must belong to the DUT, have finished, and
carry a coverage record whose merge and report completed and whose merged
database exists; its own grade does not matter, since the combined run is
graded on its own. Every run must use one tool, and all must record one
commit, since one figure describes one revision of the design. A run
recorded on a dirty tree is accepted with a warning. The runs may sit in
another checkout or in a retained copy: their artifact paths resolve against
the tree that produced them, and a design database that the copy left out is
skipped, since the merged database its own merge loaded already holds the
design data.

Two verbs, two operations. The `cov_merge` stage *merges* the leaf databases
of one run into that run's merged database, and `--stage cov_merge --run-dir X`
replays that in place. `--cov-combine` *combines* finished runs: the new run
carries the DUT's `cov_merge` and `cov_report` stages, its merge runs the
tool's `combine_cmd` over the runs' design databases and merged databases
(`urg -flex_merge union` on VCS, because runs of different frameworks
elaborate different harness tops and only the DUT subtree is common), and its
report grades the result against the same policy, threshold and exclusion
inputs as any run. `cov/coverage.json` lists the runs as its inputs (`item`
of `run:<name>`, `selection_source` of `run_dirs`) and names each run's
directory, framework, commit, tool version and database under
`combine.input_runs`. `--run-dir` names the new directory; without it the run
lands under the DUT's run tree with the label `combine`, and `latest` keeps
pointing at the last simulation run, so the dashboard's default collection is
unaffected and a combined run is collected by naming its directory.
`--fail-under` and `--dry-run` apply; selection, seed, wave and build options
do not.

[[runner-coverage-grading]]
==== How the grade forms

`cov_report` runs the tool's report command, parses the report into scalar
metrics and per-point observations, applies the DUT's coverage policy, and
grades the result. Two kinds of threshold apply, and both must be met:

[cols="<2,<5",options="header"]
|===
|Threshold |Rule

|Compatibility threshold
|`--fail-under`, then `[coverage.<tool>].fail_under`, then `0.0`, compared
with the tool's own overall percentage (`overall_percent` in
`summary.json`): Verilator's count of hit points over all points, or the
urg / imc dashboard total. Accepted waivers do not move that figure, so a DUT
gated by `--fail-under` alone sees no effect from its policy. On a `--waive`
re-grade the run's recorded `threshold` stands unless `--fail-under` is
given.

|Policy thresholds
|Each `pass:[[[thresholds]]]` rule of `coverage_policy.toml` names a metric
family and a `minimum_percent`. `population = "effective"` (the default)
grades hit points over the points that remain after accepted waivers and
exclusions, and `population = "raw"` grades the unwaived figure. With the
default `scope`, a family with several native metrics grades its weakest;
a `scope` glob pools the family's in-scope points into one figure, and is
not met when the parser recorded no complete point list. `tool` and
`target` limit a rule to one tool or target; a rule that names another is
skipped without an outcome. `max_unclassified_points` fails the rule when
more uncovered points than that carry no `pass:[[[holes]]]` entry. A rule
whose metric family has no points is not met.
|===

A report tool that applies exclusion inputs while it reports (URG with
`-elfile`) writes the effective figures only. When the report phase has such
inputs, it runs the report command a second time without them into
`cov/report_raw/`, and each family's `raw_percent` comes from that report while
`effective_percent` comes from `cov/report/`; without exclusion inputs the one
report supplies both. The stage log carries one `COVERAGE FAMILY` line per
family with both figures, the console prints them on a `coverage` line, the
manifest points at the raw report as `artifacts.report_raw`, and `result.json`
carries the figures as `raw_metrics` and `effective_metrics`.

The coverage status is `PASS` when every threshold is met and `FAIL`
otherwise. A `FAIL` gives the `cov_report` record return code `1` and a
`coverage_threshold` failure bucket, makes the run status `FAIL` and the exit
code `1`, and names each missed threshold in the stage log. A DUT whose
policy sets no `pass:[[[thresholds]]]` and whose configuration sets no
`fail_under` grades against `0.0` and cannot fail on coverage.

The grade is fail-closed on the policy itself, in two places. A policy that
fails a grammar check is refused when `cov_merge` loads it, before any
coverage file is written: that record is `ERROR` with a `config_error`
bucket and the run status is `ERROR`. Grammar checks include a
`schema_version` other than `1`, a `dut` other than the run's, an accepted
waiver with `confidence = "low"`, an open entry with an actionable
disposition and no GitHub issue, a duplicate id, a `minimum_percent` outside
0 to 100, an `expected_matches` below 1, an entry without a
`pass:[[[holes.native]]]` selector, and a category, disposition, status,
population, date, or selector key outside the grammar. A policy that
contradicts the report is refused by `cov_report` after the report command
ran: a `pass:[[[holes]]]` entry that matches a number of points other than
`expected_matches`, an accepted waiver or exclusion that matches a covered
point, or two entries that claim one point. That record is `ERROR` with a
`config_error` bucket, the run status is `ERROR`, and
`coverage-details.raw.json` is the only report file written. An accepted
waiver past its `expires` date grades its points as open and adds a warning
to `policy-application.json`, so a lapsed waiver lowers the effective figure
instead of hiding a hole.

In scheduler mode (a group, `--regress`, `--reseed`, `--retry`,
`--max-failures`, or more than one item), the leaf stage never stops the
plan: `cov_merge` and `cov_report` run after the leaves whatever their
statuses, so a red regression still carries its coverage record and the
databases of its failing and timed-out leaves are inputs like any other. A
flat single-test run stops at its first failing stage and reaches the
coverage stages only when the test passed. A run that did not finish
(`tests.completed` is `false`, or the record carries an `interruption`) is
refused by coverage-only replay and by `--waive` with exit code `2`:
coverage is graded over a complete regression only.

[[runner-waive]]
==== Waive coverage bins after a regression

A hole reviewed after a regression is closed in the DUT's
`coverage_policy.toml`, not by re-running the simulation. The loop is:

. Read the holes: `cov/report/coverage-details.json` lists every uncovered
  point with its `native_locator`, `hierarchy`, `source`, and `line`;
  `holes_summary` in `cov/report/summary.json` counts them by metric,
  category, and status.
. Add or edit a `pass:[[[holes]]]` entry. A waiver is an entry with
  `disposition = "waive"` (or `"exclude_scope"`), `status = "accepted"`,
  `confidence` of `medium` or `high`, a `rationale`, `owner`, `reviewer`, and
  `date`, plus one or more `pass:[[[holes.native]]]` selectors. `expected_matches`
  is an exact count. An accepted waiver that matches a covered point, a
  low-confidence waiver, and a `dut` that differs from the run's are rejected.
. Re-grade the finished run against the policy:
+
[source,bash]
----
python3 tools/dv/run_dv.py --dut dtp --run-dir hw/sys/dtp/dv/build/runs/latest --waive
python3 tools/dv/run_dv.py --dut dtp --run-dir hw/sys/dtp/dv/build/runs/latest --waive waivers/dtp.toml
----
+
Bare `--waive` applies the policy the DUT configures (`policy_file`, else
`cov/config/<tool>/coverage_policy.toml`); a DUT without one needs `FILE`.
`--waive FILE` applies that file instead, and it must name the run's `dut`. A
relative `FILE` resolves against the repository root, like `--run-dir`.
. Collect the run again for the dashboard.

No simulator or report tool runs: the run tree is the only input, so the
command works on a copied or downloaded run tree and on a host without the
tool. `--dut` must equal the run's `flow`; `--tool` and `--framework` are
recovered from `result.json` and must match when given. The run must have
finished: an interrupted or truncated run (`tests.completed` is `false`) is
refused with exit code `2`. The only other
options accepted are `--overlay`, `--fail-under`, `--verbose`, and `--quiet`.

The re-grade rewrites values only: `cov/report/coverage-details.json`,
`policy-application.json`, `summary.json`, and `cov/coverage.json`; the
`cov_report` record's `status`, `return_code`, `reason`, `failure_buckets`,
and coverage artifact paths in `result.json`; the run `status` and
`exit_code`; and `stages/regress/regression.json`. `generated_at`, `run_dir`,
the recorded tool versions and supported metrics, and every other stage record
keep their recorded values, and the `cov_report` stage log is read, never
written. Artifact paths point at the tree's current location.

Exit codes:

[cols="<1,<6",options="header"]
|===
|Exit |Meaning

|0 |Policy applied; the compatibility and policy thresholds are met.
|1 |Policy applied; a threshold is not met. The files carry the red reading.
|2 |Nothing written: a configuration or policy error, a missing input, or a run
that cannot be re-graded.
|===

A run can be re-graded when its report completed and parsed: the `cov_report`
record is `PASS` or carries only `coverage_threshold` / `config_error` failure
buckets, and `cov/report/coverage-details.raw.json` exists. Any other record
(`tool_error`, `timeout`, a missing record or raw file) is refused with a
pointer to `--run-dir <dir> --stage cov_report`, which reruns the report tool.
A run whose grade failed on the policy itself (`ERROR` with a `config_error`
bucket and no `summary.json`) is the repair case: correct the policy and run
`--waive`; it writes `summary.json` and grades the record.

Carried values: the tool version and supported metrics come from the run's
`summary.json` and `cov/coverage.json`. The compatibility threshold is
`--fail-under` when given, else the recorded `threshold`, else
`[coverage.<tool>].fail_under`, else `0.0`. In the repair case no threshold is
recorded, so a `--fail-under` the original run used has to be passed again.
The compatibility threshold grades the tool's raw overall figure, so a waiver
changes the verdict only through a `pass:[[[thresholds]]]` rule.

An accepted waiver may carry `expires` (`YYYY-MM-DD`). Past that date the
waiver is lapsed at grade time for its own DUT: the hole keeps its `policy_id`
and disposition, its `status` becomes `open`, it counts as an open hole and no
longer shrinks the effective denominator, and `warnings` in
`coverage-details.json` and `policy-application.json` carry
`<rule id> expired on <date>; treated as open`. `--validate-configs` reports
the expiry as a warning and stays `OK`; extending the date restores the waiver.

`pass:[[[native_files]]]` entries act inside the merge and report commands, which the
re-grade does not run. When the policy's native files differ from the digests
the manifest recorded at merge time, `--waive` exits 2; rerun
`--stage cov_report` instead.

For VCS (`urg`) and Xcelium (`imc`) the percentages are the vendor report's. A
waiver changes a hole's classification and the `unclassified_points` verdict
of a threshold, not the percentage; only the Verilator parser recomputes
effective percentages from waivers. The merged database (`merged.dat`,
`merged.vdb`, or `merged_cov`) must be present in the run tree.

A changed policy changes `comparison_key`, so trend points graded before and
after the change are not comparable and the dashboard starts a new series.

== Regression and reproducibility

Scheduler mode expands the selection into `(test, target, seed)` leaves. It
runs shared target builds first and then executes local leaves with up to
`--sim-jobs` workers.

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut smc \
  --items smoke \
  --regress \
  --reseed 10 \
  --retry 1 \
  --sim-jobs 8
----

When scheduler mode executes `sim` or `regress`, seeds are fresh random
positive integers and are recorded in leaf and regression results. `--seed` is
rejected for those scheduler runs. Each cocotb simulation process receives the
leaf seed as `RANDOM_SEED` and the directory its model was elaborated into as
`OCAH_SIM_BUILD_DIR` (`<tool>-coverage` under the DUT build directory for a
`--cov` run), so a test that records which model it simulated reads that
variable instead of assuming the plain `<tool>` path. Reproduce a leaf as a
single simulation with the recorded item and seed:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut smc \
  --items <failed-test> \
  --stage sim \
  --tool <recorded-tool> \
  --seed <recorded-seed>
----

`--retry N` retries a non-passing leaf up to `N` times. Earlier failures remain
in `regression.json`; the final effective attempt determines the leaf result.
A leaf that passes after a failed attempt is recorded as flaky.

[[runner-regression-record]]
=== The regression record

`stages/regress/regression.json` is the scheduler's own summary beside the
run-level `result.json`; both carry the run `status` and `exit_code`. Its
`jobs` list holds one record per attempt: `stage`, `item`, `target`, `seed`,
`attempt`, `status`, `return_code`, `reason`, `duration_sec`, `started_at`,
`ended_at`, `log`, `artifacts`, `failure_buckets`, `parser`, `metadata`, and
`result_json`, the per-attempt `<test>/seed_<seed>/attempt_<n>/result.json`. Attempts of one
`(item, seed, target)` leaf are grouped, and the highest attempt is the
leaf's final result.

* `failed_tests` lists every leaf whose final attempt is `FAIL`, `ERROR`,
  `TIMEOUT`, or `UNKNOWN`, with `attempt_count`, every attempt's summary, the
  final failure buckets (a leaf without a classified bucket gets one
  `unknown` bucket carrying its `reason`), the `expected_fail` record when
  the entry carries one, and a `rerun` command that reproduces the final
  attempt with its seed.
* `flaky_tests` lists every leaf whose final attempt is `PASS` after an
  earlier non-passing attempt: `flaky_reason` is `passed_after_retry`,
  `failing_attempts`, `first_fail_attempt`, `first_failure_reason`, and
  `passed_on_attempt` locate the flip, and `tests.flaky` counts these leaves.
  A flaky leaf is a passing leaf in `tests.passing` and in the run status.
* `rerun_commands` repeats the `rerun` of every failed and flaky record.
* `failure_buckets` groups the failed leaves' buckets by `(kind, signature)`
  with a `count`, the `affected` leaves, and up to five example paths; an
  interruption adds one `interruption` bucket naming the interrupted leaves.

A `--waves-on-fail` rerun is recorded on the final attempt as `wave_debug`
with `debug_only = true` and `status_affects_final_result = false`; it never
changes the leaf's status. A leaf skipped after `--max-failures` has one job
with status `SKIP`, no leaf directory, and no JUnit file.

`--max-failures N` stops launching new serial leaves after `N` final failures
and records the remainder as `SKIP`. Supplying this option disables the
parallel worker path so the threshold can be enforced deterministically.

== Waveform debug

Use `--waves [FMT]` to capture every selected simulation. Omitting `FMT` uses
the tool default. Use `--waves-on-fail [FMT]` to run normally first and then
perform a debug-only wave rerun for each final non-passing leaf:

[source,bash]
----
python3 tools/dv/run_dv.py \
  --dut dtp \
  --items smoke \
  --waves-on-fail fst \
  --wave-window 100us \
  --wave-margin 10us
----

The debug rerun never replaces or masks the original result. Its artifacts are
attached as debug evidence.

Wave times require a unit: `fs`, `ps`, `ns`, `us`, `ms`, or `s`.
`--wave-start`/`--wave-end` request an explicit interval.
`--wave-window` derives a start time from a timestamp found in the failure log;
when a window is requested, the default post-failure margin is `10us`.

Retention defaults are:

* `all` for `--waves`;
* `failed` for `--waves-on-fail`;
* `none` when waves are not requested.

If both wave modes are supplied, `--waves-on-fail` makes the default retention
`failed`.

Override them with `--wave-retention {all,failed,none}`. Kept wave directories
include a copied log and `debug_context.json` with viewer and same-seed replay
commands.

On VCS (both the cocotb flow and the standalone UVM flow), dumping is
driven by a generated UCLI script (`scripts/waves.<test>.ucli`, passed as
`simv -ucli -i`), so no testbench dump hooks are required. `fsdb` needs Verdi:
the runner resolves `VERDI_HOME` (explicit env first, then derived from `verdi`
on `PATH`), validates that the chosen root actually ships the FSDB writer
(`share/PLI/VCS/<platform>/libnovas.so`), exports the validated value to the
simulation — overriding a stale inherited `VERDI_HOME` — and fails fast with
the list of checked candidates when none is usable (`vpd` needs no Verdi
installation). If dump setup still fails inside the simulator, the script
degrades to a normal wave-less run: the test result is preserved and the
missing-wave warning fires. On Xcelium, `shm` capture is driven by a generated
Tcl script (`scripts/waves.<test>.tcl`).

[NOTE]
====
Exact ranged dumping is enforced only for Xcelium SHM and VCS
FSDB/VPD (via the generated dump scripts). Other backend/format combinations
record the requested range and set `range_supported` to false.
====

[NOTE]
====
The standalone UVM/VCS flow gains dump access by elaborating with
`-debug_access+all` when waves are requested. A waves run that skips
elaboration (`--stage sim` against a simv built without waves) cannot dump;
rerun with the elaborate stage included or `--rebuild`. cocotb's VCS runner
always compiles with `-debug_access+all`, so its cached build needs no rebuild.
If a wave-enabled simulation produces no wave file, the runner prints a
warning and records it in the run's wave metadata.
====

== Output and result contract

Automatically allocated runs use UTC and live below the selected DUT:

[source,text]
----
<dut-dv-root>/build/runs/<YYYYMMDD_HHMMSS>__<tool>__<label>/
----

The label is the first selected group, a single test name, `multi`, or `build`.
Name collisions gain `_01`, `_02`, and so on. The `latest` symlink is updated
only for automatically allocated runs.

The following representative layout separates shared stages from test-major
leaf output:

[source,text]
----
<run>/
├── result.json
├── stages/
│   ├── flist/{scripts,env,logs}/
│   ├── hdl_compile/{scripts,env,logs}/
│   ├── formal/{scripts,env,logs}/  # formal mode; sby tasks in <item>_<task>/
│   └── regress/regression.json
├── <test>/                         # flat single-test invocation
│   ├── result.json
│   ├── scripts/
│   ├── env/
│   ├── logs/
│   ├── results/results.xml
│   ├── coverage/
│   └── waves/
├── <test>/seed_<seed>/attempt_<n>/ # scheduler leaf
│   └── ...
└── cov/
    ├── coverage.json
    ├── <tool-specific-merged-database>
    └── report/
        ├── summary.json
        ├── coverage-details.json
        ├── coverage-details.raw.json
        └── policy-application.json
----

Nested regressions also write `<test>/result.json` rollups. Most subprocess
stages emit replayable shell scripts; in-process cocotb HDL builds and `clean`
are exceptions. Environment snapshots redact values when variable names
indicate licenses, tokens, secrets, passwords, credentials, API keys, private
keys, or authentication data.

`result.json` uses schema version `1` and records the resolved flow, tool,
executor, selected items, CLI overrides, test/coverage summary, Git metadata,
tool versions, and per-stage details. It is the authoritative run result.

The `tests` summary counts the recorded leaves (`total`, `passing`,
`failing`, `skipped`) and records whether the run finished: `leaves_planned`
is the number of (test, seed) leaves the selection planned, `leaves_run` the
number that executed (a leaf skipped after `--max-failures` did not), and
`completed` is `true` only when the two are equal and the record is not a
checkpoint. `pass_rate` is `passing / total` for a completed run and `null`
otherwise: an interrupted or truncated run has no denominator, so it
publishes no figure that reads as a grade. `regression.json` carries the same
fields, with one difference in `total`: `result.json` counts a skipped leaf in
`total` and in `skipped`, `regression.json` counts only leaves with a final
status in `total` and reports skipped leaves in `skipped` alone.
A formal run adds a `formal` object with proof totals
(<<runner-formal-grading>>).
When an adopter overlay was applied, its path is recorded under `overlay`
(repo-relative when inside the checkout, absolute otherwise) and its `[env]`
table, when present, under `overlay_env` in both the run-level `result.json`
and `regression.json`. When a site layer was active, its path is recorded
under `site` in the same two files (<<runner-site-layer>>).

[[runner-log-provenance]]
=== Provenance lines in the per-test log

A cocotb or VCS sim leaf ends its per-test log with one `PROVENANCE` line
naming the commit, branch, dirty flag, build fingerprint and, where the flow
has one, the filelist and its digest. The same facts are recorded under
`provenance` in the leaf's stage record, so a log and its `result.json` name
the same build.

Every `+key=value` simulator argument whose value is an existing regular file
(firmware, ROM, eFuse and shadow-register images such as `+rom_hex`,
`+sep_itcm_hex`, `+smc_efuse_hex` or `+smc_shadow_reg_preload`) is digested
as well. Each one adds a line directly after `PROVENANCE`:

----
PROVENANCE commit=<sha> branch=<name> dirty=false build_fingerprint=<fp> filelist=<path> filelist_sha256=<digest>
FW-PROVENANCE rom_hex=hw/sys/smc/dv/assets/smc_rom_default.hex sha256=<64 hex>
FW-PROVENANCE smc_efuse_hex=hw/sys/smc/dv/assets/smc_efuse_default.hex sha256=<64 hex>
----

The path is repo-relative when the image sits inside the checkout and absolute
otherwise, and the digest is the full SHA-256 of the file's bytes. The stage
record carries the same map under `provenance.images`, keyed by the plusarg
name. Bare flags, numeric values and values that do not name a regular file are
not recorded. An image a testbench opens by a fixed name rather than a plusarg
is outside this binding; pass it through a plusarg to bring it in.

[[runner-interrupted-checkpoints]]
=== Interrupted-run checkpoints

Before executing the first planned leaf, the runner writes an atomic
schema-version-1 checkpoint to the run-level `result.json`. The checkpoint has
status `UNKNOWN`, so automation cannot mistake an incomplete run for a pass.
It is replaced atomically after every completed leaf. An explicit `--result`
copy follows the same lifecycle.

The additive `progress` object records a stable identity for every planned leaf
(`id`, stage, item, target, and seed) and partitions those identities into
`completed`, `active`, `missing`, and `interrupted` lists with matching counts.
Its `state`, `sequence`, and `updated_at` fields distinguish successive
snapshots. A running checkpoint uses `active`; a handled interruption moves
those identities to `interrupted`. On a cluster executor every `active` or
`interrupted` leaf also lists its scheduler `jobs`: the task id, attempt,
whether it is a wave-debug rerun, the executor and driver, the job id, and
the submission time, and after an interruption `cancel_confirmed`. A
coordinator that dies without running its handler therefore leaves the ids
of its live jobs in its last checkpoint.

SIGINT and SIGTERM produce an `ERROR` checkpoint with an `interruption` object
that records the received signal and reason. External supervisors may use
SIGTERM for either cancellation or a wall-clock timeout, so the runner records
the signal rather than guessing which policy sent it. The first signal stops
new submissions, cancels every attempt in flight, and waits up to the
executor's cancel grace for the scheduler to confirm each stop; a second
signal ends that wait, and every signal received is listed under
`interruption.signals`. `interruption.cancellation` records the executor and
driver, the number of attempts asked to stop and the number confirmed, the
unconfirmed attempts with their item, seed, target, attempt, and job id, the
grace applied, whether the wait was cut short, and the path of the
`cancel-unconfirmed.json` record when one was written. If termination
prevents the final handler from running, the most recent atomic `UNKNOWN`
checkpoint still preserves all completed leaves. Normal completion replaces
all checkpoint-only fields with the ordinary final aggregate.

Every checkpoint, running or interrupted, carries `tests.completed = false`
and `tests.pass_rate = null`. A handled interruption also prints
`incomplete run: N of M planned leaves ran, no pass rate` on the console
instead of a pass count and writes one run-level `results/results.xml` with a
single errored testcase (`type="interruption"`) naming the interruption, so a
JUnit consumer does not read the finished leaves as the whole run. A run that
stops early for any other reason (`--max-failures`, a failing leaf in a flat
run, a build failure before the leaves) records `tests.completed = false` and
`tests.pass_rate = null` and prints the same console note, but carries no
`interruption` object and gets no run-level interruption testcase; its JUnit
evidence is the leaf files it wrote.

=== Status and exit codes

[cols="<2,<2,<5",options="header"]
|===
|Status |Exit code |Meaning

|`PASS` |0 |All required stage evidence passed.
|`FAIL` |1 |A backend stage returned nonzero, or a test, proof, or coverage
threshold failed.
|`ERROR` |2 |Configuration, infrastructure, or invocation failed.
|`TIMEOUT` |124 |A stage exceeded its resolved timeout.
|`UNKNOWN` |5 |The parser could not prove pass or classify a stronger failure.
|`SKIP` |n/a |A scheduler leaf was intentionally skipped; not a run-level status.
|===

A handled SIGINT or SIGTERM checkpoint records the `ERROR` status code (`2`)
in JSON, while the runner process exits with the conventional
`128 + signal number` value (`130` or `143`).

`--waive` exits by its coverage grade alone (`0`, `1`, or `2`; see
<<runner-waive>>), independent of the run status it records, and
`--cov-combine` exits by the grade of the combined run it writes.

Run-level aggregation uses:

[source,text]
----
ERROR > TIMEOUT > FAIL > UNKNOWN > PASS
----

For simulation, return code zero is not sufficient for `PASS`. The selected
parser policy examines structured XML, hard-failure markers, required and
failure patterns, framework summaries, and positive pass evidence. Missing or
ambiguous positive evidence produces `UNKNOWN`, which should fail CI closed.
A leaf with `expect_fail` is graded after that classification: its `FAIL`
becomes `PASS` and its `PASS` becomes `FAIL` (<<runner-expected-failures>>).

For formal mode, the exit code is never the status source: task status lines,
status files, and JUnit reports, or the app's summary file, are
(<<runner-formal-grading>>). Missing evidence produces `UNKNOWN`.

[[runner-leaf-grading]]
=== How a simulation leaf is graded

A `sim` or `regress` leaf that ran to the end is graded by its parser policy
from three inputs: the structured result files the policy names under
`results/`, the leaf log, and the process return code. The rules apply in
this order, and the first that decides ends the grading:

. A structured result with a `failure` or `error` node is `FAIL`
  (`status_source` `structured_result`, bucket `sim_failure`). A structured
  result with only passing testcases is positive evidence. A structured
  result that is missing, empty, malformed, or has no testcase is
  inconclusive and is remembered.
. A log line matching a `hard_fail_patterns` entry is `ERROR`
  (`log_pattern`, bucket `tool_error`).
. A nonzero return code is `FAIL` (`return_code`, bucket `sim_failure`).
. A `required_patterns` entry with no match in the log is `FAIL`.
. A `fail_patterns` match that no `ignore_patterns` entry covers is `FAIL`;
  an ignored match is recorded as evidence with status `IGNORED`.
. The last match of each `summary_patterns` entry is read: counts with a
  zero total, a nonzero failure figure, or a total that the passing and
  skipped figures do not add up to, are `FAIL` (`log_summary`); otherwise the
  summary is positive evidence.
. A `pass_patterns` match is recorded, and counts as positive evidence only
  when the policy names no structured result.
. With an inconclusive structured result remembered, the leaf is `UNKNOWN`
  (`structured result missing or inconclusive`, bucket `unknown`).
. With `require_positive_evidence` set and no positive evidence, the leaf is
  `UNKNOWN` (`no positive pass evidence matched`).
. Otherwise the leaf is `PASS`.

A leaf whose command exceeded its resolved timeout is `TIMEOUT` (bucket
`timeout`) before any of this runs, and a leaf whose stage raised a
configuration or tool exception is `ERROR` (bucket `config_error` or the
stage's default). `expect_fail` grading follows (<<runner-expected-failures>>).
Every decision records under `parser` the policy name, its fingerprint,
`status_source`, the applied extensions, and up to 25 evidence records, each
naming the file, its kind, the status it contributed, and the matched text.

The policy is `[pass_fail].policy` in the sim config, else the framework's
default: `cocotb-default` for cocotb (structured `results.xml`, the cocotb
`TESTS=` summary line), `uvm-log` for SystemVerilog UVM (no structured
result; `UVM_ERROR` and `UVM_FATAL` counts, `UVM Report Summary` required),
and `generic-regex` otherwise, which validation rejects unless the flow names
a positive-evidence source. `[pass_fail]` adds to a policy only:
`extra_pass_patterns`, `extra_fail_patterns`, `extra_ignore_patterns`,
`extra_required_patterns`, `extra_hard_fail_patterns`,
`extra_summary_patterns`, and `extra_structured_results`; a `replace_*` key
is rejected because it would weaken the policy. A tool's
`[<tool>.parser_extensions]` table in `simulators.toml` adds
`extra_fail_patterns` and `extra_hard_fail_patterns` for that simulator's
own error markers. Every pattern is compiled at validation time.

[[runner-coverage-record]]
=== The coverage record

A run that collected coverage carries the grade in four places, all under
the run directory, so a copied or downloaded tree describes itself:

[cols="<2,<1,<5",options="header"]
|===
|File |Schema |Carries

|`coverage` in `result.json`
|`1` (the run record)
|`enabled`; `status`, the rollup of the coverage stages (`SKIP` with
`total_percent` `null` when the run had none); `total_percent`, the tool's
raw overall figure; `threshold` and `threshold_met`; `metrics`, the
parser's per-family figures overlaid with the effective percentage of every
family that has point records; `raw_metrics` and `effective_metrics` per
family; `policy_thresholds`; `holes_summary`; `comparison_key`,
`scope_fingerprint`, and `policy_fingerprint`; `target` and
`build_fingerprint`; the tool version and supported metrics; the input list;
and the paths of the files below.

|`cov/coverage.json`
|`2`
|The merge manifest (<<runner-coverage-inputs>>) and, once the report has
run, the grade: `status`, `metrics`, `overall_percent`, `threshold`,
`threshold_met`, `policy_thresholds`, `holes_summary`, the fingerprints, and
the merge and report return codes, with `artifacts.report_raw` when the
report ran without its exclusion inputs as well. A combined run's manifest
lists the runs as its inputs (`selection_source` of `run_dirs`) and carries
the `combine` block (<<runner-cov-combine>>).

|`cov/report/summary.json`
|`2`
|The graded summary: `status`, `overall_percent`, `threshold`,
`threshold_met`, `compatibility_threshold_met`, `policy_thresholds` (one
outcome per rule that applies to the run's tool and target, with
`actual_percent`, `unclassified_points`, and `met`),
`metrics`, `holes_summary` (`open`, `accepted`, `unclassified`, counts by
metric, category, disposition, and status, and up to 100 sample holes),
`comparison_key`, `scope_fingerprint`, `policy_fingerprint`, and the artifact
paths.

|`cov/report/coverage-details.json`
|`1`
|Every observation with its `native_locator`, `hierarchy`, `source`, `line`,
`count`, and `covered`, plus the fields the matching `pass:[[[holes]]]` entry
stamped on it (`policy_id`, `category`, `disposition`, `status`,
`confidence`, `rationale`, `owner`, `reviewer`, `issues`), and one record per
native metric with `covered`, `total`, `excluded`, `raw_percent`, and
`effective_percent`. `coverage-details.raw.json` is the same before the
policy applied.

|`cov/report/policy-application.json`
|none
|The policy path and SHA-256, the native policy files applied, every
`matched` entry with the observation ids it claimed, and the warnings, one
per lapsed waiver.
|===

Three fingerprints decide whether two grades are comparable.
`policy_fingerprint` is the SHA-256 of the policy file. `scope_fingerprint`
hashes the build fingerprint, the scope the parser recorded, and the policy's
`scope_epoch`; without a policy it is the parser's hash alone and
`policy_fingerprint` is `null`. `comparison_key` (`COVCMP-` and 16 hex digits) hashes the DUT,
the tool, the target, and both fingerprints: two grades share a key only when
the same design build was graded against the same policy, so compare trend
points and `holes_summary` counts only when their keys match. A waiver added
to the policy changes the key by design; the hit counts do not.

The dashboard collector carries the `coverage` object into the normalized
record and stages `coverage.json`, `summary.json`, and
`policy-application.json` beside it; the details files and the merged
database stay in the run tree (the Continuous integration section of
xref:run-dashboard.adoc[DV and FV Dashboard]). Hosted CI keeps a weekly run
tree for 30 days and the normalized bundle for 90 (<<runner-ci-budgets>>).

[[runner-junit-ownership]]
=== JUnit ownership

Every executed simulation leaf ends with xUnit XML at
`<leaf>/results/results.xml`. A framework that writes its own file, as cocotb
does, owns it: the runner reads it as evidence and never rewrites it. When
the file is absent after grading, for a SystemVerilog UVM leaf or a leaf
whose simulator died before the framework could write, the runner
synthesizes a single-testcase file from the graded result, with the node
mapping above and a `system-out` block naming the log, the leaf
`result.json`, the parser policy, the `status_source`, the failure buckets,
and the attempt. Either way the path is recorded as `artifacts.results_xml`
on the leaf.

A synthesized file is a reporting artifact, written after grading, atomically,
and never read back as evidence. Its suite carries a `producer` property
with the value `run_dv.py junit-fallback`, and only a file carrying that
marker is ever removed or replaced; a file without it is left alone even
when it sits where the runner would write.

Two run-level files follow the same rule. A handled interruption writes
`<run>/results/results.xml` with one errored testcase of type `interruption`
(<<runner-interrupted-checkpoints>>). A run that fails before any leaf
executed writes the same path with one testcase for the first failing stage
in `ERROR`, `TIMEOUT`, `FAIL`, `UNKNOWN` order, so a compile or filelist
failure stays visible to a JUnit consumer; a run in which a leaf executed,
or that passes, removes a marked run-level file left by an earlier
invocation into the same directory.

[[runner-ci]]
== Continuous integration

Two GitHub workflows run simulator jobs on GitHub-hosted runners. Both run
each DUT through the composite action `.github/actions/dv-run` (toolchain
setup, `run_dv.py`, the native result gate, and the artifact upload), so the
callers differ only in their matrix and tier policy, and a regression-tier
change can never alter the pull-request gate:

[cols="<2,<4,<5",options="header"]
|===
|Tier |Workflow and trigger |Behavior

|`smoke`
|`sim.yml`: `pull_request`, `push` to `main`, `workflow_dispatch`
|`--items smoke --sim-jobs 2` for `dtp`, `sep`, `smu_block`, and `smc`, and
`--items hosted_smoke` for `smu`, whose own `smoke` group reaches firmware
tests the hosted runner cannot build; 60-minute budget per job. The job
names `verilator-smoke (<dut>)` are the stable check contexts. Every job
runs for a documentation-only change too, so the contexts report; each job
then prints one line and skips the simulation.

|`qualify`
|`slurm-qualify.yml`: `workflow_dispatch` only, with `dut`, `items` and
`sim-jobs` inputs
|Installs a single-node Slurm with accounting on the runner and runs the
selected tests through `--executor slurm --mem-mb 2000 --walltime 30`; the
result gate also requires every leaf to carry a Slurm job in a terminal
state. A live check of the Slurm driver for a change to the driver, the
registry's Slurm table or the worker; one node adds latency and no capacity,
so it is not a tier and no pull request runs it.

|`nightly`
|`regress.yml`: `schedule` Sunday to Friday at 18:00 UTC, or
`workflow_dispatch` with `tier=nightly`
|One random seed per test of each DUT's regression group at `--sim-jobs 4`:
DTP `all`, SEP `cpu_stub`, SMU `hosted`, SMC `hosted`, and the IP-level
benches' `all` groups (the three `cross_trigger` benches, the four UART-family
benches, `system_timer_octs` and `scrambler`). No coverage.
Nightly is not a merge gate; a red nightly run is a triage signal.

|`weekly`
|`regress.yml`: `schedule` Saturday at 18:00 UTC, or `workflow_dispatch`
with `tier=weekly`
|The regression the dashboard publishes, one random seed per test on every
row and no coverage: DTP `all`, SEP `cpu_stub`, SMU `hosted`, SMC `hosted`,
and the IP-level benches' `all` groups. A second SMC row
(`label: rtl_issue`) runs the `rtl_issue` reproducers: every leaf carries
`expect_fail` (<<runner-expected-failures>>), so the row is green while the
filed defects stand and red the week one is fixed. `--sim-jobs` follows the
runner core count. The coverage regression runs on the licensed simulator
flow outside hosted CI; the coverage-instrumented Verilator models of DTP,
SEP, and SMU do not fit a hosted job.
|===

Pull requests never run the `all` regression; `sim.yml` carries only the
smoke matrix, so PR cost stays bounded by the smoke group. The larger-runner
promotion is a repository variable rather than a workflow edit:

[source,bash]
----
gh variable set DV_LARGE_RUNNER --body ubuntu-latest-16-cores
----

A label with no matching runner does not fail fast (the job queues until it
times out), so the default stays the always-present standard runner.

[[runner-ci-budgets]]
=== Budgets, concurrency, and retention

Every job carries a `timeout-minutes` budget: 60 for each smoke job, and
360, the hosted runner's cap, for every nightly and weekly job; the
scheduled tiers are bounded by that cap alone. A job that exceeds its
budget is cancelled by the hosted runner;
`run_dv.py` receives the cancellation as a signal and, when its handler
completes, writes the interruption checkpoint and the run-level JUnit
testcase, and otherwise its last `UNKNOWN` checkpoint stands
(<<runner-interrupted-checkpoints>>). The artifact upload runs regardless of
the outcome, so a cancelled job publishes non-passing evidence either way.
Inside a job, each leaf is bounded by its resolved leaf timeout, and
a leaf that exceeds it grades `TIMEOUT` without ending the run.

A Verilator cache miss adds the from-source build to every job of that run
that starts before one of them has saved the cache: the composite action
keys its cache on the Verilator version, the runner operating system, and
the architecture, so the first run after a version change pays the build in
every row that starts together, and a coverage row pays it before its
coverage-instrumented model build.

Concurrency is per workflow: a pull-request push cancels the smoke run it
supersedes, and a push to `main` never cancels a run in progress. The two
regression crons and each dispatched tier are separate groups that are never
cancelled: a dispatched tier runs beside a scheduled one and queues only
behind an earlier dispatch of the same tier. Exactly one scheduled tier runs
per day.

Retention: smoke and nightly run trees for 14 days, weekly run trees for 30,
the normalized dashboard bundle for 90; the `dv-dashboard-data` branch keeps
the trend history trimmed to 90 points and each DUT's weekly archives to 90
runs. The runner has
no automatic retry in hosted CI; a leaf is graded on its single attempt, and
the weekly digest's flaky list names a test whose seeds disagree within a
run, which at one seed per test is only a test with its own `reseed` value.

Each job writes an explicit per-run directory
(`build/ci/runs/<dut>/<tool>/<tier>/<run-id>`; the workflow run id keeps the
recorded run identity unique for downstream trend history), gates on the
native run-level `result.json` (`schema_version` 1, matching `flow`/`tool`,
`status` `PASS`). A caller that sets the action's `coverage` input adds
coverage evidence to that gate; no hosted row does. The
action uploads `dv-run-<dut>-<tool>-<tier>` (`-<label>` appended for a
labelled row), including on failure, for the retention periods in
<<runner-ci-budgets>>.
Explicit run directories never create or update the `latest`
symlink.

=== Framework-aware CI matrices

Hosted invocations omit `--framework`, so every DUT runs its default
framework (cocotb) — adding a second framework to a DUT changes
nothing for existing jobs. The canonical invocation for a licensed SV-UVM
job selects a group under the UVM view. A group whose cocotb-only members
declare `uvm = false` runs its UVM-implemented subset with no flag; a DUT
whose scenarios lack a `uvm` entry rides `--skip-unimplemented`:

[source,bash]
----
python3 tools/dv/run_dv.py --dut dtp --framework uvm --items smoke
python3 tools/dv/run_dv.py --dut dtp --framework uvm --items jtag2axi
python3 tools/dv/run_dv.py --dut ocah_axi_vip --framework uvm --items smoke
python3 tools/dv/run_dv.py --dut sep --framework uvm --items smoke --skip-unimplemented
python3 tools/dv/run_dv.py --dut smc --framework uvm --items smoke --skip-unimplemented
----

Each (DUT, framework) pair a DUT implements is one _framework view_: the DUT
resolved with that framework selected. CI matrices should enumerate views
from configuration instead of hardcoding DUT names: `--list --json` emits one
entry per view with its tool set, default tool, and license need, so
a licensed UVM job selects `.duts[] | select(.framework == "uvm")` and a DUT
joins that matrix by declaring `[frameworks.uvm]` and adding module bindings
— no CI edit. Every entry carries `mode` (`sim` or `formal`) and
`available`; a formal view whose site-named config is absent is listed with
`available: false`, its `path`, and a `reason`, so a formal job selects
`.duts[] | select(.mode == "formal" and .available)`. `--list --dut <dut>
--json` additionally carries the per-scenario binding matrix
(`tests.<name>.bindings`) and per-framework implemented counts for
dashboards. `--validate-configs` validates every framework view a DUT
implements and every available formal view, so a broken UVM overlay or
formal config fails config validation even in cocotb-only CI.

=== Qualification and limits

`--validate-configs` proves config schema consistency across all DUTs; it
does not qualify a simulator. Qualification evidence for a DUT/tool pair is a
successful `sim` or `regress` workflow run at head — link the run URL when
promoting a pair into the CI-run tier.

`--cores`, `--mem-mb`, and `--walltime` are executor metadata only and
enforce nothing locally or in CI. The enforceable controls are the job
`timeout-minutes` each caller sets (60 for smoke; 360 for the regression
tiers), the pinned cached Verilator build, and the `--sim-jobs`/`--build-jobs`
fan-out.

== Troubleshooting

=== A different DUT's config blocks the run

Normal execution validates every selectable DUT, its simulation views and
any available formal view, before resolving the requested one. Run
`--validate-configs` and fix every reported failure; a stale registry entry
or config can block an otherwise unrelated DUT. An unavailable site-named
formal config does not block anything.

=== The selected tool is missing

Run:

[source,bash]
----
python3 tools/dv/run_dv.py --doctor --dut <dut> --tool <tool>
----

`--doctor` checks configured binaries on `PATH` (the launcher's first token
when the site layer wraps the tool, after sourcing the tool's `setup_hook`),
supported Python packages, and the presence count of configured license
environment variables, and names the file that supplied each tool
(<<runner-site-layer>>). Each found tool's row is followed by the release its
binary reports (a tool the site layer wraps in a `launcher` reports none); a
required tool below the `min_version` its registry table sets, as
`verilator` does, fails the same way an absent one does
(<<runner-environment-matrix>>). When the
required tool is absent and needs a license, the result points at the
`(licensed)` marking in `--list`. For a cocotb
DUT it also imports every testlist module, or with `--items` or `--tag` the
modules of that selection, in a child interpreter whose
`PYTHONPATH` is rebuilt from the DUT config exactly as a run rebuilds it
(`test_dir`, `python_root`, `python_paths`, and the generated namespace
bridge), so an import failure reported here reproduces in a real run and an
import that only works with extra ambient packages does not mask one. The
probe assigns the simulation-time `cocotb.log` attribute the way cocotb's
initialization does before importing test modules, so modules that touch it
at import scope are not false-flagged. Modules are probed 20 per child
interpreter with a 120-second budget per batch; a batch that exceeds it is
retried once with twice the budget, and only a batch that exceeds both is
reported as failed. `OCAH_DOCTOR_PROBE_TIMEOUT=<seconds>` replaces the
per-batch budget on a slow filesystem. The
shared VIP check imports `ocah_axi_vip` from its in-repo root
(`hw/common/dv/vip`); no `pip install` of `hw/common/dv` is required. The
doctor does not check out a license or comprehensively probe Bender, Make,
coverage utilities, or every firmware toolchain.

=== The doctor fails on modules the run would never import

An unscoped `--doctor --dut <dut>` imports every module in the DUT's
testlist, including modules whose dependencies a run of your selection never
touches; the `sep` modules that import the private submodule are the case a
public clone meets (<<runner-environment-matrix>>). Add the selection to the
doctor:

[source,bash]
----
python3 tools/dv/run_dv.py --doctor --dut sep --items smoke
----

The `test modules` row then covers the tests the same `--items` and `--tag`
select, before a run's framework-binding and `--tool` filters drop any, and
names the selection; an unscoped failure prints the hint, and a selection the
testlist cannot resolve is a usage error. A module that fails inside the
selection fails the run too.

=== A zero-return-code simulation is UNKNOWN

Inspect the leaf `result.json` fields `reason` and `parser.evidence`, then check
the recorded log and `results/results.xml`. A missing, empty, or malformed
structured result and absent positive log summary correctly fail closed.

=== A formal run with exit code zero is FAIL or UNKNOWN

The formal stage is graded from the backend's task status lines, status
files, and JUnit reports, or from the app's summary file, never from the exit
code (<<runner-formal-grading>>). Inspect the stage record's `reason`,
`parser.evidence`, and `formal.tasks`. `UNKNOWN` with "no formal task
evidence" means the log carried no task status line and the stage directory
held no task work directory: check the launch template's `--prefix` and the
app's `cwd`. <<runner-formal-results>> lists the next step for every
status.

=== An explicit sim-only run cannot find build or firmware output

`--stage sim` does not add `flist` or firmware compilation. A parallel cocotb
scheduler may insert a model prebuild, and a cocotb simulation may build its
model, but the generated filelist and required firmware outputs must already
exist. Run the missing preparation stages first, or use the implicit path.

=== Coverage was collected but no report appeared

With explicit `--stage sim --cov`, run `cov_merge` and `cov_report` explicitly
against the same run directory. Verify that the selected tool's coverage
utility (`verilator_coverage`, URG, or IMC) is available.

=== A run's coverage grade failed on the policy

The `cov_report` record is `ERROR` with a `config_error` bucket and
`cov/report/summary.json` is absent: a `pass:[[[holes]]]` entry matched a different
number of points than `expected_matches`, or an accepted waiver matched a
covered point. Correct the entry and run `--run-dir <dir> --waive`; the report
tool does not need to rerun. See <<runner-waive>>.

[[runner-current-limitations]]
== Limitations

The following behaviors are not part of the runner contract:

* A cluster executor keeps the coordinator in the foreground: there is no
  detached mode and no scheduler-managed build. First attempts go out as job
  arrays where the executor's templates allow it and as one job per attempt
  otherwise; retries and wave-debug reruns are always single jobs. The target
  build runs on the submitting host, and every worker verifies its ready
  marker before it simulates. Queue, core, memory, and wall-time flags reach
  a cluster job's submit command; the local executor records them and
  enforces nothing.
* The runner writes no `run.json` and has no background execution or job
  lifecycle/status commands.
* `--dry-run` avoids backend execution and result writes, but bootstrap may
  still provision the locked `uv` environment and update the generated
  namespace bridge.
* Configured test/run-mode timeouts apply to simulation leaves. CLI
  `--timeout` reaches many subprocess stages, but Bender filelist generation
  and in-process Verilator/Xcelium cocotb build stages are unbounded.
* An explicit `--run-dir` is reused as supplied, is not made unique, and does
  not update `latest`. Choose an empty directory unless performing the
  documented coverage replay.
* `--max-failures 0` satisfies the stop condition immediately and therefore
  skips every scheduler leaf. The aggregate reports `PASS` and exits `0`
  despite running no tests; the record says so (`tests.completed = false`,
  `leaves_run = 0`, `pass_rate = null`). Use a positive threshold.
* Exact waveform range enforcement is limited to Xcelium SHM and VCS FSDB/VPD.
* A DV root that carries a formal config and no sim config is not a DUT;
  formal views attach to selectable DUTs.
* Hosted CI runs no formal job and no formal result reaches the dashboard;
  formal mode is a developer-host flow (<<runner-formal>>).
* Formal results have no waiver mechanism; coverage waivers apply to
  coverage bins only.
* `--doctor` compares a tool's release against `min_version` only where its
  registry table sets one (`verilator`); the other rows report a release
  without judging it, and Bender's release is recorded per run in
  `result.json` rather than probed.
