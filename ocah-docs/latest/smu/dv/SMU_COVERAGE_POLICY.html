1. SMU coverage targets and closure policy

This chapter defines what the SMU release group is graded on and how a hole is waived. It does not install a CI fail-on-hole gate; that gate needs a measured database first.

Field Value

Release group

--dut smu --items hosted (live size in the Release Qualification section of hw/sys/smu/dv/docs/SMU_VPLAN.adoc)

Metrics

the runner’s native families: user (the cov/sv cover properties) on Verilator; toggle and assertion on VCS, where toggle is every bit of every port of smu_wrapper in both directions after cov/config/vcs/smu_wrapper_toggle_exclusions.el has left the population, and assertion is where urg reads the same cover properties

Numeric target

VCS toggle 80 percent effective and assertion 80 percent effective, both gated by cov/config/vcs/smu_wrapper_coverage_policy.toml (toggle 96.03/95.93 raw/effective and assertion 84.11 on the hosted group when this chapter was written); user 95 percent effective on Verilator, reported and not yet gated

cov/sv/ carries ten cover-property modules, 111 points in all; the counts are the OCAH_FCOV_COVER invocations in each file. tb/tb_wrapper_top.sv instantiates all ten, and 107 points elaborate on its single target, compile_smu_chiplet, which has SEP present: the four inside g_nosep generate blocks exist only on a SEP=0 elaboration, which this package does not build.

1.1. Public versus commercial evidence

Path What it collects Where it runs

Public Verilator

line / expr / user over smu_wrapper_cov_scope.vlt, which drops everything the wrapper instantiates at compile time — the SMU block, the SEP, SMC and DTP trees, the hw/top integration shells, vendored and generated RTL. Toggle is not collected on Verilator, as the DTP set does not collect it: coverage_off -file does not apply to a source file whose last line has no newline, and the vendored and hw/common files in that state would carry subsystem toggle points into the wrapper’s database

weekly --cov on the large runner (regress.yml). Nightly does not collect.

Commercial

toggle / code / assertion databases under the licensed flow. smu_wrapper_cov_scope.hier drops the same trees and the bench’s AXI egress glue at compile time, -cm_tgl portsonly keeps toggle on the wrapper’s ports and -cm_noconst leaves tied-off nets out; cov/config/vcs/smu_wrapper_toggle_exclusions.el names, with a reason per class, the fields that are not the wrapper’s to toggle, and the policy applies it at report time. cov/config/vcs/smu_wrapper_coverage_policy.toml floors toggle and assertion at 80 percent; run_dv.py grades both and prints them on its coverage line (see cov/config/vcs/README.md)

not a public CI job; not a substitute for the public weekly

The DUT is an integration shell with no logic of its own: smu_wrapper.sv is three instances and their wiring. What it owns is its ports, so it is graded on toggle rather than line or expression, on the same per-bit, both-directions definition and through the same runner family as every other DUT. The exclusion file is the only place where the population is shaped, and every class in it carries the reason. A Python smu_fcov.py sampler is not the release metric and is not a gate.

1.2. Structural OUT versus a waiver hole

Three mechanisms. Do not mix them.

Kind Effect Carrier

Structural OUT, by source file

the point never enters the database

coverage_off file patterns (hw/sys/smu/rtl, SMC, DTP, SEP, hw/ip, hw/common, CPU cluster, TB, vendor trees the file pattern can reach)

Structural OUT, by elaboration

the point is not elaborated, so it never enters the database and no waiver names it

the SepPresent parameter and its g_sep generate blocks in cov/sv/*_fcov.sv; a point whose observable exists only with SEP elaborated is absent from a SEP=0 build; the wrapper’s single target elaborates SEP, so every g_sep point exists there

Waiver hole

the point exists and is not hit

with the fields below

A vendor site that coverage_off cannot name (hierarchy under .u_smc / .u_dtp) is a hole with category = "out_of_scope" and disposition = "exclude_scope". Write it only from a real database: expected_matches is a hard count, and a guessed count is a ConfigError on the first run.

1.3. Waiver fields

Every row must carry:

  • tool, metric_family (the family that database holds: user and the wrapper’s own toggle), hierarchy or file selector

  • category (one of the runner’s hole categories, such as missing_stimulus, config_disabled, out_of_scope or unreachable)

  • disposition

  • owner

  • review_date

  • issue when the disposition is actionable

max_unclassified_points = 0 is the fail-on-new-hole knob. It is not set here; it is set together with the threshold, from a measured weekly --cov database.

A waiver reaches a finished run without a simulator: python3 tools/dv/run_dv.py --dut smu --run-dir <run> --waive re-grades the run’s report against this policy and rewrites its coverage grade in place. A dispatch of dashboard.yml with the weekly’s regress run id does the same for the published weekly. Both are described on the runner and dashboard pages under tools/dv/doc/.
