Design-for-Debug (DFD) and Core Logic Analyzer (CLA)

The SMC integrates a Design-for-Debug (DFD) subsystem that observes internal activity, triggers on programmable conditions, and captures trace, all on-chip and without external instrumentation. Its core is a Core Logic Analyzer (CLA) that watches a configurable debug bus, evaluates programmable events, and fires actions — an interrupt, a clock stop, a cross-trigger, or a trace capture — when those events occur. Trace storage uses the connected external sink-memory interface. Several capabilities of the generic DFD block are not connected in SMC, as detailed below.

Figure 1. DFD reference architecture

Figure 1 shows the full tt-dfd block. SMC does not connect the instruction trace (N-Trace) input; its CLA and debug-signal trace paths provide the observation functions described here.

Key features include:

  • A programmable debug bus that routes internal signals of interest to the analyzer under software control

  • An event engine supporting signal-match, edge, transition, ones-count, any-change, and counter events

  • Event-action pairing that binds detected events to system actions

  • Per-trigger snapshot of the debug bus and status flags identifying which pair fired

  • Cross-trigger exchange with the rest of the debug infrastructure

  • Trace capture through the external sink-memory interface

Figures and tables: Figure 1.

1. Debug Bus

The analyzer operates on a debug bus: a fixed-width vector of internal signals sampled every cycle. A selection fabric chooses which internal signals are driven onto the bus, so a single analyzer can be pointed at different parts of the design without RTL changes. Software selects the observed signal set, then programs the event engine against the resulting bus value.

2. Core Logic Analyzer

The CLA is organized as a set of nodes, each holding several event-action pairs (EAPs). An EAP binds one or more events, computed from the debug bus, to one or more actions taken when those events occur. The event engine evaluates several event types in parallel (Table 1).

Table 1. SMC CLA event types
Event Description

Signal match

Fires when the masked debug bus equals a programmed value (debug_bus & mask == match). Several independent match events are available.

Edge

Fires on a rising or falling edge of selected debug-bus signals.

Transition

Fires when a masked subset of the bus moves from a programmed value A to a programmed value B.

Ones count

Fires when the population count of a masked subset equals a programmed value.

Any change

Fires when any signal within a masked subset changes.

Time match

Unavailable in this integration. Its timestamp input is tied to zero. The comparator requires a nonzero match value, so the event cannot fire; it does not use the local CLA timestamp register.

Counter

Counts cycles following an event match and fires when the count is reached; a small pool of counters is available for measuring intervals or deferring an action.

When an EAP fires, a status flag records which pair triggered — for example, so an interrupt handler can identify the source — and a snapshot register latches the debug-bus value at the moment of the trigger for post-mortem inspection. EAPs are enabled together once programming is complete, so a partially programmed pairing never triggers.

3. Actions and Cross-Triggering

An EAP can drive one or more actions:

  • Debug interrupt — raise a non-maskable interrupt to the CPU.

  • Clock stop — halt clocks to freeze the design for inspection.

  • GPIO toggle — the generic block provides this action, but SMC terminates it on an unused local signal; it does not drive a pad.

  • Cross-trigger out — signal other debug blocks that a local event occurred.

  • Trace capture — hand the event to the trace subsystem.

  • Custom actions — reserved outputs for design-specific use.

Cross-trigger inputs let events elsewhere in the system arm or fire local actions, and cross-trigger outputs propagate local events outward, so debug conditions can be correlated across blocks rather than observed in isolation.

4. Trace

The configured trace sink uses external memory request/response ports. The optional trace AXI master has unconnected request outputs and tied-low response inputs, so it cannot stream trace over the SMC fabric.

SMC selects local CLA timestamp scheme 0, advanced by the wrapper’s reference clock-derived time_tick. This local counter is distinct from the generic i_timestamp, reference timestamp, and OCTS timestamp inputs, all tied to zero. The integration does not provide the advertised global timestamp alignment through those inputs. In particular, the time-match event consumes the tied-off timestamp rather than the running CLA timestamp register.

5. Interrupts

The SMC interrupt table lists the two CLA-driven sources. See Interrupts.

  • CLA clock stop — asserted while the CLA has stopped clocks.

  • CLA debug interrupt — the debug interrupt raised by a CLA action.

6. Register Map

The CLA counter values and timestamp fields are software-writable. Software writes take priority over simultaneous hardware updates; later hardware updates can advance or clear them according to their configured controls. The sink’s trDstRamWPHigh register likewise accepts software writes. Treat these as live read/write state when programming or testing them, not read-only status.

The generated smc_cla map is the programmer view of this aperture (see Memory Map ).
