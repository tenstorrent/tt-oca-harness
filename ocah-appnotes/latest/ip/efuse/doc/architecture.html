Architecture

The eFuse IP provides secure One-Time Programmable (OTP) memory management with foundry-agnostic design. The layered architecture separates security control logic from foundry-specific implementation details, enabling deployment across different OTP technologies while maintaining consistent security characteristics and software interfaces.

Interface Controller

The eFuse Interface Controller (efuse_interface_controller.sv) provides dual-path access control with security policy enforcement.

Access Paths

  • SMC AXI4-Lite Interface: Functional access for normal system operations

  • JTAG AXI4-Lite Interface: Debug access for manufacturing test and development

Destination Endpoints
Endpoint Description

Shadow Registers

High-performance boot-time caching for rapid access without OTP timing constraints

eFuse CSR

Control and status registers for read, program, and verification operations

MMR

Memory-Mapped Registers for SEP security tokens with specialized access control

Interface SHIM CSR

Configuration registers for foundry-specific timing adaptation. Implemented by the adopter, but always accessed via the interface controller.
Shadow Register Subsystem

The shadow register subsystem accelerates OTP access by caching eFuse contents at boot time. On power-up, a dedicated FSM automatically issues a bulk read command (with access_length_words set to cover the full eFuse bank), copying all OTP data into the shadow registers. This ensures the shadow registers are fully populated and always synchronized with the OTP state at each boot.

Features

The feature list for the shadow register subsystem is as follows:

Feature Description

Capacity

Configurable (default: 24576 bits / 3KB, 768 × 32-bit words), set via the SHADOW_REG_BITS parameter

Initialization

Automatic boot-time loading via Fuse Sense FSM

Access Control

Multi-tier hardware and software lock mechanisms

Data Consistency

Maintains synchronization with underlying OTP storage upon each power-on reset
State Machine Architecture

The read interface FSM (efuse_read_interface.sv) operates in a simple two-state sequence, transitioning from idle to waiting for a response as it handles on-demand eFuse reads that fall outside the shadow register cache. This mechanism works alongside the shadow subsystem, providing direct access only when necessary, and actively reports status to support robust error handling and retry logic.

The program interface FSM (efuse_program_interface.sv) enforces the write-once nature of OTP hardware, ensuring that programmed data cannot be altered once set. It supports write-and-verify procedures for reliability, integrating verification steps that check programmed values against intended data, and fully blocks any unauthorized overwrites to maintain data integrity.

Parameterized Command Typedefs

The fuse command request/response structs exchanged between the controller and the SHIM are not declared with fixed types. Instead, they are generated from parameterized preprocessor macros defined in efuse_typedef.svh. This keeps the command interface technology-agnostic: each integration supplies its own address, data, access-length, and command types, while the macros guarantee a consistent struct layout and field ordering across all OTP variants.

Macro Generated Type Purpose

EFUSE_COMMAND_REQ_T

fuse_command_req_t

Controller-to-SHIM command request

EFUSE_COMMAND_RESP_T

fuse_command_resp_t

SHIM-to-controller command response

The request macro is parameterized over the struct name plus four payload types (addr_t, data_t, access_length_words_t, command_t), allowing the controller to size the address space, transfer length, and command encoding to match the target OTP technology:

`define EFUSE_COMMAND_REQ_T(fuse_command_req_t, addr_t, data_t, access_length_words_t, command_t)  \
  typedef struct packed {                                       \
    addr_t                    address;             // Target address       \
    logic                     program_data;        // Data to program (1'b1) \
    access_length_words_t     access_length_words; // Transfer size        \
    command_t                 command;             // Command type         \
    logic                     valid;               // Request valid        \
  } fuse_command_req_t;

The response macro is parameterized over the struct name and the data_t read-data type:

`define EFUSE_COMMAND_RESP_T(fuse_command_resp_t, data_t)       \
  typedef struct packed {                                       \
    data_t              data;       // Read data                \
    logic               status;     // Operation status         \
    logic               valid;      // Response valid            \
  } fuse_command_resp_t;

A typical instantiation expands both macros with the integration’s local types:

`EFUSE_COMMAND_REQ_T(fuse_command_req_t, addr_t, data_t, access_length_words_t, command_t)
`EFUSE_COMMAND_RESP_T(fuse_command_resp_t, data_t)

Interface SHIM Layer

The Interface SHIM (efuse_interface_shim.sv) is an example, foundry-specific implementation of the custom fuse command interface. Its role is to translate the controller’s generic commands into the signaling expected by a particular OTP macro; in this reference version the macro-side interface is APB, but a real integration would replace this with the foundry’s native signals.

The SHIM decodes three command types from the controller:

  • Read — fetch one or more words from the bank.

  • Program — burn new bits into the bank.

  • Program/read-back — program, then read back to verify success.

It implements these with dedicated read and program FSMs that sequence the macro-side transactions and return a fuse_command_resp_t to the controller. Foundry-specific timing and configuration (for example, program pulse widths) are exposed through the SHIM Control CSRs, accessed over the fuse_bank_ctrl AXI4-Lite interface.

eFuse Bank Model

The eFuse bank model (efuse_bank_model.sv) is a reference, simulation-only stand-in for the real foundry OTP macro. It is a 3KB (768 x 32-bit word) store fronted by a standard APB interface, and it emulates the set-once behavior of real OTP so the controller and SHIM can be exercised end-to-end without silicon. In a production integration it is replaced by the actual foundry macro driven by the SHIM.

Access Permissions and Security

Access control is layered for defense in depth: per-field permissions are described by efuse_field_map_i, lock state is enforced by the eFuse guard (efuse_guard.sv), security-disable tokens are validated, and access can additionally be gated by the chip lifecycle state.

Each eFuse field is described by a rule_t entry that pairs an address range with a 4-bit lock permission field:

typedef struct packed {
    logic [EFUSE_FIELD_MAP_IDX_WIDTH-1:0] idx;        // Field index
    logic [3:0]                           lock;       // Permission bits
    logic [31:0]                          start_addr; // Field start address
    logic [31:0]                          end_addr;   // Field end address
} rule_t;

The lock field encodes read, write, and secure-test-mode permissions for the field:

Bits Function Encoding

lock[0]

Read

0 = readable, 1 = read-locked

lock[2:1]

Write

00 = unlocked, 10 = set-only (1’s may be added, never cleared), 11 = write-locked

lock[3]

Secure test mode

0 = unrestricted, 1 = access requires secure test mode
Hardware vs. Software Locks

The same permission semantics are reached through two independent mechanisms, and the guard enforces whichever is more restrictive:

Property Hardware Lock Software Lock

Source

Permission bits fused into the eFuse array (the field map reflects the programmed values)

Runtime writes to the LOCKS CSR (write-1-to-set)

Persistence

Permanent — backed by one-time-programmable bits and cannot be cleared once set

Volatile — retained only until the next system reset

Reversibility

Irreversible by any means

Cleared by reset, allowing the field to be re-opened

Typical use

Final production lockdown of provisioned secrets

Temporary protection during boot, debug, or staged provisioning

Because software locks are write-1-to-set, firmware can tighten access at runtime but can never loosen a restriction without a reset; hardware locks cannot be loosened at all. On top of these per-field locks, sensitive fields can be further gated by the chip lifecycle state and by secure test mode (lock[3]), so a field may be accessible in one operational mode and fully blocked in another even when its read/write bits are clear.

For sensitive functions, such as those governed by the MMR registers, the system enforces token-based security. Only by providing the correct 256-bit tokens, such as the RMA SOP Token for state transitions, the RMA Chiplet Token for chiplet-specific operations, or the Security Disable Token to override protections, can access to these resources be granted.

Security Disable Bypass Mechanism

The eFuse interface controller supports a security disable bypass mechanism via the security_disable_i input signal. This mechanism is primarily used for test and debug scenarios where the automatic fuse sensing sequence needs to be bypassed.

Behavior when security_disable_i is asserted:

Behavior Description

FSM Bypass

The automatic fuse sensing state machine is bypassed and does not issue read commands to the physical eFuse bank.

Shadow Register Output

Shadow register values are output directly to downstream logic via shadow_regs_o, regardless of fuse_sense_done status.

Shadow Register Loading

Shadow registers are not loaded from fuse command responses; they retain their reset values (all zeros for SMC).

APB Access

APB access to shadow registers is permitted without waiting for fuse_sense_done completion.

Reset Values

When the system is in reset state with security_disable_i asserted, shadow registers are initialized to zero (default reset value for SMC).

For SMC, the internal security disable signal is directly driven by the security_disable_i input port.

The access control mechanism uses an AXI-Lite demux that routes blocked requests to an error slave. When a request is blocked, the error slave returns an error response with data value 0xbadcab1e.

Chiplet ID Exception:

Even in PROD or RMA_SOP states, JTAG read access to the chiplet ID and package ID registers is permitted. This allows identification of the chip for manufacturing and field returns without exposing sensitive eFuse contents.

Secure Test Mode (secure_tm_i)

The eFuse interface controller supports a Secure Test Mode via the secure_tm_i input signal. This mode provides additional protection for sensitive security assets during secure manufacturing test operations.

Behavior when secure_tm_i is asserted:

Behavior Description

Fuse Command Blocking

All fuse commands to the physical eFuse bank are blocked. The guard logic filters incoming requests and returns default responses.

RMA Token Protection

RMA SOP and RMA Chiplet tokens are disconnected from shadow register outputs (set to zero), preventing token exposure during test.

Write Lock Contribution

Secure test mode contributes to write lock status, preventing shadow register modifications.

Response Behavior

When fuse commands are blocked, default response values (all zeros) are returned to requesters.

SMC Configuration:

For SMC, secure_tm_i is tied to logic 0, meaning Secure Test Mode is not active during normal SMC operation. This signal is primarily relevant for SEP where sensitive RMA tokens must be protected during manufacturing test flows.
