Mailbox Unit

1. Overview

This document specifies the Mailbox Unit hardware IP functionality. The Mailbox Unit provides FIFO-based bidirectional communication channels for inter-processor or inter-chiplet communication using AXI4-Lite interfaces. It enables efficient data exchange between processing elements through dedicated hardware channels with minimal software overhead.

2. Description and Features

The Mailbox Unit enables secure, FIFO-based, bidirectional communication between processing elements or chiplets in multicore systems. Each configurable mailbox instance consists of paired inbound and outbound channels, allowing simultaneous data transfer with a 64-bit data path. Multiple independent mailbox pairs are supported, each equipped with dedicated control registers, status monitoring, and programmable interrupt thresholds.

The architecture uses standard AXI4-Lite interfaces for integration and provides robust error detection, reporting, and software-controllable FIFO flushing. Channel depth is adjustable per instance to suit system needs, while hardware minimizes software overhead for efficient, low-latency data exchange.

3. Architecture

The Mailbox IP provides inter-processor and inter-chiplet communication through a register-based interface. A single AXI4-Lite slave port is demuxed into one register aperture per mailbox direction, and each mailbox pair owns the two FIFOs that carry data between its two apertures.

3.2. Address Space

The architecture supports up to 64 mailbox instances (32 bidirectional pairs):

  • Total Space: 2 × MAILBOX_SIZE × NUM_MAILBOXES, decoded from a port that is ADDR_WIDTH bits wide

  • Data Width: 64 bits

  • Per-Aperture Space: 0x800 bytes (2KB)

  • Decoding: Address bits above $clog2(MAILBOX_SIZE) select one of 2 × NUM_MAILBOXES apertures

The 64-bit data width handles addresses, data payloads and status information without multi-word transfers. The 2KB allocation per aperture leaves the ten registers sparsely mapped; offsets above the register map are unmapped rather than aliased.

3.3. Internal Structure

The unit is an axi_lite_demux in front of NUM_MAILBOXES mailbox instances. Each mailbox instance has two AXI4-Lite slave ports, one per aperture, and holds two message FIFOs of MAILBOX_DEPTH entries each. The FIFOs are cross-coupled between the two ports: the push side of one port is the pop side of the other. The FIFOs are internal to the IP; there is no external FIFO interface.

3.4. Transaction Processing

AXI4-Lite transactions follow this flow:

  1. Aperture Decode: The demux selects an aperture from the address bits above $clog2(MAILBOX_SIZE), relative to MAILBOX_BASE_ADDR

  2. Register Decode: The mailbox slave port decodes the offset within the aperture into one of the ten registers

  3. FIFO Access: WRITE_DATA pushes the port’s write FIFO, READ_DATA pops the port’s read FIFO; full and empty conditions set the error flags described in the Error Handling table

  4. Response: The B and R responses are emitted through spill registers, giving one cycle of latency and keeping the response path free of combinational paths from the request

3.5. Bidirectional Communication

Each mailbox pair provides two register apertures, conventionally used as an outbound and an inbound direction. The two are not independent storage: they share the same pair of FIFOs, so WRITE_DATA in one aperture is what READ_DATA in the other aperture returns. Both apertures hang off the same AXI4-Lite slave port, so a local agent can drive either end; the direction naming reflects intended use, not an access restriction.

Separate apertures give each direction its own thresholds, status, error flags and interrupt output.

3.6. Clock and Reset

The mailbox uses a single clock domain for integration reliability:

Signal Type Description

clk_i

Single clock

Unifies functional logic and AXI4-Lite interface

rst_ni

Asynchronous, active-low

Primary reset, initializes all mailbox state

test_en_i

Test enable

DFT support

No internal clock domain crossings eliminates CDC complexity. Single clock domain simplifies timing analysis and integration verification.

3.7. Interrupt Architecture

The mailbox provides independent interrupt outputs for each mailbox instance:

  • inbound_interrupt_o[NUM_MAILBOXES-1:0]: Inbound communication events

  • outbound_interrupt_o[NUM_MAILBOXES-1:0]: Outbound communication events

Separate inbound/outbound interrupts reflect different processing requirements. Inbound interrupts indicate incoming commands requiring immediate processing; outbound interrupts indicate successful transmission or buffer availability.

The following table reports the interrupt sources.

Source Description

Write Threshold

FIFO fill level exceeds configured threshold (proactive buffer management)

Read Threshold

FIFO data available for efficient retrieval scheduling

Access Error

Write to full FIFO or read from empty FIFO; both set the same error interrupt bit (fault detection)

Each interrupt output aggregates these sources and is level-triggered and active high. Threshold-based interrupts reduce polling overhead; error interrupts enable fault recovery and diagnostic analysis.

4. Interface

The Mailbox Unit exposes a single struct-based AXI4-Lite slave port. All mailbox apertures are decoded from this one port by an internal demux.

Sets read_error in ERROR_FLAGS and the error bit in IRQS; returns 0xFEEDDEAD with SLVERR

Read returns 0 with SLVERR; write is ignored with SLVERR

Read of ERROR_FLAGS

Both flags clear on read; an error raised in the same cycle as the clearing read is retained

Triggered if enabled via IRQEN register

Address Space Characteristics:

  • Per-Aperture Size: MAILBOX_SIZE, 2KB (0x800)

  • Total Address Space: 0x20000 bytes for 32 pairs

  • Decoded Address Span: 17 bits for 32 pairs; the slave port itself is ADDR_WIDTH bits wide (32 in the SMC and SEP integrations)

  • Maximum Mailboxes: 32 pairs (64 apertures)

The two apertures of a pair are the two ends of the same pair of FIFOs: WRITE_DATA in the outbound aperture pushes the FIFO that READ_DATA in the paired inbound aperture pops, and vice versa. Both ends are reachable from the same AXI4-Lite slave port.

5.2. Per-Mailbox Register Map

Within each 2KB mailbox aperture, registers are organized as follows. Offsets are spaced by DATA_WIDTH/8, so they are 8 bytes apart in the 64-bit configurations used today. The generated detailed register map below is authoritative for offsets, widths, access, and field descriptions. The CTRL flush bits are pulses rather than stored state, so reads return zero with an OKAY response.

Offsets 0x50 and above within an aperture are unmapped and respond SLVERR.

5.3. Address Examples

For mailbox pair N, the outbound aperture begins at BASE + N * 0x1000; the inbound aperture begins 0x800 bytes later. A register address is the aperture base plus the generated register offset. For example, in pair zero, READ_DATA is at BASE + 0x8 outbound and BASE + 0x808 inbound.
